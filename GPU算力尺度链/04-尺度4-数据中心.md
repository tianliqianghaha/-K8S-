# 尺度 4 · 数据中心 / 园区

## 0. 本篇对象

> **原样题面**：按照这种从小到大的尺度，给我每个尺度详细介绍一下。我的中心是学习。你要给我介绍学习的重点。比如学传统网络的最大重心就是 IP 和路由，像这种形式，你在每个层级章节把重心罗列并且详细讲解。

**本篇讲尺度链第 4 格：数据中心内部与园区级的算力和网络。** 主角是 DCI/算力专线、算力池化、集群调度。物理范围从一个集群向外，到单个数据中心或园区边界为止。

这一格是**过渡带**：往上接机内的高性能网络，往下接跨域的算力网络。

---

## 1. 学习重心（先罗列）

对标"学传统网络 = 学 IP + 学路由"：

```text
学数据中心 = 学「池化」 + 学「调度」

重心一：池化 —— 把一堆异构的机器和卡，变成一个统一的算力资源池
重心二：调度 —— 这个池子里的资源，分给谁、什么时候分、怎么分

其余都是配角：
  DCI / 算力专线 —— 连接方式，理解边界即可
  交换机 / 布线   —— 工程细节
  容器技术       —— 池化的实现手段之一
```

**为什么是这两个**：因为到了这一格，问题变了。尺度 1–3 问的是"怎么算得快、怎么连得快"，到了数据中心问的是"**资源怎么组织、怎么分配**"。传统网络学 IP 和路由，是因为它解决"包去哪"；数据中心这一层解决"活给谁"——对应就是池化和调度。

---

## 2. 重心一详解：池化

### 2.1 核心直觉：从"一台台机器"到"一池算力"

买来 1000 张卡，如果还是"每张卡单独用"，那只是堆了一堆硬件。
池化要做的，是让上层看到的是**一个统一的算力资源**，而不是 1000 个孤立的地址。

```text
池化前：你有 A 机器的 8 卡、B 机器的 8 卡……要分别申请、分别配置
池化后：你面对一个"算力池"，说"我要 64 卡"，系统去池里切给你
```

### 2.2 池化要抹平什么

```text
异构差异
  不同代次的卡（A100 / H100）、不同厂商的卡，性能不同
  池化要给它们统一标识、统一计量，上层才能无差别使用

环境差异
  每台机器的驱动、CUDA、库版本可能不同
  容器技术把"驱动 + CUDA + 库 + 应用"封装成一致的运行环境
  —— 这就是 NVIDIA Container Toolkit 在这一层的意义

状态可见
  哪些卡空闲、哪些卡故障、哪些卡在跑什么
  —— DCGM 的遥测数据是池化的"眼睛"，看不见就没法池化
```

### 2.3 学到什么程度算掌握

```text
能回答：池化和"买一堆机器"的本质区别在哪
能解释：为什么容器是算力池化的基础（环境一致，算力才能被调度搬运）
能理解：DCGM 为什么在这一层很重要（状态是池化的前提）
能说清：异构算力池化最大的难点是什么（生态与编程模型不统一）
```

## 3. 重心二详解：调度

### 3.1 核心直觉：调度就是"活给谁、什么时候给"

池子是资源，调度是决策。一个数据中心级的调度器要回答三个问题：

```text
放哪？   这个训练任务需要 64 卡、同机架、高速互联 —— 池里哪块地方合适
何时放？ 现在资源不够，是排队等，还是抢占低优先级任务
怎么放？ 是独占，还是和别人共享一张卡（切分 / 分时）
```

### 3.2 调度为什么难

```text
约束多
  任务要的卡数、卡型、互联拓扑、存储位置、网络带宽都是约束
  一个任务放不下，不等于池里总资源不够 —— 是"碎片化"了

动态性
  任务会失败、会扩缩容、有优先级
  调度不是一次性的，是持续在变

目标冲突
  利用率要高（多塞任务）vs 公平性（不能饿死小任务）
  吞吐要大 vs 时延要低
```

### 3.3 与集群调度器的分工

```text
集群内调度器（尺度 3 的上层）：管一个集群内的作业排布
数据中心调度器（本层）：管跨集群、跨池的资源分配和配额
  —— 边界不在"功能"，在"管多大范围"
```

### 3.4 学到什么程度算掌握

```text
能回答：调度和池化的关系（池化提供资源视图，调度做分配决策）
能解释：为什么"资源碎片"是调度的大敌
能理解：为什么调度需要实时状态（DCGM / 监控数据）
能说清：集群调度器和数据中心调度器的边界在哪
```

## 4. 八问展开

```text
【是什么】
  一个数据中心/园区内的算力组织与分配。主角是池化和调度。

【物理边界】
  管：单个数据中心内的资源组织、跨集群协调
  不管：跨地域、跨数据中心的调度（那是尺度 5）

【跨哪道鸿沟】
  一堆异构机器 ↔ 一个统一可调度的资源池。
  没有这一格，资源是孤岛，跨集群调用无从谈起。

【内部构成】
  连接：DCI、算力专线（L2）、SDN
  平台：算力池化、容器封装、计量、集群调度器

【对上给什么 / 对下藏什么】
  对上给：一个可申请、可计量的算力资源视图
  对下藏：卡型号差异、机器位置、环境配置

【概念归位】
  池化     = 资源抽象（把异构收敛成统一）
  调度     = 决策能力（资源分配）
  DCI/专线 = 连接方式（L2 两点搬得快）
  Container Toolkit = 池化的使能技术

【现在咋样 + 怎么用】
  主流：多云/多集群统一管控，算力互联互通平台
  典型场景：一个平台下挂多个集群，统一申请、统一计量

【为什么不能省 + 交接点】
  没有这一格：跨域调度没有"可被调度的对象"——调度器面对的是一堆孤岛
  交接点：SRv6 骨干网 / 算力标识 —— 出了数据中心，交给尺度 5
```

## 5. 本篇小结

```text
一句话记住：数据中心 = 池化 + 调度

池化回答"资源怎么统一"：抹平异构、封装环境、状态可见
调度回答"资源怎么分"：放哪、何时放、怎么放

最容易踩的坑：把"买了很多卡"当成"有了算力池"
最该建立的直觉：这一层的问题从"怎么算得快"变成"活给谁"——是管理问题不是计算问题
```

### 附：L2 算力专线 vs L3 算力网络（本层的边界辨析）

```text
L2 算力专线 —— "两点之间搬得快"
  一条点到点的高速通道，用于两个智算中心之间传数据
  像：租一条专用车道

L3 算力网络 —— "多点之间调得动"
  一张覆盖多地点、多云的网，配合调度做全局决策
  像：一整套有调度中心的交通网

选型判断：先问需求是"两点连"还是"多点调"，答案不同方案完全不同
```
