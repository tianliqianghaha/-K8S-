# 三机方案 · 用 3 台普通云主机做出"两级拓扑 + 真实网络栈"

## 0. 本篇对象

> **原样题面**：我一定要模拟，给你几台普通云主机的条件，①单机多卡的日常工作模拟，②无损网络的物理机制（PFC/ECN/DCQCN、大象流）工作模拟。你想办法。
>
> **追加条件**：如果是 3 台服务器呢？整体的模拟能不能再贴近真实一点。

**结论先行**：

```text
3 台不是"1 台的 3 倍算力"，是换来一样单机根本买不到的东西：
  ① 两个平面（机内 lo / 机间 eth0）—— 拓扑从"一个平面"变成"两级"
  ② 真网络栈（真网卡、真内核、真 TCP 拥塞控制）—— 不再全靠仿真器
  ③ 真故障（掉一台、慢一台、重启续训）—— 单机永远做不出来

代价：约 3 倍机时费（2.5 元 → 7.6 元/天），外加一次安全组改动。
结论：值。但"更贴近真实"有上限，第 5 节把账算给你看，别指望它是真机房。
```

## 1. 先把目标锁死（我理解的"你要模拟什么"）

不是"复现硬件"，是三件事，按重要性排：

```text
第一层 · 工程动作（必须真实）
  工程师每天在做的事：起分布式、切数据、选网卡、配 rendezvous、
  排 hang、处理慢节点、掉线续训、量带宽。
  这一层的要求是"真做一遍"，不是"看懂"。

第二层 · 机制行为（要能观测、能对照）
  ECN 什么时候标记、队列什么时候涨、吞吐什么时候塌、恢复多快；
  PFC 什么时候暂停、暂停多久、为什么会传播。
  这一层的要求是"改一个变量，曲线必须动，而且动得符合因果"。

第三层 · 交付判断力（最终目的）
  给一张曲线能判断"这是 PFC 门限设低了还是 ECN 没开"；
  给一个 hang 能判断"是网卡选错还是某 rank 少同步"。
  这一层的要求是"见过对的，才认得出错的"。
```

**关键判断**：第一层和第三层几乎不依赖硬件，但**强烈依赖"有没有第二台机器"**。
一台机器上起 8 个进程，你能练"进程协作"；但"跨机网卡选错""跨机超时""某台掉线"这些真实故障，
一台机器永远造不出来 —— 因为没有"另一台"。

**这就是 3 台机的全部意义。**

## 2. 3 台买到的三样东西（单机替代不了）

### 2.1 两个平面：拓扑从"一个"变成"两个"

```text
单机 8 进程
  所有进程走 lo（本地环回），延迟 ~50µs，带宽几十 GB/s
  本质：一个平面。不管你起 2 个还是 8 个进程，都是"同一张网里"。

3 台机 × 每台 4 进程
  机内 4 进程 → lo          实测 RTT 0.031ms   实测带宽 27.3 Gbps  ← 平面 A（模拟 NVLink）
  跨机 12 进程 → eth0 内网   实测 RTT 0.50ms    实测带宽 3.77 Gbps  ← 平面 B（模拟 IB）
  本质：两个平面，快慢差 16 倍（延迟）/ 7 倍（带宽），这个差是**真实存在的**，不需要模拟。
```

> 上面四个数字是 2026-11-24 在香港三台机（cn-hongkong-c，172.23.163.99/100/101）上
> 用 `ping` 和 `iperf3` 实测的，不是估算。

**实测基线（后面所有对照都以它为准）**

```text
平面 A · 环回（同一台机器内）
  RTT        0.031 ms   (0.020 / 0.031 / 0.038，min/avg/max)
  带宽       27.3 Gbps  (iperf3 单流，5s)

平面 B · 跨机（同 VPC 同子网，172.23.163.x）
  RTT        0.50 ms    (0.252 / 0.497 / 1.137)   ← 是环回的 16 倍
  带宽       3.77 Gbps  (iperf3 单流) / 3.14 Gbps (8 并发)   ← 是环回的 1/7

对照真实硬件（只作方向参考，不是等价）
  NVLink     带宽 ~900 GB/s，延迟 ~1µs
  IB 400G    带宽 ~50 GB/s，延迟 ~2-5µs
  → 真实是"带宽差 18 倍、延迟差 3 倍"
  → 云上是"带宽差 7 倍、延迟差 16 倍"
  → 方向对，但两个倍数一个压缩一个夸大。别拿云上的比值当真理，
    它只能证明"放在同一台机器上确实快很多"这个定性结论。
```

**这条实测还顺手纠正了方案里的估算**：原以为 e 系列内网只有约 1 Gbps，
实测 3.77 Gbps；原以为跨机 RTT 约 0.3ms，实测 0.50ms。

真实 AI 集群就是两级：机内 scale-up（NVLink）+ 机间 scale-out（IB）。
一台机器只能演一级，所以"为什么机内要 NVLink、机间要 IB"这句话，
在单机方案里只能靠讲；在 3 台机上可以**测出两个数字摆在一起**。

### 2.2 真网络栈：从"全靠仿真"变成"一半真、一半仿真"

```text
单机方案：ECN/PFC 全部在 ns-3 事件队列里，一个真实包都没有。

3 台方案：incast 实验可以在真内核上做
  node1 + node2 同时打 node0（真 TCP 流，真网卡，真 congestion window）
  在 node0 的 eth0 上挂 tc red ... ecn → 内核真的会给包打 CE 标记
  接收端 TCP 真的会回 ECE → 发送端真的会降窗
  队列积压用 tc -s qdisc show 读 → 真的 backlog / drops / ecn_mark 计数

  于是"开 ECN vs 关 ECN"变成真实的对照实验：
    关 ECN → 队列满 → 尾部丢包 → 重传 → 吞吐锯齿
    开 ECN → 提前标记 → 降速 → 不丢包 → 吞吐平滑
  这条因果，和 PFC/ECN 那一课讲的东西**完全同构**，但这次是你自己跑出来的。
```

### 2.3 真故障：单机永远造不出来的那一类

```text
慢节点     3 台里让 1 台的 CPU 打满 → 另 2 台在 allreduce 上等它
掉线       kill -9 掉一台 → 观察 hang → 超时 → 重启 → 从 checkpoint 续训
网卡选错   故意让某台 NCCL_SOCKET_IFNAME 指错 → 看它降级或直接连不上
端口/安全组 故意关掉一个端口 → 看 rendezvous 卡在哪一步
```

尺度3 的 80% 清单里，①多机启动 25% + ②故障排障 25% + ③基准 15% + ⑤容错 10% ≈ **75%**
这些事，单机方案只能"假装"，3 台能真做。**这是投入产出比最高的一段。**

## 3. 新方案：三机三平面

```text
节点布局（3 台同规格，同 VPC，同可用区，同安全组）
  node0  4C8G   master + ns-3 仿真机 + incast 接收端
  node1  4C8G   worker + incast 发送端 A
  node2  4C8G   worker + incast 发送端 B

三个平面，每条实验线只落在其中一个平面，不许混着讲
  平面 A  机内     同机 4 进程，走 lo          → 模拟"1 机 4 卡"
  平面 B  机间     跨 2~3 机，走 eth0 内网      → 模拟"3 机 × 4 卡"
  平面 C  仿真     node0 上 ns-3 事件队列       → PFC/DCQCN/RDMA（这段只能仿真）

为什么要分成三个平面而不是"一个大实验"：
  三个平面的"真"程度不一样，混在一起讲，你会分不清哪个结论可信。
  分开之后，每个实验都能标：这条结论来自真机 / 来自仿真 / 是真机校准了仿真。
```

## 4. 实验矩阵（按"必须 ≥2 台才能做"排前面）

```text
【E1】两级拓扑对照 —— 整个方案的核心实验，单机做不了
  同一份代码、同一个 allreduce（1MB），跑三次：
    a) 4 进程全在 node0        → 平面 A
    b) 4 进程跨 node0/node1    → 平面 B（2 机）
    c) 12 进程跨 3 台           → 平面 B（3 机）
  记录：allreduce 时延、有效带宽（数据量/时延）、随进程数的变化
  产出：三个数字。这三个数字就是"拓扑决定上限"的实证，
        比任何一张架构图都有说服力。

  【设计要点】world 固定 4、只改"放在哪"，是最干净的一组对照；
  再放开进程数看 8/12 进程。实测数字与读法见《11-实测记录-一页版.md》步骤 3。

【E2】机内/机间不对称 —— 只对 eth0 注入延迟，lo 不动
  tc 给 node0 的 eth0 加 1ms / 3ms / 10ms 延迟，重跑 E1 的 b、c
  观察：allreduce 时延随跨机跳数线性增长，而同机部分不变
  学会：为什么"通信密集的任务要放在同一台机器"，以及"分离部署"的代价

【E3】真故障三连 —— 只有 ≥2 台能做
  E3a 慢节点：node2 上 stress-ng 打满 CPU → 看另两台的等待时间
  E3b 掉线：kill -9 node1 的训练进程 → 看 hang、看 torchrun 超时日志
  E3c 续训：重启 node1，从 checkpoint 恢复 → 走完整个恢复流程
  产出：一套你自己踩出来的排障手册（比读文档强十倍）

【E4】真 incast 与真 ECN —— 平面 B，真内核
  node1、node2 各起 N 条 TCP 流同时打 node0（2:1 / 4:1 / 8:1）
  node0 的 eth0 挂 tc red ... ecn（可开可关），限速到 100M/1G
  观测（全部来自真内核计数器，tc -s qdisc show）：
    队列 backlog、drops、ecn_mark、requeues
    各流吞吐、总吞吐、恢复时间
  对照：关 ECN vs 开 ECN vs 调 min/max 门限
  这一组就是"大象流打满 buffer"的真实版，只是协议从 RoCE 换成了 TCP。

【E5】PFC / DCQCN 状态机 —— 平面 C，ns-3
  这段不要勉强上真机：云上没有 PFC，Linux 也发不出 pause 帧。
  老实待在 ns-3 里跑：2:1 incast、PFC 开关、ECN 门限、DCQCN vs DCTCP

【E6】交叉验证 —— 把 E4 和 E5 摆在一起（这是"更贴近真实"的正解）
  同一个 2:1 incast 场景：
    E4 真机（ECN + TCP）   得到收敛时间 T_real、吞吐平滑度
    E5 仿真（ECN + DCQCN） 得到收敛时间 T_sim
  你不需要它们相等。你需要知道的是：
    哪些结论两边一致（→ 可信）
    哪些只在仿真里成立（→ 存疑，别当真理）
  这一步训练的是"判断仿真结果可信度"的能力，比多跑十个实验有用。
```

## 5. 真实度账（1 台 vs 3 台，把假的部分也标出来）

```text
尺度1 · 卡内（并行模型 + 内存层次）
  1 台   0%   没有 GPU，什么都学不到
  3 台   0%   仍然没有 GPU。想补只有一条路：gpgpu-sim / Accel-Sim
              （CPU 上做周期级 GPU 模拟，能出 warp 分歧、bank conflict、occupancy）
  结论：3 台对这个尺度零提升，别指望。要么加这条线，要么放弃这一格。

尺度2 · 机内（拓扑 + 集合通信）
  1 台   60%  进程协作真实；拓扑是假的（只能看 topo 文件）；通信走 lo
  3 台   70%  多了"机内 vs 机间"的真实差；但"卡"仍然是进程，不是 GPU
  仍然假：NVLink 带宽、NCCL 的 ring/tree 算法选择、nvidia-smi topo -m 的真输出

尺度3 · 工程层（多机启动、排障、基准、容错）
  1 台   30%  全是"假装多机"，connect 的是 127.0.0.1
  3 台   85%  真的跨机、真的网卡、真的掉线、真的超时。
              剩下 15% 是真机才有的：IB 网卡、GID 索引、DCB 配置、交换机侧指标

尺度3 · 机制层（ECN / 队列 / 拥塞反应）
  1 台   0%   一个真实包都没有
  3 台   60%  真内核 ECN、真队列、真重传。缺的是 RoCE 那套（DCQCN/CNP/零拷贝）

尺度3 · 机制层（PFC）
  1 台   0%   （仿真另算）
  3 台   0%   云上交换机不给你配 PFC，Linux 虚拟网卡也发不出 pause 帧。
              这一段永远只能在 ns-3 里学，3 台机也救不了。老实承认。

尺度3 · 仿真层（PFC/DCQCN/RDMA）
  1 台   100% （但只是"能跑"，判读能力看你自己）
  3 台   100% + 多了 E6 交叉验证，知道它哪里可信
```

**一句话**：3 台把"工程层"从 30% 拉到 85%，把"ECN 机制"从 0 拉到 60%；
但"卡内"和"PFC"这两块，3 台一点忙都帮不上。别把预算花在错的期待上。
