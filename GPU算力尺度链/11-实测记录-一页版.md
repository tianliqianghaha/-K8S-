# 实测记录 · 三台云主机模拟尺度 2–3（一页版）

## 0. 目标

```text
在没有任何 GPU、没有 RDMA、交换机不可配的普通云主机上，把两件事跑通并留下可复算的数字：

  ① 单机多卡的日常工作：分布式训练的启动、数据切分、梯度同步、通信量化、故障处置
  ② 无损网络的物理机制：incast 大象流、ECN 标记、队列积压，以及 PFC/DCQCN 的仿真侧对照

判据不是"跑起来"，是每一步都能说出：
  为什么这么做 → 怎么做 → 跑出什么数 → 这个数说明什么
```

## 3. 步骤 1 · 环境就位与互通

**为什么**：三台机器不同 VPC 或不同可用区，跨机实验的延迟数据就没有可比性；
依赖装错版本（尤其 Python 与 torch），后面每个脚本都会莫名失败。这一步必须做干净。

```bash
# 每台都执行：确认身份与规格
ssh root@<IP>
hostname -I; nproc; free -g | head -2; df -h / | tail -1; cat /etc/os-release | head -2

# 依赖
apt-get update -qq
apt-get install -y -qq python3-venv iperf3
python3 -m venv /root/venv
/root/venv/bin/pip -q install --upgrade pip
/root/venv/bin/pip install torch --index-url https://download.pytorch.org/whl/cpu
/root/venv/bin/pip install numpy matplotlib

# 验证分布式后端可用
/root/venv/bin/python -c "import torch, torch.distributed as d; print(torch.__version__, d.is_gloo_available())"
```

```bash
# 三台互相验证内网可达（每台都打另外两台）
ping -c 4 -q 172.23.163.100
ping -c 4 -q 172.23.163.101
```

```text
结果：三台 nproc=4、内存 7 GiB 可用、磁盘 59 GiB；gloo 可用；互 ping 0 丢包
```

## 4. 步骤 2 · 网络基线

**为什么**：后面所有"快/慢"的结论都要以这两个数为单位。
没有基线，"跨机比同机慢 2 倍"就是一句没有参照的话。

```bash
# 环回基线（同一台机器内，模拟"机内互连"）
iperf3 -s -D --logfile /tmp/iperf.log
iperf3 -c 127.0.0.1 -t 5 -f m
ping -c 4 -q 127.0.0.1

# 跨机基线（node1 打 node0 的内网 IP）
iperf3 -c 172.23.163.99 -t 5 -f m
iperf3 -c 172.23.163.99 -t 5 -P 8 -f m
```

```text
结果
  环回    RTT 0.031 ms     带宽 27.3 Gbps
  跨机    RTT 0.50 ms      带宽 3.77 Gbps（8 并发 3.14 Gbps）
  → 延迟差 16 倍、带宽差 7 倍，这就是后面所有"两级拓扑"讨论的物理基础
```

## 5. 步骤 3 · 两级拓扑对照（E1）

**为什么**：这是整个方案的核心。真实集群是两级（机内快、机间慢），
单机方案只有一个平面，讲不清"为什么机内要 NVLink、机间要 IB"。
把 world 固定成 4，只改"放在哪"，就能把"放置代价"单独量出来。

```bash
# 场景 A：4 进程全在 node0（全部走环回）
cd /root/simlab
export OMP_NUM_THREADS=1
/root/venv/bin/torchrun --standalone --nproc_per_node=4 \
  allreduce_bench.py --sizes 1,16,64 --iters 20 --tag A

# 场景 B：2+2 跨 node0/node1（走 eth0）
# 两台都要执行，只有 --node_rank 不同，且必须指定网卡名
export GLOO_SOCKET_IFNAME=eth0
/root/venv/bin/torchrun --nnodes=2 --node_rank=0 \
  --master_addr=172.23.163.99 --master_port=29501 --nproc_per_node=2 \
  allreduce_bench.py --sizes 1,16,64 --iters 20 --tag B
```

```text
结果（allreduce 时延 / 有效带宽，数据量 1MB 与 64MB）
  4 进程全在 node0     1MB 4.41 ms     64MB 110.5 ms    busbw 0.848 GB/s
  2+2 跨两台           1MB 6.71 ms     64MB 232.3 ms    busbw 0.404 GB/s
  2+1+1 跨三台         1MB 6.72 ms     64MB 250.6 ms    busbw 0.374 GB/s
  8 进程 / 2 台                        64MB 266.0 ms    busbw 0.411 GB/s
  12 进程 / 3 台                       64MB 305.6 ms    busbw 0.375 GB/s

怎么读：世界大小一样、代码一样、只改放置位置，64MB 的时延从 110ms 涨到 250ms。
        1MB 那一组（4.41→6.72）更接近纯"放置开销"，因为大包那一档里 CPU 规约也占时间。
```

## 6. 步骤 4 · 延迟不对称（E2）

**为什么**：真实机内是微秒级、机间是毫秒级，这个不对称决定了"通信密集的任务要放同机"。
只给机间链路加延迟、机内不动，才能看清小包是"按 RTT 放大"、大包是"按带宽走"。

```bash
# 三台都给 eth0 加 1ms（用配套脚本，内部是 tc netem，层次已修正）
cd /root/simlab
/root/venv/bin/python inject_latency.py --dev eth0 --delay 1ms --add
tc qdisc show dev eth0

# 重跑 E1 的场景 B
export GLOO_SOCKET_IFNAME=eth0
/root/venv/bin/torchrun --nnodes=2 --node_rank=0 \
  --master_addr=172.23.163.99 --master_port=29511 --nproc_per_node=2 \
  allreduce_bench.py --sizes 1,64 --iters 20 --tag E2

# 加大到 3ms 再来一轮，然后务必清理
/root/venv/bin/python inject_latency.py --dev eth0 --delay 3ms --add
/root/venv/bin/python inject_latency.py --dev eth0 --clear
```

```text
结果（world=4）
             基线        +1ms/边     +3ms/边
  1MB        6.71 ms     17.60 ms    41.82 ms
  64MB       232.3 ms    279.6 ms    446.8 ms

怎么读：1MB 的时延放大约等于 RTT 的 6 倍 → "1MB allreduce ≈ 6 个 RTT"
        64MB 由带宽决定，延迟加 5 倍，时延只涨 20%
        这就是"小包看延迟、大包看带宽"的实测版
```

## 7. 步骤 5 · 故障三连（E3）

**为什么**：尺度 3 的工程动作里，约 75% 是"多机启动 + 排障 + 基准 + 容错"，
这些只有 ≥2 台机器才做得出来。单机能练进程协作，练不出"另一台出事了"。

```bash
# 5.1 慢节点：node2 上同会话打满 4 核，跑完自动回收
PIDS=""
for i in 1 2 3 4; do (while :; do :; done) & PIDS="$PIDS $!"; done
sleep 3
# 其余两台正常起 3 节点任务（略，命令同 E1，加 --nnodes=3）
kill $PIDS

# 5.2 掉线：node2 上给训练进程套一个 12 秒的 timeout，模拟节点中途消失
timeout 12s /root/venv/bin/torchrun --nnodes=3 --node_rank=2 \
  --master_addr=172.23.163.99 --master_port=29515 --nproc_per_node=1 \
  allreduce_bench.py --sizes 64 --iters 3000

# 5.3 续训：第一段跑到一半被杀，第二段从断点接上
/root/venv/bin/torchrun --standalone --nproc_per_node=2 ddp_ckpt.py \
  --steps 5000 --hidden 1024 --save-every 200 --ckpt /tmp/ck.pt
timeout 10s /root/venv/bin/torchrun --standalone --nproc_per_node=2 ddp_ckpt.py \
  --steps 5000 --hidden 1024 --save-every 200 --ckpt /tmp/ck.pt
/root/venv/bin/torchrun --standalone --nproc_per_node=2 ddp_ckpt.py \
  --steps 5000 --hidden 1024 --save-every 200 --ckpt /tmp/ck.pt --resume
```

```text
结果
  慢节点   1MB 6.72→8.03 ms（+19%），64MB 250.6→246.1 ms（基本不动）
           每个 rank 计算量小时效应有限，计算占比大的真实训练会放大
  掉线     node0/node1 立刻报：Read error [172.23.163.101]:1252: Connection reset by peer
           19 秒退出，退出码 1；报错直接指向已死节点的 IP
  续训     第一段被 kill（rc=124），最后存盘 step=2000
           第二段加载 step=2000，跑到 5000，rc=0
```

## 8. 步骤 6 · 真 incast 与 ECN（E4）

**为什么**：这一层如果全交给仿真器，学生摸不到任何真实计数器。
在接收方内核上造一个入向队列，就能让"多打一 → 队列积压 → ECN 标记 / 丢包"
变成真实的、可读数的过程。

```bash
# 8.1 在 node0 上把"入向拥塞队列"造出来（只拦 5201 端口，不动 SSH）
modprobe ifb
ip link add ifb0 type ifb            # 已存在可跳过
ip link set ifb0 up
tc qdisc add dev eth0 handle ffff: ingress
tc filter add dev eth0 parent ffff: protocol ip u32 \
   match ip dport 5201 0xffff action mirred egress redirect dev ifb0
tc qdisc add dev ifb0 root handle 1: htb default 1
tc class add dev ifb0 parent 1: classid 1:1 htb rate 2gbit ceil 2gbit
tc qdisc add dev ifb0 parent 1:1 handle 10: red \
   limit 400000 min 60000 max 240000 avpkt 1500 burst 100 probability 0.02 bandwidth 2gbit ecn

# 8.2 三台统一开启 ECN 协商
sysctl -w net.ipv4.tcp_ecn=1

# 8.3 起接收端，然后两台同时各打 4 条流（8:1 incast）
iperf3 -s -D --logfile /tmp/iperf_s.log          # node0
iperf3 -c 172.23.163.99 -P 4 -t 12 -f m          # node1 与 node2 同时执行

# 8.4 读真实计数器
tc -s qdisc show dev ifb0

# 8.5 对照组：把 ecn 关键字去掉（纯丢包），重建队列后重复 8.3/8.4
tc qdisc del dev ifb0 root
tc qdisc add dev ifb0 root handle 1: htb default 1
tc class add dev ifb0 parent 1: classid 1:1 htb rate 2gbit ceil 2gbit
tc qdisc add dev ifb0 parent 1:1 handle 10: red \
   limit 400000 min 60000 max 240000 avpkt 1500 burst 100 probability 0.02 bandwidth 2gbit

# 8.6 收尾
tc qdisc del dev eth0 ingress
tc qdisc del dev ifb0 root
pkill iperf3
```

```text
结果（8 条流同时打 node0，各 12 秒）
  ECN 开   1,842,627 包   marked 1564   dropped 19
  ECN 关   1,863,758 包   marked 0      dropped 1546   ← 丢包多 81 倍

怎么读：同一份流量、同一份带宽，ECN 把"丢 1546 个包"换成"打 1564 个标记"，
        发送端提前降速，不靠重传兜底。这条是在真内核计数器上量出来的。
```

## 9. 步骤 7 · 仿真侧（E5）

**为什么**：PFC 与 DCQCN 这两样在云上物理上做不到（交换机不给你配、虚拟网卡发不出 pause 帧），
只能靠离散事件仿真逐包跑状态机。这里的目标是把环境搭起来、把 trace 变成可读的四个量。

```bash
# 9.1 老环境镜像（这些仿真器基于 ns-3.17，需要 gcc-5 + python2）
docker build -t ns3rdma .
# docker run --rm -v $PWD/hpcc:/work/hpcc ns3rdma bash -lc 'cd /work/hpcc && ls'

# 9.2 拉源码
git clone --depth 1 https://github.com/kitmanzheng/high-precision-congestion-control.git hpcc

# 9.3 配置与编译（关键：指定 gcc-5、python 指向 2.7）
docker run --rm -v /root/ns3/hpcc:/work/hpcc ns3rdma bash -lc \
  'cd /work/hpcc && ln -sf /usr/bin/python2.7 /usr/bin/python && \
   CC=gcc-5 CXX=g++-5 ./waf configure && ./waf build -j4'

# 9.4 跑第一个 incast
docker run --rm -v /root/ns3/hpcc:/work/hpcc ns3rdma bash -lc \
  'cd /work/hpcc && ln -sf /usr/bin/python2.7 /usr/bin/python && \
   ./waf --run "scratch/third mix/config.txt"'

# 9.5 把二进制 trace 变成四个量
/root/venv/bin/python parse_hpcc.py --trace mix/mix.tr --interval 0.0001 --out-prefix hp
# 只看格式与事件分布时：加 --probe
```

```text
结果
  镜像构建 55 秒 / configure 2.3 秒 / 一次仿真 39 秒（仿真场景 4 秒）
  产出 mix/mix.tr 246 MB，解析出 440 万条记录
  四个量：per-flow 吞吐、总吞吐、交换机队列最大值、Drop 与 ECN CE 标记
  旁证文件：mix/fct.txt（每流完成时间）、mix/pfc.txt（PFC 事件）

8:1 incast（100Gbps 链路）实测曲线
  8 条流同时从 t=2.000s 起，各约 1200–1500 MB/s
  总吞吐一步跳到 12,800 MB/s ≈ 102 Gbps，正好打满线速
  流陆续完成（2.0244 → 2.0354s），先退出的把带宽让给剩下的（涨到 3000–7000 MB/s）
  交换机队列起跳瞬间冲高 400,000，随即回落

算法对照（同场景，看 FCT 分布）
  HPCC    min 25.95 / 中位 34.07 / max 36.94 ms —— 有快有慢
  DCQCN   全部 33.20 ms —— 完成时间高度对齐
  → 两种拥塞控制在公平性与收敛上的差别，可以从完成时间分布直接读出来
```

## 11. 坑点清单（一句话一条）

```text
1  ns-3 老代码缺 broadcom-node.h：补一个空 shim 到 build/ns3/ 即可编过
2  waf 只认 python2：configure 前先 ln -sf /usr/bin/python2.7 /usr/bin/python
3  脚本里别用 docker run -it：会报 ttyname failed，改用 bash -lc
4  仿真链路速率必须落在 KMIN_MAP 覆盖的集合内（25G/50G/100G 可，10G 会断言）
5  HPCC 的 mix.tr 是二进制（TraceFormat，56 字节/条，文件头 38 字节），要用专用解析器
6  tc 的层次不能反：root 用 tbf（有 class），netem 挂在 1:1 下面
7  RED 的 burst 太小会算不出 EWMA，给 100 并把 bandwidth 显式写上
8  tc 规则只拦实验端口（如 5201），别拦全量入向，否则会把自己 SSH 关在门外
9  Git Bash 下传文件要把 MSYS_NO_PATHCONV=1 打开，否则 /root 会被改成本地路径
10 多节点并发启动要给 worker 留 2 秒错峰，避免 rendezvous 撞在一起
```
