# 实施手册 · 普通云主机（无 GPU）模拟尺度 2 与尺度 3

> 本手册有头有尾：先讲清背景与为什么这么做，再给每一步的命令，最后给验收标准与边界。
> 配套脚本在 `模拟实验包/` 目录，命令里会直接引用。

---

# 第一部分 · 背景

## 1. 这件事从哪来

我们讨论的是 GPU 算力尺度链。整条链按从小到大分五格：

```text
尺度1 卡内       并行模型 + 内存层次
尺度2 机内       拓扑 + 集合通信
尺度3 集群内     无损 + 抗大象流
尺度4 数据中心   池化 + 调度
尺度5 跨域       算力路由 + 确定性
```

本手册只解决两个：**尺度 2 和尺度 3 怎么在普通云主机上模拟实践**。条件是：几台普通云主机，无 GPU，无 RDMA，交换机不归你管。

## 2. 为什么要"模拟"，以及为什么能模拟

普通云主机有三条硬限制：

```text
网卡是虚拟的（virtio / SR-IOV），没有 DCB / PFC / ECN 硬件卸载
交换机是云厂商的，你进不去配 PFC 阈值、ECN 门限、队列调度
没有 GPU，谈不上真实多卡和 NVLink
```

但关键洞察是——**你要模拟的是"行为"，不是"硬件"**：

```text
尺度2工程师80%的工作 = 进程协作逻辑
  （起分布式、切数据、梯度同步、排障、扩展性验证）
  → 与底层是 NCCL 还是 gloo 无关 → CPU 多进程能完整复现

尺度3的机制 = 状态机 + 阈值 + 反馈回路（是算法，不是硬件专属）
  → 离散事件仿真器能逐包精确复现
```

所以两条技术路线：

```text
尺度2 → PyTorch 的 gloo 后端 + 多进程（集合通信走 TCP，语义不变）
尺度3 → ns-3 + RDMA 扩展仿真器（逐包跑 PFC/ECN/DCQCN 状态机）
```

## 3. 能模拟什么、不能模拟什么（先说清边界）

```text
能模拟：
  全部工程流程（起分布式、切数据、同步、排障、扩展性）
  协议机制（PFC pause、ECN 标记、CNP 反馈、DCQCN 降速的完整回路）
  可调参数的效果（阈值、算法、并发度的对照实验）

不能模拟：
  真实硬件时序、真实 NVLink/RDMA 带宽数字
  真机 ASIC 的具体行为、真实 NCCL_DEBUG 日志
```

关键：学习目标（"工程师每天做什么"和"机制怎么闭环"）恰好都在能模拟那一栏。练不到的只有数字，而数字不是学习目标。

# 第三部分 · 尺度 2：gloo 多进程模拟单机多卡

## 4. 安装 PyTorch（CPU 版即可）

```bash
# CPU 版 PyTorch，体积小，不需要 GPU
pip3 install torch --index-url https://download.pytorch.org/whl/cpu

# 验证安装与后端
python3 -c "
import torch, torch.distributed as dist
print('torch', torch.__version__)
print('gloo', dist.is_gloo_available())
print('nccl', dist.is_nccl_available())
"
```

期望输出：`gloo True`（nccl 在无 GPU 版本里通常是 False，不影响）。

## 5. 跑通第一个多进程 DDP

配套脚本：`模拟实验包/ddp_sim.py`。

```bash
cd ~/simlab
# 把配套脚本拷进来（本机路径按实际改）
cp /path/to/模拟实验包/ddp_sim.py .

# 起 2 个进程模拟 2 张卡
torchrun --standalone --nproc_per_node=2 ddp_sim.py

# 起 4 个进程模拟 4 张卡
torchrun --standalone --nproc_per_node=4 ddp_sim.py --steps 20
```

期望输出：

```text
[data] rank0 first_indices=[13, 47, 2, 88, ...]      # 每 rank 拿到的分片不同
[model] hidden=256 params=77066 (~301 KB fp32)
[init] world_size=4 backend=gloo bucket_cap=25MB accum=1 latency=0.0ms break_sync=False
[check] param_sum  per rank = [123.456001, 123.456001, 123.456001, 123.456001]
[check] param_norm per rank = [7.890123, 7.890123, 7.890123, 7.890123]
[check] OK: all 4 ranks identical (spread=0.000e+00 <= tol=1.235e-01)
[done] steps=20 time=1.83s throughput=10.929 step/s samples/s=1398.9
```

关键看两行：

```text
[check] param_sum per rank = [...]     ← 四个数必须完全一样
[check] OK: all N ranks identical       ← 出现 OK 才算通过
```

**这一项现在有牙齿了**：旧版脚本没有 `optimizer.step()`，参数永不更新，
"各 rank 一致"是永远成立的空话。新版真的更新参数、并做跨 rank 汇总比对，
不一致会打印 `MISMATCH` 且**进程退出码为 1**。

想亲眼确认它真能抓错，跑一次反证（第 6.7 节）：

```bash
torchrun --standalone --nproc_per_node=2 ddp_sim.py --steps 6 --break-sync
# 预期：打印 [check] MISMATCH，echo $? 为 1
```

> 如果卡住不动，多半是端口被占。显式指定端口：
> `torchrun --nnodes=1 --nproc_per_node=2 --master_addr=127.0.0.1 --master_port=29501 ddp_sim.py`

## 6. 尺度 2 的 80% 工作逐项演练

### 6.1 起分布式 + 切数据（第①项）

ddp_sim.py 里已经包含，观察两点：

```bash
# 看每个 rank 拿到的样本不同：在脚本里 rank0 打印 sampler 的索引
# DistributedSampler 保证每张"卡"看到不同分片，这是数据并行的核心
```

### 6.2 通信瓶颈定位（第②项）

注入延迟，制造"通信变慢"，看吞吐怎么掉：

```bash
# 在 all_reduce 内部注入 5ms 延迟（走 DDP comm hook，不是干睡）
torchrun --standalone --nproc_per_node=2 ddp_sim.py --steps 20 --latency-ms 5

# 对照：无延迟
torchrun --standalone --nproc_per_node=2 ddp_sim.py --steps 20
```

正确的读法（别读错）：

```text
这两次运行的 throughput 差值 = 你注入的那点延迟，不是"真实通信开销"。
它证明的是"通信一旦变慢，吞吐线性掉"这条因果 —— 这是学习目的。
真实通信开销要靠在真机上对比 NCCL kernel 占比，这里做不到。
```

口径说明：旧版把 `time.sleep` 放在 `backward()` 之后，那段时间 DDP 根本没有在通信，
测出来的是"空转"，不是"通信慢"。新版通过 `register_comm_hook` 把延迟塞进
`all_reduce` 内部，通信真的变慢了。

用 Linux `tc` 在网卡层面注入延迟（更真实，需 root）：

```bash
# 配套脚本 inject_latency.py
sudo python3 inject_latency.py --dev lo --delay 5ms --loss 0.1% --rate 1gbit --add

# 查看注入状态
sudo python3 inject_latency.py --dev lo --show

# 注入后再跑一次 DDP，对比吞吐
torchrun --standalone --nproc_per_node=2 ddp_sim.py --steps 20

# 实验结束务必清除，否则影响后续所有网络操作
sudo python3 inject_latency.py --dev lo --clear
```

### 6.3 通信与计算重叠（第⑤项）

```bash
# 开 no_sync 做梯度累积（每2步同步一次）
torchrun --standalone --nproc_per_node=2 ddp_sim.py --steps 20 --no-sync

# 改梯度桶大小：桶越大，通信次数越少但单次越大
torchrun --standalone --nproc_per_node=2 ddp_sim.py --steps 20 --hidden 2048 --bucket-cap 5
torchrun --standalone --nproc_per_node=2 ddp_sim.py --steps 20 --hidden 2048 --bucket-cap 100
```

**桶实验必须带 `--hidden 2048`**，否则你什么都看不到：

```text
默认模型 params=77066 → 约 301 KB
最小桶是 5 MB → 所有参数本来就在一个桶里
--bucket-cap 5 和 --bucket-cap 100 跑出来完全一样（旧版就是这个坑）

--hidden 2048 → 约 17 MB 参数，跨过 5MB/25MB/100MB 三档才看得出通信次数差异
```

`--no-sync` 的口径也修了：现在是"每 2 步同步一次"的真累积，loss 会除以 2，
`zero_grad` 不会把累积抹掉（旧版每步清零，累积等于没做）。

### 6.4 卡死排障（第⑥项）

配套脚本：`模拟实验包/ddp_faults.py`。

```bash
# 故障1：某个 rank 慢 3 秒，其他 rank 卡在 all_reduce 等它
torchrun --standalone --nproc_per_node=2 ddp_faults.py --fault slow_rank --timeout 10

# 故障2：某 rank 少做一次同步，集合通信永久错位
torchrun --standalone --nproc_per_node=2 ddp_faults.py --fault mismatched_step --timeout 10

# 故障3：master 地址错误，起不来
torchrun --standalone --nproc_per_node=2 ddp_faults.py --fault bad_addr --timeout 10
```

排障要点（真机同样适用）：

```text
看现象：是哪个 rank 卡住？其他 rank 在等谁？
查配置：master_addr / master_port / 网卡名对不对
看代码：各 rank 的代码路径是否一致（分支导致少同步是经典错误）
用日志：真机用 NCCL_DEBUG=INFO，这里 gloo 用 print + 超时异常
```

### 6.5 扩展性验证（第⑦项）

```bash
# 先看机器有几个核，进程数不要超过核数
nproc

# 依次跑 1/2/4/(封顶到核数)，记录 throughput
for n in 1 2 4 8; do
  [ "$n" -gt "$(nproc)" ] && continue
  echo "=== nproc=$n ==="
  torchrun --standalone --nproc_per_node=$n ddp_sim.py --steps 50 2>/dev/null | grep throughput
done
```

**在这台机器上你一定会看到负加速，这是正常的，别误判：**

```text
2 核跑 4 进程 → 4 个进程抢 2 个核，throughput 掉到单进程的一半左右
看到这个现象不是 DDP 有问题，是物理核不够。

所以这一步的学习目标是三件事，不是"看加速比"：
  1) 会做扩展性验证这个动作（脚本、口径、记录方式）
  2) 会解释"为什么不是线性"
  3) 会区分"算力不够"和"通信拖累"两类原因

要看到真正的正加速，只能在真多卡机上做，那不是云主机能替代的。
```

### 6.6 补上 NCCL 那一块（口径已修正）

```text
旧写法：用 ns-3 补 NCCL 的 ring/tree，说"结论与真机一致"——这个说法站不住。
  仿真器里没有 NCCL，只有它自己写的 allreduce 流量模型。
  你在仿真里看到的是"一种 ring 流量模式"，不是 NCCL 的 ring 实现。

现在能诚实地做两件事：
  1) 用仿真验证收发量公式：ring 每卡收发 2(N-1)/N × 数据量
     —— 这是能验的，而且验得干净
  2) 在 gloo 上实测字节数：跑 allreduce 时用 tc -s 或 ss -tin 看真实收发了多少
     —— 这一步旧方案完全没做，但成本最低、最补"集合通信"的手感

真要 NCCL_ALGO=RING/TREE 的行为差异，只能在有 GPU 的机器上实测。
在普通云主机上，这一块学到"公式能推、收发量能测"就到顶了。
```

### 6.7 反证：确认验收项真的能抓错

一个测试如果永远不会失败，它就不是测试。改完脚本必须做这一步：

```bash
# 永久关掉梯度同步，参数必然发散
torchrun --standalone --nproc_per_node=2 ddp_sim.py --steps 6 --break-sync
echo "退出码=$?"

# 预期输出：
#   [check] param_sum per rank = [123.456, 123.789, ...]   ← 两个数不一样
#   [check] MISMATCH: spread=... > tol=...  —— 梯度同步没有生效
#   退出码=1
```

看到 `MISMATCH` 才算证明：第 5 节那个 `OK` 是有意义的。
如果没有 `--break-sync` 这个选项，你无法区分"同步正常"和"检查是假的"。

# 第四部分 · 尺度 3：ns-3 仿真无损网络机制

## 7. 选仿真器

```text
ns3-rdma（微软）     完整实现 PFC/ECN/DCQCN/TIMELY + Broadcom buffer 模型，
                     自带 2:1 incast @ 40Gbps（大象流场景）
HPCC simulator（阿里） 加了 HPCC/DCTCP，可多算法对比，有 run.py 自动生成配置
ns-3-alibabacloud    较新，QP 级 RDMA、ECMP、MMU

推荐：HPCC simulator（Linux 下编译最顺，资料完整）
```

## 8. 用 Docker 绕开编译坑（关键）

这些仿真器基于 ns-3 3.17，新 gcc（>5）编译会失败。用旧环境容器解决。

**软件源先探再定，别凭"16.04 已 EOL"就盲目换 old-releases**：实测 archive 的 xenial 返回 200（可用），old-releases 反而 404。凭印象换源会把本来能构建的镜像搞失败。花 10 秒探一下即可：

```bash
# 探一下当前哪个源真的能提供 xenial
for u in \
  http://archive.ubuntu.com/ubuntu/dists/xenial/Release \
  http://old-releases.ubuntu.com/ubuntu/dists/xenial/Release ; do
  echo -n "$u -> "; curl -s -o /dev/null -w '%{http_code}\n' --max-time 10 "$u"
done
# 哪个返回 200 就用哪个，不要两个都改
```

```bash
cd ~/simlab

# 写 Dockerfile —— 用 archive 源（实测可用）。只有在上面探测显示 archive 404 时才换源
cat > Dockerfile <<'EOF'
FROM ubuntu:16.04
ENV DEBIAN_FRONTEND=noninteractive
RUN apt-get update && apt-get install -y \
    build-essential gcc-5 g++-5 python2.7 git curl ca-certificates \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /work
EOF

# 构建镜像（实测 55 秒完成）
docker build -t ns3rdma .

# 拉仿真器源码
git clone --depth 1 https://github.com/kitmanzheng/high-precision-congestion-control.git hpcc

# 关键：不要用 -it（脚本化执行时没有 TTY，-it 会报 ttyname failed）
# 直接 bash -lc 跑一条命令
docker run --rm -v $PWD/hpcc:/work/hpcc ns3rdma bash -lc 'cd /work/hpcc && ls'
```

## 9. 容器内编译

```bash
# 以下命令都在容器里执行
cd /work/hpcc-ns3

# 确认 python 指向 2.7（waf 只认 python2）
python2.7 --version
ln -sf /usr/bin/python2.7 /usr/bin/python

# 用 gcc-5 配置（关键：绕开新 gcc 的编译错误）

# 编译（-j 按核数，2 核用 -j2，4 核用 -j4）
./waf build -j$(nproc)
```

如果 configure 报 Python 相关错误，先做上面那个 `ln -sf` 再重跑。

### 9.5 编译不过怎么办（30 分钟止损规则）

这一步是整个方案里最可能卡死的地方。**给自己定死 30 分钟**，超时立刻换路，
不要在编译错误上耗一天。

```text
【先做 30 分钟 go/no-go，只看三条】
  1) docker build 是否成功
       失败 → 先按第 8 节 curl 探测哪个源返回 200，用可用的那个（实测 archive 可用）
       验证：docker run --rm ns3rdma cat /etc/apt/sources.list | head

  2) ./waf configure 是否通过
       报 python 错 → ln -sf /usr/bin/python2.7 /usr/bin/python 后重试
       报编译器错 → 确认 CC/CXX 真的用了 gcc-5：echo $CC

  3) ./waf build 前 3 分钟有没有大量 error
       全是 warning → 正常，等它编完
       有 error → 看第一条 error，通常只有一类，改一个地方就通

【三条退路，按顺序试，每条给 20 分钟】
  退路 A：换仓库（换 ns3-rdma 或 ns-3-alibabacloud），可能这一个就编得过
      git clone https://github.com/microsoft/ns3-rdma.git
      git clone https://github.com/alibaba-edu/High-Precision-Congestion-Control.git

  退路 B：同仓库、放过编译告警
      ./waf configure --disable-werror CXXFLAGS="-O2 -std=c++11 -fpermissive"

  退路 C：不编译，只读代码 + 用别人的 trace
      仓库里通常带现成的 trace 样例文件，直接拿来跑 analyze_trace.py 练判读。
      机制靠读代码 + 读论文补，判读能力靠现成 trace 练 —— 学到的比卡在编译多。

【止损线】
  90 分钟还没跑出第一个 incast 的 trace → 走退路 C，把时间花在判读上。
  判读才是这一层真正的难点，编译只是门槛。
```

**别忘了一件更重要的事**：就算编译一次成功，跑完五个实验也要 1–2 天。
如果时间只有半天，直接走退路 C，用现成 trace 把"四个量怎么看、曲线什么样算对"
练熟，收益比死磕编译高得多。

## 10. 跑通第一个大象流实验

```bash
# 容器里，跑自带的 incast 样例
cd /work/hpcc-ns3
./waf --run 'scratch/third mix/config.txt'

# 或用 run.py 自动生成配置并运行
python run.py --cc hp --trace flow --bw 100 --topo topology

产出 trace 文件（通常是 `mix/mix.tr`）。配置字段含义看仓库里的 `mix/config_doc.txt`——这是改参数的字典。

### 10.1 编译三个坑的解法（HPCC fork，实测可编过）

```text
这三个坑全都不在"gcc 太新"上，按解法处理即可：

坑 1  broadcom-node.h 找不到（真坑，2 分钟解）
      这个 fork 把类挪到 network/helper/broadcom-node-container.h，
      但 scratch/third.cc、node.h、qbb-net-device.h 仍引旧名。解法——建空 shim：
        printf '%s\n' '// shim' > src/network/model/broadcom-node.h
        cp src/network/model/broadcom-node.h build/ns3/broadcom-node.h
        再 ./waf build  → rc=0

坑 2  waf 只认 python2
      ./waf configure 前：ln -sf /usr/bin/python2.7 /usr/bin/python

坑 3  docker run -it 在脚本里报 "ttyname failed"
      改用 docker run --rm ... bash -lc '命令'，不要 -it
```

> 编译时间账（docker build 55 秒 / configure 2.3 秒 / incast 仿真 39 秒 / mix.tr 246MB）与"可使仿真崩掉的 KMIN_MAP 断言"见 10 号文档第 1 节。

### 10.2 一个必须先知道的边界：mix.tr 是二进制

```text
我原来的 analyze_trace.py 是按"文本行 + 列号"设计的，对 HPCC 的 mix.tr **不适用**。

证据：
  head -c 64 mix/mix.tr 出来的是二进制
  写盘方式是 TraceFormat::Serialize() → fwrite(this, sizeof(TraceFormat), 1, file)
  结构体定义在 src/point-to-point/model/trace-format.h：
    double time; uint16_t node; uint8_t intf, qidx; uint32_t qlen;
    uint32_t sip, dip; uint16_t size; uint8_t l3Prot, event, ecn, nodeType;
    union { data{...} / cnp{...} / ack{...} / pfc{...} / qp{...} };

所以 E5 要出四个量，得先按 TraceFormat 做二进制解析——**这一条已经做完了**：

```bash
python3 parse_hpcc.py --trace mix/mix.tr --interval 0.0001 --out-prefix hp
python3 parse_hpcc.py --trace mix/mix.tr --probe        # 只看偏移与事件分布
```

```text
parse_hpcc.py 做的事
  1) 自动探文件头偏移（实测 38 字节，n % 56 == 38）
     判据：event<=3、nodeType<=1、time<=10s 的合法率最高者

## 11. 五个对照实验

每个实验只改一个变量，观察机制响应。命令框架相同，改 config 或 run.py 参数。

```text
【实验 A】关掉 PFC —— 看丢包
  run.py 里关 PFC 相关开关，或改 config.txt 的 PFC 字段
  观察：队列溢出、丢包数、吞吐骤降
  结论：没有 PFC，无损无从谈起

【实验 B】打开 PFC —— 看 pause 与恢复
  改：PFC_enable = 1
  观察：pause 帧何时发、暂停多久、队列回落、吞吐恢复曲线
  结论：PFC 是链路级"刹车"，但会带来 pause 传播风险

【实验 C】调 ECN 门限 —— 看标记率
  改：ECN 的 buffer threshold（静态/动态）
  观察：标记率、CNP 数量、平均队列长度
  结论：门限低 → 早标记早降速但保守；门限高 → 吞吐高但时延大

【实验 D】换拥塞控制算法 —— 看收敛速度
  改：--cc 参数在 dcqcn / dctcp / timely / hp 之间切
  命令示例：python run.py --cc dcqcn --trace flow --bw 100
            python run.py --cc dctcp --trace flow --bw 100
  观察：从拥塞到稳定的收敛时间、吞吐震荡幅度
  结论：算法决定"多快降、多快恢复"

【实验 E】加大 incast 路数 —— 看大象流压迫下的公平性
  改：topology 配置里的发送方数量（2:1 → 4:1 → 8:1）
  观察：各流吞吐是否公平、是否存在饿死
  结论：大象流压迫下，拥塞控制算法决定公平性

## 12. 分析 trace：先探格式，再算四个量

配套脚本：`模拟实验包/analyze_trace.py`（宿主或容器内都能跑）。

> **先选对工具**：本节针对"文本行 + 列号"的通用 trace。
> 若你跑的是 HPCC 的 `mix/mix.tr`——它是二进制 `TraceFormat`，
> 文本工具不适用，请改用 `parse_hpcc.py`（命令见 10.2 节）。

**为什么要两步**：每份仿真器的 trace 列序都不一样，硬猜列号必然算错。
所以第一步只让你看清列，第二步才按你指定的列号算指标。**只探一次**，之后照抄。

```bash
pip3 install matplotlib     # 只画图用，不装也能出 CSV

# 第一步：探格式（前 20 行原文 + 每列统计 + 提示哪列像什么）
python3 analyze_trace.py --trace mix/mix.tr --probe

# 第二步：按探出来的列号算指标（列号从 0 开始，例子里是假设值）
python3 analyze_trace.py --trace mix/mix.tr \
    --map time=0,flow=1,size=4,queue=6,pfc=7,cnp=8 \
    --interval 0.0005 --out-prefix incast
```

脚本会吐四个量，这也是五个实验唯一要看的四个量：

```text
per-flow 吞吐 + Jain 公平指数   ← 实验 D（收敛）和实验 E（公平性）靠它
总吞吐 mean / peak              ← 实验 A（关 PFC 掉多少）靠它
队列 mean / p99 / window_max    ← 实验 B、C（pause、ECN 门限）靠它
PFC 事件数 + 速率、CNP 速率     ← 实验 A、B、D 靠它
```

没映射的字段会明确打印 `[skip]` 并说明"哪个实验需要它"，不会假装算过。
没映射 `size` 会自动降级成 `pkt/s` 并告警 —— 那不是吞吐，别当吞吐用。

产出 `_throughput.csv` / `_queue.csv` / `_events.csv` 和一张 2x2 图
（每流吞吐 / 总吞吐 / 队列 / PFC-CNP 事件率）。

**预期曲线基线（第一次跑先对照这个判断对不对）**：

```text
正常的 PFC/ECN 闭环，四条曲线的时间顺序必须是：
  1) 队列先抬（incast 突发进来）
  2) CNP 事件随后起来（交换机过 ECN 门限就开始打标）
  3) 队列继续涨到 PFC 门限，pause 才出现（PFC 是最后一道闸）
  4) 之后队列回落、暂停消失、总吞吐恢复

如果你看到 pause 比 CNP 先出现 → 说明 PFC 门限设得比 ECN 低，反了。
如果关掉 PFC 后队列曲线冲顶但总吞吐没掉 → 说明 ECN/DCQCN 在兜着，不是"没 PFC 就崩"。
```

> 先说清一件事：旧版脚本只是"数每窗口有多少行"，那既不是吞吐也不是 pause，
> 五个实验做完了也判读不了。现在这版才有上面这四个量。
