## 0. 本篇对象

> **原样题面**：我一定要模拟，给你几台普通云主机的条件，①单机多卡的日常工作模拟，②无损网络的物理机制（PFC/ECN/DCQCN、大象流）工作模拟。你想办法。

**结论先行**：能模拟，但要换思路——**不是去复现硬件，是去复现"行为"**。

```text
① 单机多卡的日常工作
   硬件靠不住 → 用 PyTorch 的 gloo 后端 + 多进程，把 DDP 工程语义 100% 跑通
   NCCL 调参靠软件仿真 → 用 ns-3 的 RDMA 仿真器补上
   结论：工程动作能真练，硬件带宽是假的

② 无损网络物理机制
   云厂商交换机不给你配 PFC/ECN → 不碰真网络，改用 ns-3 离散事件仿真
   现成实现：ns3-rdma / HPCC simulator，含 PFC、ECN、DCQCN、交换机 buffer、大象流
   结论：机制能真实复现（数值级），但不是在物理网卡上
```

## 1. 为什么必须"换载体"

```text
普通云主机的三条硬限制：
  网卡是虚拟的（virtio / SR-IOV），没有 DCB / PFC / ECN 硬件卸载
  交换机是云厂商的，你进不去配 PFC 阈值、ECN 门限、队列调度
  单机多卡的"拓扑"要么是假的，要么你没有多卡

所以：
  想练"工程师每天在做什么" → 练的是流程、脚本、判读、排障，这些与硬件无关
  想练"PFC/ECN/DCQCN 怎么工作" → 这些是算法，算法可以用离散事件仿真精确复现

关键洞察：
  你以为要模拟的是"设备"，其实要模拟的是"行为"。
  行为可以跑在 CPU 进程里，也可以跑在仿真器的事件队列里。
```

## 2. 方案一：单机多卡的日常工作模拟

### 2.1 载体选择

```text
gloo 后端（PyTorch 自带，CPU 上就能跑）
  能真实跑：rank / world_size、all_reduce / all_gather、DistributedSampler、
            DDP 梯度同步、broadcast、barrier、多机 rendezvous、hang 排障
  换掉的东西：NCCL → gloo，通信从 NVLink 变成 TCP socket
  不变的东西：所有 API 调用、代码结构、工程动作、错误现象

为什么这足够了：
  尺度 2 工程师 80% 的工作是"起分布式 + 切数据 + 调同步 + 排障"
  这 80% 里，绝大多数是进程协作逻辑，跟底层是 NCCL 还是 gloo 无关
  你在 gloo 上把 DDP 跑通、把 hang 排掉，换到真多卡只需改 backend="nccl"
```

### 2.2 能练到什么（对照 80% 清单）

```text
能真实练：
  起分布式训练（torchrun 多进程）              ← 尺度 2 第①项
  DistributedSampler 数据切分                  ← 第①项
  通信瓶颈定位（profiler 看 all_reduce 占比）  ← 第②项
  通信与计算重叠（bucket 参数、no_sync）       ← 第⑤项
  卡死 / 挂起 / OOM 排障                       ← 第⑥项
  扩展性验证（1/2/4/8 进程吞吐）              ← 第⑦项

需要补工具才能练：
  拓扑确认（nvidia-smi topo -m） → 用拓扑文件 + 模拟输出练（见脚本包）
  NCCL 调参 → 用 ns-3 仿真器练（见方案二）

练不到：
  NVLink 的真实带宽数字
  NCCL 算法选择的真实日志（可以用仿真器的日志替代理解）
```

### 2.3 三步走

```text
第一步  纯 CPU 起 8 进程 DDP
        torchrun --standalone --nproc_per_node=8 ddp_sim.py
        验证：所有 rank 的梯度 all_reduce 后一致

第二步  注入故障，练排障
        故意让某个 rank 慢启动 / 数据不对齐 / 端口冲突
        观察：hang 的现场、torchrun 的报错、怎么用 NCCL_DEBUG 思路定位

第三步  用仿真验证收发量公式（不是"补 NCCL"）
        ring 每卡收发 2(N-1)/N × 数据量，这个是能验的
        注意：仿真器里没有 NCCL，看不到 NCCL_ALGO=RING/TREE 的真实行为，
        不能声称"与真机一致"（详见 08 手册 6.6）
```

## 3. 方案二：无损网络物理机制模拟

### 3.1 载体选择

```text
ns-3 离散事件网络仿真器 + RDMA 扩展
  现成项目：
    ns3-rdma（Microsoft，含 DCQCN / TIMELY / PFC / ECN / Broadcom buffer）
    HPCC NS-3 simulator（阿里 SIGCOMM'19，含 DCQCN/TIMELY/DCTCP/PFC/ECN）
    ns-3-alibabacloud（更新，含 QP 级 RDMA、ECMP、MMU、INT/PINT）

  这些项目自带大象流实验：
    2:1 incast @ 40Gbps —— 两个发送方同时打一个接收方
    这正是"大象流 + 同步突发"的标准复现场景

为什么仿真是"真"模拟：
  PFC / ECN / DCQCN 本质是状态机 + 阈值 + 反馈回路
  仿真器逐包实现这些状态机：交换机 buffer 超过阈值 → 打 ECN 或发 PFC pause
  → 接收端 CNP → 发送端降速 → 队列回落
  你在仿真里看到的行为与真硬件同构，只是时间由事件推进而非真实时钟
```

### 3.2 能练到什么

```text
PFC：
  观察 pause 帧何时触发、暂停多久、pause 传播（级联 / 死锁）
  调阈值看效果：静态阈值 vs 动态阈值

ECN：
  观察交换机何时在包上打 ECN 标记、标记率多少
  调 buffer 门限看标记率与吞吐的关系

DCQCN：
  观察 CNP 反馈回路、降速与恢复曲线
  与 DCTCP / TIMELY 在同一 incast 场景下对比收敛速度

大象流：
  2:1 / 4:1 incast —— 多打一，制造突发
   Elephant vs mice 混合流 —— 看 PFC 对短流的队头阻塞
  看吞吐曲线、队列占用、丢包、pause 次数
```

### 3.3 落地步骤（概要，详细命令见实验手册）

```text
第零步  在云主机装 ns-3 + RDMA 扩展（我们用容器封装环境，绕开老版本编译坑）
第一步  跑自带的 2:1 incast 样例，拿到 trace
第二步  用 trace 画图：吞吐随时间、队列占用、pause 次数
第三步  改 config 做对照实验：
        实验A 关 PFC → 看丢包
        实验B 开 PFC → 看 pause 和吞吐恢复
        实验C 调 ECN 门限 → 看标记率变化
        实验D DCQCN vs DCTCP → 看收敛速度
        实验E 加大 incast 路数 → 看大象流压迫下的公平性
```

## 4. 两套方案的关系

```text
方案一（gloo 多进程）    → 练"工程师每天在干什么"：流程、脚本、排障
方案二（ns-3 仿真）      → 练"机制怎么工作"：PFC/ECN/DCQCN 的状态机

二者互补，不互相替代：
  方案一让你会操作，但不懂为什么这么调
  方案二让你懂原理，但不会真机操作
  合起来 = 完整的尺度 2 + 尺度 3 能力

真要上真机时：
  把 gloo 换成 nccl，把仿真参数换成真机 NCCL_DEBUG 看到的值
  所有经验都能直接迁移
```
