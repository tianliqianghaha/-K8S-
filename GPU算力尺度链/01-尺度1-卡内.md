# 尺度 1 · 卡内

## 0. 本篇对象

> **原样题面**：按照这种从小到大的尺度，给我每个尺度详细介绍一下。我的中心是学习。你要给我介绍学习的重点。比如学传统网络的最大重心就是 IP 和路由，像这种形式，你在每个层级章节把重心罗列并且详细讲解。

**本篇讲尺度链第 1 格：一张 GPU 卡内部。** 主角是 SM、显存、驱动、CUDA。物理范围从芯片内部到单卡 PCIe 插槽为止。

---

## 1. 学习重心（先罗列）

对标"学传统网络 = 学 IP + 学路由"：

```text
学卡内 = 学「并行模型」 + 学「内存层次」

重心一：并行模型 —— 线程怎么组织、怎么被调度到 SM 上跑
重心二：内存层次 —— 数据放哪、怎么搬，为什么带宽才是真瓶颈

其余都是配角：
  CUDA 语法      —— 只是表达并行模型的工具
  驱动           —— 只是把这套模型落到硬件上的接口
  各种库         —— 只是把常用算法按这套模型写好
```

**为什么是这两个**：因为卡内一切性能问题，最终都归到两件事——**活切得够不够细（并行）**、**数据喂得够不够快（内存）**。算得快不快看 SM 用没用满，跑得快不快看显存喂没喂上。这两个抓住了，看任何优化技巧都能归位；抓不住，背一百个 API 也是散的。

---

## 2. 重心一详解：并行模型

### 2.1 核心直觉：GPU 不是"更多核心"，是"另一种活法"

CPU 像几个聪明厨师：各自能做复杂的菜，但人少。
GPU 像几千个学徒：每人只会简单动作，但可以全体同时切菜。

```text
CPU：少量复杂线程，擅长分支、串行逻辑、低延迟响应
GPU：海量简单线程，擅长同一动作重复几万次，吞吐量优先
```

**关键转变**：写 GPU 程序不是"让一个线程算得快"，是"把问题切成几万个能同时干的小块"。切法对了，性能自然来；切法错了，再优化单行代码也没用。

### 2.2 必须建立的层级概念

```text
线程 thread          —— 最小执行单位，一个学徒
线程块 block         —— 一组线程，可以互相协作、共享一小块内存
网格 grid            —— 多个线程块，一次内核启动的全部工作
SM（流式多处理器）    —— 真正干活的车间，一个 SM 同时容纳多个线程块
warp                 —— 硬件调度单位：32 个线程绑一起，同进同退
```

这里最容易踩坑的是 **warp**：它解释了"为什么我的代码里有 if 分支就变慢"——同一个 warp 里的 32 个线程必须执行同一条指令，如果一半走 if、一半走 else，就得串行跑两遍。这叫 **warp 分歧（divergence）**，是卡内头号性能陷阱。

### 2.3 学到什么程度算掌握

```text
能回答：一次 kernel 启动，grid / block / thread 三层是怎么映射到几千个核心上的
能回答：为什么 block 大小是 256 或 512，不是 1000
能回答：为什么代码里一个分支会让性能掉一半
能判断：一个问题适不适合 GPU（能不能切成大量独立的相同动作）
```

### 2.4 与驱动的接口关系

CUDA 的 `<<<grid, block>>>` 是程序员写的意图；运行时把它翻译给驱动；驱动把线程块派到具体 SM 上。**线程怎么被调度到 SM 这件事，对程序员不可见**——这正是"分层屏蔽"的价值：你只管切活，不管派活。

## 3. 重心二详解：内存层次

### 3.1 核心直觉：算得快没用，喂不上就白搭

一个经典反差：GPU 的算力每年暴涨，显存带宽涨得慢。结果大量算力的时间都花在**等数据**上。

```text
寄存器 register   —— 贴身口袋，最快，容量极小，每个线程私有
共享内存 shared   —— 车间公共台面，一个 block 内可见，快但要手动管理
L1 / L2 缓存      —— 楼层小仓库，硬件自动管理
全局显存 HBM      —— 地下大仓库，容量大但搬运慢
```

**核心矛盾**：越快的地方越小，越大的地方越慢。优化的本质就是把"频繁用的数据"尽量往快的那层挪。

### 3.2 两个必懂的性能杀手

```text
非合并访问（uncoalesced access）
  warp 里 32 个线程如果各取一个不相邻的地址，硬件得发 32 次内存请求
  如果取连续地址，一次就能批量取回
  —— 所以"数组布局"和"线程编号"要对齐，这是卡内优化的第一课

共享内存 bank conflict
  共享内存分成 32 个银行，多个线程同时访问同一个银行就得排队
  —— 类似超市只开一个收银台
```

### 3.3 学到什么程度算掌握

```text
能回答：为什么改一下二维数组的遍历顺序，性能差十倍
能回答：什么时候该用共享内存手动缓存数据
能回答：为什么"算术强度"（算多少 / 搬多少）决定一个程序是算力受限还是带宽受限
能用 Roofline 模型判断：当前瓶颈在算力还是在带宽
```

### 3.4 Roofline：把两个重心合起来的尺子

```text
横轴：算术强度（每搬 1 字节数据做多少次计算）
纵轴：可达到的性能

  低算术强度区 → 被内存带宽卡住（带宽墙）
  高算术强度区 → 被算力卡住（算力墙）

优化方向只有两个：
  提高算术强度（多算少搬）—— 对应内存层次
  提高并行度（用满 SM）    —— 对应并行模型
```

**Roofline 是把这一篇两个重心缝在一起的那根线**：任何卡内优化，都能在上面找到自己是在抬哪条线。

## 4. 八问展开

```text
【是什么】
  一张 GPU 卡内部：SM 阵列 + 显存 + 互联出口。软件上是驱动 + CUDA。

【物理边界】
  管：单卡内部的计算与数据搬运
  不管：卡与卡之间怎么通信（那是尺度 2）

【跨哪道鸿沟】
  通用程序 ↔ 专有并行硬件。没有 CUDA，你写不了能跑在几千核心上的程序。

【内部构成】
  硬件：SM、warp 调度器、寄存器文件、共享内存、L1/L2、HBM
  软件：驱动（接口层）+ CUDA 运行时 + 编程模型（grid/block/thread）

【对上给什么 / 对下藏什么】
  对上给：一套"写并行"的抽象 —— 你写内核，不写寄存器
  对下藏：线程怎么被派到 SM、warp 怎么调度、缓存怎么替换

【概念归位】
  SM / HBM   = 物理硬件
  驱动        = 接口抽象（把硬件差异收敛成统一接口）
  CUDA        = 模型抽象（一种thinking并行的方式，不只是语言）
  warp / 合并访问 = 理解上面两个重心必须掌握的机制

【现在咋样 + 怎么用】
  主流：CUDA 13.x，HBM3/HBM3e 大容量，Tile 等新写法在出现
  典型场景：矩阵乘、卷积、归约 —— 全是"切块 + 喂数据"这两个重心的具体化

【为什么不能省 + 交接点】
  没有这一格：算力是 raw 晶体管，上面所有层都无处落脚
  交接点：PCIe / NVLink 出口 —— 单卡装不下、算不完时，交给尺度 2
```

## 5. 本篇小结

```text
一句话记住：卡内 = 并行模型 + 内存层次

并行模型回答"活怎么切"：grid → block → thread → warp → SM
内存层次回答"数据怎么喂"：寄存器 → 共享 → L1/L2 → HBM
Roofline 把两者缝起来：要么提高算术强度，要么用满 SM

最容易踩的坑：warp 分歧、非合并访问
最该建立的直觉：GPU 强在吞吐不强在单线程，优化是"切活+喂数据"两件事
```
