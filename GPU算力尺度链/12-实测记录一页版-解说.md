## 开篇：先搞清楚整套实验在赌什么

```text
一句话：我们没有 GPU、没有 RDMA 网卡、交换机也不归我们管，
       却想搞懂 GPU 集群里两件最核心的事——"多卡怎么协作"和"网络怎么不丢包"。

赌注是：这两件事的本质是"行为"和"流程"，不是"硬件"。
  多卡协作的本质 = 一堆进程怎么分工、怎么同步、怎么出错 → 用 CPU 进程就能真练
  网络不丢包的本质 = 队列满了怎么办（丢？标记？暂停？）→ 用真内核 + 仿真器能复现
  唯独练不到的 = 真实的 NVLink 带宽数字、真实的 IB 网卡、真实交换机 ASIC
```

**为什么要先立这个赌注**：因为否则你会一路疑惑"没有 GPU 学个啥"。这一整套实验的合法性就建立在这句话上——**要复现的是行为，不是硬件**。学习目标（会操作、懂机制）恰好都落在"行为"这一栏，练不到的只有数字，而数字不是学习目标。记住这句，后面每一节你都知道自己在干嘛。

**三个词先认识一下（后面天天出现）**：

```text
allreduce（规约求和）  把每张"卡"算出的梯度加在一起，再把结果发回给每张卡。
                      这是分布式训练里最重、最频繁的通信动作，本套实验拿它当"标本"。
gloo / NCCL           两个"通信后端"（干 allreduce 的库）。NCCL 是 NVIDIA 的、跑在 GPU 上；
                      gloo 是 PyTorch 自带的、CPU 上就能跑。本套用 gloo 代替 NCCL。
RTT（往返时延）        一个包从这台机到那台机再回来的时间。后面反复用"几个 RTT"解释小包时延。
```

## ① 资源与环境：为什么非要 3 台、非要 4 核、非要同一个区

```text
三台机器（本次实测，2026-11-24，香港）
  node0  公网 8.218.154.81   内网 172.23.163.99   角色：master + 仿真机 + incast 接收端
  node1  公网 8.217.147.56   内网 172.23.163.100  角色：worker + incast 发送端 A
  node2  公网 47.238.173.191 内网 172.23.163.101  角色：worker + incast 发送端 B

共同配置
  4 vCPU / 8 GiB，60 GiB ESSD 盘，Ubuntu 26.04
  Python 3.14.4、torch 2.15.0+cpu（gloo 可用）、iperf3、Docker
  同地域同可用区 cn-hongkong-c，同 VPC / 同交换机 / 同子网 172.23.163.0/20
  内网全通（安全组 ingress 放行 172.16.0.0/12 的 ALL）
```

**每一样东西为什么是它**：

```text
为什么 4 核，不是 2 核
  因为要在一台机上起 4 个进程模拟"4 张卡"。2 核跑 4 进程会四个抢两个核，
  扩展性验证直接得到负加速，你会误以为分布式没用。4 核才能让 1/2/4 进程有意义。
  另外 ns-3 编译要 -j4，核多也快。

为什么三台必须同一个可用区
  跨可用区的延迟不可控、忽高忽低。步骤 3、4 要量"机内 vs 机间"的时延差，
  如果机间延迟本身在抖，测出来的数字没有可比性，整个对照就废了。

为什么是内网 IP 连号（.99/.100/.101）
  说明三台落在同一个子网、同一台交换机下，网络路径最短最稳，RTT 才量得准。

为什么无 GPU 也敢叫"多卡模拟"
  我们模拟的是"4 张卡之间的协作流程"，用 4 个 CPU 进程代替 4 张卡。
  进程之间的通信从 NVLink 变成 TCP socket，但"起分布式、切数据、同步梯度、排障"
  这些动作和代码结构一模一样。换真机时只改 backend 从 gloo 到 nccl。

安全组那个 ingress ALL 是什么
  云主机默认只开 22 端口（SSH）。三台要互相通信，得放开内网端口。
  本次不用改——现成规则已经把 172.16.0.0/12 这个内网段全放了。
  要是没这条，你会卡在"能 ping 通但 torchrun 连不上"，很冤。
```

## ② 步骤总览：七步其实是一条逻辑链

```text
步骤 1  环境就位与互通   → 先保证机器能用、能互相找到
步骤 2  网络基线         → 量出"快"和"慢"的单位尺子
步骤 3  两级拓扑对照 E1  → 用尺子量"放同一台 vs 放不同台"的代价
步骤 4  延迟不对称 E2    → 故意弄慢机间，验证"小包看延迟、大包看带宽"
步骤 5  故障三连 E3      → 真出事（慢/死/重启）会怎样、怎么救
步骤 6  真 incast 与 ECN E4 → 在真内核上造拥塞，看丢包 vs 标记
步骤 7  仿真侧 E5        → 云上做不到的 PFC/DCQCN，交给仿真器
```

**为什么是这个顺序**：1 是地基，2 是尺子，3/4 用尺子量网络，5 量"出事"，6 把网络机制从"全靠仿真"推到"一半真"，7 补上云上物理做不到的那半。前一步的产出是后一步的前提——**没有步骤 2 的基线，步骤 3 的"慢 2 倍"就是一句空话**。

## ③ 步骤 1 · 环境就位与互通（先把地基夯实）

**这一步在解决什么初级人员最容易栽的跟头**：版本。Python 和 torch 版本不对，后面每个脚本都会以莫名其妙的方式失败；三台不在一个内网，跨机实验直接连不上。所以第一步不 figure 任何"高级机制"，只做一件事——把机器收拾干净、确认能互相到达。

**这次怎么做的**：三台都装同一套东西（vcpu/内存/磁盘核对 → 装 venv、iperf3 → 装 torch CPU 版 + numpy + matplotlib → 验证 gloo 可用），然后互相 `ping`。

```text
结果：三台 nproc=4、内存 7 GiB 可用、磁盘 59 GiB；gloo 可用；互 ping 0 丢包。
```

**怎么读这个结果**：这只是"及格线"，不是成果。它证明三台是同构的、内网是通的、分布式后端是装好了的。后面所有实验都踩在这块地基上。**如果这一步有问题，别往下走**——越往后排查越难。

> 讲给初级人员：`venv` 是一个隔离的 Python 环境，把这套实验的依赖和系统的其他 Python 隔离开，避免版本打架。`gloo 可用` 这行输出，就是我们"能模拟多卡"的通行证。

## ④ 步骤 2 · 网络基线（先造一把尺子）

**这一步在解决什么**：后面会反复说"跨机比机内慢 16 倍""加了延迟涨了多少"。这些"倍"和"多少"必须有参照物，否则就是拍脑袋。**基线就是那把尺子**。

**"环回"和"跨机"分别是什么**：

```text
环回（127.0.0.1）  包不出这台机器，从网卡转一圈就回来。用它模拟"同一台机器里两张卡的通信"（机内平面）。
跨机（172.23.163.x）包真的从这台机的 eth0 出去、经交换机、进另一台机。这是真实的机间通信（机间平面）。
```

**这次怎么做的**：在一台上起 iperf3 服务端，先自己打自己（环回），再从另一台打过来（跨机），分别量时延（ping）和带宽（iperf3）。

```text
结果（这就是后面所有讨论的物理基础）
  环回    RTT 0.031 ms    带宽 27.3 Gbps
  跨机    RTT 0.50 ms     带宽 3.77 Gbps（8 并发只有 3.14 Gbps）
  → 延迟差 16 倍、带宽差 7 倍
```

**怎么读、别读错成什么**：

```text
能读出的：在同一台机器上确实比跨机快一个量级。这就是"两级拓扑"存在的物理原因，
         也是真实集群"机内用 NVLink、机间用 IB"的原因——因为机内和机间本来就不是一张网。
别读错的：别拿这两个比值去等于真实硬件。
         真实的 NVLink vs IB 是"带宽差约 18 倍、延迟差约 3 倍"；
         云上却是"带宽差 7 倍、延迟差 16 倍"。方向对（机内就是快），
         但一个倍数被压缩、一个被夸大。云上只能证明"同机确实快"这个定性结论，不能当真机数字。
```

> 讲给初级人员：`iperf3 -P 8` 是同时开 8 条流。跨机单流能到 3.77 Gbps，但 8 条流一起只分到 3.14 Gbps——说明这条内网链路的总容量就这么多，多条流要共享，每条反而更慢。这个现象在后面的 incast 实验里会以更极端的形式出现。

## ⑤ 步骤 3 · 两级拓扑对照 E1（整套方案的核心实验）

**这一步在解决什么、为什么是核心**：真实 GPU 集群是"两级"的——一台机器内部的卡用 NVLink 高速互连，机器之间用 IB 网络。单机模拟只有"一级"，永远讲不清"为什么机内要 NVLink、机间要 IB"。三台机终于有了两个平面。这一步就专门量"把通信密集的任务放一起 vs 分开"到底差多少。

**"world 固定 4、只改放在哪"是什么意思（这是全程最干净的一组对照）**：

```text
world = 参与通信的进程总数。固定成 4，就是每次都让 4 个进程一起做 allreduce。
只改"放在哪"，就是保持"4 个进程、同一份代码、同一个数据量"完全不变，
             唯一变量是这 4 个进程分布在几台机器上：
  场景 A  4 个全在 node0        → 全走环回，模拟"一台机器里的 4 张卡"
  场景 B  2 个在 node0 + 2 个在 node1 → 跨机通信，模拟"两台机器各出 2 张卡"
  场景 C  2 + 1 + 1 分布在三台  → 跨三台通信

为什么要固定 world：科学实验只改一个变量。如果进程数也跟着变，你就分不清
                   变慢是因为"放得散"还是因为"进程多"。
```

**这次怎么做的**：先跑场景 A（单机 4 进程，`torchrun --standalone`），再跑场景 B（跨两机，`torchrun --nnodes=2`，两台都要执行、只改 `--node_rank`，并指定 `GLOO_SOCKET_IFNAME=eth0` 让通信走内网网卡）。

```text
在这次实测里（gloo + eth0，iters=20）
  4 进程全在 node0     1MB 4.41 ms    64MB 110.5 ms   busbw 0.848 GB/s
  2+2 跨两台           1MB 6.71 ms    64MB 232.3 ms   busbw 0.404 GB/s   （2.1 倍）
  2+1+1 跨三台         1MB 6.72 ms    64MB 250.6 ms   busbw 0.374 GB/s   （2.3 倍）
  8 进程 / 2 台                       64MB 266.0 ms   busbw 0.411 GB/s
  12 进程 / 3 台                      64MB 305.6 ms   busbw 0.375 GB/s
```

**怎么读、别读错成什么（这一节最需要讲清）**：

```text
能读出的：代码一样、world 一样、数据量一样，只把进程放散，64MB allreduce 从 110ms 涨到 250ms。
         这就是"放置代价"——把需要频繁通信的东西放同一台机器，能省一倍多的时间。
         这就是"拓扑决定上限"的实证，比任何一张架构图都有说服力。

别读错的①：不要说"2.3 倍全是网络的锅"。
         64MB 这个档位里，CPU 做规约（把 4 份数据加起来）本身也花了不少时间，
         这部分跟放哪没关系。所以 2.3 倍里混了"网络变慢"和"CPU 固定开销"。

别读错的②：想看纯粹的"放置开销"，看 1MB 那一组更干净——
         4.41 → 6.72 ms，约 1.5 倍。数据小、CPU 规约几乎不花时间，
         差出来的主要就是网络。这一组更接近"放散的纯代价"。
```

> 讲给初级人员：`busbw`（总线带宽）是把"数据量 ÷ 时间 × 一个与进程数有关的系数"算出来的有效带宽，比单纯看时延更能反映"网络被用得充分不充分"。这里从 0.848 掉到 0.374 GB/s，说明分散放置后网络没被喂饱，大量时间花在等通信上。

## ⑥ 步骤 4 · 延迟不对称 E2（验证"小包看延迟，大包看带宽"）

**这一步在解决什么**：上一步说明了"放散会慢"，这一步要挖深一层——**慢在哪个环节**。真实机内是微秒级、机间是毫秒级，这个不对称决定了"通信密集的任务必须放同机"。做法是只给机间链路（eth0）注入延迟，机内（环回）一点不动，然后看不同大小的数据包分别怎么变。

**"注入延迟"是什么、用什么做的**：

```text
用 Linux 的 tc netem（流量控制里的"网络仿真"模块）给 eth0 人为加上 1ms、3ms 延迟。
相当于在机间这条路上人为设了个"减速带"，但机内的环回完全不受影响。
配套脚本 inject_latency.py 封装了这些命令（内部已经把 tc 的层次结构修正对了）。
做完实验必须 --clear 清掉，否则后面所有网络操作都还在减速带上运行。
```

**这次怎么做的**：三台都给 eth0 加 1ms，重跑步骤 3 的场景 B；再加到 3ms 跑一轮；最后清理。

```text
结果（world=4）
             基线        +1ms/边     +3ms/边
  1MB        6.71 ms     17.60 ms    41.82 ms
  64MB       232.3 ms    279.6 ms    446.8 ms
```

**怎么读（这两行是整个实验最有味道的对比）**：

```text
1MB 这一行：延迟从 +1ms 加到 +3ms（约 3 倍），时延从 6.71 涨到 41.82（约 6 倍）。
         把基线放回来看，1MB 的 allreduce 大约等于 6 个 RTT。
         → 小数据包：时延几乎完全由"来回跑几趟"决定，加速带就线性变慢。这叫"延迟受限"。

64MB 这一行：延迟同样加了 3 倍，时延只从 232 涨到 447（约 1.9 倍，相对涨幅小得多）。
         → 大数据包：时间主要花在"把这么多字节搬过去"，由带宽决定，延迟加再多也影响有限。
           这叫"带宽受限"。

一句话："小包看延迟、大包看带宽"。这句网络界的老话，这次是你自己量出来的，不是背的。
```

> 讲给初级人员：为什么是"6 个 RTT"？因为一次 allreduce 不是发出去就完事——它要约好几轮（建立连接、分段收发、确认），每一段都要来回。把这些来回加起来大约 6 趟，所以 RTT 涨 1ms，总时延就涨约 6ms。这就是"6 个 RTT"的来历。

## ⑦ 步骤 5 · 故障三连 E3（真出事会怎样、怎么救）

**这一步在解决什么**：尺度 3 的工程动作里，大约 75% 是"多机启动 + 排障 + 基准 + 容错"。这些只有至少两台机器才做得出来——单机能练进程协作，练不出"另一台机器出事了"。这一步故意制造三种真实故障。

**三个故障分别是什么、为什么各有意义**：

```text
E3a 慢节点    让 node2 的 4 个核全部跑满（一个死循环占一个核），
             看另外两台在 allreduce 上等它多久。
             → 模拟"集群里有一台机器性能拉胯"，真实训练里很常见。

E3b 掉线      给 node2 的训练进程套一个 12 秒的 timeout，到点直接杀掉，
             看剩下两台什么反应、多久退出。
             → 模拟"节点突然宕机"，这是最需要排障的故障。

E3c 续训      让训练跑一半被杀，再从保存的 checkpoint（断点）接着跑。
             → 模拟"长训练中途挂了怎么救"，多机训练跑几天，这是常态。
```

**这次怎么做的、跑出什么**：

```text
慢节点   1MB 6.72→8.03 ms（+19%），64MB 250.6→246.1 ms（基本不动）
掉线     node0/node1 立刻报：Read error [172.23.163.101]:1252: Connection reset by peer
         19 秒退出，退出码 1；报错直接指出死节点的 IP
续训     第一段被 kill（退出码 124），最后存盘在 step=2000
         第二段加载 step=2000，跑到 5000，退出码 0
```

**怎么读、别读错成什么（这里有两条必须诚实）**：

```text
慢节点：别读成"慢节点无害"。1MB 只涨 19%、64MB 几乎不动，是因为
       我们这个实验里每个进程的计算量太小了，allreduce 等待占主导，
       慢一点的计算被通信掩盖了。真实训练的计算量大得多，慢节点的效应会明显放大。

掉线：这才是真实世界——"节点掉线"不是安静地挂起，而是 TCP 连接被 reset，
     报错信息里直接带着死掉那台的内网 IP（172.23.163.101）。
     学会看这个报错指向谁，就是排障的第一步。

续训：checkpoint 是"存档点"。被杀后从 step=2000 接上而不是从头来，
     省下的是前面 2000 步的算力——这就是容错的钱。
```

> 讲给初级人员：退出码 124 是 Linux `timeout` 命令"我把它杀掉了"的固定信号，不是程序报错。看到 124 就知道"这是实验故意杀的，不是程序崩了"。

## ⑧ 步骤 6 · 真 incast 与 ECN E4（在真内核上看丢包变成标记）

**这一步在解决什么、为什么关键**：前面讲网络机制如果全交给仿真器，你摸不到任何真实计数器。这一步在接收方（node0）的内核里造一个真实的"入向拥塞队列"，让"多打一 → 队列积压 → 要么丢包、要么打标记"变成一个能读数的真过程。**这是整套实验里最有说服力的一条——因为它发生在真的 Linux 内核里，不是仿真。**

**先认识几个东西**：

```text
incast（多打一）  很多发送方同时给一个接收方发数据。训练里"很多卡同时把梯度发给一张卡"
                 就是典型 incast。本实验用 node1、node2 各 4 条流，共 8 条同时打 node0（8:1）。

ECN（显式拥塞通知）  一种"不丢包的拥塞处理"。队列快满时，交换机/内核不丢包，
                    而是在包上打个"我快满了"的标记（CE）。接收方看到标记就通知发送方
                    "你慢点"，发送方提前降速——避免丢包和重传。

RED             一种队列管理算法："队列到什么程度开始打标记、什么程度开始丢包"由它的
                参数（min/max/probability）决定。加 `ecn` 关键字就变成"打标记"而不是"直接丢"。

ifb             一个虚拟网卡，专门用来给"入方向"的流量挂队列规则。因为 Linux 默认只能在
                出方向做流量控制，要把入向流量先重定向到 ifb，才能在上面排队、打标记。
```

**这次怎么做的（理解思路即可，不必背命令）**：

```text
1  在 node0 上建 ifb 虚拟网卡，把发往 5201 端口（iperf3 测试端口）的入向流量引到它上面。
   只拦 5201，不动 SSH 的 22——否则会把自己远程登录掐断。
2  在 ifb 上建一个限速 2Gbit 的队列 + RED，8 条流打了 12 秒（总需求远超 2Gbit，必然拥塞）。
3  三台都打开 tcp_ecn，让内核愿意参与 ECN 协商。
4  做两组对照：一组 RED 带 ecn（打标记），一组去掉 ecn（纯丢包）。读 tc -s 的计数器。
```

**这次跑出的数（真内核计数器）**：

```text
ECN 开   1,842,627 包   marked 1564   dropped 19
ECN 关   1,863,758 包   marked 0      dropped 1546   ← 丢包多 81 倍
```

**怎么读（这是全套最该记住的一条因果）**：

```text
同一份流量、同一份带宽，唯一区别是"开不开 ECN"：
  关 ECN：队列满了就丢包，丢了 1546 个。
  开 ECN：队列快满时提前打 1564 个标记，只丢了 19 个。

也就是说，ECN 把"丢 1546 个包"换成了"打 1564 个标记"——
发送端收到标记后提前降速，队列没来得及溢出，就不需要靠丢包和重传兜底。

这就是"ECN 把丢包换成标记"的真实版本，是在 tc -s 的内核计数器上量出来的，
不是课件上的示意图。记住这个 81 倍的对比，比背十遍定义都管用。
```

> 讲给初级人员：为什么丢包不好？丢一个包，发送方要等超时才发现、再重传，这一等一传就是延迟和吞吐的损失（尤其训练这种"一个梯度都丢不起"的场景）。ECN 的思路是"与其等它溢出，不如提前打招呼"，把代价从"重传"降到"降速一点"。

## ⑨ 步骤 7 · 仿真侧 E5（云上做不到的 PFC/DCQCN，交给仿真器）

**这一步在解决什么、为什么必须仿真**：PFC 和 DCQCN 这两样，在云上物理上做不到——交换机不给你配 PFC 阈值，虚拟网卡也发不出 pause 帧。所以只能靠离散事件仿真器，逐包地跑这些协议状态机。这一步的目标是：把环境搭起来、把 trace 变成可读的数。

**先认识几个东西**：

```text
ns-3          一个网络仿真器。"离散事件"意思是：它不真的发包，而是在内存里按时间顺序
              模拟每个事件（包到达、队列满、发标记……），所以能精确控制、反复重来。
HPCC fork     一个基于 ns-3 的开源项目，实现了 DCQCN、PFC、ECN 等一整套数据中心网络机制，
              还自带 incast 实验样例。我们直接站在它的肩膀上，不用从零写协议。

PFC           链路级的"暂停"机制：队列快满时，直接发一个 pause 帧让上游"停一下"。
              和 ECN 的区别：ECN 是端到端标记、发送方自己降速；PFC 是链路级强制刹车。

DCQCN         一种数据中心拥塞控制算法：交换机打 ECN 标记 → 接收方回 CNP 通知 →
              发送方降速 → 队列回落 → 再慢慢恢复。这是个完整的反馈回路。

二进制 trace  仿真器把每个包事件写成一个固定长度的结构体（TraceFormat，56 字节一条），
              一路写进 mix.tr。它不是文本，不能用文本工具读，要按字节格式解析。
```

**这次怎么做的（四个子步骤）**：

```text
1  用 Docker 搭老环境：这些仿真器基于 ns-3.17，需要 gcc-5 + python2，
   新环境编译不过。镜像构建实测 55 秒。
2  拉 HPCC 源码，在容器里 configure（2.3 秒）+ 编译。
3  跑自带的 incast 样例：39 秒跑完一个 4 秒的仿真场景，产出 246MB 的 mix.tr。
4  用专用解析器 parse_hpcc.py 把二进制 trace 解析成四个量。
```

**"四个量"是什么、为什么要这四个**：

```text
per-flow 吞吐       每条流各拿到多少带宽 → 看公不公平、有没有流被饿死
总吞吐              所有流加起来多少     → 看链路有没有被打满
交换机队列最大值     队列涨到多高         → 看有没有接近 ECN/PFC 门限
Drop 与 ECN CE 计数  丢了多少、标记了多少 → 看拥塞控制到底生效没有
```

**这次跑出的数、怎么读**：

```text
解析：246MB / 440 万条记录，四个量都算出来了。
      另有旁证文件 fct.txt（每流完成时间）、pfc.txt（PFC 事件）。

8:1 incast（100Gbps）曲线：
  8 条流同时从 t=2.000s 起，各约 1200–1500 MB/s
  总吞吐一步跳到 12,800 MB/s ≈ 102 Gbps —— 正好打满 100G 线速
  流陆续完成（2.0244→2.0354s），先退出的把带宽让给剩下的（涨到 3000–7000 MB/s）
  交换机队列起跳瞬间冲高 400,000，随即回落

算法对照（同场景，看完成时间 FCT 分布）：
  HPCC   25.95 / 34.07 / 36.94 ms（最小/中位/最大）—— 有快有慢
  DCQCN  全部 33.20 ms —— 完成时间高度对齐
  → 两种拥塞控制在"公平性和收敛"上的差别，从完成时间分布就能读出来。
```

**这里必须诚实说清的一条边界（别读错成"验证了 PFC/ECN"）**：

```text
在这次这套样例配置下：
  ECN CE 标记 = 0，Drop = 0，pfc.txt = 0 行 —— 全程什么都没触发。
  改 ENABLE_QCN、USE_DYNAMIC_PFC_THRESHOLD、BUFFER_SIZE 三个旋钮，结果逐位不变。

怎么理解：8 打 1 确实把 100G 链路打满了（总吞吐=线速），队列起跳也确实冲高到 400KB，
         但缓冲把它吸收了，既没到 ECN 标记门限，也没到 PFC 门限 —— 所以全 0。
         这是"没跨过门限"，不是"机制不存在"。

能读出的：这套样例能演示"incast 打满链路 + 队列瞬时冲高"。
不能声称的：它演示不了"超过门限后 PFC 刹车 / ECN 降速"那一步。
            想触发，得造真正的汇聚瓶颈（把接收方那条链路单独压低），留作下一步。

所以 again：ECN 机制的可靠实证在步骤 6（真内核，marked 1564 vs dropped 1546），
            不在步骤 7 的样例。两条不要混为一谈。
```

> 讲给初级人员：为什么会"队列冲高又回落、但没触发任何机制"？想象一个水库（缓冲），8 条河同时灌进来灌了一下，水位猛涨一下但没漫过警戒线（门限），水库自己就把它消化了。要看到"泄洪"（PFC/ECN），得让灌进来的水量真的超过警戒线——这就是"造汇聚瓶颈"的意思。

## ⑪ 判官卡：哪些结论能当真，哪些只能存疑

```text
结论来源分三种，可信度不一样（这是"判断力"训练的核心）：

真机实测（最可信）
  E1/E2 的时延、E3 的故障现象、E4 的 ECN 计数器
  → 这些是三台真机器、真内核上跑出来的，可以直接信。

仿真器（理解机制可信，数字不可信）
  E5 的吞吐曲线、队列冲高、算法 FCT 分布
  → 用来理解"机制怎么闭环"没问题；但 buffer 模型是研究模型，
    不是某款真交换机，不能拿数字当真机性能。

没拿到信号的（存疑，别写成已验证）
  E5 里的 PFC 触发、DCQCN 降速曲线 —— 本次样例没跨过门限，
  三个旋钮也改不动。要下结论，得先造出真正的汇聚瓶颈再跑。

判据：一条结论能不能迁移到真机，先看它属于哪一类。
      真机类直接迁；仿真类只迁"因果方向"，不迁数字；没信号类不许下结论。
```

## ⑫ 这一章的坑（讲给初级人员：现象 / 根因 / 怎么防）

```text
现象  ns-3 编译报 ns3/broadcom-node.h 找不到
根因  这个 fork 把类挪了位置，但三处代码还引旧名字
防    建一个空的同名头文件放到 build/ns3/ 即可编过（编译三个坑之一）

现象  waf configure 报 python 相关错
根因  waf 只认 python2
防    configure 前先 ln -sf /usr/bin/python2.7 /usr/bin/python

现象  脚本里 docker run -it 报 ttyname failed
根因  非交互脚本里没有 TTY
防    用 docker run --rm ... bash -lc '命令'，去掉 -it

现象  把链路速率从 100G 改成 10G，仿真直接断言崩掉
根因  HPCC 的 KMIN_MAP 没覆盖 10G（25G/50G/100G 才行）
防    改速率前确认在映射覆盖集合内

现象  用文本工具读 mix.tr，出来一堆乱码、算不出数
根因  它是二进制 TraceFormat（56 字节/条，文件头 38 字节）
防    用专用解析器 parse_hpcc.py

现象  inject_latency 的限速/延迟不生效，还谎报成功
根因  tc 的层次挂反了：netem 是无类 qdisc，不能挂在 tbf 的 1:1 下面
防    正确顺序是 root 建 tbf（有 class）、再在 parent 1:1 挂 netem

现象  RED 参数算不出 EWMA、标记率恒为 0
根因  burst 给太小（20）
防    burst 给 100，并把 bandwidth 显式写上

现象  在 ifb 上拦了全量入向流量，结果自己 SSH 断线
根因  把 22 端口的入向流量也拦进拥塞队列了
防    tc filter 只 match 实验端口（如 5201），别动 SSH

现象  Git Bash 里用 scp/ssh 传路径，/root 被改成本地盘符路径
根因  MSYS 的路径自动转换
防    命令前加 MSYS_NO_PATHCONV=1

现象  多节点 torchrun 启动撞车，rendezvous 连不上
根因  几台机器同时抢着连主节点
防    worker 比主节点晚 2 秒启动（错峰）
```

## 一句话总结

```text
这套实验用三台没有 GPU 的普通云主机，把 GPU 集群的两件事"演"了出来：

  多卡协作这边——用 4 个 CPU 进程代替 4 张卡（gloo 后端），
  量出了"放同一台比放不同台快一倍"（拓扑），
  验证了"小包看延迟、大包看带宽"（延迟注入），
  走通了"慢节点/掉线/续训"三种真实故障。

  网络机制这边——在真内核上把"ECN 把丢包换成标记"量出来（81 倍差），
  又用 ns-3 仿真器逐包跑了 PFC/DCQCN 的状态机、解析了二进制 trace。

全程守一条诚实底线：要复现的是行为、不是硬件；
真机的结论直接信，仿真的只信因果方向，没拿到信号的一律不写成"已验证"。
读完这份，初级人员应该能回答：为什么放同机更快、为什么小包怕延迟、
ECN 到底改变了什么、以及"仿真结果能不能信"该怎么判断。
```
