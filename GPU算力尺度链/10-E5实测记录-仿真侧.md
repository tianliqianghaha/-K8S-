# E5 实测记录 · 仿真侧（ns-3 / HPCC fork）

> 本文只记"实际跑出来什么"，不写计划。配套手册是 08 的第四部分，配套的解析器是
> `模拟实验包/parse_hpcc.py`。

## 1. 工具链实测（node0，4 核）

```text
docker build（ubuntu:16.04 + gcc-5 + python2.7）   55 秒
git clone --depth 1 HPCC fork                      约 10 秒
./waf configure（CC=gcc-5）                        2.3 秒
./waf build -j4                                    数分钟（增量）
跑一次 scratch/third 仿真（仿真 4 秒场景）          39–42 秒墙钟
产出 mix/mix.tr                                     246 MB
```

三个坑（详见 08 手册 10.1）：

```text
① broadcom-node.h 找不到 → 建 shim 到 build/ns3/broadcom-node.h
② waf 只认 python2 → ln -sf /usr/bin/python2.7 /usr/bin/python
③ docker run -it 在脚本里报 ttyname failed → 改用 bash -lc
另有一个新坑（本次才踩到）：
④ 把链路速率从 100Gbps 改成 10Gbps → 断言失败
   "must set kmin for each link speed"（third.cc:755）
   原因：HPCC 的 KMIN_MAP/KMAX_MAP 必须覆盖拓扑里每一种链路速率。
   100G 改成 25G 可以（映射里有 25000000000），改成 10G 就会断言。
```

## 2. 二进制 trace 与解析器

```text
结构体 TraceFormat（src/point-to-point/model/trace-format.h）
  sizeof=56  align=8（容器内实测打印，不是猜）
  0    uint64 time(ns)      8   uint16 node     10  uint8 intf
  11   uint8  qidx          12  uint32 qlen     16  uint32 sip
  20   uint32 dip           24  uint16 size     26  uint8 l3Prot
  27   uint8  event(0 Recv/1 Enqu/2 Dequ/3 Drop)
  28   uint8  ecn(3=CE)     29  uint8 nodeType(0 host/1 switch)
  32   union 24B：data{sport,dport,seq,ts,pg,payload} / cnp / ack / pfc / qp

文件头有 38 字节（n % 56 == 38），不是整条记录 → 解析器要自动探偏移。
探测方法：按 event<=3、nodeType<=1、time<=10s 的"合法率"打分，得分最高的偏移即真偏移
（实测 38 字节，合法率 99.33%，其余 7 个候选偏移的合法率都明显低）。

另发现：4,400,025 条记录里有 20 条字段非法（文件尾部半条或垃圾），解析时丢弃，占 0.00045%。
```

`parse_hpcc.py` 现在能出四个量：

```text
per-flow 吞吐（按 Recv 事件 + size 累加）
总吞吐 mean/peak
交换机队列最大值（switch 事件的 qlen 字段）
Drop 数、CE 标记数（ecn==3）
外加 fct.txt（每流完成时间）、pfc.txt（PFC 事件）
```

## 4. 这些数字说明了什么（看完图之后校正过的版本）

```text
先说一句自我纠正：
只看 fct.txt（8 条流全是 33.20ms）我一度以为仿真给的是"静态均分"。
把 trace 画出来之后发现不是——图上有真实动态，结论要改。

图（res/hpcc8/trace.png，8:1 incast / 100Gbps / HPCC）：
  ① 8 条流同时从 t=2.000s 开始，每条约 1200–1500 MB/s（≈10–12 Gbps）
  ② 总吞吐从 0 一步跳到 12,800 MB/s —— 也就是 102 Gbps，正好打满 100G 线速
  ③ 流不是同时结束：2.025 → 2.035s 陆续完成；先完成的流退出后，
     剩下 2–3 条流各自动涨到 3000–7000 MB/s（分到更多带宽）
  ④ 交换机队列在 t=2.000 起跳瞬间冲高到 400,000，之后立刻回落到接近 0
  ⑤ ECN CE 标记 = 0、Drop = 0、pfc.txt = 0 行

怎么读这张图（这是对的东西）：
  8 打 1 确实把接收方那条 100G 链路打满了（总吞吐 = 线速），
  起跳瞬间也确实把队列顶起来一次（400KB），
  但缓冲把它吸收了，既没到 ECN 标记门限，也没到 PFC 门限 —— 所以全 0。

  也就是说：**这个样例能演示"incast 打满链路 + 队列瞬时冲高"，
  但演示不了"超过门限后 PFC 刹车 / ECN 降速"那一步。**

三个旋钮（ENABLE_QCN / USE_DYNAMIC_PFC_THRESHOLD / BUFFER_SIZE 32→1）改了之后
结果逐位不变，说明它们没有改变上面那条因果：
  · 要么这几个参数没接到数据面
  · 要么门限远高于 400KB 这个量级，改 BUFFER_SIZE 也没把它拉下来
两种可能都要读代码确认，不能猜。

HPCC 与 DCQCN 的差别（这个差别是真的，但别拿它讲 ECN）：
  HPCC   FCT  min 25.95 / med 34.07 / max 36.94 ms —— 有快有慢，和图上"陆续完成"一致
  DCQCN  FCT  全部 33.20 ms —— 完成时间完全对齐，图上曲线也更平
  这是"两种 CC 的公平性/收敛行为不同"，不是"ECN 开关"的效果。

所以：ECN 机制的可靠实证在 E4（真内核），不在 E5（这套样例）。
E4 拿到 marked 1564 vs dropped 1546（81 倍差）是真信号；
E5 这套配置只拿到"队列冲高 400KB 后回落"，没有跨过门限。
```

## 5. 要让 PFC/ECN 真正触发，下一批该拧的旋钮（按可能性排序）

```text
1  造真正的"汇聚瓶颈"：现在 8 个发送方各有一条 100G 到交换，接收方也是 100G，
   8 打 1 却在仿真里被均分掉了。要在 topology.txt 里把"接收方那一条链路"单独压低
   （比如 8 个发送 100G、接收方 25G），才是教科书式的 incast 汇聚。
2  确认 BUFFER_SIZE 的单位（1 到底是多少字节），以及它是否真的作用在交换机队列上。
   实测 BUFFER_SIZE 从 32 改到 1，结果逐位不变 —— 这条本身就说明它没生效，或单位很大。
3  查 CC_MODE 是否真的切到 DCQCN 数据面：对比 R1 与 R3 只差 FCT 分布，
   没有出现 DCQCN 应有的"降速—恢复"锯齿，值得直接读 rdma-hw.cc 的 cc_mode 分支。
4  PFC 通道：pfc.txt 全程 0 条，需要确认这个 fork 的 PFC 触发条件
   （USE_DYNAMIC_PFC_THRESHOLD 之外是否还有 PFC 使能开关）。
```

## 6. 结论

```text
能确定的：
  仿真器可编译、可运行、可出二进制 trace，解析器能把四个量算出来（吞吐/队列/Drop/CE）。
  链路速率必须落在 KMIN_MAP 覆盖的集合里，否则断言。
  这套样例配置下 PFC/ECN 不触发，三个相关旋钮改不动结果 —— 不能拿它演示机制开关。

不能确定的（留给下一批）：
  PFC 到底怎么才能触发、DCQCN 的降速曲线长什么样。
  这两条在 E5 还没拿到，别在文档里写成"已验证"。
```
