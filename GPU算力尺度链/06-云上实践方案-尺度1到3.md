# 云上实践方案 · 尺度 1–3

> **路线定位（整理时补）**：本文的前提是"租得起 GPU 云主机"（三档 A/B/C，成本几十到上千元），回答"有 GPU 时能练到什么"。
> 若条件是"普通云主机、无 GPU、必须模拟"，走 07 号（换载体思路）与 09 号（3 台机最终落地）。三篇是同一问题在三种条件下的答案，不是三套并行方案。
> 本文第 4 节的"工程师 80% 清单"是全套文档反复引用的基准，保留。

## 0. 本篇对象

> **原样题面**：这些东西普通云服务器能模拟实践吗？尺度 1 到 3，多台服务器可以吗？我想要你罗列一下方案。要求实现，环境部署，然后 1 到 3 每个尺度工程师经常做的 80% 的事情。

一句话结论：**尺度 1 完全能，尺度 2 要选机型，尺度 3 功能能跑、物理机制看不到。** 钱从几块一小时到几百一小时，差别全在"网络"。

---

## 1. 可行性总判断（先看能学到什么）

```text
尺度 1 · 卡内
  可模拟程度：★★★★★ 完全
  普通单卡 GPU 云主机即可（按分钟租的那种）
  能学到：并行模型、warp 分歧、内存层次、合并访问、Roofline、profile
  学不到：芯片物理细节（本来也不需要）

尺度 2 · 机内多卡
  可模拟程度：★★★★☆ 取决于机型
  必须"单机多卡整机"，且确认 NVLink / NVSwitch 拓扑
  能学到：拓扑、NCCL、AllReduce 算法、通信计算重叠、多卡启动
  学不到：如果机型只有 PCIe 没有 NVLink，学不到 NVLink 那一档的高速行为

尺度 3 · 集群内 AI Fabric
  可模拟程度：★★☆☆☆ 功能能跑，机制看不到
  多台服务器可以——但要分两种"模拟"：
    功能模拟：普通云主机 + 内网就能跑多机 DDP 训练（能学到启动、配置、排障）
    物理模拟：PFC / ECN / DCQCN / 大象流这些看不到
             因为交换机在云厂商手里，流控配置对你屏蔽
  能学到：多机启动、网卡配置、nccl-tests 基准、超时挂死排障、通信调参
  学不到：无损网络的真实行为（想学这个得自建 IB 集群或白牌交换机）
```

**最关键的一句**：普通云服务器能让你学会尺度 1、2 的**全部**，和尺度 3 的**工程操作层**；但尺度 3 的**网络原理层**（无损、拥塞控制）在云上是黑盒。想补这一层，要么读文档 + 看交换机的写真值，要么自己搭小物理集群。

## 2. 三档方案罗列

```text
【方案 A】单卡入门 —— 专攻尺度 1
  配置：单张 GPU（3090 / 4090 / T4 等），16–24G 显存
  平台：按分钟租的 GPU 平台（AutoDL 等）或大厂按量单卡实例
  成本：约 0.5–2 元/分钟，学几小时几十块钱
  能覆盖：尺度 1 全部
  适合：第一次上手，先搞懂并行和内存两个重心

【方案 B】单机多卡 —— 尺度 1 + 2
  配置：一台 8 卡整机（A100 / V100 / 4090 ×8），确认 NVLink / NVSwitch
  平台：AutoDL 8 卡整机、阿里云 gn6e/gn7e、腾讯云 GN10Xp
  成本：整机按分钟约几元到十几元/分钟，按小时几十到上百元
  能覆盖：尺度 1 全部 + 尺度 2 全部（拓扑真实）
  注意：租之前问清楚"卡间是 NVLink 全互联还是只有 PCIe"——
        这决定你能否学到尺度 2 的拓扑重心
  适合：系统性学完前两个尺度

【方案 C】多机多卡 —— 尺度 1 + 2 + 3 的功能层
  配置：2–4 台多卡服务器，同地域同可用区，内网互通；
        要学 RDMA 就选带 RDMA/IB 的机型（如阿里云超算集群、UCloud RDMA 裸金属）
  平台：大厂 GPU 集群实例 / 裸金属（普通 VPC 也能跑，但没有无损）
  成本：多机整机，每小时几百元起，RDMA 机型更贵
  能覆盖：尺度 3 的工程操作层（启动、配置、排障、基准）
  学不到：交换机侧的无损机制（云厂商屏蔽）
  适合：已经掌握 1、2，要练分布式训练工程能力
```

**选择建议（按学习路径，不是按预算）**：

```text
第一步  方案 A 把尺度 1 的两个重心练到能 profile、能优化
第二步  方案 B 把尺度 2 的拓扑 + 集合通信练到能调 NCCL、能看拓扑
第三步  方案 C 练尺度 3 的多机工程——但要清醒：你学的是操作，不是网络原理
补充    尺度 3 的原理层用"自建 2 节点小集群 + 白牌交换机"或读文档 + 抓包视频补
```

## 3. 环境部署（每档具体步骤）

### 3.1 通用底座（三档都要）

```text
1. 选平台与机型
   单卡：按分钟租的 GPU 平台，选 PyTorch 预装镜像
   多卡：选"整机"而非"单卡"，下单前确认卡数和互联方式

2. 验证 GPU 与驱动
   nvidia-smi                    看卡型号、驱动版本、显存
   nvidia-smi topo -m            看卡间拓扑（多卡必做，尺度 2 的核心）
   python -c "import torch; print(torch.cuda.is_available(), torch.cuda.device_count())"

3. 确认软件栈版本
   nvcc --version                CUDA toolkit
   python -c "import torch; print(torch.__version__, torch.version.cuda)"
   注意：PyTorch 自带对应 cuDNN，通常不用单独装

4. 装监控与分析工具
   pip install nvidia-ml-py      Python 读 GPU 状态（DCGM 的轻量替代）
   Nsight Systems / Nsight Compute   nvidia-smi 之外最该装的两个工具
```

### 3.2 尺度 1 部署重点（单卡 profile 环境）

```text
目标：能观测到 warp 分歧、内存访问模式、Roofline 瓶颈

装分析工具：
  nsys profile python train.py             看整体时间线、kernel 占比、CPU/GPU 协同
  ncu --set full python single_kernel.py   看单个 kernel 的 occupancy、内存吞吐、分支效率

写第一个 kernel（二选一）：
  Triton（推荐，上手快）：@triton.jit 写向量加法，改 BLOCK_SIZE 看性能变化
  CUDA C：写 vector add，故意写非合并访问版本，对比合并访问版本

必做的对比实验（把重心变成手感）：
  实验 1  同一个加法，block=32 / 128 / 512 / 1024，看 occupancy 和耗时
  实验 2  连续访问 vs 跨步访问数组，看带宽差几倍
  实验 3  带 if 分支 vs 无分支 kernel，看 warp 分歧的影响
  实验 4  算一个矩阵乘，算算术强度，在 Roofline 上定位是算力受限还是带宽受限
```

### 3.3 尺度 2 部署重点（单机多卡）

```text
目标：确认拓扑、跑通 DDP、学会调 NCCL

确认拓扑（这一步不能跳）：
  nvidia-smi topo -m
  看输出：NVLink 显示 "NV#" 表示 NVLink 直连，PCIe 显示 "PXB/PXI"
  如果是 "PHB" 表示经过 CPU 根桥，通信最慢

跑 nccl-tests 基准（单机 8 卡）：
  git clone https://github.com/NVIDIA/nccl-tests.git
  cd nccl-tests && make CUDA_HOME=/usr/local/cuda
  ./build/all_reduce_perf -b 8M -e 8G -f 2 -g 8
  看 algbw（算法带宽）和 busbw（总线带宽），对比不同算法

起 DDP 训练：
  torchrun --nproc_per_node=8 train_ddp.py
  或 torchrun --standalone --nproc_per_node=8 train_ddp.py

调 NCCL 的关键环境变量（工程师每天在跟这些打交道）：
  NCCL_DEBUG=INFO                打印拓扑探测和算法选择过程 —— 排障第一件事
  NCCL_ALGO=RING|TREE           强制算法，对比性能
  NCCL_TOPO_FILE=...             手动指定拓扑（高级）
  NCCL_P2P_DISABLE=1             关掉卡间直连做对照实验

必做的对比实验：
  实验 1  8 卡 AllReduce，分别用 RING 和 TREE，大/小数据各测一次
  实验 2  NCCL_DEBUG=INFO 看它探测到什么拓扑、选了什么算法
  实验 3  DDP 训练，开/关梯度桶重叠，看吞吐变化
```

### 3.4 尺度 3 部署重点（多机，功能层）

```text
目标：跑通多机 DDP，学会网络配置和排障

前置：
  2 台以上多卡服务器，同地域同可用区（延迟最低）
  安全组放开节点间端口（ rendezvous 端口 + NCCL 通信端口）
  确认网卡名：ip addr 或 ifconfig —— NCCL 要指定正确的内网网卡

多机启动（torchrun 标准姿势）：
  主节点：
    torchrun --nnode=2 --node_rank=0 --master_addr=<主节点内网IP> \
             --master_port=29500 --nproc_per_node=8 train_ddp.py
  从节点：
    torchrun --nnode=2 --node_rank=1 --master_addr=<主节点内网IP> \
             --master_port=29500 --nproc_per_node=8 train_ddp.py

网卡与 RDMA 配置（最容易踩坑的地方）：
  NCCL_SOCKET_IFNAME=eth0        指定内网网卡名，不然可能走错网卡
  NCCL_IB_DISABLE=0              启用 IB/RDMA（有 RDMA 机型时）
  NCCL_IB_GID_INDEX=3            RDMA 的 GID 索引，云厂商文档会给
  NCCL_SOCKET_NTHREADS=4         增加 socket 线程，TCP 场景调优

多机 nccl-tests（测跨节点带宽）：
  ./build/all_reduce_perf -b 8M -e 8G -f 2 -g 8 -n 2
  或者在多节点上用 mpirun 拉起

排障三板斧：
  NCCL_DEBUG=INFO                看它选了哪条链路、有没有降级到 TCP
  timeout / hang                多半是网卡名错、安全组没开、master_addr 写错
  慢节点                        看每卡迭代时间，找出拖后腿的那台
```

## 4. 工程师常做的 80%（每个尺度）

> 不是按知识重要度排，是按**真实工作里花时间最多**的事排。

### 4.1 尺度 1 · 卡内，工程师 80% 的时间在

```text
① Profile 找瓶颈（约 25%）
   做什么：先测再改，不靠猜
   工具：nsys 看时间线（kernel 占比、有没有 CPU 在等 GPU）
        ncu 看单 kernel（occupancy、内存吞吐、分支效率、寄存器数）
   为什么最多：GPU 优化的第一原则是"测量优先"，不做 profile 的优化基本是瞎改

② 内存访问优化（约 20%）
   做什么：改数据布局让访问合并、用 shared memory 缓存复用数据、避免 bank conflict
   工具：ncu 的 Memory Workload Analysis
   为什么：尺度 1 的重心之二，大多数 kernel 慢在喂数据而不是算

③ 写/改 kernel 与并行配置（约 15%）
   做什么：写 Triton/CUDA kernel，调 block size、grid 切分、看 occupancy
   工具：Triton（快）、CUDA C（精细）、ncu 的 Occupancy 面板
   为什么：重心之一，但工程里更多是改现成 kernel 而非从零写

④ 算子融合（约 10%）
   做什么：把多个小 kernel 合成一个大 kernel，减少 launch 开销和显存往返
   典型：FlashAttention、fused optimizer（AdamW 融合版）
   为什么：小 kernel 多了，时间全花在启动和搬数据上

⑤ 混合精度（约 10%）
   做什么：fp16/bf16 训练，配合 GradScaler，注意数值稳定性
   工具：torch.cuda.amp / torch.autocast
   为什么：几乎零成本换 2–3 倍吞吐，是性价比最高的优化

⑥ 显存与 OOM 排查（约 10%）
   做什么：算显存账、调 batch size、gradient checkpointing、查内存泄漏
   工具：nvidia-smi、torch.cuda.memory_summary()
   为什么：显存爆了训练直接停，是日常最高频的故障

⑦ 数据管线（约 10%）
   做什么：DataLoader 多 worker、pin_memory、预处理别卡住 GPU
   工具：nsys 看 GPU 有没有在等数据
   为什么：GPU 空等数据是最常见的浪费
```

### 4.2 尺度 2 · 机内，工程师 80% 的时间在

```text
① 起分布式训练与数据切分（约 25%）
   做什么：torchrun 起多进程、DDP 包装模型、DistributedSampler 切数据
   为什么：这是每天第一件事，配置错了后面全白搭

② 通信瓶颈定位（约 20%）
   做什么：判断慢在算力还是通信、看 AllReduce 占比、找掉队的卡
   工具：nsys 时间线看 NCCL kernel 占比、torch.profiler、NCCL_DEBUG=INFO

③ NCCL 调参（约 15%）
   做什么：调 NCCL_ALGO / NCCL_PROTO / 线程数，做对照实验
   为什么：同样是 AllReduce，算法选错性能差几倍

④ 拓扑确认与利用（约 10%）
   做什么：nvidia-smi topo -m 看连接，把通信密集的进程放到直连的卡上
   为什么：重心之一，拓扑决定上限，算法只能逼近上限

⑤ 通信与计算重叠（约 10%）
   做什么：梯度桶（bucket）调大小、梯度累积、把通信藏进反向计算里
   工具：DDP 的 bucket_cap_mb 参数

⑥ 卡死 / 挂起 / OOM 排障（约 10%）
   做什么：多进程死锁、某张卡 OOM、NCCL timeout
   为什么：多卡比单卡故障率高一个数量级

⑦ 吞吐与扩展性验证（约 10%）
   做什么：测 1 卡/2 卡/4 卡/8 卡吞吐，看扩展效率是否接近线性
```

### 4.3 尺度 3 · 集群内，工程师 80% 的时间在

```text
① 多机启动与组网配置（约 25%）
   做什么：配 master_addr / rendezvous、起多节点、配网卡名、开安全组
   为什么：这一层大部分"故障"其实是配置问题，不是性能问题

② 通信故障排障（约 25%）
   做什么：超时、hang、掉卡、慢节点、某台机器连不上
   工具：NCCL_DEBUG=INFO 看链路选择、TIMEOUT 环境变量、逐节点日志对比
   为什么：多机最耗时的就是排障——节点越多，出问题的概率越大

③ 带宽与稳定性基准（约 15%）
   做什么：nccl-tests 测 AllReduce 带宽、ib_write_bw 测 RDMA、长时间稳定性测试
   为什么：上线前必须知道网络上限在哪

④ 通信参数调优（约 15%）
   做什么：一堆 NCCL_ 环境变量、socket/IB 参数、GID、算法选择
   为什么：云上不同机型最优参数不同，只能实测

⑤ 容错与断点续训（约 10%）
   做什么：checkpoint、节点故障后恢复、弹性训练
   为什么：多机训练跑几天，中途挂节点是常态

⑥ 与网络/云平台协作（约 10%）
   做什么：找云厂商开 RDMA、调安全组、看交换机侧指标（你能看到的部分）
   为什么：交换机在你控制范围外，很多问题必须提工单
```

## 5. 现实边界与取舍

```text
云上能替代的：
  尺度 1 全部     单卡 + profile 工具，和真实开发几乎无差别
  尺度 2 全部     只要机型有 NVLink，和真实机房无差别
  尺度 3 功能层   多机启动、配置、排障、基准 —— 这些经验完全可迁移

云上替代不了的：
  尺度 3 原理层   PFC/ECN/DCQCN、大象流、交换机队列 —— 云上是黑盒
                 要真学，只能：
                   路线一  自建 2 节点小集群 + 白牌交换机（成本高）
                   路线二  读交换机配置文档 + 看抓包/指标案例（成本低）
                   路线三  先用云把工程层练熟，原理层等真碰到再补（推荐）

最务实的路径：
  方案 A 练尺度 1（几十块）→ 方案 B 练尺度 2（几百块）
  → 方案 C 练尺度 3 工程层（上千块，按需短期租）
  → 尺度 3 原理层用文档补，不必为了学习去自建机房
```

> 成本与机型 availability 以各平台实时信息为准；本文数据来自 2026 年公开资料，用于方案定位，不代表报价。
