# 01 · 开工前检查表解说（10 台、3 个区，每项当场打钩）

> **这一章在整件事的哪一步**：00 看完地图 →【01 备料打钩】→ 02 开始敲第一台。
> **这一章在干什么**：从上往下打钩，把"机器够不够、外部依赖齐不齐、决策定没定"全部确认一遍。右边写的是本次真实结论，不是理论值。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `01_开工前检查表.md`。

下面把这一张检查表里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① A 组：机器与可用区（7 项）

**10 台到位（3 控制面 + 5 worker + 1 外部机 + 1 演练机）**
为什么这么分：控制面管集群、worker 跑业务、外部机放后勤服务、演练机专门搞破坏。
- 本次全是竞价实例（Spot，出价随行就市，便宜但可能被回收）。防：控制面被回收会丢 etcd 仲裁，至少把 3 台控制面的中断通知接上。

**香港有几个可用区**
为什么必须查：不能想当然。本次实测只有 b / c / d（**没有 a 区**）。任何按 "a/b/c" 写死的脚本第一次跑就失败。防：先跑一遍 DescribeZones。

**控制面必须同区同交换机（HAVIP 限制）**
为什么：HAVIP（高可用虚拟 IP）只能挂在同一交换机下的实例，跨交换机宣告不了。本次 3 台控制面全在 c 区同一交换机。
防：把控制面拆到不同可用区后 VIP 抢不到，现象看起来像"keepalived 坏了"，其实是云的限制。

**工作节点跨区分布**
为什么：把鸡蛋分到不同篮子。本次 b 区 wk-1/wk-3、d 区 wk-2/wk-4、c 区 wk-5。特别把两台 16G 的大内存机器分在不同区，避免"内存大户挤在同一个故障域"。

**数据盘**
为什么：系统盘塞不下业务数据。本次 5×150G（worker）+ 200G（infra）+ 100G（spare），全是 SSD 云盘。
判据：不要买 ESSD Entry 那种便宜盘——Longhorn 三副本重建是随机 IO，Entry 的 IOPS 会把重建拖成小时级。

**三个区的交换机都在同一 VPC 内、网段落在 172.16.0.0/12**
为什么：安全组规则是按 172.16.0.0/12 放通的。新网段一旦跳出这个范围，节点之间就"部分端口通、部分不通"，极难排查。本次 c=172.23.160.0/20、b=172.23.112.0/20、d=172.23.128.0/20。

**自动释放时间**
为什么：练完 15 项验收至少要 2 天，但也不能不设——忘了关就是持续烧钱。本次设 72 小时。

---

## ② B 组：外部依赖（4 项）

**集群入口 VIP**
为什么：所有组件都要一个固定的"门牌号"来连 API Server。本次复用上次保留的 HAVIP（172.23.163.97，不收费）。验证：8 台节点 ping VIP 全通、TCP 16443 全 OPEN（含跨区的 b/d 节点）。

**集群外对象存储**
为什么：给 Longhorn 备份、Velero、Loki 当"仓库"。本次在 infra-01 上自建 SeaweedFS（S3 兼容，端口 9000）。
判据：备份目标必须在集群外——放集群里等于"集群没了备份也没了"。

**集群外 Git（ArgoCD 的真相源）**
为什么：GitOps 要求"Git 里写什么，集群就是什么"，所以得有个集群外的 Git 仓库当唯一真相源。本次 infra-01 自建 Gitea（3000 / SSH 2222）。

**告警出口**
为什么：告警得有个"送到人"的落点。没有企业微信/短信凭据时，本次在 infra-01 自建一个 alert-receiver（/p1 /p2 /p3 三个落点），这是唯一能"证明链路通"的替代。

## ③ C 组：决策已定（4 项，现场不要临时改）

```
① 入口端点 = HAVIP:16443，写进 kubeadm 的 controlPlaneEndpoint 与 certSANs
② CNI = Cilium，kubeProxyReplacement=true，tunnel+vxlan
   理由：阿里云 VPC 不认 podCIDR 路由，native 模式走不通
③ 存储 = Longhorn 3 副本，Prometheus 保留 7 天
   本次盘够（733G 裸容量），不再有 1.0 的"副本重建失败"
④ Pod 网段 10.244.0.0/16 · Service 网段 10.96.0.0/12
```

为什么这些要提前定死？因为它们互相牵连、改一个动全身——入口地址要同时写进证书、kubeadm、Cilium 配置；CNI 和网段决定了后面所有网络规则。开工前拍板，后面才不会来回返工。

## ⑤ 这一章的坑（讲给初级人员）

```
现象：DescribeZones 里找不到 cn-hongkong-a
根因：香港地域只有 b/c/d
防：任何"a/b/c"三区的脚本先跑一遍 DescribeZones

现象：工作节点跨 AZ 后，Pod 起得来但连不上 apiserver
根因：不是跨 AZ 的问题，是 ip-masq-agent 把 VPC 网段当内网没做 SNAT（见网络章）
防：先按网络章修 masq，再判断跨 AZ 有没有问题

现象：HAVIP 绑定第 2 台时报 IncorrectHaVipStatus
根因：绑第一台后状态变 InUse/绑定中，必须等状态回落再绑下一台
防：绑定脚本里加"失败重试 5 秒 × 12 次"
```

**一句话总结**：检查表看着都是"打钩"的小事，其实是在开工前把三个大坑（可用区不存在、VIP 限制、网段越界）提前挡掉。备料十分钟，排障省两天。
