# 09 · 调度与设备解说（谁先跑、谁能拿到设备）

> **这一章在整件事的哪一步**：第 7 章会按指标伸缩 →【第 8 章管"谁能先跑、谁能拿到设备"】→ 第 9 章追踪。
> **这一章在干什么**：两件事——Kueue 解决"配额 + 排队"（作业什么时候被允许进入调度），DRA 解决"把 GPU 这类设备当成可声明申请的资源"。

我想要的是每个东西的作用。重点是要讲给初级人员。

---

## ① Kueue 是什么（它解决"排队"，不是"调度"）

**先分清两个概念**（初级人员最容易混）：
```
调度器（scheduler）决定"Pod 放到哪台机器"
Kueue 决定"这个作业什么时候被允许进入调度"
```

**为什么必须有它（和普通 ResourceQuota 的区别）**：
```
配额满了时：
  ResourceQuota → 直接"拒绝创建"
  Kueue        → "挂起排队，等前面的跑完自动放行"（Pod 根本没生成，不占调度器）
```
这个区别在批处理/AI 平台里至关重要——你提交 100 个作业，不会全挤上去把集群压垮，而是排队慢慢跑。

**本次怎么证明它生效**：
```
配额只给 1 CPU，投两个各要 800m 的 Job
如果 Kueue 没生效：两个同时 Running（800+800>1000 也照跑，K8S 默认不按总数卡）
实际结果：q2 先跑完 2m3s，q1 才开始 → 证明第二个一直被挂着排队
```

---

## ② ResourceFlavor / ClusterQueue / LocalQueue / Workload（Kueue 的四个概念）

```
ResourceFlavor     "资源口味"——给节点分组、打标签（这里定义什么是"一种可分配的资源"）
ClusterQueue       集群级的配额队列：本次 cpu=1 / memory=2Gi（全集群就这么多额度）
LocalQueue         命名空间级的"入口队列"，用户提交作业时往这里投
Workload           Kueue 为每个作业生成的对象，记录它"排队中 / 被放行（admitted）"
```

**为什么要有这一套**：作业提交进来，Kueue 生成一个 Workload，ClusterQueue 看额度够不够——够就 admitted（Pod 才被创建），不够就排队。这套对象就是排队的"账本"。

**怎么排查"Job 建了但 Pod 不出现"**：先看该命名空间有没有生成 Workload 对象；没有就是 Job 没打 `kueue.x-k8s.io/queue-name` 标签，或 LocalQueue 不存在。

## ③ 节点池标签（可按池调度）

第 3 章打过 `node-pool=memory`（两台 16G）和 `node-pool=standard`（三台 8G）。

**为什么在这里又提**：Kueue 的 ResourceFlavor 和这些标签配合，就能实现"这个作业只能用大内存机器"。也是第 4 章异构调度的基础。

## ④ DRA（Dynamic Resource Allocation：设备声明式分配）

**它是什么**：传统做法是用 device plugin 上报"这台机器有 8 张卡"，Pod 写 `nvidia.com/gpu: 1` 就完事——调度器只知道"数量"，不知道"哪一张、什么属性"。DRA 换了个模型：**Pod 声明"我要一张什么样的设备"，驱动发布设备清单，调度器按属性挑。**

**为什么必须有它（相比 device plugin）**：
```
device plugin  + 生态成熟、厂商都支持
               - 只能按"数量"申请；共享、分区、属性筛选都要靠额外手段
DRA            + 按属性申请（型号/显存/拓扑）、支持共享与分区、声明式
               - 驱动要改写、链路更长
判据："给我一张卡"→ device plugin 够；"给我两张同 NUMA、显存>40G、能共享的卡"→ 才需要 DRA。
```

---

## ⑤ DRA 的四个概念 + 一次完整流程

```
DeviceClass          设备"类型"定义（本次 gpu.example.com）
ResourceSlice        驱动发布的"设备清单"——这台机器上有什么设备、什么属性（本次 5 个，每台 worker 一条）
ResourceClaimTemplate 用户写的"我要什么样的设备"的模板
CDI                  容器设备接口——kubelet 通过它把设备真正"注入"到容器里
```

**完整流程**：
```
驱动 → 发布 ResourceSlice（清单）
用户 → 写 ResourceClaimTemplate（需求）
调度器 → 匹配 + 分配（claim 状态变 allocated）
kubelet → 调驱动把设备注入容器（CDI）
```

**怎么算 DRA 真的工作了（最容易误判的一条）**：
```
本次验收看 5 条：DeviceClass 存在 / ResourceSlice=5 / claim=allocated / Pod Running 在 wk-2 /
                容器内可见 GPU_DEVICE_0=gpu-0
第 ⑤ 条最关键：只看到 Pod Running 不够——必须看容器里有没有设备注入，
否则可能是"能调度但没设备"。
```

## ⑥ 判官卡：Kueue 值不值得在练习环境装

```
值得，如果目标是"AI/批处理平台"：它解决多人多作业抢有限 GPU/CPU 的公平性与排队，是 AI 平台核心件。
不值得，如果只是"跑微服务"：微服务用 HPA + ResourceQuota 就够，Kueue 对无状态服务几乎没价值。
本次：装了并验证配额串行，作为"能力占位"；业务侧目前没有真正需要排队的作业。
```

## ⑦ 这一章的坑（讲给初级人员）

```
现象：Job 创建了但 Pod 一直不出现
根因：Job 没打 queue-name 标签，或 LocalQueue 不存在
防：先看有没有生成 Workload 对象

现象：Kueue 装完，老作业全卡住
根因：Kueue 会接管所有带队列标签的作业，包括历史对象
防：先在测试命名空间验证，再扩到全集群

现象：DRA 驱动拉不起来，报 repository does not exist
根因：镜像没有 latest 标签（该仓库只有 v0.1.0~v0.5.0）
防：装之前先查仓库标签清单，别假设 latest 存在

现象：验收时 claim 查不到，Pod 却是 Completed
根因：由模板生成的 claim 随 Pod 生命周期回收，Pod 退出了 claim 就没了
防：验收必须在 Pod 存活期间做，或用长驻 Pod

现象：Pod 起来了但容器里没有设备
根因：DeviceClass 名字与驱动声明的不一致，claim 匹配不到设备
防：DeviceClass 名以驱动实际发布的为准
```

**一句话总结**：这一章把 K8S 的"调度"往前补了两块——Kueue 管"作业排队和配额"（不直接拒绝，而是挂起等待），DRA 管"按属性声明式申请设备"（不只是数量）。一个是批处理平台的公平性核心，一个是异构硬件的现代化申请方式。
