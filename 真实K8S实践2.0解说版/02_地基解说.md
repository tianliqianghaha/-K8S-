# 02 · 地基解说（10 台并发推到"能装 K8S"）

> **这一章在整件事的哪一步**：01 打完钩 →【把 10 台推到同一个起点】→ 第 2 章起控制面。
> **这一章在干什么**：把 10 台裸机推到同一个起跑线——**内核参数一致、容器运行时一致、kubeadm 版本一致**。三样缺一样，后面就会出现"某台节点莫名 NotReady"。而且不手敲，从本机 SSH 并发推到 10 台，单台失败不影响其他台（四段总共 67 秒推完）。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考本章文档 + `scripts/2.0-deploy/s1/` 下的 base.sh / kernel.sh / runtime.sh / k8s.sh / mount.sh。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① base.sh 里的六件事

**关 swap**
Swap 是 Linux 在内存不够时把数据挪到磁盘上的"应急内存"。K8s 要求关掉它，原因很直白：
- **性能不可控**：磁盘比内存慢几个数量级，一旦开始频繁换页，整台机器就会"CPU 不高但卡得要命"，容器响应延迟飙升。
- **资源管理失真**：K8s 靠 cgroup 精确控制每个 Pod 能用多少内存。开了 swap，Pod 可能偷偷用磁盘当内存，调度器以为还有余量继续塞 Pod，最后整节点被拖垮。K8s 的设计哲学是"内存不够就明确 OOM 或驱逐，而不是靠 swap 模糊地苟住然后拖死全场"。

**时区 + chrony 时间同步**
- **时区**：让所有节点日志、证书有效期判断用同一套时间语言。
- **chrony**：比时区更关键，保证 10 台机器时钟真正对齐。etcd、证书验证对时钟漂移非常敏感，差几秒就可能拒绝通信。

**主机名 + hosts**
- **主机名**：K8s 用主机名作为节点标识，cp-1、worker-3 这种命名让控制面/工作节点/infra 一目了然。
- **hosts**：让节点之间能用短名互相找到对方，不依赖外部 DNS，避免 DNS 故障导致集群内部通信中断。本次写了 12 行（10 台 + api-vip）。
- 附带一条：**防止 cloud-init 把主机名改回去**——云主机每次重启，cloud-init 会按元数据重设主机名成 iZxxxx 那种，所以在 cloud.cfg 里写 `preserve_hostname: true` 摁住它。

**关自动更新**
防止 apt 在后台悄悄升级内核、containerd 或 K8s 组件，破坏你精心锁定的版本一致性。配合后面 `apt-mark hold` 形成双保险。

## ② kernel.sh 里的内核模块与参数

**overlay 模块**
容器镜像文件系统的底座。容器用的是"分层文件系统"，每一层叠在一起，overlay 就是实现这个叠加的内核驱动。没有它，容器根本跑不起来。

**br_netfilter 模块 + bridge-nf-call-iptables=1**
默认情况下，Linux 网桥转发的流量不会经过 iptables 规则。但 K8s 的 Service、NetworkPolicy、kube-proxy 全靠 iptables 做流量处理。这个模块和参数的作用就是"让桥接流量也走 iptables"，否则 CNI 插件的网络规则形同虚设，Service 访问不通。

**nf_conntrack 模块 + nf_conntrack_max=1048576**
连接跟踪表，记录每一条网络连接的状态。K8s 集群里 Service 多、Pod 多，连接数极大。默认值太小会导致 conntrack 表满，新连接被丢弃，表现为"偶尔连不上服务"。调大到 100 万+ 是给生产环境留足余量。
- 注意：26.04 默认不加载这个模块，光在 sysctl 里写参数会被静默跳过。所以要在 modules-load.d 里加 `nf_conntrack` 并 modprobe。

**ip_forward=1**
节点做 Pod 间、跨节点数据包转发的开关。不开这个，跨节点网络完全不通，Pod 只能跟同节点的 Pod 说话。

**inotify.max_user_watches=524288**
kubelet 要监听大量文件（配置、日志、Pod 状态等）。默认值太小会报 "no space left on device"（其实是 watch 句柄耗尽，不是磁盘真满了），kubelet 无法正常工作。

**THP 关闭（disable-thp.service）**
透明大页是 Linux 的内存优化机制，但在容器场景下会造成不可预测的性能抖动（内存分配延迟突增）。K8s 官方明确要求关闭。这里做成一个独立 systemd unit，开机就执行，且早于 kubelet 启动；验证回显里的 `thp=[never]` 就是确认这件事做对了。

## ③ runtime.sh 里的 containerd 相关

**containerd**
容器运行时，负责镜像拉取、容器启动/停止、生命周期管理。它是 kubelet 和底层 Linux 之间的桥梁——kubelet 不直接操作容器，而是通过 CRI 接口告诉 containerd"起一个 Pod"。
- 一个版本细节：26.04 的 apt 源里包名就叫 `containerd`，**不是**老经验里的 `containerd.io`；从 22.04 抄经验会报 "Unable to locate package"。

**SystemdCgroup = true**
这是整份文档最容易翻车的一个点。cgroup 是 Linux 限制容器资源的机制，有两种驱动：cgroupfs 和 systemd。kubelet 从 1.22 起默认用 systemd，如果 containerd 这边还是 false（即 cgroupfs），两者驱动不一致，kubelet 启动 Pod 时会反复 CrashLoop。改成 true 就是让两边说同一种语言。装完必须 `grep -c` 一次，结果必须为 1。

**crictl**
专门调试 CRI 运行时的命令行工具。`docker ps` 看的是 Docker 的容器，而 K8s 的容器归 containerd 管，要用 `crictl ps`、`crictl pull` 才能看到和操作。验证步骤里 `crictl pull pause:3.10.1` 就是在测试"运行时 + 镜像拉取 + 网络"这条链路通不通。

**config_path = '/etc/containerd/certs.d'**
新版 containerd 推荐的镜像仓库配置方式，按目录结构存放各仓库的证书和 mirror 地址，比老版写在 config.toml 里的 `sandbox_image` / `registry.mirrors` 更规范、更易维护。
- 2.2.2 是 version 3 配置，键名变了（`pinned_images.sandbox` 取代 `sandbox_image`），而且 `config_path` 出现在两处（CRI images.registry 和 transfer.v1.local）——只改第一处，用 `0,/pattern/` 限定范围。

## ④ k8s.sh 里的三件套与版本锁定

**kubeadm**
集群的"安装向导"。只负责初始化控制平面、生成证书、创建 join token 这些引导工作，不负责日常运行。装完集群后它基本就退场了（除了升级时用）。

**kubelet**
每台节点上常驻的"保姆进程"。负责接收 API Server 的指令、拉起/杀掉 Pod、上报节点状态、执行健康检查。它是 K8s 在节点上的真正代理人，集群能不能跑全靠它。地基阶段它还是 inactive 是正常的（还没 init）。

**kubectl**
人机交互的命令行客户端。你敲的所有 `kubectl get pod`、`kubectl apply` 都是它在跟 API Server 对话。它不参与集群运行，只是你的操作入口。

**pkgs.k8s.io 源**
K8s 官方新软件源（旧的 apt.kubernetes.io 已于 2023 年 9 月弃用冻结）。指定 `v1.37` 是为了锁定小版本线，避免意外装上更高版本。

**apt-mark hold**
把五个包（kubelet、kubeadm、kubectl、containerd、runc）的版本冻住，apt upgrade 或 unattended-upgrades 都不会动它们。原因是 K8s 升级有严格顺序（先 kubeadm → 再控制平面 → 最后 kubelet），自动升级会打乱这个顺序，导致版本偏差超出支持范围甚至守护进程意外重启。hold 不是可选的最佳实践，是官方安装文档的强制要求。

## ⑤ mount.sh：数据盘挂载（地基里容易被忽略的一块）

**它干什么**：把云上那块额外的数据盘 `/dev/vdb` 格式化成 ext4，挂到指定目录，并把挂载写进 `/etc/fstab`（开机自动挂，参数用 noatime）。

**为什么必须有它**：K8s 自己会把系统盘塞满日志和容器镜像，所以数据盘必须单独挂出来给 Longhorn 存业务数据。不挂的话，Longhorn 会发现目标目录不在独立挂载点上，直接报 Schedulable=false，PVC 永远 Pending。

**挂哪里（本次的选择）**：
- worker 的盘挂 `/var/lib/longhorn`（Longhorn 默认路径，装完即用）
- infra-01 挂 `/data`（跑 SeaweedFS S3）
- spare-01 挂 `/data`（放 etcd 快照演练）

**怎么确认挂对了**：装完必须 `findmnt` 看一眼，再 reboot 一台验证盘还在、目录没被写满。只写 fstab 不 `mount -a` 验证，或只 mount 不写 fstab，重启后都会出问题。

## ⑥ 四探针的作用（验收门禁）

每个东西装完，都要用一条能跑完的命令证明它真的对了。这四条是地基章的门禁：

```
① uname -r                      10 台内核版本完全相同（本次 7.0.0-38-generic）
   为什么：内核不一致 = 节点行为不可预测，排障时无从判断是配置问题还是内核差异

② stat -fc %T /sys/fs/cgroup → cgroup2fs
   为什么：确认是 cgroup v2，与 SystemdCgroup=true 配套；v1/v2 混用会导致资源隔离失效

③ grep -c 'SystemdCgroup = true' → 1
   为什么：再次确认运行时与 kubelet 说同一种语言，避免经典翻车；必须为 1 且不能重复

④ crictl pull pause:3.10.1
   为什么：pause 是 Pod 的沙箱基础镜像，拉不到它，后续 kubeadm init 必卡
```

## ⑦ 判官卡：数据盘挂哪里

这不是技术对错问题，是运维策略选择：

```
选项 A 挂 /var/lib/longhorn（本次 worker 选它）
  优点：Longhorn 的默认数据路径，装完不用改 defaultDataPath，节点磁盘自动识别
  缺点：盘和 Longhorn 绑死，将来换存储要重挂

选项 B 挂 /data，再在 Longhorn 里注册
  优点：通用，一块盘能服务多个组件
  缺点：多一步 nodes.longhorn.io 注册 + tag，忘了就出现"节点有盘但调度不上去"

判据：盘只服务一个组件时用它的默认路径；盘要服务多个组件时统一 /data。
本次：worker 用 A（省事），infra/spare 用 B（它们不跑 Longhorn）。
```

## ⑧ 这一章的坑（讲给初级人员：现象 / 为什么 / 怎么防）

装的时候几乎人人都会撞这几个，提前知道就能少熬几小时：

```
现象：apt 报 Could not get lock /var/lib/dpkg
根因：云镜像的 unattended-upgrades 在你装包时启动了
防：先 systemctl stop unattended-upgrades apt-daily* 并 pkill，再给 apt 加 -o DPkg::Lock::Timeout=180

现象：apt 报 Unable to locate package containerd
根因：新机器没 apt-get update 就 install；而且 26.04 包名是 containerd 不是 containerd.io
防：install 前先 update；按新包名写

现象：sysctl 里写了 nf_conntrack_max，读不到这个 key
根因：26.04 默认不加载 nf_conntrack，整行被静默跳过
防：modules-load.d 加模块 + modprobe，再 sysctl --system

现象：kubelet 起来就 CrashLoop，报 cgroup 相关
根因：containerd 的 SystemdCgroup 还是 false
防：装完立刻 grep，必须等于 1

现象：重启后 hostname 变回 iZxxxxZ
根因：cloud-init 每次按元数据重设主机名
防：cloud.cfg 里 preserve_hostname: true、manage_etc_hosts: false

现象：containerd 起来了，Pod 卡在拉 sandbox，config 改了不生效
根因：2.2.2 是 version 3 配置，键名和两处 config_path 都变了
防：只改 CRI images.registry 那一处 config_path；sandbox 用默认 pause:3.10.1

现象：挂盘后重启变成"盘没挂、目录被写满"
根因：只写 fstab 没 mount -a 验证（或反过来）
防：挂完 findmnt 看一眼，再 reboot 一台验证
```

**一句话总结这一章**：地基做的事看着琐碎（关 swap、对时、改主机名、加载模块、装运行时、装三件套、挂盘），但每一件都是在消除"节点之间不一样"和"运行时说不上话"这两类隐患。地基歪一寸，上面全歪。
