# 16 · 运维演练解说（建好之后每天怎么维持、坏了怎么救）

> **这一册对应 `运维演练/` 整个目录**：搭建册回答"怎么建成的"，这一册回答"建好之后每天怎么维持、坏了怎么救、怎么证明它还活着"。
> **分工标准**：做一次就不变的内容归搭建册；每周/每天要重复跑、每次留新读数的归这一册。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `运维演练/00~04` 五册 + 配套 ops 脚本。

下面把这一册里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

```
  日巡检 10 项    回答"今天能不能正常干活"，每天跑、看趋势
```

## ② 十场演练（把"会不会"变成"做过一遍"）

演练册的定位不是"再加组件"，是**动作册**——每项都给"怎么练 / 判据 / 事后副作用"。本册最有价值的认识是：**真正的收获不是"知道怎么恢复"，而是"知道会留下什么副作用"**（十场里有三场，恢复本身成功了，但副作用让验收掉到 40/42）。

```
① 镜像拉不到       ErrImagePull，三类措辞分清原因：
                   manifest not found→tag 不存在 / unauthorized→缺认证 / i/o timeout→网络
                   ★ 三类词决定你下一步是改 tag、配 secret、还是查网络，别一上来就重试
② 节点 drain + PDB 持续打流量 900 次请求 0 失败，drain 32 秒
                   PDB(minAvailable=1) 作用：驱逐前先确认还剩几个副本
③ apiserver 两台下线  kubectl 仍正常、VIP 200、etcd 3 成员稳定，恢复 9 秒
                   ★ 直接停容器没用（kubelet 会拉回静态 Pod），要移出清单目录
④ 删除 CNI         新 Pod Pending（拿不到 IP）、老 Pod 2/2 存活、恢复 68 秒
                   这是 eBPF 数据面的特性：规则已在内核，agent 挂了存量照跑
⑤ etcd 快照恢复     快照 76MB/1.3s → restore 1s → 4216 个 key、业务 ConfigMap 完整
                   ★ 必须在 spare-01（隔离机器）上做，不能拿生产赌
⑥ 证书轮换         kubeadm certs renew all，11 秒；"续期成功≠生效"，要重启组件
⑦ 可用区故障       真停 d 区两台 kubelet：40s 首台 NotReady、48s 两台、恢复 3s
                   ★ 意外抓到 CoreDNS 两副本同节点的致命单点（见下）
⑧ PVC 数据恢复     Velero fs-backup：删库 55 秒恢复，文件与 md5 一致
                   ★ 前提：必须装 node-agent，否则"备份成功"但卷数据为空
⑨ 可用区网络隔离   用 iptables 断网（比停 kubelet 更接近物理故障）：49s NotReady、恢复 15s
⑩ 升级演练         spare-01 上 1.37.0→1.37.2，控制面 102 秒、总 121 秒、Pod UID 不变
```

**演练⑦抓到的真问题（本册最有价值的一条）**：
```
现象：故障期间业务报 "bad address web.demo-app.svc.cluster.local"
根因：CoreDNS 两个副本都被调度到 wk-4 上，wk-4 一停 DNS 全灭
判据：副本数 = 2 不代表高可用，要看它们是不是在同一台/同一可用区
修复：加硬反亲和（hostname）+ 扩到 3 副本 → 分散到 cp-2/wk-1/cp-3
```
这属于"平时看不出、故障时致命"的配置缺陷——YAML 里写 2 会给人安全感，但调度器并不知道你在乎它们别放一起。

## ③ 日常运维（已脚本化的重复动作）

```
日巡检 daily-check.sh    10 项一条命令，10 秒跑完、结论一眼看懂
etcd 快照 etcd-snapshot.sh  每 6 小时（cron 15 */6 * * *），本地 7 份 + 异地 7 份
                          ★ 异地这一步不是可选项：集群整体故障时本机快照一起没了，
                            本次专门配了 cp-1→infra-01 免密
Velero 定时备份           每天 02:00、TTL 7 天、含业务+密钥
周恢复抽验 weekly-restore.sh  取最近备份恢复到临时 ns、比对标记、删除，3 秒
```

**日巡检 10 项及其判据**（讲清"为什么是这些数"）：
```
节点 Ready 8/8        少一台说明有节点在滚，不是"正常波动"
异常 Pod 0            只要不是 Running/Completed 就记 WARN，不看是不是"刚起"
etcd 成员 3           少一个就失去容错，不是"能跑就行"
证书剩余 364d         <90d 排期、<30d 事故
待批 CSR 0            有 Pending 就是有节点在等证书（通常意味着重装或 kubelet 异常）
etcd 快照 <26h        比 cron 的 6 小时留足余量
异地留存 ≥1           只留本机等于没备份
Velero 备份 ≥1
Longhorn 余量 >30G    取所有节点最小值；低于此三副本重建失败
入口 Programmed=True  否则外网已进不来
```

**为什么用 CRD 声明而不是 CLI 建 Velero Schedule**：CLI 在这个版本会卡住不回显，而 Schedule 是标准 CRD、声明式下去立刻生效、可进 Git、可审计。教训：**运维要选"必然成功的那条路"。**

## ④ 告警分级投递（P1/P2/P3）

```
Prometheus 规则 → Alertmanager 按 severity 分流：
  critical → /p1  该叫人起床
  warning  → /p2  当天处理
  其余     → /p3  上班看
落点：infra-01 的 alert-receiver（模拟企微/钉钉，生产可替换成真实机器人）
```

**一条关键判据**："有告警"和"告警到人"是两件事——
```
判据一：Alertmanager 的 /api/v2/alerts 里有告警（规则与抓取正常）
判据二：落点日志里有对应级别（路由与出口正常）
两个都过才算通。本次第一次查只看了一个目录，误判成"没投递"。
```

## ⑤ 配额与限额（Quota + LimitRange）

```
ResourceQuota  管命名空间总量：cpu 4 / mem 8Gi / pods 30 / pvc 6
LimitRange     管单容器默认：request 20m/32Mi、limit 200m/128Mi、上限 2C/2Gi
为什么两个都要：只有 Quota，一个容器吃掉全部；只有 LimitRange，总量无上限。
```

## ⑥ 故障处置（现象 → 第一眼看什么 → 判据 → 边界）

故障处置册的写法很克制：**只给三样——第一眼看什么、判据是什么、什么时候必须放弃修复直接回滚**，不写命令（避免在慌乱时照着敲错）。

```
① 外网访问不了    第一眼看 Gateway 的 Programmed 条件（不是看 Pod 是否 Running）
② 新 Pod 起不来   按顺序查四层：调度 Pending → 网络层（cilium ready 数）→ 准入库 → 镜像层
③ 老 Pod 正常新 Pod 全不通  典型 eBPF 形态：先恢复 CNI，别动存量（那是你唯一通道）
④ Service 通 DNS 不通      第一眼看 CoreDNS 副本落在哪些节点（不是看副本数）
⑤ 存储写不进去    第一眼看 Longhorn 最小余量（<30G 重建会失败）与 volume 状态
⑥ 集群整体打不通  第一眼看 VIP healthz + apiserver 容器是否存在；此时唯一入口是节点本地 6443
⑦ 告警没发出去    先看 Alertmanager 有没有 active alerts，区分"规则问题"还是"路由问题"
```

**四条处置共同原则**：
```
① 先判断"新增坏还是存量坏"——存量坏是数据面，新增坏多半是准入/调度/镜像
② 数据面故障默认动作是回滚，不是修复
③ 每次处置完必须复跑 42 项验收（恢复动作本身会留副作用）
④ 处置过程只记录现象与判据，命令写在脚本里——慌乱时人只会照抄错
```

**一条通用判断（很值钱）**：
```
凡是"手工改完过一会又变回去"的，问题不在你改得对不对，而在"控制器认为自己才是真相源"。
要改就得改控制器的输入（比如给 EnvoyProxy 挂 parametersRef 声明 NodePort），
而不是手改它管理的对象。
```

## ⑦ 变更与回滚（三类变更三种纪律）

```
A 应用层（改镜像/副本/配置）  随时可做，回滚 git revert，30 秒内
B 准入层（改策略）            业务低峰做，删错会挡住所有写入（fail-closed）
C 数据面（改 CNI/加密/apiserver 参数）必须单独开窗口，先导 values/备份清单
```

**变更前四件事（缺一件别动）**：
```
① 备份要改的东西（helm get values、清单 .bak）
② 记录变更前的关键计数（agent 就绪数、Running Pod 数、42 项结果）
③ 写清楚"什么现象算失败"（例：3 分钟内 ztunnel 不到 8/8 就算失败，而不是"再看看"）
④ 想好回滚的第一条命令——想不出来 = 这个变更现在不能做
```

**不能回滚的三类（动手前必须有演练过的恢复路径）**：
```
① 删 etcd 数据目录/重建控制面  ② 把节点移出集群  ③ 改集群网段（等价重建）
```

## ⑧ 这一章的坑（讲给初级人员）

```
现象：日巡检"Longhorn 余量"长期显示 0G
根因：Longhorn 磁盘名是动态生成的（default-disk-<hash>），不是设备名
防：取所有节点所有磁盘的最小 storageAvailable

现象：从控制面 ssh 到 worker 执行 stop kubelet，"成功"但没生效
根因：控制面到 worker 没免密，ssh 静默失败
防：演练前先验通道（能否在目标机看到 hostname）

现象：Gateway 报 AddressNotAssigned
根因：没有 LB 实现时 LoadBalancer 类型拿不到地址
防：声明式指定 NodePort，并确认 Service 类型不回退
```

**一句话总结**：运维册把"建好之后怎么办"讲透了——十场演练把恢复能力变成肌肉记忆（并且每次都盯副作用）、日巡检/快照/备份/抽验把日常维持脚本化、故障处置和变更回滚给你一套"先看什么、什么时候止损"的纪律。核心心法有两条：**故障先分清新增坏还是存量坏；手改完会弹回去的，就去改控制器的输入。**
