# 11 · 交付与渐进发布解说（发得上去、退得回来、别人偷改还能自愈）

> **这一章在整件事的哪一步**：第 9 章看得见 →【第 10 章让应用发得上去、退得回】→ 第 11 章东西向网格。
> **这一章在干什么**：两件事分开——GitOps（ArgoCD）让"集群状态永远等于 Git 里的状态"，解决"谁偷偷改了线上"；渐进发布（Argo Rollouts）让"新版本分批上"，解决"一换镜像全站炸"。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `11_第10章_交付与渐进发布.md` + `s8_gitops.py` / `s16_git_addons.py` + repo 下的清单。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① Gitea（集群外的 Git 仓库）

**是什么**：一个自己搭的 Git 服务器，跑在 infra-01 上（集群外）。

**为什么必须有它（为什么要放到集群外）**：GitOps 的核心是"Git 是唯一真相源"。如果 Git 仓库跑在集群里，集群挂了 Git 也没了，就没地方恢复——和备份不能放集群里是同一个道理。本次建了 `k8s-manifests` 仓库，本地能 git push 成功。

---

## ② ArgoCD + GitOps（本章第一个核心：谁改都不算，Git 说了算）

**GitOps 是什么**：一种运维方式——**所有集群状态都写在 Git 里，一个控制器（ArgoCD）不停对比"Git 里应该是什么"和"集群实际是什么"，不一致就自动纠正。**

**ArgoCD 是什么**：这个"不停对比并纠正"的控制器。本次 server / repoServer / applicationSet 各 2 副本，NodePort 30080 暴露界面。

**为什么必须有它**：没有它，线上被谁手工改了（kubectl edit、手误 delete）你不知道、也不会自动恢复。有了它：
```
自愈实测：手工删掉 Deployment，2 秒后回到 2/2 Ready（GitOps 拉回，不是人工救）
这 2 秒 = reconcile 间隔 + 调度 + 启动，比人工快两个数量级
```

**关键对象 Application**：告诉 ArgoCD"去哪个 Git 仓库的哪个目录、同步到集群的哪个命名空间"。本次用 app-of-apps 形态（一个总 Application 管理其他 Application）。

**一个必须知道的坑（finalizer）**：Application 带 `resources-finalizer`——**删掉 Application 会级联删掉它管理的所有资源**。本次踩过一次：删 App 把 Kyverno（准入控制器）整个删没了。所以 fail-closed 的组件（准入、CNI、存储）不要交给 ArgoCD 自动纳管。

---

## ③ 仓库凭据 Secret（ArgoCD 怎么访问私有 Git）

**是什么**：一个打了特定 label（`argocd.argoproj.io/secret-type=repository`）的 Secret，存 Git 仓库的地址和账号密码。

**为什么必须有它**：ArgoCD 要能读仓库才能同步。私有仓库就得给凭据，label 是让 ArgoCD 认出"这是个仓库凭据"的标记。

---

## ④ Argo Rollouts（本章第二个核心：金丝雀发布）

**是什么**：比普通 Deployment 更高级的发布控制器，支持 canary（金丝雀）——新版本先上少量副本，观察没问题再全量替换。

**为什么必须有它**：普通 `kubectl set image` 是全量替换，新版本有 bug 就全站一起炸。Rollouts 让新版本"分批上、中间设关卡（pause）"，你可以观察、可以喊停。

**本次实测的发布节奏**：
```
换镜像触发 canary
t=15s phase=Paused        停在第一道 pause（30 秒门禁）
t=60s phase=Progressing
t=75s phase=Healthy
→ 说明"分批 + 门禁"这套机制真的在拦，不是直接全量替换
```

**一个必须写对的点（两种 canary 形态）**：
```
✗ 会报错：用了 setCanaryScale 但没配 trafficRouting
  报 "SetCanaryScale requires TrafficRouting to be set"
✓ 本次可用：只用 pause 步骤（按副本比例 + 暂停门禁，不需要流量管理器）
判据：setWeight / setCanaryScale 属于"按流量切"，必须有 trafficRouting；
      只写 pause 是"按副本比例 + 定时门禁"，不依赖任何流量组件。
```

---

## ⑤ 判官卡：canary 按什么切

```
选项 A 按副本比例 + pause 门禁（本次）
  能做：新旧版本同时存在，观察新 Pod 是否稳定
  不能：控制"多少请求打到新版本"（Service 层仍轮询）
选项 B Gateway API trafficRouting + 第 3 章的 Envoy Gateway
  能做：真正按百分比导流（1% → 5% → 50%）
选项 C 服务网格流量切分
  能做：最细（按 header、按用户）；代价最重
判据：练"发布流程"用 A；练"发布策略"必须上 B。
本次：A（入口控制器相关能力还没全打通）。
```

## ⑥ 全量纳管（把 addon 也写进 Git）

本章还把 Longhorn、Prometheus、Kyverno 等 13 个 addon 全部声明成 ArgoCD Application 写进 Git。

**为什么要做**：只把业务应用放进 Git 是不彻底的——平台组件还是手工 helm 装的，没有声明、无法审计、重建时靠记忆。全纳管后"整套集群长什么样"都在 Git 里。

**一个诚实的边界**：数据面组件（cilium/longhorn）故意不开自动同步，Kyverno 干脆不进 ArgoCD——因为它们是 fail-closed 的，乱同步会出大事。而且本次只搬了 chart+版本、没搬 values，所以它们显示 `OutOfSync` 但 Healthy。文档明确写了这是"声明已进 Git、值还没搬"，不是故障。**这种诚实记录边界的做法值得学。**

---

## ⑦ 这一章的坑（讲给初级人员）

```
现象：Application 一直 OutOfSync，但集群里看着正常
根因：Git 里的清单与线上有"无害差异"（比如 HPA 改了 replicas）
防：加 ignoreDifferences（/spec/replicas），别用 selfHeal 硬怼

现象：KEDA/HPA 托管副本数 + ArgoCD selfHeal → 副本数反复跳
根因：两个控制器都在管 replicas
防：HPA/KEDA 接管的 Deployment，ArgoCD 侧忽略 replicas

现象：Rollout 一创建就 Degraded，报 InvalidSpec
根因：用了 setCanaryScale 但没配 trafficRouting
防：要么加 trafficRouting，要么只用 pause

现象：手工改镜像演练"什么都没发生"
根因：被 GitOps 自愈改回去了（25 秒内 Pod 名字没变就是被覆盖了）
防：演练"故意改坏"的动作先暂停 ArgoCD 的 automated

现象：删带 finalizer 的 ArgoCD App，组件整个消失
防：fail-closed 组件不交给 ArgoCD 自动纳管，或去掉 finalizer
```

**一句话总结**：交付这一章让集群从"手工装的"变成"Git 声明的"——ArgoCD 保证没人能偷偷改线上（改了 2 秒自愈），Rollouts 保证新版本分批上、中间可喊停。核心纪律是：**fail-closed 的组件别交给 GitOps 自动同步，删 Application 会级联删资源**。
