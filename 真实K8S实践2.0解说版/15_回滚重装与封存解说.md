# 15 · 回滚重装与封存解说（拆的顺序、清残留、怎么从零再来）

> **这一章在整件事的哪一步**：13 是"建成了什么"、19 是"把它拆了留下什么"——这一册只在"要重来一遍"时看。
> **这一章在干什么**：讲清楚两件事——怎么干净地拆掉重装（16 册）、以及环境释放后留下了什么、怎么从零重建（19 册）。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `16_回滚与重装.md` + `19_封存与重建.md`。

下面把这两册里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

## ① 拆除顺序（从上层往下，顺序不能乱）

```
① GitOps 层（ArgoCD）     先关自愈，否则删了还会被拉回来
② 业务与应用             apps 命名空间、Gateway、HTTPRoute
③ 可观测/安全            monitoring、logging、kyverno
④ 存储                   Longhorn（先删 PVC/卷，再卸 helm，最后清数据盘）
⑤ 入口                   Envoy Gateway、cert-manager
⑥ CNI                    Cilium（在 reset 之前卸，残留更少）
⑦ 控制面                 三台 kubeadm reset
⑧ 底座                   keepalived / haproxy / 主机名 / hosts / sysctl
```

**为什么必须从上层往下**：下层是上层的地基。如果先拆地基（比如先 reset 控制面），上面的 GitOps 还在跑、Pod 还挂着，就会出现 Pod 卡在 Terminating、PVC 删不掉、CNI 残留导致新集群起不来。**先关自愈是第一步中的第一步**——不关的话你这边删，ArgoCD 那边拉，永远删不干净。

---

## ② kubeadm reset 之后必须手工清的残留（最容易漏的部分）

`kubeadm reset -f` 只清它自己管的东西，下面这些它不管，**留着就会让下一次 init/join 出怪问题**：

```
① 静态 Pod 清单 /etc/kubernetes/manifests/*.yaml
   留着会自己起旧组件

② etcd 数据 /var/lib/etcd
   不清会导致新集群带着旧成员信息启动失败

③ CNI 配置与状态 /etc/cni/net.d/* /var/lib/cni /var/run/cilium + 删 cilium_* 网卡
   ★ 最容易漏——漏了新集群 Pod 拿不到 IP

④ kubelet 配置 /var/lib/kubelet/config.yaml /pki

⑤ kubeconfig 与证书 /etc/kubernetes /root/.kube

⑥ iptables/nft 残留   最干净的的办法是 reboot 一次

⑦ 审计与加密目录 /etc/kubernetes/audit /enc /var/log/kubernetes
```

**怎么确认清干净了**：
```
ls /etc/kubernetes       → No such file or directory
ls /var/lib/etcd         → No such file or directory
ip -o link | grep -c cilium → 0
systemctl is-active kubelet → inactive 或 failed（都正常）
```

**为什么要手工清**：kubeadm reset 的设计是"只重置 K8S 自己声明的资源"，CNI、etcd 数据、网卡这些是外部组件留下的。初级人员以为 reset 就全干净了，结果新集群起不来还找不到原因——八成是这些残留。

## ③ 入口与云资源

```
keepalived / haproxy    要重装就停掉，避免 VIP 抢来抢去
HAVIP 解绑             不解绑下次绑会报 status 不对；但 HAVIP 可以保留复用（不挂实例不计费）
```
本次就是复用了前一天建的 HAVIP，省了创建步骤。

---

## ④ 数据盘（只在"确认数据不要了"时做）

```
umount 后 mkfs.ext4 格式化
注意：格式化会让 fstab 里的 UUID 变，重装后要重新写
```
**如果只是重装 K8S、想保留长期数据**：别格式化，只 umount，重装后挂回同一路径。

---

## ⑤ 重装时的三个注意点

```
① 加密 key 沿用还是重生成
   沿用（推荐）：同一份 enc-key.b64 放回去，旧备份仍可解密
   重生成：旧 key 加密的 etcd 快照，新集群无法直接读取
② certSANs 必须重新核对
   重装时 VIP 可能变了，certSANs 与 controlPlaneEndpoint 都要跟着改，否则又撞 x509
③ hostname / hosts 同名同 IP 不用撤，最省事
```

## ⑥ 不要删的东西（这份清单是"救命线"）

```
k8s-deploy/id_k8s            8 台登录密钥
k8s-deploy/enc-key.b64       etcd 加密 key（丢了旧备份读不回来）
k8s-deploy/minio-creds.txt   SeaweedFS 的 AK/SK
本册与各阶段实测记录          重建时的依据
```

**为什么单列**：重装时人会"大扫除"式清理，结果把加密 key、密钥这些一次性、不可重建的东西删了——旧备份随之作废。这张清单就是防止这种悔恨。

## ⑦ 封存与重建（19 册：环境释放后还剩什么）

本次环境在 2026-11-21 15:15 释放了。**释放是不可逆的**，19 册的意义是：下次重建时只看这一册 + 00 目录就能从零再来。

**留在本地的东西（云上不再有）**：
```
搭建册 18 册 + 运维册 5 册   每册含实测回显，回答"当时为什么这么选"
scripts/2.0-deploy/          103 个文件，回答"怎么再来一遍"
state/                       18 份验收读数 + 终态快照，回答"建成时什么样"
```

**随实例消失的东西（重建要重做，但有脚本）**：
```
集群本身         用脚本从 00 照做，全程约 3 小时
Longhorn 卷数据  9 个 PVC 里的数据（Prom 指标、Loki 日志、Tempo 链路）
S3 里的备份      Velero 备份、Longhorn 备份目标、Loki chunk
Gitea 仓库账号   本地有 repo-snapshot + 口令文件，重新 push 即可
Dex / 告警落点   配置已归档
etcd 快照        本地还有一份 76MB 的
```

**重建顺序（照这个走，别自由发挥）**：
```
1  读 01 检查表，确认可用区/盘/规格
2  用 tpl/ 模板开 10 台
3  地基 → 控制面 HA → Cilium → 第一次跑 42 项验收
4  存储/可观测/GitOps/入口/安全/弹性/DRA
5  ops 脚本铺回（etcd cron、日巡检、Velero、告警）
6  跑 verify_all.py，必须 42/42
7  想练演练就照运维册 01 轮一遍
```

## ⑧ 六条"这次踩过下次别再踩"

```
① ip-masq-agent 把 172.16/12 当内网 → Pod 出网全死；改配置后旧 Pod 必须重建
② 静态 Pod 清单不能用文本插入改 → 用 YAML 解析器，改一台验一台，留 .bak
③ 删带 finalizer 的 ArgoCD App 会级联删组件（Kyverno 就这么没的）
④ 手工改控制器管的对象会被 reconcile 回去 → 改控制器的输入
⑤ CoreDNS 两副本同节点 = 没高可用 → 必须 hostname 硬反亲和
⑥ Velero 不装 node-agent 时"备份成功"但卷数据为空
```

## ⑨ 这套东西真正的价值（19 册的收尾，也是给初级人员的话）

```
这套东西的价值不在"曾经跑起来过"，而在这三样现在可以脱离云存在：
  42 项只读验收  → 能回答"还对不对"
  103 个脚本     → 能回答"怎么再来一遍"
  23 册正文      → 能回答"当时为什么这么选"
```

**一句话总结**：回滚与重装这一册讲的是"怎么体面地推倒重来"——拆除必须从上层往下、reset 后必须手工清 CNI/etcd 残留、加密 key 和密钥绝对不能删。而封存册点破了一个更深的道理：一套环境真正的资产不是那几台云主机（它们会释放、会消失），而是**可复验的脚本、文档和数字**——这些能脱离云存在，让你随时从零再来一遍。
