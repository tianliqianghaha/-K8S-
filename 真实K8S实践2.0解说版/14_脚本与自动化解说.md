# 14 · 脚本与自动化解说（100 多个脚本各自是干什么的）

> **这一章在整件事的哪一步**：这一册专门讲 `scripts/` 目录——前面章节讲的每一步，背后都是这些脚本在自动执行。
> **这一章在干什么**：把这套部署工程里每一个脚本文件的作用讲清楚。核心思想：**每个脚本对应正文某一章、章号写在文件头、每个都幂等（重复执行不会搞坏）**。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共通读 `scripts/2.0-deploy/` 全部 81 个文件 + `scripts/` 根目录 13 个运维脚本。

下面把这一批脚本里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① 先建立整体概念：脚本分三层

```
云资源准备层   开机器、拿 IP、生成配置（cloud.py / fleet.py / tpl/*.json ...）
部署执行层     s1~s20，按章把集群一层层装起来
验收层         verify_all.py + verify_remote.sh，一键判 42 项
```

**为什么要分层**：先有机器（准备层），才能装东西（执行层），装完要证明对了（验收层）。这是任何自动化部署的通用套路。

---

## ② 云资源准备层（开机器之前的"地基中的地基"）

**cloud.py**
一个只依赖 Python 标准库的阿里云 API 客户端。为什么要有它：所有脚本都要调阿里云接口（开机、绑 VIP），它把"签名、发请求、处理错误"这些脏活封装好。一个安全细节：AK（访问密钥）只从环境变量读，不写死在文件里。

**fleet.py**
本次 10 台机器的"唯一事实源"——名字、内外网 IP、实例 ID、角色、VIP 都写在这，还提供 ssh/scp 的公共函数。为什么必须有它：所有脚本都要知道"cp-1 的 IP 是多少、怎么连它"，集中在一处，改一处所有脚本都跟着变。

**inventory.py**
调云 API 拉取 10 台真实机器的清单，生成 fleet.json。作用：机器开出来后，把真实信息（zone、规格、盘）采集下来。

**gen_templates.py**
从模板派生 8 份开机配置到 `tpl/`。里面有几个重要的"护栏"机制：
```
SpotAsPriceGo       用竞价实例（省钱）
max_lifetime_hours=72  72 小时自动释放（防止忘了关一直烧钱）
dry-run + 显式确认    防止误开资源
fallback 候选区/规格   某个区没货时自动换
```

**tpl/*.json（8 份开机模板）**
cp.json / infra.json / spare.json / wk-b-u1.json / wk-b-e.json / wk-c-e.json / wk-d-u1.json / wk-d-e.json。结构一样，只改可用区、规格、盘大小、命名。为什么分成 8 份：控制面、workload 大内存型、workload 通用型、集群外机、演练机各要不同配置。

**list_vsw.py / bind_havip.py**
- list_vsw.py：只读列出 VPC 下所有交换机和可用区（排查用）。
- bind_havip.py：把 HAVIP 幂等地绑定到 3 台控制面，并打印归属。为什么要单独脚本：HAVIP 绑定有"中间状态"坑（绑第 2 台会报 IncorrectHaVipStatus），脚本里做了重试。

**gen_init.py**
动态生成 kubeadm 初始化配置 `s2-init.yaml`——从 cp-1 读真实 kubeadm 版本、按拓扑生成证书 SAN 列表。为什么动态生成而不是写死：版本、IP 每次可能不同，从实际环境读出来最准，避免"写错小版本去拉不存在的镜像"。

## ③ S1 地基执行层

**s1_bootstrap.py**
地基阶段的总编排：并发连到 10 台，注入公钥、推送 s1 脚本、依次执行 base/kernel/runtime/k8s/mount，日志落到 s1/logs/。为什么用并发：10 台逐台敲要 10 倍时间，并发 67 秒推完，且单台失败不影响别台。

**s1/base.sh / kernel.sh / runtime.sh / k8s.sh / mount.sh**
这五个就是地基章讲的五段脚本，按顺序执行（详见《02_地基解说》）。

**s1/hosts.txt / s1/logs/\*.log**
前者是生成好的 /etc/hosts（10 台 + api-vip）；后者是每台机器各阶段的执行回显，排障用。
- 一个排障提示：日志里 mount 阶段那个 `awk` 小报错但 rc=0、kubelet 显示 inactive——都是正常的（还没 init），别误判成失败。

---

## ④ S2 控制面层

**s2a_ha.py**
3 台控制面部署 haproxy + keepalived（单播 VRRP over HAVIP），验证 VIP 归属和端口。对应控制面 HA 章。

**s2b_init.py**
下发加密配置（enc-key.b64）+ 审计策略 → 校验 kubeadm 配置 → cp-1 执行 init。

**s2c_join.py**
把 cp-2/cp-3 作为控制面加入、5 台 worker 加入，汇总结果（并发 join）。

**s2-init.yaml / s2-audit-policy.yaml / s2-encryption-config.yaml**
三份配置产物：init 配置、审计策略、Secret 静态加密配置。

## ⑤ S3~S9 核心能力层（每个脚本对应一章）

```
s3a_cilium.py       装 Helm + Gateway API CRD + Cilium（eBPF 全接管、无 kube-proxy）→ 网络章
s4_storage.py       装 iscsi 前置 + Longhorn（3 副本）+ metrics-server → 存储章
s5_infra.py         infra-01 上用 docker 起 SeaweedFS(S3) + Gitea，建 bucket → 集群外依赖
s6_velero.py        配 Longhorn BackupTarget + 装 Velero → 备份
s7_observability.py 装 Prom 栈 + Loki(S3) + Alloy → 可观测章
s8_gitops.py        Gitea 建仓 + 装 ArgoCD + app-of-apps + 自愈实测 → 交付章
s9_security.py      PSA + Kyverno 三条 CEL 策略 + 探测原生 MAP → 安全章
```

对应的 yaml（`s7-kps-values.yaml` / `s7-loki-values.yaml` / `s7-alloy-values.yaml` / `s9-kyverno.yaml` / `s9-map.yaml` 等）都是这些脚本生成的 Helm values 或策略清单，是"参数化安装"的输入。

**为什么脚本和 yaml 分开**：脚本管"怎么装"，yaml 管"装成什么配置"。分开后改配置不用改逻辑。

## ⑥ S10~S20 进阶特性层

```
s10_elastic.py         HPA 扩缩 + 原地扩缩 + VPA + KEDA → 弹性章
s11_tracing.py         Tempo + OTel Collector + 追踪 → 追踪章
s12_rollouts_kueue.py  Argo Rollouts canary + Kueue 排队 → 交付/调度章
s13_ingress.py         cert-manager 内部 CA + Envoy Gateway + Gateway/HTTPRoute → 网络入口
s14_ztunnel.sh         开 ztunnel 加密，失败自动 helm rollback → 网格章（后来回滚换 WireGuard）
s15_sealed.py          装 sealed-secrets + 封存 Secret 推 Git → 密钥
s16_git_addons.py      把 10 个 addon 全声明成 ArgoCD Application → 全量纳管

s20-netpol.yaml        demo-app 默认拒绝 + 白名单网络策略 → 网络策略
```

**s14 里一个值得学的机制**：脚本自带 `helm history / rollback`——加密这种高风险变更，失败自动回滚。为什么必须有：网格变更翻车会全断，把回滚逻辑写进脚本，比"出事后人想起来敲回滚命令"可靠得多。

## ⑦ 验收层

**verify_remote.sh**
在 cp-1 上只读采集所有读数，输出 KEY=VALUE 供判分。为什么不直接在本机判：数据在集群里，得登上去采集。只读保证不破坏环境。

**verify_all.py**
把 verify_remote.sh 推到 cp-1 执行，按 41/42 项阈值判 PASS/FAIL，结果写 `state/verify-*.json`。为什么必须有：一键出结论，变更前后各跑一次。

**verify.yaml / pvc-test.yaml**
验收用的"探针工作负载"——verify.yaml 是跨 3 个可用区强制打散的 2 副本 probe，pvc-test.yaml 是测 Longhorn 动态供给的 PVC。为什么要有：验收不能只看"配置在不在"，要真跑一个负载看通不通。

**repo/ 目录（app-of-apps.yaml / demo-app/all.yaml）**
Git 仓库的初始内容：总的 Application 入口 + demo 业务的全套资源。为什么要有：ArgoCD 得有个起点，这堆文件就是"Git 里的第一版真相"。

## ⑨ 一个贯穿所有脚本的重要习惯：Windows 传 Linux 要去掉 \r

脚本写在 Windows，传到 Linux 会带 `\r`，所以每次 scp 后必须先 `sed -i 's/\r$//'`。为什么单列出来：这是 Windows 环境下做 Linux 自动化的经典坑，忘了就报 `bad interpreter` 之类的怪错。

## ⑩ 这一章的坑（讲给初级人员）

```
现象：直接照抄静态 yaml 部署，结果和文档回显对不上
根因：有些"落盘的 yaml"和"脚本内嵌的配置"不是同一版（本次发现多处差异）
防：以"脚本实际执行时生成的配置"为准；落盘文件是产物，可能滞后

现象：脚本报权限/认证错
根因：AK/口令要从环境变量读，没设置
防：执行前先确认凭据环境变量就位

现象：Dex 口令登录失败
根因：脚本每次生成随机口令，但配置里的 bcrypt hash 是写死的，两者可能不匹配
防：演练环境留意这类"随机值 vs 固定值"的拼接点
```

**一句话总结**：这 100 多个脚本就是整套集群的"施工图"——分三层（准备/执行/验收），按章编号、幂等执行。读脚本有个心法：**看文件头注释就知道它是哪章干嘛的；以脚本实际执行的配置为准，别只信落盘的 yaml。** 具体脚本对应哪章、装什么组件，前面每一章的解说里都已经讲过，这里是把它们串成一张地图。
