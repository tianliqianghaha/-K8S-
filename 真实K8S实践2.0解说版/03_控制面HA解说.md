# 03 · 控制面 HA 解说（三台大脑，对外只有一个门牌号）

> **这一章在整件事的哪一步**：第 1 章推完地基，但 10 台全 NotReady（还没 CNI）→【第 2 章把控制面立起来】→ 第 3 章装网络。
> **这一章在干什么**：让"3 台 apiserver"对外只呈现一个地址 `172.23.163.97:16443`。kubeadm 的 controlPlaneEndpoint、所有节点的 kubeconfig、Cilium 的 k8sServiceHost，全用这一个地址。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `03_第2章_控制面HA.md` + `scripts/s2a_ha.py` / `s2b_init.py` / `s2c_join.py` / `gen_init.py`。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① HAVIP（高可用虚拟 IP）

它是什么：云上注册过的一个"浮动 IP"，可以在 3 台控制面之间飘。哪个节点持有它，外面的人就访问到哪台机器的 apiserver。

为什么必须有它，不能自己在网卡上加个 IP  exploits：本次做过实测——在自己网卡上加一个空闲 IP，从对端 ping，3 个包 100% 丢。原因是**阿里云 VPC 不转发"未分配给实例的 IP"的 ARP 请求**，自建 VIP 在云上天然不成立。所以必须用 HAVIP——它是在 VPC 里注册过的地址，允许 ARP。

附带一个限制：HAVIP 只能挂同一交换机下的实例，这就是 3 台控制面必须挤在同一个可用区的根本原因（也是本套架构的已知单点）。

---

## ② haproxy（四层转发）

它是什么：一个负载均衡器，只做一件简单的事——把 `16443` 端口的 TCP 连接，轮流转给后端 3 台 apiserver 的 `6443`，并且每 2 秒做一次健康检查（挂了的那台摘掉）。

为什么必须有它：3 台 apiserver 是 3 个独立进程，你不能让外面的人记 3 个地址。haproxy 在前面挡一层，对外永远是一个地址；后面哪台挂了，自动切到还活着的。

一个命名坑：backend 千万别跟 frontend 同名（都叫 kube-apiserver），3.2 只是警告，3.3 直接报错。本次叫 `kube_apiserver_back`。

---

## ③ keepalived（VIP 谁来持有）

它是什么：让 3 台控制面"协商"出一台来持有那个 HAVIP，优先级 cp-1=150 / cp-2=140 / cp-3=130，谁高谁主。主的那台挂了，备的自动顶上（3 秒内）。

为什么必须有它：光有 haproxy 还不够——haproxy 自己也是个进程，会挂。keepalived 的职责是"盯着 haproxy，一旦它挂了就主动降优先级，把 VIP 让给别的节点"。

两个关键点：
- **必须单播（unicast），不能组播**：云上组播被过滤，两台互相听不到，就会出现"双主"（两台都 hold 同一个 VIP）。本次用 `unicast_src_ip` + `unicast_peer`，且 `virtual_router_id` 全网唯一。
- **必须同时盯 haproxy**：只 track 网卡的话，网卡活着但 haproxy 挂了，VIP 不会漂，kubectl 全失败。做法是加个脚本探 `127.0.0.1:16443`，探不到就扣权重。

---

## ④ kubeadm init / join（真正把集群建起来）

**kubeadm init**：在 cp-1 上执行，初始化控制平面——生成一堆证书、启动 etcd、拉起 apiserver/controller-manager/scheduler。

**join**：cp-2 / cp-3 用 `--control-plane` 加入（变成第 2、3 台大脑），5 台 worker 用普通 join 加入（变成干活的手脚）。

两个关键动作：
- `--upload-certs`：把证书加密上传到集群，其他控制面 join 时自动获取，不用手工拷贝。
- `--skip-phases=addon/kube-proxy`：跳过默认的 kube-proxy 安装——因为第 3 章要用 Cilium 的 eBPF 接管这部分。这是"先进"能力的起点。

**版本不要写死**：`kubernetesVersion` 取 `kubeadm version -o short` 的真实输出（本次是 v1.37.2）。写成"最新"或写错小版本，init 会去拉一个根本不存在的镜像。

---

## ⑤ certSANs（证书里的"允许名单"）

它是什么：apiserver 证书里记录的一串"合法地址"——VIP + 10 台节点 IP + 节点名 + api-vip + 127.0.0.1，本次 19 条。

为什么必须有它：证书会校验"你访问的地址在不在名单里"。join 时如果用的是 VIP 而证书里漏了它，就报 `x509: certificate is valid for ... not 172.23.163.97`。init 前把"VIP + 全部节点 IP + 节点名"列成清单逐项核。

---

## ⑥ 静态加密 + 审计日志（两个安全底座）

**aescbc 静态加密**：apiserver 把 Secret 写进 etcd 时先加密（AES-256-CBC），防止有人直接读 etcd 拿到明文口令。密钥落在本地 `enc-key.b64`——这个文件丢了，旧备份就再也解不开，属于"绝对不能删"的东西。

**审计日志（audit-policy）**：记录谁在什么时候对集群做了什么。策略分级——探针查询不记、Secret/ConfigMap/RBAC 这类敏感写操作记完整内容、其余只记元数据。挂载进 apiserver 生效。

---

## ⑦ etcd 三成员（集群的"账本"）

它是什么：K8s 的分布式数据库，整个集群的所有状态（有哪些 Pod、哪些配置）都存在这里。3 台控制面各跑一个 etcd 成员，构成高可用。

为什么必须是 3 个（奇数）：etcd 靠"多数派"投票，3 个能容忍挂 1 个还剩 2 个（过半）。挂 2 个就丢仲裁、集群不可用。本次 healthz 提交耗时 10.4 / 15.6 / 79.2ms——跨交换机的那台最慢，正常。

---

## ⑧ 三探针：怎么确认控制面真的起来了

```
① ip -4 -o addr show eth0 | grep 172.23.163.97    VIP 现在在哪台（只应有一台 hold=1）
② curl -sk https://172.23.163.97:16443/healthz → ok   从任意节点（含跨 AZ）打 VIP 都通
③ 停 cp-1 的 haproxy，VIP 应在 3 秒内换到 cp-2      漂移真的会发生
```

为什么第 ③ 条最关键：前两条只能证明"现在能用"，第 ③ 条才能证明"挂了能切"——高可用的价值全在切换那一刻。

---

## ⑨ 判官卡：控制面能不能跨可用区

```
选项 A HAVIP + 同交换机（本次）
  优点：免费、延迟最低、配置最简单
  缺点：3 台控制面必须同 AZ；该 AZ 整体故障 = etcd 丢仲裁 = 全集群不可用

选项 B 私网 CLB 作 controlPlaneEndpoint
  优点：后端可跨可用区，控制面能拆到 b/c/d，真正跨 AZ 高可用
  缺点：多一个付费组件，且 CLB 的四层健康检查与 haproxy 要二选一

判据：目标是"练会跨 AZ 架构"→ 选 B；目标是"练会整套平台能力"→ A 够用，跨 AZ 留给工作负载层。
本次：A，并把"控制面单区"写进最终清单的"答不了"清单（诚实记录边界）。
```

## ⑩ 这一章的坑（讲给初级人员）

```
现象：HAVIP 绑第 2 台报 IncorrectHaVipStatus
根因：绑完第 1 台后进入中间状态，必须等回落
防：重试 5 秒 × 12 次，别以为配置错了

现象：init 卡在 wait-control-plane，apiserver 反复 Exit
根因：scp 加密/审计配置时目标目录还没建，文件没落盘
防：先 mkdir 再 scp，scp 完立刻 ls 确认

现象：join 报 x509: certificate is valid for ... not 172.23.163.97
根因：certSANs 漏了 VIP
防：init 前把 VIP 列进 IP 清单，看 [certs] 那行确认

现象：keepalived 双主（两台都 hold 同一个 VIP）
根因：用了组播 VRRP，云上组播被过滤，两台互相听不到
防：必须 unicast_src_ip + unicast_peer
```

**一句话总结**：这一章就是把"3 个大脑"包装成"1 个门牌号"。HAVIP 提供地址、haproxy 负责分流、keepalived 负责切换、kubeadm 负责建集群、证书和 etcd 负责安全与账本。缺任何一个，"高可用"三个字都是空的。
