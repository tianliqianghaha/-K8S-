# 06 · 可观测解说（指标 / 日志 / 告警，三件事别混成一锅粥）

> **这一章在整件事的哪一步**：第 4 章数据能存能恢复 →【第 5 章出问题能看见】→ 第 6 章安全与准入。
> **这一章在干什么**：建"监控系统"，但拆成三件独立的事——指标（谁出问题、曲线怎么变）、日志（到底报了什么错）、告警（谁能被叫醒）。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `06_第5章_可观测.md` + `s7_observability.py` + `s7-*.yaml`。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① 先分清三件事（本章最该建立的概念）

```
指标 metrics   → 数字随时间的变化曲线（CPU 多少、请求多少、磁盘多少）
                 回答"哪里不对劲、什么时候开始的"
日志 logs      → 一行行的文字记录
                 回答"具体报了什么错"
告警 alerts    → 规则触发后主动通知人
                 回答"谁来管、什么时候管"
```

为什么必须分开？初级人员常装个"监控大礼包"就以为完事了，结果出问题三样里缺一样——有曲线不知道报什么错，有日志不知道什么时候开始的。**三样各自独立，才能互相补位。**

---

## ② metrics-server（最基础的一块：kubectl top 要有数）

**是什么**：一个很轻的组件，定期从每个节点收集 CPU/内存使用量，提供给 K8S 内部用。

**为什么必须有它**：装了它 `kubectl top node` 才有数字。更重要的是——**HPA（第 7 章的自动扩缩）要靠它拿 CPU 利用率**，没它 HPA 会显示 `<unknown>/50%`。本次 2 副本，8 台节点全部有数。

---

## ③ kube-prometheus-stack（指标 + 告警 + 看板，一整套）

**它是什么（Prometheus）**：一个"按时间点拉数据"的监控系统。它每隔几秒去各个组件那里"拽"一个数字存起来，日积月累成曲线。本次活跃抓取目标 51 个，全部 up。

**为什么必须有它**：没有指标曲线，你只能"出问题后登上去看"，无法知道问题是从什么时候开始的、趋势是在恶化还是好转。

**配套的另外两个组件**：
```
Alertmanager   告警的"路由器"：Prometheus 触发告警后，由它决定按级别送到哪
               本次 3 副本 + 硬反亲和（3 个副本必须在不同节点）
Grafana        看板：把 Prometheus 里的数字画成图，人看着直观
               本次 2 副本，NodePort 30300 暴露
```

**为什么 Prometheus 要 2 副本 + 硬反亲和**：单个 Prometheus 挂了就彻底瞎了。两个副本强制放不同节点，一个挂另一个还在；数据存 20Gi Longhorn、保留 7 天。

---

## ④ Loki + S3 后端（日志系统）

**Loki 是什么**：一个日志存储查询系统（Grafana 公司的产品，类似简化版 ELK）。它不像传统日志系统那样全文索引，只索引标签，所以便宜、省空间。

**为什么日志要落到集群外 S3**（本章一个重要设计）：
```
Loki 只把索引和 WAL 放本地（10Gi Longhorn），日志正文全写到集群外的 S3（infra-01）
好处：
  ① 集群重建后日志还在
  ② 不占 Longhorn 三副本的宝贵容量
  ③ 和备份共用一套对象存储，成本低
判据：日志属于"事后取证"数据，生命周期比集群长，就不该放在集群里。
```

本次保留 72 小时。`deploymentMode: SingleBinary` 是单机模式（练习环境够用，省组件）。

---

## ⑤ Alloy（日志采集器）

**是什么**：一个跑在每台节点上的采集代理（DaemonSet，每节点一个，本次 8/8）。负责从各个 Pod 收集日志，打上标签，送到 Loki。

**为什么必须是 DaemonSet（每节点一个）**：日志产生在每个节点上，就近采集最可靠。它自动给日志打 8 个标签：app / container / instance / job / namespace / node / pod / service_name——有了这些标签，你才能按命名空间、按 Pod 去查日志。验证时 Loki 侧能查到这 8 个 label 列表，就说明"采集 → 写入 S3 → 可查询"整条链路通了。

## ⑥ 可观测这一章的两个坑（都是"看着像集群坏了，其实是配置"）

```
坑 1  Grafana 2 副本 + persistence.enabled=true → 第二个副本永远 Init:0/1
根因：两个 Pod 想共用同一个 RWO（只能单节点读写）卷，第二个挂不上，
      不报错、只是卡住（describe 里能看到 Multi-Attach error）
修法：无状态化——persistence.enabled=false，看板走 ConfigMap/Provisioning
★ 教训：凡是"多副本 + RWO 卷"的组合都要先问"这个卷能同时被两个 Pod 挂吗"。
  Prometheus/Alertmanager 用 StatefulSet（每副本一个卷，没问题）；
  Grafana 用 Deployment（共用一个卷，就有问题）。

坑 2  helm install alloy --version 1.9.2 报 chart not found
根因：1.9.2 是当年装到的 app 版本，不是 chart 版本——chart 和 app 是两套号
修法：先 helm search repo grafana/alloy --versions 看真实可用版本
★ 教训：文档里的版本号分两种——chart 版本和 app 版本，混用必踩。
```

## ⑦ 判官卡：Prometheus 要不要上 Thanos / VictoriaMetrics

```
选项 A 单集群 Prometheus 2 副本 + 7 天（本次）
  优点：组件少、查询路径最短、练习环境够用
  缺点：7 天以后查不到；跨集群看不到

选项 B 加 Thanos sidecar + 对象存储
  优点：长期存储 + 全局视图
  缺点：多 4 个组件，排查链变长
判据：先把"7 天内能不能查、告警能不能到人"做实，再谈长期存储。
```

## ⑧ 这一章的坑补充（告警分级在运维册做）

本章只把指标/日志/告警的"底座"装好，告警**分级路由**（P1 立即叫 / P2 当天处理 / P3 上班看）留到运维册和后续章节做。

**一个容易混淆的点**：本章装的 Alloy 只管日志；第 9 章追踪会用另一个组件（beyla）管链路。为什么不全塞给 Alloy？因为曾经试着往 Alloy 里塞 eBPF 采集，配置一直不生效，最后决定"日志和探针拆成两个组件，各管一件事，故障不互相牵连"。

```
现象：Alloy 报 illegal character U+003B ';'
根因：Alloy 的配置语法是一行一个属性，不能用分号分隔
防：写完用 alloy fmt 校验，或看 pod 日志确认 reload 成功
```

**一句话总结**：可观测三件套——Prometheus 看趋势、Loki 查日志、Alertmanager 送告警，采集靠 Alloy、看板靠 Grafana。核心设计原则是"日志和指标放集群外、多副本配硬反亲和、版本号分清 chart 和 app"。装齐了，出问题你才"看得见"。
