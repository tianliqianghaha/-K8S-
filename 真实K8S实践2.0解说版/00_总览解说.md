# 00 · 这套东西到底是干什么的（总览解说）

> **先把原话摆在这里，让你知道我们讲的是哪一套东西**
> 「我要的是先进的，完备的 K8S 自建集群。除了控制面 3 台以外，把机器打散在香港的 3 个可用区里面。控制面 3 台没法调整，只能在一个区，因为 HAVIP 只能在一个交换机下。」
> 「你每做一个大的章节步骤，就按照之前的格式放在 D:\真实K8S实践2.0 里面，要完整版本。」
> 「不用中间停下来问我，有问题自己解决，一直操作就行。直到所有的部署验证完毕。」

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 **19 册搭建文档 + 5 册运维文档 + 100 多个脚本**。

下面把这套资料里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。这一篇先看全局地图，后面每一篇拆一个章节。

---

## ① 这套东西最终建出来是个什么

先用一句话说清楚：**这是在阿里云香港区，用 10 台云主机，从一台裸机开始，纯手工（不依赖云厂商托管的 K8S 服务）搭出一套"先进且完备"的 Kubernetes 集群，并且把怎么搭、怎么验、坏了怎么救、怎么拆了重来全部写成文档和脚本。**

"自建"是什么意思？云厂商本来卖你一个现成的 K8S（比如 ACK），点几下就有了。这里不这么做——从装系统、调内核开始，一层一层自己装上去。为什么要这么折腾？因为只有自己装，才能用上那些"先进"能力（比如不要 kube-proxy 的 eBPF 网络、不用改代码的链路追踪），也才能真正搞懂每一层在干嘛。

---

## ② 为什么这套资料分成两本册子

```
搭建册（根目录 00–19）   从裸机到能交付，做一次就固定下来
运维册（运维演练/）      建好之后每天怎么维持、坏了怎么救、怎么证明它还活着

分工就一句话判断：
  半年后重看，一个字都不用改  →  归搭建册
  每周/每天都要跑，每次都留新读数  →  归运维册
```

为什么必须分开？因为"怎么装"和"怎么养"是两拨动作：装集群是一次性的大工程，养集群是天天重复的小检查。混在一起，看的人就分不清哪些是"当初的决定"、哪些是"今天的读数"。

## ③ 为什么 2.0 要重做一遍（它补上了 1.0 做不了的事）

1.0 已经能跑通所有闭环，但被 8 台一样的机器卡住了三件事，2.0 就是来补这三件事的：

```
① 跨可用区      1.0 全挤在一个区；2.0 把工作节点打散到 b / d / c 三个区
② 容量余量      1.0 存储 208G 被 219G 的需求撑爆，副本重建失败过；2.0 给到 1050G
③ 异构调度      1.0 全是 4C8G 一种规格；2.0 混进 2 台 16G 的机器，练"按池子调度"
```

另外把 1.0 里"纯软件能补的四项"也一起做了：准入的变更侧、链路追踪、渐进式发布、设备声明式分配（DRA）。

一句话：**1.0 证明"能跑"，2.0 证明"跑得先进、跑得有扰动也不倒"。**

## ④ 10 台机器各自扮演什么角色

```
控制面 3 台  cp-1 / cp-2 / cp-3    管集群的"大脑"，必须在同一个区（HAVIP 限制）
工作节点 5 台 wk-1 ~ wk-5          真正跑业务的"手脚"，打散在三个区
集群外 1 台   infra-01             放 Git、对象存储、身份、告警接收——集群的"后勤"
演练机 1 台   spare-01             故意不入集群，专门用来做破坏性演练（重建、升级）

可用区分布：
  c 区  cp-1 cp-2 cp-3 wk-5       （控制面全在这，这是已知单点）
  b 区  wk-1（16G） wk-3（8G）
  d 区  wk-2（16G） wk-4（8G）
```

为什么要有一台不入集群的 spare-01？因为"恢复演练"必须在跟生产隔离的机器上做——你不能为了验证"坏了能修"，就在正在跑业务的机器上搞破坏。它不入集群，就不会被调度去跑业务，才能当干净的演练场。

## ⑤ 几个老出现的网络地址是干嘛的

```
HAVIP 172.23.163.97:16443   整个集群对外唯一的门牌号（所有节点、组件连它）
Pod 网段   10.244.0.0/16    容器们内部用的地址段
Service 网段 10.96.0.0/12    服务的虚拟地址段
VPC 网段   172.16.0.0/12     云上机器所在的地址段，安全组按这个放通
```

记住一句话：**外面的人只认那个 VIP，里面 Pod 和 Service 各有各的网段。** 后面很多坑（SNAT、证书、安全组）都跟这几段地址有关。

## ⑦ 这套资料的两条铁律（懂了它，你就懂为什么文档这么写）

```
① 正面只讲正面：讲怎么装就只讲怎么装，失败统一丢到每章末尾的"核心大坑"。
② 大坑一条三行封顶：现象 / 根因 / 怎么防，不写心路历程。
```

还有一条 2.0 特有的，最重要：

```
④ 每个"先进"能力都必须有一个数。
   "装了 KEDA"不算完成；"队列长度过 20 → 副本 1 变 4、90 秒内回落"才算。
```

为什么？因为"我装了"是主观的，"数字达标"是客观的。初级人员最容易犯的错就是"组件起来了就以为成功了"，这套资料逼你用数字证明。

## ⑧ 最后验收口径：什么叫"建成"

分两栏，互不替代：

```
完备 = 每个闭环都能自己走一遍
  节点/etcd/入口高可用 · 存储与恢复 · 可观测与告警 · 密钥不落明文 · GitOps 自愈

先进 = 每个能力都有一个数
  无 kube-proxy 的 eBPF · 无 sidecar 的加密 · 事件驱动弹性 · 原地扩缩
  · 设备声明式分配 · 变更侧准入 · 零改动追踪 · 渐进式发布
```

最终成绩：**9 个"先进槽位"里，8 个完全达标，1 个（服务身份）达标一半。** 这套解说版会把每一个槽位是怎么做到的、为什么这么做，全部讲清楚。现在开始。
