# 07 · 安全与准入解说（谁能改什么、什么能进来、密钥怎么进 Git）

> **这一章在整件事的哪一步**：第 5 章看得见了 →【第 6 章管安全与准入】→ 第 7 章弹性。
> **这一章在干什么**：立三道防线管"什么能进集群"，再加密钥、身份、网络策略、配额四块，把"谁能改什么、什么能进来、密钥怎么放"全部管住。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `07_第6章_安全与准入.md` + `s9_security.py` / `s9-kyverno.yaml` / `s9-map.yaml` / `s15_sealed.py` / `s17_oidc.py` / `s20-netpol.yaml`。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

## ① 三道准入防线（管"什么能进集群"，三者各司其职）

准入（Admission）= API Server 在"接收一个创建请求"之前设的关卡。三道防线：

```
① PSA（Pod Security Admission）     API Server 内建，零组件，管"Pod 的安全上下文"
② ValidatingPolicy（Kyverno CEL）  管"团队的规范"（标签、资源、镜像来源）——负责"拒"
③ MutatingAdmissionPolicy（原生）  管"帮不规范的写法补齐"——负责"改"
```

**为什么必须有三层，一层不够吗**：
- PSA 是硬下限（不许 privileged、必须非 root），原生自带、拖不慢，但它不懂"必须有 owner 标签"这种业务规范。
- Kyverno 管规范，但它是个 webhook，**它挂了写入就受影响**（所以要 ≥2 副本）。
- 只拒不改会出问题："要么全公司改 Helm chart，要么全过不去"。所以加第三层，把能安全补齐的（label / annotation / 默认 resources）自动补上，剩下的硬要求才交给人改——这才落得了地。

---

## ② PSA restricted（一条 label 就是一道防线）

**是什么**：给命名空间打一条 label `pod-security.kubernetes.io/enforce=restricted`，这个命名空间里的 Pod 就必须满足最严格的安全要求。

**为什么必须有它**：防止有人起一个特权容器（privileged）直接拿到宿主机权限。本次实测：裸 Pod 被 API 直接拒绝，4 条原因一次列全（allowPrivilegeEscalation、capabilities、runAsNonRoot、seccompProfile）。合规 Pod 正常放行。

---

## ③ Kyverno + CEL ValidatingPolicy（团队规范的执行者）

**Kyverno 是什么**：一个专门做 K8S 策略的引擎，用一种叫 CEL 的表达语言写规则。

**本次三条规则**（逐条实测被拒）：
```
① 禁用 :latest 标签的镜像（防止"今天和明天跑的不是同一个版本"）
② 必须声明 requests + limits（防止容器不吃不设限、把节点拖垮）
③ 禁 privileged 容器
```

**一个版本坑**：Kyverno 1.20 只执行 CEL 策略，老的 ClusterPolicy（legacy 类型）已经被移除。所以用 `policies.kyverno.io/v1` 的 ValidatingPolicy。而且验证时要去**没打 PSA 标签的命名空间**测，否则永远是 PSA 先拦，测不到 Kyverno。

---

## ④ 原生 MutatingAdmissionPolicy（变更侧：帮人补齐）

**是什么**：K8S 原生的"改写"策略（1.37 已 GA，版本是 `admissionregistration.k8s.io/v1`）。给打了 `mutate=enabled` 标签的命名空间里新建的 Pod 自动加注解。

**为什么必须有它（变更侧的价值）**：前面说了——只拒不改，落地难。变更侧把能自动补的东西补上，人只需要改真正过不了的那部分。**能用原生就别用 Kyverno 的 Mutate**——少一个 webhook 就少一个故障面。

**怎么确认它生效**：做个对照组——打了标签的 ns 里 Pod 被改了（`mutated=map`），没打标签的 ns（demo-app）里是空的。证明 binding 的选择器精确生效。

**CEL 语法坑**：三元表达式里直接放 map 字面量会报 "mismatched input ':'"，拆成单层 map 或加括号。

---

## ⑤ Sealed Secrets（密钥怎么安全进 Git）

**它是什么**：让 Secret 能进 Git，但进去的是**密文**——只有集群里的私钥能解开。

**为什么必须有它**：GitOps 要求"所有配置都在 Git 里"，但 Secret 里有明文口令，直接提交等于把密码公开。Sealed Secrets 的流程是：
```
明文 Secret（本地，不提交）
  → kubeseal 用控制器的公钥加密
  → SealedSecret（可以进 Git、可以进 ArgoCD）
  → 控制器用私钥解出真正的 Secret
```
Git 泄露 ≠ 口令泄露，因为只有集群里的私钥能解。本次实测：明文泄漏检查 0 处、删掉 Secret 后 1 秒内自动重建。

**代价**：无轮换、无审计、无动态租期；**私钥丢了全部密文作废**，所以私钥必须离线备份。

---

## ⑥ OIDC + Dex（身份闭环：谁能登录、能干什么）

**OIDC 是什么**：一种标准的登录认证协议。让 K8S 不再只用本地证书，而是能对接外部身份系统（这里是 Dex）。

**Dex 是什么**：一个身份认证服务，跑在 infra-01 上（HTTPS 5556）。三台 apiserver 都配了 5 个 OIDC 参数指向它。

**为什么必须有它**：光"能登录"没用，重要的是"身份能映射到权限"。本次建了个只读角色（ClusterRole view）绑给 viewer 用户，然后验证：
```
viewer    get pods    → yes（能看）
viewer    delete pods → no（不能删）
陌生人     get pods    → no（进不来）
```
**这三行比"登录成功"更有意义**——它证明认证和授权都对了。

**两个坑**：
- 改 apiserver 静态 Pod 清单**不能用文本插入**（缩进错了 YAML 非法，apiserver 起不来、VIP 直接 EOF）。必须用 YAML 解析器结构化地改，改一台验一台，改前备份。
- Dex v2.44 起不再提供 local connector，取 token 要走授权码流程（kubelogin），别指望老版的密码授权。

---

## ⑦ NetworkPolicy 默认拒绝 + 白名单（管"创建出来能连谁"）

**是什么**：网络策略——准入管"能不能创建"，NetworkPolicy 管"创建出来能连谁"。本次在 demo-app 命名空间做：
```
default-deny           ingress + egress 全拒（先关上门）
allow-dns             放行 DNS（否则服务名解析不了）
allow-same-ns         同命名空间互访
allow-gateway-monitor 放行网关和监控的入站
allow-egress-api      放行到 apiserver
```

**为什么必须有它**：K8S 默认所有 Pod 之间可以随便互访，一个被打穿的 Pod 能横着走到任何服务。默认拒绝 + 白名单把"能连谁"收缩到最小。

**一个关键细节**：Cilium 里 apiserver 是一个"实体"（host identity），不是普通 IP。第一版按 `ipBlock 10.96.0.0/12:443` 放行仍然不通，正解是 `toEntities: kube-apiserver`。

---

## ⑧ ResourceQuota + LimitRange（配额与限额）

```
ResourceQuota   管"整个命名空间的总量上限"：cpu 4 / mem 8Gi / pods 30 / pvc 6
LimitRange      管"单个容器别不写限制就没上限"：默认 request 20m/32Mi、limit 200m/128Mi
```

**为什么两个都要**：只有 Quota，一个容器就能吃掉全部配额；只有 LimitRange，命名空间总量无上限。两个配合才既防"一个容器撑死"又防"整体失控"。

---

## ⑨ 这一章的坑（讲给初级人员）

```
现象：MutatingAdmissionPolicy apply 报 "no matches for kind ... in version v1beta1"
根因：1.37 里它已 GA，版本是 v1
防：先核对该 API 在实际环境里的 group/version，按实际写清单

现象：CEL 改写策略写好但 Pod 没变，也没报错
根因：Binding 的 namespaceSelector 没匹配上（命名空间没打标签）
防：做个不打标签的对照组确认

现象：Kyverno 装完所有 Pod 创建都变慢甚至超时
根因：admissionController 只 1 副本且 failurePolicy=Fail，webhook 一抖全站写入卡住
防：副本 ≥2 + PDB；想清楚 failurePolicy 要不要改 Ignore

现象：自己的 Kyverno require-resources 把 VPA 自己的 Pod 也拦了
根因：策略没排除平台命名空间，先拦了"自己要装的东西"
防：matchConditions 排掉 vpa/keda/kyverno/longhorn/monitoring 等
```

**一句话总结**：安全这一章是"层层设卡"——PSA 守硬下限、Kyverno 守规范、原生变更策略帮补齐；Sealed Secrets 让密钥能安全进 Git、OIDC 让身份能映射权限、NetworkPolicy 管谁能连谁、Quota 管资源上限。核心思想：**默认拒绝、最小权限、能自动补的别麻烦人**。
