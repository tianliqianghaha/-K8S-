# 08 · 弹性解说（该扩就扩、该缩就缩，而且不重启）

> **这一章在整件事的哪一步**：第 6 章管谁能改什么 →【第 7 章让集群会自己伸缩】→ 第 8 章调度与设备。
> **这一章在干什么**：四件事解决四个不同问题，别混成一个"弹性方案"——HPA（按指标扩副本）、原地扩缩（改单个 Pod 资源配置不重启）、VPA（告诉你该给多少）、KEDA（按事件扩缩、能缩到 0）。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `08_第7章_弹性.md` + `s10_elastic.py` / `s10-burn.yaml` / `s10-keda.yaml`。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① HPA（横向扩缩：副本数按指标变）

**是什么**：Horizontal Pod Autoscaler，监控 CPU 等指标，自动增减 Pod 的副本数量。本次实测：CPU 用到 200%（目标 50%）时，副本从 2 → 4，20 秒内到位。

**为什么必须有它**：流量高峰时手动加副本来不及，低谷时留着一堆 Pod 浪费钱。HPA 让副本数跟着负载自动走。

**一个关键概念**：HPA 算的是"利用率"，利用率 = 实际用量 ÷ **requests**。所以目标容器必须写 requests，否则分母算不出来，HPA 显示 `<unknown>/50%`。防：先确认 `kubectl top` 对那个 Pod 有数，再建 HPA。

---

## ② 原地扩缩（InPlacePodVerticalScaling：纵向扩缩但不重启）

**是什么**：K8S 1.33+ 的新能力——直接改一个正在运行的 Pod 的 requests/limits，容器不重建、Pod UID 不变。本次实测：requests 200m → 300m，10 秒内实际值变成 300m，重启次数 0。

**为什么必须有它**：传统的"改资源配置"要改 Deployment 模板，一改就滚动更新、起新 Pod——数据库这类有状态服务一重启就可能出问题。原地扩缩让你"热改"限额，不打断业务。

**最大的认知坑**：
```
✗ 改 Deployment 的 resources，期望原地生效
  原因：Deployment 模板一变就滚动新 ReplicaSet → 起新 Pod
✓ 正解：patch Pod 的 resize 子资源
  kubectl patch pod $POD --subresource resize ...
```
而且要 requests 和 limits **一起抬**，只抬 requests 会报 "must be less than or equal to cpu limit"。

---

## ③ VPA（Vertical Pod Autoscaler：告诉你该给多少）

**是什么**：分析 Pod 的实际用量，给出"你应该申请多少 CPU/内存"的建议。本次 Off 模式给出建议 cpu=25m / memory=250Mi。

**为什么必须有它**：人填资源请求时经常瞎填。本次 VPA 给 web 的内存建议 250Mi，远高于手填的 32Mi——说明手填值不合理。VPA 帮你校准。

**为什么用 Off 模式（只给建议、不动线上）**：VPA 自动改和 HPA 会打架（见下面）。练习环境先 Off，看建议、学经验，最安全。

---

## ④ KEDA（事件驱动扩缩：能缩到 0）

**是什么**：Kubernetes Event-Driven Autoscaling，按"事件"而不是 CPU 来扩缩。本次用 cron 触发器把 Pod 从 0 副本拉到 2 副本（20 秒内）。

**为什么必须有它**：HPA 最少留 1 个副本，但有些业务（批处理、定时任务、队列消费）空闲时**完全不需要 Pod**。KEDA 能缩到 0，来了事件再拉起，极省钱。

**一个天然死角（本章最值钱的教训）**：
```
本次实测：用 prometheus 触发器查 container_cpu_usage_seconds_total（Pod 自己的 CPU 用量），
缩到 0 之后就再也拉不起来了。
原因：0 副本时没有 Pod，就没有这条指标序列，KEDA 永远读到 0/空，判断"该扩了"无从谈起。
判据：能不能缩到 0，取决于"驱动指标是否存在于目标之外"，而不是装了 KEDA。
正确做法：
  ① 用外部事件源（队列长度、HTTP 请求速率、待处理文件数）——这些不依赖目标 Pod 在不在
  ② 用 cron 做确定性伸缩（本次用它证明了 0→2）
  ③ 保底 1 副本，就退化成按指标调整的 HPA
```

---

## ⑤ 三个会互相打架的组合（务必记住）

这是本章最容易翻车、也最体现"初级 vs 熟练"的地方：

```
✗ HPA(CPU) + VPA(Auto) 同一 workload
  原因：HPA 按 CPU 利用率扩副本，VPA 改 requests；requests 一变利用率的分母就变，
        HPA 立刻误判，两个控制器互相追。
  正解：VPA 用 Off 模式，或同一 workload 只留一个"会改 CPU"的控制器。

✗ Deployment 改 resources + 期望原地生效
  正解：原地扩缩要 patch Pod 的 resize 子资源。

✗ KEDA 缩到 0 + ArgoCD 自动同步
  原因：ArgoCD 发现 Git 里 replicas=2、线上是 0 → 判 OutOfSync 拉回 2，KEDA 再缩 0，反复抖。
  正解：ArgoCD 里加 ignoreDifferences（/spec/replicas）。
```

**为什么值得单独记**：这些组合单独看每个组件都对，凑一起就出事。初级人员装完单个组件觉得"我会了"，真正的经验是知道**组件之间的边界**。

---

## ⑥ 四探针：怎么算"弹性真的生效了"

```
① HPA    t=10s 副本=2，t=20s 副本=4，封顶在 maxReplicas=4 → 20 秒内扩完且不越界
② 原地扩缩  before/after 的 Pod UID 相同、restarts=0 → 真的没重启
③ VPA     建议值来自真实用量 → 证明它在分析，不是瞎给
④ KEDA    空闲=0，cron 触发后 20 秒内=2 → 能缩到 0 也能拉起
```

**注意第 ② 条的证据**：判断"原地"的唯一标准就是 **UID 不变、重启次数为 0**——光看配置变了不算。

---

## ⑦ 这一章的坑（讲给初级人员）

```
现象：HPA 显示 <unknown>/50%
根因：metrics-server 没装，或目标容器没写 requests
防：先确认指标管道对该 Pod 已出数

现象：patch pod 原地扩缩报 "must be less than or equal to cpu limit"
根因：只抬了 requests 没抬 limits
防：requests 与 limits 一起给，且 requests ≤ limits

现象：VPA 装不上，报被 Kyverno 拒绝（本次真实遇到）
根因：自己的准入策略 require-resources 把 VPA 自己的 Pod 也拦了
防：策略的 matchConditions 排除系统命名空间

现象：KEDA 缩到 0 后拉不起来
根因：用了依赖目标 Pod 自身的指标
防：换外部事件源或 cron
```

**一句话总结**：弹性四件套各有各的活——HPA 按指标横向扩副本、原地扩缩热改单个 Pod 限额、VPA 教你该填多少、KEDA 按事件能缩到 0。真正难的不是装它们，是记住**它们互相打架的组合**：同一 workload 上只留一个改 CPU 的控制器、缩到 0 的触发器必须用外部指标。
