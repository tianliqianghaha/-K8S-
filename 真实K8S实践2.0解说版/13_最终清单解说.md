# 13 · 最终清单解说（建成了什么、留档了哪些数、还差什么）

> **这一章在整件事的哪一步**：9 个槽位全部搭完 →【13 对账：建成后到底什么样】→ 14/15/17 备查。
> **这一章在干什么**：把建成那一刻的状态拍个快照、留下一组可复验的数字，并诚实列出"还差什么"和"本来就做不了什么"。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `13_最终清单.md` + `state/final-snapshot.txt` + `13` 章里的十四个数。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

## ④ 42 项一键验收（verify_all.py）

**是什么**：一个只读脚本，跑一次就把 42 项验收全判一遍（PASS/FAIL），存成 JSON。本次 42/42 通过。

**为什么必须有它（为什么要一键）**：手工验收 42 项又慢又容易漏。一键脚本的价值在"变更前后各跑一次"——掉项了就说明是这次变更引入的。它是判断"这套东西还是不是当初那个样子"的尺子。

**注意两个基线别混**：
```
交付基线（42 项）  回答"这套东西还是不是当初那样"——能力存在性，变更前后跑
日巡检（10 项）    回答"今天能不能正常干活"——每天跑，看趋势
两者不是替代关系
```

## ⑦ 本来就做不了什么（前置条件限制）

```
① 控制面跨可用区（HAVIP 限制）      ② 多集群容灾（只有一套环境）
③ 真实 IM 告警出口（无 webhook）    ④ 云 KMS/ESO（未开通）
⑤ Kubecost（计价 API 权限）
```

**为什么要把"做不了"也写清楚**：初级人员容易以为"文档没提就是做了"。明确列出边界，是对读者负责——知道哪些是能力问题、哪些是环境/成本限制，才不会在错误的地方较劲。

---

## ⑧ 这套环境能回答 / 不能回答的问题

```
能回答：集群挂了怎么恢复（RTO 13s）、外网怎么进来、谁能改什么、新版本怎么上、
        扩不扩得动、设备怎么分、密钥怎么进 Git、身份怎么映射权限、流量是否加密
不能答：服务之间谁能访问谁（缺身份）、跨 AZ 挂整区（控制面单区）、凌晨被叫醒看什么（无真实 IM）
```

---

## ⑨ 一句话总结（13 章自己的收尾）

```
9 个槽位：8 个完全达标、1 个半达标。
这一轮把"加密"从没做到已生效，把"密钥与身份"从零推到能证明权限边界，
并把 13 个 addon 全部变成 Git 里的声明。
剩下的两件 —— 把 values 搬进 Git、补一个外部 CA —— 都不是"装组件"的活。
```

**给初级人员的话**：最后这句"不是装组件的活"很关键——它点破了运维和搭建的本质区别。搭建是"装上就行"，而真正难的是把配置治理好（values 进 Git）、把安全链路补全（外部 CA）。这些才是从"能用"到"可信"的距离。
