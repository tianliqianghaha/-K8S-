# 10 · 追踪解说（一条请求到底走了哪几步，而且应用一行代码不改）

> **这一章在整件事的哪一步**：第 8 章调度排队 →【第 9 章搞清楚"一条请求走了哪几步"】→ 第 10 章交付与发布。
> **这一章在干什么**：建一套链路追踪（tracing），而且用的是 eBPF 自动埋点——**应用不需要 SDK、不需要 sidecar、不需要重启、不需要改一行代码**。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `10_第9章_追踪.md` + `s11_tracing.py` / `s11-beyla.yaml` / `s11-obi.yaml`。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① 链路追踪是什么（先建立概念）

一条用户请求从进网关到返回，中间可能经过 5 个服务、调用了数据库、排了队。链路追踪就是把这一整条路径记录成一棵"调用树"（每个节点叫一个 span），出问题能一眼看出"卡在哪一步、哪一步报错"。

**和指标、日志的区别**：
```
指标 → "整体慢了"
日志 → "这个服务报了个错"
追踪 → "这个请求在第 4 步调数据库时花了 2 秒"
```
三者互补，追踪补的是"跨服务的因果链"。

---

## ② 整体链路（数据怎么流）

```
应用（无埋点）→ 内核 → eBPF 探针（beyla）→ OTLP → Collector → Tempo → 查询
```

关键点：**探针在内核层抓 HTTP/gRPC 的进出**，应用完全不知情。这对"接管别人写的服务"特别有用——你不可能给 50 个老服务挨个加埋点代码。

---

## ③ Tempo（追踪数据的仓库）

**是什么**：Grafana 公司的分布式追踪后端，专门存 trace。本次单副本，S3 后端（bucket=tempo-traces，10Gi Longhorn 存 WAL）。

**为什么必须有它**：探针抓上来的 span 得有个地方存、能查。Tempo 就是那个"存和查"的地方。

---

## ④ OTel Collector（追踪数据的中转站）

**是什么**：OpenTelemetry Collector，一个统一接收/处理/转发遥测数据的管道。本次用 OTLP 协议（gRPC 4317 / HTTP 4318）接收，转发给 Tempo。

**为什么必须有它**：探针、应用、各种工具可能用不同格式输出，Collector 做统一收口和预处理（这里只做了 batch 批处理），后面换后端时只改 Collector 配置、不用动探针。解耦。

**排查顺序（照这个来，别跳）**：
```
① 先证明 Collector→Tempo 通：用 telemetrygen 打一条假 trace
② 再证明探针在跑：get ds beyla 看 ready 数
③ 再看探针日志有没有错误（attaching uprobes、RBAC 报错）
④ 最后才怪应用——大部分情况是 ① 或 ② 没通
```
这个顺序体现一个思路：**先证明管道后半截通，再往前查**，别一上来就怀疑应用。

---

## ⑤ beyla（eBPF 自动埋点探针，本章主角）

**是什么**：Grafana 的 eBPF 追踪探针，以 DaemonSet 形式跑在每台节点上（本次 5/5）。它在内核层挂钩（uprobe），自动发现服务的 HTTP/gRPC 调用，生成 span 发给 Collector。

**为什么必须有它（为什么不用老办法）**：
```
传统做法：给每个服务加 OTel SDK（改代码）或注入 sidecar（每个 Pod 多一个容器）
eBPF 做法：探针在内核抓包，应用零改动、零 sidecar、CPU 开销低（每节点约 50m）
```

**本次最漂亮的验收证据**：
```
打流量前：Tempo 里只有 telemetrygen 打的假数据 service.name=k8s20-verify
打流量后：Tempo 里自动出现 kyverno / loki 等集群内服务的 span
         —— 这两个应用本身没有任何埋点代码，是被 beyla 自动发现的
```

**必须给它权限**：beyla 要读 pod/service/node 信息来给 span 打 K8s 标签，所以要有 ServiceAccount + ClusterRole（pods/services/nodes/endpoints/namespaces 的 get/list/watch）+ Binding。用默认 SA 会报 `services is forbidden`。

---

## ⑥ 一个取舍：为什么最后没用 Alloy 自带的 eBPF

文档里记录了一次"及时止损"：一开始想用 Alloy 里的 `otelcol.receiver.ebpf` 做埋点，但配置怎么改都不生效（chart 的配置注入路径没打通，实际加载的还是默认配置）。继续调下去风险高，于是决定——

```
把"日志"和"eBPF 探针"拆成两个组件：
  Alloy 只管日志（第 5 章已装好）
  beyla 只管 trace（独立 DaemonSet）
各管一件事，故障不互相牵连。
```

**这条经验比技术本身值钱**：当一个组件既要干 A 又要干 B、且 B 怎么都不通时，拆开往往比硬调更快更稳。

---

## ⑦ 判官卡：eBPF 探针 vs sidecar / SDK

```
选项 A eBPF 探针（本次）
  + 零改动、零 sidecar、CPU 低
  - 只能看到"网络层能推断的东西"；应用内部的 span（数据库调用、函数耗时）看不到
选项 B sidecar / OTel SDK
  + 能看到应用内部细节、能加业务属性
  - 要改代码或注入 sidecar
判据：先上 A 拿到"请求级全景"，再对关键服务上 B 补"内部细节"。
      反过来（先 SDK）会卡在"没人愿意改代码"上。
```

---

## ⑧ 这一章的坑（讲给初级人员）

```
现象：Alloy 里塞 eBPF receiver 一直不生效
根因：chart 的配置注入路径没走通，实际加载的还是默认配置
防：日志和 eBPF 拆成两个组件

现象：Alloy 报 illegal character U+003B ';'（分号）
根因：Alloy 配置语法一行一个属性
防：写完用 alloy fmt 校验

现象：第三方镜像名踩空 otel/opentelemetry-ebpf-instrumentation:latest → repository does not exist
防：装之前 crictl pull 试一下；本项目实际可用的是 grafana/beyla

现象：beyla 起来了但没有 K8s 标签、看不到服务名，日志报 xxx is forbidden
根因：用了 default ServiceAccount，没有 ClusterRole
防：SA + ClusterRole + Binding

现象：beyla 单个 Pod 反复 OOMKilled
根因：eBPF 采集内存上限给太低
防：按节点 Pod 数给到 256~512Mi，滚动后复验 ready 数
```

**一句话总结**：追踪这一章证明了一件"先进"的事——**应用一行代码不改，就能拿到整个集群的请求级调用全景**。靠的是 eBPF 探针在内核层抓流量，Tempo 存、Collector 转、beyla 采。它和网格是互补的两半：网格管身份和加密，探针管可观测。
