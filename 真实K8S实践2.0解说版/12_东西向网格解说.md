# 12 · 东西向网格解说（服务之间的加密，成功了一半、停下了一半）

> **这一章在整件事的哪一步**：第 10 章发得出去 →【第 11 章服务之间要不要加密、要不要认身份】→ 13 最终清单。
> **这一章的结论先说清楚**：**链路加密已落地（WireGuard）**；**服务身份与"按身份授权"没落地**（ztunnel 需要外部 CA，主动放弃）。这一章最值钱的不是"做成了什么"，而是"为什么果断放弃一条路、怎么止损"。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `12_第11章_东西向网格.md` + `s14_ztunnel.sh`。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"，以及为什么有一条路走到了一半必须回头。

---

## ① 先分清两件事：加密 ≠ 身份

这是本章最该建立的认知，很多服务网格的混乱都来自把这两件事混为一谈：

```
链路加密（mTLS）  → 数据在服务之间传的时候不被旁路偷看
                     "数据是保密的"
服务身份（SPIFFE） → 每个服务有个可验证的"身份证"
                     "我能证明我是谁"
按身份授权        → 基于身份证决定"谁能访问谁"
                     "只有 A 能调 B"
```

**关键**：加密不等于身份。你可以把数据加密得很好，但仍然不知道"对面是谁"。要"谁能访问谁"这种策略，必须先有身份。

---

## ② 两条路线（本章最该记住的对比）

```
ztunnel（ambient 路线）
  给：链路加密 + 工作负载身份（SPIFFE）+ 可按身份授权
  要：一个能签发身份的 CA（istiod 或 SPIRE）
  代价：多一套控制面；改错会全断

WireGuard（本次最终采用）
  给：节点间链路加密（Pod 流量走 cilium_wg0 虚拟网卡）
  要：内核支持 wireguard 模块（26.04 自带）
  代价：一条参数、无额外组件；但没有身份，也没有按身份授权
```

判据：**"数据不被旁路看到"→ WireGuard 够；"谁能访问谁"→ 必须有身份，只能上 istiod/SPIRE。**

---

## ③ ztunnel 是什么、为什么试了又放弃

**ztunnel 是什么**：Cilium 的 ambient（"无 sidecar 网格"）路线里负责加密和身份的组件，以 DaemonSet 跑在每台节点。

**本次的尝试与失败链**：
```
按 1.20.4 参数开启 encryption.type=ztunnel，补了 bootstrap 根证书
→ Secret 生成了、ztunnel DaemonSet 建出 8 个副本
→ 但 ztunnel 全部 0/1 不就绪，日志显示连不上 CA（localhost:15012 无人监听）
→ 定位：Cilium 的"内置 CA"只给配置、不提供 CA 服务本身
→ 要走 SPIRE 路线的话，得再滚动重启全部 agent，风险大于收益
→ 判定：立即回滚，数据面无损
```

**为什么要放弃而不是硬修**：这里体现了一个成熟的判断——为了一个"身份"能力，要再滚一遍全部节点 agent，而当前目标是"先把加密落地"。风险收益不划算。于是止损、换更简单的 WireGuard。**这种"知道什么时候不做什么"比"能做很多"更重要。**

**一条极有价值的判据**：
```
现象：ztunnel 0/8，8 台节点却全是 Ready
根因：Ready 只反映 kubelet 与 apiserver 的心跳，不反映 CNI/数据面是否可用
防：数据面变更成败要看两个真信号——agent 的 Init 计数 + 目标 DaemonSet 就绪数，
    绝不能看"节点还 Ready"这种假象
```

---

## ④ WireGuard（本次成功的加密方案）

**它是什么**：Linux 内核里成熟的 VPN/加密技术。Cilium 启用后会建一个虚拟网卡 `cilium_wg0`，节点之间的 Pod 流量都从这里走、被加密。

**为什么选它**：一条参数就能开、无额外组件、内核自带。本次一次成功：
```
Encryption: Wireguard · cilium_wg0 · Port 51871 · Peers 7 · 8/8 agent 就绪
```
`Peers 7` 的意思是：其余 7 台节点都互相建立了加密通道（8 节点全互联）。

**加密生效后必须复验连通性**（别以为加密完就没事了）：Pod→Pod 跨 AZ 200、Service 200、apiserver 200、出网 404——全部正常，证明加密没有破坏转发。

---

## ⑤ 这一章的三个坑（讲给初级人员）

```
现象：ztunnel 0/8，日志反复连不上 localhost:15012，但 Secret 已生成、Pod 已起
根因：ca.type=internal 只决定"谁签发"，不提供 CA 服务本身；那个端口上没有进程
防：先确认"签发服务"真实存在（istiod 或 SPIRE），再开 ztunnel

现象：数据面变更失败，但 8 台节点全 Ready
根因：Ready 只反映心跳，不反映 CNI 可用
防：看 agent 的 Init 计数 + 目标 DaemonSet 就绪数，失败即回滚，不在数据面上做修复试验

现象：改完 apiserver 静态清单，集群 VIP 直接 EOF
根因：用文本插入改清单导致缩进错位、YAML 非法，kubelet 无法创建容器
防：用 YAML 解析器结构化修改，改前备份，先一台验活再推广
```

## ⑥ 优先级：为什么加密这么排

本章记录了一次事后看"排对了"的优先级：
```
① 先做"可观测"（第 9 章）：加密出问题时，你得先能看见
② 再做"链路加密"（本章）：一条参数，收益明确
③ 最后做"身份与授权"：成本最高、风险最大，必须单独窗口

反面做法：一上来就上完整网格（ztunnel + waypoint + 授权策略），
         任何一步失败都会让整个数据面变成"不可解释状态"。
```

---

## ⑦ 下次继续的方向（本章留下的诚实边界）

```
① 先在 spare-01 单节点起最小环境，验 istiod 或 SPIRE 能否给 ztunnel 签发身份
   判据：单节点上 ztunnel 1/1，能看到 workload 的 SPIFFE 身份
② 通过后再回主集群开窗口
③ 只有身份就绪，才谈"按身份写 L4 授权"
```

**一句话总结**：这一章把"服务之间的加密"从没有做到了 WireGuard 全互联（一条参数、风险可控），同时诚实记录了"服务身份"这条没走通的路——因为 Cilium 内置 CA 不提供签发服务，硬上要滚全部 agent，风险大于收益，于是回滚止损。记住两件事：**加密 ≠ 身份；节点 Ready ≠ 数据面正常**。
