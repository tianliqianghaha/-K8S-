# 04 · 网络与数据面解说（Cilium eBPF + 那个最坑的 SNAT）

> **这一章在整件事的哪一步**：第 2 章控制面起来了，但 10 台全 NotReady（没 CNI）→【第 3 章装网络】→ 第 4 章存储。
> **这一章在干什么**：把 10 台从 NotReady 拉到 Ready，让 Service 由 eBPF 直接接管（**没有 kube-proxy、没有 iptables 规则链**），再把"从外面能访问进来"补上。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `04_第3章_网络与数据面.md` + `s3a_cilium.py` / `s13_ingress.py` + 相关 yaml。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① CNI 是什么（先理清概念）

CNI = 容器网络接口，是 K8s 留给"第三方网络插件"的插座。K8s 自己不管 Pod 怎么拿到 IP、怎么互通，它把这件事交给 CNI 插件。本章装的插件就是 **Cilium**。没有 CNI，Pod 起不来（拿不到 IP），节点永远 NotReady。

---

## ② Cilium + kubeProxyReplacement=true（本章的主角）

**Cilium 是什么**：基于 eBPF（Linux 内核里的一种"可编程探针"）的网络插件。传统 K8s 靠 kube-proxy 写一堆 iptables 规则来转发 Service 流量，规则多了以后又慢又难查。Cilium 用 eBPF 直接在内核里做转发，更快、规则更少、还能看得更清楚（Hubble）。

**kubeProxyReplacement=true 是什么意思**：就是"我 Cilium 把 kube-proxy 的活全接了，kube-proxy 不用装了"。这是本章"先进"的核心。验收证据：`kube-proxy` DaemonSet 显示 NotFound，`iptables-save | grep KUBE-SVC` 计数为 0。

**为什么必须有它（为什么不用 kube-proxy）**：iptables 是线性匹配的规则链，服务一多，每条规则都要从头扫到尾；eBPF 是哈希表查找，规模上去后差距明显。而且 eBPF 能直接看到"哪个 Pod 调了哪个服务"，这是后面做追踪、做网格的基础。

---

## ③ Gateway API CRD + tunnel+vxlan + ipam（Cilium 的几个配套参数）

**Gateway API CRD v1.7.0**：一套比老 Ingress 更现代的"对外暴露服务"的标准接口。先把它装进集群，后面的入口网关（Envoy Gateway）才有东西可用。

**routingMode=tunnel + tunnelProtocol=vxlan**：Cilium 把 Pod 的包外面再包一层 UDP（VXLAN，走 8472 端口）来跨机器传输。
- 为什么不用 native routing：阿里云 VPC 不认识 10.244.0.0/16 这个 Pod 网段，native 模式要自己往 VPC 路由表里塞路由或者用 ENI 直通，前者要特殊权限、后者限制实例规格。VXLAN 不碰 VPC 路由，跨可用区天然可用。
- 代价：每个包多 50 字节开销（MTU 边界实测 1422 通、1472 不通）。

**ipam.mode=kubernetes**：让 Cilium 直接从 K8s 分配的 podCIDR 里给 Pod 分 IP，简单可靠。

**Hubble（relay + ui）**：Cilium 的"流量显微镜"，能看清楚 Pod 之间谁在通信、谁被丢了包。排查网络问题时全靠它。

---

## ④ 本章最大的坑：Pod 出网全死（一字不差复现了 1.0）

这是整章最该记住的一条，单独讲。

**现象**：Pod 之间通（跨区也通），但 Pod→Service、Pod→节点 IP、Pod→公网全部超时。

**根因链**（像破案一样串起来）：
```
ip-masq-agent 默认的"不伪装网段"包含 172.16.0.0/12
阿里云节点网段 172.23.x 正好落在这段里
→ Cilium 认为"访问节点是内网，不需要做 SNAT（地址伪装）"
→ 包带着 Pod 的源 IP 10.244.x.x 进入了 VPC
→ VPC 只认 172.23.x，看到 10.244.x 这个源就直接丢弃，而且不回报错
```

**为什么必须懂 SNAT**：SNAT = 把包的源 IP 换成"出口设备的 IP"。Pod IP 是集群内部地址，出了集群到了云网络就得换成节点 IP，否则云网络不认。这个坑的本质是"网段重叠"——阿里云内网段和 K8s 默认的 nonMasquerade 范围撞车了。

**修法**：把"不伪装网段"缩到只剩集群自己的两段 `10.244.0.0/16` 和 `10.96.0.0/12`。

**2.0 新增的教训（比坑本身更值钱）**：配置修好后，修复前创建的 Pod **仍然不通**。因为那批 Pod 的连接状态（socket LB / conntrack）是在错误配置下建立的，不会自愈。现象极有迷惑性——服务后端看着正常、Hubble 也没有丢包，只有 1/6 的请求碰巧能通。处置：删掉重建。判据：**凡是改过 CNI/SNAT 配置，验证一律用新建 Pod，别复用旧的。**

## ⑤ 节点标签（跨 AZ 调度的前提）

**它是什么**：给节点贴的"便利贴"，比如 `topology.kubernetes.io/zone=cn-hongkong-b`、`node-pool=memory`（16G 那两台）。

**为什么必须有它**：不打 zone 标签，K8s 根本不知道哪些节点在同一个故障域，`topologySpreadConstraints`（"每个区至少一个副本"这种规则）无从下手，Pod 会全挤在一台机器上。打了标签，"跨区打散"才是一条能执行的规则。node-pool 标签则是给第 7、8 章的弹性/调度用的。

---

## ⑥ 入口：从 CRD 到能访问（域名 → TLS → 路由到后端）

前面解决的都是"集群内部通"，这一节解决"外面的人怎么访问进来"。四件套：

```
cert-manager       证书的"自动签发机"。装了内部 CA（CN=k8s20-internal-ca），
                   自动签发 *.apps.k8s.local 的通配符证书，90 天，到期前 30 天自动续期。
                   为什么必须有：没有证书就谈不上 HTTPS；手工管证书到期会忘。

Envoy Gateway      入口控制器（相当于高级版 Ingress）。负责真正接住外部的 HTTP/HTTPS 请求。
                   用 release manifest 装（不走 OCI），避免旧版 CRD 把 Gateway API 的 CRD 降级。

Gateway            声明"监听 80 和 443 两个端口，443 用 TLS 终止（证书在这解密）"。

HTTPRoute          声明"访问 demo.apps.k8s.local 的请求转到 web 这个 Service"。
                   还有一条 demo-redirect 把 80 端口的请求 301 跳转到 443。
```

**为什么要有 GatewayClass**：它是"哪个控制器该认领这个 Gateway"的标识。没有它，Gateway 一直 `Programmed=Unknown`，事件里写 Waiting for controller。装完入口控制器先确认它存在。

**三种 404 要分清**（初级人员最容易在这里绕晕）：
```
错 Host 的 404     → 网关层没有匹配的 hostname（本次验收第②条就是它）
无路由的 404       → hostname 匹配了，但没有 HTTPRoute 指向后端
后端自己回的 404   → 路由通了，是应用返回的（此时查应用，别再查网关）
```

**ReferenceGrant**：证书 Secret 和 Gateway 如果不在同一个命名空间，必须放一条"跨命名空间引用许可"，否则 listener 报"证书引用无效"，Gateway 起不来。

## ⑦ 四层连通性验收（怎么算网络真的通了）

```
① Pod→Pod 跨 AZ（wk-1 b → wk-2 d）  http_code=200  time=2.3ms
② Service ClusterIP 访问 6 次        4 次到 wk-2、2 次到 wk-3  ← 跨 AZ 轮询成立
③ Pod→apiserver 10.96.0.1:443       200
④ Pod→公网 223.5.5.5                404（能收到 404 就说明 SNAT 生效、包能出去）
入口三条                              HTTPS 200 / 错误 Host 404 / HTTP 301
```

**为什么第 ④ 条用 404 当成功**：能收到公网的 404 响应，证明请求出去又回来了。如果 SNAT 没生效，这里会是超时。

## ⑧ 这一章的坑（讲给初级人员）

```
现象：Pod 互 ping 通，但 curl 服务超时，Hubble 里看不到任何 IPv4 drop
根因：ip-masq-agent 把 VPC 网段当内网，没做 SNAT，包在 VPC 层被丢
防：装完 Cilium 第一件事就改 nonMasqueradeCIDRs，别等业务上来才查

现象：改完 masq，老 Pod 还是不通
根因：旧连接状态（socket LB / conntrack）不刷新
防：改网络配置后一律重建验证 Pod

现象：kube-proxy 装了却不该装 / Cilium agent 报找不到 kube-proxy ConfigMap
根因：--skip-phases=addon/kube-proxy 后，agent 无从推断 apiserver 地址
防：显式 --set k8sServiceHost=172.23.163.97 --set k8sServicePort=16443

现象：跨可用区节点 NotReady 或 Pod 起不来
根因：安全组没放通 UDP 8472（VXLAN）与 4240（health）
防：安全组按 172.16.0.0/12 全放通组内流量，公网只开 22

现象：Gateway 一直 Programmed=Unknown
根因：集群里没有 GatewayClass
防：装完入口控制器先确认 GatewayClass 存在，再建 Gateway

现象：按端口名取 NodePort 取到空值，验收全 0
根因：不同版本端口名不一样（https 或 https-443）
防：先看服务实际端口名再按名字取值，别照抄
```

**一句话总结**：这一章把网络从"传统 iptables 转发"换成了"eBPF 转发"，这是"先进"的第一个落地点。但真正的学费交在那个 SNAT 网段重叠的坑上——记住：**云上自建 K8S，网络不通先查源 IP 有没有被正确伪装**，而且改完配置一定用新 Pod 验证。
