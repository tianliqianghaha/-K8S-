# 05 · 存储与灾备解说（数据怎么不丢、删了怎么回来）

> **这一章在整件事的哪一步**：第 3 章网络通了（Pod 能跑）→【第 4 章让 Pod 有持久盘、并且删了能回来】→ 第 5 章可观测。
> **这一章在干什么**：两件事，别混——**Longhorn** 解决"Pod 重启后数据还在"（块存储 + 三副本）；**Velero** 解决"把整个命名空间删了能不能回来"（对象级备份到集群外）。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `05_第4章_存储与灾备.md` + `s4_storage.py` / `s5_infra.py` / `s6_velero.py` + 相关 yaml。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① open-iscsi / iscsid / nfs-common（前置，不装 Longhorn 起不来）

**是什么**：Longhorn 通过 iSCSI 协议把块存储挂给 Pod，所以每台 worker 都得先装 iSCSI 的客户端工具（open-iscsi），并让 iscsid 服务常驻。nfs-common 是给 NFS 类型存储备用的。

**为什么必须有它**：没有 iscsid，Longhorn 的卷挂不到 Pod 上，PVC 会一直 Pending。本次实测 8 台（含控制面）都装了，`iscsid=active`。

---

## ② Longhorn（本章主角：给 Pod 一块不会随 Pod 消失的盘）

**它是什么**：一套跑在 K8S 之上的分布式块存储。简单理解——它把每台机器上的数据盘凑成一个"网络硬盘池"，Pod 要存数据时，从池子里切一块（PVC）给它。哪怕这个 Pod 被删了、换到别的机器重建，数据还在那块盘上。

**为什么必须有它**：K8S 里 Pod 的本地文件系统是"临时的"——Pod 一删，里面的文件全没。数据库、日志、用户上传这类数据必须有"独立于 Pod 生命周期"的盘。Longhorn 就是干这个的。

**它解决了 1.0 的痛点**：1.0 存储余量 213G/208G 爆了，副本重建失败过一次。2.0 盘够（733G 裸容量），不再有这个问题。

---

## ③ 三副本 + 跨可用区（数据可靠性的核心）

**是什么**：Longhorn 把每一份数据自动存 3 份（defaultReplicaCount=3），放在不同机器上。本次实测一个 5Gi 的 PVC，三个副本自动落在 wk-2(d) / wk-3(b) / wk-5(c)——正好跨三个可用区。

**为什么必须三副本 + 跨区**：
```
能容忍 1 台节点坏：坏了一台，另外两份还在
跨 3 个区后还能容忍 1 个区整体故障：因为三副本不在同一个区
```
- 代价：写放大 3 倍——733G 裸容量只能当约 244G 用。
- 判据：练习环境里"能演示一次 AZ 故障"比"多 100G 容量"值钱。所以可重建的数据（Prometheus 那种）单独设 2 副本，业务数据用 3 副本。

**StorageClass**：`longhorn` 是默认存储类（Immediate 绑定 + 允许扩容），Pod 申请 PVC 时写 `storageClassName: longhorn` 就会自动动态创建卷。`longhorn-static` 是给手动指定卷用的。

---

## ④ 备份目标必须在集群外（一条铁律）

**这条最容易犯错的初级认知**：把备份存在集群里面（比如用 Longhorn 卷跑一个 MinIO），看起来也行，但——

```
集群挂了 / etcd 丢了 / Longhorn 修不好 → 备份也一起没了
等于"保险柜和房子一起烧了"
```

**本次做法**：在 infra-01（不入集群的机器）上用 docker 跑 SeaweedFS（S3 兼容对象存储，端口 9000，独立 200G 云盘），备份全放这。判据：**问一句"集群整体重建时，这个备份还在不在？"——答案必须是在。**

**SeaweedFS**：就是个开源的对象存储（类似 AWS S3），本次建了 4 个 bucket 给 Longhorn 备份、Velero、Loki、Tempo 共用。与备份共用一套对象存储，成本低。

---

## ⑤ BackupTarget CRD（Longhorn 怎么找到备份仓库）

**是什么**：一个 K8S 资源对象，告诉 Longhorn"备份仓库在哪、用什么凭据访问"。本次 URL 是 `s3://longhorn-backup@us-east-1/`。

**为什么 1.13 有个坑**：Longhorn 1.13 把备份目标从"setting（设置项）"改成了"CRD（独立资源对象）"，名字固定叫 `default`。按老版本去 patch setting 会报 NotFound。而且光填 URL 不够，凭据 Secret 里必须四个键齐全：AK / SK / **AWS_ENDPOINTS**（自建 S3 不是 AWS 域名，必须告诉它地址）/ AWS_REGION。

---

## ⑥ Velero（灾备主角：整个命名空间删了能恢复）

**它是什么**：集群级的备份恢复工具。Longhorn 管的是"一块盘的数据"，Velero 管的是"一整个命名空间的所有对象（Deployment、Service、ConfigMap……）+ 可选地连卷里的数据一起备份"。

**为什么必须有它**：Longhorn 保证单块盘不丢，但如果有人 `kubectl delete ns demo-app` 把整个业务命名空间删了，你需要一个能"把整套对象一次性拉回来"的工具——这就是 Velero。

**备份位置**：BSL（BackupStorageLocation）指向 infra-01 上的 SeaweedFS（`s3ForcePathStyle=true` 是为了兼容自建 S3 的路径风格）。

**一个隐藏坑**：Velero 默认只备份 K8S 对象，**不备份卷里的数据**。要备份卷内容必须装 `node-agent`（kopia/restic 的工作单元），并在备份时加 `--default-volumes-to-fs-backup`。本次演练⑧就卡在这——"备份显示 Completed 但恢复出来的 PVC 是空的"。

---

## ⑦ 删库恢复演练（怎么证明灾备真的有效）

```
T0  删除 ns demo-app
T1  restore r-demo-1 Completed     RTO(恢复本体) = 13 秒
T2  deploy/web 2/2 Ready           RTO(端到端)   = 14 秒
一致性  marker=k8s20（ConfigMap 原文一字不差）
```

**注意这个 13 秒和 1.0 的 78 秒不是一回事**：1.0 那次含 PVC 数据恢复（打包卷文件），这次业务无持久数据、只恢复了对象。真正带数据的恢复要按演练⑧的方式测（55 秒）。判据：**看到 PVC Bound 不代表数据回来了，必须校验文件内容/md5。**

---

## ⑧ spare-01 是干什么的（那台不入集群的机器）

它不入集群，只做两件事：
```
① etcd 快照重建演练：把生产 etcd 快照拷过去，起一个独立 etcd，
   再用 kubeadm init --external-etcd-endpoints 指过去（1.0 一直没做成的一条）
② infra-01 的身份冷备：Dex / Gitea 配置每天同步一份，infra-01 挂了还能登进来
```

**为什么必须不入集群**：一旦 join，它就是第 9 个 worker，会被调度去跑业务，"空机器演练"的前提就没了。

---

## ⑨ 判官卡：副本数怎么定

```
3 副本（本次默认）
  + 能容忍 1 台节点故障；跨 3 AZ 后还能容忍 1 个 AZ 故障
  - 写放大 3 倍，733G 裸容量只能当 244G 用
2 副本
  + 容量利用率高
  - 只容忍 1 台节点；若两个副本恰好同区，该区故障=数据不可用
判据：能演示一次 AZ 故障比多 100G 容量值钱。可重建数据用 2 副本，业务数据用 3 副本。
```

---

## ⑩ 这一章的坑（讲给初级人员）

```
现象：Longhorn 节点显示 Schedulable=false，PVC 一直 Pending
根因：/var/lib/longhorn 不是独立挂载点（数据盘没挂上，落到系统盘了）
防：装 Longhorn 前先 findmnt /var/lib/longhorn，必须看到 150G 那块盘

现象：BackupTarget 填了但 available=false
根因：1.13 走 BackupTarget CRD + credentialSecret，缺 AWS_ENDPOINTS
防：Secret 里四个键一起给：AK / SK / AWS_ENDPOINTS / AWS_REGION

现象：备份 Completed，恢复出来 PVC 是空的
根因：没装 node-agent，卷数据根本没进备份
防：要备卷必须 --use-node-agent，恢复后校验文件内容而不是只看 PVC Bound

现象：3 副本卷重建失败，报 insufficient storage
根因：卷总量 × 3 超过可用空间（1.0 时 73G 卷→219G 物理 vs 208G 可用）
防：卷总量 × 3 ≤ 可用容量的 80%
```

**一句话总结**：这一章给你两把"后悔药"——Longhorn 让单块盘的数据不随 Pod 消失，Velero 让整个命名空间删了能拉回来。但两把药都有一个前提：**备份必须放在集群外、且必须验证内容真的回来了**，否则都是自欺欺人。
