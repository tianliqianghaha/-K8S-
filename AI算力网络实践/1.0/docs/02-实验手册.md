## L0 · 探路：云网络到底允许你做什么

**目的**：在配任何东西之前，先测出 vSwitch 的脾气。这一步的结果决定后面所有方案是否成立。

```
操作（三台都先跑体检）
  sudo ./bin/hpnlab check

然后：
  c 上：sudo ./bin/hpnlab probe
  b 上：sudo ./bin/hpnlab probe          # 挂着抓包等 a 发包
  a 上：sudo ./bin/hpnlab probe          # 发包

看什么
  ├─ P1：c 上能否收到 DA=fcbb:bb00:ffff:1::1 的包
  │      └─ 能收到 = 外层可以用 ULA 编码路径（本实验台的前提）
  ├─ P2：b 上抓到的包里有没有 Routing Header
  │      └─ 有 = 云上也能跑标准 SRv6；没有 = SRH 被剥，必须走 uSID
  ├─ P3：a 上不同载荷大小的 ping 结果
  │      └─ 小包通、大包不通 = PMTU 黑洞，L3 会专门处理
  └─ P4：b 上能否看到 IOAM / Hop-by-Hop
         └─ 看不到 = 逐跳扩展头被丢，L9 只能用旁路探测替代

判定
  P1 通 + P2 无 SRH  → 按本手册继续，uSID 方案成立（最常见）
  P1 通 + P2 有 SRH  → 继续，uSID 仍然更省（40B vs 88B）
  P1 不通            → 停下来，外层只能用云分配地址，需改 UDP 覆盖层

收尾
  sudo ./bin/hpnlab probe clean
```

**耗时** 20 分钟。**这一步的结论要写进报告**，它解释了"为什么选 uSID"。

## L1 · 基线：先证明你真的在跑 IPv6

**目的**：排除"以为在测 IPv6，其实走了 IPv4"这一类最隐蔽的假象。

```
操作（三台）
  sysctl -w net.ipv6.conf.all.disable_ipv6=0
  ip -6 addr show dev eth0 scope global

  # 把一个假的 IPv4 默认路由撤掉，逼程序只用 IPv6
  ip -4 route show default

  # 看程序到底连的哪个地址族
  ss -6 -tunlp | head
  getent ahosts <对端主机名>

看什么
  ├─ 程序如果连的是域名，getent 可能优先返回 IPv4 → 你测的是 IPv4
  ├─ ping -6 通但 ping 不通 → IPv4 那边被安全组挡了，正常
  └─ 检查是否存在 IPv4 映射地址（::ffff:x.x.x.x）

典型坑
  业务程序写 bind("0.0.0.0") 而不是 "::" → 只监听 IPv4
  Java/Go 默认 dual-stack 但优先 IPv4 → 用 -Djava.net.preferIPv6Addresses=true

验收
  b 上：ss -6 -lunp | grep 9999   能看到 [::]:9999 或 [fd00:b0b0::1]:9999
```

**耗时** 15 分钟。

## L2 · 双平面跑通：这是整个实验台的心脏

**目的**：让包真的从"a 封装 → c 弹栈 → b 解封装"走一遍，并在抓包里看到 uSID 位移。

```
操作
  1) c 上：sudo ./bin/hpnlab up
  2) b 上：sudo ./bin/hpnlab up
  3) a 上：sudo ./bin/hpnlab up
  4) 三台分别验收
     a 上：sudo ./bin/hpnlab verify
     c 上：sudo ./bin/hpnlab verify
     b 上：sudo ./bin/hpnlab verify

  5) 关键的抓包验证（分两个终端）
     c 上：sudo ./bin/hpnlab verify capture      # 会等你 8 秒
     a 上：ping -6 -c 3 fd00:b0b0::1

预期现象
  ├─ a 的 verify：三层路由、策略路由、ping 全通
  ├─ c 的 capture：同时出现 fcbb:bb00:2:e000 和 fcbb:bb00:e000
  │   └─ 前者是弹栈前，后者是弹栈后 —— 这就是 uSID 在工作的直接证据
  └─ b 的 capture：抓到包，且带 Routing Header 的计数为 0

如果失败，按这个顺序查
  1) a 的 ping 通不通     → 不通就查 b 的 svc0 有没有地址
  2) c 上有没有抓到包     → 没抓到说明 a 的外层路由没指向 c
  3) b 上有没有抓到包     → 没抓到说明 c 弹栈后没找到去 b 的路
  4) 都有包但业务不通     → b 的 End.DT6 没生效，看 docs/01 第 8 节换 VRF
```

**耗时** 40 分钟。**这是最有成就感的一步**，建议抓个 pcap 存档。

## L3 · MTU 黑洞：运维最经典的一课

**目的**：复现"小包通、大包不通"，并理解为什么它每天都在生产里发生。

```
操作（a 上）
  # 先测出真实上限
  sudo ./bin/hpnlab verify overhead

  # 手工对比
  ping -6 -c 1 -M do -s 1400 fd00:b0b0::1     # 应该通
  ping -6 -c 1 -M do -s 1452 fd00:b0b0::1     # 应该失败（封装多 40B）

  # 现在把"告诉你包太大"的那个 ICMPv6 消息丢掉
  sudo ./bin/hpnlab fault inject pmtu-block
  ping -6 -c 1 -M do -s 1452 fd00:b0b0::1     # 现象：卡住很久然后超时
  sudo ./bin/hpnlab fault clear

预期现象
  ├─ 不加封锁时：大包失败但会很快返回 "Message too long"
  ├─ 加了封锁后：大包静默超时，没有任何提示 —— 这就是黑洞
  └─ 小包全程正常，所以业务"看起来没坏"，只有偶尔卡顿

现实对应
  云安全组默认只放行部分 ICMP；很多人为了"更安全"把 ICMPv6 全禁了，
  结果就是 PMTU 发现彻底失效，表现为"部分请求偶发超时"。

处置
  安全组至少要放行 ICMPv6 type 2（Packet Too Big）和 type 1（Destination Unreachable）
  实在不能放，就在端侧把 MTU 钉死：ip link set eth0 mtu 1400
```

**耗时** 20 分钟。

## L4 · 哈希极化：为什么"买了双平面还是跑满一条"

**目的**：证明"流量分配"这件事，默认是交给运气的。

注意：本实验台只有一块网卡，所以不用"看链路利用率"，而是**看 c 上收到多少包**——
平面 0 必经 c，平面 1 不经 c。c 的计数就是"有多少流量被哈希到了绕行路径"。

```
操作（a 上）
  # 建一个 ECMP 组：同一个目的，两个下一跳（c 和 b）
  ip -6 route replace fd00:ecmp::/64 \
     nexthop via $NODE_C_IPV6 dev eth0 weight 1 \
     nexthop via $NODE_B_IPV6 dev eth0 weight 1

  # 场景 1：所有流共享同一个 flow label（模拟 RoCEv2 单 QP）
  sysctl -w net.ipv6.auto_flowlabels=0
  sysctl -w net.ipv6.fib_multipath_hash_policy=0
  for i in $(seq 1 200); do ping -6 -c 1 -W 1 fd00:ecmp::1 >/dev/null; done

  # 场景 2：让内核按流生成 flow label
  sysctl -w net.ipv6.auto_flowlabels=1
  for i in $(seq 1 200); do ping -6 -c 1 -W 1 fd00:ecmp::1 >/dev/null; done

同时（c 上）
  sudo ./bin/hpnlab watch 60

预期现象
  ├─ 场景 1：c 上 rx 几乎不动 —— 全部流量被哈希到了 b（直达）
  │   └─ 这就是哈希极化：100% / 0%，另一条路径白买
  └─ 场景 2：c 上 rx 明显上升，接近一半

为什么这对 AI 网络致命
  一个 QP 就是一个五元组、一个 flow label、一条路径。
  64 路 Ring AllReduce 用单 QP 时，理论上只能跑到一半带宽 —— 这不是网络不行，
  是"一条流只能走一条路"这个事实决定的。
  解法只有两个：多 QP 打散（应用层），或端侧直接指定路径（MRC 路线）。

收尾
  ip -6 route del fd00:ecmp::/64
  sysctl -w net.ipv6.auto_flowlabels=1
```

**耗时** 30 分钟。

## L5 · 端侧指定路径：把"运气"换成"确定"

**目的**：不再让哈希决定路径，由应用逐包选路。这是 MRC 的核心动作。

```
操作
  b 上（接收端）：
    cd app && sudo python3 mrc_lite.py recv --port 9999 --count 2000 --idle 5

  a 上（发送端，逐包交替两个平面）：
    cd app && sudo python3 mrc_lite.py send --dst fd00:b0b0::1 --port 9999 \
        --count 2000 --size 64 --plane both --rate 2000

  c 上（同时观察）：
    sudo ./bin/hpnlab watch 20

预期现象
  ├─ b 的接收结果：平面 0 约 1000，平面 1 约 1000 —— 精确五五开，不是概率
  ├─ c 上的 rx 上升约一半 —— 说明平面 0 的流量真的绕了
  └─ 乱序率 > 0 且丢包率 = 0
      └─ 乱序是喷洒的必然结果。这一点非常关键：不容忍乱序的传输层用不了喷洒

对照实验（把三种发送方式放一起比）
  --plane 1    只走直达      → 乱序 0，但带宽上限=单路径
  --plane both 逐包交替      → 乱序高，带宽=两条路径之和
  不加 mark    走主表默认    → 等价于 --plane 1

结论
  确定路径的代价是乱序，收益是"两条路径真的都用上了"。
  MRC 之所以要改传输层（SACK + 乱序重组），就是为了付这个代价。
```

**耗时** 30 分钟。

## L6 · 丢包与隔离：一条路径坏了会怎样

**目的**：量化"故障域隔离"到底值多少钱。

```
操作
  1) 先打伤平面 0（只影响目的地址在 fcbb:bb00:2::/48 的包，SSH 不受影响）
     a 上：sudo ./bin/hpnlab fault inject loss 100

  2) 逐包喷洒，观察
     b 上：sudo python3 mrc_lite.py recv --count 2000 --idle 5
     a 上：sudo python3 mrc_lite.py send --dst fd00:b0b0::1 --count 2000 --plane both

预期现象
  ├─ 丢包率约 50%（一半的包走了坏掉的平面 0）
  ├─ 平面 1 的包全部到达 —— 故障被限制在一个平面内
  └─ 这正是"多平面"的价值：不是不坏，是坏了只损失一个平面的带宽

  3) 对照：只用平面 1
     a 上：sudo python3 mrc_lite.py send --dst fd00:b0b0::1 --count 2000 --plane 1
     预期：丢包 0，但吞吐只有单路径水平

  4) 对照：只用平面 0
     --plane 0 → 丢包 100%，业务完全中断

  5) 观察协议栈计数（a 上）
     sudo ./bin/hpnlab stats

真实环境对应
  真实 MRC 在检测到某个 EV 连续失败后，会把它标记为坏并从活跃集合里摘掉，
  后续包不再走它 —— 这就是"端侧绕行，不等控制面收敛"。
  我们的 mrc_lite 是手动版：用 --plane 1 模拟"EV 退役后"的状态。

收尾
  sudo ./bin/hpnlab fault clear
```

**耗时** 30 分钟。

## L7 · 故障谱：三种坏法，三种排查难度

**目的**：把运维里真实存在的三类故障都演一遍，尤其是最难查的那种。

```
场景 1：显式链路失效（最好查）
  a 上：sudo ./bin/hpnlab fault inject blackhole
  现象：路由直接指向黑洞，ping 立刻不通，traceroute 立即暴露
  排查：ip -6 route get 一眼看出

场景 2：链路抖动（生产里每分钟都在发生）
  a 上：sudo ./bin/hpnlab fault inject jitter 20 5
  现象：ping 通，但 RTT 从 0.2ms 涨到 20ms 且抖动，吞吐下降
  排查：sudo ./bin/hpnlab rtt 200 看 p99
  └─ 这一类不会告警，只会让训练变慢，最容易被当成"模型问题"

场景 3：静默故障（最难查）
  a 上：sudo ./bin/hpnlab fault inject silent
  现象：接口 up、路由在、邻居正常、ping 100% 丢
  排查路径：
    1) ip -6 neigh show         邻居表正常？
    2) ip -6 route get          路由正常？
    3) tc -s qdisc show         队列有没有在丢？
    4) tcpdump -i eth0          包发出去了吗？对端收到了吗？
  └─ 这一步是"分层排除法"的实战训练：从下往上，一层层确认

带宽被压（云上很常见）
  a 上：sudo ./bin/hpnlab fault inject policer 50mbit
  现象：小包正常、大流量被压到 50M，且延迟突增
  └─ 真实原因往往是"突发额度用完了"，不是网络故障

收尾
  sudo ./bin/hpnlab fault clear
```

**耗时** 40 分钟。

## L8 · 拥塞与尾延迟：平均值骗人

**目的**：证明训练的痛点不是平均时延，是 p99；并看 ECN 能不能压住它。

```
操作（两打一，制造 incast）
  b 上：sudo python3 mrc_lite.py recv --count 4000 --idle 6

  a 上：sudo python3 mrc_lite.py send --dst fd00:b0b0::1 --count 2000 --rate 20000 --size 64
  c 上：sudo python3 mrc_lite.py send --dst fd00:b0b0::1 --count 2000 --rate 20000 --size 64
        # 注意：c 要能发包到 b，需先在 c 上补一条默认封装路由，见下方"补路由"

  然后开 ECN 再跑一遍
  b 上：sudo ./bin/hpnlab fault ecn on
  （重复上面的两打一）
  b 上：sudo ./bin/hpnlab fault ecn off

看什么
  ├─ 接收端的 p99 包间隔 vs 中位包间隔
  │   └─ incast 时中位几乎不变，p99 会涨几倍 —— 这就是"平均值骗人"
  ├─ 开 ECN 后 p99 是否下降
  └─ 关 ECN 时的丢包率

补路由（c 要发业务流时）
  c 上：
    ip -6 route add fd00:b0b0::1/128 encap seg6 mode encap.red \
       segs fcbb:bb00:e000:: dev eth0
    ip -6 route add fcbb:bb00:e000::/48 via $NODE_B_IPV6 dev eth0

现实对应
  训练里 8 个 GPU 同时 AllReduce 到一个接收者，就是最典型的 incast。
  尾延迟决定了整个 step 的时间，因为同步训练等最慢的那一个。
```

**耗时** 40 分钟。

## L9 · 带内遥测：把"哪一跳堵了"变成可测量

**目的**：不用猜，让包自己报出每一跳的时间。前提是 L0 的 P4 通过。

```
操作（b 上准备）
  modprobe ioam6
  sysctl -w net.ipv6.conf.all.ioam6_enabled=1
  sysctl -w net.ipv6.conf.eth0.ioam6_enabled=1
  sysctl -w net.ipv6.ioam6_id=2
  ip ioam namespace add 777 data 0xdeadbeef
  ip ioam schema add 888 "node_id,ingress_if,egress_if,timestamp"
  ip ioam namespace set 777 schema 888

操作（a 上挂 IOAM 路由）
  ip -6 route replace fd00:b0b0::1/128 encap ioam6 mode inline trace prealloc \
     type 0x800000 ns 777 size 12 \
     encap seg6 mode encap.red segs fcbb:bb00:e000:: dev eth0

  # 注意：两个 encap 写在一起时，先 ioam6 后 seg6，顺序决定谁包谁

操作（b 上抓包）
  tcpdump -i eth0 -nn -v 'ip6 and dst fd00:b0b0::1' -c 5

看什么
  ├─ 抓包里的 IOAM Trace 数据：每跳的 node_id 与时间戳
  ├─ 逐跳 Δt：哪一跳突然变大，就是排队点
  └─ 和前一步的 incast 对比：排队点应该落在被压的那条路径上

如果 P4 不通过（vSwitch 丢了 HbH）
  退化为"旁路探测"：定期向每个 SID 发探测包并回环，
  因为探测包和数据包走同一条静态源路由，观测到的路径是一致的。
  这正是 Clustermapper 的思路（探测与数据同路径），比 traceroute 可靠得多。
```

**耗时** 40 分钟。做不通也不影响主线，属于加分项。
