# 第一章 · L0 地基层

## E03 · 基线建立与回归

**能力** C8　**时长** 40min

**假设**：没有基线的性能数字毫无意义；同一个实验跑两次差异应小于 5%。

**变量**：无（这是唯一的"不改任何东西"的实验）。

```
步骤
1) 三台各跑一次时延基线（各 200 包）
   for n in a b c; do ssh $n 'cd /opt/hpn-v6-lab3 && ./bin/hpnlab rtt 200'; done

2) 三台各跑一次吞吐基线（平面 1，64B / 1200B 两档）
   b: ./bin/hpnlab recv --count 4000 --idle 6
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 4000 --size 64   --plane 1 --rate 5000
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 4000 --size 1200 --plane 1 --rate 4000

3) 落盘
   ./bin/hpnlab snap
   cp /var/lib/hpnlab/obs/snap-*.txt /var/lib/hpnlab/baseline/

4) 隔 10 分钟再跑一次，比对
```

**观测**：`rtt_p50 / p99`、`app_gbps`、`msgs_per_s`、接口 `rx/tx bytes`。
**判据**：两次基线 p50 差异 < 5%，p99 差异 < 15%（p99 天生抖，放宽）。
**边界**：抢占式实例的 CPU steal 会让基线漂移；基线必须在同一实例生命周期内比。
**踩坑**：若首次基线就抖 30% 以上，先查是不是邻居在抢带宽（`ip -s link` 看 rx 是否异常）。

# 第二章 · L1 转发协议层

## E06 · flavor 对比：标准 SRH / uSID / PSP

**能力** C2　**时长** 40min

**假设**：同一条两跳路径，标准 SRH 带来 88B 额外开销，uSID 只 40B，PSP 能再省掉最后一跳的 SRH。

**变量**：只改封装方式，路径与负载不变。

```
步骤
1) 标准 SRH（两段 SID → 必然产生 SRH）
   a: ip -6 route replace fd00:b0b0::1/128 encap seg6 mode encap \
        segs fcbb:bb00:2::,fcbb:bb00:e000:: dev eth0
   a: ping -6 -c 1 -M do -s 1372 fd00:b0b0::1      # 应该失败（超 MTU）

2) uSID（一个 DA 装下全部路径 → 无 SRH）
   a: ip -6 route replace fd00:b0b0::1/128 encap seg6 mode encap.red \
        segs fcbb:bb00:2:e000:: dev eth0
   a: ping -6 -c 1 -M do -s 1400 fd00:b0b0::1      # 应该成功

3) 用二分法量出两种封装的真实开销
   a: ./bin/hpnlab verify overhead
```

**观测**：`max_payload` 差值（= 额外头字节）、抓包里有无 `Routing Header`。
**判据**：SRH 组开销 ≈ 88B，uSID 组 ≈ 40B，差值 ≈ 48B；SRH 组抓包必须看到 Routing Header。
**边界**：uSID 的 `lblen+nflen×段数 ≤ 128` 才不需要 SRH；超过就要拆成多个容器。
**踩坑**：`encap` 与 `encap.red` 只差一个后缀，前者必带 SRH。写错就测不出差值。

## E08 · NDP / RA / DAD 规模化陷阱

**能力** C2、C7　**时长** 30min

**假设**：IPv6 的地址解析成本远高于 IPv4 ARP；邻居表项耗尽或 DAD 冲突会表现为"随机丢包"。

**变量**：邻居表规模、地址冲突、RA 参数。

```
步骤
1) 看现状
   ip -6 neigh show | wc -l
   sysctl net.ipv6.neigh.default.gc_thresh1 net.ipv6.neigh.default.gc_thresh2

2) 人为灌邻居表（把对端 /64 里的一批地址标成 reachable）
   for i in $(seq 1 200); do ip -6 neigh replace \
      240b:4001:1ed:2e02::$(printf %x $i) lladdr ee:ff:ff:ff:ff:ff dev eth0 nud reachable; done
   ip -6 neigh show | wc -l

3) 制造 DAD 冲突（在 c 上配一个 a 已有的地址）
   c: ip -6 addr add <a的地址>/128 dev lo
   c: ip -6 addr show dev lo | grep -E "tentative|dadfailed"

4) 清理
   ip -6 neigh flush dev eth0
   c: ip -6 addr del <a的地址>/128 dev lo
```

**观测**：`neigh` 表项数、`tentative`/`dadfailed` 状态、`/proc/net/snmp6` 的 `Ip6InAddrErrors`。
**判据**：冲突地址必须进入 `tentative` 或 `dadfailed`；邻居表灌到 gc_thresh2 以上后能看到回收行为。
**边界**：云上 /64 里的地址由 VPC 统一分配，实际很难大规模冲突；本实验是**机制演示**。
**踩坑**：给 lo 加地址不会触发 DAD（loopback 跳过），要加在 eth0 才能看到真实行为——**但这会短暂影响业务地址，必须在 a 上做而不是 c 上**。

# 第三章 · L2 队列与拥塞层

## E09 · ECN 阈值扫描与标记率

**能力** C3　**时长** 40min

**假设**：ECN 的 min/max 阈值决定了"什么时候开始减速"；阈值设太高等于没开，设太低会过早降速。

**变量**：`red min/max`，其余不动。

```
步骤
1) 建一条可调的 RED+ECN 队列（只作用于实验流量）
   sudo ./bin/hpnlab fault ecn on
   tc qdisc show dev eth0 | grep red

2) 跑固定负载（80% 线速，持续 20s）
   b: ./bin/hpnlab recv --count 20000 --idle 8
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 20000 --size 1200 --plane 1 --rate 8000

3) 读标记率
   tc -s qdisc show dev eth0 | grep -E "marked|overlimit|dropped"

4) 三档扫描：min/max 分别设 (20000/60000) (50000/100000) (100000/200000)
   tc qdisc replace dev eth0 parent 1:3 handle 30: red \
      limit 100000 min <lo> max <hi> avpkt 1500 ecn
   （每档重复步骤 2-3）
```

**观测**：`marked`（ECN 标记数）、`overlimit`、`dropped`、接收端 `p99 包间隔`。
**判据**：阈值越低 → `marked` 越早出现、吞吐略降但 p99 更平；阈值越高 → 接近丢包才反应，p99 尖峰更大。
**边界**：UDP 流量没有 ECN-Echo 回环，只能看"标记率"，看不到"降速效果"；降速效果必须用 TCP（`iperf3`）。
**踩坑**：`tc qdisc replace dev eth0 parent 1:3` 依赖 `30-fault.sh` 建好的 prio 三分带；直接挂 root 会把自己的 SSH 打死。

## E10 · 队列深度 vs 尾延迟

**能力** C3、C8　**时长** 40min

**假设**：队列越深，吞吐越稳但尾延迟越差（bufferbloat）；AI 训练要的是"浅队列 + 快速反压"。

**变量**：`netem limit`（包数）。

```
步骤
1) 队列限到 100 包
   tc qdisc replace dev eth0 parent 1:3 handle 30: netem limit 100 delay 0ms

2) 打突发（高 pps、小包）
   b: ./bin/hpnlab recv --count 20000 --idle 6
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 20000 --size 64 --rate 20000

3) 记录 p99 与丢包
   tc -s qdisc show dev eth0 | grep -E "dropped|backlog"
   （接收端输出里有 p99 包间隔）

4) 换成 limit 10000，重复 2-3
```

**观测**：`backlog`（当前排队字节）、`dropped`、接收端 `p99 包间隔`。
**判据**：limit 100 → 丢包多但 p99 低；limit 10000 → 丢包少但 p99 高一个量级。
**边界**：veth/虚拟网卡的队列模型比物理交换机简化，绝对值不可迁移，**趋势可信**。
**踩坑**：`netem limit` 的单位是包不是字节；写 `limit 100` 就真的是 100 个包。

## E11 · incast 规模扫描

**能力** C3、C5　**时长** 40min

**假设**：incast 的伤害随"同时发送方数量"非线性增长，因为瓶颈链路队列是共享的。

**变量**：并发源数量（1 / 2 / 3）。

```
步骤
1) 单源基线
   b: ./bin/hpnlab recv --count 6000 --idle 8
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 6000 --size 64 --rate 20000

2) 双源同时打（a 与 c 各 3000）
   b: ./bin/hpnlab recv --count 6000 --idle 8
   a 与 c 同时: ./bin/hpnlab send --dst fd00:b0b0::1 --count 3000 --size 64 --rate 20000
   （注意 c 需要先补路由：ip -6 route add fd00:b0b0::1/128 encap seg6 mode encap.red \
      segs fcbb:bb00:e000:: dev eth0）

3) 三源（a、c 再加一个 netns 里的发送器，或用 a 的两个进程不同源端口）
```

**观测**：平均包间隔 vs p99 包间隔、丢包率、接收端总耗时。
**判据**：平均只涨 10-30%，p99 涨 3-10 倍——这就是"平均值骗人"的量化版。
**边界**：三台机器的 incast 规模远小于真实 8 打 1，趋势一致、倍率不同。
**踩坑**：两个发送端必须**同时**启动，差 1 秒就变成两段串行负载，测不出 incast。

## E12 · 慢排空 slow-drain

**能力** C3、C8　**时长** 30min

**假设**：链路没断但被限速（光模块劣化/带宽额度耗尽）时，表现为"吞吐缓慢下滑 + 队列堆积"，告警往往不触发。

**变量**：限速值。

```
步骤
1) 把平面 0 限到 50Mbit（只影响 SID 目的段）
   sudo ./bin/hpnlab fault inject policer 50mbit

2) 持续打流 30s，逐秒采样
   sudo ./bin/hpnlab watch 30 1     # 另开一个窗口
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 30000 --size 1200 --plane 0 --rate 4000

3) 看队列与丢包
   tc -s qdisc show dev eth0 | grep -E "dropped|backlog|requeues"
```

**观测**：`requeues`（因队列满被退回）、`backlog` 持续非零、实际吞吐 vs 目标吞吐的缺口。
**判据**：吞吐卡在限速值附近、`backlog` 长期 > 0、`requeues` 上涨 —— 三项同时出现即判定 slow-drain。
**边界**：真实 slow-drain 由光层引起，可能伴随 CRC 错误；这里只有限速，没有误码。
**踩坑**：只看吞吐会误判为"应用问题"；必须同时看队列，这是区分"发不出"和"发不快"的关键。

## E13 · 丢包敏感性曲线（RDMA）

**能力** C3、C6　**时长** 40min

**假设**：RDMA 对丢包的惩罚是阶跃式的，不是线性的；这就是为什么 AI 网络宁可用 PFC 也不用 TCP 式重传。

**变量**：丢包率（0.001% / 0.01% / 0.1% / 1%）。

```
步骤
1) 建 Soft-RoCE（两台都要）
   modprobe rdma_rxe
   rdma link add rxe0 type rxe netdev eth0
   ibv_devinfo -d rxe0 | head -5

2) 基线
   b: ib_write_bw -d rxe0 -x 0 -D 10
   a: ib_write_bw -d rxe0 -x 0 -D 10 <b的内网IPv4>

3) 逐级加丢包（作用于平面 1 的 SID 段）
   a: sudo ./bin/hpnlab fault inject loss 0.01    # netem 支持小数百分比
   （重复步骤 2，记录带宽）

4) 四档扫完画曲线
```

**观测**：`ib_write_bw` 报告的 `BW average`、重传计数（`perfquery` 或 `ibv_devinfo -v`）。
**判据**：0.01% 丢包即可让吞吐掉 50% 以上（Go-back-N 特性）；曲线是**陡降**不是缓降。
**边界**：rxe 是软件实现，重传行为与硬件 RoCE 不完全一致，但"对丢包极度敏感"这一结论成立。
**踩坑**：`-x` 的 GID index 必须用 IPv4 那一行（`show_gids` 查），填错会连不上且报错含糊。

# 第四章 · L3 负载均衡层

## E16 · 大象流与老鼠流混合

**能力** C4、C5　**时长** 30min

**假设**：大流会把队列长期占满，小流被挤在后面；这解释了为什么 AllReduce 的大块传输会拖慢控制消息。

**变量**：是否同时存在大流。

```
步骤
1) 只有小流（基线）
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 5000 --size 64 --rate 5000 --plane 1
   （记录 p99 包间隔）

2) 小流 + 一条大流（不同源端口，模拟两个 QP）
   a 终端 1: ./bin/hpnlab send --dst fd00:b0b0::1 --count 5000 --size 64 --rate 5000
   a 终端 2: ./bin/hpnlab send --dst fd00:b0b0::1 --count 2000 --size 1200 --rate 3000

3) 用 collsim 复现同一现象（更接近真实集合通信）
   a: python3 app/collsim.py run --pattern a2a --rank 0 --peers ... --size 64 --count 200
```

**观测**：小流的 p99 包间隔在大流存在时的变化倍数。
**判据**：小流 p99 涨 2 倍以上，而平均几乎不变。
**边界**：真实网络里大流会被 DLB/AR 打散，本实验是"没有 DLB 时的上界"。
**踩坑**：两个发送进程如果绑同一个源端口会合并成一条流，必须让内核自动分配源端口。

## E17 · rail 局部性（多轨拓扑）

**能力** C1、C4　**时长** 60min

**假设**：rail-optimized 拓扑里，同 rail 通信只过一跳，跨 rail 要绕行，时延与带宽都有明显差异。

**变量**：走同平面（模拟同 rail）vs 跨平面（模拟跨 rail）。

```
步骤
1) 同 rail：平面 1（a→b 直达，1 跳）
   a: ping -6 -c 200 -i 0.02 fd00:b0b0::1     # 主表默认走平面 1

2) 跨 rail：平面 0（a→c→b，2 跳）
   a: python3 app/mrc_lite.py send --dst fd00:b0b0::1 --plane 0 --count 2000 --size 64
   （同时用 ./bin/hpnlab rtt 量这条路径的时延，需要临时把主表指向平面 0）

3) 对比带宽上限
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 4000 --size 1200 --plane 1 --rate 0
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 4000 --size 1200 --plane 0 --rate 0
```

**观测**：两条路径的 p50/p99 时延差、吞吐差、跳数（用抓包点的 TTL 验证）。
**判据**：多一跳带来 0.1–0.5ms 时延差；若跨 rail 流量占比高，整体 step time 会被拖长。
**边界**：这是**逻辑双平面**，不是物理 rail；真实 rail 的差异来自交换机端口与光纤长度。
**踩坑**：a 的主表默认走平面 1，测平面 0 必须显式用 mark，否则你以为在测跨 rail，其实还在同 rail。

## E18 · 多平面故障域隔离

**能力** C1、C7　**时长** 40min

**假设**：打挂一个平面，另一个平面的业务完全不受影响，损失仅为该平面的带宽。

**变量**：注入故障的平面。

```
步骤
1) 双平面并发打流（各 3000 包）
   b: ./bin/hpnlab recv --count 6000 --idle 8
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 3000 --plane 0 &
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 3000 --plane 1 &

2) 中途只打挂平面 0
   a: sudo ./bin/hpnlab fault inject loss 100

3) 观察接收端
   预期：平面 0 的包全丢，平面 1 的包全到，总丢包 ≈ 50%

4) 恢复
   a: sudo ./bin/hpnlab fault clear
```

**观测**：接收端 `平面 0 / 平面 1` 的计数、总丢包率、p99。
**判据**：平面 1 计数完整、p99 不劣化；总丢包率恰好等于平面 0 的占比。
**边界**：两条平面共享同一块 eth0 出口，所以"带宽不受影响"只能证明到"另一条路径仍可用"，不能证明"聚合带宽不变"。
**踩坑**：`loss 100` 作用于目的地址 `fcbb:bb00:2::/48`（平面 0 的外层 DA）；如果写成平面 1 的 DA，会把好路径打挂。

# 第五章 · L4 业务流量层

> 本章是整套实验里最接近"AI 集群"的部分。没有 GPU，但流量形状可以完全复刻。

## E19 · Ring AllReduce 的流量形状

**能力** C5、C6　**时长** 30min

**假设**：Ring 的消息数是 `2(N-1)`，与数据量无关；完成时间正比于 `2(N-1) × (size/带宽 + RTT)`。

**变量**：`--size`（消息大小）、`--count`（轮数）。

```
⚠ 三个 rank 必须同时在跑。两种可靠办法：
  ├─ 三个 ssh 窗口手工起（最直观）
  └─ 后台拉起（推荐，脚本可复用）：
     setsid nohup python3 app/collsim.py run --pattern ring --rank $r        --peers <a>,<b>,<c> --port 11110 --size 60000 --count 12 > /tmp/coll_$r.json 2>&1 &
     屏障会每 2 秒重发 RDY 并在 60 秒内自动重试，所以下发命令之间差几秒没关系

步骤
1) 三台各跑一个 rank（顺序无所谓，屏障会自动对齐）
   b: python3 app/collsim.py run --pattern ring --rank 1 --peers <a>,<b>,<c> --port 9100 --size 60000 --count 8
   c: python3 app/collsim.py run --pattern ring --rank 2 --peers <a>,<b>,<c> --port 9100 --size 60000 --count 8
   a: python3 app/collsim.py run --pattern ring --rank 0 --peers <a>,<b>,<c> --port 9100 --size 60000 --count 8

2) 换小消息再跑一次（size 1024）—— 此时瓶颈从带宽变成 RTT
3) 换中大消息（size 1400 / 60000 各一次，观察 chunks_per_msg 的影响）
```

**观测**：每台的 `sent`（应等于 `2(N-1)×count`）、`elapsed_s`、`rtt_p99_ms`、`app_gbps`。
**判据**：
```
sent 必须三台一致 = 2×(3-1)×8 = 32
elapsed 随 size 近似线性增长；小消息时 RTT 占主导（elapsed 不随 size 明显变化）
```
**边界**：这是 Ring 的**通信阶段**，不含计算；真实 NCCL 会按拓扑自动选 Ring/Tree，且用多个 channel 并行。
**踩坑**：
```
├─ 三台的 --peers 顺序必须完全一致，否则 rank 与地址错位，表现为"收不到但也没报错"
├─ --size 超过 60000 会被自动截断：UDP 单包上限 65507，再大必然触发 IPv6 分片，
│  而云上分片基本必丢。工具内部已按 --mtu（默认 1400）切片，chunks_per_msg 就是切片数
└─ 千万别用脚本串行下发三个 rank：屏障会互相等待，必然超时。必须三个终端同时起
```

**实测记录（2026-11-25，香港 3 台竞价实例，size=60000 / 43 片每消息）**：
```
ring  count=12   三 rank 全部 4/4（2(N-1)=4 轮），各 172 包
                 elapsed 3.1–3.5 ms，包间隔 p50 0.004 ms，p99 0.42–0.56 ms
tree  count=12   a 2/2（86 包），b 1/1，c 1/1（各 43 包）
                 elapsed 0.9–1.6 ms，p99 0.08–0.47 ms
pipe  count=30   单向链 a→b→c：a 发 1290 包（16.5 ms），b 中转 1290/1290（25.9 ms），
                 c 收齐 30 条（26.1 ms 端到端）
```

**同样这三形态，把消息从 1.4 KB 换到 60 KB，结论会翻转**（见 E20 的大小扫描）：
小包测的是 RTT 与调度，大包测的才是带宽。

## E20 · AlltoAll 小包风暴（MoE）

**能力** C5、C6　**时长** 30min

**假设**：AlltoAll 的消息数是 `N(N-1)×count`，且全是小包；对 RTT 和队列深度极敏感，对单流带宽不敏感。

**变量**：`--count`（每个对端发几条）。

```
步骤
1) 三台各跑一个 rank
   b/c/a: python3 app/collsim.py run --pattern a2a --rank <0|1|2> \
          --peers <a>,<b>,<c> --port 9200 --size 256 --count 200

2) 与 E19 对比：把 size 都换算成"总字节数"相近，再看 elapsed
   Ring: 32 × 60000 ≈ 1.9MB
   A2A : 6×200 × 256 = 307KB（更少字节，但消息数 1200 条 vs 32 条）
```

**观测**：`msgs_per_s`（应远高于 Ring）、`rtt_p99_ms`、`elapsed_s`。
**判据**：
```
同样的总字节数，A2A 的 elapsed 明显更长 —— 因为瓶颈是"包数×RTT"而不是"字节数/带宽"
这一条就是 MoE 网络难做的根本原因
```
**边界**：真实 AlltoAll 由 NCCL 用多个 channel 并发，实际 pps 更高；本实验给的是数量级。
**踩坑**：小包时应用层 `app_gbps` 会低得离谱，不要据此判断"网络差"——要看 `msgs_per_s`。

**实测：消息大小扫描（2026-11-25，a2a，count=200）**

```
  消息大小    分片数    应用层吞吐    消息速率      间隔 p50   间隔 p99
  256 B         1        70.9 Mbps    6328 /s       0.152 ms   0.522 ms
  1 400 B       1        80.1 Mbps    7153 /s       0.122 ms   0.421 ms
  8 000 B       6       301.9 Mbps    4492 /s       0.005 ms   0.373 ms
  30 000 B     22       575.2 Mbps    2334 /s       0.005 ms   0.629 ms
  60 000 B     43       681.9 Mbps    1416 /s       0.003 ms   0.898 ms
```

读法（这三条就是 MoE 网络设计的全部依据）：

```
① ≤1.4 KB：吞吐 70–80 Mbps 但消息速率最高 7153/s
   → 瓶颈是每消息一次往返，不是带宽 → 延迟敏感
   → 所以 AlltoAll 怕 RTT，怕队头阻塞，怕小包被大流挤
② ≥30 KB：吞吐爬到 680 Mbps 趋平，消息速率掉到 1416/s
   → 瓶颈变成链路带宽 → 带宽敏感
   → 所以 DDP 的 Ring 大消息怕负载不均、怕一条链路被打满
③ p99/p50 从 2.6 倍涨到 300 倍：包越多队尾越难看
   → 训练看尾延迟的量化依据
```

## E21 · 流水并行 PP 的点对点

**能力** C5　**时长** 25min

**假设**：PP 的流量最小但最怕 RTT；固定链路串行传，任何一次抖动都会直接进入 step time。

**变量**：是否给链路加 20ms 抖动。

```
步骤
1) 基线
   b/c/a: python3 app/collsim.py run --pattern pipe --rank <0|1|2> \
          --peers <a>,<b>,<c> --port 9300 --size 1048576 --count 20

2) 给平面 1 加抖动
   a: sudo ./bin/hpnlab fault inject jitter 20 5

3) 重复步骤 1，对比 elapsed
```

**观测**：`elapsed_s`、`rtt_p99_ms`。
**判据**：加 20ms 抖动后，PP 的 elapsed 增加 ≈ count × 20ms（串行累加），而 AllReduce 只增加一轮。
**边界**：真实 PP 有 micro-batch 流水重叠，不会完全串行累加。
**踩坑**：`pipe` 模式下 rank0 只发不收、rank2 只收不发，看到 `recv=0` 是正常的。

## E22 · 推理 KV cache 长连接

**能力** C5　**时长** 30min

**假设**：推理场景是"大量长连接 + 周期性小突发"，与训练的长时大流完全不同；连接数才是瓶颈。

**变量**：并发连接数。

```
步骤
1) 单连接长流（60s）
   b: ./bin/hpnlab recv --count 60000 --idle 15
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 60000 --size 64 --rate 1000

2) 100 条并发小流（用 shell 起 100 个短进程）
   for i in $(seq 1 100); do
     ./bin/hpnlab send --dst fd00:b0b0::1 --count 200 --size 256 --rate 300 &
   done; wait

3) 看连接/队列开销
   ss -s; tc -s qdisc show dev eth0 | grep backlog
```

**观测**：`ss -s` 的 socket 总数、p99 包间隔、`backlog`。
**判据**：并发连接数上升后 p99 明显变差，但总吞吐不涨——瓶颈在队列调度与中断，不在带宽。
**边界**：没有真实推理负载，只有流量形状。
**踩坑**：起太多进程会把测试机 CPU 打满，用 `--rate` 压住；否则你测的是本地调度不是网络。

## E23 · 多任务混跑与 straggler

**能力** C5、C8　**时长** 40min

**假设**：同步训练等最慢的那个；一台机器慢 5ms，整个 step 就慢 5ms，与集群规模无关。

**变量**：是否给其中一个节点加时延。

```
步骤
1) 三台跑 Ring，记录 elapsed（基线）
2) 给 c 加 5ms 单向时延
   c: sudo ./bin/hpnlab fault inject jitter 5 0
3) 重复步骤 1
4) 恢复
```

**观测**：三台各自的 `elapsed_s`（应该几乎相同——同步语义）、整体 step time。
**判据**：elapsed 增加 ≈ 5ms × 轮数，且三台同时变慢；这就是 straggler 的放大效应。
**边界**：真实 straggler 常来自 GPU 降频/PCIe 降速，网络只是其中一种。
**踩坑**：只加一侧时延会变成"单向慢"，环形拓扑里影响会被放大 N 倍，注意区分。

# 第六章 · L5 故障韧性层

## E25 · 灰故障（部分丢包 + 降速）

**能力** C7　**时长** 30min

**假设**：最难的故障不是"断"，而是"降"——链路还在、能 ping 通、但性能悄悄掉一半。

**变量**：丢包率 0.1% / 1% / 5%，外加限速。

```
步骤
1) 打 0.5% 丢包 + 限速 200Mbit（不切断）
   a: sudo ./bin/hpnlab fault inject loss 0.5
   a: sudo ./bin/hpnlab fault inject policer 200mbit    # 后一条会覆盖前一条，二选一

2) 用业务视角判断"有没有坏"
   a: ping -6 -c 20 fd00:b0b0::1          # 通
   a: ./bin/hpnlab rtt 200                # p99 明显变差
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 4000 --size 1200 --plane 1

3) 对照：完全断开
   a: sudo ./bin/hpnlab fault inject blackhole
```

**观测**：ping 成功率（灰故障下 > 95%）、吞吐相对基线的百分比、p99 放大倍数。
**判据**：灰故障下 ping 基本正常但吞吐掉 30% 以上——**只靠 ping 巡检发现不了**，必须有吞吐基线（E03）。
**边界**：真实灰故障可能只在特定五元组上出现，本实验是全量。
**踩坑**：`loss` 和 `policer` 都挂在同一个 band 上，后设的会替换前一个；要叠加必须分 band。

## E26 · 恢复时间量化：静态源路由 vs 动态路由

**能力** C1、C7　**时长** 50min

**假设**：BGP 默认 hold timer 90s，链路断了要等几十秒才收敛；端侧静态源路由 + EV 退役只需毫秒级。

**变量**：故障检测机制（BGP vs 端侧）。

```
步骤
1) 装 bird2（a 与 b 都要）
   apt update && apt install -y bird2

2) 配一个最小 BGP 会话（a 与 b 直连 IPv6）
   /etc/bird/bird.conf:
     protocol bgp peer_b {
       local as 65001;
       neighbor <b的IPv6> as 65002;
       ipv6 { import all; export all; };
       hold time 90;          # 默认值，故意不改
     }
   systemctl restart bird2; birdc show protocols

3) 量"断链到感知"的时间
   ip -6 route add 2001:db8:dead::/64 via <b> dev eth0   # 让 b 宣告这个前缀
   （在 b 上配 static route 并 export）
   然后 a 上：ip link set eth0 down  → 观察 birdc 里会话状态变化耗时

4) 对照：静态源路由
   a: ip -6 route replace fcbb:bb00:2::/48 blackhole      # 模拟路径消失
   a: 用 mrc_lite 检测丢包并切平面，记录切换耗时
```

**观测**：`birdc show protocols` 从 `Established` 到 `Active` 的时间；静态组从"首次丢包"到"改走另一平面"的时间。
**判据**：BGP 组以**秒**计（默认 hold 90s 更久），静态组以**毫秒**计，差 2-3 个数量级。
**边界**：真实生产会用 BFD 把检测压到 50ms 级，但仍远慢于端侧。
**踩坑**：bird2 需要 `router id`，纯 IPv6 环境也必须给一个 IPv4 格式的 router id，否则起不来。

## E27 · 配置漂移与回滚

**能力** C9、C11　**时长** 40min

**假设**：手工改过的机器必然漂移；能不能在 5 分钟内回到已知良好状态，是交付能力的核心。

**变量**：是否被手工改坏。

```
步骤
1) 建立"好状态"快照
   ./bin/hpnlab up && ./bin/hpnlab verify
   ip -6 route show > /var/lib/hpnlab/good-routes.txt
   ip -6 rule show > /var/lib/hpnlab/good-rules.txt
   tc qdisc show > /var/lib/hpnlab/good-qdisc.txt

2) 制造漂移（三条典型：多加一条路由、多一条规则、多一个 qdisc）
   ip -6 route add 2001:db8:bad::/64 via <b> dev eth0
   ip -6 rule add fwmark 0x9 table 999
   tc qdisc add dev eth0 parent 1:1 handle 40: netem delay 100ms

3) 用 diff 发现漂移
   diff <(ip -6 route show) /var/lib/hpnlab/good-routes.txt

4) 回滚
   ./bin/hpnlab down && ./bin/hpnlab up && ./bin/hpnlab verify
```

**观测**：diff 输出的差异行数、回滚后 verify 是否全绿、回滚耗时。
**判据**：能从 diff 直接看出"多了什么"；回滚后 verify 全绿且 diff 为空。
**边界**：本实验是"重建式回滚"，不是"增量回滚"；生产里大集群更常用声明式配置（Ansible/NetBox 源真）。
**踩坑**：`down` 不清 `tc qdisc`，回滚前要 `./bin/hpnlab fault clear`，否则延迟会一直挂着。

# 第七章 · L6 可观测层

## E28 · 逐流统计（eBPF）

**能力** C8　**时长** 50min

**假设**：接口计数器只能告诉你"总量"，看不出"哪条流在吃带宽"；逐流视角要靠 eBPF。

**变量**：有无逐流统计。

```
步骤
1) 装工具
   apt install -y bpfcc-tools linux-headers-$(uname -r)

2) 逐流字节数（按五元组聚合 10 秒）
   tcplife-bpfcc -D 10        # TCP 视角
   # UDP 没有现成工具，用 bpftrace 写 4 行：
   bpftrace -e 'kprobe:udp_sendmsg { @[comm] = count(); } interval:s:5 { print(@); clear(@); }'

3) 与接口计数器对账
   ip -s link show eth0
```

**观测**：每进程/每五元组的包数与字节数，是否与接口增量吻合。
**判据**：eBPF 聚合总量与 `rx_bytes` 增量差 < 5%（差额来自 ARP/NDP/ICMP 等控制流量）。
**边界**：云主机内核可能限制 kprobe；容器内需要 privileged。
**踩坑**：bpftrace 的 `kprobe:udp_sendmsg` 在高版本内核可能被内联，改用 `tracepoint:net:net_dev_queue` 更稳。

## E29 · 排队点定位（逐跳）

**能力** C8　**时长** 40min

**假设**：端到端时延变差时，能定位到"哪一跳在排队"，而不是只知道"慢了"。

**变量**：在哪一跳注入拥塞。

```
步骤
1) 分段测 RTT：分别打到 c 的 SID 和 b 的 SID
   a: ping -6 -c 100 -i 0.02 fcbb:bb00:ffff:1::1    # 到 c 的探测地址
   a: ping -6 -c 100 -i 0.02 fd00:b0b0::1           # 到 b 的业务地址

2) 在 c 上注入排队（限速 + 小队列）
   c: tc qdisc replace dev eth0 root handle 1: prio bands 3
   c: tc qdisc replace dev eth0 parent 1:3 handle 30: netem limit 50 delay 0ms
   c: tc filter replace dev eth0 parent 1: protocol ipv6 prio 1 \
        u32 match ip6 dst fcbb:bb00::/24 flowid 1:3

3) 重复步骤 1，看两段的 ΔRTT
```

**观测**：`RTT(到b) - RTT(到c)` 的差值变化。
**判据**：注入前差值 ≈ 0.1ms；注入后差值放大到几 ms，而"到 c"那一段不变 → 排队点就在 c 之后这一跳。
**边界**：这是 Clustermapper 思路的手工版：探测包与数据包走**同一条静态源路由**，所以观测可信；传统 traceroute 在 ECMP 下会拼出假路径。
**踩坑**：探测地址必须挂在 c 的 lo 上并能被 seg6local/VPC 路由送到，否则 ping 不通会误判成"这一跳丢了"。

## E30 · 时延分解：NIC / 内核 / 应用

**能力** C8、C7　**时长** 40min

**假设**：应用看到的 RTT 远大于 ping 的 RTT，差额来自内核收发路径与应用调度；不知道差额就无法判断优化方向。

**变量**：测量层次。

```
步骤
1) ping（内核 ICMP，最快）
   a: ping -6 -c 200 -i 0.02 fd00:b0b0::1

2) 应用层 UDP 往返（mrc_lite 记的是单调时钟）
   b: ./bin/hpnlab recv --count 2000 --idle 5
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 2000 --size 64 --rate 2000

3) 抓包看"线上时间"
   a: tcpdump -i eth0 -nn -tt 'udp port 9999' | head
   （对比相邻两包的发出时间与接收端到达时间）
```

**观测**：三层的 p50 与 p99 差值。
**判据**：通常 ping < 应用 RTT 0.05–0.3ms，差额就是内核与调度开销；若差额 > 1ms，说明 CPU 在抢。
**边界**：chrony 未对齐时，跨机抓包时间不可直接相减（见 E31）。
**踩坑**：`--rate` 太高会让应用自己成为瓶颈，测出来的是本地处理延迟。

## E31 · 时钟同步与测量误差

**能力** C8　**时长** 25min

**假设**：跨机时间戳不齐时，逐跳时延会算出负数或虚高；所有"逐跳"结论都建立在对齐之上。

**变量**：chrony 是否对齐。

```
步骤
1) 看当前偏差
   chronyc tracking
   （若未装：apt install -y chrony && systemctl enable --now chrony）

2) 三台同时抓包，比较同一包的到达时间戳
   a: tcpdump -i eth0 -nn -tt 'udp port 9999' -c 5
   b: tcpdump -i eth0 -nn -tt 'udp port 9999' -c 5

3) 人为制造偏差（只在测试机上，把某台调到 +500ms 观察现象，随后恢复）
   注意：不要让 ntpd/chrony 自动纠回去，先 systemctl stop chrony

4) 恢复 chrony
```

**观测**：`chronyc tracking` 的 `Offset`、两机抓包时间戳差。
**判据**：对齐后 Offset < 1ms；未对齐时逐跳差值会出现负数。
**边界**：云主机没有硬件时间戳，软件时间戳精度在几十微秒级，别声称"微秒级测量"。
**踩坑**：停掉 chrony 做实验后忘记恢复，后面所有时延数据都不可信——这是最容易留下的"脏状态"。

# 第八章 · L7 多租户与安全层

## E32 · VRF 切片与路由泄漏

**能力** C10　**时长** 50min

**假设**：同一张物理网上可以切出互不可见的租户平面；但一条错误的 `ip route` 就能让两个租户互通（路由泄漏）。

**变量**：是否把接口放进 VRF。

```
步骤
1) 在 b 上建两个租户
   ip link add vrf-t1 type vrf table 1001; ip link set vrf-t1 up
   ip link add vrf-t2 type vrf table 1002; ip link set vrf-t2 up
   ip link add svc1 type dummy; ip link set svc1 master vrf-t1; ip link set svc1 up
   ip link add svc2 type dummy; ip link set svc2 master vrf-t2; ip link set svc2 up
   ip -6 addr add fd00:1111::1/128 dev svc1
   ip -6 addr add fd00:2222::1/128 dev svc2

2) 验证隔离
   b: ip -6 route get fd00:1111::1 vrf vrf-t1    # 有结果
   b: ip -6 route get fd00:1111::1 vrf vrf-t2    # 应该无结果

3) 制造路由泄漏（把租户地址加到主表）
   b: ip -6 route add fd00:1111::1/128 dev svc1
   b: ip -6 route get fd00:1111::1                # 主表能看到了 → 泄漏

4) 清理
   b: ip -6 route del fd00:1111::1/128; ip link del svc1; ip link del svc2
   b: ip link del vrf-t1; ip link del vrf-t2
```

**观测**：`ip -6 route get ... vrf X` 的结果、`ip -6 route show table 1001/1002`。
**判据**：隔离时跨租户查不到路由；泄漏后主表可见。回滚后必须完全消失。
**边界**：VRF 只隔离路由表，不隔离带宽；带宽隔离要靠 QoS（E09/60-qos.sh）。
**踩坑**：`End.DT6 vrftable` 要求 `net.vrf.strict_mode=1`，否则装不上；这条在 docs/01 第 8 节也有。

## E33 · ACL / 安全组分区验证

**能力** C10　**时长** 30min

**假设**：网络分区必须能被验证，而不是"配了就当做了"。

**变量**：ACL 放行/拒绝。

```
步骤
1) 现状：平面 0 通、平面 1 通
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 100 --plane 0
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 100 --plane 1

2) 在 c 上用 ip6tables 只挡平面 0 的外层 DA
   c: ip6tables -I INPUT -d fcbb:bb00:2::/48 -j DROP

3) 复测：平面 0 应全丢，平面 1 不受影响

4) 清理
   c: ip6tables -D INPUT -d fcbb:bb00:2::/48 -j DROP
```

**观测**：两条平面的到达率。
**判据**：ACL 生效后仅目标平面受影响，另一平面 100% 到达。
**边界**：云安全组与主机 iptables 是两层，安全组只对进出的公网/内网流量生效，对同机 loopback 不生效。
**踩坑**：`ip6tables` 与 `nft` 混用时规则可能不在同一张表，用 `ip6tables-save` 确认。

## E34 · 管理面与数据面隔离

**能力** C10　**时长** 30min

**假设**：管理通道（SSH/带外）与业务数据面必须分离，否则一次网络实验就能把机器搞失联。

**变量**：数据面故障时的管理可达性。

```
步骤
1) 记录管理通道
   ss -tnp | grep :22

2) 在数据面注入全丢（只作用于 uSID 段，不影响管理）
   ./bin/hpnlab fault inject loss 100
   ssh 仍然可用（验证这一点）

3) 反例：直接打挂 root qdisc
   tc qdisc add dev eth0 root netem loss 100%
   → SSH 立刻断（这就是为什么 30-fault.sh 要用 prio+u32）

4) 用控制台/云助手恢复
```

**观测**：故障期间 SSH 是否可用、恢复耗时。
**判据**：正确做法（分 band）下管理通道 100% 可用；错误做法下失联。
**边界**：真正的带外管理需要独立网口/BMC，云上只有控制台可用。
**踩坑**：这条实验会让你短暂失联，务必先确认能用云助手（`scripts/remote.py`）执行命令再动手。

## E35 · UEC / MRC 传输：SACK 选择性重传

**能力** C12、C3　**时长** 90 min　**脚本** `app/mrctp.py`

**假设**：在有损网络上，"只补洞"（SACK + 立即 NACK）比"整窗回退"（Go-back-N）
代价低得多；并且多路径喷洒只有配上选择性重传才有收益。这是 MRC/UEC 敢关掉 PFC 的前提。

**变量**：重传策略（gbn / sack）、是否开立即 NACK、路径数（1 / 2）、丢包率。

``` 
步骤
1) 先给两条平面分配两个目的端口（这是"每 QP 一条平面"的等价物）
   平面 0 = 9600（经 c 绕行），平面 1 = 9601（a→b 直达）

2) b 起接收端（同时监听 9600 与 9601，后台跑并落盘）
   setsid nohup python3 -u app/mrctp.py run --role recv --peer <a>      --port 9600 --msg-mb 1 --timeout 90 > /tmp/r.json 2>&1 &

3) a 起发送端，六种配置各跑一次
   python3 app/mrctp.py run --role send --peer <b> --port 9600 --port1 9601      --msg-mb 1 --msgs 20 --paths <1|2> --retx <sack|gbn> --nack <on|off> --timeout 90

4) 只有打伤某一条平面时，才用 lossport（不要用 loss，那个匹配的是 uSID 段）
   ./bin/30-fault.sh inject lossport 2 9601        # 只打伤平面 1
   ...
   ./bin/30-fault.sh clear

5) 读接收端
   cat /tmp/r.json
``` 

**观测**：`msgs_done`、`elapsed_s`、`goodput_mbps`、`retx_pkts`、`retx_ratio_pct`、
`spurious_retx`、`sacks_recv`、`dup`、`nack_sent`。

**实测（2026-11-25，1 MB × 20 条）**

``` 
                                   完成    用时      吞吐       重传包(比例)   伪重传
① 单路径 / SACK / 无丢包           20/20   0.325 s   515.8 Mbps   40 (0.27%)      0
② 单路径 / SACK / 平面1 丢 2%      20/20  12.830 s    13.1 Mbps  1001 (6.27%)   935
③ 单路径 / GBN  / 平面1 丢 2%      20/20  11.627 s    14.4 Mbps  2073 (12.17%) 2032
④ 双平面 / SACK / 平面0 丢 2%      20/20   9.778 s    17.2 Mbps   455 (2.95%)   407
⑤ 双平面 / GBN  / 平面0 丢 2%      20/20  10.187 s    16.5 Mbps  3853 (20.48%) 3797
⑥ 双平面 / SACK / 平面1 丢 2%      20/20   8.298 s    20.2 Mbps   898 (5.66%)   850
``` 

**判据**

``` 
① 丢包的代价：515.8 → 13.1 Mbps，塌 25–40 倍
   → 这就是"无损网络不是优化，是能不能跑"的量化依据
② 重传策略的差异：同丢包下 GBN 重传 12.17%，SACK 6.27%，差一倍
   且 GBN 多出来的几乎全是伪重传（2032 vs 935）
   → 伪重传在真实集群里会变成额外拥塞，反过来再触发丢包
③ 喷洒的收益：⑥ 20.2 Mbps vs ② 13.1 Mbps，快 55%
   → 坏一条平面只损失一半，不是全损
④ 最反直觉的一条：⑤ 双平面 + GBN 的重传率 20.48%，比单路径 GBN 的 12.17% 还高
   → 整窗回退不看路径，把好路上的好包也重发了，等于自己堵死第二条路
   → 结论：多路径必须配选择性重传，否则不如不喷
``` 

**边界**（比结论更重要）

``` 
├─ 515 Mbps 是 Python 用户态上限，不是网络上限。
│  可比的是相对关系（25–40 倍塌陷、2 倍重传量、55% 提升），不是绝对值
├─ 本原型没有拥塞控制（无 CWND 增长、无 ECN 响应），
│  所以它只证明"重传策略"，不证明"拥塞控制"
├─ RTO 固定 300 ms。真实 RoCE 用自适应 RTO；固定 RTO 会放大伪超时，
│  这也是 ② 的 1001 次重传里有 935 次是伪重传的原因
├─ packet trimming 没真做（需网卡支持），这里用"立即 NACK"近似它的收益
└─ 单次运行，未做多轮统计；看量级，不看小数点
``` 

**踩坑（九条，全部实际踩过）**

``` 
├─ 跨机 time.monotonic() 相减 → 负 RTT；跨机只能比本地 elapsed
├─ SACK 位图锚在 min(收到的) → 永远停在 0..255；必须锚在第一个洞 + 累积 ACK
├─ 接收端收齐后先清状态 → 终态 SACK 被 `and st` 挡掉 → 发送端永远不算完成
├─ total_chunks 用单字节 → 4 MB 消息 2996 片溢出
├─ socket.timeout 是 OSError 子类 → 被兜底分支先接住，错误提示全错
├─ 发送端也绑 a.port → 同机测试两端抢同一个 UDP 端口，收包串台；应绑临时端口
├─ 每包都 setsockopt(SO_MARK) → 每个包多一次系统调用；只在切路径时改
├─ 洞定位写成 range(0, max(st)) 扫描 + 每包都发同一个洞的 NACK
│  → 发送端被自己的 NACK 打爆，重传 39%，六种配置差异 < 3%（等于没测出东西）
│  → 改成 O(1) 的 cbase 指针 + 20 ms NACK 抑制窗口后，才看到真实差异
└─ fault clear 无条件删 SID 路由 → 把正常外层路由一起删了（见 docs/03 第 16 条）
``` 

一句话总结这一段：**v1 那组"配置之间没差异"的数据不是网络没差异，是测量工具坏了。**

## E36 · APN6 应用感知（近似）

**能力** C12　**时长** 40min

**假设**：让网络知道"这个包属于哪个应用"，就能按应用给不同路径/优先级，而不是按五元组猜。

**变量**：应用标识（用 DSCP + Flow Label 近似 APN6 的 APN ID）。

```
步骤
1) 建两张表：训练流走平面 0，推理流走平面 1
   a: ip -6 rule add fwmark 0x2 table 100 priority 200
   a: ip -6 rule add fwmark 0x1 table 101 priority 201

2) 按 DSCP 打标（模拟应用自报身份）
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 1000 --dscp 46 --plane 0   # 训练
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 1000 --dscp 10 --plane 1   # 推理

3) 在 c 上按 DSCP 观测分流
   c: tcpdump -i eth0 -nn -c 200 'ip6 and net fcbb:bb00::/24' | awk '{print $0}' | head
```

**观测**：两条平面的包数、c 上看到的 DSCP 分布。
**判据**：不同 DSCP 的流稳定落在不同平面，且 c 上能按 DSCP 区分。
**边界**：真正的 APN6 是把 APN ID 编码进 IPv6 扩展头（HbH），云上扩展头未必透传；这里用 DSCP 是**近似**，要说清楚。
**踩坑**：DSCP 只 6 位，最多 64 类；超过就要靠 Flow Label 的 20 位做区分。

## E37 · 带内遥测的替代方案

**能力** C12、C8　**时长** 60min

**假设**：IOAM 不可用时（当前 iproute2 无 `ip ioam`），仍能做到"逐跳时延可测"，代价是要多机协同。

**变量**：测量方式（IOAM vs 同步抓包拼接）。

```
步骤
1) 确认 IOAM 不可用
   ip ioam help 2>&1 | head -2      # 应报错

2) 三台装 chrony 并对齐（见 E31）
   chronyc tracking | grep Offset

3) 三台同时抓包（同一条流，带时间戳）
   a/b/c: tcpdump -i eth0 -nn -tt -w /tmp/hop-$(hostname).pcap 'udp port 9999'
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 200 --size 64 --plane 0 --rate 100

4) 把三份 pcap 的同一 seq 的时间戳排出来，算逐跳 Δt
   tshark -r /tmp/hop-a.pcap -T fields -e frame.time_epoch -e udp.payload 2>/dev/null | head
```

**观测**：同一 seq 在三个抓包点的 `frame.time_epoch`，两两相减得逐跳时延。
**判据**：三段时延相加 ≈ 端到端时延（误差 < 20%）。
**边界**：软件时间戳精度几十微秒；只能测毫秒级以上的排队，测不了微秒级处理时延。
**踩坑**：抓包本身会引入延迟和丢包（尤其 `-s 0` 全包），高 pps 下要用 `-s 128` 并接受采样。

## E38 · 数字孪生与流量重放

**能力** C12、C9　**时长** 90min

**假设**：把真实拓扑在单机 netns 里复刻一份，重放同一份流量，能复现同样的性能曲线（误差可接受）。

**变量**：真实环境 vs 孪生环境。

```
步骤
1) 在单机上用 netns 搭同构拓扑（4 个 netns：h1/t0/t1/h2），veth 互联
   （完整脚本见 docs/01 第 3 节的单机版思路；这里只需要 2 跳）

2) 在真实环境抓一份流量
   a: tcpdump -i eth0 -w /tmp/real.pcap 'udp port 9999'

3) 在孪生环境重放（tcpreplay）
   apt install -y tcpreplay
   tcpreplay -i veth-h1 --pps 5000 /tmp/real.pcap

4) 对比两边的时延曲线与丢包点
```

**观测**：两边 p50/p99 的相对关系、丢包是否发生在同一量级。
**判据**：趋势一致（相对差异 < 30%），绝对值允许差一个量级。
**边界**：veth 没有真实队列与光层，孪生只能验证"机制"不能验证"容量"。
**踩坑**：tcpreplay 会改写 MAC/IP（除非 `--keep-mac`），目的地址变了就走到别的路径上，观测对象就错了。

## E39 · IPv6 单栈迁移演练

**能力** C2、C9　**时长** 60min

**假设**：关掉 IPv4 后，所有依赖它的东西会立刻暴露——这是"假 IPv6"最有效的检测手段。

**变量**：是否禁用 IPv4。

```
步骤
1) 记录当前所有 IPv4 依赖
   ss -4 -tunlp; ip -4 route; grep -r "0.0.0.0" /etc/ 2>/dev/null | head

2) 临时禁用 IPv4（先在 b 上做）
   b: sysctl -w net.ipv4.conf.all.disable_ipv4=1   # 注意：会断 SSH（走公网 IPv4）

3) 用云助手执行验证命令（不依赖 SSH）
   python3 scripts/remote.py --ids <b> --script 'ping -6 -c2 fd00:b0b0::1; ss -4 -tunl | wc -l'

4) 恢复
   b: sysctl -w net.ipv4.conf.all.disable_ipv4=0
```

**观测**：禁用后哪些服务失联、IPv6 路径是否完全可用。
**判据**：实验台全部功能（E01-E38）在纯 IPv6 下可运行；唯一例外是 SSH 管理通道。
**边界**：云上 SSH 走公网 IPv4，禁用 IPv4 等于自断管理；生产迁移必须先把管理通道切到 IPv6 或带外。
**踩坑**：`disable_ipv4` 重启不保留，但会让当前会话立即断开——**必须先用云助手确认能执行命令**。

## E40 · 数据面卸载（XDP 近似 DPU）

**能力** C12　**时长** 60min

**假设**：把统计/过滤下沉到数据面，能显著降低主机 CPU 开销——这是 DPU/IPU 的核心价值，XDP 可以近似验证方向。

**变量**：内核路径 vs XDP 路径。

```
步骤
1) 写一个最小 XDP 程序（计数 + 可选丢弃）
   cat > /tmp/xdp_count.c <<'EOF'
   #include <linux/bpf.h>
   #include <bpf/bpf_helpers.h>
   struct { __uint(type, BPF_MAP_TYPE_ARRAY); __uint(max_entries, 2);
            __type(key, __u32); __type(value, __u64); } cnt SEC(".maps");
   SEC("xdp") int x(struct xdp_md *ctx) {
     __u32 k = 0; __u64 *v = bpf_map_lookup_elem(&cnt, &k);
     if (v) __sync_fetch_and_add(v, 1);
     return XDP_PASS;
   }
   char _license[] SEC("license") = "GPL";
   EOF

2) 编译并挂载
   apt install -y clang llvm libbpf-dev
   clang -O2 -target bpf -c /tmp/xdp_count.c -o /tmp/xdp_count.o
   ip link set dev eth0 xdp obj /tmp/xdp_count.o sec xdp

3) 打流并对比 CPU
   a: ./bin/hpnlab send --dst fd00:b0b0::1 --count 20000 --size 64 --rate 20000
   b: top -b -n1 | head -12      # 看 softirq / ksoftirqd

4) 卸载
   ip link set dev eth0 xdp off
```

**观测**：`ksoftirqd` CPU 占用、pps 上限、丢包位置。
**判据**：XDP 挂载后同样 pps 下 softirq 占用下降，或同样 CPU 下 pps 上升。
**边界**：XDP 只能做转发/过滤/计数，做不了 RDMA；DPU 的价值还包含卸载协议栈与存储。
**踩坑**：云主机的虚拟网卡对 XDP 支持有限（可能只支持 `generic` 模式），`ip link` 会报 `Operation not supported`，此时改用 `xdpgeneric`。
