# HPN on IPv6 · 三节点实验台设计

> 定位：在一台**普通云服务器能做什么**的现实边界内，用 IPv6 协议族（uSID / Flow Label / IOAM6 / ECN）
> 把 AI 高性能网络（HPN）的因果链跑通。不做性能复刻，做**机制拆解**。

---

## 1. 先摆三个硬约束，再看三个设计决定

这三个约束不是猜的，是公有云上真实存在、并且会直接让"教科书方案"失效的东西。

```
约束 1：云 vSwitch 不是哑交换机
├─ 它可能解析并剥离 SRH（很多虚拟交换机不支持 SRH，遇到就丢或剥）
├─ 它可能丢弃不认识的逐跳扩展头（IOAM 首当其冲）
└─ 结论：任何"把路径塞进 SRH"的方案，在云上都可能莫名其妙不通

约束 2：只有一块网卡，且带宽/MTU 都被平台管着
├─ tc 挂在 eth0 上是全局的，做丢包实验会把自己的 SSH 打断
├─ VPC MTU 通常 1500，封一层 40B 后大包必然触发 PMTU
└─ 结论：故障注入必须能"只打实验流量"，MTU 必须当成一等公民对待

约束 3：没有 RDMA 网卡、没有 PFC、没有 400G
├─ 无损域的核心机制（PFC 反压）物理上不存在
└─ 结论：不宣称"证明了无损"，只证明"丢包的代价"和"拥塞控制的收益"
```

对应的三个设计决定：

```
决定 1：路径编码进 IPv6 目的地址（uSID），全程不用 SRH
         └─ 依据：RFC 9800 的 NEXT-C-SID，一个 128bit DA 装 6 个 16bit 段
         └─ 收益：vSwitch 想剥 SRH 也没得剥；开销从 80B 降到 40B

决定 2：故障注入用 prio + u32 过滤器，只命中 uSID 目的段
         └─ 收益：管理面 SSH 走默认 band，实验期间不会失联

决定 3：三台机器只承担"三个协议角色"，不假装是三个机房
         └─ a=headend（封装）、c=fabric（弹栈）、b=tailend（解封装）
         └─ 收益：每个角色的行为都能用 tcpdump 单独抓、单独解释
```

## 2. 为什么必须用 uSID，而不是标准 SRv6

同样是"从 a 经 c 到 b"，两种编码的差别是硬的：

```
标准 SRv6（encap + SRH）
  外层 IPv6 头            40 B
  SRH（1 个中转段）        8 + 16×1 = 24 B
  ────────────────────────────────
  合计                     64 B
  且：SRH 是扩展头，云 vSwitch 可能剥掉 → 路径信息丢失 → 包被投错

uSID（NEXT-C-SID，路径全在 DA）
  外层 IPv6 头            40 B
  SRH                      0 B   ← 一个 DA 装得下，就不需要 SRH
  ────────────────────────────────
  合计                     40 B
  且：路径在 DA 里，vSwitch 只要按 MAC 转发就不会破坏它
```

64 字节的小包（AlltoAll 的典型尺寸）下，这 24 字节不是"优化"，是生死：

```
64 B 载荷 + 64 B 头 = 128 B  →  有效载荷率 50%
64 B 载荷 + 40 B 头 = 104 B  →  有效载荷率 62%
```

这就是 RFC 9800（2025-06）存在的工程理由，也是 OpenAI/微软十万卡集群选择它的原因。

## 3. 三台机器的真实物理路径

三台在**同一 VPC、同一子网**里，形成一条直连 + 一条绕行：

```
                ┌──────────────── 平面 1（直达，1 跳） ────────────────┐
                │                                                    │
   [ node-a ] ──┴──────────────────────────────────────────────▶ [ node-b ]
    headend                                                       tailend
        │                                                             ▲
        │  平面 0（绕行，2 跳）                                        │
        └──────────────▶ [ node-c ] ──────────────────────────────────┘
                          fabric
                          （唯一做 uSID 弹栈的节点）

物理事实：
├─ a→b 直连与 a→c→b 绕行，走的是 vSwitch 里两条不同的转发路径
├─ 打挂 c 只影响平面 0，平面 1 完好  ← 这就是"多平面隔离故障域"的最小实证
├─ 两条路径共享 a 的 eth0 出口带宽    ← 这是本实验台的真实局限，必须写进结论
└─ 若给 a/b 各挂第二块 ENI，可升级为物理双平面（脚本不变，只改 via 的下一跳）
```

> 为什么不做成一堆 network namespace？
> 因为你要的是"贴近真实"。netns 里的 veth 不会丢 SRH、不会做源地址校验、不会限速——
> 那些恰好是本实验最想暴露的东西。所以这里只用真机，netns 只留给 L9 的可选扩展。

## 4. 地址与 SID 规划

```
uSID Block（32 bit）           fcbb:bb00::/32
  └─ 选 ULA 的理由：不占用公网段；外层由"同子网 via"强制 L2 送达对端 MAC，
     vSwitch 按 MAC 转发，不校验 DA 是否属于 VPC（这一点由 L0 探路实测确认）

节点段（16 bit）
  ├─ 0002   node-c 的 uN      → fcbb:bb00:2::/48
  └─ e000   node-b 的 uDT6    → fcbb:bb00:e000::/64

两条路径的外层 DA
  ├─ 平面 1：fcbb:bb00:e000::            （block + uDT，1 段）
  └─ 平面 0：fcbb:bb00:2:e000::          （block + uN + uDT，2 段）

业务地址（内层）
  └─ fd00:b0b0::1  挂在 b 的 dummy 口 svc0 上，程序绑这个地址

a 上的选路
  ├─ 主表         → 平面 1（默认，给不认 mark 的工具用）
  ├─ 表 100 + mark 0x2 → 平面 0
  └─ 表 101 + mark 0x1 → 平面 1
```

## 5. 一个包的一生（照着抓包对）

```
① a 的业务进程发包，目的 fd00:b0b0::1，socket 打了 mark 0x2
   │
   ├─ 策略路由命中表 100 → 命中封装路由
   │    encap seg6 mode encap.red segs fcbb:bb00:2:e000::
   │
② a 的内核在包外面套一层 IPv6
   │    外层 SA = a 的真实地址
   │    外层 DA = fcbb:bb00:2:e000::
   │    ← 注意：没有 SRH。整条路径就写在这一个地址里
   │
   ├─ 外层 FIB 查 fcbb:bb00:2::/48 → via node-c（同子网，直接 NDP 拿 MAC）
   │
③ node-c 收到以太帧，目的 MAC 是自己，但 IPv6 DA 不是自己
   │    转发开启 → 走转发面 → 命中 seg6local
   │    fcbb:bb00:2::/48  action End  flavors next-csid  lblen 32 nflen 16
   │
   ├─ 判断 DA.Argument ≠ 0 → 执行 NEXT-C-SID：
   │    弹掉最左边 16 bit（0002），整体左移
   │    DA 变成 fcbb:bb00:e000::
   │
   ├─ 用新 DA 再查一次 FIB → fcbb:bb00:e000::/48 via node-b
   │
④ node-b 收到 DA = fcbb:bb00:e000::
   │    命中 fcbb:bb00:e000::/64  action End.DT6 table 255
   │    → 解封装，内层包按本地地址投递
   │
⑤ b 的协议栈看到：fd00:b0b0::1 收到一个 UDP 包，源是 a 的真实地址
   │
   └─ 回包走普通 IPv6 直接回 a（单向封装，路径非对称，正常且可解释）
```

抓包时应该看到的现象（L0/L2 的验收点）：

```
在 a 的 eth0：DA = fcbb:bb00:2:e000::，next header = 41(IPv6-in-IPv6)，无 Routing Header
在 c 的 eth0：同一时刻能看到 DA=…:2:e000:: 和 DA=…:e000:: 两种，这就是"弹栈"的直接证据
在 b 的 eth0：DA = fcbb:bb00:e000::，依然无 Routing Header
```

## 6. 能证明什么 / 不能证明什么

这一节建议原样抄进你的实验报告第一页。诚实的边界比漂亮的数据值钱。

```
能证明（有抓包/计数支撑）
├─ 路径完全由端侧决定，交换机不做任何路由决策
│   └─ 证据：同一个目的地址，换一个 mark 就换一条物理路径
├─ uSID 在无 SRH 的情况下完成多跳源路由
│   └ 证据：c 上抓到 DA 从 …:2:e000:: 变成 …:e000::
├─ 封装开销 40B vs 标准 SRv6 88B，小包有效载荷率差 12 个百分点
│   └─ 证据：50-verify.sh overhead 的二分探测
├─ 默认 ECMP 会把同源宿的流全部压到一条链路
│   └─ 证据：policy=0 时逐秒采样，一条链路 100%、另一条 0%
├─ Flow Label 熵值能把流量打散
│   └─ 证据：policy=3 后两条链路接近 50/50
├─ 逐包喷洒必然带来乱序，端侧必须容忍
│   └─ 证据：mrc_lite 的乱序率 > 0 而丢包率 = 0
└─ 单条路径故障时，端侧绕行不需要控制面收敛
    └─ 证据：注入 loss 100% 后，切 plane 的恢复时间在毫秒级

不能证明（不要写进结论）
├─ PFC 的队头阻塞 —— 物理上没有 PFC
├─ 线速无损 —— veth/虚拟网卡 + 共享 eth0，绝对带宽无意义
├─ 芯片级 DLB/GLB —— 那是交换机 ASIC 行为
├─ packet trimming —— 需要网卡配合
└─ 真实 NCCL 性能 —— 没有 GPU；我们只复刻"流量形状"
```

## 7. 每个脚本动作 ↔ 真实 HPN 机制

```
a 上两条 encap 路由 + fwmark        ↔  MRC 的 EV 表（每个熵值映射一条确定路径）
c 上的 End + next-csid              ↔  uSID 交换机（静态表、不做路由决策）
静态路由 + 端侧换平面                ↔  "禁用动态路由，故障由端侧绕行"
平面上限速/丢包                      ↔  链路抖动、光模块故障、静默故障
Flow Label 参与哈希                 ↔  RFC 6438 / MRC 的 EV = UDP 源端口 + Flow Label
ECN 标记 + DCTCP                    ↔  无损网络里的拥塞信号（PFC 的替代观测面）
IOAM6 逐跳时间戳                    ↔  带内遥测，替代"猜哪一跳堵了"
mrc_lite 的逐包喷洒                  ↔  MRC 的 packet spraying（简化版）
```

## 8. 若 End.DT6 table 255 装不上（备选：VRF 模式）

某些内核/发行版对 `table 255` 的 DT6 行为处理不同。如果 `20-topology.sh up` 在 b 上报
"End.DT6 装不上"，改用标准 L3VPN 写法：

```bash
sysctl -w net.vrf.strict_mode=1
ip link add vrf-hpn type vrf table 1000
ip link set vrf-hpn up
ip link add svc0 type dummy
ip link set svc0 master vrf-hpn
ip link set svc0 up
ip -6 addr add fd00:b0b0::1/128 dev svc0
ip -6 route add fcbb:bb00:e000::/64 encap seg6local action End.DT6 vrftable 1000 dev eth0
```

代价：回包要从 VRF 里出来，需要在 VRF 表里补一条到 a 的路由，或者让业务程序用
`SO_BINDTODEVICE` 绑定。这也是真实 SRv6 L3VPN 部署里必然要处理的"VRF 泄漏"问题。
