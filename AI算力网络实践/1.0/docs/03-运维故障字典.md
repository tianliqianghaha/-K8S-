# 运维故障字典 · 14 个真实会遇到的坑

> 用法：先看「一眼判据」那条命令，30 秒内能定性，再往下看处置。
> 排序：从最底层往上，因为排障要自下而上。

---

## 一、链路与邻居层

### 1. 同子网的两台机器 ping 不通，IPv4 却好的

```
一眼判据
  ip -6 neigh show dev eth0
  └─ 状态是 INCOMPLETE / FAILED  → 邻居没解析出来

根因
  NDP（邻居发现）靠 ICMPv6 type 135/136，安全组如果只放行 TCP/UDP，
  IPv6 连第一步地址解析都过不去。IPv4 用的是 ARP（二层广播），所以不受影响。
  → 这就是"IPv4 通、IPv6 不通"最常见的原因，没有之一。

处置
  安全组入方向放行 ICMPv6（至少 type 135、136、1、2）
  临时验证：tcpdump -i eth0 -nn icmp6  看有没有 Neighbor Solicitation 发出去、有没有回

预防
  建 VPC 时就把 ICMPv6 全放行，别等出问题再查
```

### 2. 地址配上了，但显示 tentative，业务绑不上

```
一眼判据
  ip -6 addr show dev eth0 | grep -E "tentative|dadfailed"

根因
  DAD（重复地址检测）失败 —— 同一子网里已经有机器用了这个地址。
  云上常见于"从镜像克隆机器"或"手工抄了别人的地址"。

处置
  ip -6 addr del <addr>/128 dev eth0
  换一个没被占用的地址；或 sysctl -w net.ipv6.conf.eth0.accept_dad=0（不推荐，掩盖问题）
```

### 3. ping 通，但业务连不上

```
一眼判据
  ss -6 -lunp | grep <端口>      → 没有监听 或 只监听在 [::ffff:0.0.0.0]

根因
  程序 bind 了 0.0.0.0（IPv4 only）或用了 IPv4 映射地址。
  在 IPv6-only 的实验台里，这类程序完全不可见。

处置
  改 bind 到 "::" 或具体 IPv6 地址
  Java：-Djava.net.preferIPv6Addresses=true
  Go：net.Listen("tcp", "[::]:port")
```

## 二、路由与转发层

### 4. 包发出去了，但对端说没收到

```
一眼判据（在中间节点 c 上）
  ip -6 route get <外层DA>
  tcpdump -i eth0 -nn 'ip6 and net fcbb:bb00::/32'

根因（按概率排）
  ├─ 外层 FIB 没有把 ULA 段指到对端 → 包被丢在"no route"
  │   └─ 计数：Ip6OutNoRoutes 上涨
  ├─ via 的下一跳不在同子网 → 内核拒绝装路由（装的时候就会报错）
  └─ 对端没开转发 → 包到了但被丢
      └─ 计数：对端 Ip6InAddrErrors 上涨

处置
  c 上：sysctl -w net.ipv6.conf.all.forwarding=1
  a 上：ip -6 route replace fcbb:bb00:2::/48 via <c的地址> dev eth0
```

### 5. seg6local 配了，但完全不生效

```
一眼判据
  ip -6 route show fcbb:bb00:2::/48
  ├─ 显示的是普通路由（没有 encap seg6local）→ 被覆盖了
  └─ 显示 seg6local 但没 flavors next-csid     → 版本不支持

根因
  ├─ 前缀长度冲突：/48 的路由被更具体的 /64 压住
  ├─ metric 冲突：同前缀多条路由，metric 小的胜出
  └─ 内核 < 6.1 或 iproute2 太旧，flavors 被静默忽略

处置
  ip -6 route show <前缀> | grep -c seg6local     # 必须恰好 1 条
  删掉冲突路由；确认 uname -r >= 6.1；确认 ip route help 里有 flavors
```

### 6. 路由环路：traceroute 在两个地址之间来回跳

```
一眼判据
  traceroute6 -n <目的>     → 看到 A、B 两个地址反复出现
  ip -6 route get <目的>    → 指向的下一跳又指回来

根因
  静态路由成环。本实验里最常见的是：c 上把"到 b"写成了"via a"，
  而 a 上又把"到 c 的段"写成了 via c 自己。

处置
  画一张纸质的下一跳表，逐个节点确认"我到 X 走谁"，不要凭记忆配。
```

### 7. 大包不通、小包通（PMTU 黑洞）

```
一眼判据
  ping -6 -c1 -M do -s 1400 <目的>   → 通
  ping -6 -c1 -M do -s 1452 <目的>   → 卡住 / 超时（不是立刻报错）
  └─ "卡住很久" 比 "立刻报错" 更严重：说明 PTB 消息被丢了

根因
  封装加了 40 字节，路径 MTU 还是 1500 → 需要 ICMPv6 type 2 通知源端调小
  但安全组把 ICMPv6 禁了 → 源端永远不知道 → 一直重试大包

处置
  放行 ICMPv6 type 2；不能放就把 MTU 钉死：
  ip link set dev eth0 mtu 1400
  并把业务的 MSS 也压下来（TCP 用 tcpmss clamp）

预防
  封装类实验的第一天就该测这个，别等业务上线
```

## 三、队列与性能层

### 8. 做丢包实验，结果把自己 SSH 断了

```
症状
  执行 tc qdisc add dev eth0 root netem loss 100% 之后，SSH 卡死，机器失联

根因
  只有一块网卡，tc 挂在 root 上是全局生效 —— 包括管理流量。
  这是单网卡云主机做网络实验的经典事故。

处置（本实验台已内置）
  用 prio 三分带 + u32 过滤，只打实验流量：
    tc qdisc replace dev eth0 root handle 1: prio bands 3
    tc qdisc replace dev eth0 parent 1:3 handle 30: netem loss 100%
    tc filter replace dev eth0 parent 1: protocol ipv6 prio 1 \
       u32 match ip6 dst fcbb:bb00:2::/48 flowid 1:3
  → 管理流量走默认 band，实验只影响目的地址属于该段的包

救急
  已经失联的话，用云控制台的 VNC / 远程命令执行，跑：
    tc qdisc del dev eth0 root
```

### 9. 挂了 ECN 但完全没效果

```
一眼判据
  tc -s qdisc show dev eth0     → 看 red 的 marked 计数一直是 0
  sysctl net.ipv4.tcp_ecn        → 是不是 0

根因（三选一）
  ├─ tcp_ecn=0：端侧根本不协商 ECN
  ├─ qdisc 挂错层级：netem 挂在 root，red 挂在其下 → ECN 标记发生在 netem 之后，被丢了
  └─ 流量是 UDP（mrc_lite）→ 内核不会回 ECN-Echo，只有 TCP 才有闭环

处置
  sysctl -w net.ipv4.tcp_ecn=1
  用 TCP 流量测 ECN：iperf3 -6 -c <dst> -t 20
  UDP 场景只能看"标记率"，不能期待端侧降速
```

### 10. 带宽忽高忽低，怀疑网络，其实是配额

```
一眼判据
  在完全干净的链路上（不做任何 tc 注入）跑 iperf3 或 mrc_lite，
  吞吐在 20 秒后突然掉一半，然后缓慢恢复
  └─ 这是"突发额度用完"的典型锯齿

根因
  云主机内网/公网带宽有突发额度（burst credit），持续跑满会被压到基础带宽。

处置
  测性能时先确认机器规格里的"基础带宽/突发带宽"
  报告里只写相对值（开 ECN 前后、两条路径相加），不写绝对峰值
```

## 四、协议栈与观测层

### 11. 内核一升级，uSID 命令全部报错

```
一眼判据
  ip -6 route add ... flavors next-csid ...
  → RTNETLINK answers: Operation not supported

根因
  机器重启后进了旧内核（多内核共存，GRUB 默认项没改），
  或者云厂商的热补丁内核把 flavors 裁掉了。

处置
  uname -r 确认；ip route help | grep flavors 确认 iproute2
  Ubuntu: apt install linux-generic-hwe-24.04，然后确认 GRUB 默认项
```

### 12. IOAM 算出来的时延是负数

```
一眼判据
  抓包里的逐跳时间戳，后一跳比前一跳还小

根因
  各节点时钟不同步。IOAM 的时间戳是本地单调时钟，跨设备比较必须同步。

处置
  三台都装 chrony，指向同一个源：
    apt install chrony && systemctl enable --now chrony
    chronyc tracking    # 看 Offset 是否在微秒级
  跨设备比较只用"同一时钟域"的数据，或改成 RTT 差值比较
```

### 13. 抓包看不到包，但业务其实是通的

```
一眼判据
  tcpdump -i eth0 -c 10 'ip6'        → 一个都没有
  ip -s link show eth0               → rx_packets 在涨

根因
  ├─ 抓包过滤器写错了（比如 ip6 与 ipv6 不一样，后者不是合法关键字）
  ├─ 流量走了另一个网卡（多 ENI 时）
  └─ offload：大包被网卡分段，抓到的形态和你以为的不一样

处置
  tcpdump -i any -nn 'ip6' 先确认走哪块网卡
  看分段问题：ethtool -K eth0 tso off gso off gro off 后再抓
```

### 14. 报"地址已被占用"，但 ip addr 看不到

```
一眼判据
  ip -6 addr add 报 RTNETLINK answers: File exists
  ip -6 addr show | grep <地址>   → 在另一个 netns 或另一块网卡上

根因
  地址在别的 netns / 别的网卡 / VRF 里已经存在。IPv6 地址是全局唯一的资源。

处置
  ip -n <ns> -6 addr show
  ip -6 addr show | grep -w <地址>
  找到后先 del 再加，不要用 replace 掩盖
```

## 排障顺序（背下来）

```
1. 物理/邻居    ip -6 neigh show          邻居解析了吗
2. 地址         ip -6 addr show           地址在不在、是不是 tentative
3. 路由         ip -6 route get <dst>     内核认为该走哪
4. 策略         ip -6 rule show           有没有规则把包导去了别的表
5. 封装         ip -6 route show | grep seg6local   SID 在不在
6. 队列         tc -s qdisc show          有没有在丢、丢了多少
7. 抓包         tcpdump -i eth0 -nn       包到底出去了没、头长什么样
8. 计数         ./bin/hpnlab stats         是哪个计数器在涨
```

前四步能解决 80% 的问题。第五步之后才是"HPN 特有"的部分。

## 五、云平台层（公有云特有，最容易误判成"配置错了"）

### 15. 包发出去了，对端一个没收到（自定义目的地址）

```
一眼判据
  a 上：tcpdump -i eth0 -nn 'ip6 and dst <自定义DA>'   → 有包
  c 上：tcpdump -i eth0 -nn 'ip6'                      → 什么都没有
  └─ 发出去了但没到，问题在 fabric，不在你的配置

根因（两层，必须两个都解决）
  ① ENI 的 SourceDestCheck=True
     只允许"源或目的地址是本实例 IP"的报文，自定义目的地址在出网卡时被丢
     查：DescribeNetworkInterfaces 的 SourceDestCheck 字段
  ② VPC 内不是二层转发
     邻居表里对端 MAC 全是 ee:ff:ff:ff:ff:ff（虚拟路由器），
     说明所有包都发给 vSwitch 由它按 IPv6 目的地址路由。
     自定义前缀不在 VPC 网段里 → 路由器无路由 → 丢

处置
  ① ModifyNetworkInterfaceAttribute  SourceDestCheck=false
  ② CreateRouteEntry  给每个自定义前缀铺一条静态条目：
     RouteTableId=vtb-xxx
     DestinationCidrBlock=fcbb:bb00:2::/48
     NextHopType=Instance        （不能填 NetworkInterface：主网卡不支持）
     NextHopId=i-xxx
  ③ 复核：ping 通、对端 tcpdump 有包

为什么这条对 HPN 实验特别重要
  它说明"静态源路由"在云上不是免费的：
  你必须在 VPC 路由表里为每个 SID 前缀铺静态条目。
  这和 MRC 论文里"交换机装静态表、关掉动态路由"是同一个思路，
  只不过这里替你干这活的是 VPC 的虚拟路由器。
```

### 16. 清理故障注入后，某条平面从此不通了

```
症状
  fault clear 之后，平面 1 正常，平面 0 的 ping 100% 丢；
  重启、重建拓扑都不一定能好（如果重建脚本漏了那条路由）

一眼判据
  ip -6 route show fcbb:bb00:2::/48
  └─ 没有输出 = 外层路由被删了

根因
  故障注入脚本里用 blackhole 模拟"路径消失"，清理时写成了
    ip -6 route del fcbb:bb00:2::/48
  这句是无条件的：如果当时并没有 blackhole，它就把**正常的外层路由**一起删了。
  表现极具迷惑性——"故障清了，但故障还在"。

处置
  只撤自己注入的 blackhole：
    if ip -6 route show <前缀> | grep -q blackhole; then ip -6 route del <前缀>; fi
  已经删掉的，重跑 ./bin/hpnlab up 恢复

预防
  任何"清理"动作都要能证明"这个东西是我加的"再删。
  无差别删除 = 给下一次故障埋雷。
```

## 六、工具与实验环境层（写代码的人自己会踩）

### 17. 集合通信模拟：每个消息只收到第一片，然后就卡住

```
症状
  发送端报"发出 1290 包"，接收端 recv=1 后 3 秒超时返回 None，
  整体表现为"消息永远收不齐"，但 ping 和 a2a（小消息）完全正常

一眼判据
  看分片数：--size 1400 时正常，--size 60000（43 片）就卡
  └─ 只有一片时正常、多片就卡，一定是"多片里的某片不被认"

根因
  应用层按 MTU 切片时，只给第一片加了帧头（magic/pattern/seq），
  后续 42 片是纯填充字节。接收端校验 magic 失败 → 全部丢弃 → 永远凑不满。

处置
  每一片都要自带帧头，并且帧头里加 slice_idx。
  接收端只认帧头，不依赖"第一片到达顺序"。

为什么值得单独记
  "消息大小 ≠ 网络包大小"——NCCL 也是按 MTU 切。切片逻辑错，整套实验全废，
  而且它只在 size > MTU 时暴露，很容易在开发阶段被小消息掩盖过去。
```

### 18. 后台任务"没有输出"，实际上是它根本没起来

```
症状
  三台并发跑同一程序，部分节点的输出文件是空的，也没有报错

一眼判据
  ss -lun | grep <端口>
  └─ 端口还在被占：说明上一轮的进程没死
  手工在目标机 bind 同一端口：
  OSError: [Errno 98] Address already in use   ← 直接坐实

根因
  UDP 加 SO_REUSEADDR 不能让两个进程绑同一端口（那是 SO_REUSEPORT 的事）。
  上一轮进程卡在 recvfrom 里没退出，新进程 bind 失败当场退出，
  输出重定向到 /tmp/xxx.json 就是空文件 —— 看起来像"没输出"，其实"没启动"。

处置
  pkill -9 -f '[程]序名.py'      # 方括号写法避免匹配到自己的命令行
  sleep 1
  ss -lun | grep <端口>          # 确认干净再起
  或者每轮换一个端口号，最省事

预防
  任何"后台跑 + 落盘 + 事后读文件"的实验，第一步都要先清端口。
```

### 19. tc 按端口打伤：偏移算错，一个包都不丢

```
症状
  tc filter 装上了，netem 统计 dropped 0，但 tc filter show 也有 match 行

一眼判据
  发 200 个包（100 个目标端口 + 100 个其他端口），看 netem 的 dropped
  ├─ dropped 0    → 匹配错位
  ├─ dropped 100  → 正确
  └─ dropped 200  → 匹配范围太大

根因
  IPv6 头 40 B + UDP 源端口 2 B → 目的端口在偏移 42。
  偏移 40 命中的是 IPv6 头里的错误字节，所以 0 个匹配。
  （实测：40 → 丢 0；41/42/43 → 都丢 100，tc 对奇数偏移做了对齐）

顺带一个连带坑
  prio 会自动给每个 band 挂隐式子队列，此时
    tc qdisc replace dev eth0 parent 1:3 handle 30: netem ...
  会报 "Invalid qdisc name: must match existing qdisc"。
  必须先 tc qdisc del dev eth0 parent 1:3，再 add。

处置
  别背偏移，用"发 200 个包数 dropped"的方式标定一次，写进脚本注释。
```

### 20. 脚本文件里混进了 NUL 字节，Python 直接语法错误

```
症状
  SyntaxError: source code string cannot contain null bytes
  打开文件看不出任何异常（编辑器把 NUL 显示成空白）

一眼判据
  python3 -c "print(open('x.py','rb').read().count(b'\x00'))"

根因
  用脚本批量改代码时，替换串里的 \x00 被上游解释成了真正的 0 字节，
  而不是这两字符的转义序列。写入后文件里就是一个 NUL。

处置
  用字节码构造转义序列，绕开多层转义：
    esc = bytes([92, 120, 48, 48])      # 反斜杠 x 0 0
    data = data.replace(bytes([0]), esc)
```

### 21. "所有配置测出来都一样"——先怀疑测量工具，不要怀疑网络

```
症状
  六种配置（单/双路径 × GBN/SACK × 有无 NACK）跑出来的吞吐差异不到 3%，
  而且和是否丢包无关

一眼判据
  ├─ 重传率异常高（本次 39%），且伪重传占绝大多数
  └─ 换任何参数都不变 → 瓶颈在工具，不在被测对象

根因（本次的具体形态）
  接收端每个包都从 0 扫到 max(st) 找洞（O(n)），
  并且同一个洞每来一个包就发一次 NACK。
  发送端收到 NACK 就重发 → 自己把自己打爆 → 39% 全是自发重传。
  真实丢包信号被本地风暴完全淹没。

处置
  ├─ 洞定位改成 O(1)：维护 cbase 指针，只在 idx == cbase 时推进
  ├─ NACK 加抑制窗口（同洞 20ms 一次）
  ├─ 发送端只对 inflight 做 RTO 扫描，并在 ack 时从 inflight 里摘掉
  ├─ 收缓冲拉到 32 MiB（net.core.rmem_max 也要改）
  └─ 只在切换路径时 setsockopt(SO_MARK)，不要每包改

修完：吞吐 3.2 → 515 Mbps，重传 39% → 0.27%，六种配置的差异才显现

教训
  性能实验里，"测不出差异"的第一嫌疑永远是测量工具。
  先做一个已知答案的对照（无丢包 vs 100% 丢包），工具过不了这一关就别往下做。
```
