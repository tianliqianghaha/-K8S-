## 1. 转发面：uSID 在真机上的行为

### 1.1 双层封装与零 SRH

```
抓包点       b（tailend）的 eth0
命令         python3 app/mrc_lite.py send --dst fd00:b0b0::1 --plane 0
观测         两层 IP6 头：
               外层 DA = fcbb:bb00:e000::
               内层 DA = fd00:b0b0::1
             Routing Header 计数 = 0
```

结论：**整条路径编码在 128 bit DA 里，一个扩展头都没有**。云 vSwitch 想剥 SRH 也剥不到，
因为根本没有 SRH。这是选 uSID 而不是标准 SRv6 的全部理由。

### 1.2 弹栈（DA 左移）的直接证据

```
抓包点       c（fabric）的 eth0，过滤 ip6 and net fcbb:bb00::/24
同一微秒区间内、同一条流的两帧：

  11:17:27.674951  > fcbb:bb00:2:e000::    ← 进 c（block + node + 下一跳）
  11:17:27.674983  > fcbb:bb00:e000::      ← 出 c（已左移 16 bit）

相隔 32 微秒
```

这是 uSID 的灵魂，也是整个实验里最硬的一条证据：**路径不是配置出来的，是逐跳弹出来的**。

### 1.3 云平台层的前置条件（两个都必须满足）

```
① ENI 源/目的检查必须关     SourceDestCheck=false
② VPC 路由表必须有静态条目  NextHopType=Instance（主网卡不能用 NetworkInterface）
   fcbb:bb00:2::/48     → hpn3(c)
   fcbb:bb00:e000::/48  → hpn2(b)
   fcbb:bb00:ffff::/48  → hpn3(c)
```

判据：`ping fcbb:bb00:ffff:1::1` → 4/4 通，RTT 0.48 ms，且 c 上抓得到 DA 为 ULA 的包。

## 2. 集合通信流量形态（collsim）

### 2.1 三种形态都能跑通（size=60000，43 片/消息）

```
ring  count=12   三个 rank 全部 4/4（2(N-1)=4 轮），各 172 包
                 elapsed 3.1–3.5 ms，包间隔 p50 0.004 ms，p99 0.42–0.56 ms
tree  count=12   a 2/2（86 包）、b 1/1、c 1/1（各 43 包）
                 elapsed 0.9–1.6 ms，p99 0.08–0.47 ms
pipe  count=30   单向链 a → b → c
                 a 发出 1290 包（16.5 ms）
                 b 中转 1290/1290（25.9 ms）
                 c 收齐 30 条（26.1 ms，端到端）
```

pipe 的读法：**端到端时延看最后一个 rank 的 elapsed**（26.1 ms），
前面的 rank 只反映"往链路上推入"的耗时（16.5 ms），不是端到端。

### 2.2 消息大小扫描：小包 RTT 受限，大包带宽受限

```
a2a（count=200，每个节点给另外两个各发一条）

  消息大小    分片数    应用层吞吐    消息速率      间隔 p50   间隔 p99
  256 B         1        70.9 Mbps    6328 /s       0.152 ms   0.522 ms
  1 400 B       1        80.1 Mbps    7153 /s       0.122 ms   0.421 ms
  8 000 B       6       301.9 Mbps    4492 /s       0.005 ms   0.373 ms
  30 000 B     22       575.2 Mbps    2334 /s       0.005 ms   0.629 ms
  60 000 B     43       681.9 Mbps    1416 /s       0.003 ms   0.898 ms

ring（count=12）

  1 400 B       1        41.0 Mbps    3657 /s       0.206 ms   0.299 ms
  30 000 B     22       486.1 Mbps    1973 /s       0.005 ms   0.373 ms
  60 000 B     43       541.2 Mbps    1124 /s       0.005 ms   0.646 ms
```

这张表是整套体系里最值得带走的一张，它把三件事同时说清了：

```
① 小包段（≤1.4 KB）：吞吐只有 70–80 Mbps，但消息速率最高（7153/s），
   说明瓶颈不是带宽而是**每消息一次的往返与调度开销** → 延迟敏感型
   → MoE 的 AlltoAll、推理的 KV 传输都落在这个区间，所以它们怕 RTT
② 大包段（≥30 KB）：吞吐爬到 680 Mbps 后趋平，消息速率掉到 1416/s，
   说明瓶颈变成**链路带宽** → 带宽敏感型
   → DDP 的 Ring AllReduce 大消息落在这个区间，所以它怕带宽和负载不均
③ p99/p50 从 2.6 倍涨到 300 倍：包越多，队尾越难看。
   这就是"训练看尾延迟、不看平均"的直接量化
```

### 2.3 边界（必须一起读）

```
├─ 应用层切片 1400 B，不是链路 MTU；传输层看到的包数 = 分片数
│  所以"消息大小 ≠ 网络包大小"，NCCL 也是这么干的（按 MTU 切）
├─ 绝对吞吐受 Python 单线程限制（约 700 Mbps 量级封顶），
│  只可比趋势与相对关系，不可当作网络能力上限
└─ 没有 GPU，复刻的是流量形状，不是集合通信算法的正确性
```

## 3. MRC/UEC 传输原型（mrctp）

### 3.1 六组对照（1 MB × 20 条，双平面端口 9600/9601）

```
                                   完成    用时      吞吐       重传包(比例)   伪重传
① 单路径 / SACK / 无丢包           20/20   0.325 s   515.8 Mbps   40 (0.27%)      0
② 单路径 / SACK / 平面1 丢 2%      20/20  12.830 s    13.1 Mbps  1001 (6.27%)   935
③ 单路径 / GBN  / 平面1 丢 2%      20/20  11.627 s    14.4 Mbps  2073 (12.17%) 2032
④ 双平面 / SACK / 平面0 丢 2%      20/20   9.778 s    17.2 Mbps   455 (2.95%)   407
⑤ 双平面 / GBN  / 平面0 丢 2%      20/20  10.187 s    16.5 Mbps  3853 (20.48%) 3797
⑥ 双平面 / SACK / 平面1 丢 2%      20/20   8.298 s    20.2 Mbps   898 (5.66%)   850
```

### 3.2 三个结论

**第一，丢包把吞吐打掉 25–40 倍。**

```
无丢包 515.8 Mbps  →  2% 丢包 13.1 Mbps（②）
```

这就是 PFC 存在的全部理由。RoCEv2 一旦丢包，源端只能等 RTO 再整窗重传，
2% 的随机丢包足以让有效吞吐塌到 1/40。**无损网络不是"优化"，是能不能跑的问题。**

**第二，同样的丢包下，SACK 的重传量只有 Go-back-N 的一半。**

```
单路径 2% 丢包：
  SACK  重传 1001 包（6.27%），伪重传  935
  GBN   重传 2073 包（12.17%），伪重传 2032
```

GBN 多出来的那一倍全是**伪重传**：洞已经补上了，整窗回退还在重发已经到达的包。
在真实集群里，这些伪重传会变成额外的拥塞，反过来再触发更多丢包。

**第三，多路径喷洒 + SACK 是最好的组合；GBN 配多路径是最差的组合。**

```
④ 双平面 / SACK / 平面0 丢 2%   17.2 Mbps   重传  2.95%
⑤ 双平面 / GBN  / 平面0 丢 2%   16.5 Mbps   重传 20.48%   ← 最差
⑥ 双平面 / SACK / 平面1 丢 2%   20.2 Mbps   重传  5.66%   ← 最好

对比 ② 单路径 / SACK / 丢 2%    13.1 Mbps
```

⑥ 比 ② 快 55%，因为一半的包走了没受伤的那条路——**这就是喷洒的全部价值**：
不是"负载均衡好看"，是"坏一条平面只损失一半，而不是全损"。

⑤ 值得单独说：GBN 在多路径上重传率飙到 20.48%，比单路径的 12.17% 还高。
原因是整窗回退不看路径，把没受伤那条平面上的好包也重发了一遍，
等于亲手把自己的第二条路堵死。**多路径必须配选择性重传，否则不如不喷。**

### 3.3 边界（这一节比结论更重要）

```
├─ 绝对吞吐 515 Mbps 是 Python 用户态的上限，不是网络上限。
│  真正可比的是同一环境下的相对关系（25–40 倍塌陷、2 倍重传量、55% 提升）
├─ 本原型没有拥塞控制（没有 CWND 增长、没有 ECN 响应），
│  所以它只证明"重传策略"的差异，不证明"拥塞控制"的差异
├─ RTO 固定 300 ms，真实 RoCE 用自适应 RTO；
│  固定 RTO 会放大"伪超时"，这也是 ② 的重传里有 935 个伪重传的原因
├─ packet trimming 没有真做（需网卡支持），
│  这里用"立即 NACK"近似它的收益：不等超时、立刻补洞
└─ 单次运行，没有做多轮统计；结论看量级，不看小数点
```

### 3.4 版本演进（为什么要"v3"）

```
v1   3.2 Mbps，重传 39%，六种配置差异 < 3%（等于什么都没测出来）
     根因：接收端每包从 0 扫到 max(st) 找洞，且同一个洞每个包都发一次 NACK
           → 发送端被自己的 NACK 打爆，39% 全是自发重传

v2   570 Mbps，重传 0.27%
     改法：洞定位做成 O(1)（维护 cbase 指针）、NACK 加 20 ms 抑制窗口、
           发送端只对 inflight 做 RTO 扫描、分片载荷预生成、
           只在切路径时改 SO_MARK（不是每包改）

v3   加上按端口分平面（9600/9601），tc 才能真正只打伤一条平面
     这才让"喷洒 vs 单路径"的差异第一次显现（13.1 → 20.2 Mbps）
```

一句话：**v1 那组"配置之间没差异"的数据不是网络没差异，是我的测量工具坏了。**
把工具修好之后，差异才出来。这件事本身就是做性能实验最重要的一条纪律。

## 4. 故障与运维（已验证的部分）

```
uSID 拓扑验收     a 10 项 / b 4 项 / c 3 项，全绿
日常巡检          三台 80-daily.sh --brief 全部"正常，可交接"
QoS 三级          1:10 300M / 1:20 200M / 1:30 20M 建立成功
按端口打伤        tc filter u32 match u16 9701 at 42 → netem 统计 dropped 100/200
                  证明只打伤了目标端口，管理流量与其他端口不受影响
```

按端口过滤的偏移是实测出来的，不是算出来的：

```
偏移 40   丢 0 包      ← 匹配到了 IPv6 头的错误字节
偏移 41   丢 100 包
偏移 42   丢 100 包    ← 正确：IPv6 头 40B + UDP 源端口 2B
偏移 43   丢 100 包
```

只有 40 是错的，因为 tc 对奇数偏移做了对齐处理。**结论：别背偏移，发 200 个包看 dropped 数。**

QoS 那一组的边界：只验证了分类与限速生效，未做"低优先级被压时高优先级 p99 不受影响"的对照，
因为纯 Python 流量撑不出真正的队列压力。

## 5. 本环境证明不了的事（写在最前面，防止误用）

```
PFC 本身            没有交换机，产生不了真 pause 帧。
                    能证明的是"丢包的代价"（第 3.2 节），不是"PFC 的收益"。
芯片级 DLB / GLB    碰不到。本实验的等价物是端侧选路，其实比芯片 DLB 更激进（MRC 路线）。
packet trimming     需网卡支持，这里用立即 NACK 近似。
线速                400G/800G 无从谈起。所有吞吐都是相对值。
真 NCCL             没有 GPU。复刻的是流量形状与传输策略，不是集合通信算法。
IOAM6               iproute2 6.19 没带 ip ioam 子命令，L9 带内遥测跳过。
```

## 7. 一句话汇总

```
能对外讲的
├─ uSID 在真云上完成了"无 SRH 的多跳源路由"，抓包可见 32µs 内的 DA 位移
├─ 2% 随机丢包把有效吞吐打掉 25–40 倍 —— 这就是无损网络的必要性
├─ 同丢包下 SACK 的重传量只有 GBN 的一半，多路径配 GBN 会反噬（重传 20.48%）
├─ 双平面喷洒 + SACK 比单路径快 55%
├─ 小包受 RTT 限制（70.8 Mbps / 7153 msg/s），大包受带宽限制（681.9 Mbps / 1416 msg/s）
└─ 云上做源路由需要两件额外配置：关源目检查 + VPC 路由表静态条目

不能对外讲的
├─ 任何绝对带宽数字（Python 用户态 + 虚拟网卡）
├─ "PFC 能带来多少收益"（没有交换机）
└─ "NCCL 性能"（没有 GPU）
```
