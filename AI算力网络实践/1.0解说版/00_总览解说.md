# 00 · 这套东西到底是干什么的（总览解说）

> **先把原话摆在这里，让你知道我们讲的是哪一套东西**
> 「设计一个普通云服务器的实验，V6 的协议……面向未来的，**HPN High Performance Network（AI HPN）**：
> DCN 里的一个子集，专门面向 AI 训练，**无损、超低 RTT、超高带宽、低抖动优先**，
> 牺牲一部分多租户能力换极致性能。」

这十六篇解说，就是围绕这句话做出来的东西。重点不是"我搭了个拓扑"，
而是**把这四个词变成能量、能对比、能证伪的实验**。

---

## ① 一句话说清楚

**用三台普通云服务器，把 AI 训练网络的四个目标拆成四组实验，并跑出真数字。**

不需要 400G 网卡，不需要 RDMA 交换机，不需要 GPU。
需要的是三台能装内核模块、能建 network namespace 的普通云主机——
一台 2 核 4G 的抢占式实例，一小时三毛钱。

---

## ② 为什么不能"复刻"，只能"拆解"

初学者最容易犯的错，是想在云主机上模拟"无损网络"。这条路走不通，原因很实在：

```
没有交换机     → 产生不了真正的 PFC pause 帧
没有 RDMA 网卡 → 没有硬件 RoCE，只有软件 rxe，慢一个数量级
没有 GPU       → 跑不了 NCCL
共享 eth0      → 两条平面其实走同一块虚拟网卡，"线速"无从谈起
```

所以正确做法不是"复刻性能"，而是**把每个设计决定翻译成一个软件能测的代理量**：

```
HPN 的目标          翻译成什么               用什么测
无损                 丢包的代价               tc netem 丢包 + 传输重传统计
超低 RTT             时延分布而不是平均值      ping / IOAM / 逐包间隔 p50 p99
超高带宽             相对吞吐 + 链路利用率     iperf3 / 自研喷洒程序逐段计数
低抖动               尾延迟、乱序率           包间隔分位数、乱序计数
```

这四条一旦翻译完，实验就成立了——因为你不需要"像"，你需要"关掉它指标会变差"。

## ③ 这套资料的四根柱子

```
第一根  转发面：路径由端侧点名
  SRv6 的压缩形态 uSID（RFC 9800）：整条物理路径编码进 128 bit 目的地址
  好处不是"高级"，是"零扩展头"——云 vSwitch 会剥 SRH，但剥不到 DA
  能看到的证据：同一条流的两帧，32 微秒内 DA 左移了 16 bit

第二根  流量形态：小包和大包是两个物种
  小包（≤1.4KB）：吞吐上不去，但消息速率高 → 怕 RTT、怕排队、怕被大流挤
  大包（≥30KB）： 吞吐能打满，消息速率掉   → 怕带宽不均、怕一条链路被打满
  这张表决定了 MoE 和 DDP 的网络设计为什么不一样

第三根  传输策略：SACK 与喷洒值多少钱
  2% 随机丢包 → 吞吐塌 25–40 倍（这就是 PFC 存在的全部理由）
  同样丢包下，只补洞（SACK）的重传量只有整窗回退（GBN）的一半
  多路径喷洒 + SACK 比单路径快 55%；但多路径 + GBN 比单路径还差
  （整窗回退不看路径，把好路上的好包也重发了，自己堵死第二条路）

第四根  运维与故障：能不能修，比能不能搭更重要
  三类故障谱：链路 down / 抖动 / 静默丢（接口 up、路由在、包全丢）
  21 条故障字典，每条都是"症状 → 一条命令判据 → 根因 → 处置"
  班前五段巡检，输出能直接交接
```

## ④ 这套东西的目录长什么样

```
1.0/
├── 00_总览与复现路线.md      ← 一页看懂（比本篇更干）
├── 01_速查卡.md              ← 动手时翻这个
├── conf/  bin/  app/         ← 脚本和程序
├── docs/  01~07              ← 设计、手册、字典、实录、体系、进阶、SOP
├── nodes/                    ← 三台机器的清单
└── reports/                  ← 真机跑出来的全部数字
```

`bin/` 里九个脚本，每个只干一件事：

```
_env.sh          统一的配置加载（顺带修掉 Windows 换行造成的整类假故障）
00-preflight     体检：内核版本、iproute2 能力、地址、连通性
10-probe         探路：云平台到底允许你做什么 —— 最关键的一步
20-topology      建拓扑：两条封装路由 + seg6local 弹栈 + 策略路由
30-fault         故障注入：只打实验流量，不断 SSH
40-observe       观测：时延分布、逐秒采样、协议栈计数
50-verify        验收：每项都是断言，不是"看起来对"
60-qos           QoS 三级分级与带宽保障
80-daily         日常巡检：五段输出，能直接交接
```

`app/` 里三个程序，分别对应第二、三根柱子：

```
mrc_lite.py   逐包多路径原型（打 fwmark 换路径 + 序号 + 乱序统计）
collsim.py    集合通信流量形态（ring / tree / a2a / pipe 四种）
mrctp.py      MRC/UEC 传输原型（累积 ACK + SACK 位图 + 立即 NACK + 喷洒）
```

## ⑤ 这套东西最值钱的三个数字

```
515.8 Mbps  →  13.1 Mbps
  同一条路径、同样 1MB 消息，只因为加了 2% 丢包，有效吞吐塌了 40 倍。
  这就是"无损网络不是优化，是能不能跑"的量化依据。

12.17%  vs  6.27%
  同样 2% 丢包，Go-back-N 的重传量是 SACK 的两倍，多出来的几乎全是伪重传。
  伪重传在真实集群里会变成额外拥塞，反过来再触发更多丢包。

20.48%
  双平面 + GBN 的重传率，比单路径 GBN 的 12.17% 还高。
  这个数字最反直觉，也最有用：多路径必须配选择性重传，否则不如不喷。
```

## ⑥ 这套东西证明不了什么（一定要看）

```
PFC 本身          没有交换机，产生不了真 pause 帧。
                  能证明的是"丢包的代价"，不是"PFC 的收益"。
芯片级 DLB/GLB    碰不到。本实验的等价物是端侧选路（MRC 路线，更激进）。
packet trimming   需网卡支持，这里用"立即 NACK"近似。
线速              400G/800G 无从谈起，所有吞吐都是相对值。
真 NCCL           没有 GPU，复刻的是流量形状与传输策略。
```

把这一节放在最前面，是这套资料的一个原则：
**凡是证明不了的，先写出来，不要等别人来问。**
