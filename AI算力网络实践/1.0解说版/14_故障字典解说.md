# 14 · 故障字典解说（docs/03-运维故障字典.md）

> 对应文件：`docs/03-运维故障字典.md`

这份文档是整套资料里**最像"资产"的一份**：21 条真实故障，
每条都是"症状 → 一条命令判据 → 根因 → 处置"。

---

## ① 为什么是"一条命令判据"

```
常见故障文档       "检查网络配置是否正确"        ← 没法执行
这份文档           "ip -6 route show fcbb:bb00:2::/48 有没有输出"
```

判据必须满足三个条件：

```
① 一条命令   不是一套流程
② 有明确输出 空 / 非空、等于几 / 不等于几
③ 能区分原因 不同原因给出不同输出
```

第 ③ 条最难，也是最有价值的。比如"ping 不通"这一个症状，可能是因为：

```
没有地址       ip -6 addr show | grep inet6      空
没有路由       ip -6 route get <dst>             unreachable
安全组拦了     ping 通 IPv4 但不通 IPv6
邻居没解析     ip -6 neigh show <对端>           INCOMPLETE / FAILED
MTU 黑洞       小包通、大包不通                   ping -M do -s 1400
```

**同一个症状，五条命令区分五个原因。** 这才是"判据"。

## ② 六章 21 条，按层分组

```
一  邻居层      地址解析失败、NDP 不响应
二  地址层      地址没配上、配错口、重复
三  路由层      缺路由、路由指错、策略路由优先级
四  队列层      tc 残留、prio 子队列、限速不生效
五  可观测层    计数不动、抓包抓不到、时间对不上
六  云平台层    ★ 自定义 DA 不通（本资料最有价值的一条）
七  工具层      ★ 自己写的工具踩的 5 个坑
```

第六、七章是这份文档区别于"网上抄的故障表"的地方：
**它们记录的是"这套环境特有"的故障。**

## ③ 第 15 条（云平台层）：包发出去了，对端一个没收到

这一条值得单独讲，因为它是"云上做 HPN"的核心障碍。

```
一眼判据
  a 上：tcpdump -i eth0 -nn 'ip6 and dst <自定义DA>'   → 有包
  c 上：tcpdump -i eth0 -nn 'ip6'                      → 什么都没有
  └─ 发出去了但没到，问题在 fabric，不在你的配置

根因（两层，必须两个都解决）
  ① ENI 的 SourceDestCheck=true
     只允许"源或目的地址是本实例 IP"的报文，自定义目的地址在出网卡时被丢
  ② VPC 内不是二层转发
     邻居表里对端 MAC 全是 ee:ff:ff:ff:ff:ff（虚拟路由器），
     说明所有包都发给 vSwitch 由它按 IPv6 目的地址路由。
     自定义前缀不在 VPC 网段里 → 路由器无路由 → 丢

处置
  ① ModifyNetworkInterfaceAttribute  SourceDestCheck=false
  ② CreateRouteEntry 给每个自定义前缀铺静态条目
     NextHopType=Instance（不能填 NetworkInterface：主网卡不支持）
```

文档里还专门写了一段"为什么这条对 HPN 实验特别重要"：

```
它说明"静态源路由"在云上不是免费的：
你必须在 VPC 路由表里为每个 SID 前缀铺静态条目。
这和 MRC 论文里"交换机装静态表、关掉动态路由"是同一个思路，
只不过这里替你干这活的是 VPC 的虚拟路由器。
```

**把故障和理论对上，是这份字典最有价值的地方。**

## ④ 第 16 条：清理故障注入后，某条平面从此不通了

这条记录的是一次**自己给自己挖坑**的事故，也是唯一一条"因为清理动作导致"的故障。

```
症状   fault clear 之后，平面 1 正常，平面 0 的 ping 100% 丢
根因   清理写成了无条件 del：
         ip -6 route del fcbb:bb00:2::/48
       如果当时没有 blackhole，它就把**正常的外层路由**一起删了
处置   只撤自己注入的 blackhole：
         if ip -6 route show <前缀> | grep -q blackhole; then del; fi

预防   任何"清理"动作都要能证明"这个东西是我加的"再删。
       无差别删除 = 给下一次故障埋雷。
```

这条最狠的地方是它的**隐蔽性**：清理动作"成功了"（没报错），
但留下了一个更难查的故障。而且当时正在做"双平面喷洒"对比，
**平面 0 一直是断的，所有配置都只在单路径上跑，怎么调都没差别。**

## ⑤ 第七部分（工具层 5 条）：这一类最容易被忽略

```
17  每片都要带帧头     只有首片带头 → 后续分片被当垃圾丢弃
18  旧进程占着端口     bind 失败即死 → 输出空文件，看起来像"没输出"
19  tc 按端口打伤      偏移算错 → 一个包都不丢；prio 子队列 replace 报错
20  文件里混进 NUL     看起来正常，Python 直接语法错误
21  所有配置测出来一样  先怀疑测量工具，不要怀疑网络
```

第 21 条是这一整套里最重要的一条经验，值得单独记住：

```
性能实验里，"测不出差异"的第一嫌疑永远是测量工具。
先做一个已知答案的对照（无丢包 vs 100% 丢包），
工具过不了这一关，后面的数据全是废的。

本次的具体形态：接收端每包 O(n) 找洞 + 每包都发 NACK
→ 发送端被自己的 NACK 打爆 → 39% 重传全是自发
→ 六种配置的差异被淹没，一度以为"喷洒没有收益"
```

## ⑥ 怎么用这份字典

```
第一步  按"症状"找，不按"技术名词"找
        （所以章节按层分，标题都是症状）
第二步  先跑"一眼判据"，不要先想根因
第三步  判据对上了，再看根因；对不上，说明是别的条
第四步  处置之后，用验收脚本复验
```

一个习惯值得养成：**每次修完一个字典里没有的故障，就往里加一条。**
半年之后，这份字典会比任何教程都有用——因为它只记录"这个环境真实发生过的事"。
