# 07 · 集合通信流量形态解说（collsim.py）

> 对应文件：`app/collsim.py`

这个程序回答一个问题：**没有 GPU，能不能研究"AI 训练的流量长什么样"？**
答案是可以——因为网络看到的不是计算，是**流量形状**。

---

## ① 网络只关心四件事

```
① 一次迭代发多少条消息
② 每条多大
③ 谁发给谁（拓扑形状）
④ 是否需要等齐（同步点）

这四项决定网络怎么设计。计算本身，网络看不见。
```

四种并行策略在这四项上完全不同，所以复刻这四种，就复刻了 AI 训练对网络的诉求。

---

## ② 四种形状，各自的物理含义

```
ring   Ring AllReduce 的 Ring 阶段
       每轮只和左右邻居换数据，2(N-1) 轮
       流量特征：节点两两之间的长连接、大消息、严格同步
       对应：DDP 数据并行

tree   Tree AllReduce
       递归二分，log2(N) 轮，每轮扇出更大
       流量特征：跳数少、瞬时并发高，靠近根节点的链路压力大

a2a    AlltoAll（MoE 专家并行的典型）
       每个节点给其余每个节点各发一条
       流量特征：N(N-1) 条小包、对 RTT 极其敏感
       对应：MoE 的专家并行（公认最难搞）

pipe   流水线并行
       单向链 0→1→…→n-1，逐跳转发，不回 ack
       流量特征：串行，端到端时延 = 跳数 × 单跳
       对应：PP 流水线并行
```

为什么这四个够用？因为它们覆盖了"全连 / 树 / 全对全 / 链"四种极端，
真实业务都是这四种的组合。

---

## ③ 关键技术点：三层都要小心

### 3.1 起跑对齐：屏障而不是对时

``` 
问题：三台机器要同时开始发，否则测出来的时间包含"启动误差"
错误做法：约定一个绝对时间戳（本地时钟不同步，而且 time.monotonic 起点不同）
正确做法：RDY → ACK → GO 三次握手
```

具体流程：

```
rank0 给其他每个 rank 发 RDY（每 2 秒重发一次，防止落在对方还没起监听的空窗里）
每个 rank 收到 RDY 回 ACK:<自己的 rank 号>
rank0 收齐所有 ACK 后，给所有人（包括自己）发 GO
所有人收到 GO 才开始计时
```

两个细节值得说：

```
① ACK 用 rank 号而不是源地址匹配
   因为对端回包的源地址可能不是 peers 列表里的那个（隐私地址、选路问题）
   用源地址匹配会永远等不齐
② 用消息对齐，不用时钟
   这样起跑误差只剩"单向网络时延"，而且与机器时钟无关
```

### 3.2 时间怎么算才不荒谬

```
禁止：跨机 time.monotonic() 相减（起点不同，会算出负数）
允许：
  本地 elapsed          本机从 GO 到结束的时间
  本地收包间隔分位数    相邻两个包到达本机的时间差
```

所以程序输出的每个数字都标了 `note: 均为本机时钟，不可跨机相减`。

### 3.3 应用层切片：消息大小 ≠ 网络包大小

```
一条 60000 字节的消息，会被切成 43 个 1400 字节的 UDP 包发出去
chunks_per_msg 就是切片数
```

为什么必须切？两个原因：

```
① UDP 单包上限 65507 字节，超了直接 EMSGSIZE
② 就算没超，60KB 的 UDP 包会触发 IPv6 分片，而云上分片基本必丢
```

**这也解释了为什么 NCCL 也要按 MTU 切**——集合通信的"消息大小"是个逻辑概念，
网络看到的是一个个 MTU 大小的包。

### 3.4 每一片都必须带帧头（踩过的坑）

最初的做法是"只有第一片带帧头，后面都是填充"。结果：

```
现象  发送端报"发出 1290 包"，接收端 recv=1 后 3 秒超时返回 None
      → 消息永远收不齐，但 ping 和小消息（1 片）完全正常
根因  接收端校验 magic 失败，把后面 42 片全当垃圾丢了
改法  每一片都带 4 个字段：magic / pattern_id / seq / slice_idx
```

这个坑很值得记：**它只在 size > MTU 时暴露**，开发阶段用小消息测试会完全掩盖。

## ④ 跑出来的那张表（最值得记住的结果）

```
a2a（count=200，每个节点给另外两个各发一条）

  消息大小    分片数    应用层吞吐    消息速率      间隔 p50   间隔 p99
  256 B         1        70.9 Mbps    6328 /s       0.152 ms   0.522 ms
  1 400 B       1        80.1 Mbps    7153 /s       0.122 ms   0.421 ms
  8 000 B       6       301.9 Mbps    4492 /s       0.005 ms   0.373 ms
  30 000 B     22       575.2 Mbps    2334 /s       0.005 ms   0.629 ms
  60 000 B     43       681.9 Mbps    1416 /s       0.003 ms   0.898 ms
```

读法（这三条就是 MoE 网络设计的依据）：

```
① ≤1.4 KB：吞吐只有 70–80 Mbps，但消息速率最高 7153/s
   瓶颈是"每消息一次往返"，不是带宽 → 延迟敏感
   → 所以 AlltoAll 怕 RTT、怕排队、怕小包被大流挤
② ≥30 KB：吞吐爬到 680 Mbps 趋平，消息速率掉到 1416/s
   瓶颈变成链路带宽 → 带宽敏感
   → 所以 Ring 大消息怕负载不均、怕一条链路被打满
③ p99/p50 从 2.6 倍涨到 300 倍
   包越多，队尾越难看 → 这就是"训练看尾延迟"的量化依据
```

## ⑤ 三种形状的实测

```
ring  count=12   三 rank 全部 4/4（2(N-1)=4 轮），各 172 包
                 elapsed 3.1–3.5 ms，p99 0.42–0.56 ms
tree  count=12   a 2/2（86 包），b 1/1，c 1/1（各 43 包）
                 elapsed 0.9–1.6 ms，p99 0.08–0.47 ms
pipe  count=30   a→b→c 单向链
                 a 发出 1290 包（16.5 ms），b 中转 1290/1290（25.9 ms）
                 c 收齐 30 条，端到端 26.1 ms
```

pipe 的读法要特别注意：

```
端到端时延看**最后一个 rank** 的 elapsed（26.1 ms）
前面的 rank 只反映"往链路上推入"的耗时（16.5 ms），不是端到端
```

## ⑥ 怎么跑

```bash
# 三个 rank 必须同时在跑。两种可靠办法：

# ① 三个 ssh 窗口手工起（最直观）
# ② 后台拉起（推荐，脚本可复用）
for r in 0 1 2; do
  setsid nohup python3 app/collsim.py run --pattern a2a --rank $r \
    --peers <a>,<b>,<c> --port 12110 --size 60000 --count 200 > /tmp/c$r.json 2>&1 &
done

# 三个 rank 的 --peers 顺序必须完全一致，否则 rank 与地址错位
```

## ⑦ 边界

```
├─ 绝对吞吐受 Python 单线程限制（约 700 Mbps 量级封顶）
│  只可比趋势与相对关系，不可当作网络能力上限
├─ 没有 GPU，复刻的是流量形状，不是集合通信算法的正确性
├─ 没有拥塞控制与重传，丢包就丢了
└─ 单次运行，未做多轮统计
```

---

## ⑧ 一句话记住这一篇

**ring/tree/a2a/pipe 覆盖了"全连/树/全对全/链"四种极端，
屏障保证起跑对齐、每片自带帧头保证能收齐、只输出本地时钟量保证不荒谬；
它跑出的那张"大小-吞吐"表，就是 MoE 与 DDP 网络设计不同的根因。**
