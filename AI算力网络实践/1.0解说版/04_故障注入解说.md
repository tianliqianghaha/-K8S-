# 04 · 故障注入解说（30-fault.sh）

> 对应文件：`bin/30-fault.sh`

这是整套实验台里**最容易出事故的一个脚本**——因为它动的是队列，
而单网卡的云主机只有一块 eth0，你的 SSH 也走这块网卡。

---

## ① 一句话原理

**不去断网，而是把"坏的网络"精确地造在实验流量上，管理连接一点不受影响。**

```
不这么做的后果
  tc qdisc add dev eth0 root netem loss 100%
  这一条命令会把 SSH 一起打死 —— 你从此登不上这台机器，
  只能去控制台重启。这是运维现场最经典的自杀操作。
```

---

## ② 结构：prio 三分带 + u32 过滤器

```
            ┌─────────────────────────────┐
            │  root qdisc: prio (handle 1:)│
            └──────┬───────┬───────┬──────┘
                band1    band2    band3
                  │        │        │
             默认流量   空闲    handle 30: netem
             （SSH）                  ↑
                              过滤器把"实验流量"挑进 band3
```

两条过滤规则，分别对应两种打伤方式：

```
按目的地址（早期版本，针对 uSID 段）
  tc filter ... protocol ipv6 prio 1 u32 match ip6 dst fcbb:bb00:2::/48 flowid 1:3

按 UDP 目的端口（后来加的，能打单条平面）
  tc filter ... protocol ipv6 prio 2 u32 match u16 9601 0xffff at 42 flowid 1:3
```

---

## ③ 为什么后来要加"按端口"

早期只有"按目的地址"，它有一个致命局限：

```
一个实验里，两条平面都往同一个目的地址发（对端真实 IPv6），
只是路径不同（一个经 c，一个直达）。
按目的地址过滤 → 两条平面一起被打伤 → 测不出"单平面故障"
```

改成"按端口"就好了：

```
平面 0 → 目的端口 9600
平面 1 → 目的端口 9601
tc 只打伤 9601 → 精确模拟"一条平面坏了"
```

这也和真实 MRC 的做法对齐：**每个 QP 绑定一条平面**，而不是靠五元组哈希碰运气。

### 3.1 偏移 42 是标定出来的，不是算出来的

理论上：IPv6 头 40 字节，UDP 源端口在 40，目的端口在 42。但实测发现：

```
偏移 40   丢 0 包      ← 匹配到了 IPv6 头里的错误字节
偏移 41   丢 100 包
偏移 42   丢 100 包    ← 正确
偏移 43   丢 100 包
```

标定方法（每次换环境都该做一次）：

```bash
# 发 100 个到 9701 + 100 个到 9700，看 netem 的 dropped 是 0 / 100 / 200
tc -s qdisc show dev eth0 | grep -A2 'netem 30'
```

`dropped 100` 才是"只打伤了目标端口"。

**结论：别背偏移，用包数验证。**

## ④ 七种可注入的故障，对应真实世界的什么

```
loss <pct>                 平面 0 丢包            → 链路误码、拥塞溢出
lossport <pct> <port>      按端口丢包             → 只坏一条平面
jitter / jitterport        时延 + 抖动            → 光模块劣化（生产上每分钟 2–8 条）
policer <rate>             限速                   → 云带宽超额、突发额度耗尽
pmtu-block                 丢 ICMPv6 PTB          → PMTU 黑洞（最难查的一类）
blackhole                  路由层指向黑洞         → 控制面撤路
silent                     接口 up、路由在、包全丢 → 静默故障（靠监控看不出来）
hash <0|1|3>               ECMP 哈希策略          → 复现"哈希极化"
ecn <on|off>               ECN 标记 + DCTCP       → 拥塞信号 vs 丢包
clear                      清掉全部注入
```

后三种（hash / ecn / pmtu-block）不是"打坏"，而是"改条件"，
用来做对照组，比如：

```
hash 0 → 只哈希 {src,dst,flow label}，同源宿的多条流必然撞同一条链路
hash 3 → 把 flow label 纳入哈希，同一条流也能打散
```

## ⑤ 这一篇最值钱的一条：清理必须能证明"是我加的"

脚本里有一段看起来有点啰嗦的代码：

```bash
# 只撤自己注入的 blackhole，绝不能无条件 del
if ip -6 route show "$SID_PREFIX" | grep -q blackhole; then
  ip -6 route del "$SID_PREFIX"
else
  note "没有 blackhole 需要撤（正常路由保持不动）"
fi
```

原来的写法是：

```bash
ip -6 route del "$SID_PREFIX" 2>/dev/null && note "blackhole 已撤" || true
```

差在哪？**如果不删 blackhole 而直接 del，它会把正常的外层路由一起删掉。**

后果极其隐蔽：

```
现象   fault clear 之后，平面 1 正常，平面 0 的 ping 100% 丢
      重启、重建拓扑都不一定好（如果重建脚本漏了那条路由）
误判   "故障清了但故障还在" → 怀疑云平台、怀疑内核
真相   清理动作把正常路由删了
```

更糟的是，当时正在做"双平面喷洒 vs 单路径"的对比实验，
**因为平面 0 一直是断的，所有配置都只在单路径上跑，怎么调都没差别**。
一度以为"喷洒没有收益"，其实是自己把第二条路拆了。

这条经验的通用形式是：

**任何"清理"动作，都要先证明"这个东西是我加的"再删。无差别删除 = 给下一次故障埋雷。**

---

## ⑥ 还有两个坑写在脚本注释里

```
① prio 会自动给每个 band 挂隐式子队列
   tc qdisc replace dev eth0 parent 1:3 handle 30: netem ...
   会报 "Invalid qdisc name: must match existing qdisc"
   → 必须先 tc qdisc del dev eth0 parent 1:3，再 add

② fault clear 之后要确认队列真的没了
   tc qdisc show dev eth0   应该只剩默认
   否则下一次注入会叠在旧配置上，测出来的数字没有意义
```

---

## ⑦ 怎么用

```bash
# 打伤平面 0（按 uSID 目的地址）
sudo ./bin/hpnlab fault inject loss 100

# 只打伤平面 1（按 UDP 端口）
sudo ./bin/hpnlab fault inject lossport 2 9601

# 加抖动
sudo ./bin/hpnlab fault inject jitterport 20 5 9600

# 看当前状态
sudo ./bin/hpnlab fault show

# 清干净（每次实验结束都做，别留残留）
sudo ./bin/hpnlab fault clear
```

打伤之后一定要做一件事：**用 tcpdump 确认目标流量真的在丢**。
`tc -s` 的统计是唯一的客观证据，别靠"感觉变慢了"。

---

## ⑧ 一句话记住这一篇

**prio 分带保住 SSH，u32 把实验流量挑进 band3，
按端口才能打单条平面，清理只撤自己加的——这四条缺一条就会出事故。**
