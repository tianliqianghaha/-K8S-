# 05 · 观测、巡检与 QoS 解说（40-observe.sh + 80-daily.sh + 60-qos.sh）

> 对应文件：`bin/40-observe.sh`、`bin/80-daily.sh`、`bin/60-qos.sh`

三个脚本，回答三个不同层次的问题：

```
40-observe   "这条路径现在有多快、抖不抖"        面向一次实验
80-daily     "这台机器今天能不能交接"            面向每天上班
60-qos       "给流量分级到底管不管用"            面向设计决策
```

---

## ① 40-observe：为什么不报"平均时延"

四个子命令：

```
rtt [n]      发 n 个包，输出时延分布（min/avg/max/p50/p95/p99）
watch [秒]   逐秒采样 rx/tx 字节数，算出每秒吞吐
snap         一次性快照（接口计数 + 队列计数 + 路由条数）
stats        协议栈统计（IP6 各计数器）
```

关键设计：**只给分位数，不给平均值。**

```
原因：AI 训练的性能由"最慢的那一步"决定，不是由平均决定。
      AllReduce 是同步操作，一轮里任何一个包慢，整轮就慢。
      平均值 20ms 但 p99 是 200ms 的链路，训练会明显掉速，
      而看平均值你会以为一切正常。
```

实测印证：incast 场景下平均 RTT 只涨 20%，p99 涨 10 倍。

## ② 80-daily：班前五分钟，输出能直接交接

五段检查，顺序是"从下往上"排的：

```
1 主机      load / 内存 / 磁盘
2 接口      状态 / 错误计数 / dropped / MTU
3 地址邻居  全局 IPv6 / 邻居异常项 / 路由条数 / SID 前缀 / 策略路由
4 队列      根队列类型 / 累计 dropped
5 业务面    平面 1 通不通 / 平面 0 通不通
```

为什么是这个顺序？因为**排障是从下往上走的**：

```
机器资源不够 → 后面的网络现象全是假象
接口没 UP    → 谈路由没意义
地址没配上   → 谈策略路由没意义
路由不对     → 谈业务通不通没意义
```

每一行有三个状态：

```
ok     正常（绿色）
warn   可疑，但不一定是故障（黄色）
bad    确定有问题（红色）
```

退出码的设计：有 `bad` 时非 0，可以直接挂 cron：

```cron
*/10 * * * * /opt/hpn-v6-lab3/bin/80-daily.sh --brief || echo "HPN 巡检异常" | mail -s ...
```

### 2.1 两个"角色感知"的细节

```
① c 是 fabric 节点，不承载业务地址
   → 业务面检查对它跳过，否则每天都报一条假警
② 平面 0 的健康度不能靠 ping 探针地址
   → 改成"c 的 SID 路由在 且 c 可达"，因为探针地址不一定长期挂着
```

这两条是"巡检能不能长期用"的关键：**一个每天误报的巡检，三天后没人看。**

### 2.2 一个刚修的误报

```
现象  重建拓扑后立刻巡检，c 报"没有 fcbb:bb00 前缀路由"
真相  路由还在内核里同步，巡检太快了
改法  连续检查三次、每次间隔 0.5 秒，任一次命中即算通过
```

这类"时序性误报"在巡检脚本里非常常见，处理原则是：
**宁可多等 1.5 秒，也不要每天报一次假警。**

## ③ 60-qos：三级 HTB 与 DSCP 映射

```
       root htb (handle 1:, default 20)
        ├── 1:10   满速       prio 1   ← DSCP 46 (EF)   训练 RDMA
        ├── 1:20   2/3 速率   prio 2   ← 未标记         业务一般流量
        └── 1:30   1/15 速率  prio 3   ← DSCP 10 (AF11) 存储/备份
```

DSCP 是怎么被 tc 认出来的：

```
IPv6 头第一字节 = 版本(4bit) + Traffic Class(8bit)
Traffic Class 的高 6 位就是 DSCP
所以 tc 的 u32 要匹配 "ip6 priority"，值 = DSCP << 2，掩码 0xfc

  DSCP 46 → 46 << 2 = 0xb8，掩码 0xfc
  DSCP 10 → 10 << 2 = 0x28
```

发送端怎么打标记？在 socket 上设 `IPV6_TCLASS`：

```python
s.setsockopt(socket.IPPROTO_IPV6, IPV6_TCLASS, dscp << 2)
```

`mrc_lite.py` 和 `collsim.py` 都支持 `--dscp`，就是为了这个实验。

### 3.1 这个实验的边界（必须说清）

```
已验证   三级 HTB 能建立，DSCP → 队列的映射正确，各类有独立计数
未验证   "低优先级被压时，高优先级 p99 不受影响"
原因     纯 Python 流量撑不出真正的队列压力（吞吐只有几百 Mbps，
         而队列要打满才有排队），所以对照做不出来
```

**能做的是"分级生效"，做不出的是"分级的收益"。** 这条写在报告里。

## ④ 三个脚本怎么配合

```
日常：   80-daily 每天上班跑一次，30 秒
实验前： 40-observe snap 存一个基线
实验中： 40-observe watch 看实时吞吐，rtt 看抖动
实验后： 再 snap 一次，两个快照相减 = 这次实验发生了什么
排障时： 80-daily → 40-observe stats → 查 docs/03 故障字典
```

一个小技巧：**做任何故障注入前后各存一次 snap**。
队列计数、接口错误计数、路由条数，这三个数字的变化本身就是证据。

## ⑤ 常见故障

```
rtt 输出 p99 是 null
  → 包数太少，分位数算不出来；至少发 200 个

watch 的吞吐是 0
  → 采样窗口内没有流量，或者网卡名写错（看 docker0 去了）

80-daily 全绿但业务不通
  → 巡检只看"本机状态"，跨机问题要看 verify（50-verify）
  → 巡检通过 ≠ 拓扑正确，两者互补

60-qos test 三种 DSCP 走的一样多
  → 发送端没打 DSCP 标记（--dscp 没传），全部落默认类
```

## ⑥ 一句话记住这一篇

**观测给分位数不给平均值，巡检按"从下往上"排并保证不误报，
QoS 用 DSCP<<2 匹配——三件事都为了"数字能拿去说事"。**
