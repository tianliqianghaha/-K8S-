## ② 四个坑，按踩到的顺序（这一节是全文核心）

### 坑 1：ECS 端点查不到交换机的 IPv6 网段

```
现象  用 ECS 端点的 DescribeVSwitches 读 Ipv6CidrBlock，永远是 null
       → 我据此判断"用户没开 IPv6"，并把这个结论告诉了用户
真相  ECS 端点的这个接口根本不返回该字段。
      必须调 VPC 端点：https://vpc.aliyuncs.com/  +  Version 2016-04-28
修法  describe_vswitches 改走 VPC 端点，读不到再逐个查 DescribeVSwitchAttributes 兜底
```

这个坑最值得记的不是技术细节，是**判断方式**：

```
错误   一个接口返回 null → 下结论"没有"
正确   一个接口返回 null → 换一个接口验证，再下结论
```

而且这次是**用户拿着控制台截图纠正我的**。
教训：当 API 结果和人的直观观察冲突时，先假设自己读错了字段。

### 坑 2：IPv6 分配了，但 DescribeInstances 不返回

```
现象  RunInstances 带了 Ipv6AddressCount=1，DescribeInstances 的 Ipv6Address 永远空
      再调 AssignIpv6Addresses 报 exceeds the limit(1) —— 说明其实已经分配了一个
真相  地址在，只是 DescribeInstances 不返回该字段
修法  从 DescribeNetworkInterfaces 的 Ipv6Sets 读
```

`exceeds the limit(1)` 这个报错反而是好消息：**它证明"有一个"**。

### 坑 3：安全组的 IPv4 规则不覆盖 IPv6

```
现象  VPC 开了 IPv6，实例也有地址，但 ping 不通，邻居都解析不出来
真相  12 条入站规则，Ipv6SourceCidrIp 全部为空
      看着有 "ALL -1/-1 172.16.0.0/12" 和 "ICMP 0.0.0.0/0"，
      但对 IPv6 一条都不生效
修法  新建专用安全组，显式写 IPv6 来源：
      ALL    240b:...::/64    本子网全通（NDP / 实验 UDP / SSH）
      ICMPv6 ::/0             路径 MTU 发现 + 排障 ping
      TCP 22 0.0.0.0/0        SSH 走公网 IPv4
```

这条最容易误判，因为控制台上"看起来已经全放行了"。
**判据：看 `Ipv6SourceCidrIp` 是不是有值，不看有没有 ALL 规则。**

### 坑 4（最有价值）：VPC 内不是二层转发

```
现象  ping 自定义 DA（ULA）：a 上抓到 3 个包出去了，c 上一个都没收到
排查  先查 SourceDestCheck（开着，已关），仍然不通
转折  看邻居表：对端 MAC 全是 ee:ff:ff:ff:ff:ff（虚拟路由器）
      a 自己的 MAC 是 00:16:3e:15:7d:74
结论  VPC 内所有包都交给 vSwitch，由它按 IPv6 目的地址路由；
      ULA 不在 VPC 网段里 → 无路由 → 丢
修法  两步，缺一不可：
      ① ModifyNetworkInterfaceAttribute  SourceDestCheck=false
      ② CreateRouteEntry  给每个 ULA 前缀铺静态条目
         NextHopType=Instance（主网卡不能用 NetworkInterface）
结果  ping 4/4，RTT 0.48 ms
```

为什么这个坑最有价值？因为它顺带说明了**一件关于 HPN 的事**：

```
云上的"静态源路由"不是免费的。
你必须在 VPC 路由表里为每个 SID 前缀铺一条静态条目。
这和 MRC 论文里"交换机装静态表、关掉动态路由"是同一个思路，
只不过这里替你干这活的是 VPC 的虚拟路由器。
```

**理论（端侧选路）和现实（云平台要配合）在这里对上了。**

## ③ 端到端验证证据（这一节是"别说我吹"）

```
P1 通透性     ping fcbb:bb00:ffff:1::1 → 4/4，RTT 0.48 ms
uSID 弹栈     c 上同一条流的两帧，相隔 32 微秒：
              11:17:27.674951  > fcbb:bb00:2:e000::   进 c
              11:17:27.674983  > fcbb:bb00:e000::     出 c（左移 16 bit）
端到端        b 上抓到双 IP6 头，外层 fcbb:bb00:e000::，内层 fd00:b0b0::1，SRH 计数 0
验收          a 10 项 / b 4 项 / c 3 项，全部通过
```

三个证据分别对应三件事：

```
P1     证明"云让我自己编码目的地址"          ← 前提
弹栈   证明"路径真的逐跳消费"                ← 机制
双层   证明"封装/解封装整条链路成立且无 SRH"  ← 结果
```

## ④ 部署方式：不依赖 SSH 密码

```
用云助手（ECS 的 RunCommand）在实例内执行命令
  ├─ 优点：不用开 SSH、不用管密钥、批量下发
  ├─ 注意：单条命令内容有上限（约 16KB），大文件要分片传
  └─ 坑：RunCommand 必须 POST（GET 会返回 InvalidAction.NotFound）
```

文件怎么传？两级跳：

```
① 本地 base64 分片 → 云助手追加写入 /tmp/x.b64 → base64 -d 还原
② 第一台起临时 HTTP 服务（绑 IPv6），其余两台 curl 拉取
```

第二级很实用：**一次上传，三台分发，而且走的是内网 IPv6 不计流量费。**

## ⑤ 已知限制（最后一节）

```
IOAM6 不可用      iproute2 6.19 没带 ip ioam 子命令 → L9 跳过
抢占式随时回收    数据不保留，长实验要自己落盘
释放前必须删路由  否则 ULA 前缀一直指向已释放实例
```

第三条是操作纪律，不是限制：

```
顺序不能反：先删 VPC 路由 → 确认删干净 → 再释放实例
反了会留下一堆黑洞路由，下次开机会莫名不通
```

## ⑥ 一句话记住这一篇

**四个坑里有三个是"我读错了字段"而不是"云有问题"，
第四个（VPC 不是二层转发）反过来印证了 HPN 的核心思想：
静态源路由在云上要你在 VPC 路由表里亲手铺。**
