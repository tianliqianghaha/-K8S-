# 13 · 运维日常 SOP 解说（docs/07-运维日常SOP.md）

> 对应文件：`docs/07-运维日常SOP.md`

这份文档回答一个问题：**这个岗位的人每天到底在做什么？**
不是"搭一次拓扑"，是五个反复循环的动作。

---

## ① 五个动作，一周的完整循环

```
一  班前巡检    每天 5 分钟      今天能不能开工
二  变更流程    每次改配置       改之前备份、改之后验证
三  故障处置    出事时           五步定位法
四  交接班      每班一次         状态一致、残留清净
五  周复盘      每周一次 30 分钟 把踩过的坑变成资产
```

为什么是这五个？因为它们覆盖了运维的全部时间分布：

```
90% 的时间在"一"（巡检）
遇到故障才有"三"
剩下的时间是"二、四、五"，看起来不紧急，但决定了故障时的从容程度
```

---

## ② 班前巡检：五段输出，一条结论

```bash
./bin/80-daily.sh --brief
# 最后一行只有三种：
#   全部正常，可交接
#   有 N 项可疑，建议关注
#   有 N 项异常，先别跑实验
```

为什么强调"一条结论"？

```
巡检的目的是"决定要不要开工"，不是"展示我很细"。
三十行细节 + 一句结论，比五十行细节没有结论有用得多。
```

`--brief` 只打异常项和结论，适合贴到群里；不带参数打全量，适合自己看。

---

## ③ 变更流程：五步法（这一步最容易被跳过）

```
1) 现状快照     路由 / 规则 / 队列 / 计数   存一份
2) 配置基线     文本形式，便于 diff
3) 健康基线     巡检输出
4) 变更
5) 变更后验证   与基线对比
```

为什么必须存快照？因为**排障时最缺的是"变化之前长什么样"**。

```
常见场景
  "昨天还好好的，今天就通了/不通了"
  → 没有基线，你只能猜
  → 有基线，diff 一下就知道变了什么（甚至是别人改的）
```

一个具体做法：

```bash
# 快照存成一个文件，带时间戳
./bin/40-observe.sh snap > /var/log/hpn/snap-$(date +%H%M).txt
ip -6 route show > /var/log/hpn/routes-$(date +%H%M).txt
ip -6 rule show  > /var/log/hpn/rules-$(date +%H%M).txt
```

## ④ 故障处置：五步定位法（这是 SOP 里最实用的部分）

```
① 先确认范围        一台还是三台？一条平面还是两条？
② 从下往上查        物理 → 接口 → 地址 → 路由 → 策略 → 业务
③ 找"最近的变化"    谁改了什么？什么时间？
④ 二分             把链路切成两半，看断在哪
⑤ 修完必须复验      用验收脚本，不用"感觉好了"
```

第 ④ 步"二分"在网络排障里特别有效，因为链路是线性的：

```
a → c → b 不通
  先看 a 有没有发包（a 上 tcpdump dst <DA>）
  有 → 再看 c 有没有收到（c 上 tcpdump）
      收到 → 看 c 有没有转发出去（同一接口两个方向都抓）
      没收到 → 问题在 a 到 c 之间（云路由？源目检查？）
```

实际案例：本实验里"a 抓到 3 个包、c 一个没收到"，
一刀就把范围切到了"a 的出方向之后、c 的入方向之前"，
最后定位到 VPC 路由 + SourceDestCheck。

## ⑤ 交接班：三件事

```
1) 清残留        最容易被忘
   实验进程、故障注入、临时路由
2) 三台状态一致  role / 拓扑 / 巡检结论
3) 数据落盘     这次跑的原始输出（json / pcap / 日志）
```

"清残留"为什么排第一？

```
因为残留会让下一个人得出完全错误的结论。
本实验真实发生过：fault clear 把正常路由删了，
下一个人接手时"平面 0 不通"，查了半天以为云出问题。
```

具体清单：

```bash
pkill -9 -f '[c]ollsim.py'
pkill -9 -f '[m]rctp.py'
./bin/30-fault.sh clear
tc qdisc show dev eth0          # 确认没残留
ip -6 route show | grep fcbb    # 确认前缀都在
```

## ⑥ 周复盘：把坑变成资产

```
每周 30 分钟，回答三个问题：
① 这周踩了几个坑？分别是什么类型（配置 / 代码 / 云平台 / 判断失误）
② 哪些坑已经写进故障字典了？没写的补上
③ 哪些操作重复了三次以上？该写脚本了
```

这份 SOP 里的很多东西就是这么来的：

```
"fault clear 只撤自己加的 blackhole"     ← 来自一次真实事故
"VPC 内按目的地址路由"                    ← 来自一次误判
"巡检对 c 跳过业务面检查"                 ← 来自每天一次假警
```

**复盘的产出不是会议纪要，是脚本里的一行代码或字典里的一条。**

---

## ⑦ 常用命令速查（文档最后一节）

分成五组：状态 / 观测 / 故障 / 业务 / 清理。
原则是"**任何一条都能单独粘贴执行，不依赖上下文**"。

```bash
# 状态
ip -6 route show | grep fcbb
ip -6 rule show
tc -s qdisc show dev eth0

# 观测
./bin/40-observe.sh rtt 200
./bin/40-observe.sh watch 10

# 故障
./bin/30-fault.sh inject lossport 2 9601
./bin/30-fault.sh clear

# 业务
./bin/hpnlab verify
```

## ⑧ 一句话记住这一篇

**巡检给结论不给细节，变更先存基线，故障从下往上二分，交接先清残留，
复盘把坑写成代码——SOP 的价值是让"上次怎么解决的"变成"下次怎么一分钟解决"。**
