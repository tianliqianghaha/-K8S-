# 03 · 拓扑与验收解说（20-topology.sh + 50-verify.sh）

> 对应文件：`bin/20-topology.sh`、`bin/50-verify.sh`

这一篇讲"真正把网络做出来"的那一步。拓扑脚本负责建，
验收脚本负责**证明它建对了**——两个脚本配套使用，不能只看前者。

---

## ① 三台机器各装什么

```
node-a  headend（入口）
  装两条"封装路由"：同一个业务地址，两个不同的外层 DA，放在两张路由表里
  装两条"策略路由"：给包打上 fwmark，决定走哪张表
  效果：同一个目标，程序说走哪条就走哪条

node-c  fabric（中转）
  装一条 seg6local End（带 next-csid flavor）：
  收到 DA = block + 自己编号 + 下一跳编号 的包，
  弹掉自己那 16 bit，DA 左移，然后按普通路由送出去

node-b  tailend（出口）
  装 dummy 口 svc0 + 业务地址
  装一条 seg6local End.DT6 table 255：
  解封装，把内层包按本地地址投递（table 255 = local）
```

---

## ② a 端：为什么必须两张路由表

初学者最容易疑惑的一点：为什么不能直接改默认路由？

```
因为"同一时刻要向同一个目的发两种路径的包"。
一张表里，同一个目的只能有一条路由。
所以要有两张表，靠 fwmark 选表。
```

具体命令长这样：

```bash
# 两条封装路由，分表存放
ip -6 route replace $SVC/128 encap seg6 mode encap.red segs $DA_PLANE0 dev eth0 table 100
ip -6 route replace $SVC/128 encap seg6 mode encap.red segs $DA_PLANE1 dev eth0 table 101

# 主表里放一条默认（不挑路径时走平面 1）
ip -6 route replace $SVC/128 encap seg6 mode encap.red segs $DA_PLANE1 dev eth0

# 策略路由：mark 决定去查哪张表
ip -6 rule add fwmark 0x2 table 100 priority 200
ip -6 rule add fwmark 0x1 table 101 priority 201
```

`encap.red` 里的 `.red` 是 "reduced"——**减少一层封装**，
也就是把段列表直接写进外层 DA，不额外造 SRH。这正是 uSID 的用法。

而 fwmark 这一套，就是 MRC 论文里"EV（熵值）表"的软件等价物：
程序在 socket 上打个标记，内核就按标记选表，包就走了不同的物理路径。

```
EV 在硬件里 = 一个 256 项的映射表，每个 EV 指向一条确定的路径
EV 在 Linux 里 = fwmark + 路由表 + 规则，三者组合出来的等价能力
```

## ③ c 端：一行命令就是 uSID 的全部

```bash
ip -6 route replace fcbb:bb00:2::/48 encap seg6local action End \
   flavors next-csid lblen 32 nflen 16 dev eth0
```

拆开看每个词在说什么：

```
encap seg6local        端点行为，不是隧道。这个节点是"路径中的一站"
action End             弹栈：把 DA 最左边那一段消费掉，剩下的继续按路由转发
flavors next-csid      使用 RFC 9800 的压缩段（uSID），不是一个 SID 占 16 字节
lblen 32               块长度 32 bit（fcbb:bb00）
nflen 16               节点长度 16 bit（下一跳编号）
```

装完之后，一个 DA 形如 `fcbb:bb00:2:e000::` 的包进来，c 做的是：

```
进 c：  fcbb:bb00 : 2 : e000 ::
出 c：  fcbb:bb00 : e000 ::
        ↑ block  ↑ 下一跳（已左移 16 bit）
```

**没有 SRH，没有额外头部，路径就是 DA 里的字节。**

## ④ b 端：解封装与投递

```bash
ip link add svc0 type dummy && ip link set svc0 up
ip -6 addr replace fd00:b0b0::1/128 dev svc0
ip -6 route replace fcbb:bb00:e000::/48 encap seg6local action End.DT6 table 255 dev eth0
```

`End.DT6 table 255` 的 `255` 是 local 表——意思是"解完封装，把这个内层包
当成发给本机的包投递"。不用 VRF，最简单。

如果这台内核对 `End.DT6 table 255` 不支持，退路是用 VRF（标准 L3VPN 那套），
写法在 `docs/01` 第 8 节。**这是整套脚本里唯一"不保证所有内核都行"的地方。**

还有一个容易被忽略的点：dummy 口上的地址是 `/128`。为什么不是 `/64`？

```
因为我们不希望这个地址参与任何前缀路由。
它只是一个"投递终点"，投递规则由 seg6local 写死，不需要邻居发现。
```

## ⑤ 验收脚本：为什么它比拓扑脚本更重要

拓扑脚本只会说"命令执行了"，验收脚本会说"**结果对不对**"。

```
a 端五项
  A1 外层 FIB：到 c、到 b 的前缀路由在不在
  A2 三条封装路由：主表 / 表 100 / 表 101 各指向哪个 DA
  A3 策略路由：mark 0x2 是否真去查表 100，mark 0x1 是否真去查表 101
  A4 选路结果：ip -6 route get ... mark 0x2 解析出来的 DA 对不对
  A5 端到端：ping 业务地址通不通

b 端三项
  B1 svc0 上有业务地址
  B2 End.DT6 就位
  B3 抓包：抓到 n 个外层包，其中带 SRH 的必须是 0 个
```

A3 和 A4 的区别特别值得说：

```
A3 只证明"规则存在"        ip -6 rule show 里有这一行
A4 证明"规则真的生效"      ip -6 route get 带上 mark，看解析结果
```

**只查 A3 是不够的**——规则可能优先级被别的东西盖住，或者表号写错。
用 `route get` 走一遍真实的选路，才算验完。

B3 是这套实验的"卖点断言"：

```
抓到 n 个包（证明封装确实发生了）
且带 SRH 的是 0 个（证明用的是 uSID，不是标准 SRv6）
```

如果这里报"出现 SRH"，说明 `encap.red` 写成了 `encap`——
那就退回了标准 SRv6，云 vSwitch 很可能把它剥掉。

## ⑥ 建与拆必须配套

`20-topology.sh` 有三个子命令：

```
up      建
down    拆（删规则、删路由、删 dummy 口）
status  看现状（不修改任何东西）
```

`down` 写得比 `up` 还啰嗦，是故意的：

```
删之前先 del 一遍（幂等，重复执行不报错）
删路由表要 flush table 100 / 101（不是删单条）
删 dummy 口之前先删地址（否则会残留）
```

因为现场最怕的是"拆了一半"，下次 `up` 就建在一个半干净的状态上，
表现出来是各种玄学不通。**幂等的拆，是能反复做实验的前提。**

## ⑦ 常见故障

```
up 之后 ping 不通，但路由都在
  → 先看 b 的 End.DT6 装上了没（verify B2）
  → 再看 c 的 forwarding 和 seg6_enabled（sysctl）
  → 最后看 a 的外层包有没有真出去（tcpdump -i eth0 dst <DA>）

平面对不上：mark 0x2 却走到了平面 1 的 DA
  → ip -6 rule show 看优先级，priority 数字小的先生效
  → 检查是不是残留了旧规则（脚本已做 del 再 add，手工改时要注意）

c 上装 seg6local 报错
  → 内核 < 6.1，或 iproute2 太旧
  → 回 00-preflight 看功能探测那一项
```

## ⑧ 一句话记住这一篇

**a 用"两张表 + 两个 mark"实现端侧选路，c 用一行 flavors 实现 uSID 弹栈，
b 用 End.DT6 实现解封装；验收脚本负责证明这三件事都真的生效了。**
