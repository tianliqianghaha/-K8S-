# 02 · 体检与探路解说（00-preflight.sh + 10-probe.sh）

> 对应文件：`bin/00-preflight.sh`、`bin/10-probe.sh`

这两个脚本是**开工前的两道闸门**。第一道问"这台机器行不行"，
第二道问"这朵云让不让你干"。两道都过了，后面才值得花时间。

---

## ① 为什么要分成两道

```
体检（preflight）    只跟机器有关：内核版本、编译选项、iproute2 能力、地址、互通
探路（probe）        只跟云平台有关：能不能自定义目的地址、会不会剥扩展头、MTU 多少
```

分成两道的价值在排障：**报错时能立刻定位是"我的机器不行"还是"云不让我干"。**
如果混在一个脚本里，一个 `bad` 出现，你不知道该换机器还是换方案。

---

## ② 体检脚本的六段

```
1 权限      必须是 root（建 netns、改 sysctl、装路由都要）
2 内核      版本 + 三个编译开关
3 iproute2  能不能真的装 uSID 路由（功能探测，不是看版本号）
4 IPv6      地址、默认路由、对端可达、邻居解析
5 转发      forwarding / seg6_enabled 是否打开
6 结论      通过几项、失败几项
```

### 2.1 为什么查编译开关而不是只看版本号

内核版本号只说明"大概是哪一代"，不说明这个功能编进去了没有。
云厂商的定制内核经常裁掉一些模块。所以直接查：

```
CONFIG_IPV6_SEG6_LWTUNNEL      SRv6 封包/解包（seg6local 也在其中）
CONFIG_IPV6_SEG6_LOCAL         seg6local 端点行为
CONFIG_IPV6_MULTIPLE_TABLES    多路由表（策略路由要用表 100/101）
```

后两个是硬需求：没有它们，`encap seg6` 和 `table 100` 直接装不上。

### 2.2 最巧的一段：功能探测代替版本判断

```bash
ip -6 route add fcbb:ff00::/48 encap seg6local action End \
   flavors next-csid lblen 32 nflen 16 dev lo table 12345
```

它的思路是：**别猜，真装一条试试，装完就删。**

早期版本这里是 `ip route help | grep flavors`——那是错的，因为帮助文本里
有 `flavors` 不代表你的内核支持 `next-csid` 这个具体 flavor。
改成"真装一次"之后，判断才准。

这条经验可以推广到所有能力探测：**能力要用"执行"验证，不要用"声明"验证。**

## ③ 探路脚本在探四件事（整个实验台的生死判据）

```
P1  外层 ULA 目的地址能不能穿过 vSwitch
    → 决定"能不能自己编码路径"，还是只能在外层用云分配的地址

P2  SRH 扩展头会不会被中间设备剥掉
    → 决定走"标准 SRv6"还是"uSID"（uSID 没有 SRH，剥不到）

P3  封装之后的真实 MTU 上限
    → 决定单个载荷能塞多大，以及会不会踩 PMTU 黑洞

P4  逐跳扩展头（IOAM）能不能穿过
    → 决定带内遥测那组实验做不做得了
```

为什么这四件事文档里查不到？因为它们是**云厂商 vSwitch 的实现细节**，
不在任何 SLA 里。同一个厂商不同地域可能都不一样。只能实测。

### 3.1 P1 的原理与本次结论

```
原理：如果 vSwitch 只按 MAC 转发、不看 IPv6 目的地址，
      那我们就能在外层 DA 里随便编码 uSID，不必是云分配的公网段。

本次实测（阿里云香港）：
  第一次失败 —— a 抓包有 3 个包出去，c 抓包 0 个
  根因两条，缺一不可：
    ① ENI 的 SourceDestCheck=true，自定义目的地址在出网卡时就被丢了
    ② VPC 内不是二层转发：邻居表里对端 MAC 全是 ee:ff:ff:ff:ff:ff（虚拟路由器），
       说明所有包都交给 vSwitch 按 IPv6 目的地址路由；ULA 不在网段里 → 无路由 → 丢
  修法：
    ① ModifyNetworkInterfaceAttribute SourceDestCheck=false
    ② CreateRouteEntry 给每个 ULA 前缀铺静态条目（NextHopType=Instance）
  结果：ping 4/4 通，RTT 0.48 ms
```

这一段是整套实验里最有价值的一条云上经验：
**云上的"静态源路由"不是免费的，你得在 VPC 路由表里为每个 SID 前缀铺一条静态条目。**
这和 MRC 论文里"交换机装静态表、关掉动态路由"是同一个思路，
只不过这里替你干这活的是 VPC 的虚拟路由器。

### 3.2 P2 的设计很聪明

```
单段 SID 用 encap.red 不产生 SRH；多段 SID 必然产生 SRH。
所以：从 a 分别发"无 SRH"和"有 SRH"两组包，
      在 b 上各抓一次 —— 两组都到，说明 SRH 被剥了但不影响转发；
      有 SRH 的那组丢，说明 SRH 被剥且转发失败。
```

一句话：**用"有没有 SRH"做对照变量，而不是去猜中间设备的行为。**

本次结论：外层改用 uSID 之后完全不需要 SRH，P2 变成"不需要关心"。

## ④ 探路脚本里几个"因为踩过坑所以写成这样"的细节

```
① grep -c 无匹配时返回 1，会让变量变成 "0\n0"，整数比较直接崩
   → 必须写成 ... || echo 0，或者用 wc -l

② 内层目的地址和外层 DA 不能写成同一个
   → 否则封装后外层再查路由会撞回自己，形成自封装环

③ 路由前缀必须和实际地址一致
   曾经用 fcbb:bb00:ffff:1::/128 做路由，却 ping fcbb:bb00:ffff:1::1
   → 前缀和地址不一致，包落到默认路由去了网关，看着像"云不允许"
   → 这个 bug 让我白排查了一轮，最后发现是自己的错
```

第 ③ 条特别值得记：**当现象和"云平台限制"高度吻合时，先怀疑自己写的东西。**
云确实会限制你，但它不会伪造一个只有一位数字不对的地址。

## ⑤ 这两个脚本的用法

```bash
sudo ./bin/hpnlab check          # 体检，三台都跑
sudo ./bin/hpnlab probe          # 探路，注意时序！

探路的时序很讲究（数据面要对得上）：
  1) c 上挂抓包（后台，抓 15–25 秒）
  2) b 上挂抓包
  3) a 上发包
  4) 回到 c / b 读结果
```

本环境用云助手批量下发时，三台的启动时间会差几秒，抓包窗口容易错过。
**建议三个 ssh 窗口手工起**，比脚本可靠。
