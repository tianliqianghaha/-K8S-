# 08 · MRC 传输原型解说（mrctp.py）

> 对应文件：`app/mrctp.py`

这是三个程序里最有内容的一个。它要回答的问题是：

**在一个会丢包的网络里，"只补洞"比"整窗重发"到底省多少？多路径喷洒到底值不值？**

---

## ① 先讲清楚什么是 MRC / UEC 的那套思路

传统的 RoCEv2 有一个硬伤：**丢一个包，整窗重传（Go-back-N）**。

```
发 100 个包，第 3 个丢了
等 RTO 超时 → 从第 3 个开始重发后面所有包（哪怕 4–100 都到了）
代价：一次丢包，可能重发近百个包
```

所以生产上宁可用 PFC 保证"一个都不丢"。代价是 PFC 会带来队头阻塞，
搞不好整条链路卡死。

MRC/UEC 的思路反过来：

```
① 接收端能精确告诉发送端"哪几个洞"（SACK 位图）
② 发送端只重发那几个洞
③ 一旦发现洞，立刻 NACK，不等超时
④ 每个包单独选路径（喷洒），把链路用满
⑤ 于是可以在有损网络上跑 → 可以关掉 PFC
```

这个程序就是 ①–③ 的最小实现，外加 ④ 的开关。

---

## ② 三个可切换的维度

```
--retx gbn | sack     重传策略：整窗回退 vs 只补洞
--nack on | off       发现洞时立刻要 vs 等 RTO 超时
--paths 1 | 2         单路径 vs 双平面逐包喷洒
```

六种组合里，最有说服力的两组是：

```
② 单路径 / SACK / 丢 2%       ← "选择性重传在有损网络上的表现"
③ 单路径 / GBN  / 丢 2%       ← 对照组
⑤ 双平面 / GBN  / 丢 2%       ← 最反直觉的一组
```

## ③ 包格式与确认机制

### 3.1 数据包

```
!IIIBI   msg_id(4) chunk_idx(4) total_chunks(4) flags(1) ts_ms(4)   + 填充
```

`total_chunks` 原来是 1 字节，结果 4MB 消息有 2996 片直接溢出。
**凡是"总数"字段，一律给 4 字节。**

### 3.2 确认包有两种

```
S   msg_id(4) base(4) nbits(2)   + 位图      ← 累积确认 + 选择性确认
N   msg_id(4) chunk_idx(4)                   ← 立即重传请求
```

`base` 是"第一个洞的位置"，位图里 1 表示"收到了"。

**为什么 base 必须是"第一个洞"而不是"最小已收到"？**
这是踩过的坑：

```
错误做法：base = min(收到的)
  第 0 片永远在，所以 base 永远是 0 → 位图永远覆盖 0..255
  → 发送端永远只能学到前 256 片的状态，后面的包全在超时重发
正确做法：base = 从 0 开始一直推进到第一个没收到的位置（累积 ACK 点）
  这就是 TCP 的累积确认 + SACK 的经典组合
```

### 3.3 完成判定

```
不用"inflight 是否清空"判断（个别在途残留会让消息永远不结束）
用"这条消息被确认的分片数 >= 总片数"判断
```

还要注意一个顺序问题：接收端收齐后必须**先发终态 SACK 再清状态**，
否则清空后 `len(st)` 变 0，那个"发 SACK"的判断条件就不成立了，
发送端永远不知道已经收齐。

## ④ 性能：为什么第一版只有 3.2 Mbps

这是这一篇最重要的部分。第一版的数字是：

```
六种配置跑出来几乎一样，吞吐 3.2 Mbps，重传率 39%
差异 < 3% —— 等于什么都没测出来
```

原因不是网络没差异，是**测量工具坏了**。四个缺陷：

```
① 洞定位是 O(n)
   每个包都从 0 扫到 max(st) 找洞 → 4MB 消息 2996 片，每包扫 1500 次

② 同一个洞每个包都发一次 NACK
   → 发送端收到 NACK 就重发 → 自己把自己打爆
   → 那 39% 的重传全是自发重传，跟真实丢包无关

③ 发送端 RTO 扫描遍历全部历史包
   （而不是只扫 inflight）→ 每轮循环几万次比较

④ 每个包都 setsockopt(SO_MARK)
   → 每包多一次系统调用
```

修法：

```
① 维护 cbase 指针，只在 idx == cbase 时推进 → O(1)
② NACK 加 20ms 抑制窗口（同一个洞 20ms 内只报一次）
③ 发送端只扫 inflight，ack 时立刻从 inflight 里摘掉
④ 只在切换路径时改 SO_MARK；分片载荷按消息预生成（不每包 pack）
```

修完：**3.2 Mbps → 515 Mbps，重传 39% → 0.27%。**
六种配置的差异这才显现出来。

还有一个衍生改动：**发送端绑临时端口**。
原来发送端也绑 `--port`，同机测试时两端抢同一个 UDP 端口，收包互相串台。

### 4.1 这条经验比任何数字都重要

```
"测不出差异"的第一嫌疑永远是测量工具，不是被测对象。
先做一个已知答案的对照（无丢包 vs 100% 丢包），
工具过不了这一关，后面的数据全是废的。
```

---

## ⑤ 按端口分平面：让"喷洒"第一次能被证明

早期两条平面都发往同一个目的地址，只是路径不同。
想打伤其中一条，只能按目的地址过滤 —— 结果两条一起被打伤。

改法：**每条平面一个目的端口**

```
平面 0 → 9600（经 c 绕行）
平面 1 → 9601（a→b 直达）
```

这样 tc 能精确打伤 9601，模拟"一条平面坏了"。
这也和真实 MRC 对齐：**每个 QP 绑定一条平面**，而不是靠五元组哈希碰运气。

接收端要同时监听两个端口（9600 和 9601），在哪个 socket 上收到，
就用那个 socket 回 SACK。

## ⑥ 六组对照的实测结果

```
                                   完成    用时      吞吐       重传(比例)   伪重传
① 单路径 / SACK / 无丢包           20/20   0.325 s   515.8 Mbps   0.27%       0
② 单路径 / SACK / 平面1 丢 2%      20/20  12.830 s    13.1 Mbps   6.27%     935
③ 单路径 / GBN  / 平面1 丢 2%      20/20  11.627 s    14.4 Mbps  12.17%    2032
④ 双平面 / SACK / 平面0 丢 2%      20/20   9.778 s    17.2 Mbps   2.95%     407
⑤ 双平面 / GBN  / 平面0 丢 2%      20/20  10.187 s    16.5 Mbps  20.48%    3797
⑥ 双平面 / SACK / 平面1 丢 2%      20/20   8.298 s    20.2 Mbps   5.66%     850
```

四个结论：

```
① 丢包代价：515.8 → 13.1 Mbps，塌 25–40 倍
② 重传策略：同丢包下 SACK 6.27% vs GBN 12.17%，差一倍
   且 GBN 多出来的几乎全是伪重传（2032 vs 935）
③ 喷洒收益：⑥ 20.2 vs ② 13.1，快 55%
④ 最反直觉：⑤ 双平面 + GBN 重传 20.48%，比单路径 GBN 还差
   整窗回退不看路径，把好路上的好包也重发了，等于自己堵死第二条路
   → 多路径必须配选择性重传，否则不如不喷
```

第 ④ 条是整套实验里最有洞察的一条：它说明**"多路径"和"选择性重传"不是两个独立优化，
而是一对必须配套的机制**。

## ⑦ 边界

```
├─ 515 Mbps 是 Python 用户态上限，不是网络上限
│  可比的是相对关系（25–40 倍塌陷、2 倍重传量、55% 提升）
├─ 没有拥塞控制（无 CWND 增长、无 ECN 响应）
│  只证明"重传策略"，不证明"拥塞控制"
├─ RTO 固定 300 ms，真实 RoCE 用自适应 RTO
│  固定 RTO 会放大伪超时（② 的 1001 次重传里 935 次是伪重传）
├─ packet trimming 没真做（需网卡支持）
│  这里用"立即 NACK"近似它的收益
└─ 单次运行，未做多轮统计；看量级，不看小数点
```

## ⑧ 怎么跑

```bash
# b 起接收端（同时监听 9600/9601）
setsid nohup python3 -u app/mrctp.py run --role recv --peer <a> \
  --port 9600 --msg-mb 1 --timeout 90 > /tmp/r.json 2>&1 &

# a 起发送端，打伤平面 1
./bin/30-fault.sh inject lossport 2 9601
python3 app/mrctp.py run --role send --peer <b> --port 9600 --port1 9601 \
  --msg-mb 1 --msgs 20 --paths 1 --retx sack --nack on --timeout 90
./bin/30-fault.sh clear
```
