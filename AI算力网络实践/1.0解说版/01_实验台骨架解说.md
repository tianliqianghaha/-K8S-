# 01 · 实验台骨架解说（README + hpnlab + _env.sh + lab.env）

> 对应文件：`README.md`、`bin/hpnlab`、`bin/_env.sh`、`conf/lab.env`

这一篇讲"骨架"。骨架的意思是：**还没开始做任何网络动作，但所有动作都要经过它们。**

---

## ① 四个文件各管什么

```
conf/lab.env    三台机器上唯一要改的文件。改完这一份，其他脚本都不用动。
bin/_env.sh     把 lab.env 读进来，并且"洗干净"再交给别人用。
bin/hpnlab      命令入口。你不用记"哪个脚本第几个参数"，只记 hpnlab 后面的词。
README.md       给要动手的人看的：五分钟上手 + 三个限制。
```

为什么要分这四层，而不是一个大脚本全写完？因为运维现场最容易出的事是
**"我不知道该改哪个文件"**。把"改什么"（lab.env）和"怎么用"（hpnlab）分开，
换机器时只碰第一个。

---

## ② conf/lab.env：三台机器只改这里

```
ROLE="a"                      每台只改这一行：a / b / c
IFACE="eth0"                  主网卡名

NODE_A_IPV6="240b:...:f9a7"   三台填一样的三个地址
NODE_B_IPV6="240b:...:f9a5"
NODE_C_IPV6="240b:...:f9a6"

USID_BLOCK="fcbb:bb00"        uSID 的 block
U_TRANSIT="2"                 平面 0 的中转节点编号（c）
U_TAIL="e000"                 平面 1 的终结节点编号（b）
SERVICE_ADDR="fd00:b0b0::1"   b 上 dummy 口的业务地址

PLANE0_MARK=0x2               平面 0 的 fwmark（走 c）
PLANE1_MARK=0x1               平面 1 的 fwmark（直达 b）
PLANE0_TABLE=100              策略路由表号
PLANE1_TABLE=101
```

三个地址为什么三台都要填全？因为**每台都要知道自己所有邻居的地址**：
a 需要 b 的地址来封包，c 需要 b 的地址来转发，b 需要 a 的地址来回包。
只填自己那台，另外两台就得靠猜。

## ③ bin/_env.sh：一个看起来多余、其实救命的文件

它只干两件事，但第二件是踩过坑才加的。

```
第一件  找到 conf/lab.env 并 source 进来
        支持用环境变量 LAB_ENV 覆盖路径（换机器做多套实验时有用）

第二件  把每个变量里的 \r 字符剥掉
```

第二件为什么必须有？

```
现象   三台 check 全部报"MTU=0、没有 IPv6、找不到 eth0"
怀疑   内核不支持 / 网卡名不对 / 云平台限制
真相   lab.env 在 Windows 上被编辑过，换行是 CRLF。
       bash 里 IFACE="eth0\r" 是完全合法的字符串，不报任何语法错，
       但 /sys/class/net/eth0\r 这个路径不存在 → 后面全部连带失败
```

所以它做了这件事：

```bash
for _v in ROLE IFACE NODE_A_IPV6 ... ; do
  if [ -n "${!_v+x}" ]; then
    printf -v "$_v" '%s' "${!_v//$'\r'/}"
  fi
done
```

`${!_v}` 是"用变量名取变量值"（间接引用），`//$'\r'/` 是"把所有 CR 换成空"。
这两句合起来，等于给所有配置项做了一次消毒。

**这一类故障最坑的地方不是难修，是它会伪装成"环境不支持"。**

## ④ bin/hpnlab：把九条命令记成一条

它的实现简单到有点土——一个 `case`，每个分支 `bash 某个脚本`：

```
./bin/hpnlab check        → bin/00-preflight.sh
./bin/hpnlab probe        → bin/10-probe.sh
./bin/hpnlab up / down    → bin/20-topology.sh up|down
./bin/hpnlab verify       → bin/50-verify.sh
./bin/hpnlab rtt / watch  → bin/40-observe.sh
./bin/hpnlab fault ...    → bin/30-fault.sh ...
./bin/hpnlab qos ...      → bin/60-qos.sh ...
./bin/hpnlab send / recv  → app/mrc_lite.py
./bin/hpnlab coll ...     → app/collsim.py
```

为什么要这一层？三个理由：

```
① 现场排障时手忙脚乱，少记一个路径就少一次出错
② 脚本改名或挪位置时，只改这一处
③ ./bin/hpnlab 不带参数会打印用法，等于自带帮助
```

有个细节值得学：`HERE` 和 `ROOT` 是用 `BASH_SOURCE` 算出来的，
所以这个入口不管从哪个目录调用都能找到自己的兄弟脚本。

```bash
HERE="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
ROOT="$(cd "${HERE}/.." && pwd)"
```

## ⑤ README.md：给动手的人，不是给看客

它只讲三件事：

```
五分钟上手     五步命令，从"三台机器"到"跑出第一个数据"
角色分工       哪台是 headend、哪台是 fabric、哪台是 tailend
三个限制       共享出口带宽 / 没有 PFC 与 RDMA / ULA 要靠云路由
```

第三段是最重要的：**先把限制写清楚，后面所有结论才可信。**
一个不写限制的实验报告，读者第一反应就是"这能算数吗"。

## ⑥ 骨架部分的常见故障

```
改了 lab.env 但没生效
  → 脚本用的是 _env.sh 里的路径，检查是不是改了另一份
  → 有些脚本会在启动时打印 role，看输出对不对

hpnlab 报 command not found
  → 它是脚本不是二进制，要用 ./bin/hpnlab
  → 或者 chmod +x bin/hpnlab

三台 role 全一样
  → 复制目录时把 nodes/hpnX/lab.env 覆盖成了同一份
  → 每台单独 cp nodes/hpnX/lab.env conf/lab.env
```

## ⑦ 一句话记住这一篇

**lab.env 决定"你是谁"，_env.sh 保证"你读到的是干净的"，
hpnlab 让你"不用记路径"，README 告诉你"别指望它做什么"。**
