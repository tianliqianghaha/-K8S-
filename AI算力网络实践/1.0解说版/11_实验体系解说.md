# 11 · 实验体系解说（docs/05-实验体系总览.md）

> 对应文件：`docs/05-实验体系总览.md`

这份文档不是"实验清单"，而是**一张能力地图**。
它回答的问题不是"能做什么实验"，而是"**这个岗位要什么能力，我现在缺哪一块**"。

---

## ① 起点：12 份真实 JD，提炼出 12 个能力域

做法不是"我想学什么"，而是"**招聘方到底要什么**"：

```
读 12 份 JD（智联 / 猎聘的智算网络、AIDC 组网岗位 + 海外 GPU 集群 network engineer）
去重、归并
→ 12 个能力域
```

这 12 个域大致是：

```
C1  架构           CLOS / Fat-Tree / Multi-Rail 设计与容量规划
C2  协议           IPv6 / BGP EVPN / SRv6 / VXLAN
C3  无损拥塞       PFC / ECN / DCQCN / 队列与水线
C4  负载均衡       ECMP / DLB / GLB / 自适应路由
C5  集合通信       AllReduce / AllGather / AlltoAll 的流量特征
C6  性能测试       perftest / nccl-tests / 压测设计
C7  故障定位       慢排空 / credit starvation / PFC 风暴
C8  可观测         逐流统计 / 逐跳遥测 / 时钟与测量误差
C9  自动化         配置生成 / 幂等 / 回归
C10 多租户安全     VRF 切片 / ACL / 管理面隔离
C11 文档交付       手册 / 故障字典 / 交接
C12 前沿跟踪       UEC / MRC / APN6 / 在网计算
```

### 1.1 这张表的第一个作用是"发现缺口"

对照原来的 L0–L9，会发现只覆盖了 5 个域：

```
已覆盖   C2 协议  C3 无损拥塞(部分)  C4 负载均衡  C6 性能测试  C7 故障定位
缺口     C5 集合通信 ★  C8 可观测 ★  C9 自动化  C10 多租户安全 ★  C1 架构  C12 前沿
```

带星号的三个，恰好是 JD 里出现频率最高的三句话：

```
「掌握 NCCLTest、分布式训练通信测试和跨节点性能验收」   → C5
「了解慢排空、credit starvation、PFC 风暴与死锁」        → C7 + C8
「具备 Leaf-Spine、Fat-Tree、Multi-Rail 架构设计能力」   → C1
```

**这就是为什么后来要补 collsim（C5）和 IOAM/逐流统计（C8）。**
不是为了"实验更多"，是为了"把缺口补上"。

## ② 八层结构：从"包能走"到"集群能扛"

```
L8 前沿     UEC/MRC 传输、APN6、带内遥测替代、数字孪生、单栈迁移、XDP 近似 DPU
L7 租户     VRF 切片与路由泄漏、ACL 分区、管理面隔离
L6 可观测   逐流 eBPF、排队点定位、时延分解、时钟同步与测量误差
L5 故障     三类故障谱、灰故障、恢复时间量化、配置漂移回滚
L4 流量     Ring/Tree AllReduce、AlltoAll、PP、KV cache、混跑与 straggler
L3 均衡     哈希极化、端侧选路、大流小流、rail 局部性、故障域隔离
L2 拥塞     ECN 阈值扫描、队列深度、incast、慢排空、丢包敏感度
L1 转发     单栈、uSID、flavor 对比、PMTU、NDP 规模陷阱
L0 地基     能力矩阵、通透性探路、基线回归
```

为什么是这个分法？因为它对应**排障时从上往下还是从下往上的思路**：

```
网络不通        从 L1 往上查
跑不满带宽      从 L2/L3 往上查
训练掉速        从 L4/L6 往上查
多租户串了      直接看 L7
```

**层的意义不是分类，是给出排查顺序。**

## ③ 每条实验记录都强制五个标签

```
环境        单机 netns / 三台真机 / 需要交换机
层次        落在 L0–L8 哪一层
难度        半天 / 一天 / 两天
云依赖      需不需要特定云能力（自定义 DA、关源目检查…）
可落地性    本环境能真做 / 只能近似 / 做不了
```

第 5 个标签（可落地性）是最诚实的一个：

```
能真做    IPv6-only、uSID、ECMP 极化、ECN、netem 损伤、IOAM（若内核支持）
只能近似  PFC（只能证明丢包代价）、DLB/GLB（用端侧选路代替）、trimming（用立即 NACK）
做不了    线速、真 NCCL、芯片行为
```

把"做不了"写进索引，是为了防止自己或别人误用这些实验的结论。

## ④ 三条推荐路线（不同目的走不同路）

```
面试冲刺 3 天（约 8 小时）
  E01 能力矩阵 → E05 uSID → E14 哈希极化 → E09 ECN
  → E19 Ring/AlltoAll → E24 三类故障谱
  选这六个的理由：覆盖 JD 里最高频的六句话

完整跑通 2 周
  八层从上到下，每层挑 3–5 个

专项深挖
  只挑某一层，比如"负载均衡"的 E14–E18 五个实验连做
```

## ⑤ 这份文档最容易被忽略的一节

第 6 节：**"哪些东西这三台机器永远证不了"**。

```
├─ PFC 的真实收益（没有交换机）
├─ 线速与绝对带宽（共享 eth0）
├─ 真 NCCL 性能（没有 GPU）
└─ 芯片级 DLB/GLB 行为
```

为什么把它放在体系文档里，而不是放在报告末尾？

```
因为它是"选实验"的前置约束，不是"结论"的免责声明。
一开始就知道哪些证不了，才不会设计出一个注定失败的实验。
```

## ⑥ 一句话记住这一篇

**先读 JD 提炼能力域，再用八层结构排布实验，最后用五个标签标出
"能真做 / 只能近似 / 做不了"——这张地图的价值在于告诉你缺哪块，不是告诉你做了多少。**
