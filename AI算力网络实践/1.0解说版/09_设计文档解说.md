# 09 · 设计文档解说（docs/01-设计.md）

> 对应文件：`docs/01-设计.md`

这份文档回答一个问题：**为什么这么设计，而不是那么设计。**
它是整套资料的"宪法"——后面所有脚本和实验，都是这份文档的推论。

---

## ① 它的结构（八节，一条因果链）

```
1  三个硬约束 → 三个设计决定        ← 骨架
2  为什么必须 uSID，不是标准 SRv6   ← 最关键的一次取舍
3  三台机器的真实物理路径           ← 落地
4  地址与 SID 规划                  ← 编码
5  一个包的一生（照着抓包对）       ← 把抽象变成可见
6  能证明什么 / 不能证明什么        ← 边界
7  每个脚本动作 ↔ 真实 HPN 机制     ← 别为了跑通而跑通
8  若 End.DT6 table 255 装不上       ← 唯一的不确定点与备选
```

---

## ② 第 1 节：三个硬约束推出三个决定

这是整份文档最值得学的一段写法——**先摆约束，再推决定**。

```
约束一  云 vSwitch 会剥 SRH（很多实现不支持，遇到就丢）
        → 决定一：不用 SRH，改用 uSID，把路径编码进 DA

约束二  veth / 云网络会限速、会丢包、会做源地址校验
        → 决定二：不用 netns 单机模拟，用三台真机（否则测不出云的真实行为）

约束三  单网卡上 tc 挂 root 会打断 SSH
        → 决定三：故障注入走 prio 分带 + u32 过滤，只打实验流量
```

为什么这种写法重要？因为它把"我选择这样做"变成了
"**在给定约束下，只能这样做**"。前者是偏好，后者是论证。

面试里被问"为什么用 uSID 不用 SRv6"，照第三节回答就行。
被问"为什么不用 netns 更省钱"，照约束二回答。

---

## ③ 第 2 节：uSID vs 标准 SRv6 的那笔账

```
标准 SRv6：外层 IPv6(40) + SRH(8 + 16×N)
  4 跳路径：40 + 8 + 64 = 112 字节额外开销
  64 字节载荷的有效载荷率 = 64 / (64+112) ≈ 36%

uSID：外层 IPv6(40)，段全在 DA 里，无 SRH
  4 跳路径：40 字节额外开销
  64 字节载荷的有效载荷率 = 64 / (64+40) ≈ 57%
```

一个 1.6 倍的差距。**而且小包是 AI 网络的常态**（MoE 的 AlltoAll 全是小包），
所以这不是"优化一下"，是能不能用。

再叠加云的现实：SRH 会被剥，uSID 没有 SRH 可剥。

```
结论：选 uSID 不是因为它更先进，是因为它是唯一"既不撑爆 MTU、
      又不被云剥掉"的方案。
```

## ④ 第 3、4 节：物理路径与编码

```
a → b 直达          = 平面 1
a → c（弹栈）→ b    = 平面 0

地址规划
  block   fcbb:bb00::/32
  平面 0  fcbb:bb00:2::/48       → c
  平面 1  fcbb:bb00:e000::/48    → b
  探针    fcbb:bb00:ffff::/48    → c
  业务    fd00:b0b0::1（b 的 dummy 口 svc0）
```

一个 DA 长这样：`fcbb:bb00:2:e000::`

```
fcbb:bb00   block（32 bit）
2           第一个节点（c 的编号，16 bit）
e000        下一个节点（b 的编号，16 bit）
::          剩余
```

c 收到后弹掉自己那 16 bit，DA 变成 `fcbb:bb00:e000::`，按路由继续送。
**路径就是 DA 里的字节，不需要任何控制面协议。**

## ⑤ 第 5 节：一个包的一生（这一节最值得反复读）

它把"封装"这个抽象，拆成了三次变换 + 三个抓包点：

```
① a 发出            内层 fd00:b0b0::1，外层被 encap 成 fcbb:bb00:2:e000::
   抓包点①          两层 IP6 头，DA = fcbb:bb00:2:e000::

② c 收到并弹栈      DA 左移 16 bit → fcbb:bb00:e000::
   抓包点②          同一微秒区间内，进 c 的 DA 和出 c 的 DA 不一样
                    实测：11:17:27.674951 → .674983，相隔 32 微秒

③ b 收到并解封装    剥掉外层，内层包按本地地址投递
   抓包点③          只剩内层 fd00:b0b0::1
```

**这一节的价值在于：它让"能不能算出证据"变成了"去哪个位置抓什么包"。**
不写这一节，抓包就是碰运气；写了，抓包就是验证。

---

## ⑥ 第 6 节：边界（和结论同等重要）

```
能证明
  ├─ 路径由端侧决定（同一目的，不同 mark 走不同 DA）
  ├─ uSID 逐跳弹栈（抓包可见 DA 位移）
  ├─ 零 SRH（抓包里 SRH 计数为 0）
  └─ 故障域隔离（打挂 c 只影响平面 0）

不能证明
  ├─ 线速（共享 eth0 + 软转发）
  ├─ PFC 的收益（没有交换机）
  ├─ 真 NCCL 性能（没有 GPU）
  └─ 芯片级 DLB/GLB（碰不到）
```

## ⑦ 第 7 节：脚本动作 ↔ 真实机制（防止"为了跑通而跑通"）

这一节是一张对照表，意思是：**每一条命令都必须对应一个真实的 HPN 机制，
不能有"为了让实验跑起来"的凑数命令。**

```
ip -6 route ... encap seg6local action End flavors next-csid
  ↔ 交换机芯片的 uSID 弹栈（Broadcom/Jericho 的 End 行为）

ip -6 rule add fwmark 0x2 table 100
  ↔ MRC 的 EV 表（每个 EV 指向一条确定的物理路径）

tc qdisc ... netem loss
  ↔ 链路误码 / 拥塞溢出丢包

tc filter ... u32 match ip6 priority
  ↔ 交换机 QoS 的 DSCP→队列映射
```

这条纪律很值得记：**如果一个动作在真实系统里找不到对应物，
那它测出来的东西也没法迁移到真实系统。**

---

## ⑧ 第 8 节：唯一的不确定点与备选

```
不确定    End.DT6 table 255 在某些内核上装不上
备选      用 VRF（标准 L3VPN 那套）：
          ip link add vrf10 type vrf table 10
          然后把 DT6 指向这张表
```

写这一节的意义不是"给个退路"，而是**明确标出"这套东西里哪一步我不确定"**。
一个诚实的设计文档，一定有一个"这里可能不行"的段落。

---

## ⑨ 一句话记住这一篇

**三个约束推出三个决定，一次取舍（uSID）解释了全部开销，
一个包的一生把抽象变成抓包点，一节边界把话说死——
这份文档的作用是让后面每一条命令都有出处。**
