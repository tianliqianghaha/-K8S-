## 四、常见故障自查表

```
症状：公网请求 401
判断：API Key 不对或缺 Authorization 头。gateway 正常，只是鉴权拦住了。

症状：公网请求 503 或连接被拒
判断：Envoy Gateway 或 ai-gateway Pod 没起来。
      先看 kubectl -n ai get pods，再看 kubectl -n envoy-gateway-system get pods。

症状：/health 里 agents 为 0
判断：本地 Agent 掉线。看 journalctl -u ai-agent -n 20，通常是网络或证书问题。

症状：请求一直挂着不出字
判断：任务进了队列但没有 Agent 接手，或 vLLM 卡住。
      看 /health 的 queued 数、本地 vLLM 的 health、显存是否异常。

症状：显存从 17.7G 掉到 300M
判断：vLLM 进程被杀了。查 journalctl -u vllm 末尾，常见是收到了终止信号。

症状：kubectl 突然全部 connection refused
判断：控制面假死。第一件事看 etcd 日志里的"请求耗时过长"和压缩耗时，
      不要看 CPU 和内存。处置见第 6 章第 28 条。

症状：GPU Pod 一直 Pending
判断：分两种。配额层拒绝是 Forbidden（对象都没建）；调度失败是 Pending（Insufficient）。
      先看 Events 的原文，别猜。

症状：GPU Pod ContainerCreating 卡住
判断：本地节点没有 CNI。检查 Pod 有没有 hostNetwork。

症状：GPU Pod StartError
判断：缺 runtimeClassName: nvidia。

症状：kubectl logs 到本地节点超时
判断：已知限制，节点宣告的是 NAT 地址，云端访问不到 10250。
      改用 hostPath 把结果写出来再本地读。
```

## 五、重启与恢复

```bash
# 本地推理栈（按顺序）
sudo systemctl restart vllm          # 约 150 秒就绪
sudo systemctl restart ai-agent      # 约 5 秒连上

# 只重启 Agent（不影响推理）
sudo systemctl restart ai-agent

# 云端 gateway
kubectl -n ai rollout restart deploy/ai-gateway    # 约 30 秒（要重装 pip 依赖）

# WSL 整体重启后的顺序
wsl --shutdown
# 重新拉起后：systemd 自动起 vllm/ai-agent/exporter，
# 等 150 秒，确认 /health 返回 200，再看 gateway 的 agents
```

## 七、停止与释放（2026-11-22 21:40 已执行）

按这个顺序停，顺序错了会有残留（隧道会一直重连已释放的云端）。

```bash
# 1. 本地五个服务先停再禁用
sudo systemctl stop vllm ai-agent vllm-tunnel gpu-exporter gpu-exporter-tunnel
sudo systemctl disable vllm ai-agent vllm-tunnel gpu-exporter gpu-exporter-tunnel

# 2. 确认显存释放、容器清掉
nvidia-smi --query-gpu=memory.used --format=csv,noheader     # 应回 270MiB 左右
sudo ctr -n k8s.io task ls | grep vllm                        # 应无输出

# 3. 删保活计划任务（Windows PowerShell）
schtasks /delete /tn "WSL-KeepAlive" /f

# 4. 关闭 WSL
wsl --shutdown

# 5. 释放云端实例（抢占实例删除即释放，不再计费）
python3 release-ecs.py        # DeleteInstance + Force，随后确认地域内实例数为 0
```

执行后确认：

```
wsl --list --running      → 没有正在运行的分发
地域实例数                → 0
显存                      → 270 MiB
```

安全组入站规则（6443 / 10250 / 8000 / 31154）**保留不删**：
不产生费用，且是共享安全组，下次重建直接复用。

## 八、重新启用（下次要用时照这个做）

```bash
# 1. 云端：按第 2 章重开 4C8G，重新 kubeadm 或从快照恢复
# 2. 本地：WSL 启动后把五个服务打开
sudo systemctl enable --now vllm gpu-exporter
# 等 vLLM /health 返回 200（约 150 秒）
sudo systemctl enable --now gpu-exporter-tunnel vllm-tunnel
sudo systemctl enable --now ai-agent

# 3. 恢复常驻客户端（否则命令一结束发行版就被终止）
schtasks /create /tn "WSL-KeepAlive" /sc minute /mo 1 `
  /tr "C:\Windows\System32\wsl.exe -d Ubuntu-24.04 -u root --exec sleep 86400" /f
schtasks /run /tn "WSL-KeepAlive"

# 4. 验证
systemctl is-active vllm ai-agent gpu-exporter
curl -sk https://<新公网IP>:31154/health        # agents 应为 1
```

注意：`vllm-tunnel` 与 `gpu-exporter-tunnel` 里的目标 IP 写死在单元文件里，
换机器后要改 `/etc/systemd/system/*-tunnel.service` 里的地址。

## 九、从零重建的最短路径

```
1. Windows 侧：启用两个功能 → 关快速启动 → 重启 → 确认 Hypervisor Present
2. 装 WSL 平台（镜像代理）+ 导入 Ubuntu（Canonical 镜像）
3. .wslconfig 分配 11G/8核 → 建用户 → 开 systemd → 设常驻客户端
4. 跑 02_wsl-init.sh：GPU 工具链 + containerd 双 runtime + kubelet
5. 三道闸门验收（systemd / 宿主 GPU / 容器内 GPU）
6. 云端开 4C8G → kubeadm → 去控制面污点 → Cilium → device plugin
7. 本地 kubeadm join → 打 GPU taint → 确认 allocatable=1
8. 按第 3 章部署：Envoy Gateway → 证书 → gateway → vLLM → Agent
9. 按第 4 章验证资源语义（记得先腾卡，做完恢复）
10. 按第 5 章装治理平面（监控必须按本文参数调，否则 etcd 会被压死）
```

第 8 步之后每一步都有明确验收点，不通过就不要往下走。
