# 06 · 经验与陷阱

> 这里只记经验和判断方法，不记错误命令。
> 每一条都是实际踩过并解决的，按发生层次分组。
> 遇到类似现象时先查这里，能省掉大部分排查时间。

---

## 一、Windows 与 WSL 层

### 1. 「重启」可能没有真的重启

**现象**：启用了 WSL 相关功能，重启后状态仍是未生效，系统运行时间还是旧的几十小时。
**根因**：Windows 快速启动会恢复内核会话，DISM 的收尾工作没有执行，hypervisor 没有被拉起。
**正解**：关掉快速启动，并确认重启方式是"重启"而不是"关机再开"。判断依据看系统运行时间是否归零、
以及 Hypervisor 是否处于 Present。

### 2. 国内环境装 WSL 的两条路都可能断

**现象**：应用商店里找不到 WSL 平台包；命令行安装又会去 GitHub 读取发行版清单，直接超时。
**根因**：中国区商店不提供该平台包；发行版清单托管在 GitHub 的 raw 域名上。
**正解**：走镜像代理下平台包，再用管理员权限注册；发行版从 Canonical 的镜像站下 `.wsl` 格式直接导入。
这条路比商店更稳，而且 `.wsl` 是官方支持的格式，不比商店安装低一档。

### 3. 平台包注册必须管理员

**现象**：普通权限注册报一个 0x80073D28 的错误码。
**根因**：这个包内嵌了 Windows 服务组件，注册打包服务需要管理员令牌。
**正解**：以管理员身份执行注册。这一步没有绕过方式。

### 4. 会话一结束，服务就"自己死掉"

**现象**：vLLM 明明已经加载完模型、健康检查返回 200，只要命令一结束，显存瞬间从 20G 掉到 300M，
日志里是收到 SIGTERM 后的优雅退出。
**根因**：WSL 在最后一个客户端断开后会终止整个发行版，systemd 随之停掉所有 unit。
**正解**：制造一个长期不退出的客户端连接（例如一个持续 24 小时的睡眠进程），让发行版始终有客户端挂着。
注意：配置文件里的空闲超时参数不足以解决这个问题，实测无效。

### 5. WSL 的 GPU 通道不需要装 CUDA

**现象**：容器里看不到卡时，第一反应是去容器里装 CUDA toolkit。
**根因**：WSL 的 GPU 能力由 Windows 驱动提供，通过一个特殊设备节点直通，与容器内是否装 CUDA 无关。
**正解**：检查的是 Windows 侧驱动版本、以及容器运行时有没有把设备节点注入进去。
在 WSL 里反复装 CUDA toolkit 是白费功夫。

### 6. 显卡驱动版本是新版推理框架的硬门槛

**现象**：vLLM 启动即退出，报驱动太旧，附带的版本号是 12060（即 CUDA 12.6）。
**根因**：新版 PyTorch 用 CUDA 12.8+ 编译，要求驱动 570 以上；560 跑不动。
**正解**：升级 Windows 驱动并重启，再重启 WSL。这是唯一解，换旧版框架只是把问题往后拖。

## 二、脚本与编码层

### 7. PowerShell 读中文脚本会乱码

**现象**：脚本本身没问题，但一执行就报"缺少右括号"之类的语法错误。
**根因**：Windows PowerShell 5.1 对无 BOM 的 UTF-8 文件按本地代码页解析，中文注释被撕碎。
**正解**：脚本统一存成带 BOM 的 UTF-8。

### 8. 批处理文件里不要出现中文

**现象**：双击 bat 后，窗口里全是"'ocal"' 不是内部或外部命令"这类碎片，命令被截断。
**根因**：代码页切换与文件编码不一致，中文被打碎后连带把后面的命令行也切了。
**正解**：bat 保持纯 ASCII，路径用脚本自身所在目录的相对写法，不要写死含中文的绝对路径。

### 9. 命令行的引号会被吞掉

**现象**：用命令行直接发带 JSON 的请求，服务端报 JSON 解析错误，而同样的内容在 Linux 里没问题。
**根因**：Windows 命令行对引号的转义规则与 bash 不同。
**正解**：把请求体写进文件，用从文件读取的方式提交。

## 三、容器运行时层

### 10. 新版本 containerd 的配置路径变了，工具会"静默成功"

**现象**：NVIDIA 的配置工具报告成功，但配置文件里一个字都没写进去，CRI 插件也起不来。
**根因**：containerd 2.x 把 CRI 配置从旧的插件路径挪到了新的运行时路径下，工具版本没跟上。
**正解**：手工按新路径补运行时配置。判断方法：改完必须能读到这一段，且 CRI 插件状态是 ok。

### 11. 镜像加速的写法有讲究

**现象**：在配置里加镜像源之后，CRI 插件直接报错，整个容器服务不可用。
**根因**：新版本 containerd 不允许"证书目录"和"镜像源列表"同时设置，冲突会让插件加载失败。
**正解**：只走镜像源的独立配置目录方式，不要动主配置文件里的镜像段。

### 12. 容器的启动命令必须写全

**现象**：容器创建失败，报某个参数名"不是可执行文件"。
**根因**：命令行工具的语法是"镜像 容器名 命令 参数…"，容器名之后的第一个词会被当成命令，
镜像自带的入口点不会自动生效。
**正解**：把完整命令和参数都显式写出来。

### 13. 某些命令行参数在旧版本里不存在

**现象**：服务起不来，报"未知参数"，而同样的参数在文档里存在。
**根因**：本地工具版本比文档旧，不认这个参数。
**正解**：去掉该参数，把等价的限制交给 systemd 单元去设。

### 14. 容器里统一用 hostNetwork 会带来端口冲突

**现象**：两个副本都起来，但只有一个能监听端口。
**根因**：hostNetwork 下所有 Pod 共享宿主网络命名空间。
**正解**：要么给不同端口，要么接受"同一时间只有一个副本真正提供服务"。

## 四、K8S 与调度层

### 15. 单节点集群第一步要去掉控制面污点

**现象**：某个组件（证书生成、监控）永远 Pending，事件里写"没有节点能容忍污点"。
**根因**：控制面节点默认带有不允许普通负载调度的污点，单节点集群里没有别的节点可去。
**正解**：装任何业务组件之前先去掉这个污点。

### 16. Gateway API 的控制器不会自动建 GatewayClass

**现象**：控制器日志反复打"没有已接受的 GatewayClass"，Gateway 一直是未编程状态。
**根因**：较新版本的 chart 把这一职责交给了使用者，不再自动创建。
**正解**：手动建一个指向该控制器名的 GatewayClass。

### 17. 自定义资源的 API 组名容易记错

**现象**：应用自定义资源时报"找不到这个 kind"。
**根因**：组名是网关自身的域名，不是带 config 前缀的那个。
**正解**：以集群里实际注册的 CRD 组名为准，不要凭记忆写。

### 18. 没有 CNI 的节点上，普通 Pod 建不出网络

**现象**：Pod 卡在容器创建阶段，事件里写"建立 sandbox 网络失败"。
**根因**：这个节点刻意没有装 CNI，Pod 拿不到网络命名空间。
**正解**：这类节点上的工作负载一律用宿主网络。
代价是 Pod 拿不到集群内 IP，但单卡单实例本来也不需要。

### 19. 只有宿主网络还不够，GPU 需要专门的运行时类

**现象**：加了宿主网络后容器能创建，但启动即失败，连显卡工具都执行不到。
**根因**：默认运行时不会把 GPU 设备节点和驱动库注入容器。
**正解**：显式指定 GPU 的运行时类。

### 20. 打污点挡不住 DaemonSet

**现象**：给 GPU 节点打了污点，本以为能把某个 DaemonSet 挡在外面，结果它照样调度过去。
**根因**：DaemonSet 通常带有"容忍所有污点"的配置，污点对它无效。
**正解**：用节点亲和性明确排除，而不是靠污点。

### 21. 时间切片是超卖，不是分享

**现象**：把 GPU 的副本数从 1 改成 4 之后，四个 Pod 都声明 1 卡，全部调度成功并同时加载模型，
显存一路涨到接近物理上限。
**根因**：时间切片只是让调度器"以为"有 4 张卡，底层没有任何隔离。
**正解**：理解成"共享同一份资源，谁抢到算谁的"。要隔离必须用 MIG 或干脆排队。
**这条最反直觉**：预期会出现 OOM 被杀的明确信号，实际是两个进程各自缩小份额勉强共存，
代价是整卡被吃满、任何一个再要一点就会崩。

### 22. 节点会"假死"又自己回来，别急着重建

**现象**：Pod 显示运行中，但容器里的进程早就退出了；或者节点先是不可用、过一会儿又好了。
**根因**：kubelet 在 WSL 上会因为运行时套接字丢失而反复重启，每次重启都会给容器发终止信号。
**正解**：先确认运行时套接字是否存在、kubelet 是否在稳定运行，再判断 Pod 状态是否可信。
这类抖动在 WSL 上无法根治，所以关键服务不放 K8S。

### 23. 配额拒绝和调度失败是两回事

**现象**：同样是"起不来"，有的报 Forbidden，有的报 Pending。
**根因**：配额在 API 层就拒绝创建；调度失败是对象建好了但没有节点能满足资源。
**正解**：看报错类型判断是"配额不够"还是"卡不够"，两者处理方式完全不同。
再往下一层还有 OOM 被杀，那是"给了但用超了"，三者不要混。

## 五、网络与入口层

### 25. 云主机访问自己的公网 IP 会超时

**现象**：在云主机内部请求自己的公网地址没反应，从外部请求正常。
**根因**：云平台不支持这种"自己绕出去再回来"的访问方式。
**正解**：内部验证一律走回环地址或私网 IP，公网验证必须从外部发起。

### 26. 自签证书在客户端侧必须显式跳过校验

**现象**：Agent 一直连不上，健康检查里连接数为 0，也没有明显报错。
**根因**：WebSocket 客户端默认校验证书，自签必然失败。
**正解**：实验环境显式关闭主机名校验与证书校验；生产环境换成挂载真实 CA。

### 27. 反向隧道进程自己也需要被托管

**现象**：隧道断开后不会自己恢复，公网访问一直失败。
**根因**：隧道是普通进程，没人管它。
**正解**：和业务服务一样用 systemd 托管，并打开保持连接与断线重试的选项。

## 六、监控与观测层

### 28. 监控会把低配云盘上的控制面拖死（本次最大的坑）

**现象**：装完监控一段时间后，所有命令行操作全部"连接被拒"，但服务器内存还剩 3G、CPU 97% 空闲，
看起来一切正常。
**根因**：入门档云盘的 IOPS 有限，监控默认抓十几个目标、每 15 秒一次，
时序数据库的写入把磁盘 IOPS 吃满；etcd 的落盘操作被拖到几十秒，
线性化读超时，API Server 健康检查失败，整个控制面就假死了。
**判断依据**：不要看 CPU 和内存，要看 etcd 日志里的"请求耗时过长"和"压缩耗时"。
正常压缩是毫秒级，出问题时是分钟级（实测出现过 3 分 55 秒）。
**正解**：监控必须当作"需要调参才能用"的组件——关掉无关抓取目标、拉长抓取间隔、
限制内存上限，只保留真正要看的指标。

### 29. vmstat 的列很容器看错

**提醒**：最后几列的用户态/系统态/空闲/IO 等待，倒数第二列才是空闲。
容易把"空闲 89%"看成"IO 等待 91%"，方向完全相反。

### 30. 容器指标在 WSL 上要用替代方案

**现象**：官方的 GPU 监控组件起不来。
**根因**：它依赖一套在 WSL 里不存在的设备访问方式。
**正解**：用轮询式导出替代，指标定义保持一致，数值是真的，只是采样粒度粗。

### 31. systemd 单元的 PATH 很短

**现象**：手动能跑，做成服务就报"文件不存在"。
**根因**：WSL 把 NVIDIA 工具放在一个非标准路径下，systemd 的默认 PATH 里没有。
**正解**：在单元里显式补 PATH，或在代码里解析成绝对路径。

## 七、发布与回滚层

### 32. 分析模板的失败必须体现为"非零退出"

**现象**：注入了明显错误的版本，金丝雀分析却判定成功，坏版本被全量发布。
**根因**：分析用的检测脚本以 0 退出，平台只判断"Job 是否跑完"，不判断输出内容。
**正解**：检测逻辑不达标时必须非零退出，让平台看到"这一步失败了"。

### 33. 命令行工具不认识自定义资源

**现象**：改镜像这类操作报"这个 kind 没有注册"。
**根因**：命令行工具内置的类型表里没有自定义资源。
**正解**：用通用的补丁方式直接改字段。

### 34. 混沌实验的方向参数有约束

**现象**：创建网络延迟实验被准入拦截。
**根因**：双向延迟必须同时指定目标对象，否则不知道对谁生效。
**正解**：先用单向，或者把目标写全。

## 八、几条方法论

### 35. 先证明链路通，再优化性能

三个实验的顺序不是随便排的：先应用层打通（变量最少），再上调度语义，最后加治理。
每一步只引入一类新变量，出问题时范围是可控的。

### 36. 每加一个组件，先问它吃多少内存和 IOPS

这台机器上所有事故都来自资源耗尽，而不是配置写错。
装之前先算账，装之后立刻看 etcd 的耗时指标。

### 37. 不可靠的底座上，把关键服务挪出依赖链

kubelet 在 WSL 上会反复重启，这是底座问题。
推理服务因此放在 systemd，K8S 只负责"谁有资格用卡"。这不是妥协，是分层。

### 38. 回滚路径要在动手前就写好

时间切片、监控调参、Rollout 演示，每一步都先想清楚怎么退。
实测中回滚救回来两次（显存打满、控制面假死）。

### 39. 成本类组件对指标完整性极其敏感

**现象**：成本看板部署正常、接口有响应，但所有数值都是 0，日志里刷"没有找到价格"。
**根因**：这类组件算的是"分配"（资源申请量）而不是"实际用量"，
它依赖资源申请量这一族指标；而为了保控制面精简抓取时，最容易被剔掉的正是它们。
**正解**：装成本组件之前，先确认它需要哪几个指标名；
精简抓取时按白名单保留这些指标，间隔可以放长（120 秒足够），但一个都不能少。

### 40. 同一个问题，判断依据要选对

这次遇到两次"看起来一切正常但服务不可用"：
一次是显存打满前的平静（内存与 CPU 指标都很好看），
一次是 etcd 被拖死（CPU 97% 空闲）。
两次都说明：**选错指标就等于没有监控**。
GPU 负载看显存与温度，控制面健康看 etcd 的落盘耗时，不要用 CPU 和内存当万能判据。
