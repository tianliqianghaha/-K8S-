# 05 · 第 5 章 实验三：治理平面（排队才是主角）

> 本章目标：数据平面完全复用前两章，只加「治理平面」——把"能跑"变成"能管"。
> 前置条件：第 3 章的服务在跑、第 4 章的 GPU 资源已恢复为 1 卡。
> 警告：本章组件多，云端 8G 内存与 100G 低档云盘都会被压到边缘，必须按本文的参数装。

### 3.2 GPU 指标：自建 exporter（DCGM 在 WSL 起不来）

源码 `scripts/app/exporter/gpu_exporter.py`，暴露 `:9101/metrics`：

```
gpu_memory_used_bytes / gpu_memory_total_bytes
gpu_utilization_percent / gpu_temperature_celsius / gpu_power_watts
```

```bash
mkdir -p /home/k8s/exporter
cp scripts/app/exporter/gpu_exporter.py /home/k8s/exporter/

sudo tee /etc/systemd/system/gpu-exporter.service > /dev/null <<'UNIT'
[Unit]
Description=GPU metrics exporter (nvidia-smi based)
After=network-online.target

[Service]
Type=simple
User=k8s
WorkingDirectory=/home/k8s/exporter
Environment=PATH=/usr/lib/wsl/lib:/usr/local/bin:/usr/bin:/bin
ExecStart=/usr/bin/python3 -u /home/k8s/exporter/gpu_exporter.py
Restart=always
TimeoutStartSec=0
UNIT

sudo systemctl daemon-reload && sudo systemctl enable --now gpu-exporter
curl -s http://127.0.0.1:9101/metrics | head
```

`Environment=PATH=/usr/lib/wsl/lib:...` 是必须的：WSL 的 nvidia-smi 在这个路径下，
systemd 默认 PATH 找不到。

再把 9101 通过反向隧道暴露到云端：

```bash
sudo tee /etc/systemd/system/gpu-exporter-tunnel.service > /dev/null <<'UNIT'
[Unit]
Description=Reverse tunnel: gpu-exporter 9101 -> cloud
After=network-online.target gpu-exporter.service

[Service]
Type=simple
Restart=always
RestartSec=10
TimeoutStartSec=0
ExecStart=/usr/bin/ssh -N -i /home/k8s/.ssh/id_ed25519 -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -o LogLevel=ERROR -o ServerAliveInterval=20 -o ExitOnForwardFailure=yes -R 9101:127.0.0.1:9101 root@47.238.160.73
UNIT

sudo systemctl daemon-reload && sudo systemctl enable --now gpu-exporter-tunnel
```

## 四、chaos：注入延迟

```bash
helm repo add chaos-mesh https://charts.chaos-mesh.org
helm install chaos-mesh chaos-mesh/chaos-mesh -n chaos-mesh --create-namespace \
  --set chaosDaemon.runtime=containerd \
  --set chaosDaemon.socketPath=/run/containerd/containerd.sock \
  --set dashboard.create=false \
  --version 2.7.2 --wait --timeout 6m

kubectl apply -f - <<'YAML'
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata: {name: gateway-delay, namespace: ai}
spec:
  action: delay
  mode: all
  selector:
    namespaces: [ai]
    labelSelectors: {app: ai-gateway}
  delay: {latency: "300ms", correlation: "100", jitter: "20ms"}
  direction: to
  duration: "5m"
YAML
```

注意：`direction` 只能是 `to` 或 `from`；写 `both` 会要求同时指定 `targets`，否则 webhook 拒绝。

测首字延迟变化：

```bash
for i in 1 2 3 4 5; do
  curl -skN -o /dev/null -X POST https://47.238.160.73:31154/v1/chat/completions \
    -H "Authorization: Bearer sk-ai-pool-2026" -H "Content-Type: application/json" \
    -d '{"model":"qwen","messages":[{"role":"user","content":"一句话说明网络延迟"}],"max_tokens":40,"stream":true}' \
    -w "TTFT=%{time_starttransfer}s\n"
done
```

实测：

```
基线        0.132 / 0.152 / 0.138 / 0.131 / 0.162
+300ms      0.719 / 0.436 / 0.730 / 0.425 / 0.451
撤销后      0.121 / 0.134 / 0.141 / 0.163 / 0.122
```

抬升约 0.30-0.35s，与注入值吻合。**延迟伤的是首 token，不是生成速率。**


### 6.1 两个版本的 nginx（好 / 坏）

```bash
kubectl apply -f - <<'YAML'
apiVersion: v1
kind: ConfigMap
metadata: {name: nginx-good, namespace: ai}
data:
  default.conf: |
    server { listen 80; location / { return 200 "v1-ok\n"; } }
---
apiVersion: v1
kind: ConfigMap
metadata: {name: nginx-bad, namespace: ai}
data:
  default.conf: |
    server { listen 80; location / { return 500 "injected-failure\n"; } }
---
apiVersion: v1
kind: Service
metadata: {name: demo-canary, namespace: ai}
spec:
  selector: {app: demo-canary}
  ports: [{port: 80, targetPort: 80}]
YAML
```

### 6.2 分析模板（关键：失败必须非零退出）

```bash
kubectl apply -f - <<'YAML'
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: {name: http-success-rate, namespace: ai}
spec:
  metrics:
  - name: success-rate
    interval: 15s
    count: 3
    failureLimit: 1
    successCondition: result[0] >= 9
    failureCondition: result[0] < 9
    provider:
      job:
        spec:
          backoffLimit: 0
          template:
            spec:
              restartPolicy: Never
              containers:
              - name: check
                image: docker.io/library/nginx:alpine
                command:
                - sh
                - -c
                - |
                  ok=0
                  for i in $(seq 1 10); do
                    code=$(wget -qO- -T 3 -S http://demo-canary.ai.svc.cluster.local/ 2>&1 | grep -o 'HTTP/1.1 [0-9]*' | head -1 | awk '{print $2}')
                    [ "$code" = "200" ] && ok=$((ok+1))
                  done
                  echo $ok
                  if [ "$ok" -lt 9 ]; then
                    echo "FAIL: only $ok/10 succeeded" >&2
                    exit 1
                  fi
YAML
```

**`exit 1` 是这段的灵魂**：Argo 只判断 Job 是否成功退出，
如果脚本永远 `exit 0`，它会认为"跑完了就是通过"，坏版本会被放行。

### 6.3 Rollout 与演示

```bash
kubectl -n ai apply -f - <<'YAML'
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: {name: demo-canary, namespace: ai}
spec:
  replicas: 4
  selector: {matchLabels: {app: demo-canary}}
  strategy:
    canary:
      steps:
      - setWeight: 25
      - analysis: {templates: [{templateName: http-success-rate}]}
      - setWeight: 100
  template:
    metadata: {labels: {app: demo-canary}}
    spec:
      containers:
      - name: app
        image: docker.io/library/nginx:alpine
        ports: [{containerPort: 80}]
        volumeMounts: [{name: conf, mountPath: /etc/nginx/conf.d}]
      volumes: [{name: conf, configMap: {name: nginx-good}}]
YAML

# 触发坏版本（不能改镜像，kubectl set image 不认识 Rollout CRD，用 patch 改 volume）
kubectl -n ai patch rollout demo-canary --type=json \
  -p '[{"op":"replace","path":"/spec/template/spec/volumes/0/configMap/name","value":"nginx-bad"}]'
```

预期（约 30 秒内）：

```
phase=Progressing → Degraded
message: RolloutAborted: Rollout aborted update to revision 2
AnalysisRun demo-canary-xxx-2-1   Failed

回滚后 4 个 Pod 全部 nginx-good，实测响应 "v1-ok"
```

正常版本的金丝雀分步推进（25% → 50% → 100%）用 `setWeight` + `pause` 即可，
事件流会显示 `Scaled up revision 2 from 0 to 1`、`Scaled down revision 1 from 4 to 3` 这样的交替。

```bash
helm repo add opencost https://opencost.github.io/opencost-helm-chart
helm install opencost opencost/opencost -n opencost --create-namespace \
  --set opencost.exporter.defaultClusterId=ai-pool \
  --set opencost.ui.enabled=true \
  --set opencost.prometheus.internal.enabled=true \
  --set opencost.prometheus.internal.namespaceName=monitoring \
  --set opencost.prometheus.internal.serviceName=kube-prom-kube-prometheus-prometheus \
  --set opencost.prometheus.internal.port=9090 \
  --wait
```

给一套价格（否则全部为 0）：

```bash
kubectl -n opencost create configmap opencost-custom-pricing --from-literal=custom-pricing.json='{
  "provider":"custom","currencyCode":"CNY",
  "CPU":0.02,"RAM":0.004,"GPU":0.075,"storage":0.0001,
  "zoneNetworkEgress":0,"regionNetworkEgress":0,"internetNetworkEgress":0
}'

# 挂到 /models/custom-pricing.json
kubectl -n opencost get deploy opencost -o json | python3 -c "
import json,sys
d=json.load(sys.stdin)
c=d['spec']['template']['spec']['containers'][0]
c['volumeMounts']=c.get('volumeMounts',[])+[{'name':'cp','mountPath':'/models/custom-pricing.json','subPath':'custom-pricing.json'}]
d['spec']['template']['spec']['volumes']=d['spec']['template']['spec']['volumes']+[{'name':'cp','configMap':{'name':'opencost-custom-pricing'}}]
json.dump(d,open('/tmp/oc.json','w'))"
kubectl replace -f /tmp/oc.json
```

**前提**：OpenCost 算的是"分配"（request），必须有这两类指标：

```
container_cpu_usage_seconds_total / container_memory_working_set_bytes   （cAdvisor）
kube_pod_container_resource_requests / kube_pod_container_resource_limits （kube-state-metrics）
```

如果为了保控制面删掉了抓取，补一个精简版（间隔 120s，只留这几个指标）：

```bash
kubectl apply -f - <<'YAML'
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata: {name: kube-state-metrics-min, namespace: monitoring, labels: {release: kube-prom}}
spec:
  selector: {matchLabels: {app.kubernetes.io/name: kube-state-metrics}}
  endpoints:
  - port: http
    interval: 120s
    metricRelabelings:
    - action: keep
      sourceLabels: [__name__]
      regex: 'kube_(pod_status_ready|pod_info|node_status_ready|node_capacity|node_allocatable|pod_container_resource_requests|pod_container_resource_limits)'
YAML
```

查询：

```bash
kubectl -n opencost port-forward svc/opencost 9003:9003 &
curl -s 'http://127.0.0.1:9003/allocation/compute?window=3h&aggregate=namespace'
```

### 7.1 实测结论：部署通过，数值没算出来

```
部署      2/2 Running，能连上 Prometheus（PROMETHEUS_SERVER_ENDPOINT 正确）
价格      ConfigMap 已挂到 /models/custom-pricing.json
指标      container_cpu_usage_seconds_total 106 条
          container_memory_working_set_bytes 107 条
          kube_pod_status_ready 108 条
          kube_pod_container_resource_requests 43 条
接口      /allocation/compute 返回 {"code":200,"data":[{}]}

四次尝试（重装、改 internal.enabled、补 resource_requests、重启 Pod）均无数据
```

判断：机制是通的（接口有响应、指标在库里、价格已加载），缺的是 OpenCost 内部
指标聚合链路的某一环，本次没有继续深挖。要继续排查的话，方向是它的
`/allocation/heatmap` 与 exporter 日志里的 Prometheus 查询语句，
把那条查询单独拿到 Prometheus 里执行，看是"查不到"还是"查到了但聚合为 0"。

已知前提：OpenCost 算的是**分配**（request）而不是用量，
所以 `kube_pod_container_resource_requests` 必须存在，且 `namespace` 标签要完整——
这正是本环境为了保控制面而反复精简抓取目标时最容易丢的东西。

```
Argo 自动回滚       坏版本自动退回              ✅ AnalysisRun Failed → Aborted
OpenCost            按 namespace 出成本         ⚠️ 部署通过、接口可达，数值未算出
```

八项里七项完全达成，OpenCost 停在"机制通、数字没有"。
这一项不影响前七项的价值——成本分摊是"管理视角"的加分项，
而排队、配额、观测、弹性、回滚这些才是算力池能不能被信任的硬指标。
