## 二、Kueue：排队与配额（本实验的核心）

### 配置

```
ResourceFlavor   gpu-node，绑定 kubernetes.io/hostname=ai-gpu-1
ClusterQueue     gpu-cq，nominalQuota: nvidia.com/gpu = 1
LocalQueue       team-a（namespace ai）→ gpu-cq
                 team-b（namespace team-b）→ gpu-cq-b（配额 0）
```

### team-a：10 个 Job，只有 1 个能跑

```
ClusterQueue 视角
  gpu-cq    PENDING WORKLOADS = 9

Workload 视角
  job-infer-job-1    RESERVED IN gpu-cq   ADMITTED True     ← 唯一被准入的
  job-infer-job-2..10                                     ← 全部排队

Job 视角
  infer-job-1    SUSPEND false  ACTIVE 1
  infer-job-2..10  SUSPEND true
```

30 秒后（第一个 Job 的 sleep 25 结束）：

```
  gpu-cq    PENDING WORKLOADS = 8      ← 自动把下一个放进来
  已完成 1 个，infer-job-2 开始跑
```

这就是"排队然后交替获得"，不需要人工干预。

### team-b：配额 0，永远排不上

```
3 个 Job 全部 SUSPEND true
kubectl describe workload 的原话：

  couldn't assign flavors to pod set main:
  insufficient quota for nvidia.com/gpu in flavor gpu-node,
  request > maximum capacity (1 > 0)
```

`1 > 0` 这个数字对比，就是"部门抢不到卡"最直白的证据。

## 三、观测：一张外行能看懂的大盘

Grafana 里导入了 6 个面板（uid `alctnx`，标题「AI 算力池 · 一张图看懂」）：

```
左上：显卡在忙吗（利用率 %）        绿<70 / 橙<90 / 红>=90
上二：显存占了多少（GB）            阈值 20G 橙、23G 红
上三：排队的活儿（Kueue pending）
右上：温度 / 功耗

中左：同时有几个请求在跑 / 在等      vllm:num_requests_running / waiting
中右：首字延迟 P99 与 P50           histogram_quantile(vllm:time_to_first_token_seconds)
下左：GPU 利用率与显存的时间曲线
下右：prefix cache 命中率           省不省钱看这个
```

数据源：

```
gpu-exporter  172.23.163.98:9101    up，显存 17.7G/24G、利用率 4%、温度 26.6°C、功耗 24W
vllm-metrics  172.23.163.98:8000    up，547 个 vllm: / prefix_cache 指标
```

DCGM 为什么换掉：它需要 nv-hostengine 与特权设备访问，WSL2 只暴露 `/dev/dxg`，
DCGM 起不来。自建 exporter 用 nvidia-smi 轮询，数值是真的，只是采样粒度粗。

## 四、chaos：注入延迟，量首字延迟被抬高多少

```
基线（5 次）     TTFT 0.132 / 0.152 / 0.138 / 0.131 / 0.162
注入 300ms 后     TTFT 0.719 / 0.436 / 0.730 / 0.425 / 0.451
撤销后（5 次）    TTFT 0.121 / 0.134 / 0.141 / 0.163 / 0.122
```

NetworkChaos 状态 `AllInjected / Injected Count 1`，延迟真的生效。

抬升约 0.30-0.35s，与注入值吻合。**这条数据印证了原设计的判断：
延迟伤的是首 token，不是 token 生成速率。**
用户体感上就是"多等 0.3 秒才看到第一个字"，而生成过程并没有变慢。

踩到的坑：`direction: both` 会被 webhook 拒绝 ——
`from` 和 `both` 方向在 netem 动作里必须指定 targets，只能改成 `to`。

## 五、KEDA：扩出来，但拿不到卡

```
ScaledObject  infer-worker / min 0 / max 6
trigger       prometheus: sum(kueue_pending_workloads) > 1

观察结果
  t=0s    队列积压=1   worker 副本 0 → 1
  t=0s    队列积压=1   worker 副本 1 → 4
  t=0s    队列积压=0   worker 副本 4   Running=1  Pending=3

最终    4 个 Pod：1 个 Running，3 个 Pending
```

这就是原设计要求演示的"算力不足"正确形态：
不是 HPA 扩副本失败，而是**扩出来了、但被卡数硬性限制住**。
调度器的 Pending 原因就是 `Insufficient nvidia.com/gpu`。

真实云平台里看到的正是这个样子：负载上来了，副本数上去了，
但 GPU 利用率长时间 100%，队列一直有积压 —— 扩容解决不了物理卡数。

## 六、Argo Rollouts：金丝雀与分步推进

```
Rollout demo-canary，4 副本
steps: setWeight 25 → pause 25s → setWeight 50 → pause 25s → setWeight 100

触发：镜像 alpine → 1.25-alpine
观察
  t=6s    step=0  Progressing
  t=12s   step=1  Paused       25%（1/4 副本）
  t=30s   step=2  Paused
  t=36s   step=3  Paused       50%
  t=54s   step=4  Progressing
  t=60s   step=5  Healthy      100%

事件流
  Created ReplicaSet demo-canary-688946fb9d (revision 2)
  Scaled up ReplicaSet revision 2 from 0 to 1
  Scaled down ReplicaSet revision 1 from 4 to 3
  ... 最终 revision 2 = 4，revision 1 = 0
```

坑：`kubectl set image rollout/...` 会报
`no kind "Rollout" is registered for version "argoproj.io/v1alpha1"`。
kubectl 内置 scheme 不认识 CRD，必须用 `kubectl patch --type=json` 改镜像。

关于"注入 5% 错误率触发自动回滚"：这需要 AnalysisTemplate 查 Prometheus 的错误率，
而 gateway 目前只有计数没有错误率指标，所以只做了金丝雀分步推进，没做自动回滚。
这是本次的缺口，如实标注。

## 七、OpenCost：机制通，数字算不出来

```
部署     opencost 2.5.34，2/2 Running，能连 kube-prom 的 Prometheus
价格     写入 ConfigMap opencost-custom-pricing，CPU 0.02 / RAM 0.004 / GPU 0.075 元每时
结果     allocation 接口返回 {"code":200,"data":[{}]} —— 结构和机制在，数值全 0
```

原因不是配置错误，而是**我主动删掉了 kubelet 的 ServiceMonitor**（见第八节）。
OpenCost 靠 cAdvisor 的 `container_cpu_usage_seconds_total` 等指标算成本，
删掉之后它没有原料。

这是一个真实取舍：这台机器的 100G ESSD entry 盘扛不住全量监控写入，
控制面稳定性和成本报表精度只能二选一。我选了控制面。

要恢复的话，重新 apply kubelet 的 ServiceMonitor，并把抓取间隔放到 120s 以上。

## 八、本次最大的坑：监控把 etcd 压死，整个控制面失联

### 现象

```
20:53  KEDA 演示途中，kubectl 突然全部失败
       dial tcp 172.23.163.98:6443: connect: connection refused
       failed calling webhook "mjob.kb.io": no route to host
```

### 排查

```
apiserver 进程还在（22% CPU），但日志刷满：
  "event bookmark expired ... no events received for 50s"

etcd 日志说得很直接：
  "apply request took too long" took=15.000023099s expected-duration=100ms
  "[+]linearizable_read failed: context canceled" status-code=503
  "finished scheduled compaction" took="3m55.284703385s"    ← 正常应是毫秒级
```

### 根因

100G ESSD entry 是最低档云盘，IOPS 有限。
kube-prometheus-stack 默认抓十几个目标（apiserver / kubelet / coredns / kube-state-metrics /
node-exporter / operator …），15 秒一次，TSDB 写入把磁盘 IOPS 吃满。
etcd 的 fsync 依赖这块盘，写延迟从毫秒级涨到几十秒，线性化读超时，
apiserver 健康检查失败，整个控制面就"假死"了。

### 处置

```
① 立刻 scale Prometheus 到 0（止血）
② 删掉 8 个与 GPU 无关的 ServiceMonitor
   只留 gpu-exporter / vllm-metrics / kueue
③ scrapeInterval 15s → 60s，内存 limit 900Mi → 600Mi
④ 重新拉起，验证 kubectl 恢复、公网请求 200
```

处置后 etcd compaction 恢复正常，控制面稳定。

### 教训

```
① 低配云盘上跑 kube-prometheus-stack，默认配置一定会出问题
   把它当成"必须调参才能用"的组件，不要默认接受
② 监控和服务抢 IOPS 这件事，在真实生产里同样成立
   etcd 官方建议 fsync < 10ms，低档云盘单独跑 etcd 都不一定达标
③ 判断依据看 etcd 的 "apply request took too long" 和 compaction 耗时
   而不是看 CPU / 内存 —— 这次 CPU 97% idle，内存还剩 3G，看起来一切正常
```

## 十、踩到的坑汇总

```
① etcd 被监控写入压死（第八节，最重要）
② chaos 的 direction: both 需要指定 targets，否则 webhook 拒绝
③ kubectl set image 不支持 Rollout CRD，要用 patch --type=json
④ DCGM 在 WSL 起不来，要自建 exporter
⑤ nvidia-smi 在 WSL 的路径是 /usr/lib/wsl/lib/nvidia-smi
   systemd 的 PATH 里没有，exporter 要写绝对路径或在单元里补 PATH
⑥ node-exporter 默认调度到 GPU 节点，但那里没有 CNI，必须 nodeSelector 限制到控制面
⑦ kueue 的 webhook Service 在 Cilium 环境下偶发 no route to host
   影响新建带 kueue 队列标签的 Job，已存在的 Job 不受影响
```
