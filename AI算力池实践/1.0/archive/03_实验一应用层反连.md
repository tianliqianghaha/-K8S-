# 03 · 实验一：最小闭环（应用层反连）

> 时间：2026-11-22 19:24 起，20:24 收尾
> 目标：不用 kubelet，先用「云端 gateway + 本地 Agent + WebSocket 反连」把请求链路接起来，
>       拿到首字延迟与并发拐点的基线，并证明重启/断网时任务不丢。

---

## 一、这条链路长什么样

```
客户端 curl
  │  HTTPS + Bearer API Key
  ▼
Envoy Gateway（v1.10.0，GatewayClass eg，NodePort 31154，自签 TLS）
  │  纯转发，不做业务
  ▼
云端 ai-gateway（FastAPI / uvicorn，Deployment 1 副本，命名空间 ai）
  ├─ 鉴权      Authorization: Bearer / X-API-Key
  ├─ 限流      每 key 每分钟 60 次滑动窗口，超限 429 + Retry-After
  ├─ 幂等      Idempotency-Key 命中已完成任务直接回缓存
  ├─ 任务队列  内存任务表，queued → streaming → done
  └─ 派发      通过 /agent 的 WebSocket 推任务
  │  WSS 出站长连接（本地主动连云端，所以 NAT 后面也能被派活）
  ▼
本地 ai-agent（systemd 托管，Python asyncio + aiohttp + websockets）
  ├─ 收任务    调本地 vLLM 的流式接口
  ├─ 增量回传  每吐一个 token 发一个 chunk，不整段缓冲
  ├─ 幂等      已完成的 task_id 记住，重复派发直接回 done
  └─ 不丢任务  断线时保留 inflight，重连后 resume 上报
  │  HTTP 流式（SSE 逐行解析）
  ▼
本地 vLLM v0.34.0（Qwen2.5-7B-Instruct-AWQ，systemd 托管 ctr 容器）
```

为什么是反连：WSL 在本机 NAT 后面，没有固定可达地址。边缘节点主动连云端是标准做法，
这也是与实验二「kubelet 内核层注册」对照的关键差异。

## 二、代码与落盘位置

```
D:\AI算力池实践\1.0\scripts\app\gateway\main.py   374 行
D:\AI算力池实践\1.0\scripts\app\agent\main.py     179 行
```

gateway 关键设计：

```
任务对象   Task(id, payload, idem, chunks, status, usage, waiters)
派发策略   单 Agent 优先；多 Agent 时 round-robin（代码已留，不用改即可扩）
无 Agent   不返回 503，任务留在队列 —— 这是"任务不丢"的前提
断连处理   Agent 断开时，streaming 且尚未产生 chunk 的任务退回 queued 并重派
指标       /metrics 暴露 agents_connected、queue_depth、streaming_tasks
           以及 requests / dispatched / done / failed / rate_limited / idempotent_hits 计数
```

agent 关键设计：

```
重连退避   1s → 2s → 4s → 8s → 10s 封顶，永不放弃
并发上限   信号量 MAX_CONCURRENT=8，防止把本地服务打满
resume     重连后把所有未完成任务连 buffer 一起上报，gateway 重建上下文
SSL        自签证书，check_hostname=False + CERT_NONE（生产要换真实 CA）
```

```

     -addext "subjectAltName=IP:47.238.160.73"

③ Gateway 资源配置
```

## 四、四道闸门实测

### 闸门① 首字延迟 < 1.5s

经公网 HTTPS 全链路（含隧道往返、鉴权、WS 派发），连续 5 次：

```
第1次  TTFT=0.1436s  TOTAL=1.0150s
第2次  TTFT=0.1160s  TOTAL=0.7246s
第3次  TTFT=0.1158s  TOTAL=0.8059s
第4次  TTFT=0.1287s  TOTAL=0.8810s
第5次  TTFT=0.1205s  TOTAL=0.6891s
```

平均首字 **0.125s**，验收线 1.5s，余量 12 倍。这个数含 RTX 3090 上的 prefill 与网络往返。

### 闸门② 并发曲线出现拐点

```
并发  总耗时  平均延迟  P95     完成/失败
  1   0.43s   0.43s    0.43s   1/0
  4   0.37s   0.35s    0.37s   4/0
  8   0.47s   0.45s    0.46s   8/0
 16   3.05s   1.46s    2.81s   16/0
```

**拐点在 8 与 16 之间。** 8 并发时 P95 仍是 0.46s，到 16 并发 P95 跳到 2.81s，
总耗时从 0.47s 涨到 3.05s。这说明这台 3090 + 当前 vLLM 配置的全链路容量上限约 8 并发，
再多就开始排队。这个 8 是实验三队列设计的基准值。

补充：直连 vLLM 时曾测到 32 并发仍能撑住（1553 字/秒），说明瓶颈不在模型，
而在 Agent 侧的 MAX_CONCURRENT=8 与单条 WS 的串行派发。这本身就是一个可优化的点。

### 闸门③ gateway 重启，Agent 自动重连，任务不丢

```
重启前  agents=1
重启    kubectl rollout restart deploy/ai-gateway
Agent   [20:02:53] disconnected: ConnectionClosedError: received 1012 (service restart)
        retry in 1s
        [20:02:54] connecting wss://...:31154/agent
        [20:02:54] connected
        [20:02:54] welcome agent_id=agent-6bfbd3b9
重启后  agents=1，请求 200，0.59s
```

1 秒内完成重连。因为 gateway 用 1012（service restart）明确告知，Agent 按退避策略立即重连。

### 闸门④ 断网 30 秒，积压任务继续执行

做法：本地 `iptables -I OUTPUT -d 47.238.160.73 -j DROP`，断网期间连发 3 个请求，30 秒后解封。

```
断网瞬间   gateway 不可达
断网期间   Agent: keepalive ping timeout → retry
           3 个请求全部进队列，客户端挂住不报错（gateway 不返回 503）
恢复       [20:03:44] connecting → connected
结果       请求1 HTTP=200 "好的"
           请求2 HTTP=200 "好的"
           请求3 HTTP=200 "好的"
```

三个积压请求全部成功，没有丢失、没有重复推理。

### 附加验证（"功能全要"的部分）

```
鉴权失败   无 key → 401 {"detail":"missing api key"}
           错 key → 401 {"detail":"invalid api key"}
幂等       第一次 idempotent_hit=false 0.326s
           第二次 idempotent_hit=true  0.139s（命缓存，未重复推理）
限流       配额 60/分钟；压测用掉 31 次后，第 29 次连续轻请求撞线
           返回 429，共触发 12 次

           requests_total / dispatched / done / rate_limited / idempotent_hits 全在

```

## 五、踩到的坑

```
① Envoy Gateway certgen 永远 Pending
   现象  0/2 nodes are available: 2 node(s) had untolerated taint(s)
   根因  单节点集群，控制面带 node-role.kubernetes.io/control-plane:NoSchedule
   解    kubectl taint nodes ai-cp-1 node-role.kubernetes.io/control-plane-
   教训  单节点集群第一步就该去掉这个 taint，否则一半组件装不上

② GatewayClass 不存在
   现象  controller 日志反复打 "no accepted gatewayclass"
   根因  Envoy Gateway 1.10 的 helm chart 不自动创建 GatewayClass
   解    手动 kubectl apply 一个 controllerName=gateway.envoyproxy.io/gatewayclass-controller

③ CRD 的 API group 写错
   现象  no matches for kind "EnvoyProxy" in version "config.gateway.envoyproxy.io/v1alpha1"
   根因  我按记忆写成 config.gateway.envoyproxy.io
   正解  实际是 gateway.envoyproxy.io/v1alpha1

④ CRD chart 装不上（可选，不影响）
   现象  Secret "sh.helm.release.v1.eg-crds.v1" is invalid: data: Too long
   根因  CRD chart 的 release 元数据超过 Secret 1MB 上限
   说明  主 chart 已带 CRD，不需要单独装

⑤ Agent 在 K8S Pod 里 CrashLoopBackOff
   现象  容器启动即退出，云端 kubectl logs 因 10250 不通拿不到日志
   决定  改成宿主 systemd 托管。边缘 Agent 以宿主服务部署在真实架构里很常见
   影响  K8S 侧只保留 gateway，Agent 脱离调度 —— 这一点在文档里如实标注

⑥ Agent 连不上 wss（自签证书）
   现象  agents=0，连接失败无明确报错
   根因  websockets.connect 默认验证证书，自签必然失败
   解    ssl.create_default_context() + check_hostname=False + verify_mode=CERT_NONE

⑦ ctr 的 --rlimit 参数不存在
   现象  ctr: flag provided but not defined: -rlimit
   影响  vLLM 单元起不来，GPU 显存掉到 300MiB
   解    去掉该参数，fd 上限交给 systemd 的 LimitNOFILE

⑧ 云端访问自己的公网 IP 会超时（hairpin NAT）
   现象  curl https://47.238.160.73:31154/health 在云端空返回
   根因  阿里云不支持私网访问自己的公网 IP
   解    云端内部验证走 ClusterIP / 127.0.0.1，公网验证必须从外部发起
```

## 六、这一层与实验二的关系

实验一证明的是「应用层能通」，实验二证明的是「调度是真的」。两者故意用不同机制接入同一张卡：

```
实验一   反连 WebSocket    优点是能穿越 NAT、无需开放入站
                          缺点是要自己处理重连、幂等、队列，语义全靠应用实现

实验二   kubelet 注册      优点是资源语义由调度器统一裁决（配额、抢占、taint）
                          缺点是要开放 6443/10250，对网络要求高

两者可以并存：实验二的 K8S 负责"谁有资格用卡"，实验一的 Agent 负责"任务怎么跑完"。
本次实现就是并存的 —— 集群能调度 GPU，但没有把 vLLM 放进 Pod。
```
