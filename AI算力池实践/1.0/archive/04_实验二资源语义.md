# 04 · 实验二：真节点入集群（调度是真的）

> 时间：2026-11-22 20:05 — 20:24
> 目标：把接入机制从应用层换到内核层，验证 K8S 对 GPU 的资源语义 ——
>       要 1 卡能跑、要 2 卡就 Pending、配额能卡死、抢占能踢人、假共享会出事、断网有明确时序。

前提：本地 ai-gpu-1 已以真 kubelet 注册进集群，`nvidia.com/gpu` capacity=1 / allocatable=1。
GPU 资源由 NVIDIA device plugin v0.17.4 上报。

---

## 一、资源模型：1 卡与 2 卡

### 1 卡 —— 能跑，容器内真的看到卡

```
Pod  spec: hostNetwork + runtimeClassName nvidia + limits nvidia.com/gpu: 1
结果  Completed（nvidia-smi 退出码 0）

容器内实测输出
  NVIDIA GeForce RTX 3090, 24576 MiB, 621.24     ← 卡名、显存、驱动版本
  /dev/dxg 存在（WSL 的 GPU 直通设备）
```

### 2 卡 —— Pending，且报错说得非常清楚

```
Pod  spec: limits nvidia.com/gpu: 2
结果  Pending，调度器原话：

  0/2 nodes are available:
    1 Insufficient nvidia.com/gpu,
    1 node(s) didn't match Pod's node affinity/selector.
  preemption: 0/2 nodes are available: 2 Preemption is not helpful for scheduling.
```

这是「资源不足」的正确长相：**Pending + Insufficient**，不是 OOMKilled，不是 ContainerCreating 卡死。
区分这两件事很关键 —— Pending 是调度器根本没给，OOM 是给了但用超了。

### 两个必要前提（不做就起不来）

```
hostNetwork          本地节点没有 CNI，普通 Pod 建 sandbox 会报
                     failed to find network info for sandbox
                     加上 hostNetwork 后问题直接消失（原设计就是这么定的）

runtimeClassName     默认 runc 不注入 /dev/dxg 和 NVML 库
  nvidia             不加会 StartError，容器连 nvidia-smi 都执行不到
```

## 二、ResourceQuota：部门抢卡

```
namespace  team-a
配额       requests.nvidia.com/gpu: 1 / limits.nvidia.com/gpu: 1

第一个 Pod  quota-pod-1 → 创建成功，Running
第二个 Pod  quota-pod-2 → 被拒，原话：

  pods "quota-pod-2" is forbidden:
  exceeded quota: gpu-quota,
  requested: requests.nvidia.com/gpu=1,
  used: requests.nvidia.com/gpu=1,
  limited: requests.nvidia.com/gpu=1
```

注意这是 **API Server 层拒绝**（Forbidden），比 Pending 更早一步：连对象都不让你建。
真实场景里就是「A 部门把卡占满了，B 部门提交作业直接被配额挡住」。

## 三、PriorityClass：抢占，一眼看出谁被踢

```
PriorityClass  ai-low  = 100     （batch 推理，可被抢）
               ai-high = 10000   （在线服务，抢别人）

① low-pri 提交，占住唯一的卡   → Running
② high-pri 提交               → FailedScheduling:
                                 1 Insufficient nvidia.com/gpu
                                 preemption: found a potential placement for pod
                                             on node ai-gpu-1, preempting 1 victims
③ 驱逐事件                     → Preempted by pod 09179f6c-0395-48e0-9e4f-8f3e5ff6b69c
                                 on node ai-gpu-1
④ low-pri                      → Killing（terminationGracePeriodSeconds: 0 立即走）
⑤ high-pri                     → Running，node ai-gpu-1，priority 10000
```

单卡集群里这个体感特别直接：卡只有一张，高优先级的作业一来，低优先级必然被踢，
Evicted 的是谁、为什么被踢，Events 里写得明明白白。

## 四、断网：NotReady 与恢复的时序

做法：只切断本地到云端 6443（kubelet → API Server），保留 22 端口以免影响操作。
比拔网线更精准，效果等价。

```
T0 20:11:19   切断 6443
+10s          ready=True  | KubeletReady
+20s          ready=True  | KubeletReady
+30s          ready=True  | KubeletReady
+40s          ready=True  | KubeletReady
+50s          ready=Unknown | NodeStatusUnknown     ← NotReady

此时 Pod 状态：high-pri 仍 1/1 Running
（hostNetwork Pod 不依赖 kubelet 通信，节点失联不等于容器停）

T1 20:12:11   恢复 6443
+10s          ready=Unknown
+20s          ready=True                            ← 恢复 Ready
```

时序结论：**失联 40 秒以上判定 NotReady（node-monitor-grace-period），恢复后 20 秒内回到 Ready。**
这解释了为什么 WSL 抖动时节点会短暂 NotReady 又自己好 —— 不是集群坏了，是心跳窗口。

## 五、time-slicing：假共享的代价（含一次意外）

### 配置

```
给 device plugin 加 ConfigMap：
  version: v1
  sharing:
    timeSlicing:
      resources:
      - name: nvidia.com/gpu
        replicas: 4

patch DaemonSet 加 --config-file=/config/config.yaml 并挂载

结果：allocatable 从 1 变成 4
```

**这一步本身就是问题所在**：物理上只有 1 张卡，调度器认为有 4 张。
四个 Pod 各自声明 1 卡，全部都能调度成功 —— 这就是"假共享"。

### 实测：两个 vLLM 同时声明 1 卡

```
vllm-a  声明 nvidia.com/gpu: 1，util 0.70，端口 8001
        140 秒后就绪，显存 17166 MiB

vllm-b  声明 nvidia.com/gpu: 1，util 0.70，端口 8002
        也被调度到 ai-gpu-1（同一个物理卡），90 秒内 Running
```

两个 Pod 都是 1/1 Running、都声明了 1 卡、都落在同一个节点同一张卡上。

### 意外：没有 OOMKilled，而是显存冲到 98%

```
时间轴    vllm-a 就绪   17166 MiB
         +10s          17167
         +60s          17511
         +70s          23246      ← vllm-b 开始加载
         +80s          23526
         +90s          24185      ← 98%，逼近物理上限
         随后回落       21065
```

按预期应该出现"第二个 Pod 加载模型时 OOMKilled"，实际却是两个都活着、显存被推到 24185 MiB。
原因是 `--gpu-memory-utilization 0.70` 对 vLLM 是软目标而不是硬上限，两个进程各自
拿到比 70% 更小的份额也能勉强跑起来 —— 代价是整卡被吃满，任何一个再要一点就爆。

**这比 OOMKilled 更值得记住**：假共享下没有隔离，谁抢到算谁的。
真实集群里如果四个人都声明 1 卡，不是"每人 1/4"，而是"同时加载时集体逼近物理上限，
谁先崩看运气"。OOMKilled 反而是运气好的情况 —— 至少它明确告诉你超了。

考虑到机器还要继续用，看到 24185 MiB 就立刻止血了，没有继续加压去逼 OOM。
这一步的结论仍然成立：**time-slicing 是超卖，不是分享。**

### 止血与回滚

```
① 强删 vllm-a / vllm-b            → 显存回 271 MiB
② 移除 DaemonSet 的 args / 挂载    → allocatable 回到 1
③ 重启 systemd 的 vLLM 与 Agent    → 公网服务恢复，请求 200
```

回滚时遇到一个坑：`kubectl replace -f /tmp/dp.yaml` 报 Conflict（对象已被修改），
最后用 json patch 精确删除 `args`、`dp-config` 的 volumeMounts 与 volumes 才干净。

## 七、踩到的坑

```
① 普通 Pod 建不出 sandbox
   现象  failed to find network info for sandbox
   根因  本地节点故意不装 CNI
   解    GPU Pod 一律 hostNetwork（原设计如此）

② 加了 hostNetwork 仍 StartError
   现象  容器创建了但起不来
   根因  默认 runc 不注入 /dev/dxg 与 NVML 库
   解    加 runtimeClassName: nvidia

③ kubectl logs 到本地节点超时
   现象  dial tcp 192.168.236.130:10250: i/o timeout
   根因  节点宣告的是 WSL NAT 地址，云端访问不到
   解    让容器把结果写进 hostPath，本地读文件；或本地读 /var/log/pods
   注    这是本环境已知限制，实验三的大盘要用别的方式抓指标

④ kubectl replace DaemonSet 报 Conflict
   原因  对象在 patch 之后又被控制器改过
   解    先 get -o json，用 python 精确删字段，再 replace
```
