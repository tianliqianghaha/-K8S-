# 00 · 这套东西到底是干什么的（总览解说）

> **先把原话摆在这里，让你知道我们讲的是哪一套东西**
> 「D:\AI算力池实践\1.0 你把这个详细讲解一下。我只能看懂大概。但是细节不清晰。而且没有一个整体框架。」

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `00_总览与复现路线.md` + 01~05 五章正文 + `06_经验与陷阱.md` + `07_速查卡.md`。

下面把这套资料里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① 一句话说清楚这套东西

**把一张家用的 RTX 3090，变成云上可调度、可计量、可排队、可抢占的推理算力池。**

云上只放控制面和治理件（4C8G 抢占实例，约 0.22 元/时），真正的算力在家里的机器上。用最少的钱，把"一张能跑推理的卡"变成"一个像样的算力池"。

"算力池"和"一台能跑推理的机器"区别在哪？三个字：**能被管**。有排队、有配额、有监控、有回滚、有成本账，才叫池子。

---

## ② 三个实验分别证明什么（这是整套资料的骨架）

```
实验一  应用层反连        证明「云调度、本执行」这条链每一环都通
        客户端 → HTTPS 入口 → 云端 gateway（鉴权/限流/队列）
        → WebSocket 出站长连接 → 本地 Agent → vLLM → 逐字回流
        验收：首字 < 1.5s、并发有拐点、gateway 重启不丢任务、断网 30s 能恢复

实验二  内核层注册        证明「调度是真的」，资源语义由 K8S 裁决
        同一张卡：要 1 卡能跑、要 2 卡就 Pending、配额能卡死、抢占能踢人
        验收：Capacity 有 nvidia.com/gpu=1、GPU Pod 落本地、抢占事件可见、断网有明确时序

实验三  治理平面          证明「能跑」变成「能管」
        Kueue 排队 + KEDA 按队列扩 + Grafana 大盘 + chaos 延迟注入
        + Argo 金丝雀自动回滚 + OpenCost 成本分摊
        成绩：七项全过，OpenCost 部署通过但数值没算出来
```

为什么三个实验要分开做？因为它们回答的是三个不同的问题：

```
实验一回答  任务怎么送到卡上
实验二回答  谁有资格用卡
实验三回答  跑起来之后怎么管
```

一次全上，出问题你不知道是链路断了、调度拒了、还是治理组件把控制面压死了。分开做，每一步只引入一类新变量。

---

## ③ 两次接入方式并存，是这套东西最值钱的地方

```
应用层反连（第 3 章）   本地 Agent 主动连云端 WSS → 任务送达到卡上
内核层注册（第 4 章）   本地 kubelet 真 join 集群 → K8S 裁决谁有资格用卡
```

**反连负责把任务送到卡上，K8S 负责裁决谁有资格用卡。**

初级人员最容易问："既然 K8S 已经把节点注册进来了，为什么还要自己写 gateway 和 Agent？"

因为这两套东西解决的不是同一个问题：

```
K8S 调度       决定"这个 Pod 能不能放到这张卡上"，但它不管"公网用户怎么把请求送到家里机器"
应用层反连     解决"没有公网地址怎么被派活"，但它不管"多个人抢卡谁先谁后"

两者互补，不是重复。真正的算力池两个都需要。
```

还有第三类通道，作用又不同：SSH 反向隧道把本地的 8000/9101 端口借给云端，只给监控和排障用，不是任务通道。

```
   │  Envoy Gateway 1.10.0  ──►  ai-gateway（FastAPI）         │
   │    GatewayClass eg            鉴权 / 限流 / 幂等 / 队列    │
   │    NodePort 31154             WebSocket 派发              │
   │                                                           │
   │  Kueue 0.13.0        排队与配额                            │
   │  KEDA 2.21.1         按队列积压扩副本                      │
   │  kube-prometheus-stack   Prometheus + Grafana             │
   │  chaos-mesh 2.7.2    延迟注入                              │

   │  Cilium 1.20.4       eBPF 数据面（无 kube-proxy）          │
   └───────────────────────────────────────────────────────────┘
                     ▲
                     │ WSS 出站长连接（本地主动连云端，穿透 NAT）
                     │
   ┌───────────────────────────────────────────────────────────┐
   │ 本地 ai-gpu-1   RTX 3090 24G · WSL2 Ubuntu 24.04          │
   │                                                           │
   │  kubelet 1.37.2   真注册进集群（内核层）                    │
   │  device plugin    上报 nvidia.com/gpu = 1                  │
   │  ai-agent         systemd，接任务、调本地 vLLM、增量回传     │
   │  vLLM 0.34.0      Qwen2.5-7B-Instruct-AWQ（systemd + ctr） │
   │  gpu-exporter     nvidia-smi 指标导出（DCGM 的替代）        │
   └───────────────────────────────────────────────────────────┘
```

**诊断时永远分清三条线**（后面每一章都按这个框架看）：

```
数据流    客户端 → Envoy → gateway → WSS → agent → vLLM → token 原路回流
          这是"请求怎么被回答"

资格线    K8S 调度器 / ResourceQuota / Kueue 决定谁被准许用卡
          这是"谁能用"

观测线    gpu-exporter、vLLM 指标 → Prometheus → Grafana
          靠 SSH 反向隧道把本地数字送上去。这是"用得怎么样"
```

## ⑤ 三个硬约束（不要试图绕过，只能适配）

```
约束一  本机只有 16G 内存、24G 显存
        对策  模型用 7B AWQ 4bit（权重 4.5G），显存利用率 0.72
              WSL 分配 11G，宿主留 5G

约束二  Windows 10 + WSL2，不是裸金属 Linux
        对策  GPU Pod 一律 hostNetwork + runtimeClassName nvidia
              本地节点不装 CNI，跨公网靠反连而不是 Pod 网络
              推理服务放在 systemd 而不是 K8S（kubelet 在 WSL 上会因 socket 丢失反复重启）

约束三  云端是最低档 100G ESSD，IOPS 有限
        对策  监控抓取间隔 120s，只留必要指标
              etcd 对 fsync 极敏感，任何"大写入"都会直接把控制面拖死
```

为什么要反复强调这三条？因为**这套环境里的所有事故都来自资源耗尽，不是配置写错**。装任何组件前先问它吃多少内存和 IOPS。

## ⑥ 成本账（为什么这套设计不追求"完备"）

```
云上 4C8G 抢占          0.075 元/时
100G ESSD entry         约 0.14 元/时
合计                    约 0.22 元/时 ≈ 5 元/天

三个实验合计约 6.5 小时，云上花费约 1.5 元
本地电费 3090 满载 350W × 6.5h ≈ 1.3 元
全程 3 元以内
```

省下来的关键：**不做控制面 HA（省 2 台）、不装 Longhorn（省每节点 150G 盘）**。这两笔在通用 K8S 平台里占成本六成以上，但对"验证 AI 链路"零贡献。

## ⑦ 复现顺序与章节地图

```
第 1 章  本地 GPU 节点        三道闸门：systemd / 宿主 GPU / 容器内 GPU
         ↓ 过了才往下做
第 2 章  云端控制面 + 节点入集群   kubectl get nodes 能看到两个 Ready
         ↓
第 3 章  实验一 应用层反连      公网首字 < 1.5s，四道闸门全过
         ↓
第 4 章  实验二 资源语义        1卡跑 / 2卡 Pending / 配额 / 抢占 / 断网时序
         ↓
第 5 章  实验三 治理平面        排队 / 大盘 / 延迟注入 / 弹性 / 金丝雀回滚 / 成本
```

每章结构统一：本章目标（要证明什么）→ 前置条件（上一章验收结果）→ 部署步骤 → 验收标准 → 不做什么（本章刻意不碰的边界）。

**会计较"不做什么"，是这套资料成熟的地方**。不装 Loki、不做 HA、不上正式证书，每一个"不做"都有明确理由。

## ⑧ 判官卡：为什么用抢占实例 + 单控制面

```
选项 A  按量 + 抢占实例 + 单控制面（本次）
  优点：成本 0.22 元/时；实验三小时级别，被回收了大不了重建
  缺点：控制面只有一台，挂了整个集群停摆；随时可能被回收

选项 B  按量 + 3 台控制面 HA
  优点：高可用，生产可用
  缺点：成本 ×3 以上；对"验证 AI 链路"零贡献

判据：实验的目的是验证链路和语义，不是验证高可用。
      能用快照和脚本在 10 分钟内重建，就不需要为 HA 付钱。
```
