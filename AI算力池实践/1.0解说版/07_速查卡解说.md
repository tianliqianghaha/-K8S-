## ① 地址与凭据：为什么记这几个

```
公网入口      https://47.238.160.73:31154
API Key       sk-ai-pool-2026（Authorization: Bearer ...）
健康检查      /health        返回 agents / queued / streaming
指标          /metrics       Prometheus 文本格式

云端控制面    47.238.160.73:6443     私网 172.23.163.98
本地 GPU 节点 192.168.236.130        WSL NAT 地址，仅在集群内部可见

Grafana       经 port-forward 访问，admin / admin123456
OpenCost      经 port-forward 9003 访问
```

**为什么这些地址要分开记**：它们属于三个不同的网络平面。

```
公网地址 31154   外部客户端进来的唯一入口
私网 6443        kubelet 注册 / kubectl 操作
NAT 192.168.*    本地节点在集群内部看到的样子，公网够不着
```

**为什么健康检查返回这三个数**：`agents` 是链路活不活、`queued` 是任务堵没堵、`streaming` 是有没有卡住的活。三个数覆盖了第 3 章链路的三种状态。

## ② 服务清单：谁在跑、谁托管

```
本地（systemd，5 个全部 enabled）
├─ vllm.service                 ctr 单容器跑 vLLM，端口 8000
├─ ai-agent.service             反连云端 gateway，接任务
├─ vllm-tunnel.service          SSH -R 8000（备用通道）
├─ gpu-exporter.service         nvidia-smi 指标，端口 9101
└─ gpu-exporter-tunnel.service  SSH -R 9101（给 Prometheus 抓）

本地（Windows 侧）
└─ 计划任务 WSL-KeepAlive       每分钟触发，实例跑 24h，保发行版不被终止

云端（K8S）
├─ ai-gateway                   鉴权/限流/队列/WS 派发
├─ Envoy Gateway                入口，NodePort 31154
├─ Cilium / Kueue / KEDA
├─ kube-prometheus-stack
├─ chaos-mesh / Argo Rollouts / OpenCost
```

**为什么要分清"谁托管"**：这是判断故障范围的第一刀。

```
systemd 服务挂了    → 看 journalctl -u 服务名
K8S 组件挂了        → 看 kubectl -n 命名空间 get pods
计划任务没了        → 发行版会被终止，所有 systemd 服务一起停
```

**特别注意两条隧道**（`vllm-tunnel`、`gpu-exporter-tunnel`）：它们是 SSH 反向隧道，目标 IP 写死在 unit 文件里。换机器或重建云端后必须改地址，否则一直重连失败。

## ③ 日常自查：为什么是这个顺序

```
1. systemctl is-active vllm ai-agent gpu-exporter
   先看本地三个关键服务在不在。这是最底层，它们挂了上面全白搭。

2. nvidia-smi 查显存/利用率/温度
   GPU 负载的正确判据。预期约 17.7G / 24G，温度 30 度左右。

3. curl 本地 vLLM /health
   确认推理服务本身能响应（200），而不只是进程在跑。

4. curl 公网 /health
   看 agents 是否为 1 —— 本地 Agent 有没有连上云端。

5. 端到端发一条真实请求
   前面四步都过了，还要证明"整条链真的能回答问题"。

6. kubectl get nodes + GPU 资源
   最后看集群视角：两个 Ready、GPU 资源为 1。
```

**为什么从下往上查**：每一条都是上一条的前提。跳过底层直接看顶层，你会把"Agent 没连上"误判成"网络故障"，其实是 vLLM 没起来。

## ④ 故障自查表：症状 → 判断

这一节的价值在于"把症状和层次对上号"：

```
症状：公网请求 401
判断：API Key 不对或缺 Authorization 头。gateway 正常，只是鉴权拦住了。

症状：公网请求 503 或连接被拒
判断：Envoy Gateway 或 ai-gateway Pod 没起来。
      先看 kubectl -n ai get pods，再看 envoy-gateway-system 命名空间。

症状：/health 里 agents 为 0
判断：本地 Agent 掉线。看 journalctl -u ai-agent -n 20，通常是网络或证书问题。

症状：请求一直挂着不出字
判断：任务进了队列但没有 Agent 接手，或 vLLM 卡住。
      看 /health 的 queued 数、本地 vLLM 的 health、显存是否异常。

症状：显存从 17.7G 掉到 300M
判断：vLLM 进程被杀了。查 journalctl -u vllm 末尾，常见是收到终止信号。

症状：kubectl 突然全部 connection refused
判断：控制面假死。第一件事看 etcd 日志里的"请求耗时过长"和压缩耗时，
      不要看 CPU 和内存。

症状：GPU Pod 一直 Pending
判断：Forbidden（配额层，对象没建）vs Pending（调度层，卡不够）。
      先看 Events 原文，别猜。

症状：GPU Pod ContainerCreating 卡住
判断：本地节点没有 CNI，检查 Pod 有没有 hostNetwork。

症状：GPU Pod StartError
判断：缺 runtimeClassName: nvidia。

症状：kubectl logs 到本地节点超时
判断：已知限制，节点宣告 NAT 地址，云端访问不到 10250。
      改用 hostPath 把结果写出来再本地读。
```

## ⑤ 重启与恢复：顺序不能反

```
本地推理栈（按顺序）
1. restart vllm          约 150 秒就绪（要加载 4.5G 模型）
2. restart ai-agent      约 5 秒连上（它的连接对象是 gateway）

为什么这个顺序：Agent 起来时如果 vLLM 还没就绪，请求会打到未就绪的推理服务上。

只重启 Agent（不影响推理）  → 只 restart ai-agent 即可

云端 gateway               rollout restart，约 30 秒（要重装 pip 依赖）

WSL 整体重启后：systemd 自动起 vllm/ai-agent/exporter，
                等 150 秒确认 vLLM /health 返回 200，再看 gateway 的 agents
```

## ⑥ 验证清单：交付前跑一遍

把三个实验的关键指标各取一条，确认环境仍然健康：

```
curl -sk https://<入口>:31154/health          ← 链路
kubectl get nodes                             ← 集群
GPU 资源为 1                                  ← 资源语义
kubectl get clusterqueue                      ← 排队
kubectl -n monitoring get pods                ← 治理
systemctl is-active vllm ai-agent gpu-exporter
nvidia-smi 显存
```

## ⑦ 停止与释放：顺序错了会有残留

```
1. 本地五个服务先停再 disable
   为什么先停本地：否则隧道会一直重连已释放的云端

2. 确认显存释放（回落到 270MiB 左右）、容器清掉

3. 删 Windows 保活计划任务 WSL-KeepAlive
   为什么：不删的话计划任务每分钟拉起一个 WSL 客户端

4. wsl --shutdown

5. 释放云端实例（抢占实例删除即释放，不再计费）
   随后确认地域内实例数为 0
```

**安全组入站规则保留不删**：不产生费用，且是共享安全组，下次重建直接复用。

## ⑧ 重新启用 / 从零重建

```
重新启用（环境还在，只是停了）：
1. 云端：按第 2 章重开 4C8G，重新 kubeadm 或从快照恢复
2. 本地：WSL 启动后把五个服务打开
   先 vllm + exporter → 等 /health 200（约 150 秒）
   → 再两条隧道 → 最后 ai-agent
3. 恢复常驻客户端（否则命令一结束发行版就被终止）
4. 验证：systemctl is-active + 公网 /health 的 agents 应为 1

注意：两条隧道的目标 IP 写死在 unit 文件里，换机器后要改。

从零重建的最短路径：
1. Windows 启用两个功能 → 关快速启动 → 重启 → Hypervisor Present
2. 装 WSL 平台（镜像代理）+ 导入 Ubuntu（Canonical 镜像）
3. .wslconfig 分配 11G/8核 → 建用户 → 开 systemd → 设常驻客户端
4. 跑初始化脚本：GPU 工具链 + containerd 双 runtime + kubelet
5. 三道闸门验收（systemd / 宿主 GPU / 容器内 GPU）
6. 云端开 4C8G → kubeadm → 去控制面污点 → Cilium → device plugin
7. 本地 kubeadm join → 打 GPU taint → 确认 allocatable=1
8. 按第 3 章部署：Envoy Gateway → 证书 → gateway → vLLM → Agent
9. 按第 4 章验证资源语义（记得先腾卡，做完恢复）
10. 按第 5 章装治理平面（监控必须调参，否则 etcd 会被压死）
```

**第 8 步之后每一步都有明确验收点，不通过就不要往下走。** 这是整套资料的纪律。

## ⑨ 判官卡：自查为什么要按固定顺序

```
选项 A  哪个报警看哪个
  优点：直觉，快
  缺点：同一个症状可能是不同层的原因（比如"起不来"有三层解释），容易修错地方

选项 B  从最底层往上逐层验（本次）
  优点：每层都是上层的前提，定位准确
  缺点：步骤多，要按顺序做

判据：底层不通时，上层的所有现象都是假象。
      systemctl → 显存 → vLLM health → 公网 health → 端到端 → kubectl
      这个顺序本身就是因果链。
```

## ⑩ 这一章的坑补充

```
现象：停服务时先释放了云端，本地隧道一直重连
根因：停止顺序错了，隧道进程还在跑
防：严格按"停本地服务 → 释放云端"的顺序

现象：重建后 Agent 连不上，但配置看起来没改
根因：两条隧道 unit 里的目标 IP 是旧云主机的
防：换机器后先改 /etc/systemd/system/*-tunnel.service 里的地址

现象：WSL 重启后所有服务都没起来
根因：发行版被终止后 systemd 不会自动恢复；或常驻计划任务被删了
防：确认 WSL-KeepAlive 任务存在，再按第 5 节顺序重启服务

现象：Envoy 的 Gateway 一直未编程
根因：GatewayClass 没建（1.10 不自动建）
防：补建 GatewayClass，这是第 3 章的坑，重建时最容易忘
```

**一句话总结这一章**：速查卡不是命令清单，是**因果顺序清单**。服务 → 显存 → 健康检查 → 端到端 → 集群，从下往上逐层验；停止时反过来从上往下拆。顺序对了，故障范围自然收敛。
