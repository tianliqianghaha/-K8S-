# 05 · 治理平面解说（从"能跑"到"能管"）

> **这一章在整件事的哪一步**：第 3 章链路通、第 4 章调度真 →【加治理平面】→ 交付。
> **这一章在干什么**：数据面完全复用前两章，只加一层治理——排队、配额、观测、弹性、故障注入、渐进发布、成本。让算力池变得"能被信任"。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `05_第5章_实验三_治理平面.md` + `scripts/app/exporter/gpu_exporter.py` + `scripts/app/dashboard.json` + `06_经验与陷阱.md` 第六节。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① 先分清两个层次：调度治理 vs 运维治理

```
调度治理    Kueue（排队与配额）+ KEDA（按队列扩副本）
            决定"谁先跑、要扩几个"

运维治理    观测 + chaos 注入 + Argo 回滚 + OpenCost 成本
            决定"看得见、扛得住、退得回、算得清"
```

八项组件看着多，其实全在这一层里。**数据面一个字没改**——这是本章最重要的设计纪律。

---

## ② Kueue：排队才是主角

**是什么**：K8S 的作业排队与配额控制器。

**为什么必须有它**：第 4 章的 ResourceQuota 是"硬拒绝"——超了直接 Forbidden，对象都建不出来。Kueue 是"准入 + 排队"——对象建好了，但先挂起（`SUSPEND=true`），等有额度再放行。**有排队，才有池子**。

```
ResourceFlavor  gpu-node     指向那台 GPU 节点，带污点容忍
ClusterQueue    gpu-cq       总配额 1 卡
LocalQueue      team-a       部门从总队列分额度
```

**实测**：提交 10 个 Job，只有 1 个 `ADMITTED`，9 个挂起；30 秒后前一个跑完，下一个自动放行。team-b 给 0 配额，提交就报 `request > maximum capacity (1 > 0)`。

---

## ③ KEDA：扩出来的副本，拿不到卡

**是什么**：事件驱动自动伸缩器，这里盯着 Prometheus 里的 `kueue_pending_workloads`。

**实测**：积压=1 → worker 副本 0→1→4，但最终是 **1 Running、3 Pending（Insufficient nvidia.com/gpu）**。

**这不是失败，这是正确的形态**：

```
治理层决定"想要多少"  → KEDA 扩副本
资源层决定"能给多少"  → 卡数硬性限制，只有 1 个能跑
Kueue 把拿不到卡的排进队列

两层配合，而不是互相打架。
```

---

## ④ 观测：Prometheus + Grafana（必须裁剪着装）

**为什么这块最难**：本章最大的坑不是某个组件装不上，而是**装完之后把控制面压死**。

事故链条：

```
默认监控抓十几个目标、每 15 秒一次
  → TSDB 写入把入门 ESSD 的 IOPS 吃满
  → etcd 落盘被拖到几十秒（正常毫秒级，实测压缩出现 3 分 55 秒）
  → API Server 线性化读超时、健康检查失败
  → 所有 kubectl 命令 connection refused，控制面假死
```

**迷惑性在于**：出事时 CPU 97% 空闲、内存还剩 3G，看什么都正常。

**正确的诊断依据**：不要看 CPU 和内存，看 etcd 日志里的"请求耗时过长"和"压缩耗时"。正常压缩是毫秒级，出问题时是分钟级。

**对策（装之前就算账，装之后立刻做减法）**：

```
关 alertmanager / node-exporter / kubeEtcd / kubeScheduler 等抓取
retention 2h、抓取间隔 60~120s、内存上限 600Mi
装完立刻删多余的 ServiceMonitor，只留真正要看的
```

## ⑤ GPU 指标：自己写 exporter 替代 DCGM

**是什么**：一个轮询 `nvidia-smi` 的小服务，暴露显存 / 利用率 / 温度 / 功耗四个指标。

**为什么必须有它**：官方 DCGM exporter 在 WSL 上起不来——它依赖一套 WSL 里不存在的设备访问方式。自建 exporter 数值是真的，只是采样粒度粗一点，对实验完全够用。

**两个配套细节**：

```
systemd 单元的 PATH 要显式加 /usr/lib/wsl/lib
  为什么：WSL 把 nvidia-smi 放在非标准路径，systemd 默认 PATH 找不到

用 SSH -R 反向隧道把 9101 暴露到云端
  为什么：Prometheus 在云端，抓不到 NAT 后面的本地端口
  这是第 2 章"反连"思路在监控上的复用
```

**大盘六个面板**：利用率、显存、排队数、温度功耗、并发请求数、首字延迟 P99/P50。目标不是花哨，是**四个关键数字一张图**。

---

## ⑥ chaos-mesh：延迟注入

**是什么**：故障注入工具，这里给 ai-gateway 的出站流量加 300ms 延迟。

**为什么必须有它**：不故意搞破坏，你不知道系统对故障的真实反应。

**实测**：

```
基线       TTFT 0.132 / 0.152 / 0.138 / 0.131 / 0.162
+300ms     TTFT 0.719 / 0.436 / 0.730 / 0.425 / 0.451
撤销后     TTFT 0.121 / 0.134 / 0.141 / 0.163 / 0.122
```

抬升约 0.30–0.35 秒，与注入值吻合。**延迟伤的是首 token，不是生成速率**——这个结论只有靠注入实验才能得到。

---

## ⑦ Argo Rollouts：金丝雀与自动回滚

**是什么**：渐进式发布控制器。

**流程**：`setWeight 25% → analysis → setWeight 100%`。分析脚本每 15 秒查一次成功率，10 次请求里少于 9 次 200 就算失败。

**灵魂在"非零退出"**：

```
检测脚本失败时必须 exit 1
为什么：Argo 只判断分析 Job 是否成功退出，不读你打印的文字
如果脚本永远 exit 0，它会认为"跑完了就是通过"，坏版本会被全量放行
```

**实测**：坏版本约 30 秒内 `Degraded → Aborted`，四个 Pod 全部退回好版本。

---

## ⑧ OpenCost：成本分摊（唯一没走完的一项）

**是什么**：按 namespace / 工作负载算成本的组件。

**实测状态**：部署 2/2 Running、接口可达、价格 ConfigMap 挂上了、必需指标也在 Prometheus 里，但 `/allocation/compute` 返回空。四次尝试（重装、改 internal.enabled、补 requests 指标、重启）都没算出数值。

**判断**：机制通、数字没有。缺的是 OpenCost 内部指标聚合链路的某一环，没继续深挖。

**关键知识点**：这类组件算的是**分配量（request）而不是用量**，所以它依赖的 `kube_pod_container_resource_requests` 恰恰是前面为了保控制面精简抓取时最容易丢的指标。要继续排查，方向是把它的 Prometheus 查询语句单独拿出来执行，看是"查不到"还是"查到了但聚合为 0"。

**为什么这项没做完也不影响整体价值**：排队、配额、观测、弹性、回滚这些才是"算力池能不能被信任"的硬指标。成本是管理视角的加分项。

## ⑨ 判官卡：监控要不要"全装"

```
选项 A  默认全装（本次明确不做）
  优点：开箱即用，面板多
  缺点：十几个抓取目标 × 15s 把低档云盘 IOPS 吃满，etcd 假死

选项 B  裁剪着装（本次）
  优点：只留必要指标，控制面稳定
  缺点：很多默认面板没数据；要自己写 exporter 和 dashboard

判据：监控本身不能成为故障源。
      在 8G 内存 + 入门云盘上，"装了会自动拖死系统"的组件必须先调参再装。
```

## ⑩ 这一章的坑（现象 / 根因 / 防）

```
现象：装完监控一段时间后，所有 kubectl 命令 connection refused，
      但 CPU 97% 空闲、内存还剩 3G
根因：TSDB 写入吃满 IOPS，etcd 落盘被拖到分钟级，API Server 健康检查失败
防：不要看 CPU 内存，看 etcd 日志的耗时；装之前就裁剪抓取目标和间隔

现象：官方 DCGM exporter 起不来
根因：它依赖 WSL 里不存在的设备访问方式
防：自建 nvidia-smi 轮询 exporter，指标定义保持一致

现象：systemd 里的 exporter 报"文件不存在"，手动能跑
根因：systemd 的默认 PATH 里没有 WSL 的 nvidia-smi 路径
防：单元里显式 Environment=PATH=/usr/lib/wsl/lib:...

现象：反向隧道断开后不会自己恢复
根因：它是普通进程，没被托管
防：和业务服务一样用 systemd 托管，打开保持连接与断线重试选项

现象：KEDA 扩到 4 个副本，只有 1 个 Running
根因：卡数硬性限制，其余 Pending —— 这是正确形态不是故障
防：看 Events 确认是 Insufficient，交给 Kueue 排队

现象：注入明显错误的版本，金丝雀分析却判定成功
根因：检测脚本以 0 退出，平台只判断"Job 是否跑完"
防：检测逻辑不达标时必须 exit 1

现象：网络延迟实验创建被准入拦截
根因：direction 写 both 时必须同时指定 targets
防：先用单向 to/from，或把目标写全

现象：OpenCost 接口有响应但金额全是 0
根因：它算 request 分配量，而 kube-state-metrics 的 requests 指标被精简掉了
防：精简抓取时按白名单保留 requests / limits 指标，间隔可放长但不能少
```

**一句话总结这一章**：治理平面八项，七项全过。排队（Kueue）让"能跑"变成"能等"，弹性（KEDA）让"想要多少"和"能给多少"分层，观测让问题"看得见"，chaos 让韧性"可验证"，Argo 让发布"退得回"。最大的教训只有一条——**监控本身不能成为故障源**。
