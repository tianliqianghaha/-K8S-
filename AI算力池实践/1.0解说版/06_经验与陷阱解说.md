# 06 · 经验与陷阱解说（判断依据比命令更重要）

> **这一章在整件事的哪一步**：贯穿全册。前面五章讲"怎么搭"，这一章讲"出事怎么判断、动手前怎么防"。
> **这一章在干什么**：把实测踩过的坑按层次分组，只记经验和判断方法，不记错误命令。遇到类似现象时先查这里。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `06_经验与陷阱.md` 全部 40 条 + `07_速查卡.md` 故障自查表。

下面把这些经验用初级人员能听懂的方式讲清楚它"为什么这么判断"。

---

## ① 这一章和前五章有什么不同

前五章是"正面":先证明链路通、再证明调度真、最后证明能管。这一章是"反面"——只讲踩过的坑。

**两条铁律**：

```
① 只记经验和判断方法，不记错误命令
   为什么：错误命令的价值在于"当时为什么觉得它是对的"，这个心路历程比命令本身重要。
           而照抄错误命令没有意义。

② 按发生层次分组
   为什么：故障排查的第一步是定位层次，不是找命令。
           Windows/WSL、脚本编码、容器运行时、K8S 调度、网络入口、监控观测、发布回滚
           —— 先确认在哪一层，再找对应的经验。
```

---

## ② Windows 与 WSL 层（6 条）

```
1.「重启」可能没有真的重启
   快速启动恢复内核会话，DISM 收尾没执行
   判断：系统运行时间归零 + HypervisorPresent=True

2. 国内装 WSL 两条路都可能断
   商店不提供平台包，命令行要读 GitHub 清单超时
   正解：镜像代理下 msixbundle + Canonical .wsl 直接导入

3. 平台包注册必须管理员
   包内嵌 Windows 服务组件，普通权限报 0x80073D28

4. 会话一结束服务就"自己死掉"
   WSL 最后一个客户端断开 → 发行版终止 → systemd 停掉所有 unit
   正解：造常驻客户端；配置文件里的空闲超时参数无效

5. WSL 的 GPU 通道不需要装 CUDA
   GPU 能力由 Windows 驱动通过特殊设备节点直通
   在 WSL 里反复装 toolkit 是白费功夫

6. 驱动版本是硬门槛
   新版 PyTorch 要 CUDA 12.8+，560 跑不动；升级驱动是唯一解
```

**这一层最核心的一句**：WSL 不只是"Linux 跑在 Windows 上"，它有自己的生命周期、自己的网络层、自己的 GPU 直通路径。把这三件事当成独立系统对待，坑就少一半。

## ③ 脚本与编码层（3 条）

```
7. PowerShell 读中文脚本会乱码
   Windows PowerShell 5.1 对无 BOM 的 UTF-8 按本地代码页解析
   防：脚本统一存成带 BOM 的 UTF-8

8. 批处理文件里不要出现中文
   代码页与编码不一致，中文被打碎后连带切碎后面的命令
   防：bat 保持纯 ASCII，路径用相对写法

9. 命令行的引号会被吞掉
   Windows 命令行对引号的转义规则与 bash 不同
   防：把请求体写进文件，从文件读取提交
```

**为什么这一层值得单独写**：这些坑跟技术架构无关，纯属环境差异。但它们浪费的时间一点不少——语法错误看起来像脚本逻辑错了，其实是编码。

## ④ 容器运行时层（5 条）

```
10. 新版本 containerd 的配置路径变了，工具会"静默成功"
    containerd 2.x 把 CRI 配置挪到 io.containerd.cri.v1.runtime
    判断：改完必须能读到那段，且 CRI 插件状态是 ok

11. 镜像加速的写法有讲究
    新版不允许"证书目录"和"镜像源列表"同时设置
    防：只走 certs.d 独立目录

12. 容器的启动命令必须写全
    容器名之后的第一个词会被当成命令，镜像的 ENTRYPOINT 不自动生效

13. 某些命令行参数在旧版本里不存在
    防：去掉参数，把等价限制交给 systemd 单元

14. hostNetwork 会带来端口冲突
    所有 Pod 共享宿主网络命名空间
    防：给不同端口，或接受同一时间只有一个副本真正服务
```

## ⑤ K8S 与调度层（9 条）

```
15. 单节点第一步去掉控制面污点
16. Gateway API 控制器不会自动建 GatewayClass
17. 自定义资源的 API 组名容易记错（以集群实际注册的 CRD 为准）
18. 没有 CNI 的节点上普通 Pod 建不出网络（一律 hostNetwork）
19. 只有宿主网络还不够，GPU 需要 runtimeClassName
20. 打污点挡不住 DaemonSet（它自带容忍所有污点，要用节点亲和性排除）

21. time-slicing 是超卖，不是分享
    最反直觉的一条：预期 OOMKilled，实际是两个进程缩小份额勉强共存，
    把整卡吃到 98%。没有报错比报错更危险。

22. 节点会"假死"又自己回来，别急着重建
    kubelet 在 WSL 上因 socket 丢失反复重启，每次都给容器发终止信号

23. 配额拒绝和调度失败是两回事
    Forbidden（API 层）/ Pending（调度层）/ OOMKilled（运行层）
    三者不要混
```

**这一层的总原则**：先看 Events 原文，再判断层次。不要在"起不来"三个字上做推理。

---

## ⑥ 网络与入口层（3 条）

```
25. 云主机访问自己的公网 IP 会超时
    云平台不支持"自己绕出去再回来"
    防：内部验证走回环/私网，公网验证从外部发起

26. 自签证书在客户端侧必须显式跳过校验
    WebSocket 客户端默认校验证书，自签必然失败，且报错不明显

27. 反向隧道进程自己也需要被托管
    隧道是普通进程，断了不会自己恢复
    防：systemd + 保持连接 + 断线重试
```

## ⑦ 监控与观测层（4 条）

```
28. 监控会把低配云盘上的控制面拖死（本次最大的坑）
    现象：所有命令 connection refused，但 CPU 97% 空闲、内存剩 3G
    根因：TSDB 写入吃满 IOPS → etcd 落盘分钟级 → API Server 健康检查失败
    判断：不看 CPU 内存，看 etcd 日志的"请求耗时过长"和压缩耗时

29. vmstat 的列很容易看错
    倒数第二列才是空闲；把"空闲 89%"看成"IO 等待 91%"方向完全相反

30. 容器指标在 WSL 上要用替代方案
    DCGM 起不来 → 自建 nvidia-smi 轮询 exporter，数值真、粒度粗

31. systemd 单元的 PATH 很短
    WSL 把 NVIDIA 工具放在非标准路径，要在单元里显式补
```

## ⑧ 发布与回滚层（3 条）

```
32. 分析模板的失败必须体现为"非零退出"
    平台只判断 Job 是否成功退出，不读输出内容

33. 命令行工具不认识自定义资源
    kubectl set image 不认 Rollout CRD，用通用 patch 直接改字段

34. 混沌实验的方向参数有约束
    direction=both 必须同时指定 targets，否则 webhook 拒绝
```

## ⑨ 几条方法论（35~40 条，最值得背下来）

```
35. 先证明链路通，再优化性能
    三个实验的顺序不是随便排的：先应用层打通（变量最少）→ 上调度语义 → 加治理。
    每一步只引入一类新变量，出问题时范围可控。

36. 每加一个组件，先问它吃多少内存和 IOPS
    这套机器上所有事故都来自资源耗尽，不是配置写错。
    装之前先算账，装之后立刻看 etcd 的耗时指标。

37. 不可靠的底座上，把关键服务挪出依赖链
    kubelet 在 WSL 上会反复重启，这是底座问题。
    推理服务因此放在 systemd，K8S 只负责"谁有资格用卡"。
    这不是妥协，是分层。

38. 回滚路径要在动手前就写好
    时间切片、监控调参、Rollout 演示，每一步都先想清楚怎么退。
    实测中回滚救回来两次（显存打满、控制面假死）。

39. 成本类组件对指标完整性极其敏感
    它算的是"分配"不是"用量"，依赖 requests 指标族。
    精简抓取时最容易剔掉的正是它们。

40. 同一个问题，判断依据要选对
    "看起来一切正常但服务不可用"遇到两次：
    显存打满前的平静、etcd 被拖死（CPU 97% 空闲）。
    两次都说明：选错指标就等于没有监控。
    GPU 负载看显存和温度，控制面健康看 etcd 落盘耗时。
```

## ⑩ 判官卡：遇到故障先看什么

```
选项 A  先看 CPU 和内存
  优点：最直觉
  缺点：在这套环境里 97% 空闲 + 剩 3G 时系统照样假死，属于假信号

选项 B  按层次选判据（本次）
  网络入口层  → /health 的 agents / queued / streaming
  GPU 负载    → 显存、温度、利用率（nvidia-smi）
  调度层      → Events 原文：Forbidden / Pending / OOMKilled
  控制面健康  → etcd 日志的请求耗时、压缩耗时
  推理服务    → vLLM /health + 显存是否异常

判据：选错指标就等于没有监控。定位层次比找命令更重要。
```

## ⑪ 这一章的坑补充（判断依据选错的典型）

```
现象：显存从 17.7G 掉到 300M，内存和 CPU 都很好看
根因：vLLM 进程被 kubelet 重启杀掉
防：查 journalctl -u vllm 末尾，看是不是收到终止信号；
    别被"内存充足"误导

现象：kubectl 全部 connection refused，CPU 97% 空闲
根因：etcd 被监控写入拖死
防：看 etcd 日志的压缩耗时（正常毫秒级，出问题分钟级）

现象：两个 vLLM 共存，显存 98% 但没有 OOM 报错
根因：time-slicing 的假共享，进程各自缩小份额
防：显存 > 23G 立刻停，不要等 OOM 信号
```

**一句话总结这一章**：40 条经验里，真正要背下来的只有方法论那六条——**先链路后治理、装组件先算账、关键服务挪出不可靠底座、动手前写回滚、成本组件护住指标、判断依据要选对**。其余 34 条都是这六条的具体投影。
