# 01 · 本地 GPU 节点解说（把 Windows 变成"容器里能用 GPU 的 Linux 节点"）

> **这一章在整件事的哪一步**：动手前检查 →【地基：本机推到"容器里能看到 3090"】→ 第 2 章起云端控制面。
> **这一章在干什么**：把 Windows 这台机器，变成一张能让容器用上 GPU 的 Linux 节点。三道闸门全过，才允许它去 join 云上集群。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `01_第1章_本地GPU节点.md` + `scripts/local/` 下的 WSL 安装与初始化脚本 + `06_经验与陷阱.md` 第一、三节。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① 先记住这一章的原理：GPU 不是"装"进 Linux 的

初级人员最容易走弯路的地方：以为要在 WSL 里装 CUDA toolkit，容器才能看到显卡。

真相是——**GPU 能力是 Windows 驱动透过 WSL 的虚拟化层，把设备节点和驱动库一路递给容器的**：

```
Windows NVIDIA 驱动（621.24）    真正管卡的是它，不是 Linux
        ↓ 虚拟化直通
WSL 里的 /dev/dxg                 GPU 的虚拟化入口（一个设备节点）
        ↓ 自动挂载
NVIDIA 用户态库                   驱动配套的动态库，随 WSL 挂进来
        ↓ nvidia runtime 注入
容器                             拿到 /dev/dxg + 库 → nvidia-smi 看到 3090
```

所以：$\text{容器里能不能看到卡} \neq \text{装没装 CUDA toolkit}$，而是看**驱动版本对不对、运行时有没有把设备节点注入进去**。在 WSL 里反复装 toolkit 是白费功夫。

---

## ② 动手前确认的三件事（不确认会白折腾半天）

```
① 虚拟化是否真的开着       HypervisorPresent 必须是 True
   为什么：WSL2 不是"翻译层"，是跑在 Hyper-V 上的轻量虚拟机，没有硬件虚拟化起不来

② 驱动版本                 必须 ≥ 570（本次 621.24），显存 24576 MiB
   为什么：新版 PyTorch 用 CUDA 12.8 编译，560 驱动会直接报
          "The NVIDIA driver on your system is too old"。这是硬门槛，只能升级

③ C 盘可用空间             ≥ 60G
   为什么：WSL 虚拟磁盘 + 4.5G 模型权重 + 容器镜像都要放这里
```

三件事里最坑的是第一件：BIOS 里开了虚拟化，Windows 里也显示支持，但功能没生效——因为"重启"没有真的重启。

---

## ③ 打开两个 Windows 功能 + 关快速启动

```
Microsoft-Windows-Subsystem-Linux    WSL 功能本体
VirtualMachinePlatform               虚拟机平台（WSL2 依赖它）

关快速启动 + 设 hypervisorlaunchtype=auto + 完整"重启"而不是"关机再开"
```

**为什么关快速启动这么重要**：它会把"重启"变成"恢复内核会话"。DISM 的功能收尾没执行，hypervisor 也没拉起来。表面上看重启了，实际什么都没变。

**怎么判断真的重启了**：看系统运行时间是否归零、`HypervisorPresent` 是否为 True。这两个信号比"我确实点了重启"可靠得多。

## ④ 装 WSL 平台和 Ubuntu：两条路都不走 Store

```
平台包    国内商店不提供；命令行 wsl --install 又要读 GitHub 上的发行版清单，超时
          正解：从镜像代理下官方 msixbundle，用【管理员权限】注册
          为什么必须管理员：这个包内嵌 Windows 服务组件，普通权限报 0x80073D28

发行版    Ubuntu 24.04，从 Canonical 镜像站下 .wsl 格式直接导入
          为什么不用商店：同一个原因，国内商店这条路不通
          .wsl 是官方支持的格式，不比商店安装低一档，只是换了获取渠道
```

**判官卡：为什么要绕这么一大圈**

```
选项 A  商店 / wsl --install
  优点：命令最短
  缺点：国内两条路都不通，卡在下载阶段

选项 B  镜像代理 + 官方 .wsl 导入（本次）
  优点：走的是官方包和官方镜像，只是换了下载渠道，稳定可复现
  缺点：步骤多，要校验 SHA256

判据：能跑通的路径才是好路径。国内环境"绕一圈"反而是最短路径。
```

## ⑤ 基础配置：内存、systemd、用户、常驻

**内存边界**：宿主只有 16G，WSL 分 11G / 8 核，给 Windows 自己留 5G，swap 8G 放 `C:\WSL`。这是硬约束下的分配，不是性能调优。

**systemd**：WSL 默认不是完整的 init 环境。cgroup2 挂上之后 systemd 才能接管，后面 vLLM、Agent、exporter 才有地方托管。验收看 `systemctl is-system-running` 和 `stat -fc %T /sys/fs/cgroup` 返回 `cgroup2fs`。

**常驻客户端：这一章最关键的一步**

```
WSL 的生命周期规则：最后一个客户端断开 → 整个发行版终止 → systemd 停掉所有服务

典型现象：
  vLLM 明明加载完模型、健康检查返回 200
  命令一结束，显存瞬间从 20G 掉回 300M
  日志里收到 SIGTERM 优雅退出

正解：造一个 24 小时不退出的客户端（计划任务每分钟触发一次睡眠进程）
      第一个实例跑满 24 小时，后续触发因"实例未结束"被自动跳过

注意：配置文件里的空闲超时参数（vmIdleTimeout）不足以保证发行版存活，实测无效。
```

**为什么必须这样**：systemd 是"发行版内"的服务管理器，管不了"发行版本身被 Windows 关掉"。这是两层生命周期，必须用 Windows 侧的手段兜住。

## ⑥ GPU 工具链：把设备节点和库递给容器

```
① nvidia-ctk 配置 containerd       让运行时认识 NVIDIA 设备
② 手工补 nvidia runtime 配置        containerd 2.x 的 CRI 配置路径变了
③ 装 kubelet / kubeadm 并锁版本    为第 2 章入集群准备，但本章不启动 join
④ 镜像加速走 certs.d/hosts.toml    不要动主配置里的 mirrors 段
```

**第②条的详细原因**：containerd 2.x 把 CRI 配置从旧插件路径挪到了 `io.containerd.cri.v1.runtime` 下，nvidia-ctk 1.20 的工具版本没跟上——**报告"配置成功"，但配置文件里一个字都没写进去**。这是典型的"静默成功"，判断方法只有一个：改完必须能读到那段配置，且 CRI 插件状态是 ok。

**第④条的详细原因**：新版本 containerd 不允许"证书目录"和"镜像源列表"同时设置，冲突会让整个 CRI 插件加载失败、容器服务不可用。所以只走独立的 `certs.d` 目录方式。

## ⑦ 三道闸门：地基验收

每件事装完，都要用一条能跑完的命令证明它真的对了。这三道是地基章的门禁：

```
① systemd 已运行 + cgroup2fs
   证明：服务能被托管，systemd 不只是装上了

② WSL 里 nvidia-smi 看到 3090 / 24576 MiB / 621.24
   证明：Windows 驱动通道通了，卡能被 Linux 侧看到

③ 容器里 nvidia-smi 看到 3090 / 24576 MiB / 621.24
   证明：nvidia runtime 注入成功，GPU 通道走完了最后一米
```

**为什么必须是三道而不是一道**：每一道对应剖面图里的一层。②过了③没过，说明卡在运行时注入；①没过，说明 systemd 根本没接管，后面所有服务都无处托管。分层验收，故障范围一眼锁定。

## ⑧ 判官卡：推理服务放 systemd 还是 K8S

```
选项 A  放 K8S Pod（本次刻意不做）
  优点：声明式、统一调度
  缺点：kubelet 在 WSL 上会因运行时 socket 丢失反复重启，
        每次重启都给容器发终止信号 → vLLM 被反复杀掉

选项 B  放 systemd（本次）
  优点：绕开 kubelet 的不稳定，服务独立托管
  缺点：失去 K8S 的声明式管理，要自己写 unit 文件

判据：不可靠的底座上，把关键服务挪出依赖链。
      K8S 只负责"谁有资格用卡"，不负责"把推理跑稳"。这不是妥协，是分层。
```

## ⑨ 这一章的坑（现象 / 根因 / 防）

```
现象：启用了 WSL 功能，重启后状态仍未生效，系统运行时间还是旧的几十小时
根因：Windows 快速启动恢复了内核会话，DISM 收尾没执行
防：关快速启动（powercfg /h off），确认是完整"重启"，看 HypervisorPresent

现象：注册平台包报 0x80073D28
根因：包内嵌 Windows 服务，普通权限注册不了
防：管理员身份注册，这一步没有绕过方式

现象：vLLM 加载完、健康 200，命令一结束显存掉回 300M
根因：WSL 在最后一个客户端断开后终止整个发行版，systemd 随之停掉所有 unit
防：造常驻客户端（计划任务睡眠 24h）；别指望 vmIdleTimeout

现象：vLLM 启动即退出，报驱动太旧，附带 CUDA 12.6
根因：新版 PyTorch 用 CUDA 12.8+ 编译，560 驱动跑不动
防：升级 Windows 驱动到 570+、重启 WSL；换旧版框架是把问题往后拖

现象：nvidia-ctk 说配置成功，但容器里看不到卡
根因：containerd 2.x 的 CRI 配置路径变了，工具写错位置且静默成功
防：手工按新路径补配置，改完必须能读到那段，CRI 插件状态为 ok

现象：加了镜像源之后 CRI 插件直接报错，容器服务不可用
根因：新版 containerd 不允许"证书目录"和"镜像源列表"同时设置
防：只走 certs.d 独立配置目录，不动主配置的 mirrors 段

现象：批处理 bat 双击后满屏 "'ocal" 不是内部命令
根因：中文路径在无 BOM 的代码页下被撕碎，连带切碎后面的命令
防：bat 保持纯 ASCII，路径用脚本自身所在目录的相对写法
```

**一句话总结这一章**：地基做的事看着琐碎（开功能、装平台、导镜像、划内存、开 systemd、保活、配运行时），但每一件都是在消除"节点起不来"和"容器看不到卡"这两类隐患。三道闸门全过，才配去入集群。
