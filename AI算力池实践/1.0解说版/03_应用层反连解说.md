# 03 · 应用层反连解说（任务怎么送到卡上）

> **这一章在整件事的哪一步**：节点已入集群、GPU 已上报 →【把请求链路第一次真正接起来】→ 第 4 章验证调度语义。
> **这一章在干什么**：用"云端 gateway + 本地 Agent + WebSocket 反连"接出一条完整链路，拿到首字延迟与并发拐点，并证明重启 / 断网时任务不丢。本章刻意不碰 kubelet 调度。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `03_第3章_实验一_应用层反连.md` + `scripts/app/gateway/main.py` + `scripts/app/agent/main.py` + `scripts/app/bench/gw_bench.py`。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① 先看整条链路：一个请求的完整往返

```
去程：
客户端 curl
  │  HTTPS + Bearer API Key
  ▼
Envoy Gateway（NodePort 31154，自签 TLS）
  ▼
云端 ai-gateway（FastAPI / uvicorn）
  ├─ 鉴权      Authorization: Bearer / X-API-Key
  ├─ 限流      每 key 每分钟 60 次滑动窗口，超限 429 + Retry-After
  ├─ 幂等      Idempotency-Key 命中已完成任务直接回缓存
  ├─ 任务队列  queued → streaming → done
  └─ 派发      通过 /agent 的 WebSocket 推任务
  │  WSS 出站长连接（本地主动连云端，所以 NAT 后面也能被派活）
  ▼
本地 ai-agent（systemd 托管）
  ├─ 收任务 → 调本地 vLLM 流式接口
  ├─ 增量回传 → 每吐一个 token 发一个 chunk
  └─ 不丢任务 → 断线保留 inflight，重连后 resume
  ▼
本地 vLLM v0.34.0（Qwen2.5-7B-Instruct-AWQ）

回程：token chunk 原路回流 → agent → WSS → gateway → SSE → 客户端
```

**为什么必须反连**：WSL 在本机 NAT 后面，没有固定可达地址。云端想主动连本地是连不上的。让边缘节点主动连云端是标准做法——**连接方向由内向外，NAT 就不是问题**。

## ② Envoy Gateway：公网入口

**是什么**：实现了 Gateway API 的入口网关，负责 TLS 终止和七层路由。

**为什么必须有它**：ai-gateway 只是个跑在 Pod 里的 Python 服务，没有公网地址、不会处理证书。Envoy 是站在它前面的门卫——对外提供 HTTPS，对内转发到服务的 ClusterIP。

**本章两个容易踩的点**：

```
① GatewayClass 不会自动创建
   1.10 版本把这个职责交给了使用者，控制器日志反复打"没有已接受的 GatewayClass"
   正解：手动建一个指向该控制器名的 GatewayClass

② 自签证书的 SAN 必须同时写公网和私网 IP
   实验环境没有域名，SAN 里只写域名会导致 IP 访问时证书校验失败
   客户端侧 curl -k 跳过校验；Agent 侧显式关闭主机名和证书校验
```

## ③ ai-gateway：把"请求"变成"有状态的任务"

这是本章最核心的一段代码（374 行）。它做的不是简单转发，而是把每个请求变成一个可追踪、可恢复的对象。

**核心数据结构**：

```
Task:  id / payload / idem / chunks / status / usage / waiters
```

**四个机制逐个讲**：

```
鉴权      Bearer API Key；缺头或 Key 不对 → 401
         为什么：这是公网入口，不鉴权等于把家里的显卡开放给全网

限流      每 key 每分钟 60 次滑动窗口，超限 429 + Retry-After
         为什么：防止单个调用者把唯一的卡打满（3090 的容量上限实测是 8 并发）

幂等      Idempotency-Key 命中 done 直接回缓存
         为什么：网络超时后客户端会重试，没有幂等就会重复扣算力、重复生成

队列      queued → streaming → done
         dispatch() 从 agents 里挑一个 WS 推任务；没有 Agent 时保持 queued
         （关键：不返回 503！断网期间请求挂在队列里，恢复后继续）
```

**为什么"没有 Agent 不返回 503"是重要的设计**：这是断网 30 秒不丢任务的前提。如果直接返回错误，客户端要么失败要么重试；挂在队列里，恢复后原样返回。

## ④ 任务状态机：不丢任务的根本

```
queued         等 Agent 接手
  │ dispatch()
  ▼
streaming      逐 chunk 回传
  │ done()
  ▼
done           结果缓存，幂等键可命中

异常分支：
Agent 断线  → 未产出 chunk 的任务退回 queued
Agent 重连  → resume：把未完成任务连同已缓冲的 chunk 一起上报，接着吐，不从头来
```

初级人员常问："为什么不用一个简单的请求-响应？"因为流式推理是长连接，一次生成可能持续几十秒。中间断网、重启都可能发生。只有把任务做成有状态对象，才能在这些事故里保持不丢。

## ⑤ 本地 vLLM：真正跑推理的那张卡

```
镜像        vllm/vllm-openai:latest（v0.34.0）
模型        Qwen2.5-7B-Instruct-AWQ（4bit，权重 4.5G）
启动时间    约 150 秒
显存占用    约 17.7G / 24G
```

**关键参数逐个讲**：

```
--gpu-memory-utilization 0.72
  为什么是 0.72：WSL 下 0.80 会 OOM，0.72 是实测安全线

--enforce-eager
  为什么不捕获 CUDA graph：降低峰值显存，代价是速度略慢

--enable-prefix-caching
  为什么开：KV 复用，长对话省钱省时间
```

**为什么用 systemd + ctr 而不是 K8S Pod**：kubelet 在 WSL 上会因运行时 socket 丢失反复重启，每次重启都给容器发终止信号。vLLM 加载一次模型要 150 秒，被杀一次就白等。systemd 绕开了这个不稳定层。

## ⑥ 本地 Agent：反连的执行端（179 行）

```
重连退避    1s → 2s → 4s → 8s → 10s 封顶
           为什么退避：gateway 重启时如果所有 Agent 同时狂连，会把它再打挂一次
并发上限    semaphore MAX_CONCURRENT = 8
           为什么是 8：第 4 章会实测并发拐点在 8 与 16 之间，8 是这张卡的容量上限
resume      重连时把未完成任务连 buffer 一起上报
SSL         自签证书：check_hostname=False + verify_mode=CERT_NONE
```

Agent 用 systemd 托管，和 vLLM 一样的原因——不依赖 kubelet。

**启动顺序很重要**：先 gateway 就绪，再起 Agent。顺序反了，Agent 只会不断重连，`/health` 里 `agents=0`，看着像网络问题，其实是启动顺序问题。

## ⑦ 四道闸门：怎么证明真的通了

```
闸门①  首字延迟 TTFT
       实测 0.116 / 0.116 / 0.120 / 0.129 / 0.144 秒
       平均 0.125 秒，验收线 1.5 秒，余量 12 倍
       └ 说明整条链没有多余等待

闸门②  并发曲线出现拐点
       1/4/8 并发：0.43 / 0.37 / 0.47 秒
       16 并发：3.05 秒，P95 2.81 秒
       └ 拐点在 8 与 16 之间 → 8 是这张卡的容量上限
         第 5 章的排队设计就以这个数字为基准

闸门③  gateway 重启
       Agent 日志：disconnected → connecting → welcome
       1 秒重连，重启后请求照常 200

闸门④  断网 30 秒
       用防火墙规则切断到云端的出口，期间发 3 个请求
       └ 全部 200 返回，恢复后 1 秒重连
       这是状态机那一节的直接证据
```

附加的三项功能验证：401 证明鉴权生效、第二次同幂等键返回 `idempotent_hit=true` 证明缓存命中、打满 60 次出现 429 证明限流生效。

## ⑧ 判官卡：队列放应用层还是放 K8S

```
选项 A  应用层队列（本次）
  优点：变量最少，不依赖 kubelet 调度；断网恢复由自己控制，行为可预测
  缺点：K8S 看不见这个队列，无法用原生调度语义管理

选项 B  直接上 Kueue / K8S 原生排队
  优点：声明式、统一治理
  缺点：本章目的只是"证明链路通"，先上调度会把变量搅在一起

判据：先证明链路通，再优化性能，最后才谈治理。
      第 5 章上 Kueue 时，本章的队列就是它的对照组。
```

## ⑨ 这一章的坑（现象 / 根因 / 防）

```
现象：Gateway 一直未编程，控制器日志反复说没有已接受的 GatewayClass
根因：1.10 不再自动创建 GatewayClass
防：手动建一个，指向 gateway.envoyproxy.io/gatewayclass-controller

现象：Agent 一直连不上，health 里连接数为 0，也没有明显报错
根因：WebSocket 客户端默认校验证书，自签必然失败
防：实验环境显式关闭主机名校验与证书校验；生产换真实 CA

现象：/health 里 agents = 0，但 Agent 服务显示 active
根因：启动顺序反了，或 gateway 刚重启还没就绪
防：先 gateway 再 Agent；看 journalctl -u ai-agent 的 connected / welcome

现象：请求一直挂着不出字
根因：任务进了 queued 但没有 Agent 接手，或 vLLM 卡住
防：看 /health 的 queued 数、本地 vLLM 的 health、显存是否异常

现象：网关重启后 Agent 重连风暴，Gateway 又被打挂
根因：Agent 没有退避，同时狂连
防：1→2→4→8→10s 封顶的退避算法

现象：云主机内部请求自己的公网 IP 超时，从外部请求正常
根因：云平台不支持"自己绕出去再回来"的访问方式
防：内部验证走回环或私网 IP，公网验证必须从外部发起

现象：命令行发带 JSON 的请求，服务端报 JSON 解析错误，Linux 里却正常
根因：Windows 命令行对引号的转义规则与 bash 不同
防：把请求体写进文件，用从文件读取的方式提交
```

**一句话总结这一章**：把请求变成有状态任务，让本地主动连云端，用鉴权 / 限流 / 幂等 / 队列把公网入口守住，用断线回退和 resume 把任务保住。四道闸门全过，才算"链路通"。
