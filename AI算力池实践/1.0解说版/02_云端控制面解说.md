# 02 · 云端控制面解说（云上大脑 + 本地节点入集群）

> **这一章在整件事的哪一步**：第 1 章三道闸门全过 →【把本地 GPU 节点真正注册进集群】→ 第 3 章起应用层反连。
> **这一章在干什么**：云上起一台控制面，让 `nvidia.com/gpu` 出现在 K8S 的 Capacity 里。从此算力池有了两种身份——云端负责裁决，本地负责干活。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `02_第2章_云端控制面.md` + `06_经验与陷阱.md` 第四、五节。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① 云端只买"大脑"，不买"肌肉"

```
规格      4C8G 抢占实例（按量 + SpotAsPriceGo，无保护期）
地域      香港区
镜像      Ubuntu 26.04（24.04 只有带驱动的 100G 变体，控制面不需要）
系统盘    100 GiB ESSD entry，随实例释放
公网      按流量，峰值 100 Mbps
自动释放  12 小时后兜底
```

**为什么用抢占实例**：实验是小时级别的，被回收了大不了重建。控制面这台机器只跑 API Server、etcd 和控制器，真正吃算力的是家里的 3090。为它付高价的钱没有意义。

**安全组只放行三个端口，且只对自己的出口 IP**：

```
6443    kube-apiserver（本地节点要连）
10250   kubelet（云端排障用）
31154   Envoy Gateway 入口（第 3 章）
```

这是最小暴露面。实验环境里把这些端口对全网开放，等于把自己的集群管理面挂在网上。

## ② 装控制面：三个关键决定

```
① containerd 开 SystemdCgroup = true
② 关 swap
③ kubeadm 初始化时：私网 IP 做 advertise address，公网 IP 写进证书 SAN
```

**第①条为什么重要**：cgroup 是 Linux 限制容器资源的机制，有 cgroupfs 和 systemd 两种驱动。kubelet 从 1.22 起默认用 systemd，containerd 这边如果还是 false，两者"说不同的语言"，Pod 会反复 CrashLoop。这是全项目最容易翻车的点。

**第②条为什么**：K8S 要求内存管理可预测。开了 swap，Pod 可能偷偷用磁盘当内存，调度器以为还有余量继续塞，最后整节点被拖垮。K8S 的设计哲学是"内存不够就明确 OOM 或驱逐，不靠 swap 模糊地苟住"。

**第③条是最容易埋雷的地方**：本地节点是从**公网**连 6443 的，而 kubeadm 默认按 advertise address（私网 IP）签证书。不把公网 IP 写进证书的 SAN，节点 join 时报的是 TLS 错误，看着像网络问题，其实是证书不认这个地址。

---

## ③ 第一件必须做的小事：去掉控制面污点

```
kubectl taint nodes ai-cp-1 node-role.kubernetes.io/control-plane-
```

**为什么必须做**：控制面节点默认带"不许普通负载调度"的污点。单节点集群里没有第二个节点可去，不去掉它，后面 Envoy Gateway 的证书生成、监控组件全部 Pending。

**什么时候做**：装任何业务组件之前。往后拖，你会面对一堆查不出原因的 Pending。

---

## ④ Cilium：换掉 kube-proxy

**是什么**：基于 eBPF 的网络数据面，这里用来代替 kube-proxy。

**为什么必须有它**：K8S 集群里 Pod 之间要通信，需要一个数据面把 Service 的虚拟 IP 翻译成真实 Pod IP。默认方案是 kube-proxy，用 iptables 做转发，规则多了以后性能下降。Cilium 用 eBPF 在内核里直接处理，少一层转发。

**为什么这套环境要换**：云端只有 8G 内存，后面还要装一堆治理组件。少一个组件、少一层转发，就多一分余量。验收标志是节点 Ready，且 `kube-system` 里**没有** kube-proxy。

---

## ⑤ device plugin：让集群"认识" GPU

这是本章最需要讲清楚的对象，也是初级人员最容易搞混"装在哪"的东西。

**K8S 原生只懂 CPU 和内存**。`nvidia.com/gpu` 这种扩展资源，必须有人告诉它——这个人就是 device plugin。

```
逻辑上：它是一个 DaemonSet 对象，声明在云端的 kube-system 命名空间
        由云端提交，对象本身存在 etcd 里

物理上：它被节点选择器限定，只在 ai-gpu-1（本地 WSL 节点）上运行
        云端控制面节点没有 GPU，选择器不匹配，那里不会起这个 Pod

它做什么：读取设备节点和 NVML 库，通过 kubelet 把
         nvidia.com/gpu = 1 写进 Node 的 capacity 和 allocatable
```

**为什么必须先做这一步再 join**：DaemonSet 的规则是"每个匹配节点跑一个副本"。先在云端把"上报器"部署好并锁定目标节点，此时它因为没有匹配节点而等待；本地节点一 join，它立刻起来上报。顺序反过来，节点上来后集群不认识 GPU，你还要排查为什么 Capacity 里没有卡。

**镜像拉不到怎么办**：官方镜像 `nvcr.io/nvidia/...` 国内拉不到，走云端中转——云端拉取 → 导出 → 传到本地 → 导入。这是国内环境的常态，不是故障。

## ⑥ 本地 join：token + CA hash 是双向信任

云端生成加入凭证，本地 kubelet 拿着它去 API Server 注册。

```
token      证明"这个节点被允许加入"
CA hash    证明"我要连的集群是真的"，防止连到冒牌 API Server
```

注册完成后，kubelet 在 Node 对象上持续上报状态和资源清单。

**注意方向仍然是本地主动连云端**——和第 3 章的 WSL 反连是同一个思路：不管本地在什么 NAT 后面，由内向外连接总是通的。

---

## ⑦ 打污点 + 验收：让"有卡"变成"受控"

节点注册进来后，最后一步是给它打污点 `nvidia.com/gpu=present:NoSchedule`。意思是：这张卡默认不接活，只有明确声明"我能忍这个污点"的 Pod 才准上来。这样普通负载不会偷偷占掉推理卡。

验收看三样：

```
两个节点 Ready
capacity / allocatable 都是 nvidia.com/gpu = 1
污点存在
```

**埋两个伏笔，后面会用到**：

```
① 污点挡不住 DaemonSet
   DaemonSet 通常自带"容忍所有污点"，要排除得用节点亲和性

② 本地节点刻意不装 CNI，GPU Pod 一律 hostNetwork
   代价是云端 kubectl logs 到本地节点会超时（NAT 地址上的 10250 够不着）
   改成让 Pod 把结果写进 hostPath，再本地读文件
```

## ⑧ 判官卡：GPU 节点要不要装 CNI

```
选项 A  装 CNI（常规 K8S 做法）
  优点：Pod 有集群内 IP，Service 可用，kubectl logs 正常
  缺点：本地节点在 WSL NAT 后，Pod IP 跨公网不可路由；
        kubelet 在 WSL 上本就不稳，再叠一层 CNI 会多出
        "建 sandbox 失败"的故障点

选项 B  不装 CNI + hostNetwork（本次）
  优点：跨公网靠 WSS 反连，不依赖 Pod 网络；少一层故障面
  缺点：Pod 无独立 IP；端口共享宿主，两个副本不能同端口；logs 超时

判据：CNI 解决"集群内 Pod 互通"，但这套系统的跨公网链路靠反连、
      卡的使用资格靠 K8S 裁决 —— Pod 网络对这两个目标零贡献。
      不是妥协，是分层。
```

GPU Pod 还必须配 `runtimeClassName: nvidia`，因为默认 runc 不会把 GPU 设备节点和驱动库注入容器，加了 hostNetwork 也照样看不到卡。

## ⑨ 这一章的坑（现象 / 根因 / 防）

```
现象：某个组件永远 Pending，事件里写"没有节点能容忍污点"
根因：单节点集群没去掉控制面污点
防：装任何业务组件之前先去掉；这是本章第一件必须做的小事

现象：节点 join 报 TLS 错误，看着像网络不通
根因：kubeadm 初始化时没把公网 IP 写进 apiserver 证书的 SAN
防：初始化就带 --apiserver-cert-extra-sans=公网IP，别等 join 失败再补

现象：nvidia-ctk 报告成功，但节点 Capacity 里没有 nvidia.com/gpu
根因：containerd 2.x 的 CRI 路径变了，运行时配置写错位置（静默成功）
防：手工按 io.containerd.cri.v1.runtime 路径补，改完能读到、CRI 状态 ok

现象：device plugin 镜像拉不到
根因：nvcr.io 国内不可达
防：云端拉取 → ctr export → 传本地 → ctr import；或提前导出好镜像

现象：GPU Pod 卡在 ContainerCreating，事件写"建立 sandbox 网络失败"
根因：本地节点没有 CNI，Pod 拿不到网络命名空间
防：这类节点上的工作负载一律 hostNetwork: true

现象：加了 hostNetwork 后容器能创建，但启动即失败，连 nvidia-smi 都跑不到
根因：缺 runtimeClassName: nvidia，设备节点和库没注入
防：显式指定 RuntimeClass 对象 + Pod 的 runtimeClassName 字段

现象：云端 kubectl logs 到本地节点超时
根因：节点宣告的是 WSL NAT 地址，云端访问不到 10250
防：把输出写进 hostPath，再本地读文件。这是已知限制，不是故障

现象：kubectl 突然全部 connection refused，但内存还剩 3G、CPU 空闲
根因：etcd 被磁盘 IO 拖死（详见第 5 章监控大坑）
防：看 etcd 日志里的"请求耗时过长"和压缩耗时，别看 CPU 内存
```

**一句话总结这一章**：云端只做大脑，本地才是肌肉。控制面初始化的三个决定（Cgroup 驱动、关 swap、证书 SAN）、Cilium 替 kube-proxy、device plugin 上报 GPU、join + 打污点——所有动作都指向一个结果：让 K8S 真正认识并管住这张卡。
