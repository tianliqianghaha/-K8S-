# 04 · 资源语义解说（调度是真的）

> **这一章在整件事的哪一步**：第 3 章链路已通 →【换到内核层，验证 K8S 的资源语义】→ 第 5 章加治理。
> **这一章在干什么**：证明 K8S 对 GPU 的调度是真的——同一张卡，要 1 卡能跑、要 2 卡 Pending、配额能卡死、抢占能踢人、断网有明确时序、假共享会出事。

我想要的是每个东西的作用。重点是要讲给初级人员。
已完成分析，共参考 `04_第4章_实验二_资源语义.md` + `06_经验与陷阱.md` 第四节。

下面把这一章里出现的每一个东西，用初级人员能听懂的方式讲清楚它"到底是干什么的、为什么必须有它"。

---

## ① 开工前先腾卡

这一章要把 vLLM 放进 Pod 做验证，必须先停掉第 3 章的 vLLM 和 Agent，把显存从 17.7G 回落到 300MiB 左右。

**为什么**：整张卡只有一张，vLLM 占着的时候，任何 GPU Pod 都拿不到卡。不做这一步，后面所有"1 卡能跑"的验证都会失败，而且报错看起来像调度问题。

---

## ② 两个必要前提（不做就起不来）

```
hostNetwork: true          本地节点没有 CNI，普通 Pod 建 sandbox 会失败
runtimeClassName: nvidia   默认 runc 不注入 /dev/dxg 和 NVML 库
```

第 3 章的 vLLM 走 systemd，绕开了这两项。现在把推理放进 Pod，就必须补齐 K8S 侧的设备注入路径：网络用宿主网络，GPU 用专门的运行时类。两项缺一，Pod 分别卡在 ContainerCreating 或 StartError。

**RuntimeClass 对象要先存在**（`handler: nvidia`），Pod 里写 `runtimeClassName` 才找得到它。

---

## ③ 资源模型：为什么 2 卡一定 Pending

device plugin 上报的是 `nvidia.com/gpu = 1`，这是一个**整数扩展资源**：没有 0.5 卡，也不能超用。

```
请求 1 卡  → Running，容器里 nvidia-smi 看到 3090 / 24576 MiB / 621.24
请求 2 卡  → Pending，事件写：
             FailedScheduling: 0/2 nodes are available:
               1 Insufficient nvidia.com/gpu,
               1 node(s) didn't match Pod's node affinity/selector
```

**关键是理解"Pending + Insufficient"的含义**：调度器根本没把 Pod 放上去。它不是"给了但用超了"（那是 OOMKilled），也不是"不让建"（那是 Forbidden）。

---

## ④ 三层判定：同一个"起不来"，三种原因

这是本章最该建立的心智模型，初级人员最容易在这里混淆：

```
API 层        超 namespace 配额 → Forbidden
              对象都不让建。ResourceQuota 把 team-a 锁在 1 卡，
              第二个 Pod 提交时直接被 API Server 拒绝：
              "exceeded quota: used 1, limited 1"

调度层        节点资源不足 → Pending / Insufficient
              对象建好了，但没有节点能满足资源请求

运行层        给了但用超 → OOMKilled
              调度成功，进程实际吃超了显存/内存被杀
```

**报什么错，就说明卡在哪一层**。不要看到"起不来"就猜，先看 Events 的原文。

---

## ⑤ PriorityClass：抢占是怎么回事

```
ai-low  = 100      低优先级，先占住唯一的卡
ai-high = 10000    高优先级，来了却没地方放
```

调度器为了安置高优先级 Pod，会主动驱逐低优先级 Pod。事件里留下：

```
FailedScheduling: preemption: found a potential placement ... preempting 1 victims
Preempted:        Preempted by pod <uid> on node ai-gpu-1
Killing:          Stopping container cuda
```

**为什么要设 `terminationGracePeriodSeconds: 0`**：让低优先级 Pod 立刻让位，不要拖 30 秒优雅退出。抢占的本质是"资源紧张时让重要的事先做"。

## ⑥ 断网时序：NotReady 与恢复

只切断 kubelet → API Server 的 6443，保留 ssh 以免影响操作：

```
T0        切断
+10..40s  ready=True   KubeletReady      ← 还在宽限期
+50s      ready=Unknown NodeStatusUnknown ← 判定 NotReady

恢复后：
+10s      Unknown
+20s      True                            ← 回 Ready
```

**为什么 50 秒才判 NotReady**：`node-monitor-grace-period` 默认 40 秒，加上心跳周期的余量。这不是"卡住了"，是设计值。

**为什么这段时间 Pod 仍 Running**：`hostNetwork` 不依赖 kubelet 和 API Server 的通信。节点心跳失联不影响已经跑起来的进程。

## ⑦ time-slicing：假共享的代价（本章最反直觉）

配置 device plugin 的 `replicas: 4`，节点的可分配 GPU 数从 1 变成 4。两个 vLLM 各声明 1 卡，都被调度到同一张 3090 上：

```
vllm-a   140 秒就绪，显存 17166 MiB
vllm-b   90 秒内 Running，也声明 1 卡

显存曲线：17167 → 17511 → 23246 → 23526 → 24185（98%）
没有 OOMKilled，两个进程各自缩小份额勉强共存
```

**结论：time-slicing 是超卖，不是分享。**

```
调度器眼里的 4 张卡 = 同一个物理设备的 4 个时间片
底层没有任何显存隔离
四个人都声明 1 卡，不是"每人 1/4"，而是"同时加载时集体逼近上限，谁先崩看运气"
3090 没有 MIG 硬件隔离，真隔离只能靠排队
```

**最反直觉的点**：预期会出现 OOMKilled 的明确信号，实际是两个进程各自缩小份额勉强共存，把整卡吃到 98%。**没有报错比报错更危险**——系统看起来正常，但任何一点额外请求都会把它推过悬崖。

**做完必须精确回滚**：删掉 configMap 和 DaemonSet 的补丁，否则节点永远显示 4 卡，后续所有调度语义都失真。

## ⑧ 判官卡：怎么实现"多人共享一张卡"

```
选项 A  time-slicing（本次验证，验证完回滚）
  优点：一行配置把可分配卡数从 1 变 4，能调度更多 Pod
  缺点：零隔离，显存集体逼近上限，谁崩看运气；没有任何"每人 1/4"的保证

选项 B  MIG 硬件切分
  优点：真隔离，每份显存独立
  缺点：3090 不支持 MIG（只有 A100/H100 等数据中心卡才有）

选项 C  排队（第 5 章 Kueue）
  优点：真隔离，每次只放一个任务上卡，超限的排队等
  缺点：任务要等，不能同时跑多个

判据：消费级显卡没有硬件隔离能力时，"共享"的正确形态是排队，不是超卖。
      time-slicing 只适合"多个轻量推理进程且显存占用很小"的场景。
```

## ⑨ 这一章的坑（现象 / 根因 / 防）

```
现象：GPU Pod 一直 Pending
根因：分两种 —— 配额层 Forbidden（对象都没建）vs 调度层 Pending（Insufficient）
防：先看 Events 的原文，别猜

现象：GPU Pod 卡在 ContainerCreating
根因：本地节点没有 CNI，建不出 sandbox
防：hostNetwork: true

现象：GPU Pod StartError，连 nvidia-smi 都执行不到
根因：缺 runtimeClassName: nvidia
防：先建 RuntimeClass 对象，Pod 里显式引用

现象：kubectl logs 到本地节点超时
根因：节点宣告的是 WSL NAT 地址，云端访问不到 10250
防：让 Pod 把输出写进 hostPath，再本地读

现象：给 GPU 节点打了污点，DaemonSet 照样调度过去
根因：DaemonSet 通常带"容忍所有污点"，污点对它无效
防：用节点亲和性明确排除

现象：两个 Pod 都 Running，但只有一个能监听端口
根因：hostNetwork 下共享宿主网络命名空间，端口冲突
防：给不同端口，或接受同一时间只有一个副本真正服务

现象：time-slicing 后显存冲到 98% 但没有 OOM
根因：两个进程各自缩小份额勉强共存，底层无隔离
防：显存 > 23G 立刻停；这本身是实验结论，不是异常

现象：做完 time-slicing 后节点永远显示 4 卡
根因：configMap 和 DS 补丁没精确回滚
防：按文档逐项移除 args / volumeMount / volume，删 configMap，验证回到 1

现象：节点假死又自己回来
根因：kubelet 在 WSL 上因运行时 socket 丢失反复重启，每次都给容器发终止信号
防：先确认 socket 存在、kubelet 稳定，再判断 Pod 状态是否可信
```

**一句话总结这一章**：GPU 是整数资源，不可切分、不能超用。配额在 API 层拦、调度在资源层拦、OOM 在运行层拦——三层报错对应三种处置。而"共享"的正确答案，在消费级显卡上是排队，不是超卖。
