## 9.1 在干什么

```
应用（无埋点） → 内核 → eBPF 探针（beyla） → OTLP → Collector → Tempo → 查询
```

关键点：**探针在内核层抓 HTTP/gRPC 的进出，应用不需要 SDK、不需要 sidecar、不需要重启**。
这对"接管别人写的服务"特别有用 —— 你不可能给 50 个老服务挨个加埋点。

## 9.2 敲什么

```bash
# ① Tempo（S3 后端）
helm upgrade --install tempo grafana/tempo --version 1.24.4 -n monitoring -f s11-tempo-values.yaml

# ② Collector
helm upgrade --install otelcol open-telemetry/opentelemetry-collector \
  --version 0.120.0 -n monitoring -f s11-otelcol-values.yaml

# ③ eBPF 探针（beyla，注意要 SA + ClusterRole，否则读不到 pod/service/node）
kubectl apply -f s11-beyla.yaml
kubectl -n monitoring patch ds beyla --type=merge \
  -p '{"spec":{"template":{"spec":{"serviceAccountName":"beyla"}}}}'
```

beyla 的关键环境变量：

```yaml
- {name: BEYLA_OPEN_PORT, value: "8080"}                       # 抓哪个端口
- {name: OTEL_EXPORTER_OTLP_ENDPOINT, value: "http://otelcol-opentelemetry-collector.monitoring.svc.cluster.local:4317"}
- {name: BEYLA_KUBE_METADATA_ENABLE, value: "true"}             # 自动打 k8s 标签
```

## 9.3 看到什么算过

```
本次真实回显

① telemetrygen（先证明 Collector→Tempo 这段是通的，别一上来就怀疑探针）
   {"tagValues":["k8s20-verify"]}

② beyla DaemonSet
   beyla  5  5  5  5  5          （desired/current/ready/up-to-date/available 全 5）
   日志：attaching uprobes as uprobe_multi links · Starting main node

③ 打流量后再查 Tempo
   {"tagValues":["k8s20-verify","kyverno","loki"]}
   → kyverno / loki 是被 beyla 自动发现的，这两个应用本身没有任何埋点代码
```

## 9.4 排查顺序（照这个顺序，别跳）

```
① 先证明 Collector→Tempo 通     → 用 telemetrygen 打一条假 trace
② 再证明探针在跑               → kubectl -n monitoring get ds beyla（ready 数）
③ 再看探针日志有没有错误       → logs 里找 "attaching uprobes" 和 RBAC 报错
④ 最后才怪应用                 → 大部分情况是①或②没通
```

## 9.5 本章三个坑

```
坑 1  Alloy 里塞 otelcol.receiver.ebpf 一直不生效
现象：helm upgrade 成功，但 alloy 读到的还是 chart 默认配置（日志里在跑 ingress/endpointslice 发现）
      ；改过的配置里如果用分号分隔属性，会报
      illegal character U+003B ';'（Alloy 语法是一行一个属性）
结论：Alloy 的 chart 配置注入路径（configMap.create + content vs 默认 config）没打通，
      与其继续调，不如把"日志"和"eBPF 探针"拆成两个组件 —— 各管一件事，故障不互相牵连。
      本次最终形态：Alloy 只管日志，beyla 只管 trace。

坑 2  第三方镜像名踩空
现象：otel/opentelemetry-ebpf-instrumentation:latest → repository does not exist
防：装之前 crictl pull 试一下；本项目实际可用的是 grafana/beyla

坑 3  beyla 起来了但没有 k8s 标签、也看不到服务名
现象：日志里 services is forbidden / nodes is forbidden / pods is forbidden
根因：用的是 default ServiceAccount，没有 ClusterRole
防：SA + ClusterRole(pods/services/nodes/endpoints/namespaces, get/list/watch) + Binding
```

## 判官卡：要不要上"服务网格"来换 trace

```
选项 A eBPF 探针（本次）
  + 零改动、零 sidecar、CPU 开销低（每节点 50m）
  - 只能看到网络层能推断的东西；应用内部的 span（数据库调用、函数耗时）看不到

选项 B sidecar / OTel SDK
  + 能看到应用内部细节，能加业务属性
  - 要改代码或注入 sidecar；每个 Pod 多一个容器

判据：先上 A 拿到"请求级全景"，再对关键服务上 B 补"内部细节"。
      反过来做（先 SDK）会卡在"没人愿意改代码"上。
本次：A。这也正是第 11 章 ambient 要解决的问题的一半（身份/加密在网格侧，可观测在探针侧）。
```
