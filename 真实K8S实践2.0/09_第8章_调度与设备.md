## 8.1 在干什么

Kueue 解决的是"**配额 + 排队**"，不是"调度"：
调度器决定"Pod 放哪台机器"，Kueue 决定"这个作业什么时候被允许进入调度"。

```
提交 Job（带 queue-name=lq 标签）
  → Kueue 生成 Workload
  → ClusterQueue 看配额够不够
  → 够 → admitted（Pod 才被创建）
  → 不够 → 排队（Pod 根本没生成，不占调度器）
```

**这就是它和普通 ResourceQuota 的区别**：配额满了，ResourceQuota 是"拒绝创建"，
Kueue 是"挂起排队，等前面的跑完自动放行"。

## 8.2 敲什么

```bash
kubectl apply --server-side -f https://github.com/kubernetes-sigs/kueue/releases/download/v0.13.0/manifests.yaml
kubectl apply -f s12-kueue.yaml     # ResourceFlavor + ClusterQueue + LocalQueue + 两个 Job
```

## 8.3 看到什么算过

```
本次真实回显

kueue-system  pods: 1 Running（controller-manager）

workloads（按时间看）
job-q1-80cee   lq   cluster-queue   True              ← 后放行
job-q2-36402   lq   cluster-queue   True   True       ← 先放行，已完成

jobs
q1   Running    0/1   10s     2m13s
q2   Complete   1/1   2m3s    2m13s
```

**判读方式**：配额只有 1 CPU，两个 Job 各要 800m。如果 Kueue 没生效，两个会同时 Running
（800+800 > 1000 也照样跑，因为 K8s 默认不按总数卡）；现在是 q2 先 Complete，q1 才开始 ——
说明第二个 Job 在 q2 结束前一直没被放行。

## 8.4 判官卡：Kueue 值不值得在练习环境装

```
值得，如果你的目标是"AI/批处理平台"
  它解决的是"多人多作业抢有限 GPU/CPU"的公平性与排队，是 AI 平台的核心件。

不值得，如果只是"跑微服务"
  微服务用 HPA + ResourceQuota 就够；Kueue 对无状态服务几乎不产生价值。

判据：你的集群里有没有"作业会排队"这件事。没有，就先用 PriorityClass + ResourceQuota。
本次：装了并验证了配额串行，作为"能力占位"；业务侧目前没有真正需要排队的作业。
```

## 核心大坑（2 条）

```
现象：Job 创建了但 Pod 一直不出现
根因：Job 没打 kueue.x-k8s.io/queue-name 标签，或 LocalQueue 不存在
防：先看该命名空间是否生成了 Workload 对象；没有就是队列标签没打上

现象：Kueue 装完，老作业全卡住
根因：Kueue 会接管所有带队列标签的作业；集群里已有带该标签的历史对象
防：先在测试命名空间验证，再扩到全集群
```

## 8.5 DRA：把设备当成"可声明申请的资源"（本次新增）

### 在干什么

传统做法是用 device plugin 上报"节点有 8 张卡"，Pod 写 `nvidia.com/gpu: 1` 就算了事 ——
调度器只知道"数量"，不知道"哪一张、有什么属性"。
DRA 换了模型：**Pod 声明"我要一张什么样的设备"，驱动发布设备清单，调度器按属性选。**

```
驱动 → 发布 ResourceSlice（这台机器上有什么设备、什么属性）
用户 → 写 ResourceClaimTemplate（要什么样的设备）
调度器 → 匹配 + 分配（claim 状态变 allocated）
kubelet → 调驱动把设备注入容器（CDI）
```

### 本次实装

```
驱动          kubernetes-sigs/dra-example-driver v0.5.0
节点插件      5 个（每个 worker 一个），全部 Running
DeviceClass   gpu.example.com
ResourceSlice 5 个（对应 5 台 worker）
申请方        demo-app 里的 ResourceClaimTemplate + 一个引用它的 Pod
结果          Pod Running 在 wk-2，claim 状态 allocated,reserved
容器内可见    GPU_DEVICE_0=gpu-0 · DRA_RESOURCE_DRIVER_NAME=gpu.example.com
              GPU_DEVICE_0_SHARING_STRATEGY=TimeSlicing
```

### 看到什么算过

```
① DeviceClass 存在                       gpu.example.com
② ResourceSlice 数量                     5（每台 worker 一条）
③ claim 状态                            gpu-user-gpu-4clm8   allocated,reserved
④ Pod 相位 / 落点                        Running / wk-2
⑤ 容器内设备注入                         GPU_DEVICE_0=gpu-0（CDI 生效，不是"能调度但没设备"）
```

第⑤条最关键：只看到 Running 不足以证明 DRA 真的工作 —— 必须看容器里有没有设备注入。

### 判官卡：DRA 与 device plugin 怎么选

```
device plugin
  + 生态成熟，GPU 厂商都支持
  - 只能按"数量"申请；共享、分区、属性筛选都要靠 sidecar 或自定义
DRA
  + 按属性申请（型号/显存/拓扑）、支持共享与分区、声明式
  - 驱动要改写；调度链路更长（claim → 分配 → CDI 注入），排查点多

判据：如果你的需求是"给我一张卡"，device plugin 够；
      如果是"给我两张同 NUMA、显存 >40G、能共享的卡"，才需要 DRA。
```

### 核心大坑（3 条）

```
现象：驱动拉不起来，报 repository does not exist
根因：镜像没有 latest 标签（该仓库只有 v0.1.0 ~ v0.5.0），写 latest 必然失败
防：装之前先查仓库的标签清单，不要假设 latest 存在

现象：验收时 claim 查不到，Pod 却是 Completed
根因：由模板生成的 claim 随 Pod 生命周期回收
防：验收必须在 Pod 存活期间做；或用长驻 Pod 而不是 sleep 几十秒就退出的

现象：Pod 起来了但容器里没有设备
根因：DeviceClass 名字与驱动声明的名字不一致，claim 匹配不到设备（此时多半 Pending）
防：DeviceClass 名以驱动实际发布的为准，别用示例里的默认值猜
```
