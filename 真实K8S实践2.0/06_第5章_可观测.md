## 5.1 在干什么

三件事分开做，别混成一个"监控大礼包"：
- **指标**：Prometheus 拉（谁出了问题、什么曲线变了）
- **日志**：Alloy 采 → Loki 存 → 按 ns/pod 查（到底报了什么错）
- **告警**：Alertmanager 分级送出去（谁能被叫醒）

## 5.2 为什么日志要落到集群外 S3

```
Loki 只把索引和 WAL 放本地（10Gi Longhorn），chunk 全写 S3（infra-01）。
好处：① 集群重建后日志还在；② 不占 Longhorn 三副本容量；③ 与备份共用一套对象存储，成本低。
判据：日志属于"事后取证"数据，生命周期比集群长，就不该放在集群里。
```

## 5.5 本章两个坑（都是"看着像集群坏了，其实是配置"）

```
坑 1  Grafana 2 副本 + persistence.enabled=true → 第二个副本永远 Init:0/1
根因：两个 Pod 共用同一个 RWO（ReadWriteOnce）卷，第二个挂不上，且不报错、只是卡住
判断：kubectl describe pod 看到 "Multi-Attach error" 或一直 Init
修法：无状态化 —— persistence.enabled=false，副本 2 个；
      看板走 ConfigMap/Provisioning（本来就该这样），不需要持久卷
★ 教训：凡是"多副本 + RWO 卷"的组合都要先问一句"这个卷能不能同时被两个 Pod 挂"。
        Prometheus/Alertmanager 用的是 StatefulSet（每副本一个卷，没问题），
        Grafana 用的是 Deployment（共用一个卷，就有问题）。

坑 2  helm install alloy --version 1.9.2 报 chart not found
根因：grafana/alloy 的版本号已经走到 1.14~1.16（1.0 册子里记的 1.9.2 是当时装到的 app 版本）
修法：helm search repo grafana/alloy --versions 先看真实可用版本，再定 --version
★ 教训：文档里的版本号分两种 —— chart 版本和 app 版本，混用必踩。
```

## 判官卡：Prometheus 要不要上 Thanos/VictoriaMetrics

```
选项 A 单集群 Prometheus 2 副本 + 7 天（本次）
  优点：组件少、查询路径最短、练习环境够用
  缺点：7 天以后查不到；跨集群看不到

选项 B 加 Thanos sidecar + 对象存储
  优点：长期存储 + 全局视图
  缺点：多 4 个组件（sidecar/query/store/compact），排查链变长

判据：先把"7 天内能不能查、告警能不能到人"做实，再谈长期存储。
本次：A。第 10 章如果能把 trace 打通，再考虑 B。
```
