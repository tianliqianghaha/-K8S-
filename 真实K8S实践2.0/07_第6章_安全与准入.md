## 6.1 在干什么

三条不同的防线，别混：

```
① PSA（Pod Security Admission）     API Server 内建，零组件，管"Pod 的安全上下文"
② ValidatingPolicy（Kyverno CEL）  管"团队的规范"（标签、资源、镜像来源）
③ MutatingAdmissionPolicy（原生）   管"帮不规范的写法补齐"（而不是一拒了之）
```

**为什么"变更侧"值得单独做**：只拒不改，结果是"要么全公司改 Helm chart，要么全都过不去"。
把能安全补齐的部分（label / annotation / seccompProfile / 默认 resources）自动补上，
剩下的硬要求（runAsNonRoot）才交给人改 —— 这才是能落地的方式。

## 6.2 敲什么

```bash
# ① PSA：一条 label 就是一道防线
kubectl label ns psa-test pod-security.kubernetes.io/enforce=restricted

# ② Kyverno + 三条 CEL 策略
helm upgrade --install kyverno kyverno/kyverno -n kyverno --create-namespace \
  --set admissionController.replicas=2 --wait
kubectl apply -f s9-kyverno.yaml --server-side

# ③ 变更侧：先探原生，探不到再用 Kyverno MutatingPolicy
kubectl api-resources | grep -i mutatingadmissionpolicy
kubectl apply -f s9-map.yaml
```

策略原文（本次实测被拒的三条之一）：

```yaml
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata: {name: require-resources}
spec:
  validationActions: [Deny]
  matchConstraints:
    resourceRules:
      - {apiGroups: [""], apiVersions: ["v1"], operations: ["CREATE","UPDATE"], resources: ["pods"]}
  validations:
    - expression: "object.spec.containers.all(c, has(c.resources) && has(c.resources.requests) && has(c.resources.limits))"
      message: "必须声明 requests 与 limits"
```

变更侧原文（原生 CEL，注意版本是 **v1**）：

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicy
metadata: {name: inject-defaults}
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - {apiGroups: [""], apiVersions: ["v1"], operations: ["CREATE"], resources: ["pods"]}
  reinvocationPolicy: Never
  mutations:
    - patchType: ApplyConfiguration
      applyConfiguration:
        expression: "Object{ metadata: Object.metadata{ annotations: {'admission.k8s.local/mutated': 'map'} } }"
---
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicyBinding
metadata: {name: inject-defaults-binding}
spec:
  policyName: inject-defaults
  matchResources:
    namespaceSelector: {matchLabels: {mutate: enabled}}
```

## 6.3 看到什么算过

```
本次真实回显

① PSA
Error from server (Forbidden): pods "bad" is forbidden: violates PodSecurity "restricted:latest":
  allowPrivilegeEscalation != false / unrestricted capabilities / runAsNonRoot != true / seccompProfile

② Kyverno 三条（逐条）
测1 latest     → denied: Policy disallow-latest-tag failed: 禁止使用 :latest 标签
                  （同时命中 require-resources，说明策略并行生效）
测2 无 resources → denied: Policy require-resources failed: 必须声明 requests 与 limits
测3 privileged  → denied: Policy disallow-privileged failed: 禁止 privileged 容器
合规 Pod        → pod/good created

③ 变更侧（原生 MAP）
mutated=map        （mutate-test 命名空间，打了 mutate=enabled）
对照 demo-app      → 空（未打标签，不被改写）  ← 证明 binding 选择器精确生效
```

## 6.4 三种策略的取舍（判官卡）

```
选项 A PSA
  适用：Pod 安全上下文的"硬下限"。K8s 原生，零组件，挂不了也拖不慢。
  不适用：业务规范（它不懂"必须有 owner 标签"这种要求）。

选项 B Kyverno ValidatingPolicy（CEL）
  适用：团队规范 + 跨资源校验 + 需要"为什么被拒"的可读 message。
  代价：是一个 webhook，它挂了写入就受影响（所以要 ≥2 副本 + failurePolicy 想清楚）。

选项 C 原生 MutatingAdmissionPolicy（CEL）
  适用：能安全补齐的改写。零 webhook、零外部依赖。
  代价：CEL 写起来不如 YAML patch 直观；复杂改写（比如按容器改 securityContext）容易写出语法错。
        本次实测：三元表达式里直接放 map 字面量会报
        "mismatched input ':' expecting '}'" —— 拆成单层 map 或加括号。

本次结论：A 打底 + B 管规范 + C 管补齐，三层各司其职。
         C 能用原生就别用 Kyverno Mutate —— 少一个 webhook 就少一个故障面。
```

## 核心大坑（3 条）

```
现象：MutatingAdmissionPolicy apply 报 "no matches for kind ... in version v1beta1"
根因：1.37 里它已经 GA，group/version 是 admissionregistration.k8s.io/v1
防：先核对该 API 在你环境里注册的版本，按实际版本写清单，不照抄外部示例

现象：CEL 改写策略写好但 Pod 没变，也没报错
根因：Binding 的 namespaceSelector 没匹配上（命名空间没打对应标签）
防：做个"对照组"——同一份 Pod 在一个不打标签的 ns 里创建，确认它没被改

现象：Kyverno 装完，所有 Pod 创建都变慢甚至超时
根因：admissionController 只有 1 副本，且 failurePolicy=Fail，webhook 一抖全站写入卡住
防：副本 ≥2 + PDB；评估 failurePolicy 要不要改成 Ignore（安全 vs 可用性的取舍）
```

## 6.5 密钥闭环：Sealed Secrets（本次新增）

### 在干什么

让 Secret 能进 Git，但**进去的是密文**：只有集群里的私钥能解开，Git 泄露不等于口令泄露。

```
明文 Secret（本地，不提交）
  → kubeseal 用控制器的公钥加密
  → SealedSecret（可以进 Git、可以进 ArgoCD）
  → 控制器用私钥解出 Secret
```

### 本次实装与回显

```
控制器      sealed-secrets-controller 0.41.2（manifest 安装）
kubeseal    0.41.2
封存对象    demo-secrets/db-cred
明文泄漏检查  Git 内密文中检索明文口令 → 0 处
ArgoCD      application secrets → Synced / Healthy
Secret 内容  与本地记录一致
删掉重建     删除 Secret 后 1 秒内由 SealedSecret 重新生成
```

### 判官卡：密钥放哪

```
选项 A Sealed Secrets（本次）
  + 密文可进 Git、无外部依赖、离线可用
  - 无轮换、无审计、无动态租期；私钥丢了全部密文作废（必须离线备份）
选项 B Vault + ESO
  + 动态凭据、审计、轮换
  - 多一套系统；1.0 在本环境遇到过 listener 绑定问题
判据：练习环境用 A 足够；生产要"谁能读哪个密钥"可审计，才需要 B。
```

## 6.6 身份闭环：OIDC（本次新增）

### 本次实装

```
IdP        Dex v2.44（infra-01，docker，HTTPS 5556，自签证书含 IP SAN）
接入      三台 apiserver 增加 5 个 OIDC 参数 + 挂载 CA
授权      ClusterRoleBinding：User "viewer@k8s.local" → ClusterRole view
```

### 看到什么算过

```
viewer    get pods     → yes
viewer    delete pods  → no
陌生人     get pods     → no
```

**这三行比"登录成功"更有意义**：它证明"身份能映射到权限"，而不是只证明"能认证"。

### 核心大坑（2 条）

```
① 静态 Pod 清单不能用文本方式改
   现象：改完 apiserver 起不来，VIP 直接 EOF
   根因：插入位置/缩进错，YAML 非法；kubelet 无法创建容器
   判据：改前备份、改后先单台验活、健康检查通过再推广

② Dex 新版没有 local connector
   现象：配置 connectors: type local → 启动即报 unknown connector type
   根因：密码授权在 v2.44 里不再由 local connector 提供
   判据：取 token 走授权码流程（kubelogin），不要指望密码授权
```

## 6.7 网络策略：默认拒绝 + 白名单（本次新增）

### 在干什么

准入管"能不能创建"，网络策略管"创建出来能连谁"。两者不重叠，缺一个都留着大口子。

### 本次实装（demo-app）

```
default-deny            ingress + egress 全拒
allow-dns               放行 kube-system 的 53/UDP+TCP
allow-same-ns           同命名空间互访
allow-gateway-monitor   放行 envoy-gateway-system 与 monitoring 的入站
allow-egress-api        放行到 apiserver（按实体，不是按 IP）
```

### 看到什么算过

```
同 ns 访问            200
DNS 解析              ok
入口经网关            200
跨命名空间直连        BLOCKED（对照组，证明策略真的在拦）
出公网                超时（被拒，符合预期）
```

### 判据（这里有个关键细节）

```
第一版把 apiserver 放行写成 ipBlock 10.96.0.0/12:443 → 仍然 000
根因：Cilium 里 apiserver 是一个"实体"（host identity），不是普通 IP
正解：加一条按实体的放行（toEntities: kube-apiserver）
判据：改完必须复测 apiserver 访问，不能只看同 ns 通就以为好了
```

## 6.8 配额与限额（本次新增）

```
ResourceQuota   总量上限：cpu 4 / mem 8Gi / limits.cpu 8 / limits.mem 16Gi / pods 30 / pvc 6
LimitRange      单容器默认：request 20m/32Mi，limit 200m/128Mi，上限 2C/2Gi
实测用量        requests.cpu 180m / 4，limits.cpu 1200m / 8，pods 11 / 30
判据            只有 Quota 时，一个容器能吃光配额；只有 LimitRange 时，总量无上限 —— 两个都要
```
