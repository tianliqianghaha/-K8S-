# 08 · 第 7 章 · 弹性（HPA / 原地扩缩 / VPA / KEDA）

> **这一册在整件事的哪一步**：第 6 章 谁能改什么 →【第 7 章 该扩就扩、该缩就缩，且不重启】→ 第 8 章调度与设备。

## 【本章已做】

```
✅ HPA（autoscaling/v2）：CPU 200%/50% → 副本 2→4，20 秒内到位
✅ 原地扩缩（InPlacePodVerticalScaling）：requests 200m→300m，10 秒内 actual 变 300m，
   Pod UID 不变、重启次数 0 —— 真正"不重启改配置"
✅ VPA（cowboysysop chart，recommender/updater/admission 三件套）：
   Off 模式给出建议值 cpu=25m / memory=250Mi，不动线上
✅ KEDA（kedacore chart）：cron 触发器把 evt 从 0 副本拉到 2 副本（20 秒内）
```

## 【本章未做】

```
▢ KEDA 的 CPU/内存类触发器"从 0 拉起"（做不到，见 7.5 判官卡）
▢ VPA 的 InPlaceOrRecreate 自动模式（会与 HPA 打架，见 7.4）
▢ 基于 SLO 的弹性（需要先在 Prometheus 里定义 SLI）
```

## 7.1 在干什么

四件事，解决的是四个不同问题，不要混成一个"弹性方案"：

```
① HPA      副本数按指标变（横向）
② 原地扩缩  单个 Pod 的 requests/limits 变了，不重建 Pod（纵向，K8s 1.33+ Beta）
③ VPA      告诉你"应该给多少"，可选自动改（纵向，建议模式最安全）
④ KEDA     按"事件"扩缩，能缩到 0（横向，事件源驱动）
```

## 7.2 敲什么

```bash
# ① HPA
kubectl autoscale deploy burn --cpu-percent=50 --min=1 --max=4        # 或写 autoscaling/v2

# ② 原地扩缩：直接 patch Pod 的 resize 子资源（不是改 Deployment！）
kubectl patch pod $POD --subresource resize --type=merge \
  -p '{"spec":{"containers":[{"name":"burn","resources":{"requests":{"cpu":"300m"},"limits":{"cpu":"400m"}}}]}}'

# ③ VPA
helm install vpa cowboysysop/vertical-pod-autoscaler -n vpa --create-namespace
# VPA 对象 updateMode: Off（只给建议）

# ④ KEDA
helm install keda kedacore/keda -n keda --create-namespace
```

## 7.3 看到什么算过

```
① HPA
起始：burn Deployment cpu: 200%/50%  1  4  2
t=10s replicas=2   t=20s replicas=4   t=30s replicas=4（稳定）
→ 结论：扩容发生在 20 秒内，且封顶在 maxReplicas=4

② 原地扩缩
before: uid=fcffcdc8-…  spec=200m  actual=200m
patch → 300m
t=10s actual=300m   resize=(空，表示已完成)
after : uid=fcffcdc8-…（同一个）  restarts=0
→ 结论：容器没有重启、Pod 没有换，cgroup 限额被热改

③ VPA
{"cpu":"25m","memory":250Mi}   web-vpa  Off  25m  250Mi  True  76s
→ 结论：建议值来自真实用量（web 只是 netexec，25m 合理）
   注意 VPA 给的内存建议 250Mi 远高于我们手填的 32Mi —— 说明手填值不合理

④ KEDA
空闲：replicas=(空)=0
cron 触发：replicas=2（20 秒内）
scaledobject evt-cron  True  cron
→ 结论：能缩到 0，也能被事件拉起来
```

## 7.4 三个会互相打架的组合（务必记住）

```
✗ HPA(CPU) + VPA(Auto)   同一个 workload
  原因：HPA 按 CPU 利用率扩副本，VPA 按用量改 requests；
        requests 一改，利用率分母变了，HPA 立刻误判 —— 两个控制器互相追。
  正确：VPA 用 updateMode=Off（只给建议）或 controlledValues=RequestsOnly，
        且同一 workload 上只保留一个"会改 CPU"的控制器。

✗ Deployment 改 resources + 期望"原地生效"
  原因：Deployment 模板一变就滚动新 ReplicaSet → 起新 Pod，不是原地。
  正确：原地扩缩要 patch Pod 的 resize 子资源；Deployment 那条路必然重启。

✗ KEDA 缩到 0 + ArgoCD 自动同步
  原因：ArgoCD 发现 Git 里 replicas=2、线上是 0 → 判 OutOfSync 并拉回 2，KEDA 再缩 0，循环抖。
  正确：ArgoCD Application 里加 ignoreDifferences（/spec/replicas），或者用 KEDA 的 HPA 接管后关掉 ArgoCD 的 selfHeal 对 replicas 的管辖。
```

## 7.5 判官卡：KEDA 能不能"从 0 拉起"

```
本次实测（值得记住）
用 prometheus 触发器查 container_cpu_usage_seconds_total → 副本缩到 0 之后就再也拉不起来。
原因：0 副本时没有 Pod，就没有这条指标序列，KEDA 永远读到 0（或读到空），无法判断"该扩了"。
这是"按自身资源用量的指标做事件驱动"的天然死角。

正确做法（按顺序选）
① 用**外部**事件源：队列长度（Kafka lag / Redis list / RabbitMQ）、HTTP 请求速率（网关侧）、
   对象存储待处理文件数 —— 这些指标不依赖目标 Pod 是否在跑
② 用 cron 触发器做"确定性伸缩"（本次用它证明了控制回路 0→2）
③ 保底 1 副本（minReplicaCount=1），就退化成一个按指标调整的 HPA

判据：能不能缩到 0，取决于"驱动指标是否存在于目标之外"，而不是取决于装了 KEDA。
```

## 核心大坑（3 条）

```
现象：HPA 显示 <unknown>/50%
根因：metrics-server 没装或目标容器没写 requests（利用率算不出来）
防：先确认指标管道对该 Pod 已出数，再建 HPA；HPA 的分母是 requests，不是节点容量

现象：patch pod 报 "must be less than or equal to cpu limit"
根因：只抬了 requests 没抬 limits
防：原地扩缩同时给 requests 与 limits，且 requests ≤ limits

现象：VPA 装不上，报被 Kyverno 拒绝（本次真实遇到）
根因：自己的准入策略 require-resources 把 VPA 自己的 Pod 也拦了
防：策略必须先用 matchConditions 排掉系统命名空间（vpa/keda/kyverno/longhorn/monitoring…）
```
