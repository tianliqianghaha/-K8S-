## 一、2.0 与 1.0 的差别（只看这张）

```
                    1.0（2026-11-20）              2.0（2026-11-21）
落地时间             当天裸机到 GitOps 约 6 小时       分章节推进，每章带真实回显
机器数               9 台（8 节点 + 1 外部机）        10 台（8 节点 + infra + spare）
可用区               全部 cn-hongkong-c 单区          工作节点 b / d / c 三区（2/2/1）
控制面               3× e-c1m2 4C8G                  3× e-c1m2 4C8G（仍在 c，HAVIP 限制）
工作节点             5× e-c1m2 4C8G 同构             2× u1-c1m4 4C16G + 3× e-c1m2 4C8G 异构
数据盘               5×50G = 250G                    5×150G + 200G + 100G = 1050G
存储余量             213G/208G 已爆，副本重建失败过一次   733G 裸 / 三副本约 244G 可用
弹性和设备           无 HPA / 无 VPA / 无 KEDA / 无 DRA  见 08/09 章
准入                 只有 validate（拒）               增加变更侧（补齐后放行）
追踪                 无                                见 10 章
发布                 全量同步                          见 11 章（渐进式）
```

**为什么 2.0 值得重做一遍**：1.0 证明了“每一个闭环都能真跑通”，但受 8 台同构机限制，
有三件事做不了——跨 AZ、容量余量、异构调度。2.0 把这三点补上，同时把 1.0 里
“做不了的九项”里**纯软件能做的四项**一起做掉。

## 四、本书的三条写作铁律（与 1.0 相同）

```
① 正向段落不掺负面：讲命令就只讲命令，失败统一放每章末尾「核心大坑」。
② 负面只留核心大坑：一条三行封顶（现象 / 根因 / 怎么防），不写心路历程。
③ 每个外部依赖都给探针：VIP 能不能抢、S3 能不能写、镜像能不能拉，都给一条能跑完的命令。
```

额外一条 2.0 特有的：

```
④ 每个"先进"能力都必须有一个数
   —— 例如"装了 KEDA"不算完成，"队列长度过 20 → 副本 1→4 且 90 秒内回落"才算。
```

## 五、验收口径

分两栏，互不替代：

```
完备（每个闭环都能自己走一遍）
  节点/etcd/入口 HA · 存储与恢复 · 可观测与告警 · 密钥不落明文 · GitOps 自愈
先进（每个能力都有一个数）
  无 kube-proxy 的 eBPF 数据面 · 无 sidecar 的 mTLS · 事件驱动弹性 · 原地扩缩
  · 设备声明式分配 · 变更侧准入 · 零改动追踪 · 渐进式发布
```

具体条目与真实回显见 `13_最终清单.md`。
