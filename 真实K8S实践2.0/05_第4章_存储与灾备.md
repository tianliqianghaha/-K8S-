## 4.1 在干什么

两件事，别混：
- **Longhorn** 解决"Pod 重启后数据还在"（块存储 + 三副本）
- **Velero** 解决"把整个命名空间删了能不能回来"（对象级备份到集群外）

## 4.2 为什么备份目标必须在集群外

```
如果 S3 跑在集群里（比如用 Longhorn 卷做 MinIO）：
  集群挂了 / etcd 丢了 / Longhorn 修不好 → 备份也一起没
本次：SeaweedFS 跑在 infra-01 的 docker 里，/data 是独立 200G 云盘，与集群生命周期无关。
判据：问一句"集群整体重建时，这个备份还在不在？" —— 答案必须是"在"。
```

## 4.3 敲什么

```bash
# ① 前置（每台 worker）
apt-get install -y open-iscsi nfs-common && systemctl enable --now iscsid

# ② Longhorn
helm upgrade --install longhorn longhorn/longhorn --version 1.13.0 \
  -n longhorn-system --create-namespace \
  --set defaultSettings.defaultReplicaCount=3 \
  --set defaultSettings.defaultDataPath=/var/lib/longhorn \
  --set persistence.defaultClassReplicaCount=3 \
  --wait --timeout 15m

# ③ 备份目标：先建 Secret，再建 BackupTarget（1.13 没有 backupTarget 这个 setting 可改）
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Secret
metadata: {name: longhorn-backup-secret, namespace: longhorn-system}
stringData:
  AWS_ACCESS_KEY_ID: "<AK>"
  AWS_SECRET_ACCESS_KEY: "<SK>"
  AWS_ENDPOINTS: "http://172.23.163.111:9000"
  AWS_REGION: "us-east-1"
---
apiVersion: longhorn.io/v1beta2
kind: BackupTarget
metadata: {name: default, namespace: longhorn-system}
spec:
  backupTargetURL: "s3://longhorn-backup@us-east-1/"
  credentialSecret: longhorn-backup-secret
  pollInterval: "1m"
EOF

# ④ Velero（注意 --bucket 与 --no-default-backup-location 不能同时给）
velero install --provider aws --plugins velero/velero-plugin-for-aws:v1.11.0 \
  --bucket velero-backup --secret-file /root/velero-credentials \
  --use-volume-snapshots=false \
  --backup-location-config region=us-east-1,s3ForcePathStyle=true,s3Url=http://172.23.163.111:9000 \
  --namespace velero --wait
```

② Longhorn storageclass: longhorn (default) / longhorn-static

            backup demo-1  STATUS=Completed  ERRORS=0  WARNINGS=0

⑤ 删库恢复演练
   T0  删除 ns demo-app
   T1  restore r-demo-1 Completed       RTO(restore 本体) = 13s

**这个 13 秒和 1.0 的 78 秒不是同一件事**：1.0 那次含 PVC 数据恢复（fs-backup 打 tar）；这次
`use-volume-snapshots=false` 且业务无持久数据，所以只有对象恢复。真正带数据的恢复时间要按 5.5 的方式测。

## 4.5 带数据恢复怎么测（下次照这个做）

```bash
# 1) 往 PVC 里写一个可校验的文件
kubectl -n data-test run w --image=busybox --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"w","image":"busybox","command":["sh","-c","echo MARKER-$RANDOM > /d/x; sleep 3600"],"volumeMounts":[{"name":"v","mountPath":"/d"}]}],"volumes":[{"name":"v","persistentVolumeClaim":{"claimName":"pvc-test"}}]}}'
# 2) 备份时开 fs-backup（Velero 默认对 PVC 走 restic/kopia）
velero backup create data-1 --include-namespaces data-test --default-volumes-to-fs-backup --wait
# 3) 删 PVC / ns 后恢复，比对 /d/x 的内容
```

## 4.6 spare-01 是干什么的

```
它不入集群，只做两件事：
① etcd 快照重建演练：把生产 etcd 的快照拷过去，起一个独立 etcd，
   再用 kubeadm init --external-etcd-endpoints 指过去 —— 这是 1.0 一直没做成的那条
② infra-01 的身份冷备：Dex / Gitea 的配置每天同步一份过去，infra-01 挂了还能登进来

为什么必须"不入集群"：一旦 join，它就是第 9 个 worker，会被调度器拿去跑业务，
"空机器演练"的前提就没了。
```

## 判官卡：副本数怎么定

```
3 副本（本次）
  + 能容忍 1 台节点故障；跨 3 AZ 后还能容忍 1 个 AZ 故障（因为三副本不在同一 AZ）
  - 写放大 3 倍；733G 裸容量只能当 244G 用

2 副本
  + 容量利用率高（366G）
  - 只容忍 1 台节点，且如果两个副本恰好在同一 AZ，则该 AZ 故障=数据不可用

判据：练习环境里，"能演示一次 AZ 故障"比"多 100G 容量"值钱。
      所以 Prometheus 那种可重建的数据可以用 2 副本，业务数据用 3 副本。
本次：默认 3 副本，等第 5 章装 Prom 时单独给它的 PVC 设 2 副本。
```

## 核心大坑（3 条）

```
现象：Longhorn 节点显示"Schedulable=false"，PVC 一直 Pending
根因：/var/lib/longhorn 不是独立挂载点（数据盘没挂上，落到系统盘）
防：装 Longhorn 前先 findmnt /var/lib/longhorn，必须看到 150G 那块盘

现象：BackupTarget 填了但 available=false
根因：Longhorn 1.13 的备份目标走 BackupTarget CRD + credentialSecret，
      里面必须有 AWS_ENDPOINTS（自建 S3 不是 AWS 域名），只填 URL 不够
防：Secret 里四个键一起给：AK / SK / AWS_ENDPOINTS / AWS_REGION

现象：velero install 报 "Cannot use both --bucket and --no-default-backup-location"
根因：两个参数互斥；另一个组合 --no-default-backup-location + --use-volume-snapshots=false 时还要求 --provider 为空
防：本次用"给 --bucket 不给 --no-default-backup-location"，让 install 直接建好 BSL
```
