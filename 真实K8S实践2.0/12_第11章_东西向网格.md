## 11.1 两条路线的差别（这是本章最该记住的）

```
ztunnel（ambient）
  给：链路加密 + 工作负载身份（SPIFFE） + 可按身份授权
  要：一个能签发身份的 CA（istiod 或 SPIRE）。Cilium 的 "内置 CA" 只给配置，不给 CA 服务。
  代价：多一套控制面；改错会全断

WireGuard（本次采用）
  给：节点间链路加密（Pod 流量走 cilium_wg0）
  要：内核支持 wireguard 模块（26.04 自带）
  代价：一条参数、无额外组件；但没有身份，也没有按身份的授权
```

**判据**：要"数据不被旁路看到"→ WireGuard 够；要"谁能访问谁"→ 必须有身份，只能上 istiod/SPIRE。

## 11.2 看到什么算过

```
直接读 cilium 状态，而不是看 Pod 数量：
  Encryption: Wireguard [NodeEncryption: Disabled, cilium_wg0
                          (Pubkey: oB2/…, Port: 51871, Peers: 7)]

Peers 7 = 其余 7 台节点都对上了公钥（8 节点全互联）。
再跑四层连通性，确认加密没有破坏转发：200 / 200 / 200 / 404。
```

## 11.3 这一轮踩到的三个坑（不含命令）

```
① 内置 CA ≠ CA 服务
   现象：ztunnel 0/8，日志反复重连 localhost:15012
   根因：ca.type=internal 只改变谁签发，不负责提供签发服务；这个端口上没有进程
   判据：Secret 有了、Pod 起来了，但只要健康检查不过，就是 CA 链路没通，不是镜像慢

② 数据面变更失败时，"节点还 Ready"是假象
   现象：8 台节点全 Ready，但 ztunnel 0/8、两个 agent 卡在 Init
   根因：Ready 只反映 kubelet 与 apiserver 的心跳，不反映 CNI 是否可用
   判据：看 agent 的 Init 计数与目标 DaemonSet 的就绪数，这两个才是数据面的真相

③ 结构化的清单改动，别用文本插入
   现象：改完 apiserver 清单后 apiserver 根本不启动，集群 VIP 直接打不通
   根因：文本方式插入缩进错位，产生的 YAML 不合法
   判据：改静态 Pod 清单必须走 YAML 解析器（读→改结构→写回），改完先在一台上验活，
        再推广到其余节点；且必须留备份
```

## 11.5 判官卡：加密这件事怎么排优先级

```
本次的实际排序（事后看是对的）
① 先做"可观测"（第 9 章）：加密出问题时，你得先能看见
② 再做"链路加密"（本章）：一条参数，收益明确
③ 最后做"身份与授权"：成本最高、风险最大，必须单独窗口

反面做法：一上来就上完整网格（ztunnel + waypoint + 授权策略），
         任何一步失败都会让整个数据面变成不可解释状态。
```
