## 演练① 镜像拉不到

### 在干什么

把"Pod 起不来"缩小到"镜像这一层"，并且分清三种完全不同的原因。

### 本次结果

```
deployment.apps/web image updated
web-b5f7cb699-cxwhc   0/1   ErrImagePull
其余两个副本 1/1 Running（滚动发布不会一次全挂）
```

### 判据：三段措辞对应三类原因

```
manifest unknown / not found          → 标签（tag）不存在，最常见
unauthorized / pull access denied     → 仓库要认证，缺 imagePullSecret
dial tcp / i/o timeout                → 网络或镜像仓库不可达
```
**这三个词决定你下一步是改 tag、配 secret、还是查网络**，不要一上来就重试。

### 事后副作用（本次真实踩到）

```
手工改镜像会被 GitOps 自愈改回去 —— 第一次演练因此"什么都没发生"
判据：改完 25 秒内 Pod 名字没变 = 变更被覆盖了
做法：演练这类"故意改坏"的动作，先暂停 ArgoCD 的 automated，做完再恢复
```

## 演练② 节点 drain + PDB

### 在干什么

模拟节点维护：把 Pod 安全赶走，同时业务不中断。

### 本次结果

```
loadgen（落 wk-5，每 0.2s 一次请求）：OK=900  BAD=0
drain wk-2：32 秒完成
web 两个副本：一个从 wk-2 迁到 wk-4，另一个留在 wk-3 不动
```

### 判据

```
成功率 100% 才叫"不中断"；任何一次 BAD 都要能解释是哪一段窗口
PDB(minAvailable=1) 的作用是"驱逐前先确认还剩几个"，
没有 PDB 时 drain 会把两个副本一起赶走（对照组才有说服力）
```

### 事后副作用（三项，都必须知道）

```
① 裸 Pod（无控制器）会卡住 drain：本次 gpu-user 就是裸 Pod，必须 --force
② drain 会驱逐 Longhorn 的 instance-manager（它跑在节点上）→ 存储在 drain 期间有短暂抖动
③ 被驱逐的东西不会自动回来：
   - 网关数据面 Service 变成了 LoadBalancer，Programmed 变 False（AddressNotAssigned）
   - DRA 的 claim 随 Pod 一起消失
   判据：drain 之后必须重跑一遍验收，而不是"看起来没坏就算了"
```

## 演练③ apiserver 两台下线

### 在干什么

验证控制面 HA 到底剩几条命：3 台里停 2 台，集群还能不能用。

### 本次结果

```
下线后：kubectl get nodes 正常返回 8 台
        VIP healthz = 200
        etcd 成员 = 3 started
恢复：9 秒（两台都回到 Running）
```

### 判据

```
"能用"不是看 Pod 状态，是看三件事同时成立：
  ① kubectl 能读（走 VIP）
  ② healthz 200
  ③ etcd 成员数不变、无 leader 抖动
```

### 事后副作用（一条关键）

```
直接停容器没用：kubelet 会在几秒内把静态 Pod 拉回来，你测的是"没停"
判据：如果 apiserver_up 一直是 3，说明演练根本没生效
做法：把静态 Pod 清单移出 manifests 目录，再停容器
```

## 演练④ 删除 CNI

### 在干什么

生产里最常见的"手滑"：把网络组件删了。练的是**爆炸半径**和**恢复速度**。

### 本次结果

```
删 cilium DaemonSet 后：cilium pod 数 = 0
新建 Pod：Pending，没有 IP（拿不到地址）
已经在跑的 Pod：2/2 存活（BPF 程序已加载在内核里，不依赖 agent 活着）
恢复：helm 按备份的 values 重装，8/8 就绪，用时 68 秒
```

### 判据

```
爆炸半径 = "新增"全死 + "存量"存活
这就是 eBPF 数据面的特性：控制面（agent）挂了，已下发的转发规则还在
如果是 iptables/kube-proxy 型 CNI，清理规则时反而更容易把存量流量打断
```

### 恢复前必须先做的一件事

```
把当前 values 导出来再动手。本次先导了一份 52 行的 values，
恢复时就是一条 helm upgrade -f；没有这份文件，恢复等于重装一套 CNI。
```

## 演练⑤ etcd 快照恢复（最值钱的一项）

### 在干什么

回答"集群彻底没了，数据能不能回来"。用的是 spare-01（不入集群的那台），演练不影响生产。

### 本次结果

```
打快照：76 MB，耗时 1.3 秒（在 cp-1 上执行）
传输：cp-1 → 本机 → spare-01
恢复：etcdutl snapshot restore，耗时 1 秒
起独立 etcd（--force-new-cluster）：1 个成员
抽查：
  总 key 数        4216
  Pod 记录数       162
  业务 ConfigMap   demo-app/marker 完整回来（含 velero 备份/恢复注解）
```

### 判据

```
① 快照能在秒级完成 → 说明可以做成"每小时一次"的常态，不是重活
② 恢复后要抽查"业务对象"，不是抽查 etcd 自己的元数据
   （能列出 key 不等于数据对，要看到 marker 的内容）
③ 全流程（快照→传输→恢复→抽查）在一台 4C8G 的机器上 5 分钟内可完成
```

### 为什么用 spare-01 而不是 cp 上直接试

```
在生产环境里，"恢复演练"必须落在与生产隔离的机器上，
否则你会用一次演练的风险去换一次"确认"。
spare-01 不加入集群，就是为这个准备的。
```

## 演练⑥ 证书轮换

### 结果

```
续期前   apiserver / etcd-server / admin.conf 等 6 张证书：剩余 364 天
执行     kubeadm certs renew all → 逐个重启 apiserver / controller-manager / scheduler / etcd
耗时     11 秒（续期 + 重启 + healthz 恢复）
续期后   到期时间从 01:29 UTC 变为 05:34 UTC，剩余仍 364 天（重新计时）
```

### 判据

```
"续期成功"不等于"生效"：证书文件换了，但进程还用着老证书，必须重启对应组件
判据：kubeadm certs check-expiration 的 EXPIRES 时间变了 + healthz 200，两个都要
```

### 边界

```
证书是全集群的命门：轮换必须一台一台做，做完一台验一次 healthz 再动下一台
本次只做了 cp-1（演练），生产要按"控制面逐台"滚动
```

## 演练⑦ 可用区故障（真停 d 区两台 kubelet）

### 在干什么

不是 cordon/drain（那是"计划内维护"），而是**机器突然不可达**——kubelet 直接停掉。

### 本次结果

```
t=0      停 wk-2 / wk-4 的 kubelet
t=40s    第 1 台变 NotReady，web 的 Service 端点从 2 个降到 1 个
t=48s    2 台都 NotReady，端点仍 1 个（跑在 wk-3 的那个副本继续服务）
恢复     启动 kubelet，3 秒后 8/8 Ready
```

### 意外发现（本册最有价值的一条）

```
现象：故障期间业务请求报 "bad address web.demo-app.svc.cluster.local"
根因：CoreDNS 两个副本都调度在 wk-4 上。wk-4 一停，DNS 直接全灭
判据：副本数 = 2 不代表高可用，要看它们是不是在同一台/同一可用区
修复：给 CoreDNS 加硬反亲和（kubernetes.io/hostname）+ 扩到 3 副本
      修复后落在 cp-2 / wk-1 / cp-3 三台不同节点，DNS 恢复
```

**为什么值得记**：这属于"平时看不出、故障时致命"的配置缺陷。
副本数在 YAML 里写 2 会让人产生安全感，但调度器并不知道你在乎它们别放一起。

### 判据（可用区故障怎么算通过）

```
① 受影响节点在 40~60 秒内变 NotReady（kubelet 心跳超时）
② 端点被摘除（NotReady 的 Pod 不再接流量）——这是"业务不中断"的真正机制
③ 恢复后节点自动回 Ready，不需要人工介入
④ 顺带检查：DNS、存储副本、入口后端是否也跟着降级
   本次就是靠第 ④ 条抓到 CoreDNS 单点的
```

## 演练⑧ PVC 数据恢复（fs-backup）

### 在干什么

前面演练⑤ 只证明了"etcd 里有数据"，这次证明"**卷里的文件也能回来**"。

### 前提（第一次就卡在这）

```
Velero 默认只备份 K8s 对象，不备份卷里的数据。
要备份卷内容必须先有 node-agent（kopia/restic 的工作单元）：
  velero install ... --use-node-agent
本次补装后 node-agent 5/5 就绪。
```

### 本次结果

```
建 2Gi PVC（longhorn）→ 写入 proof.txt（MARKER-PVC-OK）与 md5
备份：--default-volumes-to-fs-backup → Completed
删库：kubectl delete ns pvc-drill（PVC 与数据一起没了）
恢复：55 秒，PVC 重新 Bound，Pod Running
校验：proof.txt 内容 = MARKER-PVC-OK，md5 = 7ae294fe11903b4d33f7623783de751d（与备份前一致）
```

### 判据

```
① 必须"删干净"再恢复：只删 Pod 不删 PVC 是假演练
② 必须校验内容：能看到 PVC Bound 不代表数据回来了
③ 记录耗时：本次 55 秒（2Gi 数据 + Longhorn 重建卷）
```

## 演练⑨ 可用区网络隔离（比停 kubelet 更接近物理故障）

### 在干什么

上一项演练⑦ 停 kubelet 是"机器还活着但不汇报"，这次是**网络被切断**——
机器活着、kubelet 也在跑，但它连不上控制面，也连不上其他可用区。

### 做法（不碰云安全组，避免把自己锁在外面）

```
在 wk-2 / wk-4（d 区）上用 iptables 切断到 c 网段（172.23.163.0/24）与 b 网段（172.23.112.0/20）的进出
保留公网方向，这样还能 ssh 进去恢复
```

### 本次结果

```
t=0      隔离生效
t=49s    两台 NotReady，web 的 Service 端点 2→1
隔离期间  wk-3（b 区）的副本继续服务
恢复     去掉 iptables 规则，15 秒后 8/8 Ready
```

### 判据

```
① 只有"网络断"才算 AZ 级：停 kubelet 只影响本机汇报，网络隔离会连带存储与副本通信
② 恢复时间看的是"规则撤掉→节点回 Ready"，本次 15 秒
③ 要看 Longhorn 副本状态：跨区副本会短暂 degraded，恢复后自愈
```

## 演练⑩ 升级演练（1.37.0 → 1.37.2，在演练机上）

### 为什么不在主集群做

```
① 这个 yum/apt 源里根本没有 1.38（只有 1.37.0/1.37.1/1.37.2），"跨小版本"升不了
② 补丁升级虽小，但会重启控制面静态 Pod，主集群正在跑一堆平台组件
③ spare-01 本来就是演练机：从 1.37.0 起一套单节点，升到 1.37.2，练的是"步骤与顺序"
```

### 本次结果

```
起点      spare-01 单节点，kubeadm 1.37.0（独立网段 10.245/10.97 避免冲突）
init      20 秒
CNI       cilium 1.20.4（简化参数，只为让节点 Ready）
升级前    Ready，v1.37.0
装新 kubeadm  1.37.2
upgrade plan  目标 v1.37.2
upgrade apply 控制面 102 秒，SUCCESS
升 kubelet/kubectl 后 restart kubelet
升级后    Ready，v1.37.2，Server v1.37.2
总耗时    121 秒
关键验证  演练 Pod 的 UID 没变（98d2ac71…）→ 控制面升级不动工作负载
静态 Pod  etcd 91s / apiserver 61s / controller 40s / scheduler 25s（按顺序重启）
```

### 判据与顺序（这是本项真正要记的）

```
顺序（控制面）：装新 kubeadm → upgrade plan → upgrade apply → 升 kubelet → restart kubelet
顺序（多节点）：先升第一个控制面 → 其余控制面用 kubeadm upgrade node → 再逐个 worker
判据一：kubeadm version 与 kubectl Server 版本都变
判据二：节点 Ready、静态 Pod 全 Running
判据三：工作负载 Pod 的 UID 不变（变了说明顺带重建了业务，那就不是"只升控制面"）
边界：kubelet 升级必须最后做，且必须先 drain（本次单节点演练机无业务，省略了 drain）
```
