## 2.1 日巡检（10 项，一条命令）

```
PASS 节点Ready        8/8            期望 8
PASS 异常Pod          0              期望 0
PASS etcd成员         3              期望 3
PASS 证书剩余         364d           期望 >90d
PASS 待批CSR          0              期望 0
PASS etcd快照         0h前           期望 <26h
PASS 异地留存         1份            期望 >=1
PASS Velero备份       2              期望 >=1
PASS Longhorn余量     142G(最小)     期望 >30G
PASS 入口状态         True           期望 True
------------------------------------
PASS=10 WARN=0 FAIL=0
```

### 判据怎么定的（这是本册的核心，不是照抄公式）

```
节点 Ready      必须 8/8 —— 少一台说明有节点在滚，不是"正常波动"
异常 Pod        只要不是 Running/Completed 就记 WARN，不看它是不是"刚才才起"
etcd 成员       必须 3 —— 少一个就是失去容错，不是"能跑就行"
证书剩余        <90d 就要排期，<30d 是事故；kubeadm 证书默认一年
待批 CSR        有 Pending 就是有节点在等证书，通常意味着节点重装或 kubelet 异常
etcd 快照       <26h 才算合格（比 cron 的 6 小时留了足够余量）
异地留存        >=1 份 —— 只留本机等于没备份
Velero 备份     >=1 份 Completed
Longhorn 余量   取所有节点的最小可用空间 >30G；低于这个数三副本重建会失败
入口状态        Gateway Programmed 必须 True，否则外网已经进不来
```

**为什么这 10 项而不是 42 项**：日巡检要能在 10 秒内跑完、结论一眼看懂。
能力存在性检查（"有没有 DRA""有没有 OIDC"）半年不会变，属于搭建册的 42 项基线。

## 2.2 etcd 快照（每 6 小时，本地 + 异地）

```
脚本     /root/ops/etcd-snapshot.sh
cron     15 */6 * * *   →  每天 00:15 / 06:15 / 12:15 / 18:15
本地     /var/lib/etcd/snapshots/etcd-<时间戳>.db，保留 7 份
异地     infra-01:/data/etcd-backup/，保留 7 份（免密已配：cp-1 → infra-01）
耗时     单次 1.3 秒 / 76 MB（实测），对 apiserver 无可感影响
```

**异地这一步不是可选项**：集群整体故障时，本机的那 7 份快照一起没了。
本次为此专门配了 cp-1 到 infra-01 的免密，并把"异地留存份数"做进了日巡检。

## 2.3 Velero 定时备份

```
Schedule   velero/daily
cron 表达式 0 2 * * *
范围       demo-app + demo-secrets（业务与密钥）
TTL        168h（7 天）
存储       s3://velero-backup（infra-01 上的 SeaweedFS）
首次触发   手动用同一 schedule 打标签触发 → Completed
```

**为什么用 CRD 声明而不是 `velero schedule create`**：CLI 在这个版本上会卡住不回显，
而 Schedule 是标准 CRD，声明式写下去立刻生效、可进 Git、可被审计。运维要选"必然成功的那条路"。

## 核心大坑（2 条）

```
现象：日巡检里"Longhorn 余量"长期显示 0G
根因：Longhorn 的磁盘名是动态生成的（default-disk-<hash>），不是设备名
判据：取所有节点所有磁盘的最小 storageAvailable，而不是按设备名取

现象：Velero 的 schedule 用 CLI 建了但没回显、也没生效
根因：CLI 与 server 版本不匹配时会静默卡住
判据：以 kubectl 能否看到 Schedule 对象、以及 lastBackup 是否更新为准
```

## 2.6 告警分级投递（本次新增）

### 结构

```
Prometheus 规则 → Alertmanager 路由（按 severity 分流）
  severity=critical → /p1    （该叫人起床的）
  severity=warning  → /p2    （当天处理的）
  其余              → /p3    （上班看的）
落点：infra-01:8088，systemd 常驻，按级别写 /data/alerts/{p1,p2,p3}.log
```

### 实测

```
造三条规则（DrillCritical / DrillWarning / DrillInfo，expr=vector(1)）
p1.log 收到 1 条（DrillCritical）
p2.log 收到 1 条（DrillWarning）
p3.log 收到 6 条（含 DrillInfo 与重复投递）
```

### 判据

```
"有告警"和"告警到人"是两件事：
判据一：Alertmanager 的 /api/v2/alerts 里有告警（说明规则与抓取正常）
判据二：落点的日志里有对应级别（说明路由与出口正常）
两个都过才算通 —— 本次第一次查就是因为只看了一个目录，误判成"没投递"
```

## 2.7 配额与限额（本次新增）

```
demo-app 生效值（当前用量 / 上限）
requests.cpu      180m / 4
requests.memory   288Mi / 8Gi
limits.cpu        1200m / 8
limits.memory     832Mi / 16Gi
pods              11 / 30
pvc               0 / 6
LimitRange 默认     request 20m/32Mi，limit 200m/128Mi，单容器上限 2C/2Gi
```

**为什么两者都要**：Quota 管"整个命名空间的总量"，LimitRange 管"单个容器别不写也没上限"。
只有 Quota，一个容器就能吃掉全部配额；只有 LimitRange，命名空间总量无上限。
