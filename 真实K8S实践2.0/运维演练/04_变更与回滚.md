# 04 · 变更与回滚

> **这一册在整件事的哪一步**：03 处理"已经坏了"→【04 管"要动手之前"】。
> 核心一句：**变更的风险不取决于动作大小，而取决于"失败时你能不能回到上一个状态"。**

## 一、三类变更，三种纪律

```
A 应用层（改镜像、改副本、改配置）
   窗口      随时
   验证      滚动完成后 Pod 全 Ready + 入口 200
   回滚      ArgoCD 回退 revision 或 git revert；30 秒内
   注意      停掉 selfHeal 再手工改，否则改不上去（本次演练踩过）

B 准入层（改 Kyverno 策略、改 MAP）
   窗口      业务低峰
   验证      对照组：打标签的 ns 应被改/被拒，未打标签的不受影响
   回滚      删除策略对象；策略是 fail-closed，删错会挡住所有写入
   注意      排除名单要含全部平台命名空间（本次扩到 14 个才够）

C 数据面（改 CNI、改加密、改 apiserver 参数）
   窗口      必须单独开，且事先导出 values / 备份清单
   验证      三个数：agent Init 计数、目标 DaemonSet 就绪数、加密/状态字段
   回滚      helm rollback 到上一 revision；清单类用备份文件覆盖
   注意      任何"节点仍 Ready"都不能作为成功的证据（03 册第 3 条）
```

## 二、变更前的四件事（缺一件就别动）

```
① 备份要改的东西
   helm get values → 文件；静态 Pod 清单 → 复制一份带 .bak
② 记录变更前的关键计数
   agent 就绪数、Pod Running 数、42 项验收结果
③ 写清楚"什么现象算失败"
   例：3 分钟内 ztunnel 不到 8/8 就算失败（而不是"再看看"）
④ 想好回滚的第一条命令
   想不出来 = 这个变更现在不能做
```

## 三、变更后的三步

```
① 复跑 42 项验收（不是看一眼）
② 对比变更前的计数，逐项解释差异
③ 如果有差异但"看起来没事"，一律按未完成处理
   —— 本次三次演练都是这一步抓到副作用的（网关地址丢失、DRA claim 消失、beyla OOM）
```

## 四、已经发生过的回滚（可当模板）

```
场景                     动作                     恢复耗时
ztunnel 起不来             helm rollback            约 2 分钟
apiserver 清单写坏        还原 .bak + 等 kubelet    立即（本次 9 秒内恢复 3 台）
Del ArgoCD App 误删准入    helm 按原版本重装         约 3 分钟
删 CNI                     helm -f 备份 values 重装  68 秒
```

## 五、不能回滚的变更（必须提前想清楚）

```
① 删掉 etcd 数据目录 / 重建控制面 —— 只能靠快照恢复（02 册每 6 小时一份）
② 把节点从集群移除 —— 上面 Pod 会被重建，但本地 emptyDir 数据丢失
③ 修改集群网段（Pod/Service CIDR）—— 等价重建集群
判据：这三类在动手前必须有一次"演练过的恢复路径"，否则不做。
```
