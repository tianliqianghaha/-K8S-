# 00 · 运维册总览（演练与日常运维）

> **这一册是什么**：搭建册（`D://真实K8S实践2.0//` 根目录 01–17）回答"怎么建成的"；
> 本册回答"**建好之后每天怎么维持、坏了怎么救、怎么证明它还活着**"。
> 两册分工唯一标准：**做一次就不变的内容归搭建册，需要每周重复做的归本册。**

## 一、边界（避免两册互相污染）

```
搭建与交付册（根目录）        运维演练册（本目录）
├─ 01 开工前检查表            ├─ 00 本册总览
├─ 02–12 各章（地基→网格）     ├─ 01 演练手册（五项真实演练）
├─ 13 最终清单（一次性基线）    ├─ 02 日常运维（日/周/月动作，已脚本化）
├─ 14 大坑速查（搭建期踩的）    ├─ 03 故障处置（现象→判据→边界）
├─ 15 速查卡（地址/版本）       └─ 04 变更与回滚（窗口与回滚路径）
├─ 16 回滚与重装
└─ 17 版本锁定表

判断归属的两句话：
  "这条内容半年后重看会发现一个字都没改" → 搭建册
  "这条内容每周都要跑、每次都要留新读数"   → 本册
```

## 二、目录

```
01 演练手册      五场演练（镜像失败 / drain / apiserver 两台下线 / 删 CNI / etcd 恢复）
                 每项给：怎么练 · 判据 · 事后副作用
02 日常运维      日巡检 10 项（已脚本化，10/10 通过）· etcd 每 6 小时快照（本地+异地各 7 份）
                 · Velero 每日 02:00（TTL 7 天）· 周/月动作清单
03 故障处置      按"现象"排的处置顺序：第一判据是什么、边界在哪、什么时候必须回滚
04 变更与回滚    三类变更（数据面/准入/应用）各自的窗口、验证点、回滚路径
```

## 三、节奏（这套环境按这个跑）

```
每日   日巡检脚本（10 项）→ 有 WARN 当天处理，有 FAIL 立刻进 03 册
每 6h  etcd 快照（已上 cron：15 */6 * * *，本地 7 份 + 推 infra-01 7 份）
每日   02:00 Velero 全量备份（demo-app + demo-secrets，TTL 7 天）
每周   恢复抽验一次（Velero 恢复一个 ns 到新名字，比对标记）
       容量看一次（Longhorn 最小余量、节点磁盘、Prom 保留期）
每月   演练一项（照 01 册轮着来）· 证书到期检查（当前剩余 364 天，不用管）
每季   升级评估（kubeadm / CNI / 存储版本），先在 spare-01 试
```

## 四、两个基线，别混

```
交付基线（搭建册 13）  42 项只读验收，用来回答"这套东西还是不是当初那个样子"
                       变更前后各跑一次，掉项就是变更引入的
日巡检（本册 02）      10 项，用来回答"今天能不能正常干活"
                       每天跑，看趋势不看单点
两者不是替代关系：42 项里有一半是"能力存在性"，日巡检里全是"今天健康度"。
```
