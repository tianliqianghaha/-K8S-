# 03 · 故障处置（现象 → 第一判据 → 边界）

> **这一册在整件事的哪一步**：02 是"日常维持"→【03 是"今天出事了"】→ 04 是"要改东西时"。
> 写法：每条只给三样 —— **第一眼看什么、判据是什么、什么时候必须放弃修复直接回滚**。
> 不写命令（命令在搭建册各章与 ops 脚本里），避免在慌乱时照着敲错东西。

## 1 · 外网访问不了

```
第一眼看   Gateway 的 Programmed 条件（不是看 Envoy Pod 是否 Running）
判据        Programmed=True 但访问仍失败 → 问题在 HTTPRoute 或后端
            Programmed=False 且 reason=AddressNotAssigned → 数据面 Service 没地址
              （本次真实遇到：drain 之后 Service 变回 LoadBalancer，没有 LB 实现就没地址）
边界        改 Service 类型属于入口层变更，可在 5 分钟内回滚；
            超过 10 分钟仍未恢复，先回到"上一个能访问的 Service 类型"再排查
```

## 2 · 新 Pod 起不来（四层判断，按顺序）

```
① 调度层   Pod 是否 Pending。Pending 且事件是"0/N nodes available" → 资源/污点/亲和性
② 网络层   Pending 但没有 IP、或事件是"failed to setup network"→ CNI agent 不在了
           （判据：cilium DaemonSet 的 ready 数，不是节点是否 Ready）
③ 准入库   事件是"admission webhook ... denied"→ 准入策略拒绝，看策略名即可定位
④ 镜像层   事件是 ErrImagePull/ImagePullBackOff → 三类措辞区分 tag/认证/网络
边界       只要 ②（网络层）成立，先恢复 CNI，不要在缺网的情况下继续调业务
```

## 3 · 老 Pod 都正常，新 Pod 全不通

```
第一眼看   cilium DaemonSet 的 ready 数
判据        这是 eBPF 数据面的典型形态：转发规则已在内核，agent 挂了存量照跑、新增全死
            （本次演练：删 NS 后老 Pod 2/2 存活，新 Pod 直接 Pending）
处置        恢复 agent（按搭建册第 3 章的 values 重装），68 秒可恢复
边界        不要动存量 Pod；它们是你还能进集群的唯一通道
```

## 4 · Service 通但 DNS 不通（本次真实案例）

```
现象：可用区演练期间，业务报 "bad address xxx.svc.cluster.local"
第一眼看   CoreDNS 副本落在哪些节点上（不是看副本数）
判据        两个副本在同一台 → 那台一停就等于 DNS 全灭
            （本次两副本都在 wk-4，wk-4 停掉后立刻全挂）
处置        加硬反亲和 + 扩到 3 副本 → 分散到三台不同节点
边界        DNS 全挂时先用 IP 直连保业务，再修 DNS
```

```
第一眼看   CoreDNS 的 ready 数 + kube-dns 的 Endpoints
判据        Endpoints 为空 → CoreDNS 没被选进服务；有 Endpoints 但仍不通 → 查 Service 转发
边界        DNS 全挂时，可用 IP 直连先恢复业务，再修 DNS
```

## 5 · 存储写不进去

```
第一眼看   Longhorn 节点的最小余量与 volume 的 robust 状态
判据        余量低于 30G → 三副本重建会失败（1.0 真实栽过）
            volume 状态 degraded → 有副本掉了，先看是哪台节点
边界        余量告急时，先扩盘或删无用 PVC，不要触发大规模重建
```

## 6 · 集群整体打不通（最严重）

```
第一眼看   VIP 的 healthz + 各台 apiserver 容器是否存在
判据        容器不存在（不是 CrashLoop）= 静态 Pod 清单有问题或被移走
            （本次真实事故：文本改清单导致 YAML 非法，容器根本没被创建）
处置        还原清单备份 → 等 kubelet 拉起 → 从一台节点本地 6443 验证
边界        这时候"能进集群"的唯一路径是节点本地直连 6443，不是 VIP
```

## 7 · 告警没发出去

```
第一眼看   Alertmanager 的 active alerts 有没有
判据        有告警但没到人 → 路由/接收器问题；连告警都没有 → 规则或抓取问题
边界        当前环境没有真实 IM 出口，这一项只能验证到"告警产生且路由命中"
```

## 处置共同原则（四条）

```
① 先判断"是新增坏还是存量坏"——存量坏是数据面，新增坏多半是准入/调度/镜像
② 数据面故障的默认动作是回滚，不是修复（01 册演练③④⑤都验证过）
③ 每次处置完必须复跑 42 项验收，因为恢复动作本身会留下副作用
   （本次五次演练，三次都是"恢复了但验收掉到 40/42"）
④ 处置过程只记录"现象与判据"，命令写在脚本里 —— 慌乱时人只会照着抄错
```


## 8 · 入口 Programmed=False（本次遇到两次）

```
第一次现象  AddressNotAssigned：No addresses have been assigned to the Gateway
第一版处置  删掉数据面 Service 让它重建、再手工改成 NodePort → 恢复，但几分钟后复发
根因        EG 会把自己的 Service 类型 reconcile 回 LoadBalancer，而集群没有 LB 实现
            → 手改属于"和控制器对抗"，必然复发
正解        把 NodePort 写进声明：给 GatewayClass 挂 EnvoyProxy（envoyService.type=NodePort）
判据        看 Service 的 type 是否稳定为 NodePort，以及网关地址是否出现节点 IP
注意        这个 API 组是 gateway.envoyproxy.io，不是 config.gateway.envoyproxy.io
```

**这条要记住的判断**：凡是"手工改完过一会又变回去"的，问题不在你改得对不对，
而在"控制器认为自己才是真相源"。要改就得改控制器的输入。
