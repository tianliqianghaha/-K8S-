## 3.1 在干什么

让"3 台 apiserver"对外只呈现一个地址：`172.23.163.97:16443`。
kubeadm 的 controlPlaneEndpoint、所有节点的 kubeconfig、Cilium 的 k8sServiceHost，都用这一个地址。

## 3.2 为什么必须是 HAVIP，不能自己 ARP

```
本次真实结论（1.0 已验证，2.0 直接复用）
在自己网卡上加一个空闲 IP/32，从对端 ping：3 包 100% 丢包。
原因：阿里云 VPC 不转发"未分配给实例的 IP"的 ARP 请求，自建 VIP 在云上天然不成立。
结论：通道必须是 HAVIP（高可用虚拟IP）——它是在 VPC 里注册过的地址，允许 ARP。
```

## 3.3 在哪台敲

- HAVIP 绑定：本机调 VPC API（`AssociateHaVip`）
- haproxy / keepalived：3 台控制面
- kubeadm：cp-1 上 init，其余 join

## 3.4 敲什么

```bash
# ① 绑 HAVIP（第 2、3 台要重试，状态 InUse 时会报 IncorrectHaVipStatus）
aliyun vpc AssociateHaVip --HaVipId havip-j6crlqrs65eu0p9ulankm \
  --InstanceId i-j6cb6kihp7cqtdl0luqa --InstanceType EcsInstance

# ② haproxy：只做 16443 → 6443 的四层转发
frontend kube-apiserver
    bind *:16443
    default_backend kube_apiserver_back
backend kube_apiserver_back
    balance roundrobin
    option tcp-check
    server cp-1 172.23.163.109:6443 check inter 2s fall 3 rise 2
    server cp-2 172.23.163.108:6443 check inter 2s fall 3 rise 2
    server cp-3 172.23.163.107:6443 check inter 2s fall 3 rise 2

# ③ keepalived：单播 + 健康检查脚本（haproxy 挂了就降优先级让出 VIP）
vrrp_instance VI_APISERVER {
    state BACKUP
    interface eth0
    virtual_router_id 51
    priority 150                    # cp-2=140 cp-3=130
    unicast_src_ip 172.23.163.109
    unicast_peer { 172.23.163.108  172.23.163.107 }
    virtual_ipaddress { 172.23.163.97/32 dev eth0 }
    track_script { chk_haproxy }
}

# ④ kubeadm init（关键两行）
controlPlaneEndpoint: 172.23.163.97:16443
# 命令行加：--skip-phases=addon/kube-proxy   ← 交给 Cilium
```

**版本不要写死**：`kubernetesVersion` 取 `kubeadm version -o short` 的真实输出。
本次 apt 装到 v1.37.2，配置里就写 v1.37.2；写成"最新"或写错小版本，init 会去拉不存在的小版本镜像。

## 判官卡：控制面能不能跨可用区

```
选项 A HAVIP + 同交换机（本次）
  优点：免费、延迟最低、配置最简单
  缺点：3 台控制面必须同 AZ；该 AZ 整体故障 = etcd 丢仲裁 = 全集群不可用

选项 B 私网 CLB 作 controlPlaneEndpoint
  优点：后端可跨可用区，控制面能拆到 b/c/d，真正跨 AZ 高可用
  缺点：多一个付费组件（按小时），且 CLB 的 4 层健康检查与 haproxy 要二选一

判据：如果目标是"练会跨 AZ 的架构"，B 是必修；
      如果目标是"练会一整套平台能力"，A 够用，把跨 AZ 留给工作负载层。
本次：A（工作负载已跨 AZ，控制面单区这条写进 13 章的"答不了"清单）。
```

## 核心大坑（3 条）

```
现象：HAVIP 绑第 2 台报 IncorrectHaVipStatus
根因：绑完第 1 台后 HAVIP 进入中间状态，必须等它回落
防：重试（5 秒 × 12 次），不要以为配置错了

现象：join 时报 x509: certificate is valid for ... not 172.23.163.97
根因：certSANs 漏了 VIP
防：init 前把"VIP + 全部节点 IP + 节点名"列成清单逐项核

现象：keepalived 双主（两台都 hold 同一个 VIP）
根因：用了组播 VRRP，云上组播被过滤，两台互相听不到
防：必须 unicast_src_ip + unicast_peer，且 virtual_router_id 全网唯一
```
