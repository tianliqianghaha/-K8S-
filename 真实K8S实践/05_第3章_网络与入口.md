## 3.1 装 Cilium（判官卡：参数为什么这么写）

### 在干什么

用 Helm 装 Cilium，让它同时承担 CNI + Service 代理 + 网络策略 + 可观测。

### 为什么现在做

节点现在全是 NotReady，装完才 Ready；而 Service 能不能用，取决于 kube-proxy 是否被正确替代。

### 在哪台敲

cp-1（有 kubeconfig 的那台）。

### 敲什么

```bash
export KUBECONFIG=/etc/kubernetes/admin.conf

# 1) Helm
curl -fsSL https://get.helm.sh/helm-v3.19.0-linux-amd64.tar.gz -o /tmp/helm.tgz
tar -C /tmp -xzf /tmp/helm.tgz && install -m755 /tmp/linux-amd64/helm /usr/local/bin/helm

# 2) Gateway API CRD（先装标准 CRD，后面 Envoy Gateway 要用）
kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.6.1/standard-install.yaml

# 3) Cilium
helm repo add cilium https://helm.cilium.io/ && helm repo update cilium
helm upgrade --install cilium cilium/cilium --version 1.20.4 \
  --namespace kube-system \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=172.23.163.97 \
  --set k8sServicePort=16443 \
  --set routingMode=tunnel \
  --set tunnelProtocol=vxlan \
  --set ipam.mode=kubernetes \
  --set operator.replicas=2 \
  --set hubble.enabled=true \
  --set hubble.relay.enabled=true \
  --set hubble.ui.enabled=true \
  --set hubble.ui.service.type=NodePort \
  --set bpf.masquerade=true \
  --set ipMasqAgent.enabled=true \
  --wait --timeout 12m
```

### 每个参数为什么这么写

```
kubeProxyReplacement=true   kube-proxy 已经被 skip 掉，Service 必须由 eBPF 接管
k8sServiceHost/Port         ★ 没有 kube-proxy 的 ConfigMap 可读，必须显式告诉 agent
                              apiserver 在哪；写 VIP 而不是某台 IP，控制面挂一台不受影响
routingMode=tunnel          ★ 阿里云 VPC 不认 podCIDR 路由，不能用 native
tunnelProtocol=vxlan        IPIP 在云上常被丢，VXLAN(UDP 8472) 才是能落地的
ipam.mode=kubernetes        用 kubeadm 分的 podCIDR，避免与 VPC 网段撞车
bpf.masquerade=true         用 eBPF 做 SNAT，省掉 iptables 规则（3.3 的坑就出在这里的默认值上）
```

### 看到什么算过

```bash
kubectl get nodes                     # 8 台全 Ready
kubectl -n kube-system get ds cilium  # 8/8
kubectl -n kube-system get ds kube-proxy   # NotFound
kubectl -n kube-system exec <cilium-pod> -c cilium-agent -- cilium-dbg status | grep -E 'KubeProxy|Routing|Masq'
```

```
本次真实回显
KubeProxyReplacement: True [eth0 172.23.163.102 (Direct Routing)]
Routing:              Network: Tunnel [vxlan]  Host: BPF
Masquerading:         BPF (ip-masq-agent) [eth0] 10.244.8.0/24
```

## 3.2 第一次连通性验收（会在这里撞上本章最大的坑）

### 在干什么

按四层顺序验证：Pod→Pod（跨节点）、Pod→Service、Pod→节点、Pod→公网。**不要跳过任何一层**，因为不同层挂的症状完全不同。

### 敲什么

```bash
# 起一个带工具的调试 Pod
kubectl run nettest --image=nicolaka/netshoot:v0.13 --restart=Never --command -- sleep 3600
kubectl wait --for=condition=Ready pod/nettest --timeout=120s

# 四层
kubectl exec nettest -- ping -c 3 <另一个节点上的 Pod IP>          # ① Pod→Pod
kubectl exec nettest -- curl -sk https://10.96.0.1:443/healthz     # ② Pod→Service（apiserver）
kubectl exec nettest -- curl -sk https://172.23.163.99:6443/healthz # ③ Pod→节点 IP
kubectl exec nettest -- curl -s -o /dev/null -w '%{http_code}\n' http://223.5.5.5  # ④ 出网
```

### 本次真实结果（修复前）

```
① Pod→Pod 跨节点：3 packets, 0% packet loss          → 通
② Pod→Service：  超时（exit 28）                      → 不通
③ Pod→节点：     超时                                 → 不通
④ 出网：         超时                                 → 不通
```

**这就是最容易被误判成"CNI 装错了"的形态：Pod 之间好好的，只剩出网全死。**

## 3.3 定位与修复：Pod 出网不带 SNAT

### 在干什么

用"抓包看源 IP"把问题从"网络不通"缩小到"SNAT 没发生"。

### 为什么这么查

```
Pod→Pod 通，说明 VXLAN 与 BPF 转发都正常；
那么 Pod→外部失败只可能是三件事之一：
  a) 包出不去（路由/BPF 丢）
  b) 包出去了，但源 IP 是 Pod 网段，外部回不来
  c) 包出去了、回得来，但被策略丢
抓一次 eth0 就能区分 a 和 b：看包有没有出现、源 IP 是什么。
```

### 敲什么（三个证据）

```bash
# 证据 1：从 Pod 发起 ping，同时在 Pod 所在节点抓 eth0
kubectl exec nettest -- ping -c 8 172.23.163.99 &
ssh root@<nettest 所在节点> 'timeout 8 tcpdump -ni eth0 icmp'

# 证据 2：对端节点看它收到什么源 IP
ssh root@172.23.163.99 'timeout 7 tcpdump -ni eth0 icmp'

# 证据 3：看 cilium 的 drop/trace
kubectl -n kube-system exec <cilium-pod> -c cilium-agent -- cilium-dbg monitor --type drop
```

### 本次真实结果

```
证据 1（本节点 eth0）
10:22:28 IP 10.244.8.6 > 172.23.163.99: ICMP echo request, ...
         ↑ 源是 Pod IP，没有被 SNAT 成节点 IP

证据 2（对端节点）
什么都没有收到（VPC 直接丢了：源 10.244/16 不在 VPC 路由表里）

证据 3（drop 监控）
无任何 drop 事件 → 说明不是策略丢包，是缺少 SNAT
```

### 根因

```
Cilium 的 ip-masq-agent 默认 nonMasqueradeCIDRs 包含 172.16.0.0/12（RFC1918 全套）。
而阿里云 VPC 的节点网段正好是 172.23.160.0/20 —— 落在 172.16/12 里面。
结果：Pod 访问 172.23.x.x 被认为"是内网，不需要 NAT"，于是源 IP 保持 10.244.8.6，
      而 VPC 只认 172.23.x，包进不了 VPC 的路由 → 丢弃。
```

验证这一点（看 agent 启动时加的 CIDR 列表）：

```bash
kubectl -n kube-system logs <cilium-pod> | grep -i 'ip-masq-agent' | grep CIDR
```

```
本次真实输出（节选）
Adding CIDR cidr=10.0.0.0/8
Adding CIDR cidr=172.16.0.0/12      ← 元凶
Adding CIDR cidr=192.168.0.0/16
...
```

### 修复：只排除集群自己的网段

```bash
helm upgrade cilium cilium/cilium --version 1.20.4 -n kube-system --reuse-values \
  --set ipMasqAgent.config.nonMasqueradeCIDRs="{10.244.0.0/16,10.96.0.0/12}" \
  --set ipMasqAgent.config.masqLinkLocal=false

# 确认 ConfigMap 生效
kubectl -n kube-system get cm ip-masq-agent -o jsonpath='{.data}'
```

```
本次真实输出
{"config":"{\"masqLinkLocal\":false,\"nonMasqueradeCIDRs\":[\"10.244.0.0/16\",\"10.96.0.0/12\"]}"}
```

修复后复测（等待 30~60 秒让 agent 下发）：

```
② Pod→Service 10.96.0.1 → ok
③ Pod→节点 172.23.163.99:6443 → ok
④ 出网 → 403 / 404（有 HTTP 响应就是连通）
DNS → nslookup kubernetes.default 成功返回 10.96.0.1
```

### 判官卡：这个值怎么定

```
判据只有一条：nonMasqueradeCIDRs 里的网段，必须是"集群自己的、不需要 NAT 的"。
本次 = Pod 网段 10.244.0.0/16 + Service 网段 10.96.0.0/12。
凡是节点网段（172.23.x）、VPC 网段，都必须从列表里移出去，否则 Pod 出网就断。
换个云、换个 VPC 网段，这个值就要重算 —— 这是本方案唯一必须按环境改的网络参数。
```

## 3.5 MTU：必须验一次，否则会遇到"玄学问题"

### 在干什么

用大包确认隧道开销被正确扣掉了。

### 为什么现在做

VXLAN 减 50 字节。小包（ping、curl 首页）全通，大包（HTTPS 握手、镜像层、SSH 传文件）会静默卡住，
现象极像"网络时好时坏"。

### 敲什么

```bash
POD=$(kubectl -n apps get pod -l app=podinfo -o jsonpath='{.items[0].status.podIP}')
kubectl exec nettest -- ping -c 2 -M do -s 1422 $POD   # 1422+28 = 1450，应通
kubectl exec nettest -- ping -c 2 -M do -s 1472 $POD   # 1472+28 = 1500，应不通
```

```
本次真实结果
-s 1422 → 2 received, 0% packet loss
-s 1472 → 失败（exit 1）
Pod 内 ip route：default via 10.244.x.239 dev eth0 mtu 1450
```

## 3.6 入口：Gateway API + Envoy Gateway

### 在干什么

装 Envoy Gateway（与 CNI 解耦的入口实现），用 Gateway + HTTPRoute 暴露业务，TLS 由 cert-manager 签。

### 为什么选它而不是 Cilium 自带 Gateway

```
换 CNI 时入口一行都不用改。今天的 Cilium 明天可能换 Calico，
但 Gateway API 的 HTTPRoute 是标准，不绑在某个 CNI 上。
```

### 敲什么

```bash
# 1) 装 Envoy Gateway（★ 必须 --skip-crds）
helm install eg oci://docker.io/envoyproxy/gateway-helm --version v1.5.0 \
  -n envoy-gateway-system --create-namespace --skip-crds --wait --timeout 10m

# 2) 手建 GatewayClass（本次 chart 没自动建）
kubectl apply -f - <<'EOF'
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: eg
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller
  description: "Envoy Gateway（与 CNI 解耦的独立入口实现）"
EOF
kubectl get gatewayclass          # ACCEPTED = True

# 3) cert-manager + 内部 CA
helm repo add jetstack https://charts.jetstack.io && helm repo update jetstack
helm upgrade --install cert-manager jetstack/cert-manager --version v1.19.1 \
  -n cert-manager --create-namespace --set crds.enabled=true --set replicaCount=2 --wait

kubectl apply -f - <<'EOF'
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: {name: selfsigned-bootstrap}
spec: {selfSigned: {}}
---
apiVersion: cert-manager.io/v1
kind: Certificate
metadata: {name: internal-ca, namespace: cert-manager}
spec:
  isCA: true
  commonName: k8s-prod-internal-ca
  secretName: internal-ca-keypair
  duration: 87600h
  privateKey: {algorithm: ECDSA, size: 256}
  issuerRef: {name: selfsigned-bootstrap, kind: ClusterIssuer}
---
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: {name: internal-ca}
spec: {ca: {secretName: internal-ca-keypair}}
EOF

# 4) 业务 + 通配符证书 + Gateway + 跳转
kubectl create ns apps
kubectl apply -f - <<'EOF'
apiVersion: cert-manager.io/v1
kind: Certificate
metadata: {name: apps-wildcard, namespace: apps}
spec:
  secretName: apps-wildcard-tls
  duration: 2160h
  renewBefore: 360h
  commonName: "*.apps.k8s.local"
  dnsNames: ["*.apps.k8s.local", "apps.k8s.local"]
  issuerRef: {name: internal-ca, kind: ClusterIssuer}
EOF
```

Gateway 与 HTTPRoute（要点：HTTP 只做跳转，HTTPS 才路由）：

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: {name: prod-gateway, namespace: apps}
spec:
  gatewayClassName: eg
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes: {namespaces: {from: Same}}
    - name: https
      protocol: HTTPS
      port: 443
      hostname: "*.apps.k8s.local"
      tls:
        mode: Terminate
        certificateRefs: [{name: apps-wildcard-tls}]
      allowedRoutes: {namespaces: {from: Same}}
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: {name: podinfo, namespace: apps}
spec:
  parentRefs: [{name: prod-gateway, sectionName: https}]
  hostnames: ["demo.apps.k8s.local"]
  rules:
    - matches: [{path: {type: PathPrefix, value: /}}]
      backendRefs: [{name: podinfo, port: 9898}]
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: {name: podinfo-redirect, namespace: apps}
spec:
  parentRefs: [{name: prod-gateway, sectionName: http}]
  hostnames: ["demo.apps.k8s.local"]
  rules:
    - filters:
        - type: RequestRedirect
          requestRedirect: {scheme: https, statusCode: 301}
```

### 看到什么算过（本次真实回显）

```
kubectl -n apps get gateway   → CLASS=eg  PROGRAMMED=True（等 2~3 分钟）
Envoy 的 Service 是 LoadBalancer 但 EXTERNAL-IP pending（云上没有 CCM 时正常），
NodePort 已被分配：http 31559 / https 32691

curl -sk --resolve demo.apps.k8s.local:32691:<任意节点IP> https://demo.apps.k8s.local:32691/
  → 200，返回 podinfo 的 JSON
curl -sk --resolve wrong.apps.k8s.local:32691:... https://wrong.apps.k8s.local:32691/
  → 404（Host 不匹配）
curl -s --resolve demo.apps.k8s.local:31559:... http://demo.apps.k8s.local:31559/
  → 301
证书：subject=CN=*.apps.k8s.local  issuer=CN=k8s-prod-internal-ca  notAfter=+90 天
```

⚠️ 记住一件事：**Envoy 的 Service 重建时 NodePort 会变**。本次从 31320/32663 变成 32691/31559，
如果脚本里写死了端口，会得到 "Connection refused"。

## 3.7 默认拒绝 + 白名单

### 在干什么

把 apps 命名空间改成"默认谁都不能进、只放行明确列出的"。

### 敲什么

```yaml
# 1) 默认全拒
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny-all, namespace: apps}
spec:
  podSelector: {}
  policyTypes: ["Ingress", "Egress"]
---
# 2) 放行 DNS（不放这条，所有解析都断）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: allow-dns-egress, namespace: apps}
spec:
  podSelector: {}
  policyTypes: ["Egress"]
  egress:
    - to:
        - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: kube-system}}
          podSelector: {matchLabels: {k8s-app: kube-dns}}
      ports: [{protocol: UDP, port: 53}, {protocol: TCP, port: 53}]
---
# 3) 只允许入口数据面进
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: allow-from-gateway, namespace: apps}
spec:
  podSelector: {matchLabels: {app: podinfo}}
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: envoy-gateway-system}}
      ports: [{protocol: TCP, port: 9898}]
```

### 看到什么算过（本次真实回显）

```
未打标签的 Pod 访问 → 超时
Hubble 明确给出两条：
  policy-verdict:none INGRESS DENIED (TCP Flags: SYN)
  Policy denied DROPPED (TCP Flags: SYN)

同时入口不受影响：三台节点上 HTTPS 都是 200、HTTP 都是 301
```

### 判官卡：策略生效没生效，信谁

```
别只看 curl 超时（超时可能是别的原因）。信 Hubble：
  hubble observe --namespace apps --verdict DROPPED
看到 "Policy denied" 才是策略真的在拦。
```

## 核心大坑（5 条，每条三行封顶）

```
现象：Pod 之间通，Pod 出网 / 访问 Service 全死；节点 IP 都 ping 不通
根因：ip-masq-agent 默认把 172.16.0.0/12 当内网不 SNAT，与阿里云节点网段重叠
防：nonMasqueradeCIDRs 只留 Pod 段 + Service 段（本章 3.3 的完整诊断路径）

现象：cilium agent CrashLoop，日志说找不到 kube-proxy ConfigMap
根因：kubeadm 加了 --skip-phases=addon/kube-proxy，agent 无从推断 apiserver 地址
防：必须显式 --set k8sServiceHost=<VIP> --set k8sServicePort=16443

现象：装 Envoy Gateway 报 "Installing CRDs with version before v1.5.0 is prohibited"
根因：我们装的是 Gateway API v1.6.1，EG chart 自带的 CRD 更旧，被 safe-upgrades 策略拦
防：--skip-crds 安装，并手建 GatewayClass

现象：Gateway 一直 PROGRAMMED=False
根因：云上没有 LB 实现，Service 的 EXTERNAL-IP 永远 pending
防：不用等它；直接用 NodePort，或以 NodePort 方式访问（端口会随 Service 重建而变）

现象：前一天还能访问，第二天 curl 报 Connection refused
根因：Envoy 的 Service 重建后 NodePort 变了（本次 31320→32691）
防：每次从 kubectl get svc 现取端口，别写死
```
