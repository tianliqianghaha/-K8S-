不看评价，只看 01/05/07/12/16 的真实回显：

```

           kube-proxy 不存在 · KUBE-SVC 链 = 0 · MTU 边界 1422 通 / 1472 不通
           ★ 但 Pod 出网靠 ip-masq-agent 修（说明 bpf.masquerade 很可能没开，吃不到 eBPF 全收益）

           ★ 容量 213G / 上限 208G，已超，副本重建失败过一次

           OIDC（Dex）按用户 RBAC · aescbc etcd 加密 · 审计开启
           ★ 准入只有"拒"，没有"改写"；密钥只有"静态封存"，没有轮换
```

**一句话**：这套东西的强项是"闭环的深度"（恢复、告警分级、验签、自愈都真跑过），
弱项是"能力的宽度"（弹性、trace、东西向身份、变更侧、渐进发布全是空的）。

## 18.3 那套评价逐条核

### 先说它对的（三条，都是硬道理）

```
① "先进不等于装得多，取决于选择对不对"
   —— 这条对，而且是你这套东西唯一的价值观来源。别丢。

② ①②⑧⑨ 四个判断与你真实状态完全一致
   —— Cilium eBPF 无 kube-proxy ✓、Gateway API 无 Ingress ✓、
      备份目标在集群外 ✓、ArgoCD + 外部 Git ✓。这四个它没看错。

③ "每个验一个数，这套就是先进的"
   —— 这是全文最值钱的一句。你的 15 条硬验收本来就是这么干的，
      它只是把标准说穿了：没有回显的能力等于没装。
```

### 再说它薄的（四条，都是"工具当能力"）

```
薄一  ⑤ 把 Kueue 和 DRA 塞进同一槽
      排队（谁先跑）和分设备（跑在哪张卡上）是两件事，不能一个槽位打包。
      更要紧的是"假设备也能跑通"不是开关：DRA 必须有 driver，
      要装 kubernetes-sigs 的 dra-example-driver（模拟 GPU）才有 Claim 可发。
      而 Kueue 的 DRA 集成还要额外开 feature gate。
      → 正确做法：先单独把 DRA 跑通（一个 Pod 拿到 ResourceClaim），再上 Kueue 排队。
        一次上两个，失败时你不知道是 driver 没起还是队列没放行。

薄二  ③ ambient 只覆盖了"半个网格"
      ztunnel 给你的是 L4 mTLS + L4 授权，不给 L7（重试/超时/流量切分/HTTP 级策略）。
      要 L7 还得加 waypoint proxy（每 ns 一个），那才是完整网格。
      你还有个更硬的隐性风险：你现在是 tunnel+vxlan、MTU 只剩 1422，
      ztunnel 的 HBONE 还叠一层封装 —— 装完 MTU 边界必须重测，
      大概率从 1422 掉到 1350 左右，应用不调 MTU 会出现"大包偶发卡死"。
      （tunnel 模式与 ambient 的兼容性以 1.20.4 的官方 compat 表为准，装前先探）

薄三  ⑦ 让你新装一套 OTel Collector —— 你已经有 Alloy 1.9.2 在 8 台跑着
      Grafana Alloy 自带 eBPF receiver（OBI / 原 Beyla），能直接从内核拿 span，
      应用零改动。所以这条的正确姿势是"接通"而不是"新装"：
      Alloy(eBPF) → OTel Collector(tail sampling) → Tempo。
      Collector 值得留（统一出口 + 尾部采样），但它真正的缺口是后端 Tempo，不是采集端。
      另外 eBPF 自动埋点有硬前提：内核要有 BTF（/sys/kernel/btf/vmlinux）、
      agent 要 privileged、语言要支持。你的 podinfo 是 Go，正好在支持列表里。

薄四  ⑥ 变更侧默认等于 Kyverno MutatingPolicy —— 这是把工具当成了能力
      变更侧的"能力"是：不合规的 Pod 被自动补齐后放行，而不是被拒。
      实现至少有两条路：
        a) K8s 原生 MutatingAdmissionPolicy（CEL，无 webhook，无外部依赖）
        b) Kyverno MutatingPolicy（1.20 上可能还要开 feature flag）
      你版本够新的话，a 更干净：少一个 webhook 就少一个故障面。
      Kyverno 留着做 validate + image verify 就够。
      → 装前探：kubectl api-resources | grep -i mutatingadmission
```

### 最后说它错的（一条，而且是它最自信的那条）

```
错  "5 个件全为纯软件，不需要加机器"

    CPU/RAM 这半句成立：5 个件加起来约 +5 核 / +6.5G，5×4C8G 的盘子放得下。
    存储这半句不成立：你的 Longhorn 已经 213G / 上限 208G，
    02 章 C3 自己写了"逼近上限"，06 章记了"副本重建因此失败过一次"。
    而 OTel 链路的 Tempo 必须有卷（估 10G × 3 副本 = 30G），集群里没有 30G 可放。

    → 结论不是"不用加机器"，是"必须先给每台 worker 补一块 100G 数据盘"
      （约 0.1 元/时/块）。这块盘一举三得：
      ① Tempo 有地方放 ② 副本重建不再失败 ③ 顺手把 Harbor 补上（16.4④ 就是卡在这）
```

## 18.4 它没看见的 7 个缺口（我按"漏了会怎样"排序）

```
缺口一  HPA 一次都没跑过                    ← 比 KEDA 更基础的缺口
        现状：metrics-server 装了，理由是"为 HPA 提供数据"，但 HPA 从未创建。
        后果：谈"事件驱动弹性"之前，连"CPU 超 70% 扩到 3 副本"都没验过。
        验一个数：压测下副本 2 → 4 → 压力撤掉 5 分钟后落回 2，且不抖（stabilizationWindow）。

缺口二  备份没有自动化恢复校验                ← "备份不算数，恢复才算数"
        现状：Velero restore 只做过一次手工（RTO 78s），etcd 快照恢复只做过一次。
        后果：三个月后你不知道那些备份还是不是好的。
        验一个数：每天 03:30 自动 restore 到 backup-verify 命名空间，
                  比对 MARKER 行数与 etcd 对象计数，连续 7 天全绿 + RTO 曲线。

缺口三  kubeadm upgrade 只有 SOP，没真跑       ← 一套没升过级的集群不算完备
        现状：08 章明写"升级 SOP（未实际执行）"。
        后果：v1.37.2 是你唯一验证过的状态，升级路径（含 addon 兼容、
              PDB 生效、etcd 滚动、证书重签）全是纸面。
        验一个数：1.37.2 → 1.37.x 或 1.38 升一个 minor，全程 kubectl 不断、0 Pod 丢失。

缺口四  渐进式交付（Argo Rollouts）            ← 08 章自己列在"未做"
        现状：ArgoCD 只会"全量同步"，发版 = 一起换。金丝雀/自动回滚没有。
        坑：Rollouts 原生只对接 Istio / NGINX / ALB / SMI，Gateway API 要靠
            argoproj-labs/gatewayAPI 插件。没网格时它只能按"副本比例"切，
            不能按"流量比例"切 —— 这一条正好和 ③ ambient/waypoint 绑在一起。
        验一个数：canary 5% → 50% → 100%，中间人为注入 5xx，指标越界自动 abort 回滚。

缺口五  供应链只有"验签"，没有"扫描"        ← 半条链
        现状：cosign 签名 + ImageValidatingPolicy 验签（未签名被拒）✓
              但没有 SBOM、没有 CVE 门禁、registry 无 trivy（Harbor 缺）。
        后果：签名只证明"是我推的"，不证明"这个镜像没有已知漏洞"。
        验一个数：一个带高危 CVE 的镜像即使签名正确也被拒（trivy-operator 出报告 +
                  Kyverno 校验 attestation 或报告）。

缺口六  多租户只有"网络隔离"，没有"资源隔离"
        现状：18 个命名空间，PSA + 默认拒绝 ✓，但 ResourceQuota / LimitRange /
              PriorityClass 一个都没有（全册搜不到）。
        后果："谁能占多少资源""谁被驱逐时先死"这两问答不了。
        验一个数：一个 ns 超配额被 API 拒；高优先级 Pod 抢占低优先级 Pod 成功。

缺口七  出口（egress）没有任何治理
        现状：只有 ingress 方向的默认拒绝。Pod 想出就能出。
        后果：云上最现实的风险面（数据外带、意外打到公网、出口 IP 不固定）。
        验一个数：DNS-aware 策略下，某 ns 只能解析白名单域名，其他 drop 且 Hubble 可见；
                  或 Egress Gateway 让该 ns 出口固定成某个 IP。

另有一个"不算缺口但要说清"的：
        Kubecost / Karpenter 这两条我同意它（和你 16.4⑨）的判断，别做 ——
        Kubecost 要云计费 API 权限；Karpenter 在 8 台固定机器上没有腾挪空间，
        收益全是理论值。成本这件事你用"加盘 + 容量巡检"就够，不必上工具。
```

## 18.5 换一个坐标系：同样 9 个，但换成"能力面"

它数的是**组件位**（装了没有）；该数的是**能力面**（闭环没有、有数没有）。
同样 9 个，换过来是这样（每面三行：现状 / 缺 / 验什么数）：

```
面1 数据面（可编程数据路径）
   现状  eBPF 接管 Service ✓，KUBE-SVC=0 ✓（这条你已经做到 90 分）
   缺    bpf.masquerade 可能没开（还在用 ip-masq-agent 的 iptables 路径）
         无 L7 策略、无 egress gateway、NodeLocal DNS 没装
   验    kubectl -n kube-system get cm cilium-config -o yaml | grep -i masq
         目标：masquerading=true + bpf.masquerade=true（此时才能关掉 ip-masq-agent）

面2 南北入口
   现状  Gateway API + EG + 自动证书 ✓，HTTP→HTTPS 301 ✓
   缺    重试/超时/限流这类 L7 策略（BackendTrafficPolicy / RateLimitPolicy）
   验   一条 1 秒超时策略生效：curl 用时被截断在 1s，后端收到 cancel

面3 东西向身份（加密）
   现状  只有 L3/L4 默认拒绝，跨节点明文
   缺    ambient（ztunnel）mTLS + L4 授权；要 L7 还要 waypoint
   验    两个无 sidecar 的 Pod 之间，ztunnel 侧能查到 mTLS 身份；
         节点抓包看不到 HTTP 明文（这一条最能证明"真加密了"）

面4 弹性
   现状  metrics-server 只有 top，HPA 从未创建
   缺    HPA（CPU + 外部指标）→ VPA（建议/RequestsOnly）→ 原地扩缩 → KEDA（事件驱动）
   验    副本 2→4→2 不抖；改 requests 后 RESTARTS 不变（原地扩缩生效）；
         KEDA 用 Prometheus scaler 把队列长度打到阈值，扩到 N（不加任何中间件）

面5 调度与设备
   现状  默认调度器 + PDB
   缺    PriorityClass + 抢占 / topologySpreadConstraints / DRA + 示例驱动 / Kueue
   验    高优先级 Pod 抢占成功；Pod 拿到 ResourceClaim 且被调度到"有设备"的节点

面6 准入与供应链
   现状  validate ✓ + 验签 ✓（这两条强）
   缺    变更侧（原生 MAP 或 Kyverno Mutate）/ SBOM / CVE 门禁 / 配额
   验    一个裸 Pod（无 resources、无 seccomp）被自动补齐后通过 PSA restricted；
         一个带高危 CVE 的镜像被拒

面7 遥测
   现状  metrics + logs + SLO + 三级告警 + 抑制静默（这套是全册最强的一段）
   缺    trace（Tempo）+ 尾部采样 + exemplar 把指标和 trace 串起来
   验    Grafana 里从一条慢请求的指标点进去，能看到它对应的那条 trace 与 span

面8 交付（含渐进发布）
   现状  ArgoCD + 自愈 + 手删 5 秒重建 ✓；6 场演练 ✓
   缺    Rollouts 金丝雀 + 指标自动回滚；升级演练；addon 升级策略（只用 EG 升过一次）
   验    canary 指标越界自动 abort，且 ArgoCD 状态回到上一个 revision

面9 存储与恢复（含容量）
   现状  Longhorn 三副本 + 外部 S3 + Velero + 快照 + 恢复验证（很深）
   缺    容量余量（已超）/ 恢复自动化 / 第二环境 DR
   验    加盘后：副本重建一次成功；自动 restore 连续 7 天绿
```

**这个坐标系的好处**：每一面都逼你回答"数是多少"。
它那个坐标系只逼你回答"装了没有"——装上 KEDA 但没触发过一次扩容，在它的框里也算"填好了"。

## 18.6 补装顺序（三批，按"能不能一次验完"排）

```
第一批 · 不动数据面，一个晚上能验完（都是闭环缺口，收益最高）
  1  HPA baseline            ← 先有"能扩"，再谈"事件驱动"
  2  VPA（建议模式 / RequestsOnly）
  3  原地扩缩                ← 与 2 配套：VPA 给值 → 原地改 → 不重启
  4  变更侧（原生 MAP 优先，Kyverno Mutate 备）
  5  Alloy eBPF → Collector → Tempo   ← 顺带把 16.4⑧ 那条"做不了"消掉
  6  Argo Rollouts（先按副本比例 canary，有了面3 再换流量比例）
  7  配额三件套（ResourceQuota / LimitRange / PriorityClass）
  ⚠ 三个弹性件会互相打架：同一个 workload 不要同时挂 CPU-HPA 和全量 VPA；
    VPA 一定设 controlledValues: RequestsOnly，否则它和 HPA 会互相追。

第二批 · 要动 CNI，挑一个维护窗口，一次做完（改 CNI 参数要滚动重启 146 个 Pod）
  8  ambient（ztunnel）+ 可选 waypoint
  9  MTU 重测（1422 这条基线会变，必须重跑大包边界）
  10 bpf.masquerade 切换（若面1 探到没开；和 8 一起验，别分两次重启）
  ⚠ GatewayClass 只能有一个主人：ambient 装完别顺手开 Cilium Gateway，
    否则它和 Envoy Gateway 抢同一批 HTTPRoute。

第三批 · 有盘之后（不加盘就不要开始这一批）
  11 每台 worker +100G → 先解决容量，再装东西
  12 KEDA（Prometheus scaler，零中间件）
  13 Harbor（带 trivy）+ 供应链闭环（SBOM/CVE 门禁）
  14 DRA 示例驱动 → 跑通单 Pod → 再上 Kueue
  15 备份恢复自动化 cron + RTO/RPO 曲线
  16 etcd 加密 key 轮换（aescbc 双 key 并存 → 新写入用新 key → 旧 key 保留可解）
  17 kubeadm upgrade 真跑一次

不做：Kubecost（云 API 权限）、Karpenter（8 台固定机器无腾挪空间）、
      Vault（本环境 listener 已证明不稳，Sealed Secrets + 轮换够练）
```

## 18.7 资源账（这是"能不能一次装上"的真门槛）

```
现有盘子
  5 worker × 4C8G = 20 核 / 40G；146 Pod 已跑
  大头已被占：Prom 2 副本（2×20G 卷）、AM 3 副本、Loki、Grafana 2、Cilium 8、
              Longhorn ~10、Kyverno、ArgoCD 6

新增估算（requests，按保守给）
  ztunnel 8 × 0.1C/128Mi      ≈ 0.8C / 1.0G
  waypoint 1 个               ≈ 0.1C / 0.2G
  KEDA operator + metrics     ≈ 0.3C / 0.3G
  VPA 三件套                  ≈ 0.3C / 0.4G
  OTel Collector 2 副本       ≈ 0.4C / 0.5G
  Tempo 单二进制              ≈ 0.5C / 1.0G
  Alloy eBPF 8 × 0.2C/256Mi   ≈ 1.6C / 2.0G
  Argo Rollouts               ≈ 0.2C / 0.2G
  Kueue（若上）                ≈ 0.2C / 0.2G
  合计                        ≈ +4.4C / +5.8G

判定
  CPU  20 → 24.4 核需求，加得下（但节点只剩碎片，大 Pod 会 Pending）
  RAM  40G 里已用的部分不明，加完预计只剩 1~2G 余量 —— 能跑，但一次滚动重启就会抖
  存储 加不下。213G/208G 已超，Tempo 的 30G 无处放
  → 加盘是前置条件，不是优化项。

开工前先量这三个数（不要信估算，量完再定）：
  kubectl describe node | grep -A6 "Allocated resources"   ← 每节点 requests 余量
  kubectl get pv | awk '{print $5}' | tail -n +2            ← Longhorn 实际占用
  kubectl -n longhorn-system get nodes.longhorn.io -o wide  ← 每节点可用容量
```
