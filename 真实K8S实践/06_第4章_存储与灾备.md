## 4.1 把数据盘变成 Longhorn 专用盘

### 在干什么

把 5 台 worker 的第二块盘（/dev/vdb）格式化、按 UUID 挂到 `/var/lib/longhorn`。

### 为什么现在做

不能拿系统盘做 Longhorn：副本写满系统盘 = 节点 NotReady。必须是独立盘，且要用 UUID 挂载（设备名会变）。

### 在哪台敲

5 台 worker。

### 敲什么

```bash
cat > /root/s4-mount-disk.sh <<'SCRIPT'
#!/bin/bash
set -euo pipefail
DEV=/dev/vdb
MNT=/var/lib/longhorn

if mountpoint -q "$MNT"; then echo "already mounted"; exit 0; fi

# 有文件系统就不动（防误删）
if ! blkid "$DEV" >/dev/null 2>&1; then
  mkfs.ext4 -F -L longhorn "$DEV"
fi

mkdir -p "$MNT"
UUID=$(blkid -s UUID -o value "$DEV")
grep -q "$UUID" /etc/fstab || echo "UUID=$UUID $MNT ext4 defaults,noatime 0 2" >> /etc/fstab
mount "$MNT"
echo "mounted=$(df -h $MNT | tail -1 | awk '{print $2" "$4" free"}') uuid=$UUID"
SCRIPT

for h in 172.23.163.101 172.23.163.105 172.23.163.104 172.23.163.102 172.23.163.103; do
  scp -q /root/s4-mount-disk.sh root@$h:/root/
  ssh root@$h "sed -i 's/\r$//' /root/s4-mount-disk.sh; bash /root/s4-mount-disk.sh"
done

# Longhorn 依赖
for h in 172.23.163.101 172.23.163.105 172.23.163.104 172.23.163.102 172.23.163.103; do
  ssh root@$h "apt-get -o DPkg::Lock::Timeout=180 install -y -qq open-iscsi nfs-common cryptsetup; \
               systemctl enable --now iscsid"
done
```

### 看到什么算过（本次真实回显）

```

wk-2 mounted=49G 47G free uuid=5e2ac7f3-a7bc-4a13-bba3-ad7b0b2339d3
wk-3 mounted=49G 47G free uuid=3d97e0d1-e3fb-425e-8970-ca37f5a6e103
wk-4 mounted=49G 47G free uuid=f1023739-eb11-4f34-bb93-86781db2c38d
wk-5 mounted=49G 47G free uuid=5e348ef5-4af9-4e10-b808-372091e865db
iscsid=active iscsiadm=ok（5 台一致）
```

## 4.2 装 Longhorn

### 敲什么

```bash

helm upgrade --install longhorn longhorn/longhorn --version 1.13.0 \
  -n longhorn-system --create-namespace \
  --set defaultSettings.defaultReplicaCount=3 \
  --set defaultSettings.defaultDataPath=/var/lib/longhorn \
  --set defaultSettings.storageOverProvisioningPercentage=100 \
  --set defaultSettings.storageMinimalAvailablePercentage=15 \
  --set persistence.defaultClass=true \
  --set ingress.enabled=false \
  --wait --timeout 12m

kubectl -n longhorn-system get nodes.longhorn.io \
  -o custom-columns=NODE:.metadata.name,READY:.status.conditions[0].status,SCHED:.spec.allowScheduling
```

### 参数判官卡

```

storageOverProvisioning=100  ★ 不开 200%：3 副本下超配 200% 等于实际可用只剩 1/6，
                              卷写满时才发现没空间，Longhorn 会 degraded 且无法重建
storageMinimalAvailable=15   低于 15% 不再往上调度，避免把盘写死
defaultClass=true            PVC 不写 storageClassName 时默认用它
```

## 4.3 容量账：先算再装（本章最重要的一张纸）

### 在干什么

在装监控、日志、ArgoCD 之前，先把"3 副本吃多少"算清楚。

### 本次真实数字

```
物理：5 × 49G = 245G
Longhorn 保守可用：约 208G（保留 15%）

卷清单（本次实际申请）
  Prometheus     20G × 2 = 40G
  Alertmanager    2G × 3 =  6G
  Loki           10G × 2 = 20G
  Gitea           5G × 1 =  5G
  demo PVC        2G × 1 =  2G
  合计                   73G

按 3 副本折算物理占用：73 × 3 ≈ 219G  >  208G 可用
```

### 结论与后果（已实测）

```
余量不到一个 20G 副本 → 删掉一个副本后，调度器找不到能放 20G 的节点
实测报错：ReplicaSchedulingFailure  disks are unavailable; insufficient storage
```

### 判官卡：这套盘到底能装什么

```
安全线：卷总量 × 3 ≤ 可用量的 80%
本次：208 × 0.8 ≈ 166G 物理 → 卷总量应 ≤ 55G

按 55G 倒推（这是这套 5×50G 的真实上限）
  Prometheus  20G × 1（单副本）或 10G × 2
  Alertmanager 2G × 3
  Loki         4G × 1
  Gitea        3G
  演练卷        5G
  ─ 合计约 40G，留 15G 给重建临时空间
```

## 4.4 备份目标：Longhorn 1.13 的 BackupTarget 是 CRD

### 在干什么

给 Longhorn 接一个集群外的 S3，让 volume 能备份出去。

### 为什么现在做

快照和备份不是一回事：节点全挂时快照一起消失，只有备份在集群外才救得回来。

### 判官卡：用什么当 S3

```
探针 1：阿里云 OSS
  用 AK 调 PUT /<bucket>
  本次结果：403 UserDisable —— 账号未开通 OSS 服务（不是权限问题，是服务没开）

探针 2：MinIO 社区版
  https://dl.min.io/server/minio/release/linux-amd64/minio → 410 Gone
  https://dl.min.io/aistor/.../minio → 200 但运行后 mc 报 "No license is installed"

探针 3：SeaweedFS
  GitHub release 单文件，无 license，S3 兼容
  → 本次选它：跑在 cp-1 宿主机（K8s 之外），S3 端口 9000
```

SeaweedFS 部署要点（跑在宿主，不进 K8s）：

```bash
# 二进制
curl -fsSL https://github.com/seaweedfs/seaweedfs/releases/latest/download/linux_amd64.tar.gz -o s.tgz
tar -xzf s.tgz && install -m755 weed /opt/seaweed/weed

# S3 身份
cat > /etc/seaweed/s3.json <<'EOF'
{
  "identities": [
    {"name":"admin","credentials":[{"accessKey":"<AK>","secretKey":"<SK>"}],
     "actions":["Admin","Read","Write","List","Tagging"]}
  ]
}
EOF

# systemd
cat > /etc/systemd/system/seaweedfs.service <<'EOF'
[Unit]
Description=SeaweedFS (S3-compatible store, out of cluster)
After=network-online.target
[Service]
ExecStart=/opt/seaweed/weed server -dir=/var/lib/seaweed -ip=172.23.163.99 \
  -master.port=9333 -volume.port=8080 -s3 -s3.port=9000 -s3.config=/etc/seaweed/s3.json
Restart=always
[Install]
WantedBy=multi-user.target
EOF
systemctl enable --now seaweedfs

# 建桶（mc 指向它）
mc alias set sw http://172.23.163.99:9000 <AK> <SK>
mc mb sw/longhorn-backup sw/velero-backup sw/loki-chunks sw/loki-ruler sw/loki-admin
```

### 接给 Longhorn（★ 1.13 的写法与老教程不同）

```bash
# 老教程：kubectl patch setting backup-target ...    ← 1.13 已经没有这个 setting 了
# 新写法：BackupTarget CRD，名字固定叫 default
kubectl -n longhorn-system get backuptargets.longhorn.io default -o yaml | head -20

kubectl -n longhorn-system create secret generic longhorn-backup-credentials \
  --from-literal=AWS_ACCESS_KEY_ID=<AK> \
  --from-literal=AWS_SECRET_ACCESS_KEY=<SK> \
  --from-literal=AWS_ENDPOINTS=http://172.23.163.99:9000

kubectl -n longhorn-system patch backuptargets.longhorn.io default --type merge -p \
 '{"spec":{"backupTargetURL":"s3://longhorn-backup@us-east-1/","credentialSecret":"longhorn-backup-credentials"}}'

kubectl -n longhorn-system get backuptargets.longhorn.io default \
  -o jsonpath='available={.status.available}{"\n"}'
```

### 看到什么算过

```
available=true（本次真实结果）
```

### 这条坑值得单独记

```
错误写法 s3://bucket@us-east-1@http://172.23.163.99:9000/
  → 报 invalid input region http:
  原因：URL 里只写 bucket@region，自定义 endpoint 放 secret 的 AWS_ENDPOINTS

正确写法 s3://longhorn-backup@us-east-1/  +  secret 里 AWS_ENDPOINTS=http://...:9000
```

## 4.6 演练：删掉命名空间，再从备份恢复

### 在干什么

真删一次，看数据能不能一字不差地回来，并记下 RTO。

### 敲什么

```bash
# 0) 先在 PV 里写一个"不会被重启覆盖"的标记（这是验证精度的关键）
MARKER="MARKER-$(openssl rand -hex 6)"
kubectl -n apps exec pvc-writer -- sh -c "echo $MARKER > /data/keep.txt; sync"

# 1) 备份（含 PV 数据）
velero backup create apps-keeper --include-namespaces apps --default-volumes-to-fs-backup --wait
velero backup describe apps-keeper --details | grep -E 'Phase|Items backed up'

# 2) 破坏
kubectl delete ns apps --wait=true --timeout=300s

# 3) 恢复
velero restore create keeper-restore --from-backup apps-keeper --wait

# 4) 验收数据
for i in $(seq 1 20); do
  out=$(kubectl -n apps exec pvc-writer -- cat /data/keep.txt 2>/dev/null)
  [ -n "$out" ] && break; sleep 6
done
echo "恢复出来的标记: $out"
[ "$out" = "$MARKER" ] && echo PASS || echo FAIL
```

### 看到什么算过（本次真实回显）

```
Backup completed with status: Completed
Items backed up: 63     Errors: 0

namespace "apps" deleted
Restore completed with status: Completed（22 秒）
恢复出来的标记: MARKER-bcca2aaa36c7
RESULT=PASS 数据完全一致
整轮耗时 78s（含删命名空间 51s + 恢复 22s）
```

### 判官卡：为什么必须写"不会被覆盖"的标记

```
本次第一版测试用的是应用自带的 proof.txt，容器启动命令会重写它，
所以恢复后看到的是新时间戳 —— 看起来像"恢复失败"，其实是测试方法错。
换成外部写入、启动命令不碰的 keep.txt，才证明"数据真的从备份里回来了"。
```

## 4.7 副本重建演练（先失败、腾空间后通过）

### 想干什么

删掉一个副本，看 Longhorn 能不能自动补齐到 3 个并回到 healthy。

### 本次真实结果

```
kubectl -n longhorn-system delete replicas.longhorn.io/<某个副本>
→ 卷状态：3 个副本在册，robustness 持续 degraded
→ 卷 condition：Scheduled=False
   ReplicaSchedulingFailure  disks are unavailable; insufficient storage
→ 等待 5 分钟以上仍未恢复
```

### 根因

```
容量不足（4.3 的账）：73G 卷 × 3 副本 ≈ 219G，可用约 208G。
删掉一个副本后，重建需要在一个节点上找到该卷那么大的连续空间，
而每个节点剩余都不足 → 调度失败。
```

### 三种解法（按代价排序）

```
A 砍卷（最快，改配置即可）
   Loki 降成 1 副本 4G；Prometheus 若仍要 2 副本就用 10G（7 天保留要相应缩短）
   预期：腾出 ~60G 物理，重建可立刻完成
   代价：日志层失去 HA

B 加盘（最稳，最贴生产）
   5 台 worker 各加一块 50G 云盘，挂到同一 /var/lib/longhorn
   容量翻倍，副本重建与后续演练都有余量
   代价：约 0.05 元/时/块

C 降副本（最省，但违背生产原则）
   Prometheus 改 1 副本
   不推荐：第 6 章的"关键组件 2 副本"验收会不成立
```

### 按解法 A 修复后重跑（真实结果）

```bash
# 1) 把 Loki 从 2 副本 10G 改成 1 副本 4G，并删掉它的两个旧 PVC（释放约 60G 物理）
sed -i 's/  replicas: 2/  replicas: 1/; s/    size: 10Gi/    size: 4Gi/' loki-values.yaml
helm uninstall loki -n logging
kubectl -n logging delete pvc --all
helm install loki grafana/loki -n logging -f loki-values.yaml

# 2) 观察：原先 degraded 的两个卷（Gitea 5G、旧 Loki 2G）自己变 healthy
kubectl -n longhorn-system get volumes.longhorn.io \
  -o custom-columns=NAME:.metadata.name,ROBUST:.status.robustness

# 3) 再删一个副本，看是否自动补齐
kubectl -n longhorn-system delete replicas.longhorn.io/<该卷的某个副本>
# 持续观察副本数与 robustness
```

```
本次真实结果
腾空间前：2 个卷 degraded，报 ReplicaSchedulingFailure insufficient storage
腾空间后：9 个卷里 8 个 healthy，新 Loki 卷短暂 degraded 后也转 healthy
再删副本：gitea 卷副本数回到 3，robustness=healthy
最终：8 个卷全部 healthy，无 degraded
```

### 这条演练真正教会的事

```
"副本重建失败" 十次有九次不是 Longhorn 坏了，是空间不够。
先看卷 condition 里的 reason：ReplicaSchedulingFailure = 调度问题 = 算容量；
真要怀疑组件，再看 instance-manager 与 iscsid 状态。
```

## 核心大坑（4 条，每条三行封顶）

```
现象：patch setting backup-target 报 NotFound
根因：Longhorn 1.13 把备份目标从 Setting 改成了 BackupTarget CRD（名字固定 default）
防：改 CRD 的 spec.backupTargetURL，凭据走 secret

现象：备份目标 URL 带 endpoint 时报 invalid input region http:
根因：URL 只接受 s3://bucket@region/，自定义 endpoint 要放 secret 的 AWS_ENDPOINTS
防：URL 与 endpoint 分开写

现象：恢复后数据"变了"，看起来像恢复失败
根因：测试用的文件被容器启动命令重写
防：用外部写入、启动命令不碰的标记文件验证

现象：删副本后永远 degraded，报 insufficient storage
根因：3 副本卷把盘吃满，没有单节点空间接新副本
防：先按 4.3 算容量，卷总量 × 3 ≤ 可用量 80%
```
