## 14.1 三条链路的定位（别混）

```
指标  Prometheus  ←  已做（第 5 章）      看"资源与组件健康"
日志  Loki        ←  已做（第 5 章+Alloy）看"发生了什么"
黑盒  本章         ←  补这一层            看"用户到底能不能用"

为什么必须有黑盒
└─ 内部指标全绿 ≠ 用户可用：
   Pod Running、Service 有 Endpoint、CPU 正常 —— 但网关证书过期 / DNS 解析错 / LB 端口不通，
   用户侧已经 100% 失败，而内部指标一个都不报。
   黑盒探针是唯一站在"用户那一侧"的观测。
```

## 14.2 第一步：让集群内能解析内部域名

探针要访问 `https://demo.apps.k8s.local:32691/`，而集群内没有这个域名的解析。
两种做法，本章选第一种：

```
A 改 CoreDNS 加 hosts（本章做法）—— 生产里内网域名通常也这么做，或交给内网 DNS
B blackbox 里写死 Host 头 —— 只能解决"HTTP Host"，解决不了 TLS 的 SNI 与证书域名校验
```

CoreDNS 的 Corefile 加一段（位置在 `kubernetes` 块之后、`forward` 之前）：

```
    hosts {
       172.23.163.101 demo.apps.k8s.local
       172.23.163.106 dex.k8s.local gitea.k8s.local s3.k8s.local
       fallthrough
    }
```

`fallthrough` 必须有，否则未命中的域名会直接返回 NXDOMAIN，集群里所有外部域名解析全挂。

应用与验证：

```bash
kubectl -n kube-system get cm coredns -o yaml > /root/coredns-backup.yaml   # 先备份
kubectl apply -f s21-coredns-hosts.yaml
kubectl -n kube-system rollout restart deploy coredns
kubectl -n kube-system rollout status deploy coredns --timeout=180s

kubectl run dnsutils --image=nicolaka/netshoot:v0.13 --restart=Never --command -- sleep 300
for d in demo.apps.k8s.local dex.k8s.local gitea.k8s.local s3.k8s.local; do
  printf '%-24s ' "$d"; kubectl exec dnsutils -- getent hosts "$d" | head -1
done
# demo.apps.k8s.local      172.23.163.101
# dex.k8s.local            172.23.163.106
# gitea.k8s.local          172.23.163.106
# s3.k8s.local             172.23.163.106
```

## 14.3 第二步：blackbox-exporter（2 副本 + 三个 CA 模块）

难点不是装 exporter，是**证书校验要用对 CA**。这套环境里同时存在三套 CA：

```
① 集群内部 CA      CN=k8s-prod-internal-ca   签发入口证书（demo.apps.k8s.local）
② 集群自身 CA      /etc/kubernetes/pki/ca.crt 签发 apiserver 证书
③ Dex 自签 CA      infra-01 上 openssl 自建   签发 dex.k8s.local

用错 CA 的表现：probe_success=0，但 curl -k 是通的 → 会误判成"服务挂了"
```

把三个 CA 放进一个 Secret，挂到 exporter 里：

```bash
kubectl -n cert-manager get secret internal-ca-keypair -o jsonpath='{.data.tls\.crt}' | base64 -d > /tmp/internal-ca.crt
cp /etc/kubernetes/pki/ca.crt /tmp/k8s-ca.crt
# dex-ca.crt 从 infra-01 取：ssh root@172.23.163.106 'cat /etc/dex/tls/ca.crt'

kubectl -n monitoring create secret generic blackbox-probe-ca \
  --from-file=internal-ca.crt=/tmp/internal-ca.crt \
  --from-file=k8s-ca.crt=/tmp/k8s-ca.crt \
  --from-file=dex-ca.crt=/tmp/dex-ca.crt \
  --dry-run=client -o yaml | kubectl apply -f -
```

Helm values（关键片段，完整见 `s22-blackbox-values.yaml`）：

```yaml
replicas: 2
serviceMonitor:
  enabled: true
  labels: {release: kps}          # 必须带 release=kps，否则 Prometheus 不抓它自己的指标

config:
  modules:
    http_2xx:            {prober: http, timeout: 5s, http: {valid_status_codes: [200,301,302]}}
    http_2xx_allow403:   {prober: http, timeout: 5s, http: {valid_status_codes: [200,403]}}   # S3 匿名访问就是 403
    https_internal_ca:   {prober: http, timeout: 8s, http: {tls_config: {ca_file: /etc/blackbox-ca/internal-ca.crt}}}
    https_k8s_ca:        {prober: http, timeout: 5s, http: {tls_config: {ca_file: /etc/blackbox-ca/k8s-ca.crt}}}
    https_dex_ca:        {prober: http, timeout: 8s, http: {tls_config: {ca_file: /etc/blackbox-ca/dex-ca.crt}}}

extraSecretMounts:
  - {name: blackbox-ca, secretName: blackbox-probe-ca, mountPath: /etc/blackbox-ca, readOnly: true}
```

安装：

```bash
helm upgrade --install blackbox prometheus-community/prometheus-blackbox-exporter \
  --version 11.21.3 -n monitoring -f s22-blackbox-values.yaml --wait --timeout 6m
# 2/2 Running
```

## 14.5 第四步：etcd metrics（一个必须改的默认值）

kubeadm 生成的 etcd 清单里是 `--listen-metrics-urls=http://127.0.0.1:2381`，
Prometheus 从节点 IP 抓，于是三个 target 全 DOWN：

```
down | kube-etcd | Get "http://172.23.163.99:2381/metrics": connection refused
```

改法（幂等脚本 `s25-etcd-metrics.sh`）：

```bash
sed -i 's#--listen-metrics-urls=http://127.0.0.1:2381#--listen-metrics-urls=http://0.0.0.0:2381#' \
  /etc/kubernetes/manifests/etcd.yaml
# 备份文件要放 /root，绝不能留在 /etc/kubernetes/manifests/ （见 14.9 的坑）
touch /etc/kubernetes/manifests/etcd.yaml
```

## 14.6 第五步：规则（15 条，分三组）

```yaml
groups:
- name: blackbox.probe
  rules:
  - alert: ProbeFailed                 # P1
    expr: probe_success == 0
    for: 2m
    labels: {severity: critical, tier: edge}
  - alert: ProbeFailedShort            # P2（抖动预警，2 分钟后自动升级成 P1）
    expr: probe_success == 0
    for: 30s
    labels: {severity: warning}
  - alert: ProbeSlow                   # P2
    expr: probe_duration_seconds > 3
    for: 5m
  - alert: TLSCertExpiringSoon         # P2
    expr: (probe_ssl_earliest_cert_expiry - time()) / 86400 < 21
  - alert: TLSCertExpiringCritical     # P1
    expr: (probe_ssl_earliest_cert_expiry - time()) / 86400 < 7

- name: blackbox.slo
  rules:
  - record: slo:gateway_availability:ratio_rate1h
    expr: avg_over_time(probe_success{job="gateway-https"}[1h])
  - alert: GatewaySLOBudgetBurnFast    # P1，1h 14.4x + 5m 14.4x 同时命中
    expr: |
      (1 - slo:gateway_availability:ratio_rate1h) > (14.4 * 0.001)
      and
      (1 - slo:gateway_availability:ratio_rate5m) > (14.4 * 0.001)
    for: 5m
  - alert: GatewaySLOBudgetBurnSlow    # P2，6h 与 1h 同时命中
    expr: |
      (1 - slo:gateway_availability:ratio_rate6h) > (6 * 0.001)
      and (1 - slo:gateway_availability:ratio_rate1h) > (6 * 0.001)
    for: 30m

- name: blackbox.capacity
  rules:
  - alert: LonghornVolumeDegraded      # P1
    expr: longhorn_volume_robustness{robustness="degraded"} > 0
  - alert: LonghornDiskSpaceLow        # P2
    expr: longhorn_node_storage_available_bytes / longhorn_node_storage_capacity_bytes < 0.15
```

为什么 SLO 用"双窗口多燃烧率"而不是"可用性 < 99.9% 就报"：

```
单窗口的毛病
└─ 3 分钟抖动就报 P1 → 天天狼来了 → 最后没人看告警
双窗口
├─ 1h 烧 14.4x（一个月预算 2 小时烧完）才叫 P1 → 真事故
└─ 6h 烧 6x 才叫 P2 → 慢性劣化（如证书即将过期、某副本长期缺）
```

## 14.7 第六步：三级告警出口（自建接收端，生产换 URL 即可）

### 接收端（跑在集群外 infra-01，模拟企微/钉钉网关）

```python
# 端点：POST /p1 /p2 /p3 各写一个日志；GET /dump 汇总；GET /healthz 存活
def do_POST(self):
    level = self.path.strip("/").split("/")[0]     # p1 / p2 / p3
    alerts = json.loads(self.rfile.read(n)).get("alerts", [])
    with open(f"/data/alerts/{level}.log", "a") as f:
        f.write(raw.decode() + "\n")
    print(f"[{level}] received {len(alerts)} alert(s)", flush=True)
```

部署（docker compose 追加，端口 8088）：

```yaml
  alert-receiver:
    image: docker.io/library/python:3.12-alpine
    command: ["python", "/app/receiver.py"]
    ports: ["8088:8088"]
    volumes:
      - "/opt/stack/receiver.py:/app/receiver.py:ro"
      - "/data/alerts:/data/alerts"
    restart: always
    healthcheck:
      test: ["CMD","python","-c","import urllib.request;urllib.request.urlopen('http://127.0.0.1:8088/healthz')"]
```

### Alertmanager 三级路由

关键点：**Alertmanager CR 的字段不是 `spec.config`，是 `spec.configSecret`**
（写 `spec.config` 会得到 `Warning: unknown field "spec.config"`，配置根本没进去）。

```bash
kubectl -n monitoring create secret generic alertmanager-custom-config \
  --from-file=alertmanager.yaml=/tmp/alertmanager.yaml
kubectl -n monitoring patch alertmanager kps-kube-prometheus-stack-alertmanager \
  --type merge -p '{"spec":{"configSecret":"alertmanager-custom-config"}}'
```

配置本体：

```yaml
route:
  receiver: p3-info
  group_by: ['alertname', 'namespace', 'target_name']
  routes:
    - matchers: ['alertname = "Watchdog"']
      receiver: "null"            # 自带的永燃告警，别让它污染 P3 出口
    - matchers: ['severity = "critical"']
      receiver: p1-critical
      group_wait: 5s
      repeat_interval: 1h
    - matchers: ['severity = "warning"']
      receiver: p2-warning
      group_wait: 30s
      repeat_interval: 4h
    - matchers: ['severity = "info"']
      receiver: p3-info
      group_wait: 2m
      repeat_interval: 24h
inhibit_rules:
  - source_matchers: ['severity = "critical"']
    target_matchers: ['severity =~ "warning|info"']
    equal: ['target_name', 'namespace']     # 同名目标已 P1，就别再喊 P2/P3
receivers:
  - name: "null"
  - name: p1-critical
    webhook_configs: [{url: http://172.23.163.106:8088/p1, send_resolved: true}]
  - name: p2-warning
    webhook_configs: [{url: http://172.23.163.106:8088/p2, send_resolved: true}]
  - name: p3-info
    webhook_configs: [{url: http://172.23.163.106:8088/p3, send_resolved: true}]
```

### 三场实测（这才是证据）

```
【分级投递】注入三条不同 severity 的告警
  p1.log: alertname=E2E-P1-Test severity=critical status=firing receiver=p1-critical
  p2.log: alertname=E2E-P2-Test severity=warning  status=firing receiver=p2-warning
  p3.log: alertname=E2E-P3-Test severity=info     status=firing receiver=p3-info

【抑制】同一 target_name 同时 P1 + P2
  p1: count=1 names=['SUPPRESS-P1']
  p2: count=0 names=[]          ← 被抑制，正确

【静默】给 target_name=silence-test 建 2 小时静默，再注入 critical
  静默 ID: 9319dc3c-2301-48cb-b8cf-9933798c36d3
  结论：SILENCE-P1 出现在 p1 = False   ← 静默生效
```

## 14.9 部署时必须注意的五条

```
① Probe 的 label 必须是 release=kps
   否则 Prometheus 的 probeSelector 匹配不到，Probe 建了但永远没数据

② 三套 CA 不能混用
   gateway 用 cert-manager 内部 CA、apiserver 用集群 CA、Dex 用 infra 自签 CA
   混用表现为 probe_success=0 但 curl -k 正常

③ staticPodPath 里不能留备份文件
   把 etcd.yaml 备份成 etcd.yaml.bak-metrics 留在 /etc/kubernetes/manifests/ 里，
   kubelet 会把它当成第二个 static pod 清单解析 → 改了新清单也不生效
   备份必须放 /root

④ Alertmanager CR 的字段是 spec.configSecret，不是 spec.config
   写错只给一句 Warning，配置静默不生效（很容易以为"已经改了"）

⑤ group_wait 要按级别差异化
   P3 的 group_wait 2 分钟是为了合并；如果全用 5 秒，P3 会把出口刷爆
```
