## 12.4 迁移二：OIDC 身份（Dex + apiserver）

### 为什么 Dex 要用 HTTPS

kube-apiserver 的 `--oidc-issuer-url` 只接受 https，且必须与 token 的 `iss` 完全一致。
所以给 Dex 签一张自签证书（SAN 含 DNS dex.k8s.local 与 IP 172.23.163.106），
apiserver 用 `--oidc-ca-file` 信任它。

### apiserver 的 7 个参数

```
--oidc-issuer-url=https://172.23.163.106:5556/dex
--oidc-client-id=kubernetes
--oidc-username-claim=email
--oidc-username-prefix=oidc:
--oidc-groups-claim=groups
--oidc-groups-prefix=oidc:
--oidc-ca-file=/etc/kubernetes/pki/oidc-ca.crt
```

### 三个必踩的坑（都真实发生过）

```
① YAML 吃冒号
   - --oidc-groups-prefix=oidc:     ← YAML 解析成 {键: null}，kubelet 报 "cannot unmarshal object"
   必须写成 - "--oidc-groups-prefix=oidc:"

② kubelet 不收敛
   清单改对了，但静态 Pod 不重建（日志里 "Creating a mirror pod ... already exists"）。
   受控做法：systemctl stop kubelet → crictl rm -f <apiserver容器> → start kubelet
   （一台一台来，三台控制面 quorum 不受影响）

③ scope 少写 email
   --oidc-username-claim=email 时，token 里必须有 email claim；
   请求 token 要用 scope="openid email"，只写 openid 会导致认证失败（本次先中招）
```

### 拿 token 与验证

```bash
TOK=$(curl -s -k --cacert /etc/kubernetes/pki/oidc-ca.crt -X POST \
  https://172.23.163.106:5556/dex/token \
  -d grant_type=password -d username=viewer@k8s.local -d password='Viewer@K8s2026' \
  -d client_id=kubernetes -d client_secret='<secret>' -d scope="openid email" \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["id_token"])')

# 注意：不能带 kubeconfig 里的客户端证书，否则证书认证优先，你永远看到 kubernetes-admin
KUBECONFIG=/dev/null kubectl --server=https://172.23.163.97:16443 \
  --certificate-authority=/etc/kubernetes/pki/ca.crt --token="$TOK" auth whoami
```

实测结果：

```
Username = oidc:viewer@k8s.local
经 VIP 连续 6 次（轮询三台 apiserver）→ 6/6 身份一致

viewer：list pods=yes  delete pods=no  create deploy=no  list nodes=yes
admin ：delete nodes=yes  create pods=yes
真用 viewer token 念 API → 正常列出 podinfo 的两个 Pod
```

### 组级 RBAC 的现状（诚实说明）

```
Dex 的 password grant 返回的 id_token 里没有 groups claim（本地密码连接器不注入），
所以按组绑定（oidc:platform-viewers）不成立。
本次改为按用户绑定（--user="oidc:viewer@k8s.local"），认证与授权链路完整验证。
要按组：走授权码流程（浏览器登录）或接 LDAP/上游 OIDC connector，届时 groups 会进 token。
```

## 12.5 迁移三：供应链验签（cosign + Gitea registry + Kyverno）

```bash
# 1) infra 上允许 HTTP registry
cat > /etc/docker/daemon.json <<EOF
{ "insecure-registries": ["172.23.163.106:3000"] }
EOF
systemctl restart docker

# 2) 造一个单架构镜像并推（多架构清单 Gitea registry 接不住，本次踩过）
docker build -t 172.23.163.106:3000/gitea_admin/signed-demo:1.0.0 .
docker push 172.23.163.106:3000/gitea_admin/signed-demo:1.0.0

# 3) 生成密钥 → 签名 → 验签
cosign generate-key-pair
COSIGN_PASSWORD=$(cat cosign.pass) cosign sign --yes --key cosign.key <image>
cosign verify --key cosign.pub --insecure-ignore-tlog <image>
```

策略（Kyverno 1.20 用 ImageValidatingPolicy，且必须用单标识符的 attestor 名）：

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata: {name: require-internal-signature}
spec:
  validationActions: [Deny]
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["pods"]
  matchConditions:
    - name: only-kyv-test
      expression: "object.metadata.?namespace.orValue('') == 'kyv-test'"
  matchImageReferences:
    - glob: "172.23.163.106:3000/**"
  attestors:
    - name: internalca            # ★ 不能带连字符，CEL 会解析成减法
      cosign:
        key:
          data: |
            -----BEGIN PUBLIC KEY-----
            ...
  validations:
    - expression: >-
        images.containers.map(image, verifyImageSignatures(image, [attestors.internalca])).all(e, e > 0)
      message: "镜像必须由内部签名密钥签名"
```

还要给 Kyverno 开一个开关，否则它不认 HTTP registry：

```bash
kubectl -n kyverno patch deploy kyverno-admission-controller --patch-file /tmp/patch.json
# 追加 --allowInsecureRegistry=true
```

实测对照：

```
A) 已签名 172.23.163.106:3000/gitea_admin/signed-demo:1.0.0  → 放行（服务端 dry-run 通过）
B) 未签名 .../unsigned-demo:1.0.0 → 拒绝：
   Policy require-internal-signature failed: ... attestor "internalca":
   failed to verify cosign signatures: no signatures found
```

## 12.6 Vault 为什么没成（如实记录）

```
现象：容器起来后 listener 反复报 "bind: address already in use"，
      换端口、换 host 网络、换监听地址（0.0.0.0 / 私网 IP）都无效；
      但同一镜像 dev 模式（-dev-listen-address）能正常监听。
排查：宿主机可正常 bind 该端口；ss 看不到占用；配置去 CRLF 后仍失败；
      server 端日志里先出现 "Error parsing listener configuration." 再报 bind 失败。
结论：本环境下 Vault 正式模式的 listener 起不来，不再投入时间。
替代：Sealed Secrets（加密后的 Secret 可进 Git），列入下一批。
```
