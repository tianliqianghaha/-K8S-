## 4.1 控制面入口：HAVIP

### 在干什么

在 VPC 里申请一个高可用虚拟 IP，绑到 3 台控制面，让它在主节点故障时能漂到备节点。

### 为什么现在做

探针二已判定自建 ARP VIP 在阿里云不可用（详见 03 章 3.6）。HAVIP 是云上唯一能让 keepalived 工作的入口形态，而 kubeadm 的 `controlPlaneEndpoint` 必须在 init 之前定下来。

### 在哪台敲

运维机（调 API）或控制台。本次用 OpenAPI。

### 敲什么

```bash
# 1) 先看有没有现成的（别重复建）
aliyun vpc DescribeHaVips --RegionId cn-hongkong

# 2) 没有就建（免费；指定与节点同一交换机）
aliyun vpc CreateHaVip --RegionId cn-hongkong \
  --VSwitchId vsw-j6c11dksdhw9isjz5eahg --Name k8s-api-vip

# 3) 绑到三台控制面（要一台一台绑，中间等状态回到 InUse）
for iid in i-j6cftz561iu93ytdbcfd i-j6cftz561iu93ytdbcfe i-j6cftz561iu93ytdbcff; do
  aliyun vpc AssociateHaVip --HaVipId havip-j6crlqrs65eu0p9ulankm --InstanceId $iid
  sleep 5
done

# 4) 确认
aliyun vpc DescribeHaVips --HaVipId havip-j6crlqrs65eu0p9ulankm
```

### 看到什么算过

```
Status = InUse
IpAddress = 172.23.163.97
AssociatedInstances 有 3 个实例 ID
```

### 判官卡：HAVIP 到底能不能漂

```
探针（2 分钟）
  在 cp-1 执行：ip addr add 172.23.163.97/32 dev eth0
  在 cp-2 执行：ping -c 3 172.23.163.97  以及  timeout 5 bash -c 'cat </dev/null >/dev/tcp/172.23.163.97/22'

本次真实结果
  cp-2 ping：3 packets transmitted, 1 received（首包丢是 ARP 学习，正常）
  TCP 22：OK
  8 台一起测：全部 0% 丢包（第二次测已预热）
  撤掉地址后立刻 100% 丢包 → 说明这个地址确实是"谁配谁响应"

判据
  能 ping 通且 TCP 能连 → 可以上 keepalived（本次结论）
  首包丢但后续通      → 也正常，别被第一包骗了
```

## 4.2 haproxy：16443 → 三台 6443

### 在干什么

在 3 台控制面各起一个 haproxy，把 VIP:16443 的流量轮询转发到三台 apiserver 的 6443。

### 为什么是 16443 不是 6443

```
apiserver 自己占 6443。haproxy 若也监听 6443，会与 apiserver 抢端口，
现象是 init 卡在 wait-control-plane 或者 apiserver 起不来。
用 16443 做"前端端口"，后端各自 6443，互不冲突。
```

### 在哪台敲

3 台控制面。

### 敲什么

```bash
apt-get -o DPkg::Lock::Timeout=180 install -y -qq haproxy keepalived

cat > /etc/haproxy/haproxy.cfg <<'EOF'
global
    log /dev/log local0
    maxconn 20000
    daemon
    stats socket /run/haproxy/admin.sock mode 660 level admin
    stats timeout 30s

defaults
    mode tcp
    log global
    option tcplog
    timeout connect 5s
    timeout client 1h
    timeout server 1h
    retries 3

frontend kube-apiserver
    bind *:16443
    mode tcp
    default_backend kube_apiserver_back        # ★ 注意：backend 名字不能和 frontend 一样

backend kube_apiserver_back
    mode tcp
    balance roundrobin
    option tcp-check
    server cp-1 172.23.163.99:6443  check inter 2s fall 3 rise 2
    server cp-2 172.23.163.98:6443  check inter 2s fall 3 rise 2
    server cp-3 172.23.163.100:6443 check inter 2s fall 3 rise 2

listen stats
    bind 127.0.0.1:8404
    mode http
    stats enable
    stats uri /stats
EOF

haproxy -c -f /etc/haproxy/haproxy.cfg
systemctl enable --now haproxy
```

### 看到什么算过

```
haproxy -c → Configuration file is valid（本次还要注意：3.2 版本对 frontend/backend 同名会警告，
             3.3 起直接不支持，所以上面把 backend 命名成 kube_apiserver_back）
ss -lnt | grep 16443 → 有监听
```

## 4.3 keepalived：让 VIP 真的会漂

### 在干什么

3 台各起 keepalived，用单播 VRRP 选主，把 HAVIP 挂在主节点上；并用 vrrp_script 探本机 16443。

### 为什么必须有 vrrp_script

```
只 track 网卡 / 整机心跳时，故障形态漏一半：
  机器活着、网卡活着，但 haproxy 挂了（OOM / 配置错 / 进程崩）
  → VIP 不漂，所有 kubectl 全失败，而 keepalived 显示一切正常

加了探 16443 的脚本后，故障范围从"整机宕机"扩展到"服务级故障"。
```

### 在哪台敲

3 台控制面，配置只有 priority / src_ip / peers 不同。

### 敲什么

```bash
# 健康检查脚本（探本机 haproxy 的 16443）
cat > /etc/keepalived/chk_haproxy.sh <<'EOF'
#!/bin/bash
timeout 2 bash -c 'exec 3<>/dev/tcp/127.0.0.1/16443' 2>/dev/null
EOF
chmod +x /etc/keepalived/chk_haproxy.sh

# keepalived 主配置（cp-1 版；cp-2/cp-3 改 router_id / priority / unicast_src_ip / peers）
cat > /etc/keepalived/keepalived.conf <<'EOF'
global_defs {
    router_id cp-1
    script_user root
    enable_script_security
    vrrp_garp_interval 0.001
    vrrp_gna_interval 0.0001
}

vrrp_script chk_haproxy {
    script "/etc/keepalived/chk_haproxy.sh"
    interval 2
    weight -30
    fall 3
    rise 2
}

vrrp_instance VI_APISERVER {
    state BACKUP
    interface eth0
    virtual_router_id 51
    priority 150                     # cp-2=140，cp-3=130
    advert_int 1
    unicast_src_ip 172.23.163.99     # 本机 IP
    unicast_peer {
        172.23.163.98
        172.23.163.100
    }
    authentication {
        auth_type PASS
        auth_pass K8sHaVip2026
    }
    virtual_ipaddress {
        172.23.163.97/32 dev eth0
    }
    track_script {
        chk_haproxy
    }
}
EOF

systemctl enable --now keepalived
```

### 看到什么算过（本次真实回显）

```
cp-1 持有 VIP（ip -4 -o addr show eth0 | grep -c 172.23.163.97 → 1）
cp-2/cp-3 → 0
8 台 ping VIP 全通，VIP:16443 全 OPEN
```

## 4.4 etcd 静态加密与审计

### 在干什么

给 apiserver 配两个"开关"：Secret 写入 etcd 前加密；所有写操作留审计日志。

### 为什么现在做

这两个都必须在 **kubeadm init 之前**写进配置，事后补要重建控制面。

### 判官卡：用云 KMS 还是本地 aescbc

```
探针
  aliyun kms DescribeKeys --RegionId cn-hongkong

本次判据
  KMS 未开通（返回未开通/无权限）→ 用 aescbc + 本地 32 字节 key
  aescbc 的安全边界：key 在控制面磁盘上，能读到 key 就能解密；
  但它解决的是"etcd 备份文件泄露 = 拿到所有密码"这个最现实的风险，练到的动作与 KMS 完全一样
  将来换 KMS 只需改 provider 段，不用重建集群
```

### 在哪台敲

3 台控制面（key 必须完全一致）。

### 敲什么

```bash
# 生成 key（只在一台生成，然后拷到另外两台）
KEY=$(head -c 32 /dev/urandom | base64)
mkdir -p /etc/kubernetes/enc /etc/kubernetes/audit /var/log/kubernetes

cat > /etc/kubernetes/enc/encryption-config.yaml <<EOF
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - aescbc:
          keys:
            - name: key1
              secret: ${KEY}
      - identity: {}
EOF
chmod 700 /etc/kubernetes/enc /etc/kubernetes/audit
chmod 600 /etc/kubernetes/enc/encryption-config.yaml

# 审计策略
cat > /etc/kubernetes/audit/policy.yaml <<'EOF'
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages: ["RequestReceived"]
rules:
  - level: None
    nonResourceURLs: ["/healthz*", "/livez*", "/readyz*", "/version"]
  - level: None
    users: ["system:kube-proxy"]
    verbs: ["watch"]
    resources: [{group: "", resources: ["endpoints", "services", "services/status"]}]
  - level: RequestResponse
    verbs: ["create", "update", "patch", "delete", "deletecollection"]
    resources:
      - group: ""
        resources: ["secrets", "configmaps", "serviceaccounts", "pods/exec", "pods/portforward"]
      - group: "rbac.authorization.k8s.io"
        resources: ["roles", "rolebindings", "clusterroles", "clusterrolebindings"]
  - level: Metadata
    verbs: ["create", "update", "patch", "delete", "deletecollection"]
  - level: Metadata
EOF
```

### 看到什么算过

后面 4.6 的验证里有一条专门测它：

```bash

kubectl -n kube-system exec etcd-cp-1 -- etcdctl get /registry/secrets/demo-crypto/probe \
  --cacert ... --cert ... --key ... --print-value-only > /tmp/raw.bin
xxd /tmp/raw.bin | head -3
grep -c SuperSecret123 /tmp/raw.bin

本次真实结果
00000000: 6b38 733a 656e 633a 6165 7363 6263 3a76  k8s:enc:aescbc:v
00000010: 313a 6b65 7931 3ae0 c7f0 79a7 cf06 c56a  1:key1:...
grep 结果：0（明文不存在）
kubectl 拿到的是明文 SuperSecret123，说明加密对使用方透明
```

## 4.7 加两台控制面 + 五台 worker

### 在干什么

把 cp-2/cp-3 加成控制面（带 etcd），把 5 台 worker 加进来。

### 在哪里敲

运维机发起，命令在各目标机执行。

### 敲什么

```bash
# 1) 取 join 命令 + 上传证书 key（key 2 小时内有效）
JOIN=$(ssh root@172.23.163.99 'kubeadm token create --print-join-command')
CERTKEY=$(ssh root@172.23.163.99 'kubeadm init phase upload-certs --upload-certs | tail -1')

# 2) 两台控制面（注意 --apiserver-advertise-address 必须写各自内网 IP）
for pair in "cp-2 172.23.163.98" "cp-3 172.23.163.100"; do
  set -- $pair
  ssh root@$2 "kubeadm join 172.23.163.97:16443 $JOIN_ARGS --control-plane \
    --certificate-key $CERTKEY --apiserver-advertise-address $2 \
    --node-name $1 --cri-socket unix:///run/containerd/containerd.sock"
done

# 3) 五台 worker（并行）
for pair in "wk-1 172.23.163.101" "wk-2 172.23.163.105" "wk-3 172.23.163.104" \
            "wk-4 172.23.163.102" "wk-5 172.23.163.103"; do
  set -- $pair
  ssh root@$2 "kubeadm join 172.23.163.97:16443 $JOIN_ARGS \
    --node-name $1 --cri-socket unix:///run/containerd/containerd.sock" &
done
wait
```

### 看到什么算过

```bash

kubectl get nodes -o wide
```

## 4.8 etcd 三成员与每日快照

### 在干什么

确认三成员健康、quorum 正常；装每日快照定时任务。

### 敲什么

```bash
# 成员与健康
kubectl -n kube-system exec etcd-cp-1 -- etcdctl member list \
  --cacert /etc/kubernetes/pki/etcd/ca.crt \
  --cert /etc/kubernetes/pki/etcd/server.crt \
  --key /etc/kubernetes/pki/etcd/server.key

kubectl -n kube-system exec etcd-cp-1 -- etcdctl endpoint health --cluster \
  --cacert /etc/kubernetes/pki/etcd/ca.crt \
  --cert /etc/kubernetes/pki/etcd/server.crt \
  --key /etc/kubernetes/pki/etcd/server.key

# 快照脚本（3 台都装，任意一台都能备份）
apt-get install -y -qq etcd-client
cat > /usr/local/bin/etcd-snapshot.sh <<'EOF'
#!/bin/bash
set -euo pipefail
BK=/var/backups/etcd; mkdir -p "$BK"
TS=$(date +%Y%m%d-%H%M%S)
export ETCDCTL_API=3
etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save "$BK/etcd-$TS.db"
etcdctl snapshot status "$BK/etcd-$TS.db" -w table
find "$BK" -name 'etcd-*.db' -mtime +7 -delete
EOF
chmod +x /usr/local/bin/etcd-snapshot.sh

cat > /etc/systemd/system/etcd-snapshot.service <<'EOF'
[Unit]
Description=etcd snapshot backup
After=kubelet.service
[Service]
Type=oneshot
ExecStart=/usr/local/bin/etcd-snapshot.sh
EOF

cat > /etc/systemd/system/etcd-snapshot.timer <<'EOF'
[Unit]
Description=Daily etcd snapshot
[Timer]
OnCalendar=*-*-* 03:30:00
RandomizedDelaySec=300
Persistent=true
[Install]

EOF

systemctl daemon-reload && systemctl enable --now etcd-snapshot.timer
/usr/local/bin/etcd-snapshot.sh      # 先手动跑一次看输出
```

## 核心大坑（4 条，每条三行封顶）

```
现象：init 卡在 wait-control-plane，apiserver 容器反复 Exit
根因：scp 加密配置时目标目录还没建，文件没落盘，apiserver 找不到 encryption-provider-config
防：先 mkdir 再 scp，scp 后立刻 ls 确认（本次 cp-1 踩了，cp-2/cp-3 才修好顺序）

现象：haproxy 3.2 报警 "backend has the same name as frontend"
根因：frontend 与 backend 都叫 kube-apiserver
防：backend 改名 kube_apiserver_back（3.3 起直接不支持同名）

现象：keepalived 显示一切正常，但 kubectl 全失败
根因：只 track 网卡，没探 16443，haproxy 挂了 VIP 不漂
防：必须加 vrrp_script 探 16443 + weight -30

现象：join 报 x509，报错里不提"证书缺 IP"
根因：certSANs 漏了 VIP
防：init 时看 [certs] 那行，确认 172.23.163.97 在 IP 列表里
```
