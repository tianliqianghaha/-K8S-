## 13.1 为什么要这一层

```
没有它的时候
└─ Secret 只能 kubectl create 手动建，或者放 Git 里明文（绝对不行）
   结果：集群重建后密钥全丢；密钥变更没有版本记录；谁也说不清某个 Secret 从哪来

有了它之后
└─ 明文 → 加密成 SealedSecret（只能用这个集群的私钥解开）
   SealedSecret 可以直接进 Git，跟 Deployment 一样纳入 GitOps
   集群重建时：先恢复私钥 → Git 同步 → 所有 Secret 自动重生
```

一句话：**让"密钥"具备和"代码"一样的可版本化、可回滚、可审计属性。**

## 13.2 为什么控制器只跑 1 副本

这点容易被误认为"不够生产"，其实是正确做法：

```
Sealed Secrets 的加密密钥是一对 RSA
├─ 控制器首次启动时自己生成，存在 Secret sealed-secrets-key<随机后缀> 里
├─ 多副本时：谁先启动谁生成密钥，另一个副本读到不同密钥 → 两边解不开对方加的东西
└─ 官方建议：单副本 + 把密钥 Secret 备份好

它的可用性靠三件事保证（不是靠副本数）
① 控制器挂了不影响已有 Secret（Secret 已解封完毕，存在 etcd 里）
② 只有"新建 SealedSecret"时才需要控制器
③ 控制器被删 = ArgoCD 20 秒重建（第 6 章验过同类演练）
```

所以本章的高可用动作是**备份私钥**，不是加副本。

## 13.3 干净部署（两步，幂等）

### 第一步：装控制器

```bash
# 注意：2026 年仓库已从 bitnami-labs 迁到 bitnami，旧地址 404
REPO_URL="https://bitnami.github.io/sealed-secrets"
CHART_VERSION="2.22.0"
KUBESEAL_VER="0.41.2"
export KUBECONFIG=/etc/kubernetes/admin.conf

# 客户端（在能连集群的任意一台机器上装，也可以离线用 --cert）
curl -fsSL "https://github.com/bitnami/sealed-secrets/releases/download/v${KUBESEAL_VER}/kubeseal-${KUBESEAL_VER}-linux-amd64.tar.gz" \
  -o /tmp/kubeseal.tgz
tar -C /usr/local/bin -xzf /tmp/kubeseal.tgz kubeseal && chmod +x /usr/local/bin/kubeseal
kubeseal --version          # kubeseal version: 0.41.2

# 控制器
helm repo add sealed-secrets "${REPO_URL}"
helm repo update sealed-secrets
helm upgrade --install sealed-secrets sealed-secrets/sealed-secrets \
  --version "${CHART_VERSION}" -n kube-system \
  --set fullnameOverride=sealed-secrets-controller \
  --set resources.requests.cpu=20m --set resources.requests.memory=64Mi \
  --set resources.limits.cpu=200m --set resources.limits.memory=256Mi \
  --wait --timeout 5m

kubectl -n kube-system rollout status deploy/sealed-secrets-controller --timeout=180s
# deployment "sealed-secrets-controller" successfully rolled out
```

### 第二步：取公钥 + 备份私钥

```bash
# 公钥：加密用，可以随便传（没有它解不开，有它只能加不能解）
kubeseal --controller-name=sealed-secrets-controller --controller-namespace=kube-system \
  --fetch-cert > /etc/kubernetes/sealed-secrets.pem
openssl x509 -in /etc/kubernetes/sealed-secrets.pem -noout -subject -dates
# notBefore=Nov 20 05:57:19 2026 GMT
# notAfter= Nov 17 05:57:19 2036 GMT    ← 10 年有效期

# 私钥：丢了所有 SealedSecret 都变成废纸，必须备份
kubectl -n kube-system get secret -l sealedsecrets.bitnami.com/sealed-secrets-key=active \
  -o yaml > /etc/kubernetes/sealed-secrets-key.backup.yaml
chmod 600 /etc/kubernetes/sealed-secrets-key.backup.yaml
sha256sum /etc/kubernetes/sealed-secrets-key.backup.yaml
# a868da1ef7ba7eb8db9c2d6b1ff3576a8712285733e9b77e0e94de2b38530844   7086 字节
```

**备份要放三处**（本章实际做法）：

```
① 集群内  /etc/kubernetes/sealed-secrets-key.backup.yaml
② 本机    k8s-deploy/sealed-secrets-key.backup.yaml（运维笔记本）
③ 集群外  infra-01:/root/backup/sealed-secrets-key.backup.yaml
三处 sha256 必须一致；传异机前先确认文件是 LF 换行（CRLF 会让 YAML 里的 base64 值带 \r）
```

### 第三步（真正需要时）：恢复私钥

```bash
# 场景：整个集群重建，Git 里全是 SealedSecret，但新集群没有那把私钥
kubectl apply -f sealed-secrets-key.backup.yaml     # 先恢复密钥
kubectl -n kube-system rollout restart deploy/sealed-secrets-controller
kubectl apply -f secrets/                            # 再同步 SealedSecret，即刻解封
```

## 13.4 加密与迁移（一个脚本干完，带自动回滚）

脚本 `s20-seal-secrets.py` 的三个动作：

```
list                    列出纳管清单
seal <ns>/<name>        只加密，输出到 Git 工作副本，不动集群
migrate <ns>/<name>     加密 → 备份 → 删原 Secret → apply SealedSecret → 校验 sha256
                        任一步不一致立刻回滚（把备份 apply 回去）
```

核心片段（理解它比复制它重要）：

```python
# 1) 只取可加密的最小结构，丢掉 resourceVersion/uid/managedFields
body = {"apiVersion": "v1", "kind": "Secret",
        "metadata": {"name": name, "namespace": ns},
        "type": d.get("type"), "data": d.get("data")}

# 2) 用公钥加密（--cert 方式不需要访问控制器，CI 里也能用）
run(f"kubeseal --cert {CERT} --format yaml", stdin=json.dumps(body))

# 3) 删原 Secret 前先算指纹，apply 后再算一次，必须相等
before = sha256(data); delete_secret(); apply_sealed(); after = sha256(data)
assert before == after, "不一致就回滚"
```

## 13.5 Git 里存的是什么（安全边界）

```
SealedSecret 文件里只有
├─ metadata: name / namespace（严格绑定，拷到别的 ns 解不开）
├─ spec.encryptedData: 每个 key 一段 RSA 密文
└─ spec.template: 类型等非敏感元信息

实测：grep 明文密码 / token 在加密文件里出现次数 = 0
```

加密文件的 scope 是 **strict**（默认）：绑定 `namespace + name`。
这意味着**不能把 SealedSecret 复制到另一个命名空间复用**——这是特性不是缺陷，防止误用。

## 13.6 双重自愈实测

```
演练 A：删掉解封出来的 Secret
  kubectl -n secrets-demo delete secret demo-app-secret
  → Secret 被重建，耗时 3s        （控制器 reconcile 补回来的）

演练 B：删掉 SealedSecret 对象本身
  kubectl -n secrets-demo delete sealedsecret demo-app-secret
  → SealedSecret 被 GitOps 拉回，耗时 3s   （ArgoCD 从 Git 同步回来的）
  → 随后 Secret 也跟着重建（3s）

意义：无论删的是"结果"还是"声明"，都能自己恢复。
```

## 13.7 纳入 GitOps 的两个 Application

```yaml
# apps/sealed-secrets.yaml —— 控制器本身（chart 来自上游，values 来自 Git）
spec:
  sources:
    - repoURL: https://bitnami.github.io/sealed-secrets
      chart: sealed-secrets
      targetRevision: 2.22.0
      helm:
        releaseName: sealed-secrets
        valueFiles: [$values/addons/sealed-secrets-values.yaml]
        namespace: kube-system
    - repoURL: http://172.23.163.106:3000/gitea_admin/k8s-manifests.git
      targetRevision: main
      ref: values
---
# apps/secrets.yaml —— 所有 SealedSecret（指向 Git 的 secrets/ 目录）
spec:
  source:
    repoURL: http://172.23.163.106:3000/gitea_admin/k8s-manifests.git
    path: secrets
  syncPolicy:
    automated: {prune: true, selfHeal: true}
```

交棒时有一个必须动作：**清掉 helm 记录但保留资源**，否则 helm 和 ArgoCD 会抢同一个对象。

```bash
kubectl -n kube-system delete secret -l owner=helm,name=sealed-secrets   # 只让 helm 忘掉
```

## 13.8 部署时必须注意的四条（错一条就白做）

```
① 仓库地址变了
   bitnami-labs.github.io/sealed-secrets  →  404（2026 已迁移）
   正确：https://bitnami.github.io/sealed-secrets

② 私钥备份文件不能经 Windows 文本模式中转
   Python write_text 默认把 \n 转 \r\n，YAML 里的 base64 值会带上 \r → 解不开
   必须 open(..., newline="\n") 或先 sed -i 's/\r$//'

③ scp 不会自动建目录
   scp file root@host:/root/backup/x.yaml  → 目录不存在会静默失败
   先 ssh mkdir -p 再 scp

④ 迁移必须"先备份、后计算指纹、失败即回滚"
   顺序错了会在"原 Secret 已删、新 Secret 未生"的窗口里丢掉密钥
   本章脚本把窗口压到 1~2 秒，并且全程有备份兜底
```
