## 二、这套案例与「成功路径 SOP」的区别

```
成功路径 SOP
  给命令、给回显，读者照抄能装起来，但不知道"为什么这条命令在这"，
  也不知道"输出不对时该信什么"。

这份案例多两样东西
① 判官卡 —— 每个选择点给「探针 + 判据」，读者自己判断，不替他下结论
② 五段式 —— 每步都回答：在干什么 / 为什么现在做 / 在哪台敲 / 敲什么 / 看到什么算过

再加一条本册特有的
③ 双栏状态 —— 每章开头写清「本章已做 / 本章未做」，读者不会照着敲到一半发现断头
```

## 四、三条写作铁律（全册遵守）

```
① 正向内容不掺负面
   讲命令的段落不插"如果失败怎么办"；失败统一放每章末尾的「核心大坑」。

② 负面只留核心大坑
   一条三行封顶：现象 / 根因 / 怎么防。不写试错过程，不写心路历程。
   判据：删掉后不影响读者做决定的坑，直接删。

③ 每个外部依赖都给探针
   VIP 能不能抢、镜像能不能拉、S3 能不能写 —— 都给一条几分钟能跑完的验证命令。
   不写"应该没问题"，让读者自己确认。
```

## 七、本册的双栏约定

从 03 章起，每章开头都有这两块，含义固定：

```
【本章已做】 这次真实跑通的动作，含真实回显，可以直接照抄
【本章未做】 这次没做的动作，写明"卡在哪 / 缺什么 / 补的时候从哪开始"
```

未做不是省略，是把断点标出来——照册子走的人不会在最后一页才发现少了东西。
