## 15.1 两种灾备别搞混

```
业务级（第 4 章已做）                控制面级（本章补）
─────────────────────              ─────────────────────
对象：Deployment/ConfigMap/PVC 数据   对象：etcd 整个数据库
工具：Velero + Longhorn 备份          工具：etcdctl snapshot + etcdutl restore
问题：删了命名空间怎么活              问题：控制面全挂了怎么活
RTO：78 秒（实测）                    RTO：取决于快照大小与恢复目标

两者缺一不可：
只有 Velero → etcd 坏了连"要恢复什么"都不知道
只有 etcd 快照 → 能起控制面，但业务数据（PV 内容）还是要靠 Velero/Longhorn
```

## 15.2 一、Longhorn 快照策略（RecurringJob）

### 1.13 的关键变化：用组标签，不是卷名列表

```yaml
apiVersion: longhorn.io/v1beta2
kind: RecurringJob
metadata: {name: daily-snapshot, namespace: longhorn-system}
spec:
  name: daily-snapshot
  cron: "0 2 * * *"
  task: snapshot
  groups: [default]         # ← 组名，卷靠标签加入这个组
  retain: 3                 # 保留 3 份
  concurrency: 2
---
apiVersion: longhorn.io/v1beta2
kind: RecurringJob
metadata: {name: weekly-backup, namespace: longhorn-system}
spec:
  name: weekly-backup
  cron: "0 3 * * 0"
  task: backup
  groups: [default]
  retain: 2
  concurrency: 1
```

### 卷加入组的方式（kubectl label 会失败，必须 patch）

```bash
# 这个 key 带前缀含斜杠，kubectl label 对 --all 会输出 "not labeled" 静默失败
for v in $(kubectl -n longhorn-system get volumes.longhorn.io -o name); do
  kubectl -n longhorn-system patch $v --type merge \
    -p '{"metadata":{"labels":{"recurring-job-group.longhorn.io/default":"enabled"}}}'
done

# 验证（用 json 而不是 custom-columns，custom-columns 的转义容易看花）
kubectl -n longhorn-system get volumes.longhorn.io -o json \
  | jq -r '.items[] | .metadata.name + " " + (.metadata.labels["recurring-job-group.longhorn.io/default"] // "none")'
# pvc-16d7ab4d-... enabled      ← 8 个卷全部 enabled
```

### 真实触发验证（不等第二天 02:00）

```bash
# 把 cron 临时改成每分钟，证明"组标签 → job 真的选中了这个卷"
kubectl -n longhorn-system patch recurringjob daily-snapshot \
  --type merge -p '{"spec":{"cron":"* * * * *"}}'

# 2 分钟后
kubectl -n longhorn-system get snapshots.longhorn.io --no-headers | wc -l
# 7 → 25
kubectl -n longhorn-system get snapshots.longhorn.io --no-headers | sort -k3 | tail -3
# daily-sn-999a7e45-...  pvc-bbd81a5f-...  2026-11-20T06:54:16Z  true
# daily-sn-8cbe046b-...  pvc-fd64e773-...  2026-11-20T06:54:17Z  false   ← 正在创建
# daily-sn-a2346e1b-...  pvc-3f1e79d0-...  2026-11-20T06:54:18Z  false

# 立刻还原，别把它留在每分钟
kubectl -n longhorn-system patch recurringjob daily-snapshot \
  --type merge -p '{"spec":{"cron":"0 2 * * *"}}'
```

### 立即快照（不等 cron 的手动入口）

## 15.3 二、etcd 快照（打 + 校验）

```bash
TS=$(date +%Y%m%d-%H%M%S)

# 注意：etcd 镜像是 distroless，没有 sh，不能 kubectl exec -- sh -c '...'
kubectl -n kube-system exec etcd-cp-1 -- etcdctl snapshot save /var/lib/etcd/etcd-$TS.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
# Snapshot saved at /var/lib/etcd/etcd-20261120-145531.db

# /var/lib/etcd 是宿主机挂进来的，宿主机直接可见
mv /var/lib/etcd/etcd-$TS.db /var/backups/etcd/
ls -lh /var/backups/etcd/etcd-$TS.db
# -rw------- 1 root root 97M  Nov 20 14:55

# 校验（这一步不能省：快照损坏要提前知道）
kubectl -n kube-system exec etcd-cp-1 -- etcdutl snapshot status /var/lib/etcd/etcd-$TS.db -w table
```

```
┌─────────┬──────────┬────────────┬──────────┬─────────┐
│  HASH   │ REVISION │ TOTAL KEYS │ TOTAL SIZE │ VERSION │
├─────────┼──────────┼────────────┼────────────┼─────────┤
│ 96e616d │  165568  │    3351    │   102 MB   │  3.7.0  │
└─────────┴──────────┴────────────┴────────────┴─────────┘
```

**为什么 97MB 而早上的只有 1.3MB**：早上 10:08 那份是刚建好集群时打的（1.3M），
现在 3351 个 key、所有 CRD 与对象都在里面。这也说明：**快照体积会随集群长大，恢复 RTO 也跟着涨**。

## 15.4 三、etcd 恢复验证（本章最硬的一条）

### 为什么不在集群里直接恢复

```
直接原地恢复的风险
├─ 要把 etcd 的 --data-dir 指向新目录，等于让控制面"重生"
├─ 三台成员要一起动，动错一台就可能丢掉 quorum
└─ 恢复的是 14:55 的数据，生产此刻已经往前走了几百个 revision → 一定丢新数据

本章做法
└─ 旁路验证：在同版本的 etcd 镜像里，把快照恢复成一个独立实例（:12379），
   读回来跟生产对比。既能证明"快照可用"，又完全不碰生产。
```

### 完整流程

```bash
SNAP=/var/backups/etcd/etcd-20261120-145531.db
IMAGE=registry.k8s.io/etcd:3.7.0-0
WORK=/var/tmp/etcd-restore

# 1) 恢复成数据目录（etcdutl 在镜像里）
ctr -n k8s.io run --rm \
  --mount type=bind,src=/var/backups/etcd,dst=/snap,options=rbind:ro \
  --mount type=bind,src=$WORK,dst=/out,options=rbind:rw \
  $IMAGE restorer \
  etcdutl snapshot restore /snap/$(basename $SNAP) \
    --data-dir=/out/data --name=restore \
    --initial-cluster=restore=http://127.0.0.1:12380 \
    --initial-advertise-peer-urls=http://127.0.0.1:12380 --skip-hash-check

# 2) 用恢复的数据起独立实例（必须与上一步 name/cluster 一致）
ctr -n k8s.io run --net-host \
  --mount type=bind,src=$WORK/data,dst=/data,options=rbind:rw \
  $IMAGE restored-etcd \
  etcd --data-dir=/data --name=restore \
    --listen-client-urls=http://127.0.0.1:12379 \
    --advertise-client-urls=http://127.0.0.1:12379 \
    --listen-peer-urls=http://127.0.0.1:12380 \
    --initial-cluster=restore=http://127.0.0.1:12380 --initial-cluster-state=new &

# 3) 用一次性容器跑 etcdctl 读数（镜像里没有 shell，只能直接执行二进制）
q() { timeout 40 ctr -n k8s.io run --rm --net-host $IMAGE q-$RANDOM etcdctl --endpoints=http://127.0.0.1:12379 "$@"; }
q endpoint health
q get /registry/namespaces  --prefix --keys-only | grep -c '^/registry'
q get /registry/secrets     --prefix --keys-only | grep -c '^/registry'
q get /registry/deployments --prefix --keys-only | grep -c '^/registry'
q get /registry/pods        --prefix --keys-only | grep -c '^/registry'
```

### 回显（这是本章的核心证据）

```
=== 3. 健康检查 ===
http://127.0.0.1:12379 is healthy: successfully committed proposal: took = 4.487227ms
│ http://127.0.0.1:12379 │ ddd67b312462fd7b │ 3.7.0 │ 102 MB │ 25 MB │ 76% │ ... │ true │

=== 4. 统计快照内的业务对象 ===
  快照内：namespaces=18 secrets=47 deployments=37 pods=146
  生产集群：namespaces=18 secrets=47 deployments=37 pods=146      ← 逐项一致

=== 6. 抽查 Secret ===
  secret 前 24 字节: b'k8s:enc:aescbc:v1:key1:\x99'
```

最后那行很关键：**恢复出来的 etcd 里，Secret 依然是密文**。
这说明静态加密（第 2 章的 aescbc）是真的在 etcd 层做的，
所以就算有人把 etcd 快照偷走，没有 encryption-config 里的 key 也读不出内容。

### 一个必须知道的技术细节

```
用 etcdctl get -w json 取 k8s 对象，value 是 protobuf，不是 JSON
→ 直接 base64 解码后 json.loads 会报 "'utf-8' codec can't decode byte 0xc7"
→ 这不是恢复失败，是编码本来就不同
想验证"内容对不对"，用数量对比 + 关键词搜索（strings | grep podinfo）即可
```

## 15.5 四、硬故障演练（停 kubelet，不是优雅 drain）

第 6 章做的是 `kubectl drain`（优雅驱逐）。本章做更接近真实故障的版本：**直接停 kubelet**。

```bash
# 演练前：wk-5 上 24 个 Pod，承载 5 个 Longhorn 副本
systemctl stop kubelet

t=31s   wk-5   Ready    <none>   24 Running     ← 还在宽限期
t=61s   wk-5   NotReady <none>   24 Running     ← 触发 NotReady（node-monitor-grace-period 40s）
t=122s  wk-5   NotReady <none>   24 Running     ← Pod 仍未被驱逐（toleration 300s 还没到）

systemctl start kubelet
# 恢复后
wk-5   Ready
pods_on_wk5=24
nodes_ready=8
Longhorn 卷 robustness: 8 healthy
```

### 这个结果说明什么

```
① 节点失联判定约 60 秒（40s grace + 心跳周期），符合默认参数
② Pod 没有在 2 分钟内被驱逐 —— 这是对的
   默认 tolerationSeconds=300，意思是"给它 5 分钟自己回来"，避免网络抖动就大迁移
③ 恢复后 Pod 全部还在，没有重启、没有数据面中断
④ 8 个 Longhorn 卷全部 healthy —— 因为 3 副本，少一个节点不影响
```

### 如果要验证"驱逐 + 副本重建"，需要等 5 分钟以上

```
时间线（本集群默认参数）
0s      停 kubelet
~60s    Node NotReady，打上 node.kubernetes.io/unreachable 污点
300s    Pod 被驱逐（tolerationSeconds），在其他节点重建
~5-10m  Longhorn 检测到副本所在节点 down，标记 failed 并新建副本
```

第 6 章的 drain 演练已经覆盖了"优雅驱逐"这一半（drain wk-2 期间网关 5/5 全 200），
本章的硬故障覆盖了"节点突然失联"这一半。两半合起来才是完整的节点故障剧本。

## 15.6 部署时必须注意的四条

```
① Longhorn 组标签必须用 patch，不能用 kubectl label --all
   那个 key 含前缀与斜杠，kubectl label 会静默返回 "not labeled"

② etcd 容器是 distroless，没有 sh
   kubectl exec ... -- sh -c "..." 会报 exec: "sh": executable file not found
   直接写 kubectl exec ... -- etcdctl ...

③ ctr 起的容器与 SSH 会话同生共死
   ctr run -d 之后 SSH 一退出，容器就被杀 → 表现为"刚起来就没了"
   必须把「起 → 查 → 停」写进同一条命令

④ etcd 恢复实例的 --name 与 --initial-cluster 必须与 restore 时一致
   不一致会报 "member ... has already been bootstrapped"
```
