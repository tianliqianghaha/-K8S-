## 6.1 准备 Git 源（本次用 Gitea）

### 在干什么

起一个集群内 Git 服务，作为 GitOps 的真相源。

### 判官卡：Git 源用什么

```
选项 A 外部 GitHub/GitLab：最贴生产，但本次没有可用凭据
选项 B Gitea（集群内）：能练通全链路，缺点是"Git 与集群同生共死"
本次选 B，并把代价写进验收（集群没了 Git 也没了 → 所以生产要用外部 Git）
```

### 敲什么（★ 一定关掉默认的 HA 依赖）

```bash
helm repo add gitea-charts https://dl.gitea.com/charts/ && helm repo update gitea-charts

helm install gitea gitea-charts/gitea -n gitea --create-namespace \
  --set persistence.enabled=true --set persistence.storageClass=longhorn --set persistence.size=5Gi \
  --set gitea.admin.username=gitea_admin --set gitea.admin.password='<强密码>' \
  --set gitea.config.database.DB_TYPE=sqlite3 \
  --set postgresql-ha.enabled=false --set postgresql.enabled=false \
  --set valkey-cluster.enabled=false --set valkey.enabled=false --set redis-cluster.enabled=false \
  --set gitea.config.server.DISABLE_REGISTRATION=true

# Gitea 的 helm 默认给的是 headless Service，宿主/外部访问要补一个普通 Service
kubectl -n gitea apply -f - <<'EOF'

kind: Service
metadata: {name: gitea-http-lb, namespace: gitea}
spec:
  selector: {app.kubernetes.io/name: gitea, app.kubernetes.io/instance: gitea}

```

## 6.3 清单进 Git + 接 ArgoCD

```bash
# 1) 建仓库（公开只读即可，私有则要给 ArgoCD 建 repo secret）
GIP=$(kubectl -n gitea get svc gitea-http-lb -o jsonpath='{.spec.clusterIP}')
curl -u gitea_admin:<密码> -H 'Content-Type: application/json' \
  -X POST "http://$GIP:3000/api/v1/user/repos" \
  -d '{"name":"k8s-manifests","private":false,"default_branch":"main"}'

# 2) 推清单（本次放 3 个文件：gateway / netpol / certs）
cd /root/manifests && git init -b main && git add -A && git commit -m "init"
git remote add origin "http://gitea_admin:<密码>@$GIP:3000/gitea_admin/k8s-manifests.git"
git push -u origin main

# 3) ArgoCD 认仓库
kubectl -n argocd create secret generic gitea-repo \
  --from-literal=type=git \
  --from-literal=url="http://$GIP:3000/gitea_admin/k8s-manifests.git" \
  --from-literal=username=gitea_admin --from-literal=password='<密码>' \
  --dry-run=client -o yaml \
  | kubectl label -f - --local -o yaml argocd.argoproj.io/secret-type=repository \
  | kubectl apply -f -

# 4) Application（selfHeal + prune 是关键）
kubectl apply -f - <<EOF
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: {name: apps, namespace: argocd}
spec:
  project: default
  source:
    repoURL: http://$GIP:3000/gitea_admin/k8s-manifests.git
    targetRevision: main
    path: .
  destination:
    server: https://kubernetes.default.svc
    namespace: apps
  syncPolicy:
    automated: {prune: true, selfHeal: true}
    syncOptions: [CreateNamespace=true, ApplyOutOfSyncOnly=true]
EOF

kubectl -n argocd get application apps -o jsonpath='{.status.sync.status} {.status.health.status}{"\n"}'
```

看到什么算过：

```
本次真实结果：sync=Synced  health=Progressing（刚同步时）
```

## 6.5 巡检脚本 + 定时

### 在干什么

把"每天该看的东西"固化成一条命令，避免靠人记。

### 敲什么（要点）

```bash
# 巡检内容：节点 / etcd / apiserver / 证书剩余天数 / Longhorn degraded / PVC /
#          最近成功备份 / Alertmanager 副本 / 异常 Pod / CPU 水位
install -m755 patrol.sh /usr/local/bin/k8s-patrol.sh

cat > /etc/systemd/system/k8s-patrol.service <<'EOF'
[Unit]
Description=K8s cluster patrol
[Service]
Type=oneshot
ExecStart=/usr/local/bin/k8s-patrol.sh
EOF

cat > /etc/systemd/system/k8s-patrol.timer <<'EOF'
[Unit]
Description=Daily k8s patrol at 08:10
[Timer]
OnCalendar=*-*-* 08:10:00
Persistent=true
[Install]
WantedBy=timers.target
EOF

systemctl daemon-reload && systemctl enable --now k8s-patrol.timer
bash /usr/local/bin/k8s-patrol.sh
```

### 看到什么算过（本次真实输出）

```
-- 节点 --        [OK] 8/8 节点 Ready
-- 控制面 --      [OK] etcd 3/3 运行    [OK] apiserver 3/3
-- 证书 --        [OK] apiserver 还剩 364 天（另两张同）
-- 存储 --        [WARN] 2 个卷 degraded     [WARN] 1 个 PVC 非 Bound
-- 备份 --        [OK] 最近成功备份：2026-11-20
-- 告警 --        [OK] Alertmanager 运行 3 个
-- 异常 Pod --    [WARN] 1 个异常 Pod（logging/loki-1 ContainerCreating）
结论：有告警，见上
```

**判据**：巡检的价值不是"全绿好看"，是**把已知问题固定在报告里**，
不让人靠记忆判断"这条 WARN 是不是新出现的"。

## 6.7 把 addon 也纳入 GitOps（本轮补做）

### 在干什么

把原来用 helm 手装的 8 个 addon 全部写成 ArgoCD Application，
chart 来自上游、values 来自 Git（多源 Application），并按风险分两档同步策略。

### 为什么现在做

只接管业务的话，"删任意 addon 3 分钟重建"这条验收只在业务层成立，
集群一半的状态仍在 Git 之外——复现、审计、回滚都缺一块。

### 敲什么（模式：一个 addon 一个 Application，多源）

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: addon-cert-manager
  namespace: argocd
spec:
  project: default
  sources:
    - repoURL: https://charts.jetstack.io      # 源 1：上游 chart
      chart: cert-manager
      targetRevision: v1.19.1
      helm:
        releaseName: cert-manager
        valueFiles: [$values/addons/cert-manager/values.yaml]
        namespace: cert-manager
    - repoURL: http://<gitea>/gitea_admin/k8s-manifests.git   # 源 2：Git 里的 values
      targetRevision: main
      ref: values
  destination:
    server: https://kubernetes.default.svc
    namespace: cert-manager
  syncPolicy:
    automated: {prune: true, selfHeal: true}
    syncOptions: [CreateNamespace=true, ServerSideApply=true, ApplyOutOfSyncOnly=true]
```

values 怎么来的（关键：用 helm 的 computed values，保证与现状一致）：

```bash
helm get values <release> -n <ns> -a | sed '/^COMPUTED VALUES:/d; /^USER-SUPPLIED VALUES:/d' > addons/<name>/values.yaml
```

交棒（资源保留，只让 helm 忘掉）：

```bash
kubectl -n <ns> delete secret -l owner=helm,name=<release>
kubectl apply -f apps/<name>.yaml
```

### 分层决定（这才是生产做法）

```
自动同步（可 reconcile）
├─ cert-manager     无状态控制器
├─ kyverno          准入层，可滚动
├─ loki             采集/存储可重建
└─ metrics-server   无状态

手动同步（进 Git、状态可视、按维护窗口 apply）
├─ cilium           数据面，自动 reconcile 会重启 agent，风险与收益不成比例
├─ longhorn         存储层，涉及卷与实例管理器
├─ kps              有状态 + operator 复杂
└─ gitea            有数据（SQLite）

例外（已知项）
└─ eg（Envoy Gateway）：chart 只在 Docker Hub OCI 上，ArgoCD 匿名 HEAD 返回 401，
   应用状态表现为 Unknown；values 已在 Git，安装仍走 helm，不影响运行
```

```bash

```

```

addon-cert-manager     Synced      Healthy      ← 自动
addon-kyverno          Synced      Healthy      ← 自动
addon-loki             Synced      Healthy      ← 自动

addon-cilium           OutOfSync   Healthy      ← 手动（预期）
```

### 顺手修的一个"假告警"

云上没有 LB 实现时，Gateway 的 `Programmed` 永远是 False（原因是 AddressNotAssigned），
ArgoCD 会把整个业务 Application 判成 Progressing。这不是故障，是判定口径问题。
两种解法，本次选后者（侵入更小）：

```
解法一 给 Gateway 挂 EnvoyProxy 把 Service 改成 NodePort
  需要 EG 自有 CRD（envoyproxies.gateway.envoyproxy.io）；
  当初为绕开 Gateway API CRD 版本冲突用了 --skip-crds，把 EG 自有 CRD 也跳过了，
  补 CRD 时还会撞 262144 字节注解上限（要 --server-side）。
  本次试过，改完 Gateway 反而 Degraded，已回滚。

解法二 修 ArgoCD 的健康判定（本次采用）
  kubectl -n argocd patch cm argocd-cm → resource.customizations.health.gateway.networking.k8s.io_Gateway
  判据改成"Accepted=True 即 Healthy"，不再看 Programmed
  结果：apps 从 Progressing 变 Healthy
```

## 核心大坑（4 条，每条三行封顶）

```
现象：Gitea helm 一装就拉 3 个 Postgres + 3 个 Valkey，gitea Pod Init:CrashLoop
根因：chart 默认 HA 依赖，SQLite 单机要显式关掉 postgresql-ha / valkey-cluster
防：安装时把四个开关全关，DB_TYPE=sqlite3

现象：Gitea 的 Service ClusterIP 是 None，curl 报 Could not resolve host: None
根因：chart 默认给 headless Service
防：补一个普通 ClusterIP Service，或在集群内用 DNS 名访问

现象：Application 一创建就 OutOfSync，但集群里对象是对的
根因：对象由 helm/手工创建，缺少 ArgoCD 期望的注解，或清单与实际有字段差异
防：先让 ArgoCD 接管（sync 一次），之后所有变更走 Git

现象：删了 Deployment，5 秒就回来，但自己改的副本数也总被改回去
根因：selfHeal + prune 会把集群拉回 Git 状态
防：副本数也要写进 Git，不要临时 kubectl scale
```
