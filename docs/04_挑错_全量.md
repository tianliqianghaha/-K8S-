## 一、真产品问题（已修）

```
P1  计算题容差没考虑"显示时的四舍五入"
    现象：M05/s2 某 seed，标准答案 4.4444 显示为 4.4，玩家填 4.4 被判错。
    原因：容差只算了相对误差（0.5%），4.4 与 4.4444 差 1%，超过了。
    修法：容差取 max(相对误差, 半个最小刻度)。显示几位小数就容半个刻度。
    教训：凡是"先算再显示"的题，判定必须按显示精度兜底，否则会出现
          "标准答案自己都过不了"的荒唐情况。

P2  两个诊断案例只有三个选项
    现象：M14/s3（通信重叠）、M22/s3（离线批处理）各有一个案例写了 3 个选项。
    原因：手写案例时漏了一条，单测没管选项数量。
    修法：补齐第四个干扰项；契约测试加"选项必须 4 个"的硬断言。

P3  M03 的还原关在空答案时崩溃
    现象：契约测试传空对象，judgeA 直接读 ans.config.devices 抛异常。
    原因：judgeA 假设 answer 一定带 config。
    修法：入口先判空，返回"还没开始摆"。
    教训：判分函数必须对"什么都没填"免疫，这是玩家最常见的第一次点击。

P4  M03 的计算关与其他计算关契约不一致
    现象：契约测试报"缺单位"，因为 M03 的 scen 只有 fields[0].unit，
          没有顶层 unit；题面字段叫 question 而其他关叫 q。
    原因：M03 是手写的，工厂是后加的，两套字段名没对齐。
    修法：M03 补齐 unit 与 q，字段冗余但契约统一。
    教训：先手写再抽工厂，一定要回头把第一个实现改成工厂的形状。

P5  seed 与提示层级按 stage.key 存，跨模块串了
    现象：在 M00 的 s1 点了"换一题"，进 M01 的 s1 会沿用同一个随机 seed；
          M00 用完三层提示，M01 的 s1 一进来就是第三层。
    原因：state.seed / state.hintLv 的键只有 's1'，所有模块的 s1 共用一个格子。
    修法：键改成 "模块:关卡"。
    教训：只要有"多实例"的地方，键就必须带父级 id。这是最典型的命名空间疏漏。

P6  地图页脚文案过期
    现象：28 个模块全做完后，页脚还写着"灰色的层是这一轮还没写的"。
    修法：改成"七个平面全部开放，共 28 个模块、85 关"。
    教训：文案是代码的一部分，功能变了要一起改，否则就是自相矛盾。
```

## 二、测试自己写错（已改测试，产品不动）

```
T1  "题面泄露答案"检查把题面参数当成了泄露
    现象：M01 题面写"8 张 400G 网卡"，答案 400，被判泄露。
    修法：只检查"答案 + 单位"这种完整形式，裸数字不算。

T2  选项文案长度门槛 5 个字
    现象："内存不足""扩容"这类两三个字的选项被误判为"没有文案"。
    修法：门槛降到 2，中文两个字就是一个完整的选项。

T3  契约要求所有选择题项都有 why
    现象：M03 的 D 型选项用惩罚值判分，本来就没有 why。
    修法：D 型允许没有 why，但必须有 penalty。

T4  配对题的点击脚本点了已脱离文档的节点
    现象：先查左边节点、再查右边节点，然后依次点击；点完左边页面重渲染，
          右边那个引用已经不在文档里，点了不冒泡。
    修法：点完左边重新查右边。这是"先查询后操作"的老坑。

T5  契约测试没有引入 matrix 渲染器
    现象：M03 的侧栏用到 TopoRenderMatrix，Node 下未定义，报 reading 'html'。
    修法：测试里 require 渲染器。同时也提醒：side() 属于视图，纯逻辑测试要连视图一起载。
```

## 三、七个维度的结论

```
1 物理正确性
   ✅ 逐个复核了 24 个计算关的公式：
      PUE 倍数、6ND 算力、2(N−1)/N 通信量、KV cache 的 4×L×H、
      BDP 的带宽×RTT、超订比方向、盈亏平衡点。
   ⚠️ 诊断题里的实测带宽（PIX 24.7 / PHB 12.4 / SYS 12 GB/s）是参考机型基线，
      不可推导，已在题面标注"基线"字样，且不参与计算判分。
   📌 统一了口径：400G = 50 GB/s 在 M01/M10/M13 三处一致；跨 NUMA 统一 12 GB/s。

2 判定严格度
   ✅ 85 关的正确答案全部判过（10 个 seed 各一遍）。
   ✅ 空答案全部判不过，不白送分。
   ✅ 选择题满分项恰好 1 个（D 型允许 1 个次优也判过）。
   📌 D 型大多退化成"单选 + 代价解析"，只有 M03 真用罚分。已在台账注明。

3 题面真实度
   ✅ 命令输出保持真机格式：topo 带两列 Affinity、p2p 用设备矩阵、
      lscpu 有 NUMA node 段、XID 带 PCI 地址、事件带原始英文报错。
   ⚠️ 案例正文是中文叙述 + 英文原始日志混排，这是有意的：
      日志原文不能翻译，翻译了就失去可检索性。

4 认知负荷
   ✅ 每关只练一个判断，不叠加。排序题最多 8 项，配对最多 5 对。
   ✅ 五类零件有颜色条，五种渲染器各有独立手感（拖、填、选、排、连）。
   ⚠️ M13/M14 的计算题需要先记住公式。已在侧栏给公式，不要求背。

5 反馈质量
   ✅ 每个错项都有"为什么不成立"，不是只说"错了"。
   ✅ 计算题能识别三类典型错：差一半、差两倍、差 1000 倍。
   ✅ 排序题逐位指出"第 N 位应该是什么"，配对题逐项指出该连哪个。
   ✅ 提示三层：给方法 → 给一个具体的错 → 直接指到层级/数字。

6 可测性
   ✅ 契约测试遍历注册表，加模块不用改测试。
   ✅ 浏览器测试把 85 关真点一遍，不是调 API 作弊。
   ⚠️ 仍是 dump-dom，拿不到 console 错误；下一轮换 CDP。

7 跨模块一致
   ✅ 关系码、惩罚值、带宽口径三处单一来源。
   ✅ 契约测试扫描 undefined / null / ** / [object Object] 残留。
   📌 术语表还没建，"PXB"与"跨桥"仍混用。
```

## 四、明确不修（附理由）

```
N1  排序关的右侧栏信息偏少，只有一句话
    原因：排序题的"该看什么"已经写在题面里，再加一块会重复。
    如果以后加了提示链（比如依赖图），再补。

N2  D 型没全部用惩罚值
    原因：能算 penalty 的场景需要"方案可打分"，M22/M24 这类题目的方案是
          文字描述，硬套罚分反而假。用"单选 + 逐个说明代价"更诚实。
    记在台账里，避免下一轮误以为所有 D 型都该有 penalty。

N3  小测每题只有 2 道
    原因：关卡本身已经是 3 关，知识卡也给了三个坑。再加题会变成考试，
          而这里的目标是"上手"，不是"考核"。

N4  X1 命令行台 / X3 能力雷达没做
    原因：X1 需要一整套"假终端"，成本接近一个模块；X3 需要可视化，
          属于横向功能。这一轮先把 85 关的内容立住。
    诊断题的题面已经用了真机输出，算是 X1 的半成品。

N5  没有移动端适配
    原因：拖拽和排序在手机上体验差，硬做不如不做。桌面优先。
```

## 五、这一轮学到的两条

```
一、先手写一个模块、再抽工厂，是对的；但抽完必须回头把第一个模块改成工厂的形状。
    M03 的字段名（question / 无 unit）与新工厂（q / unit）不一致，
    直到契约测试跑到才暴露。一致性不是"设计出来的"，是"逼出来的"。

二、契约测试的价值不在于"测了多少"，而在于"加东西时不用改它"。
    27 个模块是一次性铺的，如果没有这套遍历式契约，
    光靠人点会漏掉一半的错（比如那两个只有三个选项的案例）。
```
