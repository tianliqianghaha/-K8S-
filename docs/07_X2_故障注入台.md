# X2 · 故障注入台

> 贯穿件。给定现象，让玩家按真实排障顺序走一遍：看现象 → 开终端取证 → 定根因 → 选处置。

---

## 一、为什么不做成"判断题"

单题的形态是"读完描述选一个"，那是阅读理解。真实排障是三步：

```
现象     用户能看到的那一层（作业日志、告警、监控摘要）
取证     自己敲命令确认（X1 终端）
判断     先定根因，再定处置
```

所以 X2 的每一关是**案卷**：现象给了，但只给到表面；证据在终端里，得自己查；判定分两段。

## 二、两段判定：查得出来 ≠ 修得对

```
根因错            → 0 分，并给出"证据指向的是哪个"
根因对、处置错     → 0.5 分，判不过，提示"这在实际工作里是最贵的一种错"
两段都对          → 1 分，解锁案卷笔记（概念 / 坑 / 复查顺序）
```

为什么不分两关做：分开就成了两道独立选择题，而现实里"查对了却修错"恰恰是最常见的失误——它必须被单独指出来。

## 三、二十四个案卷

```
L0 场地物理（3）  证据在带外，不在 shell
  F19  机柜电流顶到 87%，A 路空开跳过一次   四颗 PSU 全插同一路 PDU
  F20  八张卡一起降频，温度齐刷刷 91 度      进风 34°C，超过允许上限
  F21  A 路空开一跳，整机断电，作业全丢      两颗 PSU 在位且同路，冗余没建立

L1 硬件与整机（6）
  F01  一台机器上的卡少了一张          XID 79 掉总线
  F02  训练偶发 NaN，重启就好          XID 48 双比特 ECC
  F03  卡间通信变慢，偶尔卡死          NVLink CRC 增长 + XID 74
  F04  有一张卡只有一半带宽            PCIe 协商到 x8
  F09  新算子一上线就崩                XID 31 用户态越界（不是硬件）
  F10  吞吐掉了三成，温度却很高        功耗墙降频

L2 主机系统（3）
  F11  忽快忽慢，一颗核常年满载        网卡中断全落一颗核
  F12  跑二十分钟后整体变慢           swap 打满
  F13  升级驱动后卡间通信全变慢        fabricmanager 版本不匹配

L3 网络（4）
  F05  跨机带宽只有同机的一半          两张网卡都插 NUMA0
  F06  八张网卡只用了一张              NCCL 默认只挑一张 HCA
  F14  跨机通信直接卡在初始化          端口协议层 Down
  F15  带宽只有标注速率的一半          协商到 200G

L4 编排（5）
  F07  kubectl 全超时，容器还在跑      etcd 落盘被云盘 IOPS 卡住
  F08  每次都跑到第六小时 OOM          显存缓慢泄漏
  F16  8 卡作业排一小时，集群却说有空闲  资源碎片
  F17  Pod 一直拉不下镜像              节点到 registry 不通
  F18  训练跑到一半被驱逐              Evicted：节点内存压力

L5 平台运营（3）  证据在监控与账单
  F22  P99 翻了三倍，GPU 利用率只有 12%  CPU 预处理被 limit 卡住
  F23  账单翻倍，吞吐一点没涨          夜间不缩容，32 卡空转照计费
  F24  流量涨了三倍，HPA 一个副本都不加  requests 缺失，TARGETS 是 unknown
```

L0 与 L5 的取证口令不同：`ipmitool sdr`、`ipmitool sel list`、`prom query`、`bill report`、`kubectl get hpa / top pods`。这几卷在页面上会单独标出"取证终端（带外 + 监控）"，因为主机 shell 里根本看不到电力和账单。

设计上的两条刻意：

**一、干扰项必须"看起来也说得通"。** 把 DBE 当成学习率问题、把掉总线当成驱动问题、把 x8 当成降代、把 200G 当成交换机限速、把"利用率低"当成"卡不够"——这些都是真实排障里最常见的误判，不是随手编的错项。

**二、同一现象要能区分不同层。** F02 与 F09 都表现为"训练崩"，前者是硬件（XID 48），后者是用户态越界（XID 31），处置完全不同；F07 与 F17 都表现为"集群不干活"，一个是控制面磁盘，一个是单节点到仓库的路由；F22 与 F24 都表现为"延迟高"，一个是上游供数，一个是弹性没生效。

## 四、一条内容守则：现象里的数字，终端里必须查得到

这一条是 X2 与"编故事"的分界线。测试里逐条比对了：

```
F01  现象说少一张卡        → nvidia-smi 只列出 7 张，且提示"只列出 7 张"
F02  现象说 DBE +3        → nvidia-smi -q 的 Volatile Uncorr. ECC = 3
F05  现象说一半的卡跨 NUMA  → topo -m 里 GPU4-7 与网卡全是 SYS，且与模型算出的一致
F19  现象说 A 路 52.4A     → prom query 'pdu_current_a' 就是 52.4；sdr 里 PSU3/4 只有 60W
F20  现象说进风 34°C       → ipmitool sdr 里 Inlet Temp 34 degrees C，状态必须是 cr 不是 ok
F23  现象说账单 516,096    → bill report 由卡时 × 单价算出来，不是写死的字符串
F24  现象说 TARGETS 未知   → kubectl get hpa 显示 <unknown>/70%，describe 里有 missing request for cpu
```

如果现象里写了"CRC 4312"，那 `nvidia-smi nvlink -e` 就必须能查到 4312，且只有那一条链路非零。

## 五、L0 / L5 为什么要"监控视角"

L0 的证据在电力和散热，L5 的证据在监控与账单，这两类都不在主机 shell 里。硬塞进 `nvidia-smi` 就是编。

所以 X1 加了第三类现场数据 `world.mon`，包含三块：

```
bmc      ipmitool sdr / sel       进风温度、风扇、每颗 PSU 实际功率、硬件事件
metrics  prom query '<expr>'      Prometheus 即时查询（指标名 + label 过滤 + avg/max/min/sum）
bill     bill report --team X     卡时、有效算力、闲置成本
```

界面上给这三类各留了明确入口：案卷页左侧写明"证据在带外与监控里"，右上按钮变成"取证终端（带外 + 监控）"，终端横幅也会补一句"本卷有一部分证据在带外与监控里"。

## 六、和 X1 的关系

X2 没有自己的终端，它把案卷的 `world` 交给 X1：

```
案卷.world  →  TopoConsole.worldFor()  →  kind = 'scene'
横幅显示"已连接到 gpu-node-xx（本关的现场）"
```

也就是说：**X1 是工具，X2 是题库**。再加案子只需要写 `world` 和两段选项，不用碰终端。

## 八、第一轮挑出来的问题

```
1  破案后顶部计数不刷新
   现象：结算了，"已破"还是 0/8，要手动刷新页面才变 1/8。
   原因：计数只在 viewLab() 渲染时算一次，结算走的是 mountLab()，不重画头部。
   修法：给计数加 id，破案后单独更新那一处。
   教训：局部重渲染时，要清点"哪些数字是页面级、哪些是局部"，漏一个就不同步。

2  实验室的失败记录串进了错题本，链接拼成 #//X2/F06
   现象：能力雷达的错题本里出现一行 "X2 X2"，点进去是坏链接。
   原因：X2 用 PROG.record('X2', ...) 记进度，而 X2 不在 CATALOG 里，
         ability 取 plane 得到空串，拼出来的 href 就是 #//X2/...
   修法：错题本只收"注册表里存在的模块"，X2 的会话不计入。
   教训：跨系统的记录键必须带命名空间校验，否则一个自造 id 就能污染另一个页面。

3  结算后"提交"按钮还在
   现象：已经出结果了，按钮还亮着，点下去会用旧的选项再判一次。
   修法：结算态隐藏按钮 + submitLab 里加阶段守卫。
   教训：状态机要有"终态"，终态下所有输入都要么隐藏要么拒绝。

4  现象日志横向裁切
   现象：一行 NCCL 日志被切在面板边缘（跟之前模块页同样的问题）。
   修法：实验台也走 tpre-wrap 折行。
   教训：同一个坑在不同页面复现，说明当初的修法没有被抽成公共件——
         这次仍然只是"再修一处"，下次应该抽出统一的 pane 构造。

5  "现象内容太短"的判定过死
   现象：F04 的一条 P2P 告警只有 30 个字，被判"内容太短"，连改三个案卷。
   原因：单条告警本来就短，用单条长度当质量线是错的指标。
   修法：单条降到 24 字（防占位），另加"整卷现象总字数 ≥ 120"（防内容空洞）。
   教训：质量门槛要选对指标，否则会逼着人把好内容注水。
```

## 九、扩到 18 卷时补的能力与踩的坑
```
终端为了支撑新案卷，补了四处现场字段（都属于"现象里的数字必须查得到"）：
  · nvidia-smi -q 增加温度 / SM 频率 / Clocks Throttle Reasons  → 支撑 F10 功耗墙
  · /proc/interrupts 支持"四条队列全挤一颗核"的现场              → 支撑 F11
  · free -h 全字段可由现场驱动                                   → 支撑 F12 / F18
  · kubectl get pods / describe pod 支持事件与 Pending 无节点      → 支撑 F16 / F17 / F18

踩的坑：
1  kubectl get pods 的 NAME 列宽 10，写死之后 train-8card 直接把列挤歪
   修法：列宽放宽到 16，READY 按状态给 1/1 或 0/1。
   教训：凡是"名字长度不由自己控制"的表格列，宽度要按最长可能值留。

2  free -h 里 used / free 是写死的，只有 available 动态
   结果 F18 出现"used 812Gi + free 18Gi + cache 190Gi，但 available 只有 32Mi"的自相矛盾
   修法：全字段由现场给，默认值兜底。
   教训：一处动态、其余写死，比全写死更容易露馅——数字之间要自洽。

3  Pending 的 Pod 没有节点，describe 拼出了 <none>/10.0.3.21
   修法：无节点时不拼 IP。
   教训：占位符要单独处理，不能当正常值参与格式化。

4  F16 的 Pending Pod 没写 events，describe 里只显示默认的 "Started"
   结果：题目让你查"为什么排不上"，查了却看不到 Insufficient。
   修法：给 Pending Pod 补 FailedScheduling 事件，并加测试"证据链命令能查到关键行"。
   教训：案卷的每条证据链都要能在终端里真的跑出来——这条现在由 lab.test 兜住。

5  lab.test 的命令白名单只列了 10 条，新案卷用到 lscpu / free / interrupts / lsmod 就报错
   修法：白名单一次列全（16 条），并允许 kubectl describe pod <name> 与 nvidia-smi -q -i N。
   教训：白名单是测试的断言依据，也是它的盲区——加命令时要同步加白名单。
```

## 十、补 L0 / L5 这一轮踩的坑

```
1  prom 的封装把 "query" 当成表达式的一部分
   现象：prom query 'pdu_current_a' 报"解析不了"，因为只剥了 prom 前缀。
   修法：连续剥掉 prom / query 两层，再交给表达式解析。
   教训：包装命令要按"层"剥参数，不能假设用户只打一层。

2  监控数据默认值与案卷值混在一起，会出现"自相矛盾的现场"
   早期想法是每条命令各自兜底（没有 mon 就用默认值），
   结果 F19 的 sdr 显示 PSU3/4 只有 60W，而 bill 还是健康的 71% 利用率——
   两个数据源各说各话，玩家一对账就发现是编的。
   修法：把所有监控数据收进同一份 world.mon，案卷只写差异，其余从一份基线合并。
   教训：同一现场只能有一个数据源；多个兜底路径必然互相打架。

3  整机同一种病要能一次声明
   F20 是"八张卡一起被高温降频"，如果逐卡写 gpus:[{idx:0..7}]，
   既冗长又容易漏一张（漏了就会出现"7 张 91 度、1 张 62 度"的笑话）。
   修法：加 gpuAll 覆盖，一次改全部卡，再允许 gpus 单项覆盖。
   教训：批量语义要显式提供，"复制八遍"迟早漏。

4  深链与随机换卷打架
   加了 #/lab/F19 之后，"再来一个"按钮走 route()，路由又按 hash 把 F19 拉回来。
   修法：换卷时先把 hash 退回 #/lab，再让路由渲染。
   教训：引入深链后，所有"改变当前对象"的操作都要先处理 URL。

5  白名单又一次成了盲区
   lab.test 的命令白名单加上监控命令后，prom 的引号形式仍被漏掉，
   于是它没拦住任何东西，只是看起来拦了。
   修法：白名单 + 正则（prom query '<任意>'）两条一起判，并真的执行一遍看输出。
   教训：断言必须同时校验"声明"和"可执行"，只比对字符串等于没测。
```

## 十一、明确不做

```
· 不做"修好机器"的交互 —— 这一层练的是判断，不是执行
· 不做随机生成的故障 —— 故障是有名字的，随机拼出来的不可信
· 不把案子挂进七个平面 —— 它是横向练习，不占模块位（能力雷达不统计它）
· 不做计分排行 —— 已破 N/24 足够
```
