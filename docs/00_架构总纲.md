# AI Infra 认知训练场 · 架构总纲 v0.1

> 本文件是对 `github.com/tianliqianghaha/-K8S-/tree/main/ai-infra-topology-game` 的扩展设计。
> 原游戏只覆盖"单机拓扑还原"一个点，本文件要把它铺成一张覆盖 AI Infra 全链路的认知地图。

## 0. 需求拆解：你的两句话 = 三条约束

原话一："能够把所有涉及的 ai-infra 认知技能都组合进来。需要涉及整个网页和知识体系的架构层级。"

拆成两条：

- **覆盖面约束**：不是再加几个关卡，而是要做一张**自洽的知识地图**。每个格子都能进去练，格子之间不重复、不遗漏、有依赖顺序。
- **结构约束**：网页的**信息架构必须与知识层级同构**。点到哪一层，屏幕上出现的就是那一层的东西——在机房层不该看见 NVLink 带宽，在 NCCL 层不该看见机柜 U 位。层级混乱是这类教学产品最常见的死法。

原话二："后续每个知识模块需要详细实现，并且像你说的，每个做完之后进行挑毛病优化，争取精益求精。"

拆成一条：

- **过程约束**：每个模块必须走完「设计 → 实现 → 自测 → 挑毛病 → 优化 → 定稿」六步才算交付。禁止一次铺十几个空壳模块。宁可 28 个模块只做完 4 个，也不要 28 个都能点开但都经不起追问。

## 1. 先定义什么叫"认知技能"

知识点 ≠ 认知技能。知识点是"NVLink 4 是 900GB/s"，认知技能是"给你一张拓扑图，你说出哪两个设备之间会掉到 PCIe 带宽"。

本训练场只认四类**题型原子**，全部 28 个模块都由这四种拼出来：

```
A 还原型   给一堆零件 / 一张打乱的图 / 一段命令输出，摆对、连对、指对。
           考的是"空间关系是否真的进脑子了"。
           原型：原游戏的 L1。

B 诊断型   给现象（XID 报错、NCCL hang、训练慢 40%、GPU 掉卡），
           选根因，再选处置动作。考的是"会不会从症状倒推层"。
           注意：诊断必须能分层——同一现象在不同层的根因要能区分。

C 计算型   带宽 / 时延 / 通信量 / 显存 / MFU / 成本 / 端口耗时。
           所有数字必须能从题面参数**手算复现**，判定用公式算不用查表。
           原型：原游戏 L3 的 max(负载/带宽)。

D 决策型   在约束下选方案、配参数，存在真实取舍（快 vs 省、隔离 vs 利用率）。
           允许"次优但合理"的答案，按惩罚值给分，不能只有唯一解。
```

为什么要分开：同一个知识点出成不同题型，认知层次差三档。知道 PFC 是什么（记忆）→ 算出 PFC 风暴的触发条件（C）→ 看到"全网吞吐塌方但端口无丢包"判断是 PFC 反压（B）→ 在"关 PFC 保吞吐"和"开 PFC 保无损"之间选（D）。只有 B 和 D 才算真的懂。

原游戏的 `evaluateCluster` 已经是标准的 C 型；`bindingPenalty`（PIX=1 / PXB=2 / NODE=3 / SYS=6）是 D 型的雏形，可惜没接上。

## 2. 知识体系：七个平面，28 个模块

按"从墙上的插座到线上的 SLA"纵向排。**这是依赖顺序，不是教学顺序**——讲不清 PCIe，就讲不清 NCCL 为什么挑网卡。

```
L6  性能与故障      ← 站在所有层之上做归因，必须最后学
L5  平台与运营      ← 多租户、计量、推理服务、成本
L4  集群编排        ← K8s、调度、作业、弹性
L3  网络与集合通信   ← 网卡、无损、拓扑形态、NCCL
L2  主机系统        ← 内核、驱动、可见性、观测
L1  服务器与芯片     ← 整机、PCIe、GPU、NVLink
L0  场地与物理      ← 机柜、供电、制冷、布线
```

### L0 · 场地与物理（2 模块）

```
M00  机房与机柜
     核心认知点：机柜功率密度怎么算（8×H100 满配 ≈ 10kW/柜，风冷上限 15kW）
                 冷通道 / 热通道、冷板液冷与浸没液冷的边界
                 PUE、供电冗余（2N / N+1）、PDU 分路与单路过载
     A：给一张机柜立面图，把 4U/8U 设备按 U 位和功率预算摆进去
     C：给 GPU 数量与 TDP，算柜功率、算需要几路 PDU、算 PUE 后的电费
     B：给"某柜频繁触发 UPS 告警"，判断是功率超配还是分路不均

M01  布线、光模块与三网分离
     核心认知点：计算网 / 存储网 / 带内管理网 三网为什么必须物理分离
                 400G/800G 光模块（SR/DR/FR）、MPO 极性、AOC vs DAC 的传输距离
                 ToR 到 Leaf 的跳数、光纤配线架与标签体系
     A：给一台 8 卡机的 8 张网卡，把 8 条上联按 rail 接到正确的 ToR 端口
     B：给"某条链路误码率高但模块指示灯正常"，判断是极性接反还是脏端面
```

### L1 · 服务器与芯片（4 模块，原游戏所在地盘）

```
M02  整机解剖
     核心认知点：HGX H100 8-GPU 基板（4 颗 NVSwitch）、SXM vs PCIe 卡
                 CPU 双路 / 内存 8 通道 / NUMA 两个节点怎么分
                 本地 NVMe、RAID、BMC/IPMI/Redfish 带外管理
     A：给一台空机箱的槽位图，把 GPU/CPU/DIMM/NVMe/网卡插到正确位置
     B：给"OS 里只看到 6 张卡"，判断是基板供电、PCIe 链路还是 BMC 隔离

M03  PCIe 拓扑
     核心认知点：root complex → bridge → switch → endpoint 的树
                 Gen4/Gen5 x16 带宽（Gen5 双向 64GB/s，单向 32GB/s）
                 P2P 直通、ACS 阻断、Above 4G Decoding、BAR 空间
                 关系码全家桶：PIX / PXB / PHB / NODE / SYS
     A：拖拽还原拓扑（原游戏 L1 的核心，直接继承）
     C：给两颗 GPU 之间隔了几层 switch，算理论带宽与实测差距
     B：给"两张卡之间 P2P 带宽只有 6GB/s"，判断是走了 SYS 还是 ACS 没关

M04  GPU 架构
     核心认知点：SM / warp / Tensor Core / HBM 带宽 / L2 分块 / TMA
                 MIG 切分（1g.10gb ... 7g.80gb）与算力/显存的非线性关系
                 显存容量换算：81920MiB、HBM3e 141GB、B200 192GB
                 功耗墙与降频：TDP 700W、SM clock throttle、热点温度
     C：给模型参数量 + 精度 + 优化器状态，算训练显存与能否 8 卡装下
     B：给"GPU 利用率 98% 但吞吐只有基线一半"，判断是显存带宽还是降频

M05  NVLink 与 NVSwitch
     核心认知点：NVLink 4 每卡 900GB/s、18 link、NVSwitch 全互联
                 NVLink 域边界（域内 P2P，域外走 PCIe 或网络）
                 NVLink 5 / GB200 NVL72 的 72 卡单域、1.8TB/s
                 NVLink SHARP（交换机内归约）与 ring 的差别
     A：给 8 卡，判断哪两张能走 NVLink、哪两张必须过 CPU
     C：给 8 卡 all-reduce 数据量，算 NVLink 域内的理论下限
     D：选"4 台 8 卡机 + IB"还是"1 台 NVL72"，按作业规模与成本权衡
```

### L2 · 主机系统（4 模块）

```
M06  Linux 底座
     核心认知点：cgroup v2（cpu/memory 限额怎么落到容器）
                 hugepage（2M / 1G）、THP、swap 对训练的影响
                 NUMA 调优、isolcpus / nohz_full、irqbalance 与网卡中断绑核
     C：给"进程跨 NUMA 访存"，算带宽损失比例
     B：给"训练周期性卡顿 200ms"，判断是 THP 抖动还是 swap

M07  驱动与运行时栈
     核心认知点：driver / CUDA toolkit / cuDNN 版本对应关系
                 nvidia-peermem（GPUDirect RDMA 的开关）、gdrcopy
                 nvidia-fabricmanager（NVSwitch 必须，版本必须与 driver 一致）
                 容器内 toolkit 注入 vs 宿主机安装
     B：给"NVSwitch 卡不可用 / 只识别部分链路"，判断 fabricmanager 没起还是版本不匹配
     B：给"RDMA 落到 CPU 拷贝"，判断 peermem 没加载

M08  设备可见性与隔离
     核心认知点：CUDA_VISIBLE_DEVICES 与 NVIDIA_VISIBLE_DEVICES 的区别
                 MIG 实例的 UUID 映射、容器内编号漂移
                 time-slicing（假共享）与 MPS 的真共享
     A：给"容器里看到 2 张卡但 nvidia-smi 有 8 张"，还原是哪层做的裁剪
     D：多租户下选 MIG 还是 time-slicing，按隔离要求与利用率权衡

M09  单机观测与排障
     核心认知点：nvidia-smi / topo -m / dmon / query-gpu 各查什么
                 lspci -tv、numactl -H、ibstat / ibv_devinfo、ethtool -S
                 dcgm 指标、nsys / ncu 的取舍（时间线 vs 单核）
     题型：B 为主——给一段真实命令输出，五步定位法选出下一步该敲什么
```

### L3 · 网络与集合通信（5 模块）

```
M10  网卡与 RDMA
     核心认知点：ConnectX-6/7（400G = 50GB/s）、DPU/BlueField 的卸载边界
                 RoCEv2 报文封装、GPUDirect RDMA 的零拷贝路径
                 SR-IOV VF、多轨 multirail（8 卡配 8 卡）
     C：给 400G 卡 + 8 条流，算单端口打满需要多大 message size
     A：把 8 张 GPU 绑到 8 张网卡的正确 IB 设备上

M11  无损与拥塞控制
     核心认知点：PFC（按优先级反压）、ECN 标记、DCQCN 速率回调
                 PFC 风暴 / 死锁、headroom 缓冲区、watchdog
                 无损 vs 有损的代价：PFC 换来零丢包，代价是全网反压
     B：给"全网吞吐塌到 10%、端口计数器无丢包"，判断 PFC 风暴
     C：给带宽时延积，算需要多少 headroom buffer
     D：PFC+ECN 参数怎么配（阈值高低的两难）

M12  拓扑形态
     核心认知点：Spine-Leaf 两层 / 三层、超订比（1:1 vs 3:1）
                 Rail-optimized（同号 GPU 走同号 Leaf）、Torus、Dragonfly
                 超节点（NVL72 / 华为 CloudMatrix）与"域"的边界
     A：给 32 台 8 卡机，画出 rail-optimized 的 8 个 rail 平面
     C：给超订比，算最坏情况跨 spine 可用带宽
     B：给"同 rail 通信达标、跨 rail 只有 1/3 带宽"，判断超订

M13  NCCL
     核心认知点：Ring / Tree / CollNet / NVLS 四种算法的选择条件
                 channel 数与 SM 占用、NCCL_ALGO / NCCL_PROTO 强制
                 NCCL_IB_HCA、NCCL_SOCKET_IFNAME、NCCL_P2P_LEVEL、NCCL_TOPO_FILE
                 跨机走 IB 还是 socket、NCCL_DEBUG=INFO 怎么读
     C：ring all-reduce 通信量 2(N-1)/N × S，算 8 卡 / 64 卡的耗时
     B：给"NCCL 初始化卡在 30 秒后超时"，判断是网卡选错还是防火墙
     D：大 message 走 ring 还是 tree，按规模与拓扑选

M14  集合通信与并行策略
     核心认知点：AllReduce / AllGather / ReduceScatter / AlltoAll 的通信量
                 数据并行（AllReduce 梯度）、张量并行（AllReduce 激活）、
                 流水并行（点对点）、专家并行（AlltoAll）的通信特征
                 通信与计算重叠、ZeRO / FSDP 的分片收益
     C：给模型规模 + 并行切分方式，算每步通信量与是否成为瓶颈
     D：给"96 卡训 70B"，选 TP/PP/DP 的切分方案并说明为什么
```

## 3. 网页架构：与知识层级同构

### 3.1 信息架构（四层下钻）

```
入口：一张纵向剖面导航图（从机柜顶部一路切到机架、到主板、到芯片、到线缆）
  │
  ├─ 平面页  /#/L3
  │    列出本平面 5 个模块的卡片：难度、题型、前置模块、完成度
  │      │
  │      ├─ 模块页  /#/L3/M13
  │      │    左：题面（命令输出 / 现象描述 / 拓扑图）
  │      │    中：操作区（拖拽树 / 矩阵 / 连线 / 计算器 / 选择）
  │      │    右：实时反算结果 + 你的答案
  │      │    ↓ 提交
  │      │    判定反馈（错在哪一层、差多少、为什么）
  │      │    ↓ 通过
  │      │    知识卡解锁 → 3 道选择题 → 记入能力雷达
  │      │      │
  │      │      └─ 关卡页  /#/L3/M13/s2   同一模块的第 2 个 seed / 变体
  │      │
  │      └─ 排障台  /#/L3/diag            X2 在本平面的故障谱
  │
  └─ 能力页  /#/ability                   X3 雷达 + 补课路径
```

**层级铁律**：一个模块页只准出现本平面及以下的术语。M13 页面里说"这条流走 Leaf-3"可以，说"机柜 12 的 PDU 分路"不行。做不到就是层级泄漏，属于设计缺陷。

### 3.2 五种页面，不要更多

```
地图页   纵向剖面 + 28 个热度点（未通关 / 已通关 / 有错题）
平面页   模块卡片墙，带前置依赖箭头
模块页   三栏：题面 / 操作 / 反算。这是主战场，占 80% 的实现量
知识卡   概念 / 为什么长这样 / 三个常见坑 / 一条命令自己验证
能力页   七维雷达 + 错题本 + 推荐下一步
```

### 3.3 引擎分层（比原游戏多一层"领域"）

```
core/          与业务无关的地基
  rng.js           seed → 确定性随机（原游戏 rnd 的加强版，支持命名流）
  registry.js      模块注册表：declare(module) / get(id) / list(plane)
  grade.js         通用判分：逐项比对 → 差异列表 → 分数 + 归因
  progress.js      localStorage 进度、错题本、能力统计
  router.js        hash 路由

domains/       一个平面一个目录，一个模块一个文件
  L1/m02_machine.js   { meta, generator, judge, knowledge, hints }
  L3/m13_nccl.js
  ...

renderers/     表现层，按"题面形态"分，不按平面分
  board.js         拖拽层级板（继承原游戏 board/tray）
  matrix.js        拓扑矩阵表格（继承原游戏 player-topo）
  graph.js         力导向 / 分层拓扑图（L0、M12 用）
  terminal.js      X1 模拟终端
  calc.js          计算题输入器（带量纲校验）
  choice.js        单选 / 多选 / 排序

shell/         页面装配
  map.js  plane.js  module.js  card.js  ability.js
```

**关键决定：renderer 按形态分，不按平面分。** 原游戏把渲染写死在 level 1/2/3 三个 if-else 分支里，所以加第四关必须改三个函数。改成"模块声明自己用哪个 renderer"之后，加 28 个模块不用碰 renderers 一行代码。

### 3.4 模块契约（唯一的扩展点）

```js
{
  id: 'M13',
  plane: 'L3',
  title: 'NCCL',
  atoms: ['B', 'C', 'D'],
  requires: ['M03', 'M10', 'M12'],       // 前置模块，没通关给出提示但不拦
  renderer: 'terminal',                   // 或 board / graph / calc
  generate(seed) -> scenario,             // 纯函数，同 seed 必同场景
  judge(scenario, answer) -> {
      ok, score,
      diffs: [{ where, expected, actual, layer, why }],
      hintAt: '...'                        // 卡住时给下一步，不给答案
  },
  knowledge: { concept, why, pitfalls: [3 条], verify: '一条命令' },
  quiz(seed) -> [{ q, options, answer, why }]
}
```

`diffs[].layer` 是新增的关键字段——原游戏只告诉你"这格不对"，新版要告诉你"**错在 PCIe 层**"或"**错在 NUMA 亲和**"。这是"分层认知"落地的唯一抓手。

### 3.5 技术选型：故意保持"零依赖、双击能开"

```
语言      原生 JS（ES5 兼容写法 + UMD），不用框架
构建      一个 80 行的 node 脚本，把 shell + renderers + domains 拼成单文件 index.html
运行      dist/index.html 双击即开；开发期用 hash 路由 + 动态 <script> 注入
测试      engine 层 node 直跑；UI 层 CDP 连真实 Chrome（沿用原作者的 ui.test.js 思路）
持久化    localStorage；失败静默降级（file:// 场景）
```

理由：这个产品的读者是"想搞懂 AI Infra 的人"，不是"会 npm install 的人"。要求装 Node 才能玩，等于把一半人挡在门外。原作者这一点做对了，不要改。

## 6. 每个模块的交付标准（Definition of Done）

六步走完才算完，缺一步不算：

```
① 设计   填 docs/02_模块设计模板.md：认知点、题型、场景参数、判定口径、干扰项
② 实现   domains 下新增一个文件，不动其他文件；做到"删掉这个文件，站点仍能跑"
③ 自测   node tests/engine.test.js；seed 0~199 全扫，验证：场景合法、可解、无歧义
④ 挑错   逐条过 docs/03_挑错清单.md 的七个维度，每条写下结论（过 / 改了）
⑤ 优化   按挑错结论改，改完重跑 ③
⑥ 定稿   更新 01_模块台账.md 的状态与验收线
```

### 挑错清单（七个维度，每模块必过）

```
1 物理正确性   带宽、容量、功耗、时延的每个数字都要有出处或能推导
                典型错：把 PCIe Gen5 x16 的双向 64GB/s 当成单向
2 判定严格度   是否存在"合理但被判错"的答案；D 型题必须用惩罚值不用精确匹配
                典型错：原游戏网卡绑定只认 NIC0，答"绑到同 NUMA 的任一卡"算错
3 题面真实度   命令输出必须与真机字段、单位、对齐方式一致
                典型错：自造字段名、显存写 "80G" 而不是 "81920MiB"
4 认知负荷     是否要先学一套符号才看得懂；图里元素是否超过 7 个
                典型错：一张图同时画机柜、主板、NVLink 三层的连线
5 反馈质量     错了要说清"错在哪一层、差多少、为什么"，不能只说"不对"
                典型错：原游戏 L1 只给"对不上"，不给第几个格
6 可测性       每个判定分支都要有反例测试；随机生成必须可复现
                典型错：只测 happy path，错判分支没走过
7 跨模块一致   术语、量纲、关系码、颜色语义全局统一
                典型错：M03 叫 PXB，M12 叫"跨桥"，其实是同一件事
```

## 7. 原游戏盘点：能继承什么，必须重写什么

```
能直接继承
  ├ engine.js 的树模型（device → switch → bridge → CPU → NUMA）        → 进 core/model
  ├ relation() 的七个关系码与判定顺序                                   → M03 的判定内核
  ├ buildMatrix / compareMatrix 的"派生比对"思路                        → core/grade
  ├ evaluateCluster 的 max(负载/带宽) 木桶判分                          → M14 的 C 型内核
  ├ blankConfig 的"只留 NVLink，其余清空"设计                            → M03 出题手法
  ├ seed 决定一切的确定性生成                                            → core/rng
  └ 引擎与 UI 彻底分离、file:// 可用、CDP 真拖拽测试                      → 全局架构

必须重写
  ├ ui.js 里按 level 1/2/3 硬编码的三个 if-else 分支 → 换成模块注册表
  ├ 只有一句 hint 的提示系统                        → 换成"分层归因 + 下一步指引"
  ├ 没有知识卡                                      → 每模块必须有 concept/why/pitfalls/verify
  ├ bindingPenalty 写了但没接上                      → D 型题的判分入口
  ├ formatLscpu 里硬编码的 48 核                     → 按场景参数生成
  └ 纯 DOM 无动画、手机不能玩                        → 后期补响应式，不阻塞主线

明确不做
  ├ 不做真实集群连接（这是认知训练，不是运维平台）
  ├ 不做账号体系（localStorage 足够）
  └ 不做多人对战（会把实现成本翻三倍，收益不明）
```

## 8. 风险与取舍

```
风险一：28 个模块 = 28 倍的题面设计工作量
  对策：先做第 1 期 4 个，验证单模块工时，再决定是压缩到 18 个还是保持 28 个。
        宁可模块少而深，不要多而浅。

风险二：越往上（L4/L5）越难"动手玩"，容易退化成选择题
  对策：L4 以上的 A 型题改成"给一份真 yaml / 真调度日志，找出问题行"，
        保持"手上有东西可以指"的手感。

风险三：计算题的数字一旦错了，整门课的公信力就没了
  对策：所有 C 型题的答案只能由公式函数算出，禁止在题面里写死答案；
        单测里对每个公式做量纲与边界测试。

风险四：知识层级容易泄漏（在 M04 页面讲集群调度）
  对策：每个模块文件的 knowledge 字段只准引用 plane ≤ 自己的模块 id，
        加一条 lint 规则在 build.js 里拦。
```

## 9. 建议的第一刀

**M03 PCIe 拓扑**，不是 M00。

理由三条：

```
一、原游戏已解决 80%，能最快验证"注册表 + renderer 复用"这套新架构是否成立。
    如果连 M03 都无法独立成一个模块，说明架构错了，早发现比晚发现便宜。
二、M03 的判定内核（关系码 + 派生矩阵）是后面 M05 / M12 / M13 / M14 全部要复用的底座。
    先把它抽成 core，后面五个模块直接受益。
三、M03 天然覆盖 A / C / B / D 四种题型：
    A 拼拓扑、C 算带宽、B 判 P2P 掉速、D 选卡位方案。一个模块就能把四种 renderer 全跑通。
```

M03 做完并挑完毛病，再按 M02 → M04 → M05 顺序推，第 1 期收尾时把原游戏三关正式收编。
