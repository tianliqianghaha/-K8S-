## 一、物理正确性

```
F1  4 卡 PCIe 机型的 GPU 写了 700W
    问题：700W 是 H100 SXM 的功耗，PCIe 版是 350W。题面虽是 PCIe 机型，参数却抄了 SXM。
    处理：改 350W。（虽然界面不显示功耗，但设备数据是后续 M04 的输入，不能带错）

F2  跨 NUMA 带宽在两处不一致
    问题：计算题（s2 第三模板）说"跨 NUMA 实测 12 GB/s"，
          诊断题（s3 case1）的 P2P 表写 9.62 / 9.58 GB/s。
          同一个模块里两个数字对不上，玩家对账时会发现。
    处理：统一为 12 GB/s。诊断题的 P2P 表重写为 11.90~12.04 区间，
          并在解析里说明"正好是 PIX 的一半"。

F3  lscpu 固定 48 核
    问题：4 卡机型也报 CPU(s) 96、每路 48 核，与"4 卡 PCIe 机型"的定位不符。
    处理：按机型给核数（4 卡 2×32=64，8 卡 2×48=96），Affinity 列同步。

不修：
    实测带宽（PIX 24.7 / PHB 12.4 GB/s）是"参考机型基线"，不是可推导量。
    这类数字只在题面出现，且标明基线，不参与判分，允许有 ±5% 的实际抖动。
```

## 二、判定严格度

```
已修（实现阶段就发现，写在这里留痕）：
F4  D 型题的"每张卡走哪张网卡"取错了
    问题：原实现取"最后一张同 NUMA 的网卡"。
          当两张网卡都插 NUMA0 时，GPU0-3 会被判成走 NIC1（直连桥，PHB 2 分），
          而实际调度器会走更近的 NIC0（PIX 0 分）—— 无端扣分。
    处理：改成"每张卡取代价最小的网卡"，符合调度器行为。
          改完方案梯度稳定在 0 / 4 / 16 / 24。

不修：
    s1 不判零件标签（S0 和 S1 谁是谁）。标签是人为命名，拓扑才是事实。
    逼玩家猜标签属于无效难度，已写进设计表第五节。
    s4 半分阈值 8 是经验值，不是推导值。已在侧栏明示"多 8 分以内算次优"，
    玩家看得见判分口径，就不算黑箱。
```

## 三、题面真实度

```
F5  topo 少了 CPU Affinity / NUMA Affinity 两列
    问题：真机 `nvidia-smi topo -m` 末尾一定有这两列。少了两列，
          懂行的人一眼就知道是编的 —— 这属于公信力问题，不是美观问题。
    处理：补上两列，核数随机型走。

F6  P2P 输出不是真机格式
    问题：原来是 "GPU0 <-> GPU1  3.12 GB/s" 这种自造写法。
          真机 p2pBandwidthLatencyTest 输出的是设备矩阵。
    处理：四道题全部改成矩阵格式（Device to Device Bandwidth, N devices + 行列）。

F7  选项文案里残留 markdown 星号
    问题：`**第二颗**交换芯片` 原样显示成了星号。
    处理：去掉星号，改成纯文本。

不修：
    列宽用空格模拟 tab。真机是制表符对齐，视觉一致但不是字节一致。
    要 100% 还原得用 tab + 等宽字体，在网页里反而更难控，收益不成正比。
```

## 四、认知负荷

```
F8  五类零件在视觉上几乎同款
    问题：CPU / PCIe 桥 / 交换芯片 / GPU / 网卡都是同尺寸圆角块，
          只靠极淡的边框色差区分。这一关考的正是"谁在上层谁在下层"，
          层级却看不出来，等于让人摸黑。
    处理：每类零件加一条 3px 左侧色条（蓝=CPU、琥珀=桥、暗金=交换芯片、
          绿=GPU、紫=网卡），托盘里的零件也带同色条。

F9  Legend 的长行把表格顶出可视区
    问题：图例里 SYS / NODE 两行有 100 多个字符，属于 pre 块，
          把横向滚动宽度撑到 100 列，结果表格右侧的 NUMA Affinity 列永远看不见。
    处理：把"表"与"图例"拆成两块返回 —— 表保持 pre 不换行，
          图例用 pre-wrap 按栏宽折行。表本身 45 列，刚好放得下。

不修：
    8 卡版有 17 个零件，托盘和板面必然偏宽。靠色条 + 层级盒子缓解，
    不靠缩小字号解决 —— 字号再小就没人看了。
```

## 六、可测性

```
F11  浏览器测试只覆盖 4 卡机型
     问题：8 卡机型有三级交换嵌套，是渲染最容易崩的形态，却没被测。
     处理：补 4 条 —— 难版开关存在、切换后 gpuCount=8、托盘零件 ≥16、点击能解出。

F12  测试自己写错了两处（不是产品 bug，但要留痕）
     其一：解题脚本对"已就位"的零件重复点击，报"找不到框"。
           原因是 CPU 放进槽位后，那个空槽会被替换成 CPU 卡片 —— 这是正确行为。
     其二：在同一步里改 hash 立刻断言，读到的还是上一页。
           原因是 hashchange 是异步任务。改成两步走。
     处理：两处都改了测试，产品代码不动。

不修：
    E2E 用 Edge headless + dump-dom，不是 CDP。
    好处是零依赖、能进 CI；坏处是拿不到 console 报错和真实截图对比。
    这一轮的替代方案是人工看三张截图（s1 / s4 / 已解出的拼装区），
    下一轮 M02 开工前把 CDP 版补上。
```

## 一个"看着能跑但缺一半功能"的坑（单独记）

```
现象：第一版页面能打开、拼装区能拖、题面能显示，唯独右侧"你的拓扑表 · 实时反算"整块空白。
原因：board 渲染器在 mount 内部就先渲染一次，渲染完回调 onUpdate 去画侧栏，
      而此刻 view.ctrl 还没被赋值，侧栏拿不到答案对象，抛异常；
      异常发生在拼装区 HTML 已经写入之后，所以看起来"只有侧栏是空的"。
处理：onUpdate 里加 view.ctrl 存在性判断，并在 mount 返回后主动画一次。
教训：这类"部分成功"的 bug 最容易被人工验收漏掉 ——
      页面整体是活的，只是少了一块。只有断言"侧栏非空"才抓得住。
      所以 UI 测试里第一条就是 ok('右侧反算面板非空', ...)。
```
