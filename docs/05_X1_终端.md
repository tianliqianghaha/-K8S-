# X1 · 取证终端

> 贯穿件，不属于任何单一平面。目的：让"诊断题"从"读题猜答案"变成"先取证、再判断"。

---

## 一、它解决什么问题

之前的诊断关（30 关 B 型）全靠题面里写好的几行日志。玩家学到的是"读结论"，不是"取证"。

真实排障的顺序是：先敲命令 → 看到数字 → 缩小范围 → 再判断。X1 把这半步补上。

```
题面：现象 + 一小段输出
终端：可以继续敲 nvidia-smi / topo -m / lspci / dmesg / ibstat …
判断：拿着自己查到的证据去选根因
```

## 二、一条硬规则：不编造

终端有三层现场，来源不同，界面上必须说清：

```
① 主机侧（host）        卡的 ECC、PCIe 宽度、NUMA、内核日志
   真实现场（kind=model）   来自 M03 的拓扑模型。topo -m、lspci、网卡 NUMA
                            全部由配置算出，与题面矩阵逐字节一致（有测试比对）。
                            横幅写"本关的真实现场"。

   专属现场（kind=scene）   关卡在案例里声明了世界（哪张卡 DBE=3、哪张卡掉总线、
                            etcd fsync 30 秒…）。终端按声明渲染。
                            横幅写"本关的现场"。

   参考机型（kind=reference）本关没有机器现场。终端仍可用，但横幅明确写：
                            "下面是参考机型的输出，只能用来对照格式，不是题里的那台。"

② 带外侧（BMC）         ipmitool sdr / sel：进风温度、风扇、每颗 PSU 实际功率、硬件事件
                        来源是 world.mon.bmc，与主机侧互不影响。

③ 监控侧（metrics/bill） prom query / bill report / kubectl get hpa|top
                        来源是 world.mon.metrics 与 world.mon.bill。

②③ 合成一份 world.mon，案卷只写差异，其余从同一份基线合并——
   不允许每条命令各自兜底，否则两个数据源会互相打架（这是补 L0/L5 时踩过的坑）。
```

**宁可说"这不是题里的机器"，也不编一台出来。** 这条规则写在代码注释的第一行。

## 三、支持的命令

```
主机侧
nvidia-smi                卡、显存、利用率、温度、功耗（表格按列宽截断补齐，边框始终对齐）
nvidia-smi -L             列出 GPU 与 UUID
nvidia-smi -q             详细：ECC、retired pages、PCIe 宽度与代数
nvidia-smi -q -i <n>      只查某一张
nvidia-smi nvlink -e      每条 NVLink 的 CRC 计数（坏链路才非零）
nvidia-smi topo -m        关系码矩阵（有模型时与模型完全一致）
lspci -tv                 PCIe 树；没绑驱动的卡会标 [driver not bound]
lscpu / numactl -H        NUMA 节点、CPU 分布、节点间距离
ibstat / ibv_devinfo      IB 设备、端口状态、速率
dmesg                     内核日志（XID 都在这里）
free -h / uptime          内存与负载
kubectl get pods          Pod 列表
kubectl describe pod X    Pod 事件
etcdctl endpoint status   控制面 fsync 延迟（假死案的证据）
cat /proc/interrupts      中断落在哪些核
lsmod | grep nvidia       模块加载情况（peermem 在不在）

带外与监控（L0 / L5 的证据在这里）
ipmitool sdr              进风/出风温度、风扇、每颗 PSU 功率；超限标 cr，不在位标 ns
ipmitool sel list         硬件事件：AC lost、冗余丢失、过温、风扇
prom query '<expr>'       Prometheus 即时查询（封装 HTTP API 的小工具）
                          支持：指标名、{label="v"} 过滤、avg/max/min/sum(...)
bill report --team X      卡时、有效算力、闲置成本（金额由卡时 × 单价算出）
kubectl get hpa           TARGETS 那一列是不是 unknown，决定查指标还是查容量
kubectl describe hpa X    扩容事件（missing request for cpu 就在这里）
kubectl top pods          容器 CPU / 内存实际用量

help / clear
```

## 五、交互


## 七、这一轮挑出来的问题

```
1  表格边框不齐
   现象：nvidia-smi 的 | 和 + 对不上，列宽漂移。
   原因：手算 41/22/22 三段宽度，头部文案（Driver Version: 550.54.15）
         比段宽长，溢出 3 个字符。
   修法：row3 里先截断到列宽再补齐，物理上不可能对齐错。
   教训：字符画表格不要手算宽度，一律"先截断再补"。

2  测试里的 'con'.indexOf('on')
   现象：「终端可以收起」永远失败，「终端可以打开」永远通过——两个都是假。
   原因：class 是 "con"，indexOf('on') 命中的是 c-on。
   修法：改用 classList.contains。
   教训：断言类名必须用 API，不能做字符串包含。

3  测试页漏引 console.js
   现象：终端能打开但没有输出。
   原因：脚本清单只加到了 index.html，两个测试页各有一份独立清单。
   修法：补进两个测试页；同时让 app.js 兜底注入终端 DOM，测试页不再依赖手写标记。
   教训：同一份依赖出现在 N 个地方，就一定会在某一处漏掉——能注入就别手抄。

4  工厂丢了 world 字段
   现象：案例里写了 world，终端却一直显示"参考机型"。
   原因：pick 工厂在生成场景时按白名单挑字段，world 不在白名单里。
   修法：白名单补 world，并加测试"每关都能拿到现场"。
   教训：白名单式的场景构造，加字段时一定要同步改白名单——否则数据静默丢失。
```

## 七之二、补带外与监控时挑出来的问题

```
1  prom 封装把 "query" 当成了表达式的一部分
   现象：prom query 'pdu_current_a' 报"解析不了"。
   原因：只剥了 prom 前缀，剩下的 query '...' 直接进解析器。
   修法：连续剥两层（prom → query → 表达式）。
   教训：包装命令按层剥参数。

2  监控数据分散兜底 → 现场自相矛盾
   现象：F19 的 sdr 说 PSU3/4 只有 60W，账单却显示健康的 71% 利用率。
   原因：原打算每条命令各用各的默认值，两条命令各说各话。
   修法：全部收进 world.mon，一份基线 + 案卷差异。
   教训：同一个现场只能有一个数据源。

3  逐卡声明会漏
   现象：F20 是"八张卡一起降频"，逐卡写容易漏一张，出现 7 张 91°C、1 张 62°C。
   修法：加 gpuAll 批量覆盖。
   教训：批量语义要显式提供，"复制八遍"必漏。

4  深链和随机换卷打架
   现象：#/lab/F19 之后点"再来一个"，路由按 hash 又把 F19 拉回来。
   修法：换卷先把 hash 退回 #/lab，再走路由。
   教训：有深链之后，所有"换当前对象"的动作都要先处理 URL。

5  命令白名单成了盲区
   现象：白名单加了 'prom query ...' 的具体形式，换一条表达式就漏。
   修法：白名单 + 正则两条一起判，并且真的执行一次看输出。
   教训：只比对声明字符串等于没测，必须执行。
```

## 八、明确没做

```
· 命令补全 / 参数提示 —— 会让"敲命令"变成点菜单，失去训练意义
· 真实终端行为（管道、重定向、多命令） —— 只做单条命令
· 交互式 top / watch —— 静态快照足够回答问题
· 让玩家自己"修好"机器 —— 这一层是取证训练，不是运维演练
```
